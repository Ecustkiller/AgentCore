## 七、桌面端架构 ✅ 已确定

> 桌面端是唯一产品客户端（无独立 Web 端）。定位：**常驻本地、会协作的 AI 团队**——后台干活、碰本地文件、需要时敲你一下。

### 7.1 桌面价值主张（vs Web/PWA）

| 能力 | 网页天花板 | 桌面解锁 |
|------|-----------|---------|
| 异步任务 + 审批门禁 | 关标签即断 | 后台常驻 + 原生通知 + 审批闭环 |
| 全局热键召唤 | 埋在标签页里 | Spotlight 式悬浮窗 |
| 文件工作区 | 只能上传 | 本地文件直连 / Agent 读写磁盘 |
| MCP 工具层 | 浏览器跑不了 stdio | 本地 MCP 运行时（常驻进程池） |

被否决：PWA（无常驻/通知/文件）、全原生 UI（贵且漂移）、Tauri（团队无 Rust，WKWebView 有差异，备选）。

### 7.2 主进程架构

> **实现现状**：主进程当前创建窗口 + `registerAppProtocol()`（prod 经 `app://agentcore` 自定义协议加载 renderer，给其正式 origin 以受控 CORS/cookie，见下表）+ `registerFsIpc()`（→ 见代码 `apps/desktop/src/main/index.ts`、`main/fs-service.ts`）。`connection-manager`、`mcp-pool`、`local-store` **均未实现**。

```
主进程 (Node.js)
├─ ⏳ connection-manager  ← 独立 attention 轮询 + 通知（未实现）
├─ ⏳ mcp-pool            ← MCP server 常驻进程池（未实现）
├─ fs-service          ← 本地文件 IPC 服务（已落地）
└─ ⏳ local-store         ← sql.js，对话/消息读缓存（未实现）
renderer (Vite + React Router，本地)
└─ 桌面业务组件 + IPC ↔ 主进程；SSE 直连后端
         │ API (HTTPS)
         ▼
云端 api-server（LLM 推理 · Agent 运行时 · 数据持久化）
```

| 决策 | 结论 | 理由 |
|------|------|------|
| renderer 加载 | 本地（prod 走 custom protocol `app://`） | 给本地 renderer 正式 origin，CORS/CSP/cookie 可控 |
| SSE 连接 | renderer 直连后端（非 IPC 转发） | 长连接高吞吐，IPC 序列化开销不可接受 |
| 本地数据层 | ⏳ sql.js（读缓存优先，非离线写） | **未实现**；当前会话数据由后端 API 提供 |
| 组件策略 | 桌面端独立演进（非共享 packages 业务组件） | 桌面优先 = 自由演进 > 两端一致 |

### 7.3 安全基线

- `contextIsolation: true` + `sandbox: false`（当前）+ renderer 关 `nodeIntegration`
- 原生能力只经 preload 白名单 IPC 暴露
- httpOnly cookie 持久 session（Chromium OS DPAPI/Keychain 加密），不额外上 safeStorage

> 注：原设计目标 `sandbox: true`；当前 `webPreferences.sandbox` 为 `false`（→ 见代码 `main/index.ts`）。

### 7.4 OS 深度集成

- **资源管理器右键菜单**：安装期注册 shell verb，`--analyze <path>` 唤起，授权目录后 Agent 可读
- **文件关联双击**：electron-builder `fileAssociations`，`.md/.txt/.json/.csv/.yaml` 等
- **全局热键**：Spotlight 式召唤悬浮窗
- **Taskbar/Dock badge**：未读通知计数
- **深链**：`openDeepLink(target)` 统一入口，本地 renderer 已加载走 React Router，否则 `loadURL`

### 7.5 通知双通路

| 通路 | 覆盖场景 | 机制 |
|------|---------|------|
| 方向 A：SSE 桥接 | 桌面正持有 SSE 流 | `approval_required` / `checkpoint_required` / `message_end` 等事件桥接到原生通知 |
| 方向 B：Attention 轮询 | 未持有 SSE 流的盲区 | `GET /v1/attention`（45s 间隔），补 durable paused turns + pending approvals |

A+B 共用去重集（稳定 id），避免同一待办双弹。

### 7.6 自动更新

- 静默下载 + 用户决定安装时机
- 检查频率：启动 + 每 4h + `powerMonitor 'resume'`
- 远程熔断：后端 `updates_enabled = false` 才暂停（fail-open）
- 双通道：beta / stable；灰度分桶 `stagingPercentage`
- 平台：Windows + macOS（Win 优先），Linux 附带

### 7.7 关窗 = 隐藏到托盘

attention 轮询 + SSE 挂在渲染进程，`close` 默认 `preventDefault + hide`（仅 `before-quit` 放行销毁）。可配置：托盘开关「关闭时最小化到托盘」。

## 八、本地文件系统设计 ✅ 已确定

> 把本机磁盘文件提升为 **Agent 可直接读写的一等对象**。核心原则：**本地 = 唯一真身，云端不持久化文件字节**。

### 8.1 隐私边界

| 边界 | 含义 | 策略 |
|------|------|------|
| **at-rest** | 不把文件字节/正文存进服务端 | 默认守住；用户显式「备份/分享」为知情例外 |
| **in-transit** | Agent 读文件时正文临时发给 LLM | 接受（同 Cursor 把代码发给模型） |

铁律：Agent 要理解文件 → 正文必须进 prompt；at-rest 默认不外发。

### 8.2 Client-Tool 桥架构

> **实现现状**：`client_tool_requested` SSE 桥、IPC 回传 `client-tool-result` **均未实现**（→ 见代码 `services/streamConversation.ts` 事件类型预留）。

云端运行时 + 本地文件桥（与 Cursor / Claude Desktop 同构）：

```
云端 executor 命中 client-bound 工具（文件读写）
  → emit SSE client_tool_requested{op, params}
  → Redis BLPOP 阻塞（keyed by conv_id + tool_call_id）
[SSE] → Electron 渲染层 → IPC → 主进程 fs-service 在授权根内执行
  → POST /v1/conversations/{id}/client-tool-result 回传
  → resolve → 续跑 ReAct
```

设计选择：
- **原地阻塞而非 durable 快照**：文件读写秒级；桌面须在线才能执行——断连即 cancel、本轮干净失败
- **不落 Postgres**：client_tool 请求是临时态，持久化会把路径写库违 at-rest，只用 Redis
- **安全护栏**：桌面 fs 桥的授权根 allowlist + realpath 边界校验，云端视为不可信请求方

### 8.3 对话产物落点

由「本轮有无可写本地根」一个开关决定：

| 运行语境 | 落点 |
|---------|------|
| 桌面 + 有可写根 | 只挂本地写工具，产出写本地原件 |
| 桌面 + 无根（随手新对话） | 懒创建：首次写文件时在默认根创建目录，之后同上 |
| 无桌面（headless / 自动化） | 禁产：不挂写工具；要产物须声明显式出口（webhook 等） |

### 8.4 文件树设计原则

- **一棵本地主树**：以本地授权目录为根，非"本地/云端两个平级源"
- 无全局树 store——各目录节点各自懒读子项并 watch，互不串扰
- 选中/改名/新建态由组件局部持有、单向下传
- fs 操作在 IPC 边界返回判别结果（`{ ok, reason }`）而非抛异常
- `fs.watch` 跟随展开状态，磁盘变更即刷新

### 8.5 本地目录授权模型

- 授权 = 持久契约（非会话参数）——per-target 显式授权
- 作用域变更对用户与 Agent 同等显式
- 兜底只追加、不替换、留痕迹
- 绝对路径不出本机（错误语言按受众分层）

### 8.6 项目身份模型（dotfile）

> **实现现状**：`.agentcore/project.json` dotfile **未实现**。

**本地文件夹 = 项目**：文件夹根下 `.agentcore/` dotfile 记录云端项目编号（类比 `.git/`），桌面打开即认、换机即认、零绑定仪式。

```
<项目文件夹>/
  .agentcore/
    project.json     # { schemaVersion, id, name, createdAt }
    rules/*.md       # 文件夹级规则
    memory/*.md      # 文件夹级记忆
```

**决策：云端权威 + dotfile 记号**（否决本地发号）。云端继续发编号、管对话，dotfile 只负责"记号"——保留手机/网页/平板等无本地文件夹设备的接入能力（纯本地身份会从结构上焊死手机端）。

| 旧（per-device 绑定） | 新（dotfile 自带） |
|---|---|
| 映射存设备 `preferences`，换机丢失须重绑 | dotfile 跟文件夹走，同步即带、打开即认 |
| 解析方向：云端号 → 查设备表 → 路径 | 解析方向：打开路径 → 读 dotfile → 云端号 |

**复制文件夹（同号）**：学 Git 对 `cp .git/` 的态度——允许两副本指同一云端项目，并发写云端时复用三方冲突检测（冲突保留两份、绝不自动覆盖）；要独立副本须显式"另存为新项目"。

### 9.2 Store 关键拆分

**run 树独立成 store** 是核心决策：执行态（编排步骤 + 委派子 Agent 统一为一种 run）与消息态正交，分开既防 chat reducer 膨胀、又让 run 按 messageId 隔离。

### 9.3 按 messageId 隔离执行态 ✅ 已落地

> 执行态按 **assistant 消息 id** 分片：`useExecutionStore.byId: Record<messageId, ExecutionRuntime>`，每条多 Agent 回答各持自己的协作图。实时回合流入其消息槽，历史回合从持久化日志重建——live 与 replay 走**同一 fold**。

**核心决策**：键控从 `conversationId`（每对话单槽）改为 `messageId`（每回答一槽）。否则同对话连发多回合时第二回合会读到上一回合残留（节点串台），且历史回合无图可回看。「团队战报按回答留存 + 刷新可回看」是产品定位（§七）在状态层的延伸。

- **回合归属**：SSE dispatch 据 turn 的 `conversationId` 解析其 live assistant 消息 id（`lastAssistantMessageId`），把 run/tool 帧路由进该消息槽——一个回合的事件全归属于 `message_start` 开出的那条气泡。
- **持久化**：后端 `message_end` 把该回合的 run/tool 事件原样存进 `messages.runs`（`{events, finish_reason}`，见后端 `pipeline.py` / `repositories.py`），随回答落库。
- **回放**：重载对话时 `toMessage` 把 `runs` 映射到 `message.runs` 并据首个 `run_plan` 标出 `executionId`；inline 图 `hydrateFromJournal` 把日志经 `frameFromEvent` / `planFromRunPlan` 折叠回执行槽（**幂等**——已有 plan 的 live 槽不被覆盖）。
- **单一 fold**：`projectExecution(plan, frames, status)` 是纯函数，实时流与历史回放共用——无「实时态 vs 历史态」两套渲染路径。
- **作用域传递**：`ExecutionScopeContext` 把 `messageId` 透传给子树（状态轨 / 画布 / 时间线 / 节点详情，含全屏 portal——context 穿透 portal），各 graph hook（`useProjectedExecution` / `useActiveExecField` / `useMessageExecution`）据此读对应槽；detail-panel 是全局组件，故其 tab 显式携带 `messageId`。

**⏳ 已知限制**：历史执行槽的内存回收（浏览大量对话后 `byId` 累积）未做——单对话现为游标窗口（§9.7），上滚可不断加载更早回合，执行槽随浏览深度增长；开发期可接受，后续可在会话切走时连带释放其消息的执行槽。

### 9.4 单一数据源、两层投影 ✅ 已落地

聊天区分两层：**inline 信号层（状态轨 + 协作图）** 和 **详情面板层**：

- 两层同口径取数——都投影同一消息的执行槽（`projectExecution`），实时槽与历史回放（hydrate 后）走同一 fold，无「实时 vs 快照」分支
- 面板 tab 只存 `{messageId, runId}` 引用不存数据（渲染时现从执行槽取），流式中槽更新 → 面板自动跟随；槽里已无该 run 的 tab 自动隐藏
- 编排步骤与委派子 Agent 是同一种 run，面板用同一套下钻（不区分来源）
- **节点高亮一面一源**（派生而非同步）：内嵌图高亮节点 = 面板**当前激活 run-detail tab** 的 run（点节点 → 开/激活该 tab → 图自动亮；切 / 关 tab、关面板都自动跟随）；全屏 overlay 用自身的 `selectedRunId`（点节点 pin 时顺带 seed，最大化即落在最后查看的 run）。**否决**在 `setActiveTab`/`closeTab` 里反向 `selectRun` 同步——跨 store 对账会散落「清上个激活面、判跨回合」特例且留悬挂高亮（踩补丁绊线）

### 9.5 事件归属显式化

回合归属在 SSE 入口一次性确定——dispatch context 携带该回合的 `conversationId`：chat 类事件据此写会话切片（§9.6），run/tool 类事件据此解析该回合的 live assistant 消息 id 写对应执行槽（§9.3）。无差别注入 = 新增事件类型零改动自动路由，无「可路由事件白名单」需维护。

### 9.6 按 conversationId 隔离会话运行时（后台 turn 存活）✅ 已落地

> 会话运行时（消息流 + 生成态 + 错误/重试 + abort + 审批门禁）按 `conversationId` 分片存储，而非单一「活动会话」全局态——让一个回合在用户切走后仍在后台跑完。（协作图执行态按 `messageId` 分片，见 §9.3。）

**核心决策**：发起回合后切到别的对话，该回合不被打断——继续流入它自己那片切片的气泡 / 协作图，切回即见。这是产品定位「常驻、会协作的 AI 团队，后台干活」（§七）在状态层的落地。

**被否决（旧行为）**：`switchConversation` 切走即 `abort` 当前 turn 并重置其切片。否决理由：与「后台干活」心智冲突——切走就断 = 逼用户盯屏等结果。

| 维度 | 规则 |
|---|---|
| 路由不变量 | 所有回合写入按 turn **自身的 `conversationId`** 路由（非当前活动键）。SSE 分发把 turn 的 `conversationId` 注入 dispatch context，各 handler 一律写该会话切片；视图交互（focus / playhead / 手动清错）省略 id，作用于屏上会话 |
| 内存有界 | 闲（无生成中 **且** 无挂起审批）切片即**释放**（删除），下次切回由页面加载守卫从服务端重拉历史；忙片**保活**。释放触发于两处：**切走**时（释放离开的会话）+ 后台回合**跑完**时（`message_end` / 内联 `error` 释放非活动会话——否则它会一直缓存到下次切到再切走）。上界 = 活动会话 + N 个**在跑**的后台 turn，不随浏览历史无限累积 |
| 跨 store 一致 | `conversation` / `approval` 按 `conversationId` 分片（审批项带 `conversationId` 标签、按会话清理）；`execution` 按 `messageId` 分片（§9.3），SSE 据回合 `conversationId` 解析其 live 消息 id 落对应执行槽。后台 turn 的消息、图、审批各归各位互不串台 |

与 §9.3 关系：两者均**已落地**且正交——本节「按会话」隔离让回合在后台跑完（`conversation`/`approval` 按 `conversationId` 分片）；§9.3「按 messageId」让同对话每条回答各持自己的执行槽（`execution` 按 `messageId` 分片）。

→ 见代码 `apps/desktop/src/renderer/stores/`

### 9.7 消息载入模型：最新窗口 + 双向无限滚动 + 命中定位 ✅ 已落地

> 对话消息不再「一次性拉最旧 N 条」，而是**游标窗口**：打开载入最新一窗，向上滚加载更早、向下滚加载更新，或跳到「以某条消息为中心」的窗口（搜索命中定位 / load-around）。窗口边界由 `has_more_before/after` 驱动无限滚动。

**核心决策**：会话切片的 `messages` 是一段**连续窗口**而非全量历史。旧实现进对话只拉「最旧 100 条」（`asc + offset 0`），长对话看不到最新、命中窗外的消息静默失效；窗口化后既能直达最新、又能让搜索**命中必达**。这是 §9.6「会话运行时」之上的取数模型细化。

- **后端契约**：`GET /v1/conversations/{id}/messages?limit&before&after&around` → `{data, total, has_more_before, has_more_after}`。四参互斥，按 `around → before → after → 最新` 解析；游标 = 消息 `created_at` 严格 `< / >`（同秒并列是 MVP 容忍简化——回合间隔秒级、非高频 IM）。`around` 两侧 `has_more` 都计算，单向查询只计算移动方向那侧。→ 见后端 `repositories.py` 的 `window_around / list_before / list_after`。
- **前端窗口态**：会话 runtime 加 `hasMoreBefore/After` + `loadingOlder/Newer`；mutator `setMessageWindow / prependMessages / appendNewerMessages`（按 id 去重）。取数与编排放 `services/messages.ts`（`fetchMessageWindow / loadOlder / loadNewer / loadLatestWindow / jumpToMessage`），不进 store——沿用「fetch 在 service、store 只存状态」。
- **滚动机制**：AI 对话专用 `lib/useChatScroll.ts`（取代 `useStickToBottom`，IM 仍用后者）：贴底跟随**仅在 HEAD**（`hasMoreAfter=false`）才生效；上滚加载用**滚动锚定**（prepend 后按 `scrollHeight` 差回填 `scrollTop`，视口不跳）；下滚加载更新回合。
- **命中定位（load-around）**：`jumpToMessage` 命中在当前窗内 → 直接 focus；窗外 → 拉 `around` 窗换入再 focus（`requestAnimationFrame` 等渲染后滚动）。**跨对话**命中用 `conversation` store 的 `pendingFocus`：面板先设意图再导航，`ConversationPage` 载完窗口后消费，避免与页面自身拉取竞态。
- **HEAD 不变量**：live 回合只能追加在真实队尾。读历史窗口（命中跳转会留下 `hasMoreAfter=true`）时发送，`MessageInput` 先 `loadLatestWindow` 回到最新窗再追加；`truncateAfter`（重生成 / 编辑）顺带清除残留 `hasMoreAfter`。

→ 见代码 `services/messages.ts`、`lib/useChatScroll.ts`、`stores/conversation.ts`、`components/chat/ChatView.tsx`

### 9.8 全局搜索（Tier 1：跨对话 / 消息 / 文件夹关键词检索）✅ 已落地

> `Ctrl/Cmd+K` 命令面板从「客户端按对话标题过滤」升级为**后端关键词全局搜索**：一个查询覆盖当前用户的对话标题、消息正文、文件夹名，分组返回。UX 见 [`前端UX设计.md` §十四](/docs/04-前端/前端UX设计.md)。

- **后端契约**：`GET /v1/search?q&limit&types` → `{query, sections:[{type, items}]}`，`type ∈ {conversation, message, folder}`，空分组省略。消息命中带 `snippet` + `match_start/end`（snippet 内偏移，前端直接高亮、不二次查找）。→ 见后端 `routes/search.py`、`schemas.py`。
- **检索决策**：用 **ILIKE 子串**（量级到了再上 `pg_trgm` GIN），**不用 `to_tsvector`**——stock PG 不分中文词，FTS 对中文正文大面积漏召回；用户输入的 `% _ \` 统一转义为字面量（`repositories._ilike_pattern`）。
- **owner-scoped**：消息表无 `user_id`，按用户归属须 JOIN `conversations`（顺带排除软删 + 隐藏的 handoff 宿主对话），防 IDOR。
- **同 session 顺序查**：一次请求内三个 repo 共享同一 `AsyncSession`（非并发安全），三查询**顺序 await**——MVP 量级足够。
- **前端**：`services/search.ts` 按 keystroke 序号丢弃过期响应，配合 300ms 防抖 + 最短 1 字，不另设限流；`CommandPalette` 空查询显示最近对话（客户端），非空走后端分组结果 + 扁平键盘导航。跳转：对话 → 打开；消息 → 打开 + 命中定位（§9.7）；文件夹 → 跳转对话管理页 `/conversations`（经路由 state 传目标），页面选中 + 闪烁该文件夹（取代早期侧栏 `focusFolder` 聚焦，已随侧栏精简移除）。

→ 见代码 `services/search.ts`、`components/layout/CommandPalette.tsx`、`stores/folders.ts`

### 9.9 错误处理与提示分诊（统一错误契约 → 分场景承载）✅ 已落地

> 后端是错误契约的唯一真相源：每个失败都是 `{ error: { code, message } }` + HTTP status（冷却类带 `Retry-After`），由全局 handler 在 `AgentCoreError` 异常树上产出（→ 见后端 `core/errors.py`、`main.py`）。前端把这套契约**单点翻译**成「文案 / 补救动作 / 可否重试」，REST 与 SSE 两条线共用，不再各自为政（旧态：REST 裸 JSON、工作区 `window.alert`、列表项静默 `.catch`）。

**核心决策**：错误码 → UX 的映射只有一份（`lib/errors.ts` 的 `describeError` + `errorActionForCode`）。`ApiError`（REST）与 `StreamError`（SSE 回合）都解析 `{code, message, Retry-After}` 再喂给它，故同一个 `code` 在回合横幅、内联错误卡、REST toast 三处措辞与动作完全一致。

- **按 code 分诊，不靠字符串匹配**：`LLM_KEY_REQUIRED` / `LLM_KEY_INVALID` → 「去配置」跳模型配置页；`QUOTA_EXCEEDED` / `LLM_KEY_REQUIRED` 不给重试（需用户动作或等额度，立即重试只会再失败）；其余给重试。
- **优先后端 message**：多数 coded error 自带可直接展示的中文 message（校验 / 冲突 / 无效 key / 余额不足），逐字透出（单一文案源），仅缺失时回落到按 status 的通用文案。
- **auth 静默**：401 不弹任何提示——登录重定向已接管（`describeError` 返回 `null`）。

**展示分诊**（不一刀切，按错误归属选承载面）：

| 场景 | 承载面 | 代码 |
|------|--------|------|
| 对话回合失败 | 内联（`MessageBubble` 错误卡 + `ChatView` 重试横幅） | `services/turns.ts` → `setError` |
| REST 操作失败（重命名 / 保存 / 删除 / 新建 / 审批） | 轻量 toast（可带「重试 / 去配置」动作） | `lib/toast.tsx` `notifyError` |
| 路由未命中 / 渲染崩溃 | 应用风格兜底页（`errorElement`，区分 404 / 异常） | `components/layout/RouteError.tsx` |
| 会话级致命（离线 / 5xx outage） | 全屏重试屏（`AuthGate` 守卫） | 既有 |

**toast 基础设施**：引入 `sonner`（新依赖），`<Toaster>` 挂在 `App` 根（路由外，崩溃页 / 登录页也能弹）；配色用 `style` 把 sonner 内部变量映射到设计令牌（`--popover` / `--border` / `destructive`），跟随 `.dark`、零硬编码色（color-tokens）；状态色走前导图标（`AlertTriangle` / `CheckCircle2`），面板本体用中性 popover 表面。`window.alert` 与静默 `.catch(() => {})` 已统一替换为 toast；偏好类非致命写入（如 `ModeSelector` 的档位）保留静默，乐观值不回弹。

→ 见代码 `lib/errors.ts`、`lib/toast.tsx`、`components/ui/Toaster.tsx`、`components/layout/RouteError.tsx`、`services/api.ts`（`ApiError` 解析契约）、`router.tsx`（`errorElement`）

## 十一、桌面端插件架构 ✅ 已确定

> **实现现状**：插件注册表、`getPluginRoutes()`、`getPluginNavItems()`、插件 IPC 前缀 **均未实现**（→ 见代码 `main/index.ts` 仅窗口 + fs IPC）。以下为架构设计目标。

### 11.1 插件分类

| 类型 | 特征 | 示例 |
|------|------|------|
| 垂直工具 | 有独立页面、可能有本地存储 | 法规库、表格 |
| 基础设施 | 有独立生命周期、push 事件 | 文件系统、MCP |
| 轻量工具 | 仅主进程 I/O + 简单页面 | 脱敏、日程 |

### 11.2 六贡献点（类比后端 Vertical）

| 贡献点 | 消费方 |
|--------|--------|
| 路由注册 | router（经 `getPluginRoutes()` 注入） |
| 侧栏导航 | app-shell（经 `getPluginNavItems()` 注入） |
| IPC Handlers | 主进程注册表（自动加 `app:{id}:` 前缀） |
| 生命周期 | 应用启动/退出时调用 |
| 推送事件 | 主进程 → renderer 单向推送 |
| 跨插件服务 | 其他插件经 `getPluginService()` 调用 |

### 11.3 IPC 类型安全

三层结构建立编译时契约：

```
plugins/{name}/ipc-schema.ts   ← 单一真相源
        ↓
plugins/{name}/main.ts         ← TypedHandlers<Schema> 约束实现
        ↓
preload/index.ts               ← IpcBridge<Schema> + AssertIpcBridge 断言
```

新插件必须先写 schema 再写 handler；旧插件按需迁移。

### 11.4 错误隔离

每个插件路由自动包裹 ErrorBoundary（注册表注入，插件开发者无感知）。单插件崩溃仅影响其自身路由区域，不触发全局错误。

### 11.5 设计决策

| 决策 | 理由 |
|------|------|
| 显式注册（非约定扫描） | 当前体量下显式 import 更可控、可 tree-shake |
| IPC Schema 渐进迁移 | 避免大爆炸重写 preload |
| ErrorBoundary 注入在 registry | 零额外代码 |
| 路由嵌套在统一工具布局下 | 侧栏/顶栏/面包屑一致 |

## 十二、SSE 事件消费规范

后端 SSE 事件（定义于执行引擎 §十二）到前端 Zustand Store 的映射关系。消费入口为 `services/streamConversation.ts`（单次 `fetch` + `AbortController` 本地中止；access 过期会 401→静默刷新令牌→重放；**无**断线重连 / 服务端 resume·stop 端点）。

SSE 事件→Store 映射 / 未实现事件类型 → 见代码 `apps/desktop/src/renderer/services/streamConversation.ts`、`apps/desktop/src/renderer/types/events.ts`

### SSE 连接管理

| 场景 | 状态 |
|------|------|
| 发送消息 | 单次 `fetch` SSE |
| 本地中止 | `AbortController.abort()` |
| ⏳ 断线重连 | **未实现** |
| ✅ 401 过期 | 静默刷新令牌后重放（见 [`认证与会话.md` §六](/docs/05-平台与运维/认证与会话.md)） |
| ⏳ 恢复暂停 | **未实现**；无 `resume` 端点 |
| ✅ 停止生成 | 本地 `AbortController`；⏳ **无 stop 端点** |

### 消费层实现模式

SSE 事件经 `dispatchSSEEvent` 统一消费，按 `event.type` 路由到对应 Store（单一入口，不在组件中直接监听）：

→ 见代码：`apps/desktop/src/renderer/services/streamConversation.ts`（SSE 流消费与事件分发）、`stores/`（各目标 Store）

### 设计约束

- **单一入口**：所有 SSE 事件经 `services/streamConversation.ts` 统一分发，不在组件中直接监听
- **Store 最小更新**：每条事件只更新必需的 Store 字段，不做全量替换
- ⏳ **对账兜底**：`reconcileAllRuns()` **未实现**
- **乐观更新**：发送消息时立即在 conversation store 创建 user message 条目，无需等后端确认
