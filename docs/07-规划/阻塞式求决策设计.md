## 一、问题与目标

**改造前（痛点起点）**：`escalate` 是 worker 唯一的向上通道，但曾**恒为非阻塞**——worker 上报后不停工，按当下最合理假设把活做完，CEO 在收尾（`_format_for_ceo` 的「队员升级」段）时才纠偏。`blocking` 参数当时**已存在但空转**：只是给 CEO 的严重度标记（排到升级清单顶部标【关键阻塞】），即便 `true` 也不暂停 worker。

**痛点**：当 worker 撞上一个**关键到猜错就基本作废、且只有用户能拍板**的岔路时，「带着可能错的假设硬做、最后整段返工」是真实的浪费与体验缺口——这是多 Agent 协作里最像「需要通信」的场景。

**目标（已实现）**：给 `blocking=true` 装上真牙——worker 原地挂起、把问题送到用户、拿到答复再续跑；拿不到（超时）则**优雅回落**到非阻塞行为（按 `assumption` 做完）。→ 见代码：`tools/builtin/escalate.py`（`execute` 的 blocking 分支 + `escalate_tool_result`）。

**非目标**：worker↔worker 自由通信（继续否决，见 `Agent协作模式.md §二`）；产品形态的「多 AI 群聊」（另一条路线）。

## 二、硬约束：波内没有「在跑的 CEO」

CEO 调 `delegate` 后，它的 ReAct 循环就**停在那一次工具调用上**（`await WaveScheduler.run(...)`），整波 worker 执行期间 CEO 不前进。所以经典的「worker → CEO → （必要时）user」环**在波内根本跑不动**：没有活着的 CEO LLM 能在波中途接住升级、用判断去答 / 转问用户 / `revise`。

这逼出唯一要拍板的岔路：**worker 卡住时，谁来当场解？**

| 方案 | 谁当场解 | 代价 |
|---|---|---|
| **甲·worker→用户**（采纳） | 用户（worker 经统一 interaction bridge 直接发问） | 软化「worker 不直接对用户说话」一道窄口 |
| 乙·worker→CEO（**被否决**） | CEO（波暂停 → 交回 CEO → 带答案重入续跑） | 需新造「半途 worker 挂起/续跑 + 波内重入 + `revise` 扩到未完成 run」，且每次阻塞多付一次 CEO LLM 往返的延迟 |

---

## 三、决策：worker → 用户（经统一 interaction bridge），不走 CEO 中介

**采纳方案甲。** 这不只是「血量小」，而是**架构上更对**：

1. **CEO 中介对真·阻塞升级是伪价值**：触发判据已要求 worker 自证「只有用户能定」（见 §4.1），CEO 给不出答案；它能加的只有「改述 / 合并 / 干脆杀计划」，不值得为一个**时间敏感**的阻塞点多付一次 CEO LLM 往返 + 拆/重建波的延迟。
2. **不破坏「一个 CEO 声音」**：升级是**结构化决策卡**（同 `ask_user` 的卡），不是往对话流里灌 worker 散文；CEO 仍独占收尾叙事。
3. **机制一致而非 hack**：平台所有「等用户决策」（approval / ask_user / plan_review）本就都挂在同一条 `InteractionRegistry.suspend()` 上；阻塞 escalate 复用它，是**对齐**已有范式。
4. **「隔离边界」的真意由克制守**：该规则真正要防的是「并行 worker 拿散言碎语刷屏用户对话」——这由**触发克制 + 必带假设 + 并发上限**守住，而非靠强制绕道 CEO。

> **被否决：乙·CEO 中介波内重入**——理由：需把 `revise`（现仅能唤回**已完成** worker）扩到唤回半途挂起的 worker，并让 `WaveScheduler` 支持「波中途交还控制权再重入」，两者均无现成件、且动到调度器最敏感处；更关键是它给时间敏感的阻塞点平添一次 CEO LLM 往返延迟。「移除兼容/血量约束」不等于「该选更重的方案」——重机制在此是**未被需求挣来的复杂度**。

## 四、端到端设计（按方案甲）

### 4.1 触发条件

- `blocking=true` 语义从「严重度标记」升级为「真挂起等用户」。判据（克制）：① 缺的信息**关键到猜错就基本作废**；② **只有用户能定**（非 CEO 政策可拍、也非能自行合理假设的小事）。普通分歧仍 `blocking=false` / 自行假设。
- **强制带 `assumption`**（`blocking=true` 缺则拒）：超时要回落到「按假设续跑」（§4.4）。这是 `ask_user` 的对偶——`ask_user(blocking=false)` 强制 fallback，`escalate(blocking=true)` 强制 assumption，两者都堵「要么静默瞎猜、要么无限挂起」。
- `blocking=false` / 省略 = **今天的行为，零改动**（不等、按假设做、CEO 收尾纠偏）；只有 `true` 进新路径。

### 4.2 挂起粒度与机制

- **机制藏在 `ToolContext.escalation` 端口后（引擎纯化）**：`escalate.execute()` 在 `blocking=true` 且通道在场且 `armed` 时，调 `await context.escalation.request(question, assumption)`——**工具本身不碰 bridge / 不识事件词表**。该 `EscalationChannel`（`tools/protocol.py`）由 `build_agent_executor._escalation_channel` 按 worker 构造，独占整套机制：并发上限检查 → 在**共享 bridge** 上 `suspend(kind=ESCALATION, timeout=T)` → 发 `escalation_required`/`escalation_resolved` 对 → 把处置记进该 run 的 `resolutions`。工具只决定「是否阻塞」并把返回的 `EscalationOutcome` 映射成 `CONTINUE`（单一源 `escalate_tool_result`：resolved 喂答复、timeout 回落假设）。worker 的 ReAct 循环自然停在这次工具调用上——**零新循环机制**。
- **降级回落**：通道返回 `status="degraded"`（并发占满）、或通道缺席（CEO/测试）/未武装 → 落到非阻塞分支（发 `run_escalation` 横幅、按假设续跑）。于是阻塞是非阻塞的**严格超集**。
- 新增 `InteractionKind.ESCALATION`（与 `approval`/`ask_user`/`plan_review` 并列）；resolve body = `{answer}` 或 `{use_assumption}`（后者等同提前超时）。
- **兄弟不受影响**：挂起 worker 只是个 parked 的 asyncio task，其它 ready worker 照常调度；CEO 仍停在 `delegate`（不动）。
- **任意深度可用**：bridge 是进程级单例，`interaction_bridge`/`escalation_armed`/`escalation_timeout` 经 `build_agent_executor` 注入、`_make_child` 透传，depth-2 子 worker 阻塞也能问到用户，无深度特例。
- **武装门（与 ask_user 同闸）**：`escalation_armed = DelegateTool._checkpoint_active()`（有活的交互用户）时阻塞才生效；自治 / handoff 任务（无 live client）下 `blocking=true` **自动退化为非阻塞**——否则会在无人应答处卡死。

### 4.3 与并发预算 / 波次调度的交互

- 走 `ToolContext` 透传，**不改 `WaveScheduler` 内核**。
- 挂起 worker **仍占一个 `running` 槽**（还是 in-flight task），但零 CPU；`width = min(max_parallel, budget, n_pending)` 不变。
- **无环死锁**：worker 等的是**用户**（外部），不是别的 worker——CEO 等波、波等 worker、worker 等用户，链无环，用户是根解析者。与 `Agent协作模式.md §七.6` 否决的「树级共享 Semaphore 死锁」（worker 互等同一信号量）本质不同。
- **退化点**：若一整波 `width` 被阻塞 worker 占满，独立待跑工作会停等到用户答复——非死锁，是吞吐 / 延迟损失。由触发克制 + §4.6 并发上限兜住。

### 4.4 超时与降级（安全基石）

- `suspend(…, timeout=T)`：T 内有答复 → 用之；**超时 → 回落今天的非阻塞行为**（worker 按它写的 `assumption` 做完，CEO 收尾仍可纠偏）。
- 于是**阻塞式 escalate = 今日行为的严格超集**：`false` 零改动，`true` 只是「先等 T 秒用户，等不到就退回今天的样子」。**不可能回归现有行为**——本设计最重要的安全性质。
- **断连 / 重启（v1 边界）**：半途挂起**不是静止点**（兄弟在跑、blocked worker 持半截 transcript），`plan + completed` 快照式的 2b 持久续跑用不上。故 v1 **不做** mid-flight 持久续跑：断连按现有 cancel 语义结束本回合、用户重发。**区别**：超时（在线没答）优雅降级到假设；断连（离开）整回合告终、不可续。

### 4.5 前端呈现（三端）

复用 `ask_user` / `plan_review` 的卡片骨架 + 统一 interaction 基建（`*_required` / `*_resolved` 事件 + `POST …/interactions/{id}` resolve），但升级卡比 `ask_user` 简单——它是 worker 临时发问、无预设结构化选项。

**A. 升级卡（应答面）**：新建 `EscalationCard`（桌面）+ 手机镜像，琥珀基调（待裁决，对齐 `color-tokens` 检查点/警告）：

- 标题：「{角色} 请你拍板」（署名到发起的 worker）。
- 正文：`question`（自包含）。
- 只读假设块：「未答则按此继续：{assumption}」——明示回落，让想省事的用户安心略过。
- 输入：单个自由文本框（无 `ask_user` 的 questions/options/style——升级无预设选项）。
- 操作：**「提交」**（→ resolve，worker 据答续跑）+ **「按假设继续」**（→ 立即降级，等价提前触发超时回落）。**无「停止」**：停整回合是对话级 / CEO `ask_user` 的职责，不该由单个 worker 升级决定。
- 三态（同既有卡）：interactive（live+suspended，可交）/ dormant（重载或回合已结束的 pending，静态记录）/ resolved（已答显问答 + 答案；超时显「已按假设继续」）。

**B. 归属 + 回合级（非 halting）指示**：

- **worker 节点**：`RunDetailBody` 的 `EscalationSection` 按 `status` 分态——`raised`（非阻塞横幅，只读）/ `pending`（阻塞中·待你答，琥珀高亮 + 就地可应答，复用气泡同款 `EscalationCard`）/ `resolved`（+ 答案）/ `timeout`（已按假设继续）；`AgentNode` / `GraphView` 给有 `pending` 升级的节点加琥珀「待你拍板」角标（settled 自动清），非阻塞 `raised` 则显 muted「上报」角标。
- **回合级**：阻塞升级**不把回合翻成 paused**（其它队员仍在跑），故在助手气泡下渲染 `escalations.map → EscalationCard`（与 checkpoints / planReviews 并列），聚合标题「团队有 N 项待你拍板」——它既是指示也是应答面。
- **CEO 收尾不双问**：已当场解决的升级，`_escalation_block` 标「已当场答复：{answer}」、指示 CEO 无需再 `ask_user`；仅未解决 / 超时降级的才进「请先处理」清单。

### 4.6 锁定参数（默认值，可后续校准）

| 参数 | 取值 | 理由 |
|---|---|---|
| 超时 `T` | 复用 `settings.checkpoint_timeout_seconds` | 与 `ask_user`/`plan_review` 同口径——都是「等用户决策多久」 |
| 武装门 | `checkpoint_enabled` | 与 `ask_user` 同闸；无 live user 时退化非阻塞 |
| 同回合并发阻塞升级上限 | 3（超出退化为非阻塞按假设做） | 防卡片洪水 + 防一波 `width` 被占满 |
| 挂起让槽（slot-yield） | **不做**（v1） | 让 parked worker 退出 `width` 计数需把信号从工具层穿回调度器、unpark 可能瞬时超并发——是复杂度/价值权衡（非兼容问题）；阻塞本应罕见，见真痛再加 |
| mid-flight 持久续跑 | **不做**（v1） | 半途非静止点；断连即结束（见 §4.4） |

### 4.7 边界用例与不变量（动手前走查）

已对照现网代码逐条核对（`runtime/interaction.py`、`runtime/runs/wave.py`、`runtime/runs/executor.py`、`tools/builtin/delegate.py`、`tools/builtin/ask_user.py`、`api/routes/conversations/interactions.py`）：

| 边界 | 结论 | 依据 / 要点 |
|---|---|---|
| 超时 vs 答复竞态 | 安全，无双触发 | `suspend()` = `asyncio.wait_for(fut)`；`resolve()` 见 `future.done()` 即 no-op。awaiter 只观察到 {答复 / TimeoutError / Cancelled} 之一 → **由它**发 `escalation_resolved`，前端事件必与 worker 实际行为一致 |
| 「按假设继续」 | 走**同一** resolve 端点的哨兵结果（`use_assumption`），escalate 内**等同超时分支** | 复用竞态仲裁 + 迟到 resolve 的 404 语义；不另开 cancel 路径 |
| 迟到提交（已超时/已答） | route 已统一 404「已处理」 | `interactions.py`：`resolve()`→False→`NotFoundError`；前端须渲染「此决策已关闭」而非报错 toast |
| 多卡并发 | 天然支持；上限 3 在 escalate 内数 `list_pending(conv) ∩ ESCALATION` | `_pending` 按 id 存；count→`suspend.create()` 间无 await → 单循环内无竞态；超限走非阻塞分支 |
| depth-2 子 worker | 可达用户、无深度特例 | bridge 是进程级单例；`_make_child` 透传 `base_tool_context`/`registry`/`conversation_id`/`checkpoint_enabled` → 子队 `ToolContext` 同源 |
| 武装门关 | `blocking=true` 自动退化非阻塞 | 复用 `_checkpoint_active() = checkpoint_enabled and registry and conversation_id`（单一源）；非武装 → 走既有 `escalation_raised` 分支、**不发** `escalation_required` |
| 用户 stop 整回合 | parked worker 收 `CancelledError` → `suspend()` `finally: discard` → 卡片转 dormant | `wave.py` 外部 cancel 取消所有 in-flight 并 await |
| sibling 失败 abort | parked worker 不被取消、续等到答复/超时再跑完、下游 skip | `on_failure=abort` 只停派新节点、不取消 in-flight（仅外部 cancel/crash 才取消）；至多一次「白问」，非 bug |

**实现必守的两条不变量**：

1. **单一发射者**：`escalation_resolved` 只由挂起的 escalate 工具（awaiter）发、**绝不**由 resolve 路由发；事件载明 disposition（`answer` / `timeout` / `assumption`），三端 + oracle 据此同分类（对照 ask_user：route 只 settle future、`checkpoint_resolved` 由 `ask_user.py` 发）。
2. **interactive 门控按「回合非终态」而非「running」**：并发 halting gate（某 worker 的 approval / CEO ask_user）会把回合置 `paused`、而升级 worker 仍独立 parked——故升级卡 interactive 判据 = `required 已见 ∧ resolved 未见 ∧ 回合 status ∉ 终态{completed/error/cancelled}`（running 与 paused 都保活）。§4.5「重载/回合已结束 → dormant」即此。

**一处非平凡改动（防补丁绊线）**：`RunState.escalations` 项带 `status`/`answer`（与 §七 projection 同名）供 CEO 收尾不双问，**状态由结构化数据驱动、非反解 prose**：`escalations_from_transcript` 从 worker transcript 取每次 escalate 调用（默认 `status="raised"`、无 answer）作为「调用清单」；`EscalationChannel` 处理阻塞升级时把 `resolved`/`timeout` 处置 + answer 按 question 写进该 run 的 `resolutions` 字典；`_execute_node` 收尾时把两者**按 question 合流**（transcript 出清单、通道出处置），不在 serialize 里脆弱地配对 call→result。worker 串行 ⇒ 同一 question 一次一个，合流无歧义。

## 七、跨端一致性（conformance）

阻塞 escalate 是协议 fold 的危险面（SSE → 状态），按 `protocol-conformance.mdc` 扩契约 + 加棘轮向量。

**契约扩展（`packages/protocol-conformance` 单一源）**：`ProjectedRun.escalations[]` 项加 `status: "raised" | "pending" | "resolved" | "timeout"` + `answer: string | null`。**不动** `pendingInteraction`（它是 singular 的 halting gate）。

**三端 + 后端 oracle 一致的折叠规则**：

- 既有 `run_escalation`（非阻塞实时横幅）→ `{blocking:false, status:"raised", answer:null}`。
- 新 `escalation_required`（阻塞挂起）→ 追加 `{blocking:true, status:"pending", answer:null}`。
- 新 `escalation_resolved`：答复 → 该项翻 `{status:"resolved", answer:X}`；超时 → `{status:"timeout"}`。
- **回合 `status` 不因阻塞升级翻 `paused`**：升级非 halting、其它队员继续、超时自降级——与 approval / ask_user / plan_review 的 halting gate 区别（那三者 `pending != null ⇒ paused`，本特性不进这条）。回合级「N 项待答」由前端从 `runs[].escalations(status==pending)` **派生**，不另立 `ProjectedTurn` 字段（冗余 = 漂移面）。
- **卡片 interactive 门控按「回合非终态」而非「running」**（见 §4.7 不变量 2）：并发 halting gate 把回合置 `paused` 时，独立 parked 的升级卡仍须可应答，故 `pending ∧ status ∉ 终态` 即 interactive（running / paused 都保活），终态才 dormant。

**向量**：`multi_agent_blocking_escalate`（升级 → pending → resolved → 续跑 → 收尾）+ 超时变体（无 `escalation_resolved`，status → timeout，worker 按假设续跑）。后端 oracle 产 golden，桌面 / 手机 fold 跑同向量断言 `== golden`；改 fold / 投影后 `uv run python -m agentcore.conformance.export` 重生 golden 再 `pnpm conformance`。
