# 法律垂直场景设计 🗂️

> **定位**：AgentCore「第一个行业垂直」选定**法律**的落地提案。**核心主张：以「只有多 Agent 才能做的能力」为 hero（首选「对方律师作战室」），文书类型只是产物、退居次要**——记录战略契合、2026 行业调研、已对齐决策与 v0 架构草案。是 [产品定位 §三「行业垂直深度」壁垒](/docs/01-产品/产品定位与品牌.md) 的**首个落地实例**。

> **治理**：本目录仅 `07-规划`；🗂️ = 讨论中、未承诺落地。表中「✅ 已对齐」指当前讨论共识，仍待正式确认（架构选型 / 新依赖按「AI 提案 → 人确认」）。决策通过、开始落地后，能力包内容迁入 `03-AI核心`（Tool/Skill/Rule）、产品边界迁入 `01-产品`，本文退役。

## 一、为什么做法律垂直（先对齐需求，别用技术反推）

诚实声明：这不是「技术方便反推需求」。三条正向理由：

1. **兑现既定壁垒**：[产品定位 §三](/docs/01-产品/产品定位与品牌.md) 已把「行业垂直深度（平台核心行业无关 + 垂直插件可插拔）」列为三维竞争壁垒之一，演进优先级中期亦列「第二垂直行业」。法律 = 把这条从蓝图变成**首个实例**。
2. **法律天然契合唯一差异点**：AgentCore 差异化是**真多 Agent 团队协作 + 辩论互审**。法律推理**天生对抗**——这正是 §三 hero 能力「对方律师作战室」的根基：单 Agent 自导自演装不出一支有独立目标的对抗团队。
3. **空白地 + 攻击未解难题**：见 §二——中国法律 AI 几乎全是「单模型 + RAG」，引用可靠性是公认未解；多 Agent 对抗核验是结构性更优解，目前无人占据。

旁证：现有对比评测 `evals/cases/comparison/xd_tech_legal.json` 已用「工程 + 法务」证明 team 胜 single——法律本就是项目内用来展示协作优势的题材。

## 二、行业坐标（2026 调研，pointer-only）

### 2.1 全球 SOTA：都在向 agentic 转，且都承认「不能无人复核」

| 产品 | 定位 | 对本设计的意义 |
|---|---|---|
| Harvey（$11B，2026.03） | AI-native 通用，500+ 预制 agent + Agent Builder，走「同案并行调查/起草/分析」 | agentic + 可复用 agent 库是方向；印证「任务而非 prompt 为单位」 |
| CoCounsel（Thomson Reuters） | 研究 + Westlaw 接地，2026 初上 agentic workflows（自主审查 + Deep Research） | 权威库接地 + agentic；研究强、复杂起草弱 |
| Spellbook（$350M） | Word 插件，合同起草 + 条款库/playbook，$99–299/人/月，4000+ 团队 | **形态即胜负手**：律师在 Word 写字，工具就该在 Word |

共识：三者都要人最终复核，无一可无人提交。

### 2.2 中国市场：已进「实战淘汰赛」，但几乎全是「单模型 + RAG」

- 玩家：通义法睿（阿里，千问 + RAG + 法律 Agent）、幂律智能（PowerLaw + 智谱，企业合同全生命周期）、元典问达、法天使（合同模板库王者）、AlphaGPT（iCourt，数亿判例 + 法规）、智律云、法宝来签（北大英华）、法行宝（百度，免费）。律所渗透 72%、法务采用 58%。
- **文书生成主流路子 = 要素式（模板 + 要素 + 案情 → 文书）**；元典问达已产品化「要素式起诉状」。
- 战场指标 = 法条引用正确率（实测 75%–98%）；公认短板「复杂场景深度不足」。
- **几乎无人做「多 Agent 团队 + 对手方红队」→ 这就是空白地。**

### 2.3 多 Agent 法律 = 2026 前沿，且恰是 AgentCore 主场

开源 / 学界框架几乎是把 AgentCore 内核手搓了一遍：

| 框架 | 形态 | 对照 AgentCore |
|---|---|---|
| GLAW | 8 段流水线，含**强制对抗红队闸门**「递状前先摧毁自己立场」 | `debate`/互审 + [交付前核验·重层](/docs/07-规划/远期规划.md) |
| Themis | orchestrator 路由到 数据 / 教义专家（可核验引用 + 给支持与反方权威）/ 策略 / 起草 Agent，5 阶段流转 | `delegate` + 角色分配 + DAG |
| RCBSF | 合同修订 Stackelberg 主从博弈：风险审计→修订→核验 多轮闭环 | `delegate` + `revise` + 重层核验 |
| Harvey / CoCounsel / Lexis Protégé | 企业级 agentic：多专家 Agent 协作 + human-in-the-loop | CEO 编排 + `escalate` + 检查点 |

「Critic/Judge Agent 做内部红队，核事实支撑 / 管辖相关 / 时效（法条是否被修订、判例是否被推翻）/ 矛盾，不过关就逼检索重查」——这段几乎是 `delegate` + `debate`/`escalate` + 检查点的翻译。**别人要手搓的，AgentCore 内核白送。**

### 2.4 幻觉现实：连 RAG 都救不了——但这恰好抬高多 Agent

- Stanford RegLab：即便 Lexis+ / Westlaw 这类专业 RAG 工具仍 **17%–34% 幻觉**；ChatGPT 类通用工具法律问题 58%–88%。
- 「**错接地引用比凭空造假更危险**」（真案号 + 错观点，制造虚假信心）；ABA 512 号意见：律师对 AI 产物全责、须逐条核验。
- 推论：单模型 RAG 不是银弹。胜手 = **检索接地 + 独立核验/红队 Agent + 人审闸门 + 审计留痕**——这正是多 Agent 能做、单 Agent 做不了的。

> → §三据此重定方向：护城河不在「写哪类文书」，而在「对抗 + 核验」这件**只有多 Agent 才做得了**的事。

## 三、产品形态：选「只有多 Agent 能做的能力」做 hero，不选文书类型

**关键转向**：别纠结「先写哪类文书」——文书是**产物**，能力才是**护城河**。incumbents（通义法睿 / 幂律 / 元典 …）都能生成文书，且都是「单模型 + RAG」，唯独复制不了一支**真正独立的对抗团队**。所以 v0 的 hero 选「只有多 Agent 架构能做」的能力，文书类型退居其后（先挑最省力的当载体）。

三个架构原生、incumbents 复制不了的候选：

| | 能力 | 一句话 | 为什么只有多 Agent 能做 | 映射现有能力 |
|---|---|---|---|---|
| **A（hero）** | **对方律师作战室** | 把立场 / 草稿 / 合同 / 谈判方案扔进去 → 一整队 AI 对方律师先把你打一遍（预演每条抗辩、挑漏洞、模拟法官视角）→ 你的队再加固 | 需要真正独立、有自身目标的对抗团队；单 Agent 自导自演装不出 | `delegate` + `debate`/互审 + 检索接地核验；调研里 GLAW「递状前先摧毁自己立场」、Critic/Judge 红队 |
| **C（底色，横切护城河）** | **可辩护的玻璃箱过程** | 团队怎么辩、每条引用怎么核、哪里有异议，全程可见 + 审计留痕 | 面对「律师对 AI 产物全责」（ABA 512），「看得见过程、护得住结论」本身即卖点；黑箱单模型给不了 | 互审 / 辩论事件流 + [交付前核验·重层](/docs/07-规划/远期规划.md) + 审计留痕 |
| **B（可选亮点）** | **多模型法律辩论** | 难题 / 不确定问题，让不同模型当不同「法律大脑」吵出答案，分歧点 = 法律风险点 | 需要异构模型各自独立判断；已部分落地真·多模型辩论 | [真·多模型辩论与谁更聪明视频](/docs/07-规划/真多模型辩论与谁更聪明视频.md)（豆包×DeepSeek） |

**采用方案：A 为 hero，C 做底色，B 做可选亮点。** 「写法律文书」不丢，只是被重新定义——不是「又一个文书生成器」，而是**「一个会替你预演对方律师、把文书 / 立场打磨到扛得住攻击的 AI 团队」**。

> 故事一句话：**「递状 / 签约 / 开庭前，让一队 AI 对方律师先把你打一遍。」** 它跨所有文书 / 案件通用，不必赌单一文书类型——文书类型只是 hero 的首个演示载体（见 §九）。

## 五、为什么是「垂直能力包」而非改内核（设计纪律）

按 [工具与能力系统](/docs/03-AI核心/工具与能力系统.md) 的五类资产（Tool / Skill / Rule / Agent / Team）+ 能力域，法律垂直**完全落资产层**，内核保持行业无关：

| 资产 | 法律垂直内容 | 现有承载 |
|---|---|---|
| Team / Agent 模板 | 「对方律师作战室」行为模板（起草 / 对手方红队 / 核验 / 格式） | 动态角色分配 + 行为模板（[产品定位 §四/§七](/docs/01-产品/产品定位与品牌.md) Day 2） |
| Skill | 要素式文书工作流、论证结构、文书格式规范、红队对抗剧本；**三方视角案情研判**（接案评估 / 诉讼策略，见 §六之二） | 系统/市场 Skill + `consult_skill` |
| Rule | 未核验不得引用法条、标注法域、免责声明、人审闸门 | `ai_maintained` rule / 行为约束 |
| Tool | 法条 + 案例检索（接地核验）；已有库经本地检索 Tool 接入 | 内部 `Tool` Protocol（暂定本地检索 Tool，⏳ 远期可走 MCP） |

**绊线**（[dev-process 补丁绊线](/.cursor/rules/dev-process.mdc)）：一旦发现为法律改编排器 / loop / 调度，立即停、提根因重设计——那说明能力包抽象不够，而非该改内核。

## 六、v0 落地拆解：「答辩状作战室」（可动工清单）

> **设计纪律**：v0 **只用现有原语跑通 hero，不建新基建**——`delegate` / `debate(red_team)` / `revise` / `checkpoint_after` / `consult_skill` / web 检索（`tools/builtin/web/`）全部已落地。守 §五 绊线：为法律改编排器即停。v0 新增的只有**领域内容**（一支 Skill + 一组反幻觉 Rule 约束），不动内核。

### 6.1 作战室编排（复用现有，0 新基建）

CEO 读「答辩状作战室」Skill 后**动态组队**（角色是 `delegate` 的自由 `role`/`task`，无需团队模板实体）。对照 [编排器与 CEO](/docs/03-AI核心/编排器与CEO主Agent.md) + [Agent 协作模式](/docs/03-AI核心/Agent协作模式.md)：

| 步 | 角色 | 怎么落（复用） |
|---|---|---|
| 1 | CEO（主办律师） | 接「对方起诉状 + 我方事实」，拆解 → `delegate` |
| 2 | 起草 Agent | 出答辩状初稿（逐项答辩：程序异议 + 实体抗辩） → `delegate` worker + 答辩状 Skill |
| 3 | **对方红队（hero 核心）** | 扮原告，对每条抗辩单向反击、挑漏洞 → 我方回应修补 → **`debate(form=red_team, is_subject=我方答辩状)`**（现成红队形态，零改造） |
| 4 | 核验 Agent | 逐条法条检索核验、查时效 → `delegate` worker + `web_search` 接地（库导入后走本地检索 Tool） |
| 5 | 格式 / 完备 Agent | 对照答辩状格式查缺补漏 → `delegate` worker + 格式 Skill |
| 6 | CEO 收口 | 终稿前 `checkpoint_after` / `ask_user` 人审闸门 → **CEO 收口正文完整输出答辩状终稿**（已核验法条带 `[n]` 角标连来源卡；`[待核验]` 不编角标）；初稿 / 修订稿落工作区作可下载附件（§十一 方案①） |

→ 这套就是 §三 hero「对方律师作战室」的落地：`debate` 的 `red_team` 形态天然就是「把我方答辩标 `is_subject`、原告红队单向攻、我方回应修补」，与 hero 立论一一对应。[辩论编排设计](/docs/03-AI核心/辩论编排设计.md) 已交回「逐轮攻防 + 决策简报」双产物。

### 6.2 可动工清单（复用 vs 新增）

| 能力 | 状态 | v0 动作 |
|---|---|---|
| 编排（组队 / 红队 / 核验 / 收口） | ✅ 复用 | `delegate` + `debate(red_team)` + `revise` + `checkpoint_after`，**不写新编排码** |
| 法条检索（接地） | ✅ 复用起步 | `web_search` 抓权威摘要可用；**实测 `flk.npc.gov.cn` 的 `read_url` SSL / 超时打不开**（见 §六.3 M2）→ 退 `web_search` 摘要 + 标 `[待核验]` 人审（过渡）；**已有法规+案例库、后续经本地检索 Tool 导入做权威接地（根因解）** |
| 玻璃箱过程（C） | ✅ 复用 | `debate` 已产「逐轮攻防 + 决策简报 + 交锋叙事线」事件流（前端已渲染）；核验产出带出处即留痕 |
| **答辩状 Skill** | ✅ M1 已落地 + §十一 方案① 已落地 | 新模块 `runtime/legal_skills.py` 定义 `legal_answer_brief` `SystemSkill`：答辩状要素结构 + 作战室编排指引 + 原告红队对抗剧本 + 反幻觉硬约束；**收口段**教 CEO 在正文完整输出终稿、已核验法条带 `[n]` 连来源卡（Gap B） |
| **反幻觉 Rule** | ✅ M1 已落地 | 写进上述 Skill 的「反幻觉硬约束」段（最省力 stopgap）：未核验不得引法条 / 标注中国大陆法域 / 免责声明 / 人审闸门 |

> **诚实标注（非补丁绊线）**：领域 Skill / Rule 的「正道」是 ⏳ 未实现的「市场 Skill + per-agent 绑定 / `AgentEntityBinding` 能力域」（见 [工具与能力系统 §一/§二](/docs/03-AI核心/工具与能力系统.md)）。v0 先借**已落地的 system skill registry** 落地领域内容（stopgap）——但**不污染通用部署**：`legal_answer_brief` 经 `build_system_skill_registry(include_legal=…)` 由开关 `legal_vertical_enabled`（默认关）选择性叠加，平台系统 Skill 集（那 6 个）原样不变。这是「逻辑本地先行、不为远期预建抽象」的合理取舍——**它没改编排器、没加兜底对账**，故不触 §五/§八 绊线。值跑通后再把这支 Skill 迁去市场 Skill。

### 6.3 v0 里程碑（带验收标准）

1. **M1 骨架 ✅ 已落地**：`legal_answer_brief` Skill（`runtime/legal_skills.py`，含工作流 + 作战室编排指引 + 原告红队剧本 + 反幻觉硬约束）+ 开关 `legal_vertical_enabled`（`config/features.py`，默认关）选择性叠加 + 单测（`tests/test_legal_skills.py` 锁三件：opt-in gating / `consult_skill` 取回 / 正文仍教机制）。开关打开即进 CEO 能力目录、可 `consult_skill` 拉取。

## 六之二、第二支领域能力：三方视角案情研判 skill（已落地骨架）

> **缘起**：答辩状作战室解决「把我方文书打磨到扛得住攻击」；但律师在**接案 / 定策略**时更上游的问题是「这案放到对抗的法庭里，我到底站不站得住、会怎么收场」——这要**中立研判**而非起草。2026-06「从用户需求出发」讨论定下这支 sibling skill（需求优先、拒技术反推：先锁用户与决定，再映射原语）。

### 6bis.1 需求（执业律师，已对齐）

| 维度 | 决策 |
|---|---|
| 主用户 | **执业律师**（接案评估 / 诉讼策略），与 §四「真交付律师」一致 |
| 真问题 | 律师难免栽的两坑——**当事人一面之词** + **律师自身立场盲区**；用独立对方 + 中立法官对抗之，给敢据此决策的研判 |
| 为什么三方 | 「原告 / 被告 / 法官」还原纠纷三力量（主张 / 对抗 / 裁判）：少对抗=自我安慰、少裁判=各执一词没结论——正是单模型给不了的（它只顺委托人故事讲） |
| v0 范围 | **不拆**，一支 skill 覆盖**接案评估 + 诉讼策略**两场景；**A 分流**（律师明说、拿不准 `ask_user` 反问） |
| 立场 | 中立研判（不预设我方）；策略虽选边，仍守**中立纪律**让对方视角独立打 |

### 6bis.2 两份产物（按场景分别装配、落盘工作区文件；完整正文见 skill body）

- **接案评估 →《接案研判.md》**：一句话研判（胜算定性+关键条件）/ 原告视角 / 被告视角 / **法官视角（按举证责任的大概率认定 + 争议焦点 + 当事人说法站不住处）** / 证据短板清单 / 风险与告知 / 下一步（接·不接·补证再评·建议和解）。
- **诉讼策略 →《诉讼策略.md》**：策略总纲 / **攻防地图**（我方诉请抗辩→对方最强反击→我方加固）/ 争议焦点排序 / 举证计划 / 判决预期 vs 和解锚 / 庭审预案 / 下一步。
- 同一法官两副面孔：接案=**体检 / 戳破**（让律师冷静），策略=**预判 / 迎合**（让律师赢）。

### 6bis.3 原语映射（0 新基建，守 §五 绊线）

| 三方 | 现有原语 |
|---|---|
| 原告 ⟷ 被告 | `debate(form="debate")` 对称攻防（辩手自带 web 接地） |
| 法官（核心） | `delegate` **中立法官研判 worker**：读交锋 → 按举证责任出实体裁判 |
| 法条核验 | `delegate` worker（复用答辩状的检索有界 / 命中即停 / `[待核验]`） |
| 分流 / 补事实 / 人审 / 免责 | `ask_user` + `checkpoint_after` + 反幻觉硬约束 |

> **法官落点（已定·忠实方案）**：debate 只跑原被告交锋、法官另派 worker——法律大脑全在领域内容、debate 保持通用，故不触内核。**被否**：直接用 debate 主持人决策简报当法官（轻量）——主持人判的是「辩论质量 / 收敛」，够不上举证责任那种法律研判。
> **反幻觉增量**：除答辩状那套（未核验不得引法条 / 法域 / 免责 / 人审闸门）外，**胜负一律定性为「倾向性研判，非判决结果预测」**（比引法条更易被过度依赖，须给成立条件与不确定性，绝不写「必胜 / 必败 / 保证」）。

### 6bis.4 里程碑

## 七、反幻觉底座（不可省，§四「真交付」的硬底线）

四件套，缺一不可：**检索接地 → 核验 / 红队 Agent → 人审闸门 → 审计留痕**。

- **人审闸门**可借 [远期规划 §2.3 治理强制检查点](/docs/07-规划/远期规划.md)——法律「律师必须复核」可能正是启动该功能的驱动力（强制注入、声明即必停、超时取 halt、可审计）。
- **审计留痕 = §三 hero C「玻璃箱可辩护过程」的落地**：团队怎么辩、每条引用怎么核、哪里有异议全程可见，正是面对 ABA 512「律师全责」的卖点。
- **案例引用 v0 web 过渡、库后续导入**：裁判文书检索难、文书网收紧、Stanford 指出法律检索本身困难，故 v0 先走「用户提供 + 核验」+ web 起步；**已有案例库，后续经本地检索 Tool 导入**后做案例接地核验（非从零自建库）。

## 十、库接入提案（本地检索 Tool·后续，待确认）

> **缘起**：M2 实测核验 worker churn（~40 搜 / 12 轮被引擎强制收口）的**根因 = 无权威本地源**；用户已有【法律法规库 + 案例库】。本节给「后续导入」的接入草案——**v0 不依赖、web 接地照旧**；属新基建，**待确认后再写码**（守 §五 不污染内核）。

| 维度 | 提案（待确认） |
|---|---|
| 形态 | 内部 `Tool` Protocol 实现一支「本地检索 Tool」（暂定，远期可走 MCP）；**纯资产层，不改编排器 / loop / 调度** |
| 挂载 | 经 gating 仅 `legal_vertical_enabled` 时挂给起草 / 核验 worker（同 Skill 开关，平台部署无感） |
| 接口草案 | `statute_search(query, top_k) → [{法条号, 标题, 现行有效性, 原文, 出处, 版本日期}]`；`case_search(query, top_k, filters?) → [{案号, 裁判要旨, 法院, 年份, 出处}]` |
| 核验改线 | grounding 顺序：**本地检索 Tool 优先 → web 退避 → 拿不到标 `[待核验]`**（churn 根因解：1 次命中替代 ~40 次试搜） |
| 数据面（承 §八） | 库**本地化**接入；客户案情**不发往外部检索**、不随查询外泄；库 / 案情隔离；加密留存 + 可删除 |
| 索引 | 先关键词 / BM25（「条号 → 原文」精确命中已够）；向量 / 语义检索留升级（待议） |
| 排期 | M2 已实质通过为前置；依赖库数据导入就绪；v0 收口后启动评审 |
| 不做 | 不自建语料（用户已有库）、不做案例 RAG 训练、不为库改内核（越界即触 §五绊线） |

> **验收（库接入后）**：核验 worker 单 worker 检索次数 ≤ 引用法条数 ×2（不再 40+）；引用法条的原文 / 条号 / 现行有效性来自本地权威源、可回溯出处；客户案情零外发。

## 十一、来源卡接入（`citations_event`·法条出处可审计编号台账，✅ 方案① 已落地）

> **缘起**：M3 自检发现法律终稿的法条出处虽**已可回溯**（`法条核验报告.md` + worker 工具日志 + 核验 worker 的 web 源经 `collect_citations` 已汇入回合「来源卡」），但**终稿正文未与来源卡连线**——读者看不到「这条抗辩的法条 = 第 [n] 张来源卡」。2026-06 讨论对齐 **方案① + Gap B = CEO content** 后已落地，属**后端行为变更**，**未新增事件类型**。

### 11.1 机制（含落地后事实）

| 事实 | 落点 |
|---|---|
| 来源卡 = `{url, title, snippet, site}`，dedup 键 = `url`（**url 为空即丢**），每回合上限 24 | `runtime/citations.py`（`_citation_key` / `merge_citations` / `_CITATION_CAP`） |
| `web_search` / `read_url` 产 citations（来自结果 url/title/snippet） | `tools/builtin/web/*` |
| 核验 worker 的 web 源汇入回合来源卡（仅 COMPLETED worker） | `delegate` `collect_citations → add_citations → merge_citations`；回合收口再 `merge_citations(citations, delegate_tool.citations)`（`pipeline/run.py`） |
| **`delegate` 单次调用的新增 citations 随 `ToolResult.citations` 返回**（CEO 路径 `execute_tools` 当场编号并 `annotate_tool_citations` 折 `[n]=url` 回工具消息） | `tools/builtin/delegate/drive.py`（Gap A） |
| `citations_event` 收口前发、卡贴流式气泡（`if citations:`） | `pipeline/run.py` |
| **造引用闸门**：CEO 正文 `[n]` 越界（> 来源卡数）→ 判编造引用、回炉一轮 | `runtime/verify.py` `finish_guard` + `citations.out_of_range_markers` |
| CEO 终稿走**收口正文完整输出**、已核验法条带 `[n]`、`[待核验]` 不编角标 | `runtime/legal_skills.py` `legal_answer_brief` 收口段（Gap B） |

### 11.2 原 gap（已闭合）

- **Gap A — 终稿不带 `[n]` 角标连线** ✅：`delegate` `ToolResult` 携带本次调用新增（去重后）citations → CEO 路径 `execute_tools` 当场 merge 编号 + `annotate_tool_citations` 折回 `[n]=url`；回合收口 backstop merge 幂等、编号稳定。单测：`tests/delegate/test_nesting.py::test_delegate_result_carries_this_calls_new_citations`。
- **Gap B — 终稿产物形态未定** ✅：对齐 **CEO content**（正文出完整终稿 + 法条 `[n]`），工作区《答辩状初稿.md》等作可下载附件。单测：`tests/test_legal_skills.py::test_body_teaches_inline_final_brief_with_citation_markers`。
