## 一、范围与边界

**套餐**：以**产品完整度**为镜头——`project-context.mdc`「MVP = 6 模块全量 Day 1（聊天 / 多Agent / 角色分配 / 工具 / 进度 / 记忆）」这条承诺，逐模块**正向推导**（用户需求 → 产品设计 → 技术实现），核对每条「应有能力」是否真落地，把状态钉成一张矩阵，缺口登记定级。

**威胁模型替换为「完整度模型」**：不问安全，问**兑现**——每条应有能力落在 ✅已落地 / ⏳设计内延后(Day2/未来) / ⚠️部分(MVP 达成但有确认未落地的深化) / 🔀漂移(文档与实际不一致) 哪一档；并甄别 `dev-process` 警惕的两类病：**「实现冒充需求」**（用旧实现裁需求）与**「半成品冒充完整」**（占位 / stub 当功能）。

**锚定**：当前 main 工作树（`apps/server/agentcore` + `apps/desktop/src/renderer` + `docs/`）。自检用 Read，不与 git 对账。**应有能力的单一事实源**：`docs/01-产品/产品定位与品牌.md`（尤 §七 MVP Day1 vs Day2 边界表）+ 各模块 03/04 区设计文档；**as-built 证据**：[`项目审计.md` §七之二 功能清单](项目审计.md)（L1 证据已铺）+ 本轮针对性代码核验。

**不在本轮**（避免发散）：
- **L2 真模型质量**——「真模型产出好不好」属评估体系 nightly 主线，且**开发期无真实数据**（`dev-process`），本轮所有 ✅ 均为 **L1（管线 / 协议 / 逻辑层）**，不实跑真模型（见 PROD-004）。
- **垂直行业完整度**（法律垂直等）——平台核心无关，垂直插件另议（见 `07-规划/法律垂直场景设计.md`）。
- **创作工具产物体系**（文档 / 导图 / 多维表格 / 画布 / 幻灯片 …）的深挖——它**不在 MVP-6 模块内**，仅在 §五 工具模块顺带记其「可见占位」状态（PROD-003）。
- **工程健康 / 安全**——前五轮已覆盖。
