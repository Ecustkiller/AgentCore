# 职责晚绑定与动态再编排设计

> 🗂️ **状态：设计定稿 / 待落地（07-规划）**。多 Agent 协作的一个真痛：worker 的职责在 CEO `delegate` 那一刻就**绑定死**，但真实要干的活只有执行中才清楚——团队闷头按可能错的初始计划做完（「计划漂移」）。**已定方向（开发期激进重构）**：把执行模型从「CEO 下完计划即缺席」改为「**CEO 是波边界的监督者**」——`build_run_plan` 一次建全 DAG、节点可**晚绑定**、`WaveScheduler` 只在**决策边界**把控制权交回 CEO 再绑定后续。落地后把现状行为迁入 `03-AI核心` 对应文档、本文删除。
>
> **与 [`阻塞式求决策设计.md`](/docs/07-规划/阻塞式求决策设计.md) 的分界**：那篇解「worker 撞上**只有用户能定**的岔路 → 阻塞问用户」（痛点 B，已落地）；本文解「worker / 下游的**职责本身**该不该改 → 由 **CEO** 再绑定」（不同痛点）。两者都触及「worker 中途发现不对」，但**裁决者不同**（用户 vs CEO），机制不同。
>
> → 关联现状：[`编排器与CEO主Agent.md`](/docs/03-AI核心/编排器与CEO主Agent.md)（`delegate` 原语、委派判据、结构跟着证据走）、[`执行引擎架构设计.md` §十四/§十八](/docs/03-AI核心/执行引擎架构设计.md)（`WaveScheduler`、`checkpoint_after`/`steer`、Run 模型）、[`Agent协作模式.md` §二](/docs/03-AI核心/Agent协作模式.md)（禁止 Agent 直接通信）、[`多轮编排与队员热修.md`](/docs/03-AI核心/多轮编排与队员热修.md)（`revise` 续写）。

## 一、问题：职责在编排那一刻绑定得太早

**现状一句话**：worker 不是稳定的「专家实体」，而是 CEO 在 `delegate` 那一刻**临时捏出的一次性角色**（Phase 1 `agent_id == run_id`）——它的「职责」= CEO 这次给它写的那段 task，且角色 / 分工 / 工具 / DAG 依赖全在**编排那一刻**基于「用户请求 + 轻量探路」一次性拍定。worker 一次性、隔离上下文、不能反问、不能再委派（`depth ≤ 2`）。

**两个具体缺口**：

1. **绑定太早**：同一个 `delegate` 批次里，下游 worker 的 spec 在**上游产物还不存在时**就写死了。典型：CEO 一次声明「调研 A → 据 A 写报告 B」，但 B 该写什么要看 A 调研出什么——A 跑完发现真问题是 X 不是 Y，B 仍按「写 Y」的旧 spec 跑。
2. **CEO 下完计划即缺席**：CEO 调 `delegate` 后**停在那次工具调用上等整批回来**，执行期间不在场。真人经理会盯着结果改计划；我们的 CEO 死守预案、无法据中途发现纠偏。

## 二、产品需求：自我纠偏的聪明团队（正向推导锚点）

> 本节是设计的**需求锚点**：先定用户要什么，再谈技术怎么做（禁止用技术方便反推需求）。

- **谁用 + 心智**：大众用户，心智 = 管理一个 Agent 团队，自己是老板、对 CEO 下达、**不微操队员**。大众**不想微操**，要「扔个需求、拿到对的结果」——这是 `ask_user` 预填默认 / 聊天优先 / 老板不微操 的共同地基。
- **「绑定太早」的用户侧症状**：① **交付物跑偏**（按可能错的初始理解做完，没答到点 → 将就 / 重问 / 推倒重来）；② **看得见的浪费**（团队面板 / 图视图里用户**看得见**队员忙错方向，团队产品的浪费比单 Agent 更刺眼）；③ **团队显得不聪明**（CEO 死守预案 → 打脸核心卖点「真正的 Agent 团队协作」）。
- **真实需求一句话**：**结果要对，且团队能像聪明人一样按中途发现自我纠偏，而不是闷头按可能错的初始计划做完。**
- **关键产品张力**：大众用户**不要更多「重规划旋钮」**，要的是**团队自己变聪明**。故「计划漂移」的用户解法**主要是团队自我纠偏（CEO 自主再绑定），而非给用户更多干预入口**——用户只在**真正高杠杆**的岔路被叫一下（`ask_user` / checkpoint 已覆盖）。
- **呈现分层**：默认**无感**自我纠偏 → 留一条**可观测痕迹**（图上「计划已调整」轻标记 / 版本链，看得见不打断）→ 高杠杆才升成决策卡。
- **真痛认定**：已认定为真痛、不先捞日志阻塞开发；但仍在落地时**埋点观测**（晚绑定触发数 / 计划漂移返工数 / `escalate` 中 scope 信号占比）用于调参与验证。

> **需求 → 技术的挣得关系**：选「CEO 自主再绑定 / 晚绑定 / 按影响力分档」**不是因为技术最省，而是它恰好是大众用户要的形态**——自我纠偏的聪明团队，不是更多控制旋钮。

## 三、重新定位：绑定时机 + 再绑定回路（不是「静态 vs 动态」）

现状其实**已部分动态**（增量 `delegate` / `revise` / `escalate` / `plan_review` 四件套）。真正的缺口是两条：**① 绑定时机太早**；**② 偏离 → 再绑定的回路不闭合**。讨论里的两条路线恰是同一个「再绑定回路」的两半，且**收敛为一个机制**（见 §四）：

| 半边 | 路线 | 触发再绑定 |
|---|---|---|
| 自顶向下（主动） | CEO 重编排更动态 | CEO 在波边界对晚绑定下游定稿 |
| 自底向上（反应） | worker 更自治 | worker `escalate` 偏离 → 边界喂 CEO 再绑定 |

## 四、设计定稿：受监督的波循环

把「自我纠偏」做成**结构**、不依赖 CEO 自觉。

### 4.1 形态

- `build_run_plan` 一次建好**完整 DAG**（**开局可见全貌**——直接服务「团队显得有章法」的产品价值）。
- 节点可**晚绑定**：spec 在其依赖落地那一刻才定稿（部分 spec + 依赖完成时补全）。
- `WaveScheduler` 自主跑波，**只在「决策边界」把控制权交回 CEO**。边界 = ① 有待定稿的晚绑定节点 / ② 有 `escalate` 偏离信号 / ③ 声明了 `checkpoint`。
- CEO 在边界**定稿 / 再绑定 / 增删节点**，然后**续跑同一张 DAG**（不重建）。

### 4.2 双臂：同一波边界，让给用户 or 让给 CEO

现状波边界**已能挂起**——`checkpoint_after` → `plan_review` → **让给用户**。本设计在同一个边界加一条「**让给 CEO 内部再绑定**」的臂。两臂由**影响力**（决策④）选：

| 臂 | 触发 | 谁裁决 | 用户感知 |
|---|---|---|---|
| 让给 CEO（新） | 低杠杆：晚绑定定稿、据 escalate 微调下游 | CEO 自主 | **无感**（仅留图上「计划已调整」轻痕迹） |
| 让给用户（现有 `plan_review`） | 高杠杆：选错会让用户明显不满 / 推倒重来 | 用户 | 决策卡，挂起待答 |

> **复用而非另起炉灶**：两臂都走 `build_run_plan` / `WaveScheduler` 的边界机制 + [§18.2「唯一挂起原语」](/docs/03-AI核心/执行引擎架构设计.md)；让给 CEO 的臂本质是「调度器在边界把控制交回 CEO 的 ReAct 循环」，续跑同一 DAG。**不新增挂起子系统。**

### 4.3 成本纪律（避免激进 = 滥用）

- **只在真有决策的边界让出**：无晚绑定节点 + 无 `escalate` 的波，调度器自主跑过、不打扰 CEO。→ **CEO 回合数 = 真实决策点数，不是波数**。
- 简单对话（不 `delegate`）、稳定计划（全部预绑定、无偏离）**行为不变、零新增回合**。
- 只有**自适应 / 不确定**的计划才按边界付 CEO 回合——而那正是价值所在。

### 4.4 偏离信号：复用 `escalate` + 边界一等消费

worker 发现自己 / 下游 scope 错了，用现有 `escalate`（**非阻塞**）上报；信号在**波边界被一等消费**——CEO 据此重写未跑下游（复用 `RunSpec.steer` / 重定 spec）。给 `escalate` 加一个轻量 `kind=scope` 提示位（**扩展而非新原语**），让 CEO 在边界稳抓「这是职责偏离」而非淹没在自由文本里。

> **为何不为 scope 再绑定单立信号 / `InteractionKind`**：决策的是 CEO，worker 只需供「偏离事实」；worker 隔离上下文、缺全局信息，结构化「该怎么重拆」的提议易成噪声。单立 = 与 `escalate` 高度重叠（触发「补丁绊线」）。故复用 + 轻量 `kind` 位。

## 五、被吸收 / 被划清的边界

**被吸收为「受监督波循环」的特例**：

- **incremental delegate**：CEO 在边界增删节点 = 增量声明的结构化形态。
- **`bind_after_deps`（曾作候选原语）**：即「晚绑定节点」，已成本设计核心，不再是可选旋钮。
- **2c（escalate 喂再绑定）**：即 §4.4 的边界一等消费。

**划清的边界**：

| 与谁 | 关系 |
|---|---|
| 痛点 B（[`阻塞式求决策设计.md`](/docs/07-规划/阻塞式求决策设计.md)） | **不同**：那是「只有用户能定 → worker 阻塞问用户」；这是「CEO 重绑定计划」 |
| 2b 波内抢占（CEO 与 worker 并发监督） | **仍否决**：本设计是**波边界**让出，不碰「波内没有在跑的 CEO」那堵墙 |
| 禁止 Agent 直接通信（[`Agent协作模式.md §二`](/docs/03-AI核心/Agent协作模式.md)） | **不碰**：再决策走 CEO，无 worker↔worker |
| 嵌套委派 `depth ≤ 2` | **不碰**：晚绑定 / 再绑定不增深度 |
| 一个 CEO 声音 / 聊天优先 | **不碰**：再绑定是结构化 spec 改写、不灌散文；只在不确定接缝付回合、不给简单对话加税 |

## 六、5 决策（定稿）

| 决策 | 定稿 | 一句话理由 |
|---|---|---|
| ① 晚绑定形态 | **结构化晚绑定节点**（嵌进波循环） | 激进重构期由「可靠性 + 全貌可见」挣来，不靠 CEO 自觉、不只为预览 |
| ② 偏离信号 | **复用 `escalate` + 轻量 `kind=scope`**，边界一等消费 | 决策的是 CEO，worker 只供偏离事实；单立信号 = 补丁绊线 |
| ③ 触发归属 | **CEO 在边界结构性地决** | 它本就被叫到场；软护栏基本不需（列「实测漏触发率高再加」） |
| ④ 影响力分档 | **按影响力（双臂）** | 复用 `ask_user` / checkpoint 已确立的「按影响力分档」心智；自主再绑定默认 + 高杠杆弹用户 + 图上轻痕迹 |
| ⑤ v1 范围 | **建受监督波循环（结构重做）+ 埋点** | 开发期激进重构；埋点用于调参与验证真痛 |

## 七、落地契约与实现分期

> 本节是**实现层**契约；动手前逐条对照现网代码走查（参照 [`阻塞式求决策设计.md §4.7`](/docs/07-规划/阻塞式求决策设计.md) 的边界走查范式）。

### 7.1 调度器↔CEO 边界让出契约（已定）

**关键现实**：`delegate` 对 CEO 是原子的（CEO park 在一次工具调用上、跑完整棵 DAG）；但**波边界让出的缝（`WaveScheduler.on_checkpoint`）、再绑定（`_apply_steer`→`RunSpec.steer`）、续跑（`_drive(seed_completed=…)`）都已存在**，现状只「对用户开」（→`plan_review`）。本契约把它们**扩成也对 CEO 开**，不从零造。

**架构（已定）：返回 CEO 的 ReAct 主循环（方案 A）**——否决「调度器内对 CEO 发聚焦子调用（B）」：B 会在主循环外重造一条规划 LLM 路，违反「无独立编排器 LLM、CEO 既对话又规划于同一 ReAct 循环」。

| 组件 | 改动 |
|---|---|
| `RunSpec`（types.py） | 加 `bind_after_deps: bool=False`；为 True 的节点 spec 关键字段可先占位，依赖完成后由 CEO 在边界定稿（复用 `steer` 的 in-place mutate 范式） |
| `WaveScheduler`（wave.py） | `on_checkpoint`→`on_boundary`：触发集加「`bind_after_deps` 且依赖完成、未定稿的节点」「completed 节点带未消费 escalation」；返回 `BoundaryOutcome ∈ {PROCEED, YIELD, ABORT}`。`YIELD`=软暂停（复用 `should_stop` 语义：排空 in-flight、返回 partial、尾部不 skip）。调度器仍纯：触发判据用 host 注入谓词 |
| `delegate`（delegate.py） | `_drive` 收到 `YIELD`→返回**非终态 ToolResult（CONTINUE）**+「边界简报」给 CEO 主循环，暂存 `(plan, completed)` 于 `self._supervised`；CEO 决策后经续跑入口 `_drive(plan, seed_completed=completed)` 接着跑 |
| `build_run_plan`（builder.py） | `_inline_spec` 宽松解析 `bind_after_deps`；DAG 校验放行占位 spec |

**续跑入口（已定）：专用 `replan` 工具**（否决重载 delegate / 复用 revise）——CEO 在边界一次 `replan(binds=[{run_id, task/role/tools…}], steers=[{run_id, note}], add=[<task>…], stop=bool)`：定稿晚绑定节点 / 再绑定未跑下游 / 追加节点 / 或就此收口；非 `stop` 即续跑同一 DAG。让「计划已调整」成为可观测一等动作。（v1 `tools/builtin/replan.py` 先实现 `binds`/`steers`/`stop`；`add` 因需另管 id 生成与依赖接线、复杂度独立，推迟到后续阶段——见 §7.3 P3。）

**复用（不另造）**：再绑定=`_apply_steer`+`RunSpec.steer`；加节点=`RunPlan.add`+`RunOrigin.CAPTAIN`；续跑=`seed_completed`；**CEO 臂走正常回合生命周期**（非终态返回=普通 ReAct 续跑=已被 C1 detach/resume 覆盖），plan/completed 由 `plan_from_journal`/`completed_from_journal` 重建——**CEO 臂不需新 durable 挂起**（区别 user 臂的 `paused_turns`）。

**成本纪律**：无晚绑定/无 escalation/无 checkpoint 的 plan，scheduler 一路跑到 terminal、一次 delegate 返回（=今天行为、零新增 CEO 回合）。

### 7.2 其余实现落点（⏳）

- **`escalate` `kind=scope`**：信号扩展 + 边界消费（CEO 在边界读取并 `replan` 未跑下游）。→ `tools/builtin/escalate.py`、`tools/protocol.py`。
- **前端「计划已调整」轻痕迹 / 版本链**：自主再绑定的可观测呈现（图上轻标记，对齐 P-2 版本链范式）。→ [`前端UX设计.md`](/docs/04-前端/前端UX设计.md)、协作图视图。
- **埋点**：晚绑定触发次数 / 计划漂移返工次数 / `escalate` 中 scope 信号占比（类比 `BatchMetrics` sink）。→ `runtime/runs/types.py`、`wave.py`。
- **跨端 conformance**：`YIELD` 给 CEO 不产生新的对用户可见事件分类（内部 ReAct 续跑）；`replan` 若产生「计划已调整」事件则按 `protocol-conformance` 扩契约 + 加向量。
