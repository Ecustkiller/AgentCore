# AI 实测案例复盘 🗂️

> **定位**：记录真实产品 AI 运行日志里的代表性案例，供后续 AI **按 key 反查全链路日志**、定位优化点。每条案例 = 关联键（可反查）+ 现象时间线摘要 + 观察到的优化点（挂回对应正式文档的优化项，或 [`远期规划.md`](/docs/07-规划/远期规划.md) 的远期 backlog）。
>
> **治理**：本目录仅 `07-规划`；🗂️ = 讨论中、未承诺落地。本文只做**现象记录 + 优化点线索**，不含改造方案——选定项的落地设计另起文档。某项决策通过、转入落地后，把结论迁入对应正式文档、本条退役。
>
> **怎么反查日志**：方法见 `.cursor/rules/conversation-logs.mdc`。常用（在 `apps/server` 下跑）：
> - `uv run python scripts/log_timeline.py <conversation_id>` —— DB 消息正文 + 日志事件合并的会话时间线
> - `uv run python scripts/log_timeline.py --trace <trace_id>` —— 单次交互全链路（含委派 worker 嵌套）
> - **探针法**（进程内、不经 HTTP）：在 `apps/server` 下写一次性脚本，`from agentcore.conversation.service import stream_chat` 直跑一回合（取首个有 BYOK key 的 user），完成后 `select(RunSessionRow).where(conversation_id==...)` 读每个 worker 的 `spec.task`（看 CEO 怎么交活）与 `transcript` 的 `file_write` 实调用（`function.arguments` 是 JSON 串，取 `path`/`content` → 抽 Markdown 标题）。判越位看「产物标题是最终交付物名还是调研笔记名」+「位置块是否注入」。用完即删脚本（勿留 `scripts/`）。
> - ⚠️ 消息正文在 Postgres（`messages` 表），`logs/dev.jsonl` 只有事件与 `preview`。

## 案例 1 · 「研究第三者赠与合同纠纷 + 写论文」长回合连接中断

### 关联键（反查用）

| key | 值 |
|---|---|
| conversation_id | `5caff040-8647-4b8f-8dc4-39601c295b8e` |
| trace_id | `e2bf81efe3624e8facfc2bc1e6efaf8b` |
| turn_id | `55fad20d-8a8f-480b-bb7e-b0fadb10d376` |
| user_id | `5b86ae73-1b0c-4637-92a6-ae2c35cc12df` |
| 时间 | 2026-06-17 21:04:27 → 21:11:28（约 7 分钟） |
| 模型 | `deepseek-v4-flash`（全程 chat 场景） |

- **用户输入**：「我想研究下第三者的赠与合同纠纷、写一篇论文」
- **结局**：**连接中断、本回合未完成**（`chat.incomplete_persisted`，events=20521）；用户只拿到「已完成队员产出」（paper worker 写出的论文），CEO **未收敛交付**。

### 现象时间线（摘要）

- **CEO**：round0 `consult_skill(asking_the_user)` → round1 `ask_user` 澄清（用户 ~63s 回复）→ round2 `delegate` **5 节点**（cases / academia / law / comparative / paper）。
- **收敛失败**：4/5 worker（cases·academia·law·comparative）`max_rounds_exhausted`（4 轮耗尽仍 `done=False`）；仅 paper 完成。
- **出网受阻**：`read_url` 对国内法律站点（`gov.cn` / `chinacourt.org` / `hunancourt` 等）大面积失败——`SSL CERTIFICATE_VERIFY_FAILED` / 连接超时 / 出网受限 → cases worker 触发 `tool_circuit_breaker`（`disabled=['read_url']`）。检索 worker 退化为大量 `web_search`（academia 16 工具 / cases 13 / law 14）。
- **长尾延迟**：paper 生成单次 `llm.call` latency≈**170s**（output_tokens=12054）；多次收敛/合成 `llm.call` 55–72s。
- **根本张力**：7 分钟长回合 + 执行绑单次请求/SSE → 中途断连即**丢交付**。

### 观察到的优化点

| # | 现象 | 优化线索 | 关联（落点） |
|---|---|---|---|
| 1 | 7min 长回合断连即不可交付 | 执行与请求解耦 + 可靠续跑（durable execution / resume） | ✅ **A1 执行级 Journal** + ✅ **C1 slice 1a 断连续跑 + 1b 实时重连续看**（断连不取消、后台跑完落库、重连回放+tail 续看，契约见 [执行引擎 §执行与请求解耦](/docs/03-AI核心/执行引擎架构设计.md)）；余 C2（跨进程） |
| 2 | `read_url` 对国内法律站点大面积失败（SSL/超时/出网） | **✅ 已落地**：出网/SSL 韧性——SSL 证书校验失败识别 + 诚实报错并引导回退 `web_search`、超时分级（connect 5s / read 15s）、每主机熔断、5xx 抖动重试、SearXNG 启动可达性探针；**可靠回退搜索（Tavily）已补齐**——配 `TAVILY_API_KEY` 后主 SearXNG 失败即回退 Tavily（`FallbackSearchBackend`，仅失败时触发、成功零额外成本） | → 见代码 `tools/builtin/web/_net.py` / `search_backend.py`，测试 `tests/test_web_tools.py` |
| 3 | 4/5 研究型 worker 4 轮耗尽未收敛 | **✅ 已调档位预算**：`agent.fast` 轮数上限 4→8（上限≠必耗，早收敛任务零成本；真·深研究仍属 `strong` 28 档），不建启发式分类器 | 收敛治理 ✅ [执行引擎 §十四](/docs/03-AI核心/执行引擎架构设计.md)；轮数值见 `llm/config.py PROFILES`；模型路由 `classify_task` ⏳ [执行引擎 §十六](/docs/03-AI核心/执行引擎架构设计.md) |
| 4 | 论文一次性生成 170s（长尾、放大断连风险） | **🗂️ 已决·暂缓**：可靠性已由 C1（断连后台续跑、生成照常落库）覆盖，残留仅长文单次生成延迟（低频 UX）；字面「流式落盘」后 C1 边际收益最低、不降延迟、且破坏「工具原子执行+审批」模型，故暂缓——若长文延迟成高频真实痛点，倾向「分段写作 + `file_append` + 大纲优先」而非引擎级流式落盘 | 能力/质量项·暂缓 → [远期规划 §三](/docs/07-规划/远期规划.md) |
| 5 | 检索 worker 大量重复 `web_search` | **✅ 已落地检索去重 / 共享检索缓存**：会话级 `web_search` 结果缓存（镜像 `read_url` 的 `ConversationUrlCache`）——同会话重复 query（含全队 worker，共享 `conversation_id`）命中内存、不重打 SearXNG/Tavily，省网调 + 降并发熔断压力 | → 见代码 `tools/builtin/web/search_cache.py`，测试 `tests/test_web_tools.py`；余「回合内工具清理（`clear_tool_uses` 省 token / 治 context rot，动热循环）」仍 [远期规划 §三](/docs/07-规划/远期规划.md) |
| 6 | CEO 委派 paper 时把论文骨架（各章标题分节 / 字数 / 参考文献数）在 task 里定死，worker 沦为填字员 | 划清「约束 vs 方案」边界（方案归专家）+ 把定结构做成证据驱动、可把关的显式步骤（**已落地**） | → 已落地，见 [编排器与 CEO §认知分工判据](/docs/03-AI核心/编排器与CEO主Agent.md) |

> **净信号 / 收口（2026-06-18）**：本案例是 **A1（执行级 Journal）+ C1（执行/请求解耦）** 的强证据，6 个优化点已全部处置——
> - **✅ 已落地**：#1 痛点「长回合断连丢交付」由 A1 + C1 slice 1a/1b 消灭（断连续跑、后台落库、重连回放续看；余 C2 跨进程归 [远期规划 §一](/docs/07-规划/远期规划.md)）；#2 出网/`read_url` 韧性（SSL 诚实报错 + 超时分级 + 每主机熔断，`tools/builtin/web/_net.py`）+ 可靠回退搜索 Tavily（`search_backend.py`）；#3 `agent.fast` 轮数 4→8（不建分类器）；#5 会话级 `web_search` 检索去重缓存（`search_cache.py`）；#6 认知分工（[编排器与 CEO](/docs/03-AI核心/编排器与CEO主Agent.md)）。
> - **🗂️ 已决·暂缓**：#4 长文分段生成——C1 已覆盖可靠性、长文延迟属低频 UX，引擎级流式落盘性价比最低（见上 #4 行）。
> - **⏳ 待提案**：回合内工具清理（`clear_tool_uses` 动热循环，[远期规划 §三](/docs/07-规划/远期规划.md)）。
>

## 案例 2 · 「AI Agent 记忆机制综述报告」上游越权写最终交付物（D 前/后对照）

> 本案例验证「团队协作语义」的角色/结构杠杆（**D·团队位置块**）落地前/后效果：同一研究级请求跑两次，看上游 worker 是否还越权写整篇报告 + 空路径 `file_write`。这些杠杆（L3 / A / D / A1）的**行为契约已落地**，见 [编排器与 CEO §worker 侧认知分工收口](/docs/03-AI核心/编排器与CEO主Agent.md)。证据取自 `run_sessions` 表的 `spec`（CEO 派的 task）与 `transcript`（worker 的 `file_write` 实调用）。

### 关联键（反查用）

两轮同一 user_id `5b86ae73-1b0c-4637-92a6-ae2c35cc12df`、同一 prompt（「请调研并撰写一份《2025 年 AI Agent 记忆（Memory）机制》综述报告……保存到工作区。需求已明确，请直接开工」）。模型：dev 默认 chat 档（`deepseek-v4-flash`）。

| 轮次 | conversation_id | trace_id | 时间（UTC） | 节点 |
|---|---|---|---|---|
| D 前（A/B 已落地、D 未落地） | `dbb2e3f1-147a-436b-adb4-2b01bd075a1f` | `bfb6cae8a2c64c3b9983d73b382f131e` | 2026-06-17 22:17→22:23 | 2 调研员 ∥ + 1 写手 |
| D 后 | `46a67c8a-543a-4531-9458-3d9d314edfbd` | `0f93bd02208447d8a972df66a3f5143a` | 2026-06-17 22:35→22:41 | 4 研究员 ∥ + 1 技术写作专家 |

### 现象对照（按 `transcript` 的 file_write 实证）

**D 前 — 两个上游调研员都越权写整篇报告 + 空路径：**
- 调研员A：`file_write(path=None)` ×3，前两次 content **16716 字 / 72 个标题**（整篇报告级，重试），第三次 3278/13；
- 调研员B：`file_write(path=None)` ×3，前两次 **12127 字 / 65 标题**，第三次 13 字；
- 写手：`file_write(path='agent_memory_report_2025.md')` ×1（12233/23）——唯一带文件名者。
- → 上游把自己当最终作者，写出 65–72 标题的整篇报告投向**空路径**；空路径守卫拦下、退回 prose，写手照常拿到上游产出。

**D 后 — 越权显著收敛，空路径仍残留：**
- 4 研究员里 **2 个（survey_eng / survey_framework）零 file_write**，纯 prose 交回（✓ 干净）；
- 另 2 个（survey_academic ×3 / survey_taxonomy ×2）仍 `file_write(path=None)`，但内容降到 **28–38 标题（调研笔记级，非整篇报告）**；
- 写手（技术写作专家）：`file_write(path='ai-agent-memory-survey-2025.md')` ×1（13320/43）✓。
- → 上游不再写「整篇最终报告」；残留的是「想把调研笔记落盘却漏文件名」。

旁注：两轮 CEO 给 worker 的 `contract` 均为 `null`（未用合同位）；D 后写手 task 的结构是「以下是建议框架，可灵活调整」（比 D 前写手 task 的硬「结构:」更软）；D 后 CEO 先自做一轮「轻量探路」再委派。

### 观察到的优化点

| # | 现象 | 优化线索 | 关联（落点） |
|---|---|---|---|
| 1 | D 前上游写 65–72 标题整篇报告投空路径 | 团队位置块给上游「你是中间环、别产最终物」 | → 已落地 D，见 [§worker 侧认知分工收口](/docs/03-AI核心/编排器与CEO主Agent.md) |
| 2 | D 后仍 2/4 研究员 `file_write` 空路径（想落盘笔记却漏名） | 许可式提示：想落盘就自起描述性文件名 | → 已落地 A1，见 [§worker 侧认知分工收口](/docs/03-AI核心/编排器与CEO主Agent.md) |
| 3 | run1 即时委派零自研、run2 先自做一轮探路再委派（方差） | 已跨 trace 实测（现有 logs 8 委派 trace，不含本案例两 run）：委派前深读 7/8=0、委派后全=0，唯一尾巴 N=1 → 判定低频单案例、不动提示词 | → 已判，见下方 §方法与未决项 · B2 |
| 4 | 写手 task 仍带通用结构脚手架 | 决策：不再收紧 CEO 刹车，靠 A/D 在接收端兜 | 见 [§worker 侧认知分工收口·关键取舍](/docs/03-AI核心/编排器与CEO主Agent.md) |

> **净信号**：**D（团队位置块）有效**——上游从「写整篇报告」退回「做好中间环」；残留的空路径 `file_write` 已由 [A1（上游落盘起名许可）](/docs/03-AI核心/编排器与CEO主Agent.md) 在同一上游分支补上（零散→prose、大产物→`findings-<角色>.md`），不再依赖空路径守卫兜底。

## 方法与未决项（跨案例）

> 不绑定单条 conversation 的方法学告诫与跨 trace 实测结论。从原「团队协作语义优化」提示词层盘点迁入（该文已退役）——其行为契约（L3 / A / D / A1）落地于 [编排器与 CEO §认知分工判据 / §worker 侧认知分工收口](/docs/03-AI核心/编排器与CEO主Agent.md)，开放的度量 / 未决项归此。

### B1 · L3 / 角色越位的自动量化不可靠

- **现象**：用「数 task 里的编号列表 / Markdown 标题」当越位信号**误报严重**——分不清「给调研员派的调研角度（=范围，CEO 该干的）」与「给写手定的章节结构（=越位）」；项目符号大纲还会漏判。
- **方法结论**：测 L3 / 越位（如案例 1 #6 那类）用**人工读 task** 或更可靠的分类器（如一次小 LLM 判「这段是需求范围还是章节结构」），别再拿纯计数下结论。

### B2 · CEO「自研 vs 委派」的方差（跨 trace 扫描，独立于案例 2）

- **现象**：同一研究级请求两跑出现方差——run1（案例 2 · D 前）CEO 即时 `delegate`、零自研；run2（D 后）先自做一轮轻量探路再委派。核心提示「你自己的检索留给对话式直答与开工前轻量探路，不替团队扛调研腿脚活」**本就允许**轻量探路，故 run2 未必违规；真正的风险是难判它何时从「探路」滑向「自扛调研腿脚」。
- **量化判据（确定性、已用它跑出结论）**：CEO 自研可从日志**确定性**地数——`tool.execute_end` 按 CEO 作用域（`depth` 空，worker 带 `depth=1/2`）筛 `web_search` / `read_url`，再用首个 CEO `delegate`（`delegate.started` 或 `tool.execute_end tool=delegate`）时间戳**按 `trace_id`** 切「委派前=探路 / 委派后=收敛期自研」。**`read_url` 次数是最锐信号**：`web_search`=摸格局（轻量探路本该如此），`read_url`=钻进来源深读=调研员的腿脚活。
- **实测结论**（2026-06 现有 `logs/dev.jsonl`，逐 trace 拆，与案例 2 两 run 不重合——独立的跨 trace 扫描）：8 个「CEO 真正发起委派」的 trace 里——**7/8 委派前 `read_url`=0**（零深读就派活，正是想要的管理者行为）；**8/8 委派后 `read_url`/`web_search`=0**（「收敛期还自研」这个担心**完全不存在**，彻底划掉）；**唯一尾巴** trace `e824eef4`（用户请求「帮我产出一个最新的学术文章」）委派前自跑 4-5 轮 / 4 `web_search` / 6 `read_url` 深读 6 个页面才委派——真实但孤立的自扛腿脚。先前「CEO `read_url×19`」的吓人聚合就此拆解：6 次在这单个尾巴 trace 的委派前，其余 13 次全在**没委派的回合**（CEO 直答用户、自查完全正确，不算 B2）。
- **判断 → 不动提示词**：B2 是真的，但**稀、单案例方差、非系统问题**。正样本 N=1，拿 1 个案例动提示词正踩 B1 的过拟合坑，还会「让 CEO 连合理探路都不敢」。**dev 期不立伪指标、不动提示词、不给 CEO 加探路预算 / 自研刹车**；确定性配方（上方判据）留作上线后真实用量的现成度量（一次性探针用完即删，勿留 `scripts/`）。
