# 项目审计 · 成本 / 性能专项（第七轮）

> **状态**：🗂️ 首扫已收尾（后端 LLM 成本面 + DB 查询面 + 编排热路径三向静态 profiling）。**零 P0/P1，登记 11 条：3 条 P2 + 8 条 P3**——无任何「错」，全为**规模化优化 / 防御纵深**。承接 [`项目审计.md`](项目审计.md)（首轮·全栈健康体检，已结案）§一「不在首轮范围」之**「成本/性能 profiling（token/计费路径/热点）」**与 §十一之三「下一轮专项」决策——前六轮专攻工程健康 / 安全 / 产品完整度（健康 → 安全 → 提示注入 → 前端 XSS → IPC 权限面 → 产品完整度），本轮首次从**成本与性能**视角问：每个用户回合烧多少 token、走多少 DB 往返、首字延迟卡在哪。
>
> **⚠️ 开发期无真实数据（`dev-process` 纪律）**：本项目当前**没有任何真实运行数据**（无真实对话 / token 计量 / DB 慢查询日志 / 火焰图 / 压测）。**故本轮是「静态成本/性能审计」而非「动态 profiling」**——所有热点均来自**读代码 + 复杂度推演**，以 `conformance/vectors`、`evals/` 合成样本与代码常量为依据。凡涉及「在真实负载下多慢 / 多贵」，均为**假设**，须待有真实数据后用真 profiler 验证再排序。**因此本轮不给「优化 ROI 排序」，只给「静态可坐实的热点 + 修法方向 + 严重度」。**
>
> **本文是什么**：成本/性能维度的**发现与登记册 + 热点地图**。沿用前六轮的严重度（P0–P3）与登记字段；**只发现 / 登记 / 定级，不在本轮顺手改代码**（修复各自按 `dev-process` 立项，索引 / 契约级改动须人确认）。
>
> **核心结论**：**架构层面成本/性能是「健康且克制」的**——全链路 async、扇出有界（工具×5 / 子任务×8 / 辩论 gather+信号量）、提示走 DeepSeek 前缀缓存友好布局、journal 读批量化（无 N+1）、长对话有压缩。本轮**未发现任何性能缺陷或失控成本**。真正值得登记的是**规模化前该补的优化**——皇冠明珠是 **`messages` 缺 `(conversation_id, created_at)` 复合索引（PERF-001）**：它托底全 App 最高频的「打开对话」查询，是**纯增量、零契约、零回归**的最高性价比修复。其余为 token 防御纵深（无上限注入 / 无预算闸）与回合尾延迟（标题/追问/快照阻塞流关闭）等 deferred 项。

- **性能面**：DB 查询模式（N+1 / 缺索引 / 无界读）、回合热路径与并发模型、首字延迟（TTFT）、回合尾阻塞、每回合重复计算。

**锚定**：当前 main 工作树（`apps/server/agentcore`）。自检用 Read，不与 git 对账（`.cursor/rules/git-workflow.mdc`）。**单一事实源**：代码本身 + `docs/03-后端/执行引擎架构设计.md`（提示/压缩/扇出常量）+ `.cursor/rules/llm.mdc`（DeepSeek 计费事实）。

**不在本轮**（避免发散）：
- **真实负载 profiling / 压测 / 火焰图**——开发期无真实数据（见上方纪律声明），属上线后运维主线。
- **前端运行时性能**（renderer 重渲染 / 虚拟列表 / bundle 体积）——本轮聚焦后端成本/性能；前端仅在 §六 备注一句已知项。
- **基础设施成本**（DB 实例 / S3 / 带宽计费）——非代码层，另议。

**已确认良性（无需登记）**：全链路 async（FastAPI + asyncio + httpx 流式）；扇出有界（工具 `Semaphore(5)` / 子任务 width≤8 + ContextVar 树预算 / 辩论 gather+信号量）；提示**前缀缓存友好**（稳定前缀在前、易变尾在后、日期按天粒度，DeepSeek cache_hit ~50× 便宜）；journal 读**批量化无 N+1**（`load_map`、`counts_for_conversations` GROUP BY、IM peer 批量）；cost 账本多行 `pg_insert + on_conflict_do_nothing`；长对话**压缩**（64k 触发、摘要复用不每回合重算、保前缀缓存）；后台记忆整合 / 压缩**正确 fire-and-forget**、不阻塞响应；工作区快照走 `asyncio.to_thread` 不堵事件循环。

## 九、COST 护栏设计提案（COST-001 + COST-004 · AI 提案待人确认 · 2026-06-30）

### 九之一 · 定位：激活既有设计，不是打补丁（绊线自检）

两条护栏**都不是新兜底逻辑**，而是激活/补全代码里**已为此设计**的接缝：

- **COST-004** 用的 `PromptContributor.budget` 字段 + `ContextAssembler` 已留位（`runtime/context/contributor.py:55-57` 注释明言「字段存在，供**扳机 B** 一处读」；`render()` 今不强制）。
- **COST-001** 是写侧已有上限的**读侧孪生**：写侧 `memory_section_bullet_cap=20` + `memory_max_topic_files=24`（`config/persistence.py:20-23`）已在**整合时**限规模；缺的只是**注入读侧**对最终 `<rules>` body 的 char 兜底。

故不触发 `dev-process` 绊线（非兜底/对账/特例新逻辑、非同根因多层补丁）；无新依赖、无契约变化（纯内部 + 日志）。

### 九之二 · 硬约束（设计铁律，必须先讲）

`SectionOrder`（`contributor.py:35-46`）把系统提示分**稳定前缀区**（BASE 100 → CEO_VISUALIZATION 700，**含 MEMORY 300**）与**易变尾**（WORKSPACE_OVERVIEW 800 / ATTACHMENT 900）。DeepSeek **精确前缀缓存**靠稳定前缀**逐日字节不变**（cache_hit ~50× 便宜）。

⇒ **铁律**：
1. 稳定前缀段（含记忆）只能用**确定性、跨回合稳定**的 cap（同内容→同截断结果→前缀不变；在 cap 下完全不动）。**严禁**「按本回合剩余预算动态裁前缀」——那会每回合改前缀、**每回合打穿缓存、反而更贵**，南辕北辙。
2. 动态/按需裁剪**只能作用于易变尾**（800/900），不碰缓存前缀。

### 九之三 · COST-001：记忆注入上限（读侧 backstop）

**现状**：`memory/injection.py:33-56` `load_injected_memory` 把 偏好.md + 画像.md（+项目画像）chrome-strip 后 `\n\n` 拼接，**无 char cap**。

| 选项 | 做法 | 评 |
|---|---|---|
| **A（推荐）** | **分文件确定性 cap**：每文件截到 `memory_injected_file_char_cap`（默认 ~4000，对齐 `compaction_summary_char_budget`），超出「保留头部 + 尾注『（记忆过长已截断，建议精简）』」+ 记 `memory.injection_truncated` warning | 确定性→**保前缀缓存**；与写侧 bullet cap 对称；可观测；默认宽松只拦异常膨胀 |
| B | 合并后**整体 cap**，超出按 偏好>画像>项目 优先级逐个截 | 跨文件耦合、略复杂 |
| C | **只告警不截**（超 cap 仅日志/管理面报，不动内容） | 零信息损失、最保守，但不省 token |

**推荐 A**：确定性截断是唯一既省 token 又不打穿缓存的解；默认阈值宽松（正常用户的偏好/画像远不及 4000 字），仅作异常膨胀的安全网。

### 九之四 · COST-004：提示预算闸（事前 guard）

**现状**：`budget` 字段 + assembler 留位但 `render()` 不强制；无事前估算；仅事后 provider token + 日配额（`conversation/quota.py`）。**单位用 char**（全仓 cap 皆 char、无 tokenizer；保持一致、不引 tiktoken；char 代理足以拦异常膨胀）。

## 十、PERF-003 落地（读时缓存 fold · 2026-06-30）

### 十之一 · 为何选「缓存」而非「瘦 DTO 懒加载」

审计给了两条修法，**亲核前端后排除懒加载**：`apps/desktop/.../services/messages.ts` 的 `toMessage()` 在**列表加载时**就从 `m.runs` 重建内联团队图、检查点、计划复核、`process` 时间线、CEO 收到上下文、结束原因、错误卡，`AssistantMessage.tsx` 同步内联渲染。故 `runs` 必须**随列表立即返回**——

- **瘦 DTO + `/messages/{id}/detail` 懒加载**：改 REST 契约 + 前端/移动端联动改造，且团队图会「先空后弹」**伤 UX**。✗
- **按 journal 版本缓存 fold 投影**：纯服务端、**不改契约、不伤 UX**（`runs` 仍随列表返回，只是不再重复计算）。✓ 属 `dev-process`「实现细节 / 性能优化（不改契约）= AI 自主」。

### 十之二 · 实现

`runs_from_entries` 是 journal entries 的**纯函数**，而 §8.3 journal **每回合追加式**（resume 只追加、完成回合的事实不就地改）→ 投影在 journal 增长前稳定，可按版本 memoize。

| 改动 | 文件 | 内容 |
|---|---|---|
| 缓存 | `runtime/journal/fold_cache.py`（新） | `runs_from_entries_cached(message_id, entries)`：按 `(message_id, 条数, 末条 ts+kind)` 这一 **O(1)** 版本键 memoize；命中跳过 fold，追加（resume）→ 新键重算。有界 LRU（1024 条）、进程内、FastAPI 路由在 await 间同步 fold 故 OrderedDict 无需锁。**miss 即原 fold → 正确性永不依赖缓存**（可随时清空/禁用零行为变更） |
| 接线 | `api/routes/conversations/messages.py:106-119` | 列表投影 `runs_from_entries(...)` → `runs_from_entries_cached(m.id, ...)`，输出逐字节不变 |
| 导出 | `runtime/journal/__init__.py` | 加 `runs_from_entries_cached` / `clear_runs_cache` |

**收益面**：消除「重开对话 / 每回合后重载最新窗 / 回滚再前翻」对**未变回合**的重复 fold + 合成 delta。**注**：批量 `load_map` 的 DB 查询本就无 N+1、保持每次执行（缓存只省 fold CPU，不缓存 DB）。

### 十之三 · 测试与校验

`tests/test_fold_cache.py`（7 例）：与未缓存 fold **等价**、命中**返回同一对象**、清缓存/journal 追加**触发重算**、按 `message_id` **隔离**、空/None **不缓存**、LRU **上限淘汰**。`test_fold_cache + test_turn_journal + test_engine_facts + test_turn_facts` **51 passed**、`ruff` 全清、`ReadLints` 无误（顺手修了 `journal/__init__.py` 一处既有 E501 文档行）。
