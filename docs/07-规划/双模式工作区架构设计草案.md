# 双模式工作区架构设计草案（云 + 本地双模式）🗂️

> **定位**：工作区（项目空间）架构草案。回答「AI 对话能选文件夹、并在该文件夹工作」这一需求，落到一套可同时支撑**云**与**本地**两种模式的分层。**两种模式平等**——「先做云、后做本地」只是构建顺序；**不给用户云/本地开关，模式跟着「文件在哪」自动走**（见 §七）。代码未落地。落地前以本文为蓝图，正式接口契约迁入 [`核心接口定义.md`](../02-架构/核心接口定义.md) 与 [`执行引擎架构设计.md`](../03-AI核心/执行引擎架构设计.md)。

## 一、现状：三个割裂的「文件夹」概念

| 概念 | 在哪 | 现状 | 代码 |
|---|---|---|---|
| 侧边栏 `Folder.local_dir` | 服务端 DB | **纯标签**（注释明说 opaque metadata, no FS coupling）；会话靠 `folder_id` 挂载 | `db/models.py` Folder / Conversation |
| 桌面 FS Roots | Electron 端 | 用户 `openDirectory` 选本地目录，仅用于读出文本喂 **@ 附件**（临时上下文） | `apps/desktop/src/main/fs-service.ts` |
| AI 工作区 `workspace_dir` | 服务端 | **写死 `Path.cwd()`**，全会话共用 | `runtime/pipeline.py:120` |

**关键缺口**：缺的不是壳，是把三者接起来。具体接缝已勘明：

- `_run_and_persist` 调 `run_chat_pipeline` 时**未传 `folder_id`**（`conversation/service.py:92`）——工作区无从按会话/文件夹差异化。
- 文件工具（`file_ops.py` 的 read/write/list/str_replace + `grep.py`）全部经 `resolve_safe_path(context.workspace_dir, …)` 取边界（`tools/builtin/_paths.py`）——**只要改 `ToolContext` 一处，5 个文件工具自动跟随**。
- worker 在 `runs/executor.py:96` 用 `replace(base_tool_context, …)` 继承工作区——**团队全员自动随 `ToolContext` 走**，无需逐 worker 改。
- ⚠️ 潜伏 bug：`code_execute` **根本没用** `workspace_dir`（`ExecutionRequest` 无 cwd，`code_execute.py` / `sandbox/protocol.py`）——今天「代码」和「文件」压根不在同一目录。

## 二、需求推导结论：两种模式平等，云是零前提的起点

按「用户需求 → 产品设计 → 技术实现」正推（论证全文见会话决策记录，此处只留结论与理由）：

- **内核需求**：给每次协作一个**持久、可累积的项目空间**——多 Agent 在同一张「桌子」上靠文件协作，这才是「工作台 + 真正团队协作」的物理载体。「在不在我本地磁盘」是第二层偏好，不是内核。
- **云模式（服务端托管项目空间）= 零前提的起点**：打开即用、不暴露整块磁盘；并行 Agent 团队在同一台服务端协作，天然可观测、可隔离——正是产品差异化（团队）的主场。
- **本地模式（桌面本地执行，对标 Cursor）= 平等的另一种，后做**：服务开发者内环（改我真实本地仓），代价大（搬运行时，详见 §六 P2）。
- **「云优先 / 本地优先」主要是构建顺序**（先云后本地），两个都建完后是**平等选项**；而且**不给用户云/本地开关**——模式跟着「文件在哪」自动走（见 §七）。
- **行业校准（2026）**：没人给用户一个「云/本地」开关，而是给**两扇门**——走进本地工具（Cursor IDE / Codex CLI）就在你机器上干活，走进云工具（Cursor Cloud / Codex Cloud / Devin）就在他们服务端干活；走进哪扇决定在哪干活。AgentCore 把两扇门收进一个 App，用「文件在哪」自动判断，等价于同一思路。

## 三、核心设计：把「工作区」升级成 `WorkspaceBackend` 抽象

**为何 P0 就引入（而非推迟到 P2）**：B（本地优先）是**已承诺、必然建完**的路线，不是投机性未来——此时「接口先行」（项目 house style：先写 Protocol 再实现）压过「避免过早抽象」。早接缝的回报是**跨切面只动一次**：P0 把工具/引擎改成对接口编程，P2 仅新增第二实现 `LocalWorkspace`、工具与引擎零改动，省掉「P2 把同步 `Path` 操作回炉成异步 + 二次触碰全部工具与测试」的大改；契约提前钉死，P1 的 `ServerWorkspace` 就是「第一个实现」而非将来要包一层的裸 `Path`。

沿用项目已有 3 处的「Protocol + 实现 + 工厂」同构范式（`LLMProvider`/`llm/factory.py`、`SandboxProvider`、`SearchBackend`/`web/search_backend.py`），新增一个 `WorkspaceBackend`，让引擎和工具**只对接口编程**：

```python
# 落地：apps/server/agentcore/workspace/{protocol,server,_paths}.py（P0 已实现）
class WorkspaceBackend(Protocol):
    location: Literal["server", "local"]
    root_label: str  # 工作区根的人类可读名，供相对路径渲染、不暴露绝对路径
    async def read(self, path: str) -> str: ...
    async def write(self, path: str, content: str) -> int: ...                    # 返回写入字符数
    async def list(self, directory: str, pattern: str) -> list[DirEntry]: ...     # DirEntry(path, is_dir)
    async def replace(self, path, old, new, *, all_: bool) -> ReplaceOutcome: ... # (count, first_line)
    async def grep(self, query: GrepQuery) -> GrepResult: ...                     # 带 glob/files_only/截断/计数
    async def execute(self, req: ExecutionRequest) -> ExecutionResult: ...        # code_execute 走这里；backend 填 cwd
```

> **签名一次到位（实落版）**：草案初稿的 `list[str]`/`-> int` 太瘦，照它写 P2 会被迫破契约，故 P0 直接钉死结构化结果类型（`DirEntry` / `ReplaceOutcome` / `GrepHit`+`GrepResult` / `GrepQuery`）。失败语义全走**类型化异常** `WorkspaceError` 子类，工具层捕获后映射回原报错文案（用户侧报错零变化）：`OutsideWorkspace` / `PathNotFound` / `NotAFile` / `NotADirectory` / `NotUTF8` / `NoMatch` / `AmbiguousMatch(count)` / `WorkspaceIOError`。

**护栏 1·瘦接口**：持久化（snapshot/restore）**不进 backend**——它是回合级存储策略（轴3），归独立 `StorageProvider`，由 service 在 run 前后调（见 §四、§六 P1）。backend 只管「文件 + 执行」这对**必须同源**的能力（轴1+轴2 故意捆成一对，强制「无泥泞中间态」：一个 backend = 一个执行平台）。

**护栏 2·签名一次到位**：因为契约 P0 就锁，签名必须现在就对——类型化异常（保住现有 not-found / not-a-file / binary / 越界 的精确报错）、`root_label` 供相对路径渲染。否则 P2 被迫破契约重来，早接缝的收益就被抵消。

**唯一接缝**：`ToolContext.workspace_dir: Path` → `ToolContext.backend: WorkspaceBackend`。然后 6 个工具（`file_ops` 4 个 + `grep` + `code_execute`）和引擎都退化成 `context.backend.*` 的薄壳。这一步就是 Codex/Copilot 能「一套 agent 跑两种执行平台」的根因——**引擎不分叉**。`resolve_safe_path` 下沉进 `ServerWorkspace` 内部继续管越界。

> `code_execute` 收编进 `backend.execute`（`ServerWorkspace` 内**委托**现有 `SandboxProvider` 并带上 cwd）即顺带修掉 §一 的潜伏 bug：代码自然在文件所在目录跑。是「委托」不是「另起 execute 路径」——`SandboxProvider` 保留，不重复造执行抽象。

## 四、三正交轴与「本地默认云储存」判定

| 轴 | 取值 |
|---|---|
| 轴1 执行位置 | server / local |
| 轴2 文件源头 | server dir / local dir |
| 轴3 持久化 | S3 快照 / 仅本地盘 / 实时同步 |

「云模式 / 本地模式」是在**轴1+轴2** 选一整套（两个 backend）。用户提的「本地默认云储存」是 `轴1=local、轴2=local、轴3=cloud`——它**不是第三种模式，而是 LOCAL backend 的存储策略**。

| 解读 | 判定 | 理由 |
|---|---|---|
| ✅ 快照/交接式（git-push 那种） | **接受** | 本地是唯一真相源，按需经独立 `StorageProvider` 快照到 S3（非 backend 方法，见护栏 1），用于备份/跨设备/把活交给云端团队；行业已验证（Codex 本地→云、Copilot `/delegate`） |
| ❌ 实时双向同步（Dropbox 那种） | **拒绝** | 双真相源 + 冲突地狱，在「并行 Agent 团队并发写」场景尤其致命 |

**结论**：本地默认 + 云储存方向对，但务必是**快照/交接**语义，不是实时同步。它正好充当「内环在本地、团队在云」的桥：`本地 snapshot → 云端在快照上跑团队 → 结果当 diff/PR 交回本地应用`。

## 五、两个 Backend 实现

| Backend | 文件在哪 | 执行在哪 | 对应模式 | 传输 |
|---|---|---|---|---|
| `ServerWorkspace` | 服务端 `…/<user_id>/<folder_id>/`（文件夹）或 `…/<user_id>/conv/<conversation_id>/`（未分组） | 服务端（复用 `SubprocessSandbox`） | **云模式（A·先做）** | 无（同进程） |
| `LocalWorkspace` | 用户真实本地目录（复用 FS Roots） | 桌面端（工具调用路由到 Electron） | **本地模式（B·后做）** | 泛化审批门接缝（见下） |

`LocalWorkspace` 的传输**不用新造**：`runtime/approvals.py` 已是「服务端挂起 `asyncio.Future` + 客户端 HTTP 回填」（`ApprovalRegistry.create/resolve/discard`），把它泛化成一条「工具执行通道」即可。

## 六、落地分层

> **为何 P0 就立接缝**：B 是已承诺路线（非投机），早接缝让 P2 只「加第二实现」、工具与引擎零改动，并省掉二次 sync→async 大改（详见 §三）。代价是 P0 多花一次抽象设计——但因为「都会建完」，这次设计总要做，不如一次做对。

| 阶段 | 内容 | 产出 |

| **P1 云模式（A）** | ✅ 已落地：解析 `conversation →（文件夹空间或本对话空间）` 注入真实 `Path`，落 `<data_dir>/workspaces/<user_id>/<folder_id>/` 或 `…/<user_id>/conv/<conversation_id>/`（`workspace/locate.py`；service 构造 backend 经 pipeline 注入）。✅ 已落地：独立 `StorageProvider`（通用 S3 接口，prod=阿里云 OSS，dev=filesystem/MinIO，`storage/{protocol,filesystem,s3,factory}.py`）**已接线**——改过文件的回合（backend `dirty` 标记）末尾自动后台快照 + 手动留版本 + 列表/恢复/下载 API（`workspace/snapshots.py`、`conversations.py` 的 `/snapshots*`）。✅ 已落地：文件进出之**上传/下载**（raw-body `PUT`/`GET /v1/conversations/{id}/workspace/files/{path}` + 列表，走 backend 二进制 IO `read_bytes`/`write_bytes`，`workspace/files.py`；无 multipart 依赖）。⬜ 待做：`git clone`（公开仓库）紧随；附件从「临时上下文」升级为「驻留项目空间 + 成果可下载」 | 「选文件夹 + AI 在该文件夹工作」成立、团队差异化成立 |
| **P2 本地模式（B）** | **仅新增第二实现 `LocalWorkspace`**（工具/引擎零改动）+ 桌面「工具执行通道」（泛化审批门，含 `execute` 路由）+ 绑定真实本地目录 + 本地→云 snapshot 交接 | 开发者 Cursor 式内环 |

> **本地真实编辑 = 正交模型的一个配置**（不是 A 的免费副作用）：它 = 轴1 `server` + 轴2 `local_dir`（执行在服务端、文件指向真实本地目录），仅在**服务端 = 用户机器的可信自托管**下成立——此时 `resolve_safe_path` 仍管越界，但允许把 `local_dir` 喂给工作区根。这与「云端杜绝用户传任意服务端路径」不矛盾：前者是可信运维配置，后者是不可信多租户默认。

## 七、绑定模型与「模式跟着文件走」

- **粒度**：**默认每个对话有独立工作区**；放进文件夹的对话**共用该文件夹的工作区**（文件夹 = 项目，东西攒一起）。顺现有 `folder_id` 数据模型。
- **不给用户云/本地开关，模式跟着「文件在哪」自动判断**：
  - 直接聊天 / 上传文件 → 文件在服务端 → **云**。
  - 从桌面端「打开本地文件夹」（绑定 `local_dir`）→ 文件在用户电脑 → **本地**。
  - 没给任何文件就开聊 → **云**（零前提、开箱即用）。
- 因此 `Folder.workspace_mode` 是**派生值**（有没有绑定 `local_dir` 决定），不是用户要去拨的设置。
- **跨设备 / 手机端**：云项目在服务端，**跨设备同步**（手机起头、电脑接着干，是同一个项目）；本地项目只在那台电脑上，跟不到其他设备。手机没有「项目文件夹」概念，所以**手机端只用云**——同一条「模式跟着文件走」的规则不用改（手机没有本地文件夹可指，自动走云）。
- **注入路径**：`conversation/service.py` 解析 `conversation →（在文件夹用文件夹空间、否则用本对话空间）→（有绑定 local_dir 则本地、否则云）` → 构造对应 `WorkspaceBackend` → 经 `run_chat_pipeline` 注入 `base_tool_context.backend`；worker 经 `replace(...)` 自动继承。

## 八、风险与边界

| 项 | 处理 |
|---|---|
| 路径越界 | `resolve_safe_path` 继续作为单一边界，下沉进 `ServerWorkspace`；服务端目录由 user/folder 生成，**杜绝用户传任意服务端路径** |
| 未分组会话（`folder_id = NULL`） | **已定**：每对话用自己的独立空间 `…/conv/<conversation_id>/`，互不干扰；放进文件夹才共用文件夹空间（见 §九 ③） |
| folder / 会话删除后的文件 | **已定**：与软删除对齐——软删时目录原样保留（可恢复）；后台定时清理「软删超过保留期（默认 30 天，可配）」的目录 + 记录，OSS 备份同步清；用户「彻底删除」则立即清（见 §九 ⑦） |
| 同 folder 跨会话并发写 | **已定**：文件夹级锁，同一文件夹同时只一个任务跑、其余排队（进程内锁，多机再 Redis）；任务内并行小队是协作、不受此限（见 §九 ④） |
| 云端选了本地目录（路径不存在） | P1 明确降级：报错或回退到独立托管工作区，绝不静默 |
| `LocalWorkspace` 下并行团队 | 单桌面通道是瓶颈；正解是 local 内环 + snapshot 到云、由云端跑并行团队（呼应 §四交接语义） |
| 多 worker 进程态 | 审批门/通道现为单进程内存态（同限流），多 worker 需前置 Redis |

## 九、关键决策（已定）

1. **P0 引入 `WorkspaceBackend` 抽象**：B 为已承诺路线，接口先行（见 §三、§六）。
2. **不给用户云/本地开关**：模式跟着「文件在哪」自动走；快开始 / 手机端走云（见 §七）。
3. **未分组会话 = 每对话独立空间**（`…/conv/<conversation_id>/`，互不干扰）；放进文件夹才共用文件夹空间（= 项目，东西攒一起）。
4. **同 folder 跨会话 = 文件夹级锁**：同一文件夹同时只一个任务跑、其余排队（进程内锁，多机再 Redis）；任务内并行小队是协作、不受此限。
5. **文件进出：先上传**（人人可用、结果可下载）；**`git clone` 紧随**（开发者；公开仓库先、私有仓库令牌后）。
6. **云存储 = 阿里云 OSS**，代码做成通用 S3 接口（dev 用 MinIO，换家不改代码）；**快照 = 改过文件的任务结束后后台异步备份 + 手动留版本 + 随时下载**（非每写必存）。云模式文件实时在服务器硬盘，OSS 只作备份 / 留版本 / 下载。
7. **删除后的文件生命周期 = 与软删除对齐**：删文件夹/对话是软删（记录留 `deleted_at`），其工作区目录**原样保留可恢复**；后台定时扫，把软删超过**保留期（默认 30 天，可配）**的目录 + 记录一起物理清除、OSS 备份同步清；用户「彻底删除 / 清空回收站」则立即清。文件归**项目（文件夹）**所有——文件夹删了文件随项目进回收站，原属对话变「未分组」后用自己的新空间、不翻已删项目。

> 决策 6 的 S3 客户端库已定：选 `boto3`（同步 SDK，阻塞调用经 `asyncio.to_thread` 卸载），已入 `pyproject` 依赖；非 `aioboto3`。
