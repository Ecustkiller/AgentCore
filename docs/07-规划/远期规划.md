## 一、架构演进（已暂缓）

> **决策记录（2026-06 评审）**：离线 / 隐私 / 本地优先**驱动力暂无** → 下列两项**暂缓**、维持远期。**重启触发** = 出现明确的离线 / 隐私 / 本地优先场景（某类客户或合规要求）。
>
> **来源**：原 `02-架构/技术架构与基础设施.md §六`，按文档治理迁出（曾名《架构演进提案》）。其中「客户端工具执行 + 本地优先 folder」一项**已落地**（见 [`../02-架构/双模式工作区.md`](/docs/02-架构/双模式工作区.md) 的 `LocalWorkspace` + `WorkspaceChannel`），**不在本节**——勿与下面的「本地引擎」混淆：已落地的是「引擎在云、文件 op 遥控桌面执行」，本节是「引擎本体也搬到本地」。其余借鉴项（统一 Run 模型 / WaveScheduler / `delegate` / Turn Journal 投影 / Interaction 挂起等）均归属既有设计（见 [`../03-AI核心/执行引擎架构设计.md` §十八](/docs/03-AI核心/执行引擎架构设计.md)），亦不在此列。

### 1.1 Sidecar 可迁移核（中长期）

桌面 spawn `python -m agentcore.sidecar` 跑**同一 `RuntimeEngine`**，stdio JSON-RPC 通信，仅把宿主端口（[执行引擎 §18.6](/docs/03-AI核心/执行引擎架构设计.md)）换为本地实现（SQLite / 内存 / in-proc），离线可降级。

- **价值**：本地执行 / 离线 / 隐私基础，云与本地同一引擎。
- **代价**：宿主端口面大、双实现维护成本高。
- **就绪度**：§18.6 的 10 个宿主端口当前仅 2 个 Protocol 化（`EventSink` / `ClientRequestBridge`），其余 8 个仍为具体实现；`Journal` / `SnapshotStore` 地基属 Phase 2 尚未建。
- **倾向**：中长期；新代码按「引擎面向宿主端口」组织**留缝**（低风险铺路，不引入第二实现）。

### 1.2 JSON-RPC 2.0 运行时协议（与 Sidecar 绑定）

用 JSON-RPC 承载整轮运行时（initialize / startTurn / resume / pause / cancel / respond…），事件映射为 notification，传输可换 stdio（sidecar）/ WS（云）。**注意非 MCP**（MCP 仍用于 Agent↔外部工具）。

- **价值**：云 / 桌面 / UI 一套代码，pause/resume/交互回值天然统一。
- **代价**：需把现有 SSE + HTTP（[执行引擎 §十二](/docs/03-AI核心/执行引擎架构设计.md)，25 类事件已稳定对齐）重构为协议层。
- **倾向**：**与 §1.1 Sidecar 绑定**——Sidecar 不做则本项暂缓（SSE 无独立收益时重构纯亏）。

## 二、平台能力演进（抽象已预留、第二实现待启）

> 共性：抽象接口（Protocol + 工厂）在 MVP 即预留、首实现满足发布；第二实现属**发布后**增强，出现明确驱动力才启动——与 §一 Sidecar 同范式（「抽象先行、第二实现留缝」的能力域版）。

### 2.1 真实沙箱（SandboxProvider 第二实现）

代码执行当前走受限 `SubprocessSandbox`（同机子进程 + 越界守卫）；第二实现把执行搬进**真隔离运行时**（容器 / gVisor / Firecracker 等），抽象 `SandboxProvider` 已预留、工具与引擎不动。

- **价值**：不可信代码安全执行、多租户隔离，为「放开代码执行能力」解锁前提。
- **代价**：隔离运行时的运维与资源开销；冷启动 / 文件挂载 / 网络策略需逐项配。
- **就绪度**：`SandboxProvider` 抽象 + 首实现 `SubprocessSandbox` 已落地（`code_execute` 经 `backend.execute` 委托）；真隔离第二实现未建。详见 [`../05-平台与运维/安全权限与治理.md`](/docs/05-平台与运维/安全权限与治理.md)。
- **启动触发**：放开不可信代码执行 / 出现多租户共享执行 / 代码执行成为高频能力。（「用现有 subprocess 放开到什么程度」属发布前调参，见 [执行引擎 §十九](/docs/03-AI核心/执行引擎架构设计.md)。）

### 2.2 多 LLM Provider（LLMProvider 第二实现）

当前单一 `DeepSeekProvider`（Flash + Pro）；第二实现接入其他模型家族（海外 / 本地 / 其他厂商），抽象 `LLMProvider` + `llm/factory.build_provider` 已预留。

- **价值**：出海与多模型选择、客户指定模型、对冲单一供应商的可用性 / 成本风险。
- **代价**：各家 API 差异（工具调用 / 思考模式 / 流式增量）需在 provider 层抹平；定价表与计费每接一家加一份。
- **就绪度**：`LLMProvider` 抽象 + 首实现 `DeepSeekProvider` 已落地；BYOK「一轮一网关」凭据传播原则已定（[执行引擎 §18.7](/docs/03-AI核心/执行引擎架构设计.md)）；第二家 provider 未接。
- **启动触发**：出海需要海外模型 / 客户要求指定模型 / 对冲单一供应商风险。
