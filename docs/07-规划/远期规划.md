## 一、架构演进（本地引擎已落地，剩离线 LLM + 跨进程两条远期触发项）

> **已落地（as-built 见 [`../02-架构/双模式工作区.md §十`](/docs/02-架构/双模式工作区.md)）**：sidecar 本地引擎——桌面 spawn `python -m agentcore.sidecar` 跑**同一 `run_chat_pipeline`**、stdio JSON-RPC、工作区直连本地盘；LLM 经云代理权威计费（Slice 4a，平台 key 不下放，岔路 B）+ 回合云端回写（`local-turns` 幂等）+ 结构化挂起本机帧（durable pause/resume）+ 内置 Python 打包（方案 B）+ `Journal` 端口 / 执行级事实。绑本机本地文件夹的对话走 sidecar，开关「本地引擎」已**默认开**、可关闭（启动失败自动降级回云端兜底 + 首次走 sidecar 前探活预检、偏好三态存储）。
>
> **驱动力（已识别）**：同一用户兼做「改本地真实仓」与「泛知识工作」，本地交互不能长期二等（「云端引擎遥控桌面」单通道在速度 / 并行 / 离线均受限）；beta 维持「默认云 + 打开文件夹经 `WorkspaceChannel` 实时改本地真文件」作兜底。
>
> **来源**：原 `02-架构/技术架构与基础设施.md §六`（曾名《架构演进提案》）。其中「客户端工具执行 + 本地优先 folder」（引擎在云、文件 op 遥控桌面）与「引擎本体搬到本地」（sidecar）均已落地、迁入 [`双模式工作区.md`](/docs/02-架构/双模式工作区.md)（§四 / §十）；其余借鉴项（统一 Run / WaveScheduler / `delegate` / Turn Journal / Interaction 挂起）归 [`执行引擎架构设计.md §八`](/docs/03-AI核心/执行引擎架构设计.md)。本节仅余下面两条**未落地、待触发**的演进。

### 1.1 完全离线（本地推理 + 本地消息库）

现 sidecar 是**混合态**：引擎在本地，但推理 / 持久化 / 计费仍借道云（见 [双模式工作区 §10.2/10.3](/docs/02-架构/双模式工作区.md)）。完全离线 = 把这几条也换本地实现，让整轮零云依赖：

- **本地 `InferenceGateway`**：接本地模型（Ollama / llama.cpp / LM Studio 等），不走 `/v1/inference` 云代理（复用 `LLMProvider` 抽象 + 工厂，见 §2.2）。
- **本地消息库**：sidecar 本机 SQLite 落消息，替掉云端 `local-turns` 回写（`ConversationStore` 端口本地实现）。
- **计费解耦**：离线 = 用户自有算力、不计费（本地 = free，`BillingSink` 空实现）。
- **价值**：真离线 / 隐私（数据不出机器）/ 零推理成本。
- **代价 / 就绪度**：[执行引擎 §8.6](/docs/03-AI核心/执行引擎架构设计.md) 的 10 宿主端口当前仅 3 个 Protocol 化（`EventSink` / `ClientRequestBridge` / `Journal`），其余 7 个仍具体实现——`ports.py` 明示「无第二实现时 Protocol 化 = 过早抽象」，故**按纪律留缝、不预抽**；本地模型质量 ≪ DeepSeek V4，大众定位下属 niche。
- **绑定项·JSON-RPC 云侧统一**：sidecar 桌面↔本地通道已是 JSON-RPC；本项可顺带把**云侧** SSE + HTTP（[执行引擎 §二](/docs/03-AI核心/执行引擎架构设计.md)）也统一为 JSON-RPC 运行时协议（云 / 桌面 / UI 一套代码、pause/resume/交互回值天然统一）。**但 SSE 事件契约已稳定对齐、无独立收益时重构纯亏**，故与离线绑定、离线不做则不动（**非 MCP**——MCP 仍用于 Agent↔外部工具）。
- **启动触发**：出现明确的隐私 / 企业自托管 / 真离线诉求。

### 1.2 跨进程子树分发（C2）

worker 委派现为**进程内** asyncio 子 task（`DelegationTransport` 端口仍具体实现）；跨进程 = 把委派子树分发到别的进程 / 机器（Redis durable queue + 跨进程挂起 BLPOP）。

- **价值**：多机扩容、本地内环 + 云端并行团队混合执行。
- **就绪度**：[`双模式工作区.md §五`](/docs/02-架构/双模式工作区.md) 多 worker 的锁 / 审批门 / 通道 / handoff 现为进程内态；限流已留 `RateLimiter` protocol 缝；挂起跨进程 Redis 见 [执行引擎 §暂停与恢复](/docs/03-AI核心/执行引擎架构设计.md)。
- **启动触发**：单机并行触顶 / 多副本部署 / 本地↔云混合执行成为真实诉求。

## 二、平台能力演进（抽象已预留、第二实现待启）

> 共性：抽象接口（Protocol + 工厂）或机制扩展点在 MVP 即预留、首实现 / 首模式满足发布；第二实现 / 强制模式属**发布后**增强，出现明确驱动力才启动——与 §一 Sidecar 同范式（「抽象先行、第二实现留缝」的能力域版）。

### 2.1 真实沙箱（SandboxProvider 第二实现）

代码执行当前走受限 `SubprocessSandbox`；第二实现把执行搬进**真隔离运行时**（gVisor / Firecracker 等），抽象 `SandboxProvider` 已预留。

- **价值**：不可信代码安全执行、多租户隔离。
- **启动触发**：放开不可信代码执行 / 多租户共享执行 / 代码执行成为高频能力。

**Post-MVP 目标架构细节**（从安全文档迁出）：

| 方案 | 结论 |
|---|---|
| gVisor（用户态内核拦截） | Post-MVP 升级目标——不挑硬件、强度足够 |
| 独立小虚拟机（Firecracker） | 换带 KVM 机器后平滑升级 |
| 独立 Worker + NATS | API 永不接触 Docker；代码执行经 NATS request 转发到 worker 容器 |

gVisor 执行模型锁死项：默认禁止联网、只读根文件系统、内存/CPU/pids 上限、非 root。资源限额默认：256MB 内存 / 1 CPU / 128 pids / 默认禁网 / 并发 2。

→ 见 [`../05-平台与运维/安全权限与治理.md` §五](/docs/05-平台与运维/安全权限与治理.md)

### 2.2 多 LLM Provider（LLMProvider 第二实现）

当前单一 `DeepSeekProvider`（Flash + Pro）；第二实现接入其他模型家族（海外 / 本地 / 其他厂商），抽象 `LLMProvider` + `llm/factory.build_provider` 已预留。

- **价值**：出海与多模型选择、客户指定模型、对冲单一供应商的可用性 / 成本风险。
- **代价**：各家 API 差异（工具调用 / 思考模式 / 流式增量）需在 provider 层抹平；定价表与计费每接一家加一份。
- **就绪度**：`LLMProvider` 抽象 + 首实现 `DeepSeekProvider` 已落地；BYOK「一轮一网关」凭据传播原则已定（[执行引擎 §8.7](/docs/03-AI核心/执行引擎架构设计.md)）；第二家 provider 未接。
- **启动触发**：出海需要海外模型 / 客户要求指定模型 / 对冲单一供应商风险。

### 2.3 治理强制检查点层（结构化挂起的强制模式）

> **来源**：原 07 草稿《结构化挂起后端落地设计》§4.7「治理强制注入层」**已退役删除**；该蓝图 2a/2b 全落地迁入正式文档后，唯一延后项迁出至此。

结构化挂起底座（`WaveScheduler.on_checkpoint` + `InteractionRegistry` 的 `plan_review` kind + 回合级 `paused_turns` 落盘 + `POST /resume`）已全落地，**首模式 = CEO 自声明** `checkpoint_after`（CEO 自愿在高危 step 后标记，用户 continue/adjust/stop，软挂起 timeout=continue 放行，已满足发布）；**第二模式 = 治理策略强制**：检查点由策略强制注入（非 CEO 自愿声明）、声明即必停（不可被 CEO / 用户跳过）、挂起点可审计留痕、超时取 `halt`（而非软挂起的 `continue`）。

- **价值**：合规 / 企业治理场景的「保证闸门」——某些高危 / 不可逆步骤必须由人确认，不依赖 CEO 自觉；审计留痕满足审查要求。
- **代价**：调度器 / 计费 / 事件层需区分「自声明 vs 强制」两类挂起；timeout 语义按类分流（软 = continue、强制 = halt）；强制注入规则的策略面与配置。
- **就绪度**：机制底座 + 首模式（CEO 自声明）已全落地（见 [`../03-AI核心/执行引擎架构设计.md` §暂停与恢复](/docs/03-AI核心/执行引擎架构设计.md)）；仅缺「强制注入 + 必停 + halt 超时 + 审计」这层策略。
- **启动触发**：出现明确的合规 / 企业治理需求（某类客户或审查要求强制人工闸门）。

### 2.4 评估体系深化（LLM 裁判 + 对比闭环）

> **已被取代**：本节原方向（沿现行 `agentcore/evals/` 骨架做「Layer 2 裁判 + 对比闭环」深化）假设现行评测方向正确。2026-06 方向评审否决该假设——现行体系「测执行轨迹机制、不测任务结果」。新方向（以任务结果为中心：L0 契约硬门 + L1 rubric 裁判主轴 + L2 milestone 协作 + L3 真实轨迹回流）见 → [`评测体系重设计`](/docs/07-规划/评测体系重设计.md)。原「等算力 C 臂 / 思考-token 对齐 / best-of-N 擂台」机器**降级为偶发诊断**（详见重设计 §六）。

## 四、产品形态演进

> 发布后才考虑的产品形态方向在此累积，按 §一/§二 格式（价值 / 代价 / 就绪度 / 启动触发）。

### 4.1 人 + AI 混合群（消息页差异化形态）

消息页 IM 群聊里 `@` 唤起 agent → 接 CEO 编排，让 AI 作为群成员参与人类群聊（区别于对话页的纯 AI 团队群）。是消息页相对对话页的差异化卖点；数据层 `chat_messages.sender_type=agent` 已为此预留。

- **价值**：把 AI 团队能力带进人类社交 / 协作群——群里 `@` 某 agent 即可让它响应、查资料、执行任务，人与 AI 同会话协作。
- **代价**：要打通两套当前解耦的栈——IM（`messaging` service / `chat_messages` / firehose）↔ AI 执行引擎（CEO 编排 / `RuntimeEngine` / 事件流）。需处理：群消息识别 `@agent` → 转一次编排 run → agent 输出回写为 `chat_message`（`sender_type=agent`）→ 计费 / 限流归属 → 权限（谁能 `@`、agent 可见多少群历史）。
- **就绪度**：数据层 `sender_type=agent` 已留；IM transport（全员群 / 成员 / 实时 fan-out）与 CEO 编排引擎均已落地；**缺两栈之间的桥**（IM 消息 ↔ 编排 run）。
- **启动触发**：内测群验证人群聊价值后出现「群里直接调 AI」的明确诉求；或需把消息页做成区别于对话页的协作场景。
