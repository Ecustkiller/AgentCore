## 一、问题：结构像团队，行为像传声筒

复盘两次真实交付，执行轨迹都是同一个形状——**写 → 产出者自报 done → CEO 收尾上报**，验证轮数为 0：

- **宣传官网**（worker 写 `index.html`/`style.css`/`script.js` 即 done）：CEO 收尾称「浏览器直接打开即可完整预览」，但无人回读、渲染、冒烟。
- **学术文章**（worker 2 轮写完 1 个 `.md` 即 done）：CEO 没读过该文件，回复里描述的是**它派下去的任务**，不是实际产物。
- **法律概述**（CEO 直答，无 worker）：日志告警 `citations.out_of_range markers=[25,27] citation_count=24`——正文用了 [25][27] 两个**不存在**的来源（实际仅 24 条），直接违反基座提示词「绝不编造引用」，**违背了系统自己的承诺而不自知**。

根因**不是**「漏写了一道检查」（那是补丁思路，会踩 [`dev-process`](/.cursor/rules/dev-process.mdc) 的补丁绊线），而是：

> ReAct 循环唯一的终止信号是「这一轮不再调工具」（`done`），由模型**自己宣布**；唯一盯着循环的 `LoopController` 方向还相反（检测机械空转 → 推 `FINALIZE`，让 Agent **更早停**）。没有任何对称机制说「你声明 done 了，交付前先核验」。叠加角色心智被显式设计成「一次性交付」（worker）与「综述而非验收」（CEO），于是**团队有验收的结构，却没有验收的行为**。

这抽空了产品最核心的承诺。真团队的价值不只是「多几双手」，而是活在送到老板手里前**会多过几双眼睛**；一支从不过眼的团队，对用户而言和「一个慢一点的单 Agent」没区别。

详见 [执行引擎 §十四](/docs/03-AI核心/执行引擎架构设计.md)（ReAct 循环与收敛治理）、[`runtime/prompt.py`](/apps/server/agentcore/runtime/prompt.py)（CEO/worker 心智）。

## 二、核心决策

**1. 交付前核验是团队的分内职责，不是用户的额外期望。** 面向大众，「交付」二字默认承诺「有人替我看过，能直接用」，而非「这是初稿，你自己再查查」。大众用户往往**无法**自验（看不出引用是假的、数字是错的），所以这层把关只能由团队兜，且这层承诺要让用户**感知得到**（默默核了，信任也建不起来）。

**2. 责任留 CEO，动作下放团队。** 把两件事分开：
- **核验的责任归属** → 留在 CEO（它本就「对整段对话负责到底」，做最终取舍）。**所有者 ≠ 亲自做**。
- **核验的动作执行** → **不**压在 CEO 身上。CEO 亲自当 QA 有三个硬伤：把 worker 全文读进自己上下文（打破委派「不扛细节」的初衷）、它是协调者未必有对口专业眼光、所有活都汇到它会成瓶颈——正是「真团队」该避免的微管反模式。

**3. 核验动作分两层。**
- **轻层 —— 产出者自检**：产出者（worker，或直答的 CEO）对自己刚产出的东西做**机械自检**，在自己上下文内完成，几乎零额外成本。只能兜机械/卫生问题，抓不住深层语义错（「自己查自己」的固有局限）。
- **重层 —— 独立审查角色**：换一双**新鲜眼睛 + 对口专长**的审查 worker（即现有「设计 → 实现 → 审查」流水线的尾节点），跑在团队层、不压 CEO 上下文。仅在高风险时上。

CEO 的增量负担因此**不是亲自验**：触发由产物信号决定（见 §三「触发机制」，**不靠 CEO 判断「要不要核」**），CEO 只需读一个**短结论**（如「审查者：2 个角标无对应来源，已返工」）据此收尾 / 返工。

## 三、触发判据

### 判据一：要不要核验

> 产物里有没有「**客观可验 + 用户验不了**」的东西。有 → 核；没有、或只是品味 → 不核。

两个关键词缺一不可：**客观可验**（有真值可对：引用对不对得上、代码跑不跑、数字对不对账、规格满没满）是核验能使上力的前提；**用户验不了**（隐形缺陷，非一眼可见）是它值得做的理由。

**最要紧的一条边界：品味不是核验的活。** 「文章写得好不好」「设计美不美」没有客观真值，审查者验不了——这是用户的主场，该走 `ask_user`（见 [`runtime/skills.py`](/apps/server/agentcore/runtime/skills.py) 的 `asking_the_user`），不是丢给审查者。把品味塞进核验，又慢又越界。

**灰带破法：先拆，再用「指认 vs 表态」逐条归岸。** 很多请求（典型如「论证够不够有力」）不是单一问题，而是一捆——里面既有可核验的「地基」（逻辑断没断、论点有无论据、引用是否支撑、有无自相矛盾），也有纯品味的「上层」（整体说服力、文风、详略偏好、立场倾向）。别给整捆归类，要拆开，再对每条做一句话测试：

> 把这条意见说出口——形如「**X 处错了 / 缺了 / 对不上**」（指得出具体毛病）→ 核验；形如「**我觉得 / 更喜欢 / 不够……**」（只能表达偏好）→ 品味，留用户。

两个等价的加固判据：① **换一个合格的人来看，会不会同意这是个「毛病」**——会（「第 3 段结论无论据」谁都认）是地基，见仁见智（「气势弱了点」没对错）是品味；② **能不能写成对/错的 checklist**——能列条目的是地基，只能打分的是品味。

**中间带「漏了个维度 / 反驳」的划法**：漏掉「**显著且共识**」的（几乎人人会想到、不提即硬伤）→ 毛病，审查该报；「锦上添花」式的「还可以再补个视角」→ 建议/品味，留用户。界线是「显著共识」与「可有可无的丰富」。

**护栏（锁死审查者职权）**：审查者只对「指认出的具体毛病」负责，**永不出「总分」**。它可以报「第二节结论无案例支撑、引用 [12] 与论点不符」，但绝不能说「我觉得力度不够」——一旦它给「够不够有力」打分，就越俎代庖替用户定了品味。

### 判据二：轻层还是重层

> 这个核验，产出者**在自己上下文内就能机械对照**（轻层），还是**必须重跑 / 重算 / 换眼睛 / 回源对照**才客观（重层）。

| 产物信号 | 怎么核 | 层 |
|---|---|---|
| 含引用/出处角标 | 每个 `[n]` 是否有对应真实来源 | 轻（产出者自查） |
| 声明了硬规格（结构/字数/语言/必含项） | 逐条对照 | 轻 |
| 留 TODO / 能否解析 | 自查 | 轻 |
| 可运行物（网页/脚本/代码/配置） | 冷启动 / 跑一下 | **重**（要跑） |
| 关键数字/计算/统计/图表 | 与来源对账 + 重算 | **重**（要重算） |
| 事实/逻辑站不站得住 | 新鲜眼睛找漏 | **重**（要换眼睛） |
| 权威依据 / 原本忠实度（法律医疗合规断言、翻译/摘要/改写、深层引用支撑） | 回源逐项比对（断言↔法条 / 证据、译文↔原文、论点↔所引来源） | **重**（要回源对照） |

**一个便宜胜仗**：最吓人的「学术文章造引用 [25][27]」按此判据是**轻层就能抓**的（角标↔来源是纯机械对照），根本不必动用昂贵的审查者 agent；且它是 CEO 直答（无 worker），「产出者自检」恰好覆盖这种没有 worker 的场景——CEO 手里本就有刚检索的来源，对一下即可。

**重层四类（经多类型产物压测收敛）**：① **要跑**（代码 / 网页 / 脚本 / 配置——能不能跑、行为对不对）；② **要重算**（数据 / 财务 / 统计 / 图表——数字对不对账、可视化有无误导）；③ **要换眼睛找漏**（论证 / 方案 / 研究——逻辑站不站得住、有无显著漏洞）；④ **要回源对照**（法律医疗合规断言、翻译 / 摘要 / 改写、深层引用支撑——产物是否忠实于其声称依据的源）。压测同时**确认无须再增类**：**设计 / 视觉类**绝大多数是品味（不核、走 `ask_user`），仅文案 / 硬规格落轻层；**配置 / 结构化数据**走轻层 parse + 重层「要跑」。大部分交付靠轻层就兜住，代价近零。

### 显式不触发（保持轻快，别添堵）

- 对话式回答（无文件产出）。
- 一眼可见、低代价的瑕疵维度（排版、措辞、风格）——用户自己就是安全网。
- 纯主观/品味判断 → 交给用户（`ask_user`），不交给审查者。
- 用户明示「草稿就行 / 快速糙一点」——他主动放弃了安全网，尊重其 opt-out。

### 触发机制：信号决定论为主，CEO 判断兜底

> 触发尽量锚到**可观测的产物信号**、走决定论，**不依赖 CEO 临场自觉**——这才修得了「CEO 几乎从不主动触发」的原罪，也卸掉了 CEO「这次要不要核」的判断负担（直接回应「别把 CEO 压太重」）。

- **轻层 = 宽触发**：产物一出现对应信号（含角标、声明了硬规格、是文本产物）就做，**完全不经 CEO 判断**。轻层近零成本，偶尔在低风险产物上误触也无害，故宁宽勿漏。
- **重层 = 严触发**：客观信号（可运行文件类型 / 出现关键数字 /「以论证为核心的成篇交付」意图）**且**非 opt-out 才上。重层有 agent 成本，故触发收紧、叠加 stakes 与 opt-out 过滤。
- **纯语义风险**（逻辑/事实站不站得住）没法纯机械检出，但也**不交给 CEO 拍脑袋**——尽量锚到「**产物类型 × 用户意图关键词**」（如用户要的是「学术文章 / 方案 / 分析报告」这类论证为价值核心的成篇交付）这种半客观信号来触发重层语义审查。
- **CEO 的角色**因此降到「读结论、定收尾 / 返工」——它不再判断「要不要核」，只消费核验结论。这与现有「工具边界在 `pipeline.py` 结构性强制、提示词只作辅助」的设计一脉相承（见 [`runtime/prompt.py`](/apps/server/agentcore/runtime/prompt.py) 对工具边界的说明）。

### opt-out 识别：宁可多核，不可误放

> opt-out 让用户能关掉核验闸门，但**误判方向是不对称的**：误当 opt-out（漏掉该核的）→ 静默重伤；没认出 opt-out（多核了）→ 只是添堵。故总原则：**宁可没认出，不可误认**——opt-out 必须是当轮**明确的质量弃权信号**，不从「快 / 简单 / 语气」里推断。

- **真 opt-out**：当轮明说降低质量标准或放弃把关（「草稿就行」「先出个大概」「不用太严谨」「引用我自己补」）。
- **伪 opt-out（不算）**：「快 / 尽快」是要**速度**、不是弃质量；「简单 / 小」是**范围**小、不是「算错也行」；「随便」常只是语气词。这些都不构成对交付物质量的弃权。
- **opt-out 有范围、不是总开关**：它能降的是**打磨度 / 严谨度上限**（重层的彻底性、可有可无的丰富、品味），**降不掉「不造假」地板**——即便「草稿」，轻层的「别编造引用 / 别瞎编数字」照做（造假在草稿里也不可接受，且轻层近零成本）。「草稿就行」降的是「成品 vs 初稿」的预期，绝不是「可以给我假东西」。
- **拿不准 + 高风险时，问一句**：表达模糊到判不准、且产物高风险，用 `ask_user` 轻问（「这版要能直接用，还是先出草稿你再改？」），而非默默假设 opt-out。克制——仅「模糊 + 高风险」同时成立才问。

## 四、价值 / 代价 / 就绪度 / 启动触发

- **价值**：兑现「交付=验过能用」的产品承诺，把「真团队」从结构落到行为；以近零成本（轻层）堵住「造引用、带病代码、错数字」这类用户验不了、一出错就静默重伤的缺陷。
- **代价**：重层每次高风险交付多一个 agent + 一点延迟（与「首字即时 / 低成本」取向对冲，故严格限定在「要跑 / 重算 / 换眼睛 / 回源对照」四类）；轻层让产出者多一轮机械自检；CEO 仅多读一条核验结论、据此定收尾 / 返工（触发已信号化，CEO 不再承担「要不要核」的判断）。
- **就绪度**：承载缝**已存在**，无需新造子系统——重层 = 现有 `depends_on`「设计→实现→审查」流水线尾节点（[执行引擎 §18.4](/docs/03-AI核心/执行引擎架构设计.md)）；机械契约可借 `contract`（现仅表层关键词，[`runtime/skills.py`](/apps/server/agentcore/runtime/skills.py)）。**缺的是「默认行为 + 判据」这层语义**，当前全靠 CEO 临场自觉、且 CEO 几乎从不主动触发。
- **启动触发**：交付质量成为内测反馈痛点；或评估体系（[`后端架构.md §五`](/docs/02-架构/后端架构.md)）量化出「未核验缺陷率」显著。

## 六、产品呈现：让核验可感知

> 决策 #1 要求「交付=验过能用」这层承诺**让用户感知得到**（默默核了，信任也建不起来）；但又不能变成 CEO 自吹（「我已严格核验请放心」正是 output_style 要禁的 slop）。破法：**让「团队过了眼」成为可见的产物，而不是嘴上的保证**——全部复用现有 UI 原语，零新话术。

- **过眼即可见**：审查作为团队图里的一个 run 节点自然呈现（复用 React Flow 团队图 / run 节点）。用户看到「审查」成员跑过，本身就是过关凭据，无需 CEO 在正文里声称核验过。
- **不对称呈现**（呈现强度随信任价值走，避免 crying wolf）：
  - **发现并修正** → 最高信任时刻，如实简洁说出（「审查发现 2 处引用无对应来源，已返工」）。这比「已核验」有用得多——用户得知系统真抓到了实事。
  - **通过无事** → 安静，或仅在产物上留一个轻量「已核验」标记，不写一句邀功的话。
  - **按判据跳过**（对话回答 / 一眼可见低代价 / opt-out）→ 什么都不加，零噪音。
- **轻 affordance 绑到产物**：把「已核验」做成挂在交付文件 / 来源卡 / 引用角标上的轻量视觉（如核验通过的角标态），而非正文里一段话——视觉表达，符合 output_style「需要视觉结构时用 Markdown / UI 而非话术」。

**反面红线**：CEO 正文绝不出现「我已仔细核验 / 请放心 / 保证无误」这类自我背书话术；信任靠「可见的审查节点 + 如实的发现」建立，不靠形容词。

## 七、落地机制：动手前必须先拍方向的未决硬点 🗂️

> §五 收敛的是**策略层**（该不该核、责任归谁、怎么判断）；本节是**机制层**——这些「怎么落地」在动手前必须先定方向。源自一次设计 ↔ 代码对照核验：承载缝确实都在（`depends_on` 流水线、`contract`、`ask_user`、React Flow 团队图），但「缺的语义」比正文的乐观语气**多一层**，且其中三点是硬骨头。本节仍 🗂️、不含实现方案，只把待决项指认清楚。

**现状再校准（两处正文需配合理解）：**

- 「便宜胜仗：轻层就能抓造引用、产出者自检恰好覆盖 CEO 直答」**偏乐观**。`contract` 机械校验只在 **worker 执行器**生效（见 [`runs/contract.py`](/apps/server/agentcore/runtime/runs/contract.py)：`check_contract` 校验 worker 产出的*形*）；**CEO 直答的产物根本不过这道校验**。CEO 直答路径当前唯一的检查，是 [`pipeline.py`](/apps/server/agentcore/runtime/pipeline.py) 里 `citations.out_of_range` 的**一条 warning——只记不拦**，且它只抓「角标编号超范围」（[25] 而仅 24 源），抓不到「编号没超范围、但引用内容对不上」。所以那场便宜胜仗对**正文那起具体事故**成立，但需把「只记日志」改成「能拦能返工的闸门」，而 CEO 直答这条路**今天没有任何返工环**。
- 「唯一盯着循环的 `LoopController` 方向相反、只会让 Agent 更早停」**需补一句**：它已带**周期性「复盘再规划」反思注入**（[`loop_controller.py`](/apps/server/agentcore/runtime/loop_controller.py) `reflection_due` / `progress_review_prompt`，轮间插一句系统提示）。也就是说**「交付前先核一道」可复用的轮间注入口子已经存在**——对本提案是利好，而非纯阻力。

**三个硬点（正文低估）：**

1. **决定论触发 ↔ 现状 opt-in 的矛盾。** 正文要「轻层宽触发、**完全不经 CEO 判断**」；但唯一的机械承载 `contract` **今天是 CEO 在 `delegate` 时自己声明的**——用不用全凭 CEO 自觉，恰恰就是 §一 要根除的「CEO 几乎从不主动触发」的原罪。要做到自动，必须新造「按可观测产物信号**自动**决定要不要核 / 自动注入校验」的一层；这层现在不存在，是整套设计真正的命门。
2. **CEO 直答路径无承载。** 见上「现状再校准」。最吓人的「直答 + 造引用」恰恰绕开了 worker / `contract` 全链路，需要**专门给 CEO 收尾前加一道可拦截、可返工的关卡**（自然落点就是 `out_of_range` 那处，但当下 CEO 循环已结束、只来得及记日志）。
3. **核验 → 返工 与收敛治理对冲。** 返工 = 多跑轮次，而现有 `LoopController` + `max_rounds`（[执行引擎 §十四](/docs/03-AI核心/执行引擎架构设计.md)）整体取向是「催 Agent 早点停」、还有轮预算上限。核验返工算不算进预算、与早停谁优先，未定。

**机制空白（动手前需逐条定，均未讨论）：**

- **机制落点**：核验代码到底跑在哪——`pipeline.py` 收尾后 / worker 执行器内 / `WaveScheduler` 新增一道「核验波次」。
- **轻层是纯代码校验，还是一次自检 LLM 轮**：正文两种混着说——纯代码（像 `check_contract`）只能查*形*、查不了「断言 ↔ 来源」；自检 LLM 轮则非「零成本」、且「自己查自己」本就抓不住深层语义。须二选一。
- **返工路由**：发现问题后走自动返工（`contract` 式）/ `revise` 唤回原作者 / `ask_user` 交还用户，走哪条、谁来选。
- **核验自身的失败 / 超时 / 误判策略**：审查 worker 报错或超时——交付阻塞还是放行？误报（白返工、添堵）与漏报（假安心）如何权衡？以及「谁来核审查者」的成本。
- **并行交付的核验拓扑**：多 worker 并行交付时，逐个产物各核一次，还是核拼装后的整体？正文「设计 → 实现 → 审查」是线性叙事，未覆盖并行扇出。
- **上线后度量**：§四 只把「未核验缺陷率」当**启动触发**，未定上线后如何度量核验本身的准确率 / 误返工率 / 增加的时延与成本（`turn_metrics` 表可承载）。

## 八、落地机制草案（推荐路线：代码打底 + 分诊补语义）🗂️

> 对 §七 三个硬点与机制空白的一版**可落地草案**，方向已选定（代码决定论打底、廉价分诊只补模糊语义）。仍 🗂️：接口形状与处置链已收敛，具体阈值 / 重试上限待实现时按内测数据调。落地后迁入 [`执行引擎架构设计.md`](/docs/03-AI核心/执行引擎架构设计.md) 的 ReAct 循环 / Run 模型章节。
>
> **落地现状（第一刀，已实现）**：本节草案的**最小子集**已落地——只取 8.1 的 `finish_guard` 收尾守卫 + 8.2 的「角标↔来源」轻层 + 8.4 的轻层回炉 / 预算对账，作为「造引用」这**一种**缺陷的决定论闸门。与草案的差异（**以现状为准**）：① 判定函数收窄为 `finish_guard(content, *, citation_count) -> reworks: list[str]`，暂不产出完整 `VerifyPlan`（只有造引用一条轻层，无 `heavy` / `triage` 字段）；② 回炉**只覆盖模型自报 done 的正常收口**，`_force_finalize` 强制收口路径**不过**守卫——8.4「finish_guard 优先于 `FINALIZE`」**未实现**，两者是独立路径而非优先级关系；③ 重层审查、分诊员、`WaveScheduler` 审查波次、产品呈现（§六）**均未落地**。完整行为契约见 [执行引擎 §十四·交付前核验](/docs/03-AI核心/执行引擎架构设计.md)。下文 8.1–8.5 保留为**完整蓝图**。

### 8.1 一个统一判定 + 一个收尾守卫（同解 硬点 1 与 硬点 2）

关键观察：**CEO captain 与 worker 跑的是同一个 `react_loop`**（见 [`pipeline.py`](/apps/server/agentcore/runtime/pipeline.py)：captain「the same react_loop assembly the workers use」）。所以把核验做成 loop 的**收尾守卫**，一处落点同时盖住两条路：

- **纯代码判定 `classify_delivery(content, files, *, declared_contract, opt_out) -> VerifyPlan`**（纯函数，照搬 [`runs/contract.py`](/apps/server/agentcore/runtime/runs/contract.py) `check_contract` 的可单测姿态）：扫产物的*可观测信号*，产出 `VerifyPlan = {light:[…], heavy: HeavyKind|None, needs_triage: bool}`。这层就是 §三「触发判据」的代码化，**不经任何 LLM、不靠 CEO 自觉**——直接拆掉 硬点 1（opt-in 矛盾）。
- **收尾守卫 `finish_guard`**：模型在某轮宣布 `done` 时，loop **不立刻接受**，先跑 `classify_delivery` 的轻层；不过 → 注入一条**锚定具体事实**的提示（复用 [`loop_controller.py`](/apps/server/agentcore/runtime/loop_controller.py) 已有的「轮间注入系统提示」口子与措辞风格）、不算 done、继续循环。这正是 §一 根因（「ReAct 唯一终止信号是 done，没有对称机制说交付前先核」）的**对称解**，CEO 直答路径自动被覆盖——直接拆掉 硬点 2。
  - CEO 直答的 `out_of_range`：从今天 `pipeline.py` 的「只记 warning」升级为 finish_guard 的一条轻层；命中即注入「[n] 无对应来源，请修正」、回炉一轮，而非记完日志照发。

### 8.2 扫哪些信号（代码先跑，对齐 §三 判据二）

| 信号（代码可观测） | 判定动作 | 归层 |
|---|---|---|
| 正文含 `[\d+]` 角标（剔除代码围栏内） | 每个 [n] 能否落到真实来源卡 | 轻 |
| 声明了硬规格（CEO 的 `contract`：章节 / 字数 / must_contain / json） | 复用 `check_contract` | 轻 |
| 残留 TODO / 声明 `output_format=json` | 扫 TODO 标记 / 试解析 | 轻 |
| 写出可运行文件（`.html/.js/.py/.sh/…` 或调过 `code_execute`） | 自动追加冒烟 / 审查 | 重·要跑（代码可定） |
| 成篇文本交付、且无可运行文件、又无明确机械信号 | 代码定不了 → 升级分诊 | 重·待分诊 |

- 轻层 = **宽触发**：扫到就查、零成本、偶尔误触无害（呼应 §三）。
- 重层确定性信号（可运行物）→ 代码直接接 [`WaveScheduler`](/apps/server/agentcore/runtime/runs/wave.py)：检测到可运行产物且该 delegate 未挂审查尾节点时，**自动追加一道审查 / 冒烟波次**（而非等 CEO 用 `depends_on` 自觉挂）。

### 8.3 何时升级叫分诊员（把 LLM 成本压到最少）

代码先跑；**仅当三者同时成立才叫分诊员**，避免每次交付都多一次调用：

1. 产物是**成篇文本交付**（长文 / 成篇 .md），且
2. 代码扫不出能定重层与否的明确机械信号（既非可运行物、又无硬规格可凭），且
3. 非明确 opt-out。

满足 → 调一次**廉价档模型**（`model_preference="fast"`，见 [`skills.py`](/apps/server/agentcore/runtime/skills.py)）做分诊：`triage_delivery(user_intent, product) -> {level, heavy_kind, opt_out}`，判「是不是以论证为核心 / 要不要换眼睛找漏 / 回源对照 / 还是只是品味（走 `ask_user`）」。这接住代码接不住的 §三「灰带」与「以论证为核心的成篇交付」意图信号。

- **stakes 闸**：分诊员**只在高风险产物上**才被允许触发昂贵的审查 worker；低风险成篇文本即便模糊，也只落轻层 + 一句非阻塞提示。
- **opt-out**：明确弃权词代码粗筛；模糊（「草稿就行」vs「快一点」）并入分诊员一并判，遵 §三「宁可没认出、不可误认」的不对称原则。

### 8.4 查出问题怎么处置（返工路由 + 与收敛治理对账，解 硬点 3）

- **轻层不过** → finish_guard 注入提示、回炉本 loop（产出者自改，最快最省）。
- **重层不过** → 审查 worker 的结论回到 CEO，CEO 据此 `revise` 唤回原作者定向返工，或 `ask_user` 交还用户（品味 / 取舍）——按「机械毛病 vs 取舍」分路由。
- **预算对账（硬点 3）**：finish_guard 的回炉有**独立小上限**（建议 ≤2 次），且这些轮**计入** `max_rounds` 总预算；但当「done 但轻层不过」时，finish_guard 的「继续」**优先于** `loop_controller.py` 的早停 `FINALIZE`——因为这不是机械空转，是有据可依的返工。两者注入文案共用「锚定具体事实」风格，不打架。
- **核验自身失败 / 超时**：审查 worker 报错或超时 → **放行但留痕**（呈现「审查未完成」而非假装通过），不阻塞交付，避免把核验变成新的卡死点。

### 8.5 仍未定的小尾巴

- 各阈值具体值（轻层回炉上限、stakes 高低线、分诊触发的「成篇」字数门槛）——实现时按内测数据调。
- 并行扇出的核验拓扑（§七 遗留）：倾向「每个交付产物各过 finish_guard（轻层天然分散），重层审查针对拼装后的整体或关键产物」，待定。
- 上线后度量挂 `turn_metrics`：核验触发率 / 误返工率 / 增加时延，验证这套没把「首字即时」拖垮。
