## 零、一句话结论

**辩论的"推理产物"质量其实很高**（决策简报的争议焦点、双方最强论点、事实/价值分歧分流、带反转条件的倾向判断都在线），**但支撑它的"联网取证层"这次几乎全线失效，且整回合耗时约 10 分钟**——对一个法律垂直产品，这是"可信度 + 体验"的双重隐患，比单纯性能更致命。

> **取证层失效根因已确诊（2026-07-01）**：＝**开发机本地代理的 fake-IP 模式**（DNS 把所有域名应答成 `198.18.0.x` 保留段 → SSRF 正确拦截），**非产品代码缺陷、非 ISP 劫持**；**生产大概率不受影响**。详见 §一。这把 §一从"产品 P0"降级为"开发环境 P0 / 生产待验证"，但它是本次所有事实"无据"的总根源。

## 一、联网取证层几近全线失效（开发环境 P0 / 生产待验证）

三处叠加，导致辩论的事实主张基本"无据可依"：

### 1.1 `read_url` 本回合 100% 失败（且都是 1ms 内瞬间失败）

- 现象：CEO 与正反双方辩手的每一次 `read_url` 都返回 `[ERROR] 链接解析到私有/保留地址，已按 SSRF 防护拦截`，`duration_ms=1`。
- 机制：命中 [`core/net.py`](/apps/server/agentcore/core/net.py) 的 `classify_url` → DNS 解析后任一地址落私网/保留段即 `PRIVATE_IP` 拦截（1ms = 只做了 DNS 分类、未发起真正请求）。
- **根因已确诊**（2026-07-01 系统 `nslookup` + 应用同路径 `classify_url`/`_getaddrinfo` 双向复核）：本机 DNS 服务器是 `198.18.0.2`，**所有**域名（含对照组 `baidu.com` / `gov.cn` / `wikipedia.org`）一律解析到 `198.18.0.x`。`198.18.0.0/15` 是 RFC 2544 保留段、Python `ipaddress` 判 `is_private` → 被 SSRF **正确**拦截。这是本机**本地代理 / VPN 的 fake-IP 模式**的典型特征（Clash/Mihomo/Surge/v2rayN 默认 fake-ip-range 即 `198.18.0.0/16`；代理用占位 IP 应答 DNS，再自行拦截并路由这些占位 IP）。
- **定性结论**：既不是 ISP DNS 劫持，也不是代码过拦——**SSRF 防护行为正确**；真正触发源是**开发机代理的 fake-IP 模式**与「应用自解析 DNS + Pin IP」的 SSRF 设计相撞。**生产服务器无此代理，read_url 大概率正常**——故本项对线上用户的严重度远低于初看：它是**开发环境把取证打死**（导致本次复盘 trace 全部"无据"），而非产品代码缺陷。
- 连带解释：`web_search` 的超时 / 返回英文 Google 翻译页噪音，同源于走这层 fake-IP 代理。
- 备注：`core/net.py`、`web/_net.py`、`web/read_url.py` 正被并行改动（pinned transport）；本项**不擅改**——是否让产品容忍代理环境属安全/架构权衡（见 §六）。

### 1.2 `web_search` 两种坏法

- **超时**：多次 `ReadTimeout（站点响应过慢）`，单次白等约 15s，并触发 `engine.tool_circuit_breaker warned=['web_search']`。
- **结果驴唇不对马嘴**：搜"收买被拐卖妇女 2015 刑法修正案九…"竟返回一堆 **Google Translate 帮助页（英文）**。中文法律 query 拿到英文工具站噪音 → 取证等于零。
- 相关配置：`web_timeout()` / 熔断在 [`web/_net.py`](/apps/server/agentcore/tools/builtin/web/_net.py)；搜索后端质量/超时阈值需一并评估。

### 1.3 落库 citations 被污染

- 给用户展示的"来源"里混进了 `https://mail.qq.com/ 登录QQ邮箱`（还带个 1987 年的日期）这种完全无关条目；真正相关的只有一条华律网。
- 后果：UI 挂着 citations 会让用户以为答案有出处，实则来源不可信。

### 连锁后果（为什么这是 P0）

辩论里那些"很唬人"的具体数据——追诉率、丰县案"最高刑 3 年 → 时效仅 5 年"、"加刑至 10 年预期惩罚增量 +1.05 年"——**基本是模型参数化知识，而非检索证据**。法律产品里这是**幻觉/可信度风险**。取证层修好后，事实主张才谈得上"可核验"。

### 1.4 解绑 runbook（关 fake-IP → 恢复取证 → 连带解锁 §二 profile / §三 真跑）

> 全程环境侧操作、**不改产品代码**。诊断已确诊根因＝本机代理 fake-IP（§1.1），本 runbook 只给"怎么解绑 + 怎么验"。

**Step 0 · 先确认是不是 fake-IP（一条命令，`apps/server` 下）**

```bash
uv run python scripts/probe_egress.py
```

看汇总行：`fake-IP 检出: YES` 且每条 `DNS -> …198.18.x.x(FAKE-IP)…` → 坐实（脚本即 §1.1 诊断同路径：应用 `_getaddrinfo` + `classify_url` + 真 `read_url`）。

**Step 1 · 关掉代理的 fake-IP（人操作，二选一）**

- **首选·把 DNS 模式从 `fake-ip` 改成 `redir-host`**（保留代理、只换 DNS 策略）：
  - **Clash / Mihomo**（Clash Verge / ClashX 等）：配置 `dns.enhanced-mode: redir-host`（或整体关 `dns.enable`），重载配置。
  - **v2rayN**（Windows）：设置里关「FakeDNS / fake-ip」，或路由里去掉 fakedns 相关出站。
  - **Surge**（macOS）：移除 `[General]` 的 `fake-ip` 相关项；或用 `always-real-ip` 覆盖目标域名。
- **或·临时让后端不走代理 DNS**：关 TUN / 系统代理，或只代理 HTTP(S) 不劫持 DNS，让 `getaddrinfo` 落真实公网 IP。

**Step 2 · 复验**：再跑 `probe_egress.py`，出现 `=> PASS：DNS 落真实公网 IP、SSRF 放行、read_url 端到端可读` 即恢复。

**Step 3 · 解锁下游**
- **§二**：跑一场真实辩论，拿到**不含 fake-IP 超时**的干净延迟 profile，再判是否值得做主持人 `_judge`+`_summarize` 合并（见 §二）。
- **§三**：配 `EVAL_DEEPSEEK_API_KEY` 后 `uv run python -m agentcore.evals --debate-converge` 真跑，拿过保守率读数（见 §三）。

> 另一条路「后端绕代理直连可信解析器（如 223.5.5.5）/ 放宽应用自解析」＝**削弱 DNS-rebinding 防护的安全/架构权衡**，需单独拍板，不在本 runbook 内擅动 `core/net.py`（且其正被并行改动，见 §六）。

## 二、延迟与成本（P1 / 待 §一 清后再谈）

- 整回合 **604s（约 10 分钟）**；其中 `debate` 工具本身占 **542s**。落账 `$0.047`、**输入 token 57.9 万**、reasoning token 2.5 万、workers 11、最终回复仅 1084 字。
- **诊断（2026-07-01）——"辩手串行搜索"这条初判不成立**：辩手取证的**并行早已做透两层**：跨辩手（同一轮不同方）首轮 `WaveScheduler`、后续轮 `asyncio.gather`＋信号量（[`tools/builtin/debate/rounds.py`](/apps/server/agentcore/tools/builtin/debate/rounds.py)）；单步内多工具 `asyncio.gather`＋`Semaphore(MAX_PARALLEL_TOOLS=5)`（[`runtime/engine/tool_exec.py`](/apps/server/agentcore/runtime/engine/tool_exec.py)）——一步里发多个 `web_search` 本就并行。只有 ReAct【跨轮】取证还串行（想→搜→读→再想），那是 ReAct 固有节奏，砍它＝砍证据质量。
- **542s 按根因拆**：① **§一 dev-env fake-IP 是大头**——每次 `web_search`/`read_url` 超时白等 ~15s（`SEARCH_TIMEOUT=16s`/`READ=15s`，见 [`core/net.py`](/apps/server/agentcore/core/net.py)），已诊断、生产大概率无，属 §一 不属本项；② **主持人自身的串行 LLM 流水线是 §二 唯一真·结构性延迟**——每轮 `_frame → [辩手并行] → _judge → _summarize`、末尾 `_brief`，均 `thinking=True`，5 轮≈16 次串行思考调用（[`runtime/debate/moderator.py`](/apps/server/agentcore/runtime/debate/moderator.py)）；③ 辩手 ReAct 跨轮取证（固有、非缺陷）。
- **判定：不做辩手取证节流（限次/降并发）**。thorough 辩手确无轮内取证预算（快速模式已限：`QUICK_DEBATER_HINT` 至多 1 次），但给它硬加预算＝拿"证据接地的法律辩论"这一核心价值，换一个**主要由 §一 造成、且是 n=1 脏样本**的耗时——触补丁绊线（特例节流、治标不治本），故弃。
- **下一步（纪律优先·开发期无真实数据）**：§二 的耗时被 §一 污染、又无聚合真实数据，**不在脏样本上盲调**。先清 §一（关 fake-IP / 后端绕代理直连可信解析器）拿到干净延迟 profile，再谈 §二。届时 §二 唯一站得住的结构性动作＝**把主持人每轮 `_judge`+`_summarize`（读同一份输入、背靠背串行）合并成一次结构化调用**（真去重、去掉冗余 round-trip，非节流补丁）——须先在 `conformance/vectors/` + `evals/` 验证（其 "referee vs 书记 persona 合并" 的质量代价现无真实数据可量），再动热点 `moderator.py`。
