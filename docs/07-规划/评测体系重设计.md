# 评测体系重设计 🗂️

> **定位**：以「任务结果」为中心重设计 AI 评测体系，**取代** `agentcore/evals/` 现行的「执行轨迹强匹配 + 手写合成集 + 真模型从不阻断」方向。方向已经产品负责人确认（4 项决策见 §二），实现细节待评审；落地后分段迁入 [`后端架构.md §五`](/docs/02-架构/后端架构.md)，本文退役。
>
> **治理**：🗂️ 仅 `07-规划`。落地前 [`后端架构.md §五`](/docs/02-架构/后端架构.md) 仍是现状权威，本文是其继任蓝图。
>
> **来源**：2026-06 评测体系方向评审（产品负责人发起「现行方向错了，换思路」）。行业对照见 §一末。

## 一、为什么换方向（旧方向的病根）

现行评测（`agentcore/evals/`，CLI `python -m agentcore.evals`）有四支柱：功能套件 Layer 1（`checks.py` 确定性断言）、路由准确率（混淆矩阵）、输出风格 anti-slop、对比评估（团队 vs 等算力单体，`comparison.py`）。问题不在工程质量，而在**测的东西错了**：

| # | 病根 | 具体 |
|---|---|---|
| 1 | **测机制，不测结果** | `Delegated` / `NotDelegated` / `RosterMatches` / `MaxRounds` 全是**手段**。一个回合能全过 check 却给废答案；也能违反 `RosterMatches` 却因更聪明的分解而更好。golden 标签把「作者的正确编排理论」固化成回归基线——在回归测试自己的假设。**按项目自身纪律（[`dev-process.mdc`](/.cursor/rules/dev-process.mdc)），这是「实现冒充需求」。** |
| 2 | **投资倒置** | 被 per-PR 硬门禁强制的，是最便宜、最确定、最低价值的部分（JSON 能否解析、有没有调某工具）；唯一衡量用户价值的部分（rubric 质量分）是最贵、软门禁、夜跑、从不阻断、且**从未落地**（Layer 2 绝对裁判恒为 P1）。闸门修在了不重要的地方。 |
| 3 | **全合成且极小** | ~8 core + 13 comparison + 几条 routing，全手写。这是 smoke test，不是 eval set，过拟合作者对「用户会问什么」的想象。 |
| 4 | **脱离真实使用** | 有 `logs/dev.jsonl`（事件/trace）+ Postgres（消息正文）的真实对话，最富信息的信号（真实用户问什么、Agent 在哪儿翻车）完全没用上。 |
| 5 | **裁判从未校准** | 现行裁判「fixed Pro」，无人工 gold-set、无一致性度量。**未校准的裁判 = 拿没刻度的尺子量质量**；且 DeepSeek 评 DeepSeek 有同家族自偏好。 |

**行业 2026 已收敛到哪**（佐证换方向）：

- **闭环回流是护城河**：生产轨迹 → 聚类找失败 → 失败轨迹进黄金集 → 离线回归 → 门禁 → 在线采样评分回流（LangChain / Braintrust）。
- **结果/端态判定，不锁轨迹**：tau²-bench 按「目标数据库端态 hash」判定，**不要求特定动作序列**；只有路径本身即交付物时才用轨迹强匹配（全集 ~9/100）。
- **pass^k 量可靠性**：看 k 次重跑的一致成功率，非单次（Anthropic model card 已采用）。
- **套件配比**：约 30% 启发式硬门 / 10% 参考集 / **40% 成对 LLM 裁判（主力）** / 20% 人工（长尾 + 裁判校准基准）。
- **裁判是仪器，必须校准**：用 Cohen's kappa（扣除偶然）而非原始 %；exact-match 会高估 33–41pp（arXiv 2606.19544）；kappa>0.6 常见线。
- **位置偏差是头号杀手**：swap-and-aggregate；连 rubric 打分也有位置偏差（arXiv 2602.02219）。
- **多 Agent 用 milestone KPI**：里程碑进度 + 个体贡献 + 沟通/规划分衡量**协作质量**，而非「roster 对不对」（MultiAgentBench）。

## 三、新架构：四层 L0–L3

投资从「下重上轻」翻为「中间重」——硬门禁瘦身、质量裁判扶正为主轴。

| 层 | 判定对象 | 何时跑 | 门禁性质 | 实现 |
|---|---|---|---|---|
| **L0 契约/安全硬门** | 不崩、引用可解析、不编造工具调用、schema 合法、成本/延迟预算 | per-PR | **硬门禁（零 LLM）** | `checks.py` 的**不变量子集**（详见 §八） |
| **L1 结果评分** | 用户要的拿到没有（端到端、结果维） | per-PR 小集 + nightly 大集 | **可门禁**（baseline 回归） | rubric 裁判主轴 + pass^k（详见 §五） |
| **L2 体验/信任 + 协作质量** | 可读性、诚实度、首字延迟、该追问是否追问；团队跑的 milestone/协作 | nightly | 信息性 → 逐步可门禁 | 裁判 + milestone KPI（详见 §六） |
| **L3 轨迹回流 + 诊断** | 真实轨迹聚类找失败；团队 vs 单体「值不值」 | 现在挖 / 上线后在线 + 季度诊断 | 喂数据，不直接门禁 | 详见 §四、§六 |

**关键反转**：旧体系硬门禁守 L0（最低价值）、质量（L1）永不阻断；新体系 **L1 结果质量是被守的主轴**，L0 只兜安全/契约不变量。

## 四、用例来源：从真实轨迹回流（适配「未上线」）

行业「生产轨迹飞轮」默认有流量；AgentCore 尚未上线，故分两阶段，**不提前造飞轮**（那是另一种实现冒充需求）：

- **现在（开发期）**：① 从 `logs/dev.jsonl` + Postgres join 挖 dev/吃狗粮真实任务；② 按 **intent 聚类**成分桶集（QA / 检索 / 写作 / 工具改文件 / 多步研究 / 团队任务…）；③ **每个 bug / 复盘缺陷 → 一条回归用例**（沿用项目已信的「棘轮」纪律，[`protocol-conformance.mdc`](/.cursor/rules/protocol-conformance.mdc) 同思路，用在质量上）。
- **上线后**：在线采样真实流量评分 → 自动聚类失败模式（LangSmith Insights 式）→ 低分轨迹自动进黄金集，闭环。

**实现现实**：消息正文在 Postgres、运行时事件在 `logs/dev.jsonl`（见 [`conversation-logs.mdc`](/.cursor/rules/conversation-logs.mdc)），挖任务须两边按 conversation / trace join。

**人工 gold-set（决策 2）**从这批真实轨迹里抽 100–200 条标注，既作裁判校准基准、又作 L1 的高价值种子。

## 五、裁判可信工程（DeepSeek-only 适配，决策 1+2）

裁判是测量仪器，先校准再用，否则在没刻度的尺子上做决策（行业头号 pitfall）。

**校准回路**：

1. 跑生产裁判过 gold-set；
2. 算 **Cohen's kappa**（分类）/ 加权 kappa·Spearman（序数 1–5），**不用 exact-match**（高估 33–41pp）；
3. **kappa>0.6 才准上门禁**；读分歧样本找模式（偏长？偏自信？偏位置？）→ 改 rubric/prompt → 重跑；
4. **重校触发**：月度 + 改 rubric / 换模型 / 判↔人分歧 >20–25%。

**消偏（结构性）**：

- **位置偏差**：成对走 **swap-and-aggregate**（两序都跑、两边一致才计胜，不一致记平）；flip rate <5% 健康、>20% 说明位置压过内容。rubric 打分用平衡置换（cyclic permutation）抵消选项位置偏差。
- **长度偏差**：rubric 明写「不为长度加分，惩罚注水 / 冗余 / 重复」。
- **同家族自偏好**（DeepSeek-only 的代价）：用 **Pro 评 Flash**（评判档高于被评档）+ 持续监测 kappa；同家族偏差作为**已知限制**入文档。
- **CoT**：先输出理由再给分 / 选项，提升与人对齐 + 可审计。

**成本纪律**：裁判成本控在生产 LLM 成本 **10–15%** 内（采样不全量、异步、单独记账，逼近 25% 就降采样/降档）。

**反模式**：**100% 通过 = eval 太水**的警报，不是胜利；严格裁判上 70% 比水裁判上 100% 更有信息。

## 六、多 Agent：milestone KPI 取代轨迹标签（决策 4）

产品差异点是「真团队协作」，评测问题从「团队比单体好吗（研究问题）」转为「**团队这一跑，交付目标了吗 + 协作得当吗（产品质量）**」。

- **milestone 覆盖（结果维）**：给任务定一份子目标清单，判**交付物**覆盖没有（不管谁干的）。这是结果断言，不是轨迹断言。
- **协作质量分（体验维，5 点 LLM）**：子 Agent 产出有没有被 CEO 真整合（综合收尾），还是被丢 / 重复；分工合不合理。
- **个体贡献**：每个被派出的 Agent 对最终答案有无实质贡献。→ **这才是「过度编排」的正确度量**：不是 `NotDelegated` 标签，而是「派了但零贡献 = 浪费」，按价值判（叠加 L0 成本预算）。

**旧→新对照**：

| 旧（机制 / 轨迹） | 新（结果 / 价值） |
|---|---|
| `Delegated` / `NotDelegated` | 不再判；过度编排 → 个体贡献=0 + L0 成本预算 |
| `RosterMatches`（expected 角色） | milestone 覆盖（交付物对不对） |
| team vs single 胜率（夜跑软门禁） | 降为季度诊断；日常看 milestone 覆盖 + 协作分（可门禁） |

**`comparison.py` 处置**：等算力 / best-of-N / 思考-token 对齐机器**保留为偶发诊断**（回答「团队在哪些 archetype 值得」，要做路由引擎前 / 季度手动跑），不再当核心 nightly 回归指标。

**用例雏形**（以现有 `par_rag_survey` 为例，rubric 散文 → 可评分的绝对 milestone 清单）：

```json
{
  "id": "par_rag_survey",
  "intent": "parallel_research",
  "path": "team",
  "user_message": "调研 RAG 的三个优化方向：重排序、查询改写、混合检索，每个方向各找 2 条代表性做法，最后说明三者能否组合。",
  "outcome": {
    "milestones": [
      { "id": "rerank_2",  "desc": "重排序方向 ≥2 条具体、真实存在的做法", "weight": 1 },
      { "id": "rewrite_2", "desc": "查询改写方向 ≥2 条", "weight": 1 },
      { "id": "hybrid_2",  "desc": "混合检索方向 ≥2 条", "weight": 1 },
      { "id": "synthesis", "desc": "末尾给出三者能否组合的综合判断（非简单罗列）", "weight": 2 }
    ],
    "pass_threshold": 0.8,
    "no_fabrication": true
  },
  "contract": [ { "name": "FinishReason" }, { "name": "NoFabricationMarker" } ],
  "team_quality": { "collaboration": true, "individual_contribution": true },
  "samples": 5,
  "passk": true
}
```

milestone 由裁判一次结构化打分返回逐项布尔；覆盖率 = 加权命中比，≥ 阈值且无编造即过。`synthesis` 这条恰好捕获 CEO 的整合价值（团队的命门），`team_quality` 只在 team 路径跑。

## 七、门禁分层

| 闸 | 内容 | 红线 |
|---|---|---|
| **per-PR** | L0 全部（硬）+ L1 **小集**（廉价裁判档）+ baseline 回归 | L0 任一不变量破 → 红；L1 跌破 baseline 超阈 → 红 |
| **nightly** | L1 大集 + L2 + L3 诊断 + 切片分析 | 信息性为主，回归显著才告警 |

- **baseline 回归门**：分数落盘 + `--update-baseline`；只有**跌破**才红（区别于现行「全过才绿」）。
- **切片分析**：按 intent / 质量档 / 路径分段出均值 + 置信区间 + **分布**（防双峰被均值掩盖）；CI 宽于 delta 时不宣布胜利。

## 八、迁移：现有代码怎么处理

| 模块 | 处置 |
|---|---|
| `checks.py` | **保留不变量子集**：`FinishReason`(错误态)、`NonEmpty`、`ToolArgsValid`、`HasCitations`(可解析)、`NoFabricationMarker`、`Max*`(成本/延迟预算)。**降级为诊断**：`Delegated` / `NotDelegated` / `RosterMatches`（轨迹形状，不再 pass/fail）。 |
| `comparison.py` | 降为**季度诊断 CLI**，移出核心回归；等算力/best-of-N 协议保留备查。 |
| `judge.py` | 从「接口位（P1）」**扶正为主轴**：实现 rubric 绝对裁判 + milestone 结构化打分 + gold-set 校准 + swap-and-aggregate。 |
| `harness.py` / `types.py` / `runner.py` / `report.py` | 大体复用（`TurnOutcome` 归一化仍有用）；扩 milestone / 协作 / 体验字段 + 切片维度。 |
| `routing.py` | 路由准确率混淆矩阵（轨迹标签）暂留**诊断**，等路由引擎落地再定去留。 |
| `cases/` | `core` 重写为结果 milestone；`comparison` 留诊断；**新增**从真实轨迹回流的 intent 分桶集。 |
| `style_lint.py` | 并入 L0/L2（anti-slop 仍是确定性护栏，无需独立支柱）。 |

## 九、分期

- **P0（现在）**：L0 瘦身；`judge.py` 裁判扶正 + gold-set 校准回路 + baseline 门；从真实轨迹挖第一批 intent 分桶集；`core` 用例改 milestone。
