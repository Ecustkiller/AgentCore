# 评估体系后端落地设计（功能正确性 + 多 Agent 对比）🗂️

> **定位**：本文是 [`后端架构.md §五 评估体系`](/docs/02-架构/后端架构.md) 的**后端先行落地蓝图**，覆盖**两类正交的评估**，共用同一个 `agentcore/evals/` 代码包：
> - **第一部分·功能正确性评估**（Layer 1 离线确定性硬门禁 + Layer 2 在线 LLM 绝对裁判）：判定**单条回合对不对 / 防回归**。
> - **第二部分·多 Agent 对比评估**（三臂对照 + 成对盲评 + 预算对齐）：判定**多 Agent 架构是否真比单 Agent 好**，并把「团队制胜边界」喂回路由引擎。
>
> 两者**共享地基**（harness / `TurnOutcome` / costing / CI 策略 / 零侵入红线，见第〇部分），但判定单位不同（绝对正确性 vs 相对优劣）、裁判不同（`LLMJudge` 绝对打分 vs `LLMPairwiseJudge` 成对偏好）、用例不同（`cases/core/` vs `cases/comparison/`）。
>
> **为何先做评估**：「优化 AI 功能」的元前提是**能度量**。当前改 prompt / 换质量档 / 调收敛治理全凭手感，无法判断变好变坏，也防不住回归。本体系是后续一切 AI 优化（上下文工程 / 可靠性硬化 / 团队质检 / 智能路由）的方向盘与防回归网。
>
> 状态：🗂️ 蓝图，**两部分 P0 均已落地**。
> - **第一部分 P0 ✅**：评估类型 + harness〔`react_loop`/`run_chat_pipeline` + `RecordingSink`〕+ 确定性 Check + seed_lint + runner + report + CLI + 8 种子用例 + 假-provider smoke 自测（见 `apps/server/agentcore/evals/` 与 `apps/server/tests/test_evals_*.py`；离线工具尚未接 CI）；P1+ ⏳：LLM 绝对裁判 / baseline 回归门禁 / CI 接入。

## 第〇部分 共享地基（两类评估的公共底座）

### 〇.1 公共决策原则

| 维度 | 决定 |
|---|---|
| 侵入性 | **零生产风险**——只消费 `react_loop` / `run_chat_pipeline` 的现有返回值 + `EventSink` 事件，不改引擎/管线一行 |
| 运行入口复用 | 单 Agent → `react_loop`；团队 → `run_chat_pipeline`。**不新增运行入口** |
| 不挂起 | team 路径强制 `approvals_enabled=False` → 关掉 ask_user/plan_review 挂起，评测绝不空等超时 |
| 用例形态 | 黄金用例 = 数据（**JSON**，走 stdlib、无新依赖）+ 可选工作区现场（fixture 目录）；加一例 = 加数据，不是加代码 |
| 成本/用量 | 复用 `cost_runs`（管线已折算）+ `runtime/costing.py` 定价；`TurnOutcome` 已带 `cost_usd`/`latency_ms`/`usage` |
| 非确定性 | `samples=k` 重跑取通过率/均分；chat/agent 档均 `thinking=True`，思考模型常不吃 temperature，temp=0 仅辅助、不作硬门禁承诺 |
| CI 策略 | **每-PR 零 LLM 硬门禁**（seed_lint + 假-provider 自测）+ **真模型评测仅 nightly/手动软门禁**（见 〇.6） |
| 判定口径 | **规则断言全过 且（无裁判 or 裁判通过）**——功能侧绝对裁判 ≥3 分；对比侧成对偏好 + pass^k |
| 模块落点 | `apps/server/agentcore/evals/`（与 `agentcore` 同树、可 import 运行时；不被服务代码引用、不进镜像） |

**一句话**：评估体系 = 把黄金任务喂给**真实运行路径**，用**确定性断言**（消费事件流 + 返回值，判定零 LLM）+ **LLM 裁判**（真模型语义打分 / 成对偏好）双信号判定，产出可与 baseline 对比、可挂 CI 的回归报告。

### 〇.2 关键洞察：拼图已现成，落地是「纯增量」

§五此前未落地易被当作「要造一大套」。实则地基**全部现成、可离线复用**，落地主要是**组装 + 数据**：

| 需要的能力 | 现成件 | 证据 |
|---|---|---|
| 离线跑单 Agent 一轮 | [`react_loop`](/apps/server/agentcore/runtime/engine.py)，返回 `(content, reasoning, usage, rounds)` | `tests/test_engine_governance.py` 已用「脚本化假 provider + 裸 `EventSink()` + `ServerWorkspace`」离线驱动 |
| 离线跑团队整回合 | [`run_chat_pipeline`](/apps/server/agentcore/runtime/pipeline.py)，返回 `content/finish_reason/citations/runs/cost_runs` | 管线已是纯函数式入口，依赖均可注入 |
| 截获过程事实（工具调用/委派/引用） | [`EventSink`](/apps/server/agentcore/runtime/events.py)，可裸构造、`execution_journal()` 取离散事件 | 管线即用 `sink.execution_journal()` 落 `runs` |
| LLM 裁判 | [`LLMProvider.complete()`](/apps/server/agentcore/llm/protocol.py) 非流式打分；[`build_provider()`](/apps/server/agentcore/llm/factory.py) 给真实 DeepSeek | `scenario` 字段已为成本归因预留 |
| 成本/用量 | `cost_runs`（管线已折算）+ [`runtime/costing.py`](/apps/server/agentcore/runtime/costing.py) | 每用例成本直接读，不重造 |
| 等算力 C 臂（对比专用） | [`RunPolicy.candidates`](/docs/03-AI核心/Agent协作模式.md)（best-of-N） | 复用既有候选采样能力，不重造 |
| 质量档可控 | [`resolve_profile_set` / `default_profile_set`](/apps/server/agentcore/llm/modes.py) | 可分 economy / quality 跑分对比 |

**结论**：功能评估完全消费上面的返回值与事件，零成本、零侵入；对比评估只多加「对比编排 + 成对裁判 + 分段报告」。**不需要给引擎/管线加任何 hook**。

> **守零侵入**：全程只读返回值与事件。若发现「必须给引擎加 hook 才能断言某事实」→ 先停、提报（可能是可观测性缺口，单独决策），不私自改引擎。

### 〇.4 harness 接现有运行路径（零侵入）

```python
# evals/harness.py（提案骨架）
class RecordingSink(EventSink):
    """在现有 EventSink 上挂钩，捕获过程事实供断言。
    - tool_calls：从 tool_use_start 取 (name, args)
    - roster：从 run_plan(agents/runs) 与 run_completed.role 取角色（run_started 不含 role）
    其余事件照常入 execution_journal()。"""

async def run_case(case: EvalCase) -> TurnOutcome:
    backend  = ServerWorkspace(root=_fixture_root(case), sandbox=SubprocessSandbox())
    provider = build_provider(_eval_credentials())   # 真实 DeepSeek（必须自带 eval key，见 三.3 决策点）
    profiles = resolve_profile_set(case.mode, custom_modes={}, ceiling=settings.selectable_models)
    sink     = RecordingSink()
    t0 = time.monotonic()
    try:
        if case.path == "single":
            tools = build_ceo_tool_registry() if case.toolset == "ceo" else build_builtin_registry()
            profile = profiles.get("chat")             # 走 mode 解析，与 team 同口径
            content, _r, usage, rounds = await react_loop(
                messages=[*_history_messages(case.history),
                          LLMMessage(role="user", content=case.user_message)],
                llm=provider, tools=tools, sink=sink,
                tool_context=_ctx(backend), profile=profile, citation_sink=[],
            )
            # react_loop 不返回 finish_reason：镜像 pipeline 按轮数推导（degraded 当前不 emit）
            finish = "end_turn" if rounds < profile.max_rounds else "max_rounds"
            cost = price_usage(usage, profile.model)   # runtime/costing.py 现算（react_loop 不回 cost）
            return TurnOutcome(content=content, finish_reason=finish, rounds=rounds,
                               tool_calls=sink.tool_calls, citations=sink.citations,
                               delegated=False, roster=[], usage=usage, cost_usd=cost,
                               latency_ms=_ms(t0))
        # team 路径：approvals_enabled=False 关掉 ask_user/plan_review 挂起，绝不空等超时
        result = await run_chat_pipeline(
            conversation_id=new_id(), user_message=case.user_message, history=case.history,
            sink=sink, user_id="eval", backend=backend,
            approvals_enabled=False, profile_set=profiles,
        )
        return TurnOutcome(content=result["content"], finish_reason=str(result["finish_reason"]),
                           citations=result["citations"], delegated=bool(result["runs"]),
                           roster=sink.roster, rounds=result["rounds"],
                           usage=_usage(result), cost_usd=_sum_cost(result["cost_runs"]),
                           latency_ms=_ms(t0))
    except Exception as e:                              # react_loop/pipeline 失败 → error 态
        return TurnOutcome(content="", finish_reason="error", error=str(e),
                           tool_calls=sink.tool_calls, citations=[], delegated=False,
                           roster=[], rounds=0, usage={}, cost_usd=0.0, latency_ms=_ms(t0))
```

要点：
- **不新增运行入口**。单 Agent 走 `react_loop`（轻、快，测工具/引用最准；失败抛异常→捕获为 `error` 态，finish_reason 按轮数推导）；团队走 `run_chat_pipeline`（拿 `runs` 执行日志判委派 + `cost_runs` 算成本）。
- **team 路径强制 `approvals_enabled=False`**：连带关掉 ask_user/plan_review 挂起，否则用例触发它们会空等到 600s 超时（注：eval 用 `ServerWorkspace`/`location="server"`，worker 审批本就不 gate，但挂起原语仍会装配，必须显式关）。
- **成本**：单 Agent 的 `react_loop` 只回 usage、不回 cost，用 `runtime/costing.py` 现算；团队直接读 `cost_runs`。
- **temperature**：`ModelProfile.temperature` 本就存在，强制 temp=0 只需 `replace(profile, temperature=0.0)`——但 chat/agent 档均 `thinking=True`，**思考模型通常不吃 temperature**，故路由确定性主要靠多采样命中率，不靠 temp=0。
- **隔离**：`user_id="eval"` + 独立 fixture 工作区 + 隔离 data_dir（避免 `default_memory_store()` 读到残留 `eval.md`）；DeepSeek key 由 `_eval_credentials()` 从 eval 专用环境变量读（BYOK 下平台 key 为空，见 三.3）。

### 〇.5 数据基座（TurnOutcome 与归一化）

```python
# evals/types.py（节选，✅ 已落地）
@dataclass
class TurnOutcome:
    """harness 把一次真实运行归一化成可断言的事实。"""
    content: str
    finish_reason: str
    tool_calls: list[tuple[str, str]]   # (name, args_json) 按序
    citations: list[dict]
    delegated: bool
    roster: list[str]                   # 实际委派出的角色（team 路径，来自 run_plan.agents/runs + run_completed.role）
    rounds: int
    usage: dict
    cost_usd: float
    latency_ms: int
    error: str | None = None
```

`TurnOutcome` 是两类评估的**共同输入**：功能侧拿它跑 Check + 绝对裁判；对比侧把同任务多臂的 `TurnOutcome` 配对跑成对裁判 + 三轴度量。`cost_usd`/`latency_ms`/`usage` 已就位，对比的「成本比/延迟比/思考-token 预算」直接读，不重造。

### 〇.6 CI 策略：什么进每-PR、什么随 nightly

真实模型评测 = **花钱 + 不确定 + 要 key**，故按「判定是否需要真模型」而非「确定性与否」划线：

| 跑法 | 触发 | provider | 门禁 | 覆盖 |
|---|---|---|---|---|
| **零 LLM 自测** | **每 PR** | 假 provider（脚本化） | **硬门禁**（阻断合并） | `seed_lint`（纯静态）+ harness/checks/judge-解析 单测 + `test_evals_smoke`（脚本化跑通单/团队两路）+ 对比配对/PairwiseJudge 解析自测 +（可选）cassette 回放轨迹断言 |
| **真模型评测** | **nightly / 手动** | 真实 DeepSeek（CI 注入 eval 专用 key） | **软门禁**（告警 + 上传报告） | 确定性 Check（跑在真输出上）+ LLM 绝对/成对裁判 + 多采样 + baseline 对比 |

- **关键澄清**：确定性 Check 本身判定零 LLM，但要断言**真实模型行为**（真调了 web_search 吗、真委派了吗）就得先真跑 → 归 nightly。per-PR 硬门禁守的是**评估系统自身不回归**（用假 provider），不烧 token。
- **cassette（可选增强，backlog）**：录制一次真跑的事件流，存为 fixture，per-PR 回放跑确定性 Check——让「真实行为的轨迹断言」也能进硬门禁。P0 不承诺，先用脚本化 smoke。
- **CI 安全**：`tool_use`/`team` 用例若命中 `code_execute` 会在 CI 真起子进程（`SubprocessSandbox`）；首批用例**避开 code_execute**，或在受控沙箱跑。
- **baseline 回归**：`runner` 把真模型报告存 `baselines/*.json`；新跑对比 → 标回归（检查项新失败 / 裁判均分跌 > 阈值 / 成对胜率显著下滑）；`--update-baseline` 显式更新。
- CI 接线见 [`部署与运维.md §九 工程门禁`](/docs/05-平台与运维/部署与运维.md)（与棘轮/契约门禁同处挂载）。

## 第一部分 功能正确性评估（Layer 1 确定性 + Layer 2 绝对裁判）

> 回答「**功能对不对 / 有没有回归**」：判定单位 = 单条回合的绝对正确性；裁判 = `LLMJudge` 绝对打分（rubric 1–5，≥3 通过）；用例 = `cases/core/`。判定口径：**规则断言全过 且 裁判分 ≥ 3** 才算通过。

### 一.1 核心接口（dataclass + Protocol）

```python
# evals/types.py（功能评估部分）
EvalCategory = Literal["qa", "retrieval", "team", "tool_use", "no_fabrication", "routing"]
RunPath = Literal["single", "team"]   # single→react_loop, team→run_chat_pipeline

@dataclass
class EvalCase:
    id: str
    category: EvalCategory
    user_message: str
    path: RunPath = "single"
    mode: str = "economy"                       # 质量档，可分档跑分对比
    toolset: Literal["ceo", "worker"] = "ceo"   # 单 Agent 用哪套工具（只读子集/全集）
    workspace_fixture: str | None = None        # 相对 evals/fixtures/，挂为 ServerWorkspace root
    history: list[dict] = field(default_factory=list)
    checks: list[dict] = field(default_factory=list)   # [{name, args}]，名字注册表解析
    # 期望委派角色等断言参数统一进 checks 的 args（如 {name:"RosterMatches", args:{expected:[...]}}）
    rubric: str | None = None                   # Layer 2 裁判准则；None=跳过裁判
    samples: int = 1                            # 重跑次数（治非确定性，取通过率/均分）

@dataclass
class JudgeVerdict:
    score: float          # 1–5
    passed: bool          # score >= 阈值(默认 3)
    rationale: str

# CaseReport / EvalReport 聚合（按类通过率 / 裁判均分 / 总 token·$ / 与 baseline 回归项）
# Check / Judge / Harness 三 Protocol 解耦「怎么跑」与「怎么判」
```

### 一.2 确定性信号（判定层：无需裁判的 Check）

> **「确定性」是 Check 的属性（判定不调 LLM），与「何时跑」无关**——事件流仍需来自脚本化 provider 或 cassette 回放。哪些进 per-PR、哪些随 nightly 见 〇.6。

| Check | 断言 | 适用类别 |
|---|---|---|
| `FinishReason` | finish == `end_turn`（非 error/max_rounds；单 Agent 由轮数推导） | 全部 |
| `NonEmpty` | content 非空、长度 > 阈值 | qa / team |
| `ToolCalled` | 调用了 `args.tool`（如 web_search） | retrieval / tool_use |
| `ToolArgsValid` | 工具入参 JSON 合法、含必填键 | tool_use |
| `HasCitations` | citations ≥ `args.min` 且正文 `[n]` 与卡对齐 | retrieval |
| `Delegated` | `delegated == True`、无失败 run | team |
| `RosterMatches` | 实际 roster ⊇ `args.expected`（角色） | routing |
| `MaxRounds` | rounds ≤ `args.budget` | 全部 |
| `NoFabricationMarker` | 无「声称调用了未提供工具」等编造痕迹 | no_fabrication |

> **种子完整性 lint**：`seed_lint.py` 静态校验用例 JSON（必填字段、非法 `category`/`path`/`toolset`、`checks` 名不在注册表、既无 checks 也无 rubric、`samples`≥1、id 唯一）——纯静态，per-PR 硬门禁。
> **roster 来源**：`RosterMatches` 的实际 roster 由 `RecordingSink` 从 **`run_plan`（`agents`/`runs` 计划期角色）与 `run_completed.role`** 捕获——**不是** `run_started`（其载荷只有 run_id/agent_id/parent_run_id/kind/revision，无 role）。
> **路由准确率属确定性断言**（截获委派目标与 golden 比对、不需裁判）：但因思考模型非确定性，它**不进 per-PR 硬门禁**，随 nightly 真跑、以多采样命中率作软指标（见 一.3）。

### 一.3 Layer 2 绝对裁判（在线 LLM，软门禁）

| 维度 | 落地 |
|---|---|
| **路由准确率** | 团队用例跑 k 次，统计 roster 命中率（与 `RosterMatches` 的 `args.expected` 比对）；思考模型非确定，以**多采样命中率**作软门禁趋势指标（temp=0 仅辅助，不保证可复现） |
| **输出质量** | `LLMJudge.score(case, outcome)`：把 `case.rubric` + `user_message` + `outcome.content`(+citations) 组成裁判 prompt，`provider.complete(scenario="eval.judge")` 出 `{score 1-5, rationale}` |

裁判设计：
- **裁判模型用 Pro**（稳定优先）；裁判 prompt 要求**先给理由后给分**、强制 JSON 输出、锚定 rubric 维度（正确性/相关性/引用支撑/不编造）。
- **多采样**：`samples=k` 对「跑 Agent + 裁判」整体重复，报告**均分 + 通过率**而非单次，压住方差。
- **成本归因**：裁判调用打 `scenario="eval.judge"`，与被测回合的 token/$ 分开统计。

> **faithfulness 局限（已知）**：裁判判「引用是否支撑结论」时只看 `TurnOutcome.citations` 的 snippet，**看不到模型实际读到的整页/工具全文** → 该维度判得浅。彻底解决需把工具输出全文也喂裁判，但显著增成本与 prompt 长度；P1 先接受此局限，作为「方向性信号」而非铁证。

### 一.4 黄金任务集（分类 × 双层信号）

| 类别 | Layer 1 确定性 | Layer 2 裁判维度 |
|---|---|---|
| `qa` 单答问答 | FinishReason / NonEmpty / MaxRounds | 正确性 + 相关性 |
| `retrieval` 检索引用 | ToolCalled(web_search) / HasCitations / 角标对齐 | 引用是否支撑结论（faithfulness） |
| `team` 团队编排 | Delegated / 无失败 run | 产出是否整合各 worker |
| `routing` 路由准确 | RosterMatches（roster ⊇ 期望角色） | 多采样命中率（软指标） |
| `tool_use` 工具正确 | ToolCalled / ToolArgsValid | — |
| `no_fabrication` 不编造 | NoFabricationMarker | 是否坚守「不知道就说不知道」 |

首批 8 个种子用例（`cases/core/`）覆盖以上类别各 1–2 例；`fixtures/` 下放检索/文件类用例所需的小工作区现场。

## 第二部分 多 Agent 对比评估（团队 vs 单体的可证明优势）

> 第一部分判「功能对不对」；本部分判一个**正交且更难**的问题：[`产品定位与品牌.md`](/docs/01-产品/产品定位与品牌.md) 把「**真正的 Agent 团队协作**」立为核心差异、喊出「单个模型的智能有天花板，协作智能没有」——**这条命题从未被本仓库的评估验证过**。现有 `team` 类用例断言的是 `Delegated`（委派触发没）/`RosterMatches`（角色对没），是「**管道通没通**」，不是「**产出更好没**」。本部分是把命题变成**可复现证据**的对比评估蓝图。

### 二.0 命题与研究背景（2026）

多 Agent「更强」正被学术界正面狙击，且证据直指我们的底座家族：
- 《Single-Agent LLMs Outperform Multi-Agent Systems under Equal Thinking Token Budgets》(arXiv 2604.02460)：**等思考-token 预算下，单 Agent 持平或打赢多 Agent**；测了串行/辩论/集成/并行角色/子任务并行 5 种架构，含 **DeepSeek-R1**。结论：「许多所报告的 MAS 收益，用算力与上下文效应解释，比用架构优越性解释更合理。」
- 《The Illusion of Multi-Agent Advantage》：单 Agent 的 CoT 自一致用 **<10% 成本**打赢一众**自动** MAS 框架——**但**专家设计、角色专精的 **Expert-MAS 赢得很大**（某骨干模型 49.1%→96.7%，成本与单体相当）。
- MASEval (arXiv 2603.08835)：现有基准「把模型能力与框架实现混为一谈」，**框架选择对结果的影响和换模型一样大**。

**一句话风险**：若我们只做「自动委派、啥都派个团队」，大概率落进「幻觉优势」一侧——花更多钱、不更好。本评估的使命就是**找到并守住团队真能赢「等算力单体」的那条边界**，并把它喂回路由，让「协作更强」从口号变成运行时事实。

### 二.1 对比专属决策摘要

| 维度 | 决定 |
|---|---|
| 评测对象 | **架构而非单条回合**——比较「单 Agent」与「团队」在同一任务上的产出优劣，不是判某次回答对错 |
| 对照模型 | **三臂**：A=单体（`react_loop`）/ B=团队（`run_chat_pipeline`）/ **C=等算力单体**（best-of-N 或自我批判，烧到 ≈B 的预算）。A/B 看「团队比朴素单体强不强」，B/C 看「强是不是只因烧了更多算力」 |
| 公平性铁律 | **协作溢价 = B 在「与 C 预算对齐」时仍胜 C**。B 赢 A 但 token 远大于 A → 记为「算力效应」，不计协作功劳 |
| 预算单位 | 主用**思考-token**（对齐 arXiv 2604.02460），辅看总 token / 成本 / 墙钟延迟；残余不齐如实暴露 token 比 |
| 判定指标 | **成对偏好**（盲评 + 位置对调）为主，**pass^k** 治可靠性，多维（质量胜率 + 成本比 + 延迟比），**按原型分段**——不报全局单一胜率 |
| 任务集 | 黄金集每例须有「**区分杠杆**」（单体结构性做不好、团队天然能 handle，或反之）；含**负对照组 + 伪团队陷阱**防裁判 verbosity 偏好 |
| 战略闭环 | 评估产出的「团队制胜边界」→ 喂 [`Agent协作模式.md §7.1`](/docs/03-AI核心/Agent协作模式.md) 规划中的**路由引擎**，决定哪些任务该自动升级成团队 |

**一句话**：把一批「有区分杠杆」的黄金任务，**同时**喂给单体 / 团队 / 等算力单体三臂，用成对盲评 + pass^k 在「质量·成本·延迟」三轴上分原型比较，产出「团队在哪类任务、何种预算下真赢」的可复现报告，并把这条边界喂回路由。

### 二.2 三臂对照模型

```
              同一 user_message（同档模型、同 fixture）
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   Arm A 单体        Arm B 团队        Arm C 等算力单体
   react_loop      run_chat_pipeline   best-of-N / 自我批判
   （朴素基线）     （CEO+worker）      （烧到 ≈B 的 token 预算）
        │                 │                 │
        └──────► 成对盲评（B vs A、B vs C）+ pass^k + 三轴度量 ◄──────┘
```

判定逻辑（**这是本部分的命门**）：

| 比较 | 看什么 | 结论含义 |
|---|---|---|
| **B vs A** | 团队是否胜朴素单体 | 是 → 团队「有用」，但**未排除算力混淆** |
| **B vs C**（预算对齐） | 团队是否胜**等算力**单体 | 是 → **真协作溢价**（值得捍卫、可写进卖点）；否 → 收益只是算力，应收窄宣称 |
| **C vs A** | 等算力单体相对朴素单体的增益 | 量化「光给单体加算力能买到多少」，作为 B 的及格线 |

> **为什么 C 臂不可省**：arXiv 2604.02460 /《Illusion》的核心结论就是「多数所报 MAS 收益是算力效应」。没有 C 臂，B 赢 A 证明不了任何架构优越性，只会被一句「你不过是烧了 5 倍 token」击穿。

### 二.3 预算对齐协议（公平性的工程实现）

目标：让 C 臂消耗的算力 ≈ B 臂，从而隔离「协作」与「算力」。因团队 token 随任务波动，采**测量后对齐**而非拍脑袋：

1. **先跑 B 臂** k 次，取该任务**思考-token 中位数** `T_B`（主单位；辅记总 token / cost / 墙钟）。
2. **构造 C 臂**到预算 `T_B`：
   - **best-of-N 单体**（默认，对齐 CoT-SC 研究）：调 `RunPolicy.candidates` 的 N，使 N×单次思考-token ≈ `T_B`；多候选用 PairwiseJudge 或自评选优。
   - **自我批判单体**（备选 C′）：单次运行内「草稿→自审→修订」多轮，调 `max_rounds` 逼近 `T_B`。
3. **如实报告实际 token 比** `r = tokens_B / tokens_C`。`r∈[0.8,1.25]` 视为对齐；超出则给「预算未对齐」警示，结论降级为「方向性」。
4. **延迟单独看**：团队**并行扇出**可在 token 相当时仍赢墙钟延迟——这是独立且正当的赢点，**不要**被 token 对齐抹掉，单列 `latency_ratio` 报。

> **已拍板（三.3）**：预算主单位 = **思考-token 对齐**（钱/延迟并列报但不对齐）；C 臂 = **先 best-of-N**（自我批判 P2 加 C′）。

### 二.4 任务原型与黄金集

**铁律**：没有「区分杠杆」的任务是废用例——若单 Agent 也能做得一样好，跑多少次都分不出优劣。每例须标注：单体结构性短板 / 团队天然优势（或反之）。首批 13 例，4 原型：

| 原型 | 假设赢家·轴 | 区分杠杆 | 旗舰用例（带客观锚点） |
|---|---|---|---|
| **并行调研** | 团队·延迟+覆盖 | 多个**相互独立**子主题 + 单体在轮次预算内难全覆盖的硬覆盖条 | `par_reg_4region`：欧/美/中/日 AI 监管 ×〔法规名+要求+生效时间〕= **12 个可枚举事实** |
| **辩论/审查** | 团队·质量 | **植入的隐蔽缺陷** 或两个都站得住的对立立场 | `rev_code_planted`：审查**植入了隐蔽 bug** 的代码 → ground truth=抓没抓到那个 bug |
| **跨领域** | 团队·质量/完整性 | ≥2 种单个 system prompt 难同时擅长的技能/语气 | `xd_data_narrative`：精确计算 + 高管叙事（计算对错=确定性锚点） |
| **简单/紧耦合** | **单体**·成本+延迟（质量打平） | 单跳问答 / 紧耦合推理链；含**伪团队陷阱** | `neg_*` 三例 + `trap_rust_vs_go`（看着可拆实则单体两搜就够） |

设计要点：
- **客观锚点优先**：每原型至少留一个有客观正确答案的（12 facts / 植入 bug / 可算的数），别全压主观裁判。
- **负对照组 = verbosity 探针**：若团队在 `neg_*`/`trap_*` 上也「赢」，多半是**裁判偏好长答案**——先校准裁判，别信团队真更好。
- **裁判维度按原型定制**：并行→覆盖完整度；辩论→是否抓到缺陷/双面平衡；跨领域→各域分别打分；简单→质量打平 + 成本暴露。

完整 13 例（id / prompt / 杠杆 / 锚点）见**附录 A**。

### 二.5 判定指标

| 指标 | 定义 | 治什么 |
|---|---|---|
| **成对胜率** | k 次成对盲评中 B 优于对手的比例；报与 50% 的显著性 | 绝对打分不可靠，成对更稳 |
| **pass^k** | k 次尝试**全过**才记通过（借 Tau²-Bench） | 思考模型非确定，平均分掩盖不稳定 |
| **成本比 / 延迟比** | `cost_B/cost_C`、`latency_B/latency_C` | 暴露「赢质量但贵/慢」的真实代价 |
| **协作溢价** | B vs C 预算对齐时的胜率 − 50% | 唯一能反驳「算力混淆」的硬指标 |
| **覆盖完整度** | 客观锚点命中数（如 12 facts 填全几项） | 并行原型的确定性信号 |

报告**按原型分段**，每段给上述一行；**禁止**只报一个全局「团队胜率」（会把信号洗没）。

### 二.6 成对裁判（PairwiseJudge）

与第一部分的绝对分 `LLMJudge` 并列，新增成对裁判：
- **成对偏好**：把同任务两臂产出 `(X, Y)` 连同 rubric 喂裁判，要求**先理由后结论**、强制 JSON 输出 `{winner, rationale, margin}`。
- **盲评 + 位置对调**：隐去「谁是团队」；A/B 顺序换一遍各跑一次，取一致结论，抵消位置偏见；不一致计入「裁判噪声」。
- **中立/强裁判**：用 Pro，最好用不在任何一臂的模型；裁判调用打 `scenario="eval.judge.pairwise"` 单独成本归因。
- **verbosity 防护**：负对照组 + 陷阱用例作探针；rubric 显式要求「**简洁正确 > 冗长堆砌**」，并报「裁判在 `neg_*` 上是否错误偏好长答案」作为裁判校准信号。
- **faithfulness 局限**沿用第一部分结论（裁判只看 citation snippet，方向性信号）。

### 二.7 数据模型与接现有代码

| 需要 | 现成件 | 新增 |
|---|---|---|
| 跑单体 / 团队一回合 | `EvalHarness`（两路径✅） | — |
| 成本/延迟/用量 | `TurnOutcome.cost_usd/latency_ms/usage`（✅） | — |
| 等算力 C 臂 | `RunPolicy.candidates`（best-of-N，[`§7.4`](/docs/03-AI核心/Agent协作模式.md)） | best-of-N 选优封装 ⏳ P1 |

| 分段报告 | `report.py`（✅） | 按 `archetype` 分段 + 三轴 + pass^k ✅ |

**数据模型**（`evals/types.py`，✅ 已落地）：
- 新增独立 `ComparisonCase`（**非**扩展 `EvalCase`）：`archetype`（原型标签，与功能评估的 `category` 正交）、`arms`（默认 `["single","team"]`，C 臂 `matched_single` 为 P1）、`baseline_arm`（默认 `single`）、按臂可选 `checks`（`{arm: [...]}`）、`rubric`、`samples`。一条 case = 一道题 × 多臂，**配对单位即 case 自身**，无需 `group` 字段。

- 新增套件目录 `cases/comparison/`（13 例）；`seed_lint` 增「`arms`/`baseline_arm`/`archetype` 合法」校验。

### 二.8 评估 → 路由闭环（战略落点）

本评估的终值不在「发奖状」，而在**校准路由**：
1. 评估找出团队**真胜等算力单体**的任务原型与特征（并行扇出 / 对抗审查 / 真跨领域）。
2. 把这条边界喂给 [`Agent协作模式.md §7.1`](/docs/03-AI核心/Agent协作模式.md) 规划中的**路由引擎**（embedding 语义匹配），作为「哪些任务该自动升级成团队」的 ground truth。
3. 负对照组同时校准**反向**：简单/紧耦合任务**不该**升级，省钱省延迟。

> **Expert-MAS 而非 Automatic-MAS**：研究表明「赢的是专家设计、角色专精的团队」。故评估不只测「团队 vs 单体」，更要驱动 CEO 委派朝「**专家级角色设计 + 任务结构强制分工**」而非「泛化自动拆解」演进——这是我们站在「制胜」一侧的前提。

### 三.2 不做 / 边界

- **不做评估 UI**——纯离线工具，报告走 JSON + 控制台。
- **不拿真实模型评测卡每-PR**——只 nightly/手动；每-PR 仅零 LLM 自测（seed_lint + smoke）。
- **不重造成本/定价**——复用 `runtime/costing.py` 与 `cost_runs`。
- **不改引擎/管线**——只消费现有返回值与事件；若发现必须加 hook 才能断言某事实，先停下提报（可能是引擎可观测性缺口，单独决策）。
- **首批不评 `code_execute`**——它在 CI 真起子进程（`SubprocessSandbox`），有副作用与 flaky 风险；待受控沙箱就绪再纳入（见 〇.6 CI 安全）。
- **（对比）不刷公榜分**——不拿 SWE-bench/GAIA 等公开榜分当卖点（既被质疑虚高——Berkeley RDI 2026 审计：8 大基准均可刷至近满分，又测不到协作差异化）。
- **（对比）不宣称「团队永远赢」**——那是假命题，且会逼出「到处强制委派烧钱」。只宣称受原型表约束的「在 X/Y/Z 形状、可接受成本溢价下赢」；**负结果照样有价值**（若「等算力单体追平团队」，如实记录并据此收窄卖点到「并行延迟 + 真跨领域」）。

### 三.3 决策点

**已拍板（对比评估，5 项经产品负责人确认）**：

| 决策 | 已拍板 |
|---|---|
| 预算主单位 | **思考-token 对齐**——隔离「算力混淆」、对齐 arXiv 2604.02460；钱 + 墙钟延迟并列报但**不用于对齐**（回答「值不值」而非「公不公平」，因美元混入了贵/便宜模型这种与协作无关的因素） |
| C 臂构造 | **先 best-of-N**——代码现成（复用 `RunPolicy.candidates`）、与 CoT-SC 研究同款、做 N 遍好算预算；自我批判 P2 加为第二陪练。多候选选优复用 `PairwiseJudge` |
| 裁判模型 | **固定 Pro**——裁判须比选手眼光高才不出噪音；仅 nightly 跑、裁判成本可控。家族偏心顾虑暂存，真发现偏心再升级第三方裁判 |
| 首批规模 | **13 例起步**——每例三臂 × 多采样 × 裁判已是重负载；先用 13 例看清哪类原型真能分胜负，再往有信号处扩 |
| 套件归属 | **独立 `cases/comparison/`**——配对/多臂/archetype 形态与 core 单-path 不同，硬塞会搅乱现有可正常跑的功能评估 |

### 三.4 测试计划（harness 自测，随各层落）

- **seed_lint**：非法 category / 未注册 check 名 / 缺 fixture / `RosterMatches` 的 `args.expected` 拼写 / 对比 `arms`·`baseline_arm`·`archetype` 非法 → 加载期报错。
- **harness**（假 provider）：single 路径还原 `tool_calls`；team 路径从脚本化 `run_plan`/`run_completed` 事件还原 `roster`、`delegated`、`cost_usd`。
- **checks**：每个 Check 的过/不过分支（用构造的 `TurnOutcome` 单测，零 LLM）。
- **judge**（假 provider 返回固定 JSON）：rubric 渲染 + 分数解析 + 阈值判定 + 坏 JSON 容错；成对裁判的位置对调一致性。
- **runner / comparison**：聚合（按类通过率/均分；按原型分段 + pass^k + 三轴比）+ baseline 对比标回归 + `--update-baseline`。
- 以上均零真实 LLM，构成 `test_evals_smoke`/`test_evals_comparison` 与单测，可进 PR 硬门禁。
