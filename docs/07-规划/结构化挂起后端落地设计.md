## 〇、决策摘要

| 维度 | 决定 |
|---|---|
| 范围拆分 | **2a 轻增量**（进程内波间挂起，ask_user 形状）+ **2b 延后硬化**（持久 `paused`，仅为重启/多 worker，与 ask_user 共享） |
| 2a 决策面 | **仅 `continue` / `stop`**；`adjust`（steer 注入下游）延后到 2b 后 |
| 治理强制层 | **延后**——2a 只做 CEO 自声明的 `checkpoint_after`，不做「强制注入、声明即必停」 |
| timeout 默认 | **软检查点超时 = `continue`**（对齐 `ask_user` 超时不替用户选分支的克制原则，但软挂起取「放行」更顺） |
| 落地次序 | 数据层（inert）→ 调度器 hook → host 协调器 → resolve/事件 → 接线；前端（卡片 + 图检查点节点）后端出数据后另起 |

**一句话**：`checkpoint_after` = `WaveScheduler` 在**波间** `await` 一个 `plan_review` Future，复刻 `ask_user` 的「进程内挂起-恢复」，交付完整用户功能（结构化检查点 + 波间介入），**不碰 `paused`/落盘/跨进程**。

## 一、关键洞察：进程内 `await` 已足够（翻转 defer 的成本前提）

[`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md) 把 `checkpoint_after` 的两点独有价值（① 波间结构挂起 ② 治理保证闸门）判为「**都压在尚未落地的运行时地基上——`WaveScheduler` 波间挂起 + `paused` 第三终态 + 跨进程等待——代价大而价值小众，故 defer**」。

**这个成本前提不成立**：`ask_user`（[`tools/builtin/ask_user.py`](/apps/server/agentcore/tools/builtin/ask_user.py)）现在就在做「挂起-恢复」，且**完全没用** `paused`/落盘/跨进程——

- CEO 回合协程在工具调用里 `await asyncio.wait_for(fut, timeout)`（`ask_user.py`），整个回合协程**驻留内存**；
- resolve 端点（[`api/routes/conversations.py` `resolve_interaction`](/apps/server/agentcore/api/routes/conversations.py)）`registry.resolve(id, result)` set 该 Future，协程当场续跑；
- 全程只用进程内 `InteractionRegistry`（[`runtime/interaction.py`](/apps/server/agentcore/runtime/interaction.py)），无状态落盘、无第三终态。

`checkpoint_after` 可以**同形**：把这套「create → emit `*_required` → `await wait_for` → `finally discard` → emit `*_resolved`」搬到 `WaveScheduler` 的**波间**即可。于是：

- **① 波间结构挂起**（`checkpoint_after` 真正独有的价值）——用进程内 `await` 即可交付，**无需** `paused`/落盘；
- **持久 `paused` + 跨进程**只为「扛进程重启 / 多 worker」，那是**另一档硬化**（2b），且 **`ask_user` 也同样需要**——并非 `checkpoint_after` 专属，不该计入它的成本。

**结论**：原 §四「代价大」是把 2b 的成本算到了 2a 头上。剥离后，2a 是一个 **ask_user 形状的小增量**（下 §二），唯一全新的是「调度器波间挂起接缝」——而它本身只是给纯调度器加一个可选 async 回调（与既有 `on_progress` 同形）。

## 二、Phase 2a 落地设计（后端先行，逐层）

> 现有可复用面（已落地）：`InteractionRegistry`（进程内挂起桥，[`interaction.py`](/apps/server/agentcore/runtime/interaction.py)）、`CheckpointResponse`/`CheckpointDecision`（[`runtime/checkpoints.py`](/apps/server/agentcore/runtime/checkpoints.py)）、resolve 端点的判别联合、`WaveScheduler.run` 已有的 `seed_completed`/`should_stop`/`on_progress` 注入点形态。（`InteractionKind.PLAN_REVIEW` 此前仅 docstring 预留语义、并无枚举成员，2a 补为真值。）

### 2a.1 数据层（inert，先落，不改任何行为）

- **`RunSpec.checkpoint_after: bool = False`**（[`runtime/runs/types.py`](/apps/server/agentcore/runtime/runs/types.py)）——计划期声明位，调度器读它决定波后是否挂起。默认 False ⇒ 现有 plan 行为字节不变。
- **delegate task schema** 加 `checkpoint_after`（[`tools/builtin/delegate.py`](/apps/server/agentcore/tools/builtin/delegate.py) `_DELEGATE_PARAMETERS`）——布尔可选项，描述「该 step 完成后、运行其下游前，暂停请用户审视当前进展」。
- **builder 解析**（[`runtime/runs/builder.py`](/apps/server/agentcore/runtime/runs/builder.py) `_inline_spec`）——宽松读取 `bool(item.get("checkpoint_after"))`，与 `stance`/`round` 同样的「非法即丢」风格。
- **CEO prompt hint**（[`runtime/prompt.py`](/apps/server/agentcore/runtime/prompt.py) `CHAT_TEAM_CAPABILITY_HINT`）——教 CEO「在高危/不可逆/范围可能跑偏的 step 后，给该 task 标 `checkpoint_after`，让用户在继续下游前过目；克制使用，与 `ask_user` 一样只用于真正值得停的节点」。

> 这一层落完即可单测（builder 解析 + prompt hint 内容），且**完全 inert**——调度器尚未读 `checkpoint_after`，plan 照常跑完。

### 2a.2 挂起原语（复用，不新建注册表）

- `InteractionKind.PLAN_REVIEW` **新增为真值枚举成员**（[`interaction.py`](/apps/server/agentcore/runtime/interaction.py)；此前仅 docstring 预留语义、并无成员，既有成员为 approval/ask_user/client_tool）。
- 结果类型**复用 `CheckpointResponse`**（continue/adjust/stop/timeout）——plan_review 与 ask_user 的语义同构（用户对一个挂起点回「继续/停止」），无需新类型。2a 只消费 `continue` vs `stop`。

### 2a.3 调度器 hook（纯，与 `on_progress` 同形）

[`runtime/runs/wave.py`](/apps/server/agentcore/runtime/runs/wave.py) `WaveScheduler.run` 增一个可选注入：

```python
on_checkpoint: Callable[[Sequence[RunSpec], Mapping[str, RunState]], Awaitable[bool]] | None = None
```

- **触发条件**：一波跑完、`wave_results` 折进 `completed` 后，若该波**有 `checkpoint_after=True 且 COMPLETED` 的节点**，**且 `pending` 仍非空**（有下游可门）⇒ `proceed = await on_checkpoint(那些节点, completed)`。
- **`proceed=False`（用户停）**：置 `aborted`（复用既有 abort 路径）→ 跳出循环、返回 partial。未跑的 pending 节点按既有逻辑不入结果（delegate 的 `_format_for_ceo` 已把缺失渲染为「无输出」）；**可选 polish**：把剩余 pending 标 `SKIPPED` 让图/概览更干净（2a 先不做，记为待定）。
- **失败节点不触发**：仅 `COMPLETED` 的 `checkpoint_after` 节点触发——失败节点的处置已由其 `on_failure`（skip/abort/degrade/retry）管，不叠加挂起。
- **末波不触发**：`pending` 空 ⇒ 无下游可门，跳过（避免回合末尾无意义的挂起）。
- **调度器保持纯**：只持有回调，**不 import SSE/registry**——与现有「`on_progress` 只回调、不直连传输」一致。`should_stop`（同步软暂停）语义不变、与本 hook 正交。

> **为何挂在 wave 层而非 CEO 层**（独有价值所在）：`delegate` 对 CEO 原子——CEO 拿不到波间控制权，单个 `delegate` 跨多波时 `WaveScheduler.run` 跑完整子 DAG 才返回，`ask_user` 插不进去。把挂起放进调度器波间，正好命中 `checkpoint_after` **唯一 `ask_user` 表达不了**的场景。

### 2a.4 host 协调器（在 `delegate` 内，复刻 ask_user 样板）

[`delegate.py`](/apps/server/agentcore/tools/builtin/delegate.py) `execute` 里构造 `on_checkpoint` 闭包，传给 `WaveScheduler(...).run(..., on_checkpoint=...)`（仅当 checkpoint 开关开，见 2a.7）：

```python
async def _on_checkpoint(nodes, completed) -> bool:
    cid = new_id()
    fut = registry.create(cid, conversation_id, kind=InteractionKind.PLAN_REVIEW,
                          payload=_review_payload(nodes, completed, plan))
    sink.emit(plan_review_required(checkpoint_id=cid, conversation_id=..., steps=...))
    try:
        resp = await asyncio.wait_for(fut, timeout=checkpoint_timeout_seconds)
    except TimeoutError:
        resp = CheckpointResponse(decision=CheckpointDecision.CONTINUE)  # 软挂起超时=放行
    finally:
        registry.discard(cid)
    sink.emit(plan_review_resolved(checkpoint_id=cid, decision=resp.decision.value, note=resp.note))
    return resp.decision is not CheckpointDecision.STOP   # 2a: 仅 stop 截停，其余（含 adjust）放行
```

- **payload / 卡片内容**：刚完成的 checkpoint 节点（run_id/role + 产出摘要）+ 下游待跑节点（role）的预览，让用户「看着已发生的、决定要不要放行未发生的」。
- **2a 不处理 `adjust` 的 steer 注入**（影响下游节点远比 ask_user 复杂）——`adjust` 暂等同 `continue`（note 记录但不改下游）；真正的 steer 注入留到 2b 之后。

### 2a.5 resolve 端点 + schema（判别联合加一员）

[`api/schemas.py`](/apps/server/agentcore/api/schemas.py)：

```python
class ResolvePlanReviewInteraction(BaseModel):
    kind: Literal["plan_review"] = "plan_review"
    decision: CheckpointDecision            # 2a 前端只给 continue/stop
    note: str = Field("", max_length=4000)

ResolveInteractionRequest = (
    ResolveApprovalInteraction | ResolveCheckpointInteraction

```

### 2a.6 事件 + journal

[`runtime/events.py`](/apps/server/agentcore/runtime/events.py)：加 `PLAN_REVIEW_REQUIRED` / `PLAN_REVIEW_RESOLVED` 两个 `EventType` + 构造器，镜像 `checkpoint_required`/`checkpoint_resolved`。**纳入 `_JOURNAL_EVENT_TYPES`**（结构化挂起是团队执行历史的一部分，reload 应能回放该挂起点；与 ask_user 检查点入 journal 同理），并据需要纳入 `_JOURNAL_SURFACE_TYPES`。

### 2a.7 接线（pipeline 注入 + 嵌套转发 + 门控）

[`runtime/pipeline.py`](/apps/server/agentcore/runtime/pipeline.py)：构造 `DelegateTool` 时注入 `registry=default_interaction_registry()`、`conversation_id`、`checkpoint_timeout_seconds=settings.checkpoint_timeout_seconds`，并传 `checkpoint_enabled = settings.checkpoint_gate_enabled and approvals_enabled`（与 `AskUserTool` **完全同一门控**——autonomous handoff 无客户端应答，挂起只会超时，故不启用）。

- `DelegateTool.__init__` 增对应字段；`execute` 仅在 `checkpoint_enabled` 时把 `on_checkpoint` 传进 `WaveScheduler.run`。
- `DelegateTool._make_child`（嵌套子团队）**转发** registry/conversation_id/timeout/enabled，使子 DAG 的 `checkpoint_after` 同样生效。

## 三、语义决策（一处定清，省后续打补丁）

| 决策点 | 2a 取值 | 理由 |
|---|---|---|
| 决策面 | 仅 `continue` / `stop`（`adjust`≈`continue`、仅记 note） | steer 注入下游复杂，先交付「放行/截停」的核心价值 |
| 触发粒度 | 波后、有 `COMPLETED` 的 `checkpoint_after` 节点且 `pending` 非空 | 命中波间独有价值；失败节点交回 `on_failure`；末波不空挂 |
| `stop` 后未跑节点 | 不入结果（concept 同 abort）；标 `SKIPPED` 列为待定 polish | 复用既有 abort 路径，最小改动 |
| timeout | 软挂起 = `continue` | 软挂起取「放行」更顺；治理强制闸门若将来引入应改取「halt」（2b 治理层再分流） |
| cancel 清理 | `finally: registry.discard` + `_run_wave` 已 re-raise `CancelledError` | 与 ask_user 同；回合取消不漏挂起 |
| 调度器纯度 | hook 只回调、不连 SSE/registry | 守「调度器只管 when，host 管 how」 |

## 四、Phase 2b 延后硬化（持久 `paused` + 跨进程，与 `ask_user` 共享）

仅当需要**扛进程重启 / 多 worker** 才做，且**与 `ask_user` 共用**（非 checkpoint 专属，故不计入 2a 成本）：

- `RunPhase.PAUSED` 第三终态（[`types.py`](/apps/server/agentcore/runtime/runs/types.py)）+ Turn Journal 落盘 + `POST /resume` 重建 `plan`/`seed_completed`（`WaveScheduler.run` 的 `seed_completed` 已为此预留）续跑。
- 跨进程：`InteractionRegistry` 前置 Redis（[`interaction.py`](/apps/server/agentcore/runtime/interaction.py) 文档已注明「single-worker posture；front with Redis to scale」）。
- `adjust` 的 steer 注入下游、治理强制注入层（声明即必停、可审计、timeout=halt）亦在此档之后。

2a **不依赖** 2b——进程内 `await` 在单 worker 下完整可用。

### 7.1 会话流卡片 `PlanReviewCard`（✅ 已落地）

机制完全镜像 `ask_user`：卡片挂在**触发它的 assistant message** 上，live 可交互、reload 从 journal 回放。差异三点：
- **内容**：展示「刚完成的检查点步骤（role + 产出摘要）」+「待运行的下游步骤（role）」，而非 question/options/context。
