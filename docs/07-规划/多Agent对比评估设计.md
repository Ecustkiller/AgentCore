# 多 Agent 对比评估设计（团队 vs 单体的可证明优势）🗂️

> **定位**：[`评估体系后端落地设计.md`](/docs/07-规划/评估体系后端落地设计.md) 解决「**功能对不对 / 防回归**」（Layer 1 确定性 + Layer 2 LLM 裁判，判定单条回合的正确性）。本文解决一个**正交且更难**的问题：[`产品定位与品牌.md`](/docs/01-产品/产品定位与品牌.md) 把「**真正的 Agent 团队协作**」立为核心差异、喊出「单个模型的智能有天花板，协作智能没有」——**这条命题从未被本仓库的评估验证过**。现有 `team` 类用例断言的是 `Delegated`（委派触发没）/`RosterMatches`（角色对没），是「**管道通没通**」，不是「**产出更好没**」。本文是把命题变成**可复现证据**的对比评估蓝图。
>
> **为何必须做（2026 研究背景）**：多 Agent「更强」正被学术界正面狙击，且证据直指我们的底座家族：
> - 《Single-Agent LLMs Outperform Multi-Agent Systems under Equal Thinking Token Budgets》(arXiv 2604.02460)：**等思考-token 预算下，单 Agent 持平或打赢多 Agent**；测了串行/辩论/集成/并行角色/子任务并行 5 种架构，含 **DeepSeek-R1**。结论：「许多所报告的 MAS 收益，用算力与上下文效应解释，比用架构优越性解释更合理。」
> - 《The Illusion of Multi-Agent Advantage》：单 Agent 的 CoT 自一致用 **<10% 成本**打赢一众**自动** MAS 框架——**但**专家设计、角色专精的 **Expert-MAS 赢得很大**（某骨干模型 49.1%→96.7%，成本与单体相当）。
> - MASEval (arXiv 2603.08835)：现有基准「把模型能力与框架实现混为一谈」，**框架选择对结果的影响和换模型一样大**。
>
> **一句话风险**：若我们只做「自动委派、啥都派个团队」，大概率落进「幻觉优势」一侧——花更多钱、不更好。本评估的使命就是**找到并守住团队真能赢「等算力单体」的那条边界**，并把它喂回路由，让「协作更强」从口号变成运行时事实。
>
> 状态：🗂️ 蓝图。复用 [`评估体系后端落地设计.md`](/docs/07-规划/评估体系后端落地设计.md) 已落地的 harness/checks/runner 地基（✅），新增**三臂对照 + 预算对齐 + 成对裁判 + pass^k + 原型分段**（均 🗂️ 未落地）。落地后并入 [`后端架构.md §五`](/docs/02-架构/后端架构.md) 评估体系，本稿退役。

## 〇、决策摘要

| 维度 | 决定 |
|---|---|
| 评测对象 | **架构而非单条回合**——比较「单 Agent」与「团队」在同一任务上的产出优劣，不是判某次回答对错 |
| 对照模型 | **三臂**：A=单体（`react_loop`）/ B=团队（`run_chat_pipeline`）/ **C=等算力单体**（best-of-N 或自我批判，烧到 ≈B 的预算）。**A/B 看「团队比朴素单体强不强」，B/C 看「强是不是只因烧了更多算力」** |
| 公平性铁律 | **协作溢价 = B 在「与 C 预算对齐」时仍胜 C**。B 赢 A 但 token 远大于 A → 记为「算力效应」，不计协作功劳 |
| 预算单位 | 主用**思考-token**（对齐 arXiv 2604.02460），辅看总 token / 成本 / 墙钟延迟；残余不齐如实暴露 token 比 |
| 判定指标 | **成对偏好**（盲评 + 位置对调）为主，**pass^k** 治可靠性，多维（质量胜率 + 成本比 + 延迟比），**按原型分段**——不报全局单一胜率 |
| 任务集 | 黄金集每例须有「**区分杠杆**」（单体结构性做不好、团队天然能 handle，或反之）；含**负对照组 + 伪团队陷阱**防裁判 verbosity 偏好 |
| 战略闭环 | 评估产出的「团队制胜边界」→ 喂 [`Agent协作模式.md §7.1`](/docs/03-AI核心/Agent协作模式.md) 规划中的**路由引擎**，决定哪些任务该自动升级成团队 |
| 侵入性 | **零生产风险**——只消费 `react_loop`/`run_chat_pipeline` 返回值 + `EventSink` 事件，不改引擎/管线一行；C 臂复用 [`Agent协作模式.md §7.4`](/docs/03-AI核心/Agent协作模式.md) 的 `RunPolicy.candidates`（best-of-N） |
| 何时跑 | **真模型、贵、flaky → nightly/手动软门禁**；per-PR 仅跑假-provider 的配对 runner / PairwiseJudge 解析自测（守评估系统自身不回归） |

**一句话**：把一批「有区分杠杆」的黄金任务，**同时**喂给单体 / 团队 / 等算力单体三臂，用成对盲评 + pass^k 在「质量·成本·延迟」三轴上分原型比较，产出「团队在哪类任务、何种预算下真赢」的可复现报告，并把这条边界喂回路由。

## 二、三臂对照模型

```
              同一 user_message（同档模型、同 fixture）
                          │
        ┌─────────────────┼─────────────────┐
        ▼                 ▼                 ▼
   Arm A 单体        Arm B 团队        Arm C 等算力单体
   react_loop      run_chat_pipeline   best-of-N / 自我批判
   （朴素基线）     （CEO+worker）      （烧到 ≈B 的 token 预算）
        │                 │                 │
        └──────► 成对盲评（B vs A、B vs C）+ pass^k + 三轴度量 ◄──────┘
```

判定逻辑（**这是全文的命门**）：

| 比较 | 看什么 | 结论含义 |
|---|---|---|
| **B vs A** | 团队是否胜朴素单体 | 是 → 团队「有用」，但**未排除算力混淆** |
| **B vs C**（预算对齐） | 团队是否胜**等算力**单体 | 是 → **真协作溢价**（值得捍卫、可写进卖点）；否 → 收益只是算力，应收窄宣称 |
| **C vs A** | 等算力单体相对朴素单体的增益 | 量化「光给单体加算力能买到多少」，作为 B 的及格线 |

> **为什么 C 臂不可省**：arXiv 2604.02460 / 《Illusion》的核心结论就是「多数所报 MAS 收益是算力效应」。没有 C 臂，B 赢 A 证明不了任何架构优越性，只会被一句「你不过是烧了 5 倍 token」击穿。

## 三、预算对齐协议（公平性的工程实现）

目标：让 C 臂消耗的算力 ≈ B 臂，从而隔离「协作」与「算力」。因团队 token 随任务波动，采**测量后对齐**而非拍脑袋：

1. **先跑 B 臂** k 次，取该任务**思考-token 中位数** `T_B`（主单位；辅记总 token / cost / 墙钟）。
2. **构造 C 臂**到预算 `T_B`：
   - **best-of-N 单体**（默认，对齐 CoT-SC 研究）：调 `RunPolicy.candidates` 的 N，使 N×单次思考-token ≈ `T_B`；多候选用 PairwiseJudge 或自评选优。
   - **自我批判单体**（备选 C′）：单次运行内「草稿→自审→修订」多轮，调 `max_rounds` 逼近 `T_B`。
3. **如实报告实际 token 比** `r = tokens_B / tokens_C`。`r∈[0.8,1.25]` 视为对齐；超出则给「预算未对齐」警示，结论降级为「方向性」。
4. **延迟单独看**：团队**并行扇出**可在 token 相当时仍赢墙钟延迟——这是独立且正当的赢点，**不要**被 token 对齐抹掉，单列 `latency_ratio` 报。

> **已拍板（§十一）**：预算主单位 = **思考-token 对齐**（钱/延迟并列报但不对齐）；C 臂 = **先 best-of-N**（自我批判 P2 加 C′）。

## 四、任务原型与黄金集

**铁律**：没有「区分杠杆」的任务是废用例——若单 Agent 也能做得一样好，跑多少次都分不出优劣。每例须标注：单体结构性短板 / 团队天然优势（或反之）。首批 13 例，4 原型：

| 原型 | 假设赢家·轴 | 区分杠杆 | 旗舰用例（带客观锚点） |
|---|---|---|---|
| **并行调研** | 团队·延迟+覆盖 | 多个**相互独立**子主题 + 单体在轮次预算内难全覆盖的硬覆盖条 | `par_reg_4region`：欧/美/中/日 AI 监管 ×〔法规名+要求+生效时间〕= **12 个可枚举事实** |
| **辩论/审查** | 团队·质量 | **植入的隐蔽缺陷** 或两个都站得住的对立立场 | `rev_code_planted`：审查**植入了隐蔽 bug** 的代码 → ground truth=抓没抓到那个 bug |
| **跨领域** | 团队·质量/完整性 | ≥2 种单个 system prompt 难同时擅长的技能/语气 | `xd_data_narrative`：精确计算 + 高管叙事（计算对错=确定性锚点） |
| **简单/紧耦合** | **单体**·成本+延迟（质量打平） | 单跳问答 / 紧耦合推理链；含**伪团队陷阱** | `neg_*` 三例 + `trap_rust_vs_go`（看着可拆实则单体两搜就够） |

完整 13 例（id / prompt / 杠杆 / 锚点）见**附录 A**。设计要点：

- **客观锚点优先**：每原型至少留一个有客观正确答案的（12 facts / 植入 bug / 可算的数），别全压主观裁判。
- **负对照组 = verbosity 探针**：若团队在 `neg_*`/`trap_*` 上也「赢」，多半是**裁判偏好长答案**——先校准裁判，别信团队真更好。
- **裁判维度按原型定制**：并行→覆盖完整度；辩论→是否抓到缺陷/双面平衡；跨领域→各域分别打分；简单→质量打平 + 成本暴露。

## 五、判定指标

| 指标 | 定义 | 治什么 |
|---|---|---|
| **成对胜率** | k 次成对盲评中 B 优于对手的比例；报与 50% 的显著性 | 绝对打分不可靠，成对更稳 |
| **pass^k** | k 次尝试**全过**才记通过（借 Tau²-Bench） | 思考模型非确定，平均分掩盖不稳定 |
| **成本比 / 延迟比** | `cost_B/cost_C`、`latency_B/latency_C` | 暴露「赢质量但贵/慢」的真实代价 |
| **协作溢价** | B vs C 预算对齐时的胜率 − 50% | 唯一能反驳「算力混淆」的硬指标 |
| **覆盖完整度** | 客观锚点命中数（如 12 facts 填全几项） | 并行原型的确定性信号 |

报告**按原型分段**，每段给上述一行；**禁止**只报一个全局「团队胜率」（会把信号洗没）。

## 六、裁判设计（PairwiseJudge）

与 [`评估体系后端落地设计.md §六`](/docs/07-规划/评估体系后端落地设计.md) 的绝对分 `LLMJudge` 并列，新增成对裁判：

- **成对偏好**：把同任务两臂产出 `(X, Y)` 连同 rubric 喂裁判，要求**先理由后结论**、强制 JSON 输出 `{winner, rationale, margin}`。
- **盲评 + 位置对调**：隐去「谁是团队」；A/B 顺序换一遍各跑一次，取一致结论，抵消位置偏见；不一致计入「裁判噪声」。
- **中立/强裁判**：用 Pro，最好用不在任何一臂的模型；裁判调用打 `scenario="eval.judge.pairwise"` 单独成本归因。
- **verbosity 防护**：负对照组 + 陷阱用例作探针；rubric 显式要求「**简洁正确 > 冗长堆砌**」，并报「裁判在 `neg_*` 上是否错误偏好长答案」作为裁判校准信号。
- **faithfulness 局限**沿用既有结论（裁判只看 citation snippet，方向性信号）。

## 九、评估 → 路由闭环（战略落点）

本评估的终值不在「发奖状」，而在**校准路由**：

1. 评估找出团队**真胜等算力单体**的任务原型与特征（并行扇出 / 对抗审查 / 真跨领域）。
2. 把这条边界喂给 [`Agent协作模式.md §7.1`](/docs/03-AI核心/Agent协作模式.md) 规划中的**路由引擎**（embedding 语义匹配），作为「哪些任务该自动升级成团队」的 ground truth。
3. 负对照组同时校准**反向**：简单/紧耦合任务**不该**升级，省钱省延迟。

> **Expert-MAS 而非 Automatic-MAS**：研究表明「赢的是专家设计、角色专精的团队」。故评估不只测「团队 vs 单体」，更要驱动 CEO 委派朝「**专家级角色设计 + 任务结构强制分工**」而非「泛化自动拆解」演进——这是我们站在「制胜」一侧的前提。

## 十、不做 / 边界

- **不刷公榜分**：不拿 SWE-bench/GAIA 等公开榜分当卖点——既被质疑虚高（Berkeley RDI 2026 审计：8 大基准均可刷至近满分），又测不到协作差异化。
- **不宣称「团队永远赢」**：那是假命题，且会逼出「到处强制委派烧钱」。只宣称受原型表约束的「在 X/Y/Z 形状、可接受成本溢价下赢」。
- **不做评估 UI**：纯离线工具，报告走 JSON + 控制台。
- **不拿真模型对比卡每-PR**：只 nightly/手动软门禁。
- **不改引擎/管线**：零侵入红线。
- **负结果照样有价值**：若「等算力单体追平团队」，如实记录并据此收窄卖点到「并行延迟 + 真跨领域」。

## 附录 A：首批 13 个对比用例

> 每例先写成**配对**：同 `user_message`、共享 `rubric`/`archetype`/`group`，一条 `path:"single"` 一条 `path:"team"`；C 臂由 runner 在 single 基础上按预算对齐生成，不单独写用例。

### A. 并行调研（团队赢延迟+覆盖）

| id | prompt（精简） | 区分杠杆 | 客观锚点 |
|---|---|---|---|
| `par_reg_4region` | 分别调研欧盟/美国/中国/日本对生成式 AI 的最新监管，每地给〔法规名+核心要求+生效时间〕，汇成对比表 | 4 地×3 字段=12 独立事实，需各自检索 | 12 格填全数 |
| `par_notes_3x4` | 调研 Notion/Obsidian/Logseq，从〔价格/协作/本地优先/插件生态〕4 维给事实，出 3×4 表 | 3 产品×4 维独立查 | 12 格覆盖度 |
| `par_rag_survey` | RAG 三方向（重排序/查询改写/混合检索）各找 2 条代表做法，末尾说能否组合 | 3 独立子主题 + 末尾综合（考 CEO 收尾） | 每方向是否各 2 条 |

### B. 辩论/审查（团队赢质量）

| id | prompt（精简） | 区分杠杆 | 客观锚点 |
|---|---|---|---|
| `dbt_storage_pick` | 高并发计数器选存储：Redis INCR vs PG 行锁 vs 内存+定期落盘，给推荐 + 每方案翻车场景 | 真争议；con 侧逼出边界失败模式 | 翻车场景覆盖数 |
| `rev_code_planted` | 审查一段植入隐蔽 bug 的代码（竞态/off-by-one/未处理 None），列全部问题 | 植入缺陷=ground truth；读写分离评判者更易抓 | **是否抓到植入 bug**（需 fixture 代码） |
| `dbt_redteam_argument` | 压力测试一个融资论点（"竞品没做对比评估所以做了就有壁垒"） | 红队 vs 单次直答的反驳深度 | 裁判：反驳深度/数 |

### C. 跨领域（团队赢质量/完整性）

| id | prompt（精简） | 区分杠杆 | 客观锚点 |
|---|---|---|---|
| `xd_landing_page` | 为「AI 简历优化」做落地页：①营销文案 ②能跑的 HTML/CSS 首屏 ③3 条 SEO 词 | 文案/代码/SEO 三 mode 互斥 | 代码能否跑 + 各域分打 |
| `xd_data_narrative` | 给一小段销售数据：①算环比增长和最大跌幅月 ②给 CEO 的非技术解读 ③一条下一步 | 精确计算 + 高管叙事两 mode | **计算对错** + 叙事质量 |
| `xd_tech_legal` | 「用户上传文件给 AI 分析」：①最简技术实现 ②隐私合规 3 点（GDPR/个保法） | 工程 + 法务两域 | 两域是否都有深度 |

### D. 简单/紧耦合（单体赢成本+延迟；负对照）

| id | prompt（精简） | 作用 |
|---|---|---|
| `neg_qa_oneliner` | "Python 里 list 和 tuple 最主要区别？一句话。" | 团队纯浪费，质量应打平、成本/延迟应显著更高 |
| `neg_tight_math` | "x 加 7 再乘 3 等于 36，x 是多少？给步骤。" | 紧耦合推理链，拆开只增交接损耗 |
| `neg_rewrite` | "把这句口语改写成正式书面语：……" | 单步转换 |
| `trap_rust_vs_go` ⚠️ | "调研 Rust 和 Go 哪个更适合写 CLI。" | **伪团队陷阱**：看着可拆实则单体两搜就够；团队若在此赢→裁判 verbosity 偏好，需校准 |
