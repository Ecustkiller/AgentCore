# 重试机制重设计 🗂️

> **定位**：用户级「重试失败项」与「重新生成」分离、`RecoveryActions` 改造提案。落地前需人确认。
>
> **治理**：本目录仅 `07-规划`；🗂️ = 讨论中、未承诺落地。决策通过、开始落地后，对应内容迁入 [执行引擎架构设计](/docs/03-AI核心/执行引擎架构设计.md)（节点重试 / `seed_completed`）与 [前端 UX 设计](/docs/04-前端/前端UX设计.md)（救火行），本条退役。
>
> **背景**：当前用户点「重试」走 `runRegenerate` → `POST /regenerate` → 删消息后整回合从头跑。多 Agent 场景下（如 9 个 Agent 辩论只有 2 个失败），已成功的子任务全部浪费。

---

## 一、现状问题

### 1.1 重试粒度太粗

用户点"重试"→ `runRegenerate(lastUserMessageId)` → `POST /regenerate` → 后端 `delete_after` 删消息 → 全新 pipeline。

9 个 Agent 只有 2 个失败，点重试后 9 个全部重跑。浪费时间和费用。

### 1.2 regenerate 和 retry 是两个意图，但共用一条路径

| 用户意图 | 期望行为 | 实际行为 |
|---|---|---|
| "有几个挂了，再试试" | 只补跑失败的 | 全部重来 |
| "我不满意，换个答案" | 全部重来 | 全部重来 |

### 1.3 重试目标不准

`RecoveryActions` 始终找 `lastUserMessageId()`（对话中最后一条用户消息），而非当前聚焦回合对应的用户消息。在画布上看一个历史失败回合点重试，实际重跑的是最新那轮。

### 1.4 "忽略"无后端感知

点"忽略"只执行 `clearExecution(messageId)` 清前端状态，后端不知道用户已接受部分失败。

---

## 二、设计方案

核心思路：**retry 是 resume 的一种变体，不是 regenerate 的变体。**

后端 `WaveScheduler` 已有 `seed_completed` 机制（用于 checkpoint 续跑），可以告诉调度器"这些节点已完成，只跑剩下的"。retry 复用同一机制：把成功节点标记为已完成，只重新调度失败节点。

### 2.1 三层分离

```
用户意图              产品动作                    后端路径
───────────────────────────────────────────────────────────────
"我不满意，重来"   →  重新生成 (regenerate)     →  删消息 + 全新 pipeline（现有路径）
"有几个挂了，再试" →  重试失败项 (retry-failed) →  同一 turn + seed_completed + 重跑失败节点
"网络断了"         →  自动重连                   →  传输层，与业务无关（现有路径）
```

### 2.2 后端自动重试（第一层防线）

大部分子任务失败是临时性的（API 超时、限流、网络抖动），不应暴露给用户。

**做法**：辩论/协作场景的 DAG 节点默认设置 `on_failure: "retry", max_retries: 2, retry_delay_ms: 1000`，带指数退避。调度器内部静默重试，用户完全无感知。只有重试用尽仍然失败的，才通过 `run_failed` 事件上报。

**涉及文件**：
- `runtime/runs/wave.py` — `_run_node` 已支持，无需改动
- `runtime/runs/types.py` — `RunPolicy` 已支持，无需改动
- 各场景的 DAG 节点定义处 — 修改默认 policy

### 2.3 用户级"重试失败项"（第二层）

#### 后端

新增 API：`POST /v1/conversations/{conversation_id}/messages/{message_id}/retry-failed`

处理流程：
1. 从 DB/journal 加载该 turn 的执行记录
2. 收集所有 `status == "completed"` 的节点作为 `seed_completed`
3. 清除失败节点的状态
4. 用 `seed_completed` 启动 `WaveScheduler`，只调度未完成的节点
5. 通过 SSE 流返回新事件（与正常执行相同的事件协议）

**与 resume 的区别**：resume 从 checkpoint 恢复（挂起点之后全部重跑），retry-failed 从失败点恢复（只重跑 failed 的节点）。两者共用 `seed_completed` 底层机制。

**涉及文件**：
- `api/routes/conversations/turns.py` — 新增路由
- `conversation/turns.py` — 新增 `retry_failed_chat()` 业务函数
- `runtime/pipeline/resume/pipeline.py` — 可参考，但 retry 是独立函数
- `runtime/runs/wave.py` — 已支持 `seed_completed`，无需改动

#### 前端

**触发入口改造**：

`RecoveryActions` 拆分为两个动作：
- **"重试失败项"**（主按钮）→ 调用新 API `retry-failed`，只补跑失败节点
- **"全部重新生成"**（次要入口，如下拉菜单）→ 走现有 `regenerate` 路径

**修复重试目标**：不再使用全局 `lastUserMessageId()`，改为从当前 `ExecutionScope` 拿到对应的 `messageId`。

**"忽略"增强**：点击后调用后端接口标记"用户已接受部分失败"，而非仅清前端状态。

**涉及文件**：
- `components/chat/StatusStrip.tsx` — `RecoveryActions` 改造
- `components/graph/CanvasDecisionPanel.tsx` — 画布指挥台适配
- `services/turns.ts` — 新增 `runRetryFailed()` 函数
- `services/streamConversation.ts` — 新增 `retryFailedConversation()` HTTP 调用
- `stores/execution/project.ts` — 处理 retry 返回的增量事件

## 三、UI 变化

### 3.1 失败提示区域（截图中的黄色警告条）

现状：
```
⚠ 2 个子任务失败：福斯特法官、汉迪法官，可重试或忽略。
[ 重试 ]  [ 忽略 ]
```

改为：
```
⚠ 2 个子任务失败：福斯特法官、汉迪法官
[ 重试失败项 ]  [ 忽略 ]  [ ▾ 全部重新生成 ]
```

- **重试失败项**：主按钮，只补跑失败的 2 个
- **忽略**：接受部分失败，通知后端
- **全部重新生成**：次要入口（下拉或文字链接），9 个全部重来

### 3.2 画布上的节点状态

失败节点在 retry 期间显示"重试中"状态；成功节点保持"已完成"不变。前端只更新失败节点对应的 execution frame。

## 四、数据流

```
用户点"重试失败项"
  │
  ├─ 前端
  │   ├─ 不 truncate 消息（与 regenerate 不同）
  │   ├─ 不新建 assistant 气泡（与 regenerate 不同）
  │   ├─ 将失败节点状态改为 "retrying"
  │   └─ POST /retry-failed → SSE 流
  │
  └─ 后端
      ├─ 加载 turn 的执行记录
      ├─ 收集 completed 节点 → seed_completed
      ├─ 清除 failed 节点状态
      ├─ WaveScheduler(seed_completed=...) 只调度失败节点
      └─ SSE 事件流（run_started / run_completed / run_failed）
          │
          └─ 前端 fold 增量事件 → 更新 execution store → Graph 重新渲染
```

## 五、对比

| 维度 | 现状 | 改后 |
|---|---|---|
| 2/9 失败后点重试 | 9 个全部重跑（~4 分钟） | 只跑 2 个（~1 分钟） |
| 临时性错误 | 用户看到失败，手动重试 | 自动重试，用户无感 |
| "忽略" | 只清前端状态 | 通知后端，有记录 |
| 画布看历史失败回合点重试 | 实际重试最新一轮 | 重试当前聚焦的 turn |
| 概念模型 | regenerate 一条路 | regenerate（推翻重来）+ retry（补救失败）分离 |

## 六、实现顺序建议

1. **后端自动重试默认策略** — 改节点默认 policy，零 UI 工作，立即减少用户看到的失败
2. **后端 retry-failed API** — 新增路由 + 业务函数，复用 `seed_completed`
3. **前端 RecoveryActions 改造** — 拆分按钮 + 新增 `runRetryFailed` + 修复重试目标
4. **"忽略"增强** — 后端感知 + 前端调用

---

## 七、风险与边界

- **确定性失败**（如 prompt 超长）：自动重试无效，仍会暴露给用户。可考虑后续增加失败分类，确定性错误不自动重试。
- **依赖关系**：如果失败节点 A 的输出是节点 B 的输入，且 B 也失败了，retry 需要按依赖顺序重跑。`WaveScheduler` 的 DAG 调度天然处理这个——清除 A 和 B 的完成状态后，调度器会先跑 A 再跑 B。
- **幂等性**：retry 不修改已完成节点的结果，不删除消息，不改变对话历史。如果同一个 turn 被 retry 多次，每次都只重跑当时仍为 failed 的节点。
