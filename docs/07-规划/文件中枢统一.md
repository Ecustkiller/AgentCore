## 一、现状诊断：两套独立实现

| 维度 | 对话文件工作区（前者） | 文件页（后者） |
|---|---|---|
| 入口 | 右侧 `SidePanel`→「工作区」tab（`WorkspacePanel.tsx`/`FilesSection.tsx`） | 路由 `/files`（`FilesPage.tsx`，左树 + 右预览） |
| **数据通道** | 服务端 REST `services/workspace.ts` | 本地 OS FS · IPC `window.fsApi`（`main/fs-service.ts`） |
| **寻址** | `conversationId` + 相对路径 | `rootId` + 相对路径 |
| 根数量 | 1（= 该对话/文件夹的项目空间） | N（用户加的多个本地根） |
| 实时变更 | ❌ 手动刷新 | ✅ `watch` 推送（`fs:changed`） |
| 上传/下载 | ✅（字节跨网络） | ❌（文件本就在本地盘） |
| 在线编辑 | ✅ `FilePreviewView` 可改可存 | ❌ 只读预览 |
| 快照/交接 | ✅ 工作区独有（轴3 + 云端 PR 交接） | ❌ 无此概念 |
| 喂 `@` 提及 | ❌ | ✅ `listFiles` 建索引 |
| 拖拽 MIME | `application/x-workspace-path` | `application/x-agentcore-fs` |

两边的**树构建、拖拽移动、预览、增删改**各写了一遍，还各有细微分叉（两套 MIME、两套预览读取、两套空态/错误原语、折叠态只在工作区持久化、watch 只在文件页）。

> 强证据：本地绑定模式下 `LocalWorkspace` 的 op 本就经 `window.fsApi.workspaceOp` 落到**同一个 OS 目录**——「对话工作区」与「文件页某根」完全可能是磁盘上同一文件夹，只是被两条代码路径访问。**数据层概念上已经是一个东西。**

## 二、目标架构 · 前端

抽一个 **`FileSource` 接口** + **一套共用组件**，文件页与工作区只是「挂几个 source」的差别。

```
lib/fileSource.ts              ← FileSource 接口（核心 + 能力位）
  ├─ WorkspaceSource(wsId)     ← 包 REST（工作区一等资源，见 §三）→ 云项目
  └─ LocalRootSource(rootId)   ← 包 window.fsApi（IPC）→ 本地绑定项目 / 纯本地根
components/files/（source-agnostic 共用核心）
  ├─ FileTree(source)          ← 树构建 + 折叠态 + 拖拽移动（统一 MIME）+ 增删改/上传（按能力位）
  ├─ useFileTreeData(source)   ← 树数据 hook：有 listTree 走急加载、否则展开时逐目录懒读 + watch
  ├─ FilePreviewBody(result)   ← 纯渲染（文本/图片/二进制/过大），source 无关
  └─ parts                     ← 空态 / 错误 / IconButton
（各面预览包一层穿 source）files/FilePreview.tsx（文件页·只读）· workspace/FilePreviewView.tsx（工作区·可编辑可下载）
components/files/extras/（source 能力为真才挂）⏳ 未抽
  ├─ SnapshotsPanel(source)    ← 仅 source.caps.snapshots
  └─ HandoffPanel(source)      ← 仅 source.caps.handoff
pages/FilesPage.tsx            ← 中枢：左栏「项目/空间」列表 → 选中渲染 FileTree + FilePreview（现：本地多根 rail；云项目枚举待 Step 1）
components/workspace/WorkspacePanel.tsx ← 退成「中枢组件 + 单一 source」+ §五 chrome（模式 pill + 快照/交接图标浮层）⏳ chrome 未并
```

- **`FileSource` 接口**：核心 `list / read / write / delete / move / mkdir / create`；**可选能力位** `watch? / upload? / download? / snapshots? / handoff?`。
- **能力差异不靠分支硬塞**，而由 source 声明能力位：有 `watch` 才挂实时、有 `upload` 才显上传按钮、有 `snapshots` 才显快照入口。快照/交接是**叠加层**，不进共用核心。
- **文件页 = N 个 source**（每根一棵树）；**对话工作区 = 恰好 1 个 source** → 你那句「只有一个文件夹」精确落地。
- 编辑统一成「预览 + 可选编辑」，文件页顺带获得保存能力。

## 三、后端契约（✅ 已落地 · `api/routes/workspaces.py`）

把工作区升成**一等可寻址资源**（B 逼出来的唯一后端缺口：今天工作区只能「借一个对话」访问，但中枢要按项目浏览）。

```
GET    /v1/workspaces                        列用户全部工作区（枚举）
GET    /v1/workspaces/{ws_id}/files          列文件（recursive）
GET    /v1/workspaces/{ws_id}/files/{path}   读字节
PUT    /v1/workspaces/{ws_id}/files/{path}   写字节（上传/保存）
DELETE /v1/workspaces/{ws_id}/files/{path}   删
POST   /v1/workspaces/{ws_id}/move           移动/改名
POST   /v1/workspaces/{ws_id}/dirs           新建目录
POST   /v1/workspaces/{ws_id}/clone          git clone
GET/POST /v1/workspaces/{ws_id}/snapshots                列 / 留版本
POST   /v1/workspaces/{ws_id}/snapshots/{id}/restore     恢复
GET    /v1/workspaces/{ws_id}/snapshots/{id}/download    下载
```

- **`ws_id` 方案**：`folder:<folder_id>` 或 `conv:<conversation_id>`——分隔符用 `:`（UUID 不含，单段 URL 安全，无需转义；落地时由 `folder/...` 改为 `:` 以适配 path 路由）。与 `_workspace_relpath` 同一 folder-vs-未分组分叉，`format_workspace_id` / `parse_workspace_id` 在 `locate.py`（纯函数，DB 无关）。
- **枚举端点返回**：`{ ws_id, name, location: "cloud"|"local", root_id, has_files }`（`WorkspaceSummary`）。文件夹恒列；未分组**仅当 `workspace_has_entries` 为真**才列（F1，`workspace_root_path` 不创建目录地探测非空）；本地空间恒列（服务端看不到其文件，且 `has_files` 恒真）。
- **鉴权**：`ws_id` 解析出 `folder_id`/`conv_id` → 复用现有 owner 校验（非属主/坏 id/已归档对话用 `conv:` 寻址 → 一律 404）。
- **云/本地闸**（§五）：本地工作区文件走桌面 IPC，不走 REST——故 file/dir/move/clone 与 snapshot create/restore 对 `location=="local"` 返回 **409**；只读的 snapshot list/download 放行（对象存储按 ws 键，本地项目也能列历史）。
- **对话级旧路由**（`/conversations/{id}/workspace/...`）：**保留为「按对话寻址」的等价别名**——它与 ws 路由调用同一 `workspace.files`/`snapshots`/`git` 服务层（即已是薄包装，无重复逻辑），故未改写、零测试迁移；前端对话面板暂仍用它，中枢用 ws 路由。

## 四、四个分叉 · 拍板结论（已确认默认）

| # | 分叉 | 结论 |
|---|---|---|
| **F1** | 中枢列什么当根 | **文件夹项目 +「未分组」分区**；未分组**只列真有文件**的对话空间（懒展开、天然控噪音）。避免「直接聊攒的文件」在中枢看不到。 |

## 五、关键边界与决策

- **本地绑定项目在中枢里走 IPC，不走 REST**：`LocalWorkspace` 的 channel 是 per-turn SSE 挂起原语（绑在对话 run 的 sink 上），中枢「无对话上下文的浏览」没有 turn/sink。故枚举端点标 `location=="local"` 的项目，前端选 **`LocalRootSource(IPC)`** 直读其 `root_id`；`location=="cloud"` 才走 **`WorkspaceSource(REST)`**。这反证了 `FileSource` 抽象的价值：**中枢按 location 选实现，UI 不变**。
- **云项目无本机磁盘路径**：正常——云 source 以 `wsId` 寻址，不暴露绝对路径；「在本地打开」类动作只对本地绑定项目可用。
- **快照的 turn 无关性**：快照列/恢复/下载存 S3、按 `wsId` 键，可走 workspace 级 REST（即便本地项目也能在中枢列历史版本）；但**为本地项目新建快照**需 archive 通道（今天只在 handoff/turn 上下文有），中枢内创建暂缓。
- **watch / 上传下载 仅按能力位出现**：本地 source 有 watch、无上传下载（盘上直读）；云 source 反之。
- **拖拽 MIME 统一**：合并 `x-workspace-path` / `x-agentcore-fs` 为一套，载荷带 `sourceId` 防跨源误投。
