# 手机端落地设计（桌面端减能力层 · 共享核 + 平台壳 · 为 AI 开发设计）🗂️

> **定位**：把产品从「桌面唯一客户端」扩展到**手机端**。心智不是「再设计一个伴侣 App」，而是**手机端 = 桌面端 − 手机物理做不到的能力层**（黑名单减法，非白名单新设计）。云端 AI 团队是同一个产品，手机只是去掉了「碰本地文件 / 本地 MCP / 后台常驻 / 全局热键」这层桌面专属能力。
>
> **为何现在做**：同一用户既要桌面端常驻干活，也要在外面随时看进度 / 审批 / 聊天 / 找人。云端引擎模型本就为「无本地文件夹设备接入」留了口子（见 [`前端技术与架构.md §8.6`](/docs/04-前端/前端技术与架构.md) 选「云端权威 + dotfile」的原话）。
>
> **关键约束 · 项目主要由 AI 开发**：本设计的架构选择以「最适合多 Agent 并行 + 有界上下文的 AI 开发」为第一判据（见 §六），而非单纯工程审美。
>
> **状态**：🗂️ 提案。架构方向（方案 B）已确认（⏳ 未落地）。落地后现状回写 [`前端技术与架构.md`](/docs/04-前端/前端技术与架构.md) §七/§九/§十，本稿退役。本目录仅 `07-规划`。

## 〇、决策摘要

| 维度 | 决定 |
|---|---|
| 定位 | **手机端 = 桌面端 − 能力层**（黑名单减法）。同一产品、同一后端，减去手机物理做不到的能力，**其余全留** |
| 架构 | **方案 B**：共享 `packages/client-core`（逻辑核，面向**能力端口**）+ `apps/desktop`（Electron 壳）+ `apps/mobile`（响应式 / Capacitor 壳）。**否决 A**（一棵树降级）、**否决 C**（另起重写） |
| 减法边界 | 复用现成接缝：`window.fsApi` 探测 + [`FileSource.caps{}`](/apps/desktop/src/renderer/lib/fileSource.ts)。云端 `workspaceSource(REST)` **留**、本地 `LocalRootSource(IPC)` **减** |
| 组件处置 | 四类：纯逻辑 → **必复用**(core/headless hook)、尺寸无关叶子 → **复用**、布局/导航/交互容器 → **各端新建**、中间态 → **headless 拆分**(共享 hook + 各端 chrome) |
| 为 AI 开发设计 | 4 条规则落 [`cross-platform-frontend.mdc`](/.cursor/rules/cross-platform-frontend.mdc)；专防三大 AI 失败模式（**漂移 / 不可验证 / 分支税**） |
| 传输 + 打包 | **web SPA → Capacitor 套壳**上架 iOS/Android + 原生推送。**否决 RN**（弃 DOM 组件复用）、**否决纯 PWA**（推送残缺） |
| 平台粘合（不可避免新增） | bearer-token 认证、FCM/APNs 推送、响应式布局、触控适配 |
| 新依赖 | Capacitor + 推送 SDK（前端）、bearer-token 模式 + 推送下发端点（后端）。按 `dev-process`：**AI 提案 → 人确认** |

**一句话**：手机端是桌面端**减能力层**，靠**共享逻辑核 + 各端平台壳**实现——既不复制逻辑（防 AI 漂移），又让导航/交互各端原生（不把手机做成压扁的桌面）。

## 二、为何方案 B（共享核 + 平台壳）

把两件事拆开看：**共享逻辑** vs **共享布局**。

- **必须共享、重做两遍最危险的是「客户端逻辑核」**：SSE→store 折叠（[`§9.3`](/docs/04-前端/前端技术与架构.md) `projectExecution` / `hydrateFromJournal`）、run 树投影、会话运行时分片（[`§9.6`](/docs/04-前端/前端技术与架构.md)）、审批 / resume 状态机、API/SSE 客户端、错误契约（[`§9.9`](/docs/04-前端/前端技术与架构.md)）。
- **应该分叉的是「导航 / 布局 / 交互」**：桌面是鼠标 + 多面板 `SidePanel` 下钻；手机是触控 + 底栏 / 栈式导航。**交互模型本质不同**。

| | A（一棵树降级） | **B（共享核 + 平台壳）** | C（另起重写） |
|---|---|---|---|
| 逻辑核 | 共享 | **共享 ✅** | 各写一份 |
| 导航 / 布局 | 一棵树塞两种 → 永久分支税 | **各端原生 ✅** | 各端原生 |
| 手机体验 | 压扁的桌面 | **真移动 UX ✅** | 真移动 UX |
| 逻辑漂移风险 | 低 | **低 ✅** | 高 |

> **被否决 · A（一棵树降级）**：把布局 / 交互硬塞进同一组件树 → 每个共享件都背响应式 + 输入模式分支（「分支税」），且手机沦为压扁的桌面，与对标 Cursor/Claude 的打磨标准冲突。
>
> **被否决 · C（另起手机前端、只共享后端契约）**：复制客户端逻辑核 → 两套状态机锁不住、双重修 bug；在多 Agent 并行 + 有界上下文下「漂移」会静默出 bug（见 §六）。

## 四、架构与结构

```
packages/client-core/          ← 逻辑核，面向「能力端口」（与 Electron / 平台无关）
  stores/      services/      lib/      types/
  data/  ← FileSource 接口 + workspaceSource(REST) + SSE/REST 客户端
  ports/ ← 能力端口（抽象）：LocalFsPort / NotificationPort / DeepLinkPort / SecretStorePort ...
  hooks/ ← headless 行为 hook（useApprovalCard / useConversationItem / useTeamGraph ...）

apps/desktop/   ← Electron 壳：注入 IPC 实现的端口 + 侧栏 / SidePanel 多面板 + 桌面 chrome
apps/mobile/    ← 响应式 / Capacitor 壳：注入降级（或空）端口 + 底栏 / 栈式导航 + 触控 chrome
                  + 平台粘合：原生推送 / bearer-token / 响应式
```

**能力端口 = 减法的干净接缝**：`client-core` 只面向抽象端口，**不知道**自己跑在 Electron 还是浏览器。桌面壳注入 IPC 实现（`LocalFsPort` → `window.fsApi`），手机壳不注入 `LocalFsPort` → 本地文件能力**自然消失**，无需任何 `if(platform)` 分支。

> 这正是后端 [`远期规划 §1.1` Sidecar「引擎面向宿主端口」](/docs/07-规划/远期规划.md)哲学的**前端镜像**——项目在后端已信这套（`EventSink` / `Journal` 等 Protocol 化）。前端能力端口是同一范式的客户端版。

## 五、组件层落地准则：core/壳边界 + 四类处置

「复用 vs 新建」不是二元题，按组件**价值在逻辑还是在布局/交互**分四类：

| 组件类型 | 处置 | 本仓真实例子 |
|---|---|---|
| 纯逻辑 / 数据 / 状态 | **必复用**（进 core，headless hook） | [`stores/`](/apps/desktop/src/renderer/stores)（execution/conversation/approvals…）、[`services/`](/apps/desktop/src/renderer/services)、[`lib/errors`](/apps/desktop/src/renderer/lib/errors.ts)、[`lib/cost`](/apps/desktop/src/renderer/lib/cost.ts)、[`lib/format`](/apps/desktop/src/renderer/lib/format.ts)、run 树投影、@ 索引 [`lib/fileIndex`](/apps/desktop/src/renderer/lib/fileIndex.ts) |
| 尺寸 / 输入无关的叶子展示件 | **复用**（传 size/density props） | [`Markdown`](/apps/desktop/src/renderer/components/chat/Markdown.tsx) / [`Diagram`](/apps/desktop/src/renderer/components/chat/Diagram.tsx) / [`CodeBlock`](/apps/desktop/src/renderer/components/chat/CodeBlock.tsx) 渲染器、状态点 / 成本徽章、[`components/ui/`](/apps/desktop/src/renderer/components/ui) 原语 |
| 布局 · 导航 · 交互容器 | **各端新建** | [`AppShell`](/apps/desktop/src/renderer/components/layout/AppShell.tsx)、[`Sidebar`](/apps/desktop/src/renderer/components/sidebar/Sidebar.tsx)、[`SidePanel`](/apps/desktop/src/renderer/components/layout/SidePanel.tsx)、[`PageContainer`](/apps/desktop/src/renderer/components/layout/PageContainer.tsx)、[`CommandPalette`](/apps/desktop/src/renderer/components/layout/CommandPalette.tsx) |
| 中间态（行为重 + 两端都要 + chrome 真不同） | **headless 拆分**：共享行为 hook + 各端 chrome | **协作图**（共享 [`stores/execution`](/apps/desktop/src/renderer/stores/execution.ts) run 树，桌面 React Flow [`GraphView`](/apps/desktop/src/renderer/components/graph/GraphView.tsx) / 手机竖时间线）、[`ConversationItem`](/apps/desktop/src/renderer/components/sidebar/ConversationItem.tsx)（共享 rename/pin/archive 逻辑，桌面右键 / 手机长按 action sheet）、[`MessageInput`](/apps/desktop/src/renderer/components/chat/MessageInput.tsx)（共享 @ 索引，桌面 textarea+popover / 手机 input+bottom sheet）、审批卡 |

**样板 · 协作图 headless 拆分**：同一份 `useExecutionStore` run 树数据 →（桌面）React Flow + [`elk-layout`](/apps/desktop/src/renderer/lib/elk-layout.ts) 平移缩放画布；（手机）竖向时间线 / 可折叠波次树。**两个 view、一个数据源**——React Flow 平移缩放在手机上体验差，竖时间线反而更好。

核心一句：**别二元想「复用 or 新建」，按「逻辑进核、chrome 分端」切。**

## 六、为 AI 开发设计（第一判据）

项目主要由 AI 开发（多 Agent 并行、有界上下文）。这带来**人类团队没有的失败模式**，架构要专门防：

| 失败模式 | 为什么 AI 比人更危险 | 架构对策 |
|---|---|---|
| **漂移**（两份「同一个」逻辑跑偏） | 多 Agent 并行、互不通信 + 上下文有界：agent A 修了桌面那份，根本看不到也不知道手机还有一份；无人类同时读两边 | **零逻辑重复**，core 是行为单一真相 → 判死 C 与「复制式复用」 |
| **不可验证** | AI 靠测试 / Read 自检；UI chrome 难写测试，纯逻辑易写 | **最大化「可测核」、最小化「难验 chrome」**——行为往 core 推 = 往测试区推 |
| **分支税 + 撞补丁绊线** | branchy 文件让 agent 每次编辑都要 reason 所有分支、易改坏一条路；正中 `dev-process` 的「同根因改 ≥2 层 / 同接缝第 3 次补丁」 | **文件内零平台分支**；差异靠「哪个壳注入哪个端口/chrome」表达 → 判死 A |

**让 B 对 AI 友好的 4 条规则**（落 [`cross-platform-frontend.mdc`](/.cursor/rules/cross-platform-frontend.mdc)）：

1. **边界 = 显式类型契约**（core API / 能力端口 / headless hook 签名）——接 `dev-process`「优先写接口定义再实现」。agent 对着契约写一端，不用加载另一侧。
2. **能力端口显式注入，不要 ambient 探测**——别散 `if(window.fsApi)`，让壳显式 `inject(LocalFsPort)`；减法在代码里可见。
3. **可预测放置 + 命名对齐**——core `useApprovalCard` ⇄ 各壳 `ApprovalCard`，同词根；AI 靠 grep / 语义搜索一次命中全部碎片。
4. **并行安全分区**——`apps/desktop` 与 `apps/mobile` 壳是 **disjoint 文件树**，唯一共享面是小而稳的 `client-core`；两 agent 各建一端几乎零碰撞。

**一条 AI 能直接执行的决策启发式**（拿不准复用/拆分/重建时）：

> **选「不复制逻辑」且「让尽量多行为落进可测核」的那个选项，哪怕多写一遍 chrome。**

理由：重写 chrome 的成本 AI 付得起（且可并行），漂移与不可验证的成本 AI 付不起。

> **代价（诚实）**：headless 拆分是 indirection，对 AI 等于「多跳追踪」。故「别过度拆」是硬约束——**只有「行为重 + 两端都要 + chrome 真不同」三条全中才 headless 拆**；差一条就整件进 core 或整件各写。

## 七、平台粘合层（不可避免的新增，不算违反减法）

| 粘合 | 内容 |
|---|---|
| 认证 | 现为 httpOnly cookie（桌面靠 `app://` 自定义 origin 搞定 CORS/cookie）。手机 web 是新 origin、Capacitor 壳是 `capacitor://` 非常规 origin → **后端加 bearer-token 模式**给移动端（见 [`认证与会话.md`](/docs/05-平台与运维/认证与会话.md)） |
| 推送 | 手机一切后台 SSE 即断 → **原生推送 + 回前台拉 `/v1/attention`** 补盲（复用桌面 [`§7.5`](/docs/04-前端/前端技术与架构.md) 的「SSE 桥 + attention 轮询」双通路概念） |
| 响应式 | 各端壳自管布局；core 不含布局假设 |
| 触控 | 点击目标 ≥44px、hover 改长按 / 显式按钮、右键菜单 → action sheet |

## 八、传输与打包

| 路线 | 结论 |
|---|---|
| **web SPA → Capacitor 套壳** | **选定**：同一套 web 代码打 iOS/Android 原生包，拿到上架 + 原生推送（FCM/APNs），近零重写 |
| 纯响应式 web（手机浏览器） | P1 验证可用；但**无可靠原生推送**（iOS PWA 推送残缺），不能作终态 |
| React Native | **否决**：UI 要重写、用不了 core 里的 DOM 组件，等于把想复用的桌面前端全扔 |
| 纯 PWA | **否决**：推送 / 后台残缺（同桌面 [`§7.1`](/docs/04-前端/前端技术与架构.md) 否决 PWA 的理由） |

## 九、缺口与新工作

**✅ 直接复用**：整套后端 REST + SSE、OpenAPI→TS 类型、`workspaceSource(REST)`、客户端逻辑核（抽进 `client-core` 后）。

**❌ 缺口（净新工作）**：

| 缺口 | 现状 | 需补 |
|---|---|---|
| `client-core` 包 | 逻辑散在 [`apps/desktop/src/renderer`](/apps/desktop/src/renderer) 内、与 Electron 耦合 | 增量抽 stores/services/lib/types/data + 定义能力端口；桌面改注入端口（见 §十迁移） |
| 前端能力端口 | 无；当前直接 `window.fsApi` / IPC | 定义 `LocalFsPort` / `NotificationPort` / `DeepLinkPort` / `SecretStorePort`，桌面注入 IPC 实现 |
| 移动认证 | 仅 httpOnly cookie | 后端 bearer-token 模式 + 前端 token 存储（Capacitor secure storage） |
| 推送基础设施 | 无 | 后端「设备注册 + 推送下发」端点 + FCM/APNs 接入；端到端复用 attention 事件源 |
| `apps/mobile` 壳 | 不存在 | 新建：响应式 / Capacitor 壳 + 底栏 / 栈式导航 + 触控 chrome |

| **P1**（web 瘦客户端） | `apps/mobile` 响应式 web 壳，跑通看进度 / 审批 / 聊天 / 消息 / 云端文件浏览；bearer-token | 可用移动 web 端，验证「桌面减能力层」定位 |
| **P2**（上架 + 推送） | Capacitor 套壳 iOS/Android + 原生推送（FCM/APNs，源自 attention/审批事件） | App Store / Play 包 + 推送闭环 |
| **P3 ⏳**（选配） | 仅当 P2 web-in-shell 体验不足时，选择性上 RN 重做局部 chrome | — |

> **推荐**：**先做 P0 抽核**（这是 B 的地基，也直接服务桌面的可测性），再 P1 验证，P2 上架。P0 不阻塞桌面正常迭代（增量、disjoint 分区）。

## 十一、风险与边界

| 风险 | 缓解 |
|---|---|
| 抽核对桌面造成 churn（仓库多 Agent 并行） | 增量抽、桌面全程可用、core/壳边界画准；按 §六「并行安全分区」切任务（见 [`git-workflow.mdc`](/.cursor/rules/git-workflow.mdc)） |
| 逻辑漂移（两端跑偏） | 零逻辑重复：core 是行为单一真相；只允许**呈现**分叉、**行为**不许各写 |
| 过度 headless 拆分 → AI 多跳追踪 | 三条判据全中才拆（§六）；简单叶子直接进 core，纯布局直接各写 |
| 设计系统两端漂移 | token + 原语共享（[`§10`](/docs/04-前端/前端技术与架构.md) 已统一 OKLCH token；[`components/ui/`](/apps/desktop/src/renderer/components/ui) 原语收进 core） |
| 范围蔓延（手机想做本地文件 / MCP） | 守住「减法」边界：能力端口手机不注入即没有；要做须重新决策 |
