## 认知同构 · 执行异构

对模型而言 Tool / Skill / 记忆等皆为 token；执行侧异构（Skill 只读、Tool 有副作用、Agent 有循环与状态）。原则：**默认不放，按需才拉**。

条目化后（⏳）注入侧连**载体**也同构：Skill / 记忆主题 / 按需规则都是一条带 `description` 的 md 条目，异构只剩执行侧。

五杠杆（选择 / 时机 / 压缩 / 外置 / 分治）实现归属见记忆·工具·执行引擎·协作模式各篇——本文不复制。「谁来拉」已决：**模型自选**（否决 embedding / LLM 预筛）。

## 决策：注入侧 ContextAssembler ✅；不另立 ContextProvider

**现状**：prompt 注入已收敛于 `assemble_system_prompt` / `runtime/context/` 的 `ContextAssembler`（含 `PromptContributor` 插件化）。这与「不建第二套大一统 Provider」不矛盾——Assembler 即注入侧收口，不必再立门派。

仍不建「目录 + 按需取」式超级 `ContextProvider` 的理由：

1. 三份 consult 源（Skill / 记忆主题 / 按需规则）走的是**合并成同一种条目**（读侧 ✅ 步 1，存储合一待步 2–4），不是「在三种异构源上盖一层 Provider」——收敛掉的是重复，不是差异。
2. 条目侧同构之后，Tool 仍不同构于条目（有副作用、有 schema、有权限轴）；registry 层 Tool / 条目刻意不共享基类。
3. 复杂度在写侧 / 执行侧 / 预算侧；注入侧已有 Assembler，勿叠 Provider。

守恒律：统一只罩注入侧；输出侧（副作用 / 循环 / 状态）复杂度搬家不消灭。

## 扳机

- **A 抽接口**：✅ **已吃满**（步 1）。`Consultable`（目录露出 + 按名取文）现由 skill / rule / memory 三个源分别实现，`MergedConsultSource` 聚合为唯一条目源——**提示词目录与工具 `fetch_by_name` 读同一个实例，故「目录里列了什么」与「按名能拉到什么」在结构上无法漂移**，这是合并的主要风险被架构消掉而非靠测试盯住。对外单一 `consult` 工具；重名按 skill → rule → memory 固定优先级解析。生效方式对外仅 `常驻` | `按需`；`conditional` 随条目化清理。eval 机制已就位但 baseline 经决策跳过。权威行为 → [记忆与知识](/docs/03-AI核心/Agent记忆与知识系统.md)。
- **B 建预算**：**⏳ 已触发**，但触发出的既不是原设想的「长裁剪降级」，也不是读侧配额。触发源是取消固定文件名（`偏好.md` / `画像.md` / `导航.md`）后常驻集合失去天然上限；结论是**把闸放在写侧**——常驻满了不许再往常驻加，**读侧永远全量注入、不截断**。`budget` 从预留读取点变成写侧用量口径；引擎不自动裁剪或淘汰（自动淘汰与读侧截断均已进否决表）。现状 `max_instruction_*` 超限静默整条丢弃 + `keep_rank`（全局>项目、用户>AI）随权威档一并撤销——权威取消后该排序失去依据，且读侧不再有「淘汰」这回事。装配主干 + `PromptContributor` 插件化已落地；COST-004 仍只观测不闸。
