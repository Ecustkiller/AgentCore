## 认知同构 · 执行异构

对模型而言 Tool / Skill / 记忆等皆为 token；执行侧异构（Skill 只读、Tool 有副作用、Agent 有循环与状态）。原则：**默认不放，按需才拉**。

条目化后（⏳）注入侧连**载体**也同构：Skill / 记忆主题 / 按需规则都是一条带 `description` 的 md 条目，异构只剩执行侧。

五杠杆（选择 / 时机 / 压缩 / 外置 / 分治）实现归属见记忆·工具·执行引擎·协作模式各篇——本文不复制。「谁来拉」已决：**模型自选**（否决 embedding / LLM 预筛）。

## 决策：注入侧 ContextAssembler ✅；不另立 ContextProvider

**现状**：prompt 注入已收敛于 `assemble_system_prompt` / `runtime/context/` 的 `ContextAssembler`（含 `PromptContributor` 插件化）。这与「不建第二套大一统 Provider」不矛盾——Assembler 即注入侧收口，不必再立门派。

仍不建「目录 + 按需取」式超级 `ContextProvider` 的理由：

1. 三份 consult 源（Skill / 记忆主题 / 按需规则）走的是**合并成同一种条目**（读侧 ✅ 步 1，存储合一待步 2–4），不是「在三种异构源上盖一层 Provider」——收敛掉的是重复，不是差异。
2. 条目侧同构之后，Tool 仍不同构于条目（有副作用、有 schema、有权限轴）；registry 层 Tool / 条目刻意不共享基类。
3. 复杂度在写侧 / 执行侧 / 预算侧；注入侧已有 Assembler，勿叠 Provider。

守恒律：统一只罩注入侧；输出侧（副作用 / 循环 / 状态）复杂度搬家不消灭。

## 扳机

- **A 抽接口**：✅ **已吃满**（步 1）。`Consultable`（目录露出 + 按名取文）现由 skill / rule / memory 三个源分别实现，`MergedConsultSource` 聚合为唯一条目源——**提示词目录与工具 `fetch_by_name` 读同一个实例，故「目录里列了什么」与「按名能拉到什么」在结构上无法漂移**，这是合并的主要风险被架构消掉而非靠测试盯住。对外单一 `consult` 工具；重名按 skill → rule → memory 固定优先级解析。生效方式对外仅 `常驻` | `按需`；`conditional` 随条目化清理。eval 机制已就位但 baseline 经决策跳过。权威行为 → [记忆与知识](/docs/03-AI核心/Agent记忆与知识系统.md)。
- **B 建预算**：**✅ 已触发并落地**。触发出的既不是原设想的「长裁剪降级」，也不是读侧配额。触发源是取消固定文件名（`偏好.md` / `画像.md` / `导航.md`）后常驻集合失去天然上限；结论是**把闸放在写侧**——常驻满了不许再往常驻加（AI 写超限抛错并推卡，用户改既有条目放行），**读侧永远全量注入、不截断**。落地面：`memory/always_quota.py` + `GET /v1/documents/always-quota`；读侧已无 `keep_rank`（`rules_injection.py`）。`budget` 从预留读取点变成写侧用量口径；引擎不自动裁剪或淘汰（自动淘汰与读侧截断均已进否决表）。旧 `max_instruction_*` 超限静默整条丢弃 + `keep_rank`（全局>文件夹、用户>AI）随权威档一并撤销——权威取消后该排序失去依据，且读侧不再有「淘汰」这回事。装配主干 + `PromptContributor` 插件化已落地；COST-004 仍只观测不闸。

## 分层边界：事实归事实层，HOW 归行为层

同一条纪律在装配后的提示串里**只应出现一次**。谁写什么：

| 层 | 只写 | 代码 |
|---|---|---|
| 环境事实 `<workspace_context>` | 本回合**事实**：执行位置、能力行、产物格式、挂载、产物出口路径、某能力装没装配、宿主是哪种 | `runtime/context/workspace_context.py` |
| CEO 行为 | 「该怎么做 / 禁止什么」：路由、姿势、禁令 | `runtime/resolve/prompt/ceo_core.py` |
| 全员基座 | 跨角色通用纪律：挂号、凭据、交付与只读口径、未装配勿声称已用 | `runtime/resolve/prompt/base.py` |
| 工具面 | 取值语义留参数描述；跨工具路由 / 审批策略留工具描述 | 各工具 schema（→ [执行引擎 §五](/docs/03-AI核心/执行引擎架构设计.md)） |

**为什么要立这条**：事实层最贴近「模型不知道什么」，写的人会顺手把「所以你该怎么做」一并写上；而行为层的作者并不知道事实层已经写过，于是同一条约束在两层各活一份、措辞还略有出入。模型拿到的是同一条规则的两个版本——这比只写一处更糟，且两份会各自演化。典型回潮形态：浏览器指引 / 跨文件夹指挥 / 区外授权 / 三分日志在事实层与行为层对打；一条挂号纪律散进 `<tool_use>`、`<delivery_baseline>`、`<claim_evidence>`、`citation` 四处；`ask_user` 预填 `default` 在同一段里重复六次。

**按能力分支复写是最常见的回潮口**：能力未装配时的姿势（一句边界 + 禁称已用 + 禁多轮复读）对 browser / host / mcp / terminal / code_execute / package_install / git 是**同一条**，写成每个能力各一份就是七份。权威在共享基座 `base.py` 的【能力未装配·统一姿势】（CEO 与队员都看见）；`ceo_core` 只留禁把该动作派进队员任务。事实层只报该能力装没装配。

**回潮防线只有棘轮，没有闸**：工具面有 `tests/test_tool_schema_size_ratchet.py`；系统提示侧没有自动检查，靠本节与各文件模块 docstring 的短指针。`prompt_budget_char_soft_cap` 只观测不裁（见 §扳机 B），不要误当上限。
