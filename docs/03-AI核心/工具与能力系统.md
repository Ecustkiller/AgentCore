### 工作区文件与 Git 工具（内置）✅

平台内置 `build_builtin_registry()` 共 **14** 个（web / 文件 / grep / git / `code_search` / `test_run` / `code_execute` 等，单源见 `tools/builtin/__init__.py`）；worker 另加 **5** 个 worker-only 工具（`escalate`、便签三件套、`handoff`）；CEO 经 `build_ceo_tool_registry()` 只取内置中 `approval=NEVER` 的只读子集，编排原语（`delegate` / `replan` / `revise` / `debate` 等）在 pipeline 单独装配、不进 worker registry。工作区相关能力要点（契约细节 → 见代码 `tools/builtin/file_ops.py`、`tools/builtin/git_ops.py`）：

| 工具 | 要点 |
|---|---|
| `file_read` | 可选 `offset`（1-based）/ `limit`（≤500 行）；有任一参数走 `WorkspaceBackend.read_lines()`，输出带 `{n:>6}\|` 行号前缀与范围注记；都不传时全文读取（默认 500 行上限，向后兼容） |
| `file_append` | 在文件末尾追加内容（不存在则创建）；`GRANTABLE` + `FILESYSTEM`，与 `file_write` 同属文件改动类审批；长文分段写作首选（首段 `file_write`、后续 `file_append`）→ 系统 Skill `long_form_writing` |

| `code_execute` | 长任务经 `ToolContext.on_progress` 发射 `tool_use_progress`（`phase="output"` + `{stream, chunk}`），**复用现有事件、不新增 journaled 类型**；重载后权威态仍为 `tool_use_end` 完整 stdout/stderr。→ 见 [`执行引擎架构设计.md` §二](/docs/03-AI核心/执行引擎架构设计.md) |

## 一、能力域架构 ✅ 已确定（领域模块 ⏳ 未实现 · 只读能力图鉴已落地）

> **实现现状**：目标架构，后端尚无 `capability` **领域模块**（`AgentEntityBinding` / Skill / Rule 能力实体与绑定），MVP 在 pipeline 固定注册内置工具。**但只读「能力图鉴」`GET /v1/capabilities`（`api/routes/capabilities.py` + `tools/catalog.py`）已落地**——与运行时 pipeline 共用同一函数对外暴露工具/技能目录（详见 §二）。

**四关注点**：能力域 `capability`（能力定义与绑定）/ 市场侧（发现与发布）/ 本地侧（已装+自建）/ 获取通道（安装动作）。

**两铁律**：① 运行时永远只读「本地侧」，不直接碰市场侧；② 本地侧不反向依赖市场侧（市场可整体下线而运行时照跑）。

**单源原则**：Tool / Skill / Rule 经统一 `AgentEntityBinding` 绑定到 Agent；能力曾是 marketplace 子模块——根因是「能力地基盖在了市场楼里」，须拆回能力域。

**逻辑本地先行**：当前本地侧 = 云后端 user 维度私有空间；物理本地（设备侧、离线）留演进，不为后者预建 provider 抽象——两条铁律担保将来只换「本地侧从哪儿读」。

>
> **能力透明/可视化已落地**：工具 / 技能 / 提示词对用户公开（分层渐进披露，UX 详见 [`前端UX设计.md` §十二](/docs/04-前端/前端UX设计.md)）。单一事实源：① 工具全量目录（CEO/队员可用性）`tools/catalog.py`——schema 直接取自运行时同一批工具类，覆盖 CEO 的 `delegate`/`replan`/`revise`/`debate`/`consult_skill`/`consult_memory`/`ask_user`（+ 白板会话的 `board_ops`/`board_read` 也广告进图鉴）（`/v1/tools` 仅内置子集视图）；② 提示词模板 `compose_ceo_chat_prompt`；③ 本回合**逐字**系统提示词作为 captain `system` 上下文块（`run_context` 投影、与喂 LLM 同源）随「收到的上下文」呈现——桌面在 CEO 气泡**按需弹窗**里对所有人展示（详见 [`上下文传递可视化.md`](/docs/03-AI核心/上下文传递可视化.md) 决策②/④）。`consult_skill` 结果带 `display`（skill 名 + summary），前端渲染为「查阅能力」卡。

**两类来源、单一机制 ✅**：Skill 与工具对称，分**系统（内置）**与**市场**两类来源，共用同一套 `SkillRegistry` + `consult_skill` 检索原语——正如内置工具与市场工具共用 `ToolRegistry`，不另造平行系统。

| | 系统 Skill ✅ | 市场 Skill ⏳ |
|---|---|---|
| 来源 | 代码定义（`build_system_skill_registry`） | 入库实体 + per-agent 绑定 |
| 装配 | 随 CEO 常备（不入库、不走绑定） | 绑定后进 Agent 技能集 |

- 系统 Skill → 见代码 `build_system_skill_registry`。
- **可选垂直包（opt-in）**：`build_system_skill_registry(include_legal=…)` 由开关 `legal_vertical_enabled`（默认关）选择性叠加**法律垂直**领域 Skill（`legal_answer_brief` 对方律师作战室 / `legal_case_analysis` 三方视角案情研判，见代码 `runtime/legal_skills.py`）；开关关时平台系统 Skill 集原样、模块图无 `core→domain` 边。属 stopgap（正道走市场 Skill），backlog 见 [`远期规划.md §4.5`](/docs/06-规划/远期规划.md)。

> **单源原则与「两类来源」的关系**：原否决（保留）针对「**单个**市场 Skill 同时有内联 + 市场两份存储」的双源——内联 vs 市场仍应是 `status` 位、非两套存储。系统 Skill 不是任何市场 Skill 的影子，而是**另一类来源**，故与「否决内联」不冲突，是其细化。**被否决·另造 `consult_capability` 平行机制**：会与未来市场 Skill 的 `consult_skill` 重复、留合并债（补丁绊线），故收敛到同一机制。

**Prompt 自适应（目录模式 ✅）**：技能数 ≤ 阈值全文注入；超阈值转**目录模式 + `consult_skill` 按名拉取**。系统 Skill 正文合计远超任何合理阈值 → 自然落目录模式：常驻只挂一行 `name：summary` 触发描述（`render_skill_directory`），模型决定要用某能力后才 `consult_skill(name)` 把正文拉回 ReAct 循环（`CONTINUE`）。**切分判据＝模型要不要靠它决定下一步**：决定「干什么」的路由知识常驻（CEO 精简核心），决定「怎么干」的机制细节按需取。目录按「所需工具是否装配」动态显隐（`requires_tools`），永不广告 CEO 没有的能力（沿用 `ask_user` 的 live-user 门）。否决：关键词匹配 trigger、embedding 预筛、LLM 预筛。
> CEO 提示词的「精简核心 ↔ 能力目录 ↔ consult_skill」具体形态见 [`编排器与CEO主Agent.md`](/docs/03-AI核心/编排器与CEO主Agent.md) §核心定位。

**Skill ↔ Tool**：Skill 永不自动注入工具——绑定建议返回 `suggested_tools`；运行时对未持有工具注入 `<note>` 软提示。工具集仍由绑定显式决定。

**质量度量（⏳）**：安装数 / 激活数 / 描述完备度 / 用户反馈有效性——细则见 [`../06-规划/远期规划.md`](/docs/06-规划/远期规划.md)。

**Skill 编写规范（⏳）**：五要素 `name` / `trigger` / `guidance` / `constraints` / `output_format`；面向 LLM 祈使句、500–3000 字、步骤明确工具名——完整 checklist 待市场落地后补。

## 三、表达形态 vs 创作产物 vs 受控能力 ✅ 已确定

### 3.1 区分原则

| 类别 | 通道 | 判据 | 示例 |
|---|---|---|---|
| **表达形态** | LLM 直写代码块 + 前端渲染 | 只影响呈现、无副作用、不留可编辑产物 | mermaid / markmap / vega-lite |
| **创作产物** | 用户编辑器 + Agent 工具共编 | 可持久化、可反复编辑 | 导图文档、画布、多维表格 |
| **受控能力** | 工具（Tool） | 读写数据、触发副作用、需审计/计费 | 文件读写、HTTP、代码执行 |

**铁律**：纯可视化表达 = 直写代码块 + 前端渲染，绝不包装成工具；需持久化可跨轮编辑则升级为「创作产物」。

**同名异物（判据看通道，不看形态名）**：同一可视化形态名可能横跨上表两栏——最典型是**导图 / mind map**：既是**表达形态**（`markmap`：LLM 直写代码块 + 只读渲染、不留可编辑产物），又是**创作产物**（可持久、可反复编辑的导图文档）。归类**只认「通道 + 是否留可编辑产物」这条判据、不认形态名**：直写代码块 → 前端渲染 = 表达形态；用户编辑器 + Agent 工具共编 + 可持久 = 创作产物。二者是同一形态的两种落地，不矛盾。

> **表达形态层 ✅ 已落地**：聊天内 mermaid / markmap / vega-lite 三引擎渲染，流式先显源码、回合结束再渲染，失败回退源码。→ 见代码 `apps/desktop/src/renderer/components/chat/Diagram.tsx`

### 3.2 为什么直写优于工具（表达形态场景）

工具通路用于表达时有 4 个累积失败点：参数 JSON 构造 → 工具执行 → 模型原样复读结果 → 目标格式语法正确。直写代码块消除前三个失败点，且天然支持流式（半截大纲仍是合法大纲，半截 mermaid 是语法错误）。

### 3.3 文本为典范模型

当内容同时被人和多 Agent 协作创作时，**典范模型应为 Markdown 文本**（非富文本 JSON/AST）——LLM 输出文本、本地 `.md` 落盘是文本、AI diff 也是文本。由此推导：文本即真相、AI 协作一等公民、聊天与编辑器共享渲染核、绝不损坏字节。

### 3.4 创作工具：产物的两副面孔 ✅ 已确定

「创作工具」每个对应一种**产物类型**，与「动作工具」并列：动作工具执行确定性动作不留可编辑产物；创作工具产出可持久 artifact，同时有用户面（UI 编辑器）与 Agent 面（类型注册工具集）。产物统一进文件/产物体系，可被对话 `@` 引用。前端工具箱见 [前端UX设计 §十二](/docs/04-前端/前端UX设计.md)。
