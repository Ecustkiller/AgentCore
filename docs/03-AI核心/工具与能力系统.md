## 五、能力域架构 ✅ 已确定（⏳ 后端未实现）

> 能力（Tool / Skill / Rule）是平台的一等资产，市场只是其可选分发皮肤。

> **实现现状**：本节为**目标架构**，后端**尚无 `capability` 模块**、无 `AgentEntityBinding`。MVP 在 `runtime/pipeline.py` + `tools/builtin/__init__.py` 固定注册内置工具（worker 全集：web_search / read_url / file_read / file_write / str_replace / file_list / file_delete / file_move / grep / code_execute）；CEO 只取其中**只读/检索子集**、外加专属编排原语 delegate（worker 不持有 delegate），生产/变更工具仅 worker 持有；无 Skill / Rule 能力实体与绑定（→ 见代码 `apps/server/agentcore/tools/`、`runtime/prompt.py`）。

### 5.1 问题根因

能力曾被定义在 marketplace 模块里、自带市场属性出生——「用能力」被迫穿过「市场」。根因不是市场代码乱入 AI，而是**能力这块地基被盖在了市场的楼里**。

### 5.2 四关注点模型

| 关注点 | 职责 | 回答的问题 |
|---|---|---|
| **能力域 `capability`** | 能力是什么、怎么加载/绑定/创作 | 「能力本身」 |
| **市场侧** | 公共货架：发现 + 评价/版本/发布 | 「有什么能取」 |
| **本地侧** | 我的空间：已装+自建能力、我的 Agent、binding | 「我在用什么」 |
| **获取通道** | 市场侧 → 本地侧的安装/下载动作 | 「怎么取到」 |

### 5.3 两条铁律

```
铁律一：运行时永远只读「本地侧」，绝不直接碰市场侧
铁律二：「本地侧」不反向依赖「市场侧」
```

铁律立住后的效果：市场侧可整体下线而运行时照跑；市场侧可独立重建为独立服务。防回归靠 CI 而非口头约定——AST 级 import 边界测试钉死两条铁律。

### 5.4 逻辑本地先行，物理本地留演进

| 形态 | 本地侧 = | 成本 |
|---|---|---|
| **逻辑本地**（当前） | 云后端的私有空间（user 维度隔离） | 中等 |
| **物理本地**（留后） | 真存在用户设备上（离线、私有能力不出机） | 高一个量级 |

**不为物理本地预建 provider 抽象层**——用边界清晰换未来可演进，而非用预先抽象换。两条铁律担保下，将来切物理本地只需换「本地侧从哪儿读」，运行时与市场侧一行不动。

### 5.5 能力三类型

| 类型 | 定位 | 生命周期 |
|---|---|---|
| **Tool** | 确定性 API 能力 | 定义 → 绑定 → 运行时解析 |
| **Skill** | 领域能力（注入 system prompt） | 同上 |
| **Rule** | 行为准则（注入 system prompt） | 同上 |

三者通过统一的 `AgentEntityBinding`（`entity_type` + `entity_id` 多态）绑定到 Agent，运行时只读绑定 + 能力定义。

## 六、Skill 架构 ✅ 已确定（⏳ 后端未实现）

> Skill 与 Tool / Rule 走统一市场模型，Agent 通过绑定获得能力，单源消除重复注入。

> **实现现状**：本节为**目标架构**，后端**未实现** Skill 实体 / `agent_entity_bindings` / `consult_skill` / Prompt 自适应注入。MVP 的 `assemble_system_prompt` 仅做默认 prompt + 时间 + 长期记忆 `<rules>` 注入（→ 见代码 `apps/server/agentcore/runtime/prompt.py`）。

### 6.1 单源原则

Skill 只有一种存在形态：**市场实体 + 绑定**（`agent_entity_bindings`）。曾评估并否决双源（内联 + 市场并存）：

| 否决理由 | 说明 |
|---|---|
| 偶然复杂度 | 内联 vs 市场的区别仅是「是否公开」，可见性应是 `status` 的一个状态位，不该是两套存储 |
| 模型自洽 | Tool / Rule / Delegation 本就是引用式（version 只存声明/绑定，内容运行时解析）；Skill 也改为引用，使 AgentVersion = 「接线快照」模型统一 |
| 消除重复注入 | 双源下同一 Skill 可能同时存在于内联和绑定，PromptAssembler 不去重时在 prompt 中出现两次 |

**结论**：单源（市场 + 绑定）概念最省、与 Tool/Rule 对称、消除重复注入。

### 6.2 Agent 独有内容归属

| 归属 | 内容 | 特征 |
|---|---|---|
| `system_prompt` | 身份 / 不可转移的运作指令 | 随 AgentVersion 冻结、Fork 携带 |
| Skill | 可转移的能力单元 | 可复用、可发布到市场 |

### 6.3 Prompt 自适应注入

绑定的 Skill 如何进 prompt 随技能数自适应（阈值 `skill_catalog_threshold`）：

| 模式 | 条件 | 行为 |
|---|---|---|
| **全文模式** | ≤ 阈值 | guidance / constraints / output_format / examples 全量注入 |
| **目录模式** | > 阈值 | prompt 只列「技能名 + trigger」作导航；模型用 `consult_skill` 工具按名拉取完整内容 |

**为何不永远目录**：技能少时全文的 token 成本可忽略，还省一次工具往返；目录的价值只在技能多时显现。

**被否决的激活方案**：

- 关键词匹配 trigger——脆弱，把判断从模型降级为字符串匹配
- 语义检索（embedding）——对当前技能规模过重
- LLM 预筛——每轮多一次 LLM 调用，延迟/成本翻倍

**约束**：`consult_skill` 只能查本 Agent 已绑定的技能，不读任意市场技能——不扩大知识边界。

### 6.4 Skill ↔ Tool 关联策略

Skill 的 guidance 常依赖具体工具，但 **Skill 永不自动为 Agent 注入工具**——能力刻意声明、不隐式继承。走两道弥合缝隙：

| 道 | 时机 | 行为 |
|---|---|---|
| **绑定建议** | 绑定 Skill 时 | 返回 `suggested_tools`（技能引用 ∩ 已发布 ∩ Agent 未持有），前端提示「一起绑」 |
| **运行时软提示** | Prompt 组装时 | 技能引用了 Agent 未持有的工具 → 在该 Skill 内注入 `<note>`，让模型跳过需该工具的步骤 |

两道都不改变「工具集由绑定显式决定」这一契约。

### 6.5 质量度量

| 指标 | 口径 |
|---|---|
| `install_count` | 被绑定的 Agent 数 |
| `activation_count` | 被投入使用的对话轮次（全文模式=被装配即算，目录模式=仅被 `consult_skill` 取用才算） |
| `description_score` | 0~1，按结构化字段完备度（trigger/guidance/output_format/constraints/examples）推导 |
| `effectiveness_score` | 0~1，由用户 👍/👎 的 **Wilson 95% 下界**推导（小样本保守，大样本趋近真实好评率） |

**为何用 Wilson 下界**：裸好评率会让 1 票好评的 Skill 压过 50 票 96% 的 Skill；下界对小样本保守、排序才稳。被否决：净票数（up−down）忽略基数、不可比。

**闭环**：有效性分数回流到运行时——prompt 组装按有效性给技能排序（目录模式下决定 `consult_skill` 菜单顺序），口碑反过来影响 Agent 的技能偏好。

## 七、Skill 编写规范

> 面向 Agent 构建者（人类或 AI），说明如何编写高质量的 Skill。

### 7.1 Skill 结构

运行时五要素：`name`、`trigger`、`guidance`、`constraints`、`output_format`。

- **name**：唯一标识，consult_skill 按名匹配
- **trigger**：描述何时激活此 Skill（目录模式下作为菜单项展示给模型）
- **guidance**：核心指引——多步操作模板、领域知识、工具协作说明
- **constraints**：禁止事项和行为边界
- **output_format**：期望的输出结构

### 7.2 guidance 编写原则

1. **面向 Agent 写**：读者是 LLM，用祈使句，清晰直接
2. **可操作**：每个子主题包含可执行步骤，而非抽象描述
3. **场景化**：区分不同子场景，Agent 可根据实际问题选择性使用
4. **适度长度**：建议 500-3000 字。过短无价值，过长稀释注意力
5. **工具协作**：步骤应使用特定工具时，在步骤中明确提及工具名
6. **负面约束**：明确列出「禁止」事项，防止 Agent 犯常见错误
7. **不适用场景**：在 trigger 或 guidance 中说明何时不应使用此 Skill，减少误激活

### 7.3 Agent 独有内容 vs Skill

| 归属 | 内容 | 判定 |
|---|---|---|
| `system_prompt` | 身份、不可转移的运作指令 | Agent 独有、不可复用 |
| Skill | 可转移的领域能力 | 可被多个 Agent 复用、可发布到市场 |

### 7.4 质量检查清单

- trigger 明确界定了激活条件和不适用场景
- guidance 包含可操作步骤（非空洞描述），长度 500-3000 字
- constraints 列出常见错误和禁止行为
- 步骤涉及特定工具时已在 guidance 中明确提及
- 与 Agent 的其他 Skills 职责不重叠

## 八、表达形态 vs 创作产物 vs 受控能力 ✅ 已确定

### 8.1 区分原则

Agent 的产出分为三类，分属不同的技术通道：

| 类别 | 通道 | 判据 | 示例 |
|---|---|---|---|
| **表达形态** | LLM 直写代码块 + 前端渲染 | 只影响呈现、无副作用、不留可编辑产物 | 聊天内随手画的思维导图（markmap）、流程图（mermaid）、数学公式 |
| **创作产物** | 用户编辑器（人）＋ Agent 工具（AI），共编同一份持久 artifact | 可持久化、可反复编辑、人与 AI 协同 | 思维导图文档、画布、多维表格、在线文档 |
| **受控能力** | 工具（Tool） | 读写数据、触发副作用、需审计/计费 | 文件读写、数据库操作、HTTP 请求 |

**铁律**：纯可视化表达（无状态）= 直写代码块 + 前端渲染，绝不包装成工具；一旦需要可持久化、可被 AI 跨轮编辑的产物，则升级为「创作产物」——由 Agent 工具读写、走产物/文件体系。同一种形态（如思维导图）因此有两种模式，按"要不要留下可再编辑的产物"二选一。

### 8.2 为什么直写优于工具（表达形态场景）

工具通路用于表达时有 4 个累积失败点：参数 JSON 构造 → 工具执行 → 模型原样复读结果 → 目标格式语法正确。直写代码块消除前三个失败点，且天然支持流式（半截大纲仍是合法大纲，半截 mermaid 是语法错误）。

### 8.3 文本为典范模型

当内容同时被人和多 Agent 协作创作时，**典范模型应为 Markdown 文本**（非富文本 JSON/AST）——LLM 输出文本、本地 `.md` 落盘是文本、AI diff 也是文本。由此推导：

- 文本即真相，编辑器不静默 reflow
- AI 协作一等公民：干净 diff + 可自主写入
- 聊天 AI 输出与编辑器像素级一致（共享渲染核）
- 绝不损坏字节（本地优先隐私 + 内容寻址安全）

### 8.4 创作工具：产物的两副面孔 ✅ 已确定

「创作工具」面向用户，每个对应一种**产物类型**（思维导图 / 画布 / 多维表格 / 在线文档…），与「动作工具」（确定性动作执行器，无可编辑产物）并列、同属"工具"，但产出不同：

- **动作工具**：执行一次确定性动作，不留可编辑产物（`file_read/write`、`grep`、`web_search`、`code_execute`、`delegate`…）。受众主要是 Agent。
- **创作工具**：产出一份可持久化、可反复编辑的 artifact，天生有两副面孔、操作同一份产物：
  - **用户面**：UI 编辑器，用户直接创作 / 编辑。
  - **Agent 面**：该产物类型注册的一组工具（如 `table.add_row` / `canvas.add_node`），让 Agent 协同读写同一份产物。

由此，创作工具这一层**同时向 Agent 的工具集供货**——"Agent 也能用创作工具"不是特例，而是模型的自然结果，无需在"用户工具 / Agent 工具"间立硬墙。

**产物归属**：创作工具产出的 artifact 统一进"产物/文件"体系（见 [前端技术与架构 §8.3](/docs/04-前端/前端技术与架构.md)、后端 `file` / `table` 模块），可被对话 `@` 引用、分享、重开——不另起存储。

**前端表现**：工具箱页为卡片网格（非 Tab）——「AI 工具」一张卡（点开 = 内置动作工具只读目录），思维导图 / 画布 / 多维表格各一张卡（点开 = 该类型产物列表 + 新建）。详见 [前端UX设计 §十二](/docs/04-前端/前端UX设计.md)。
