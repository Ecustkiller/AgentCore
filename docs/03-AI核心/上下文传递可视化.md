> **状态**：worker 侧装配 + `run_context` 事件 + 三端前端「收到的上下文」区 ✅；CEO（captain）侧**通道①**（开场 system/历史/请求 → 回合级 `captainContext` 投影 → CEO 气泡**按需弹窗**渲染 + 重载）✅；**通道⑤**（队员产物回流 CEO 的聚合块，captain 回合内追发 `run_context` 使上下文增长）✅ 已落地。

## 一、核心：单一源 / 双投影（用户看到的 == LLM 吃到的）

一个 worker 的开场 user message **不是**手拼字符串，而是**先产出一份有序的结构化 `ContextBlock` 列表 → 再由列表渲染成 prompt 文本**（每块 `## {heading}\n{body}` 逐段拼接）。同一份列表又随 `run_context` 事件原样流到前端。

于是**一次装配、两个投影**：

```
                 ┌─→ 渲染成 prompt 文本（喂给 LLM）
ContextBlock 列表 ┤
                 └─→ run_context 事件（喂给前端「收到的上下文」区）
```

> **决策理由**：避开「拼给 LLM」与「展示给用户」两条路径各写一遍、再彼此对账的**双写**陷阱（正是 `dev-process` 补丁绊线要躲的接缝）。只要列表是唯一源，「用户看到的」就**恒等于**「LLM 吃到的」，无需任何同步逻辑。

> **被否决**：另起一条「为展示而拼」的格式化路径。它会与真实 prompt 悄悄漂移——展示出来的上下文与模型实际读到的不一致，是比「不展示」更坏的可视化。

## 二、术语澄清：端到端「5 通道」 vs worker `channel` 枚举

设计期讲的「**5 条通道**」指**端到端的 5 个上下文传递路径**；落地后 worker 侧把其中几路展开成了一个 **8 值 `channel` 枚举**（前端按它分桶展示）。二者不是一回事，对照如下：

| 端到端路径 | 含义 | 现状 | 对应 `channel` |
|---|---|---|---|
| ① CEO 输入 | CEO 自身的 system / 历史 / user | ✅ | captain 侧 `system` / `history` / `request`（见 §六） |
| ② 上游产物注入 | 依赖节点产物递给下游 | ✅ | `dependency` |
| ③ 工作区 | 共享工作区可读文件清单 | ✅ | `workspace` |
| ④ 任务装配 | 原始请求 + 团队位置 + 任务书 | ✅ | `request` / `team_position` / `task` / `expected_output` / `requirements` / `steer` |
| ⑤ worker→CEO 回流 | 队员产物聚合回 CEO | ✅ | captain 侧 `team_result`（见 §六） |

**五条端到端路径全量落地**：worker 侧（②③④）+ CEO 侧通道①（开场）与通道⑤（队员产物回流）。

## 三、worker 侧 8 通道（✅ 已落地）

`_build_context_blocks` 按固定顺序产块，每块带 `channel`（UI 分桶）+ `heading` + `body`；`dependency` 块额外带**溯源**（`source_role` / `source_run_id` / `fidelity` / `truncated` / `files`）。顺序即优先级，靠后者覆盖靠前者。

| 顺序 | `channel` | 内容 | 备注 |
|---|---|---|---|
| 1 | `request` | 原始用户请求 | 在团队中时改写为「老板交给整个团队的目标」，避免上游误当个人全权 |
| 2 | `team_position` | 你在团队中的位置（并行队友 + 产出去向） | 仅成队时出现；机制 → 见 [`Agent协作模式.md §二`](/docs/03-AI核心/Agent协作模式.md) |
| 3 | `dependency` | 前置结果（逐个上游产物 + 溯源） | 三保真度见下；机制 → 见 [`编排器与CEO主Agent.md §2.3`](/docs/03-AI核心/编排器与CEO主Agent.md) |
| 4 | `workspace` | 工作区现有文件清单（可 `file_read` 取用） | 去重 + 文件数/字符封顶；同上 §2.3 |
| 5 | `task` | 你的任务 | 必有 |
| 6 | `expected_output` | 预期产出 | 可选 |
| 7 | `requirements` | 产出要求（契约硬指标） | 由 `describe_contract` 渲染 |
| 8 | `steer` | 用户中途调整指示 | 最后 + 最高优先级（`plan_review` adjust 注入） |

> **`dependency` 三保真度**（`pointer` 递指针 / `summarize` 摘要 / `pass_through` 全文带预算）与其预算水填充、首尾保留——是**已有装配机制**，本文不重述，单一真相源见 [`编排器与CEO主Agent.md §2.3`](/docs/03-AI核心/编排器与CEO主Agent.md)。本特性的**新增**只是把它的选择结果（哪种保真度、是否截断、指向哪些文件）**结构化记进块、流到前端**，让「队友产物是怎么递下来的」对用户可见。

## 四、`run_context` 事件与前端呈现（✅）

- **发射时机**：`run_started` 之后、ReAct 循环之前——worker 一开始思考，前端的「收到的上下文」就亮起来。
- **前端折叠**：三端 fold 把 `run_context` 折进 run 帧的 `receivedContext`；桌面 `RunDetailBody` 在「任务」区下方渲染 `ReceivedContextSection`（每块一张可展开卡片，`dependency` 卡额外显「来自 {角色} · 保真度 · 是否截断」+ 指向文件）。
- **入口**：run 详情区段顺序 = 头部 → 任务 → **收到的上下文** → 思考过程 → … → 资源消耗（→ 见 [`../04-前端/前端UX设计.md §十`](/docs/04-前端/前端UX设计.md)）。

## 五、四个设计决策（①–④）

| 决策 | 取值 | 现状 | 说明 |
|---|---|---|---|
| ① 是否进 journal | **进**（`_JOURNAL_EVENT_TYPES`） | ✅ | 历史回合重载时，每个 worker 收到的上下文随团队图一起回放——经同一 fold，实时与回放一致。配套 ④ 截断保证 journal 不膨胀 |
| ② 是否暴露 CEO system prompt | **桌面按需弹窗对所有人可见 / 手机恒隐藏** | ✅ | 桌面 CEO 气泡的「收到的上下文」改为 hover 操作行的**按需弹窗**（`ReceivedContextDialog`），弹窗内 `system` 块**对所有人可见**——「按需」消解了信息过载顾虑、逐字提示词本就允许用户打开，故此面**并入了原独立「提示词」按钮**（其内容 == `system` 块）、并**退役** `powerMode` 门控。手机仍内联（`AssistantView`）、无 `用量明细` 开关，故 `system` 在手机端恒隐藏；worker 侧 `RunDetailBody` 仍内联且本无 `system` 块 |
| ③ 是否分级展示 | **分级**（worker 详情复用「用量明细」开关） | ✅ | worker 详情区：大众默认折叠看摘要，Power（`usageDetail` 开）默认展开看全文 + 字数 + 形态——卡片 `defaultOpen` 跟随 `powerMode`，避免大众被原始上下文淹没。CEO 气泡弹窗内卡片**恒默认折叠**（按需弹窗已是显式动作，由用户逐块展开） |
| ④ 单块正文上限 | `DEP_CONTEXT_BUDGET` 量级，首尾保留（`system` 块豁免） | ✅ | **prompt 喂 LLM 的是全文**；只有**事件/journal 这一份投影**按 `_CONTEXT_BLOCK_BODY_CAP` 首尾截断、置 `truncated`，并以 `chars` 记原始长度——一段超长粘贴的请求不会撑爆 journal，且 UI 明示「已截断」。**例外**：captain `system` 块**豁免此上限、恒全文**——它是有界的内部系统提示，且桌面「收到的上下文」弹窗已并入原「提示词」按钮、需逐字呈现，非该上限要防的无界用户/依赖正文（见 `_context_block_payloads`） |

> ④ 是「单一源」的诚实边界：列表 / 顺序 / heading 两投影完全一致，仅**事件投影的 body** 为护 journal 做了**有标记**的截断。这不破坏「用户看到的 == LLM 吃到的」，因为截断对用户**显式可见**（`truncated` + 原始字数）。

## 六、CEO（captain）侧通道①（开场）+ ⑤（队员回流）（✅ 已落地）

### 通道①：CEO 开场上下文 → 回合级 `captainContext`（✅）

captain（CEO 主 Run）开跑后**同样产 `ContextBlock` 列表、发 `run_context`**（`_build_captain_context_blocks`），三通道按序：

| 顺序 | `channel` | 内容 |
|---|---|---|
| 1 | `system` | 本回合 CEO 实际遵循的系统提示（**决策②**：桌面按需弹窗对所有人可见、手机恒隐藏） |
| 2 | `history` | 本回合之前的往来（`_format_captain_history` 渲染为「用户：… / CEO：…」——与喂给 LLM 的同一批 turns，单一源）；首回合省略 |
| 3 | `request` | 本回合用户请求 |

**关键决策：回合级投影，不是图节点。** captain 是团队图**之上**的气泡（纯对话回合根本没有图），因此其 `run_context` **不**落到某个图节点的 `receivedContext`，而是按 `kind=captain` 在三端 fold 中**分流**到回合级 `captainContext`（`ProjectedTurn.captainContext` / `Message.captainContext`）：

- **为何不复用节点**：captain 在纯对话回合不发 `run_plan`、无图可挂；若强行造节点会破坏「单/多 Agent 渲染边界」。回合级投影让 CEO 上下文在**纯对话与多 Agent 两种回合都可见**，且不动既有图不变量。
- **三端分流**：fold 先认下 `run_started kind=captain` 的 run id，再把该 run 的 `run_context` 收进 `captainContext`（其余 worker `run_context` 仍折到节点）。桌面 CEO 气泡经 hover 操作行的 `ReceivedContextDialog`（`components/chat/ReceivedContext.tsx`）**按需弹窗**呈现——不再随回合内联自动展开；同文件的 `ReceivedContextSection` 仍由 worker 详情区 `RunDetailBody` 内联复用。手机 `AssistantView` 维持内联。
- **重载打通**：回合级数据不随团队图走，故**单独持久化**——纯对话回合的 captain 块从 journal 的 `run_context` 事实单独回抽进 `RunsPayload.captain_context`（否则空 runs 载荷被 None 门挡掉、不落 journal），客户端读回 `message.captainContext`；实时经 `streamConversation` 落气泡。

> **resume 不重发**：续写在全新 sink 上跑，开场上下文已随挂起前段落表达过，故 resume 路径传 `received_blocks=None`——captain 不再发 `run_context`，避免重复。

### 通道⑤：worker→CEO 回流聚合（✅）

委派的队员跑完后，**它们交回 CEO 的产物**也进 CEO 气泡的「收到的上下文」——captain 在回合内**再发一次 `run_context`**（channel `team_result`），其上下文随团队产物**增长**而非被覆盖。

- **单一源（不双写）**：`delegate/tool.py` 把每个队员产物折回 CEO 的逻辑抽成 `_worker_products`（按共享保真度纪律定型：落盘者递摘要/指针、纯文产物共享一份注水预算），`_format_for_ceo`（喂给 CEO LLM 的综述输入）与本通道**读同一份 `products`**——用户看到的回传 == LLM 此处实际读到的。每块带来源角色 / 保真度 / 是否截断 / 文件产出（与依赖块 ②同样的溯源展示）。
- **追发时机与归属**：仅顶层批次（`depth==0` 且有真实 captain run id）由 `_emit_captain_readback` 发；嵌套子团队的回流喂的是它的 worker-captain（其 run 是 `kind=agent`，会折到节点而非回合级），故跳过。run id 用 captain 自身 → 三端 fold 按 `kind=captain` 分流到回合级 `captainContext`。
- **三端 APPEND**：开场（①）与每次回流（⑤）的 captain `run_context` 在三端 fold 与重载一律**追加**到 `captainContext`、不覆盖。桌面实时态按会话累加后整列 REPLACE 落库、并在 `message_start` 清零——故重连重放幂等、不翻倍。

## 七、跨端一致性（conformance）

本特性是协议 fold 的危险面（SSE → 状态），靠巡检兜漂移：

- `multi_agent_received_context`：worker `run_context` 三通道 + 依赖块溯源/保真度。
- `single_agent_captain_context`：纯对话回合，captain `run_context` → 回合级 `captainContext`。
- `multi_agent_captain_context`：多 Agent 回合，captain 上下文走回合级（captain 节点 `receivedContext` 恒空）+ worker 折到节点；并含**通道⑤ 回流**——worker 跑完后 captain 追发 `team_result` `run_context`，三端必须 APPEND 到 `captainContext`（开场之后）而非覆盖。

后端 oracle（`conformance/projection.py`）产 golden，桌面 / 手机 fold 跑同向量断言 `== golden`。改任一端 fold 或后端投影 → `uv run python -m agentcore.conformance.export` 重生 golden 后必跑 `pnpm conformance`。机制见 [`protocol-conformance.mdc`](/.cursor/rules/protocol-conformance.mdc)。
