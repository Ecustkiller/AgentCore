# 执行引擎内部架构设计

> **状态**：已确定方向

---

> **现状**：多 Agent 编排 = CEO 在 ReAct 循环里调 `delegate` → `runtime/runs/`（`build_run_plan` + `WaveScheduler`）。§十二~§十四 为已落地运行时；§十五~§十七 为设计方向；§十八 为目标模型（Interaction / Turn Journal / Run）。→ 见代码：`runtime/pipeline.py`、`runtime/runs/`、`runtime/engine.py`

## 核心定位

执行引擎是 CEO 主 Agent 与 worker 实例之间的调度中枢。它接收 CEO 经 `delegate` 下达的子任务（`build_run_plan` 据 `depends_on` 建 DAG），解析依赖图，管理 worker 生命周期，协调并行/串行执行，处理失败与取消，并向 UI 推送实时状态更新。

---

## 一、基础概念（DAG 调度，早期设计）

> DAG 调度概念提要；运行时以 §十二~§十四 为准，§十八 为目标模型。→ 见代码：`apps/server/agentcore/runtime/`（`runs/`、`engine.py`）。以下只保留代码看不直观的设计约定。

### 步骤状态与调度

计划是 DAG：每个 step 声明 `depends_on`，执行引擎扫描「依赖已满足且未启动」的 step 并发启动（受 `max_parallel` 限制）。步骤状态 `queued → running → completed`，异常分支 `failed` / `skipped`（枚举见 `runtime/runs/types.py` 的 `RunPhase`；失败重试由 `RunPolicy.on_failure=retry` 在 `runs/wave.py` 内部完成（硬上限 3 次退避），对外仍以 `FAILED` 收口并 emit `run_failed`）。并发模型为 asyncio 协程——多 Agent = 多 asyncio Task 共享事件循环（Agent 本质是 I/O 密集的 LLM 调用，协程足够）。

### 检查点决策语义

step 完成若带 `checkpoint_after`，则暂停调度、等待用户决策（`approve` / `adjust` / `stop`）。

> **实现现状**：DAG 检查点（`checkpoint_after` + 用户 `approve`/`adjust`/`stop`）为**目标态**——当前 `WaveScheduler` 不含；待 Phase 2 以 preflight / contract / `ask_user` 回归。
>
> **勿与工具审批混淆**：`approval_required` / `approval_resolved` SSE 事件**不是**检查点，而是**工具审批闸门**（GRANTABLE 工具暂停待用户授权），已落地并在 CEO 路径生效（→ 见代码 `runtime/approvals.py` 的 `ApprovalGate`、`engine._execute_tools`；按 `settings.approval_gate_enabled` 开关，worker 委派路径不 gate）。审批语义见 [`../05-平台与运维/安全权限与治理.md` §三](../05-平台与运维/安全权限与治理.md)。

### 失败与取消

可重试错误（超时 / 429 / 5xx）退避重试；不可重试错误跳过该 step 或升级用户；关键 step 失败时取消传播到所有下游依赖。完整收敛治理（重试 / 熔断 / 早停 / 反思）见 §十四。

### 性能约束

| 指标 | 目标值 |
|---|---|
| 最大并行 Agent | 10（`max_parallel`） |
| 最大步骤数 | 20 |
| 事件传播延迟 | < 50ms |

### Agent 间产物传递

每次执行在调度器内持有各 worker 产物，供下游依赖注入读取。

> **实现现状**：`WaveScheduler.completed[run_id]` 持有各节点 `RunState`，下游按 `depends_on` 取上游 `RunState.content`（按 `result_handling` 全文 / 摘要）。→ 见代码 `runs/wave.py`、`runs/executor.py`。计划热修改由 CEO 多次调 `delegate` 增量追加（§十八 `adaptive`）。

## 十二、SSE 事件协议 ✅ 已确定

后端 → 前端的实时通信采用 SSE（Server-Sent Events），定义标准事件类型。

### 事件清单

| 事件 | 触发时机 / 语义 |
|------|---------------|
| `message_start` | 助手回合开始 |
| `content_delta` | 文本增量 |
| `reasoning_delta` | 推理增量（思考模式） |
| `tool_use_start` | 工具开始执行 |
| `tool_use_end` | 工具执行完成 |
| `approval_required` | ✅ 工具审批闸门：GRANTABLE 工具暂停待用户授权（CEO 路径；worker 委派路径不 gate） |
| `approval_resolved` | ✅ 审批落定（approve / approve_always / deny；超时=deny），前端清除内联提示 |
| `ask_user_requested` | ⏳ 未实现 |
| `run_plan` | 预声明一批 run 节点（DAG 规划完成时） |
| `run_started` | 一个 Agent run 开始（编排步骤与子 Agent 的统一节点） |
| `run_output_delta` | run 自身答案文本增量 |
| `run_reasoning_delta` | run 自身思考链增量（worker 思考全文，run 级归属，与 `run_output_delta` 对称） |
| `run_completed` | run 成功完成 |
| `run_failed` | run 失败 |
| `run_retrying` | ⏳ 未实现 |
| `run_progress` | 一批 run 的聚合进度 |
| `task_state_updated` | ⏳ 未实现 |
| `pipeline_summary` | ⏳ 未实现 |
| `message_end` | 回合结束（含 `finish_reason` / usage） |
| `error` | 不可恢复错误 |
| `title_generated` | 会话标题生成 |
| `citations` | 本回合聚合去重的网页来源（`web_search`/`read_url`），emit 于 `message_end` 前；前端渲染为来源卡片并随消息持久化。单 Agent 聊天路径额外在 system prompt 注入引用规范（`prompt.py` 的 `CHAT_CITATION_HINT`），让模型在正文按首次出现顺序输出 `[n]` 角标，前端解析为可点击芯片高亮对应卡片；团队 worker 不注入（其输出会被 captain 聚合/再加工，编号会错位）|

### finish_reason 枚举

| 值 | 含义 |
|---|---|
| `end_turn` | 正常完成 |
| `max_rounds` | 达到最大轮次限制 |
| `degraded` | LLM 连续返回空响应（⏳ 枚举已定义于 `FinishReason.DEGRADED`，当前未 emit） |
| `error` | LLM 不可恢复失败 |
| `cancelled` | 手动取消或断开 |

### 契约生成策略

> **实现现状**：⏳ 未接入 CI。`.github/workflows/ci.yml` 当前仅 ruff + pytest + 前端 lint/test，无 dataclass→TS 自动生成与 `git diff` 门禁。

后端是 SSE 类型的唯一真相源。目标做法：
- 后端用 dataclass 定义每个事件的 payload schema（声明 = 构造同一对象，杜绝漂移）
- 由脚本反射 dataclass 自动生成前端 TypeScript interface
- CI 门禁：重跑生成器 + `git diff --exit-code`，拦契约漂移

## 十三、执行管线全貌 ✅ 已确定

> 从 HTTP 请求到 SSE 输出的完整后端调用链。

### 端到端流程

```
POST /v1/conversations/{conv_id}/messages
│
├─ router.send_message
│   └─ ConversationService.stream_chat
│       ├─ 落用户消息 + load_history(max_messages=40)
│       └─ ChatPipeline.run_chat_pipeline（仅 Prepare + Execute）
│           ├─ [Prepare]  → 上下文（system prompt / 工具 / 历史）
│           └─ [Execute]  → SSE 事件流 (EventSink → asyncio.Queue)
│       ├─ [Finalize] 助手消息落库 + 标题生成 + 记忆维护（在 service 层，非 pipeline）
│
└─ StreamingResponse → Client SSE
```

### Phase 1: Prepare

将 HTTP 请求转化为执行上下文（在 `ChatPipeline.run_chat_pipeline` 内）：

1. 认证 + 校验对话归属（`stream_chat` 层）
2. `assemble_system_prompt` 组装 system prompt（注入用户长期记忆 markdown）
3. 固定注册 **8 个内置工具**（`web_search` / `read_url` / `file_read` / `file_write` / `str_replace` / `file_list` / `grep` / `code_execute`）——非按 Agent opt-in / `AgentResolver` 动态解析（`AgentResolver` 为 Phase 2 方向，尚未承载）
4. 单 Agent 路径固定 `get_profile("chat")`；**无 `classify_task` 复杂度分级**
5. `model_preference`（fast/strong 两档）**仅多 Agent 步骤**经 `agent_profile()` 映射生效
6. 历史由 `stream_chat` 调用 `load_history(max_messages=40)` **按条数截断**（非 40% token 预算）
7. CEO 直接进 ReAct 循环，工具集 = 8 内置工具 + `delegate`；需分工时由 CEO 自行调 `delegate`（→ 见代码 `runtime/pipeline.py`）

**产出**：执行上下文（system_prompt、tools、history、plan）

**历史重建原则**：只回放 user/assistant 文本。工具 I/O 与委派详情属展示遥测（持久化供前端详情面板），不回放进 LLM 上下文——避免跨轮累积烧 token、撑爆窗口。

### Phase 2: Execute（ReAct 循环）

见 §十四 详述。

### Phase 3: Finalize

> **实现现状**：Finalize **不在** `ChatPipeline` 内；由 `conversation/service.py` 的 `stream_chat` 在 pipeline 返回后执行（→ 见代码）。

- 落库助手消息（content + usage metadata）
- 首条对话标题生成（`title_generated` SSE）
- 长期记忆维护（`maintain_user_memory`）
- ⏳ 无 CostEvent 记账、无 Turn 表、无长对话摘要归档

**断连收尾契约**：各步骤独立 `try/except`，失败只 warning，不中断已完成的 SSE 流。刻意「能存多少存多少」而非全有或全无——用户已离开，保住已产生的消息比元数据一致性更重要。

### Trace 关联

> **实现现状**：⏳ `trace_id` 跨链路与 NATS 未实现。

一次用户交互跨多个执行上下文（HTTP、后台 worker、委派 worker）。目标：用统一 `trace_id` 作关联键，在管线入口铸一次，随 NATS payload 流到 worker。排查时 `grep trace_id=<id>` 即得全链路。

## 十四、ReAct 循环与收敛治理 ✅ 已确定

> **实现现状**：`engine.react_loop` = 轮次上限（`ModelProfile.max_rounds`）+ LLM provider 层 3 次重试（`llm/deepseek.py`，429/5xx/timeout）+ **收敛治理 `LoopController` 已接入**（重复调用 / A-B-A-B 交替 / 重复失败的滑窗检测 → 两段式 `NUDGE` 反思注入 / `FINALIZE` 强制收口）。仍缺：引擎级 fallback 模型、工具 30s 超时、`FinishReason.DEGRADED`（枚举存在但未 emit）、结构化 `RoundOutcome`/`LoopDirective` 协议。**工具审批已在执行层生效**：`engine._execute_tools` 对 `GRANTABLE` 工具经 `ApprovalGate` 挂起待授权（CEO 路径，按 `settings.approval_gate_enabled`；worker 委派路径不 gate；→ 见代码 `runtime/engine.py`、`runtime/approvals.py`）。

### 基本循环

`message_start` 后逐轮迭代至 `profile.max_rounds`：

1. **构建消息**（system + history + user，无 `trim_history_smart`）
2. **调用 LLM**（provider 层 3 次重试；⏳ 无引擎级 fallback 模型）
3. **执行工具调用**（并行 ≤5；✅ GRANTABLE 工具审批挂起[CEO 路径]；⏳ 无 30s 超时）
4. 有正文且无工具调用 → `end_turn`；超轮 → `max_rounds`

✅ `LoopController` 判定已接入（见下文）；⏳ 轮顶查取消、工具效应模型等为目标态。

### 收敛治理（LoopController）

> **实现现状**：**部分落地**。`loop_controller.py` 已实现并接入 `react_loop`：滑窗检测三类机械循环（重复调用 / A-B-A-B 交替 / 重复失败）→ 两段式干预（首次 `NUDGE` 注入锚定「观察到的重复事实」的反思，再次 `FINALIZE` 强制无工具收口）。下表为完整目标机制，其余行（fallback 模型 / 空响应 degraded / 工具 30s 超时 / 结构化 `RoundOutcome`·`LoopDirective` 协议）仍为目标态。

所有「循环要不要继续」的判断统一收敛到 LoopController，引擎每轮交结构化 `RoundOutcome`，按 `LoopDirective` 行动：

| 机制 | 阈值 | 行为 |
|------|------|------|
| LLM 重试 | 3 次指数退避 | 仅 429/5xx/timeout |
| Fallback 模型 | 主模型耗尽 | 切 fallback_model，裁剪 system prompt |
| 工具失败熔断 | 累计失败 2/3 次 | 2 次提示勿重试；3 次本轮停用 |
| 无产出早停 | 连续 3 轮全失败且无正文 | `finish_reason=unproductive` |
| 重复调用检测 | 相同签名连续 3 轮 | 注入「换策略」提示 |
| 反思注入 | 第 4 轮起每 3 轮 | 注入进度复盘 prompt |
| 空响应 | 连续 2 轮 | `finish_reason=degraded` |
| 工具超时 | 30s | `[ERROR]` 前缀返回 |
| 协作取消 | CancellationToken | 沿委派树向下传播 |

### SSE 桥接

执行侧与输出侧经**无界 `asyncio.Queue`** 解耦。背压只对可丢弃事件（`content_delta` / `reasoning_delta`）生效，生命周期/终止事件保证送达。

**前端兜底对账**：消息落定时递归收口所有悬挂的 running/queued run 节点——后端可靠送达是主路径，前端对账是 last-resort 兜底。

### 暂停与恢复（第三终态）

> **实现现状**：⏳ Post-MVP / 未实现。挂起恢复（Suspend）为 Phase 2 方向，尚未承载；无 `paused` 终态、无 `POST /resume` 路由。

在 `completed` / `cancelled` 之外引入 `paused`——不 finalize、状态落盘、可重建续跑。

- **进入条件**：显式暂停 / 停止且已跨≥1个完成轮次边界
- **快照缝**：ReAct 轮顶是唯一干净快照点（history 满足消息配对不变量）
- **恢复**：经 `POST /resume` 开新 SSE、从断点续跑
- **计费**：暂停即计费（无清道夫），resume 段只计自己

## 十五、工具装配策略 ✅ 已确定

> **实现现状**：MVP 在 `tools.builtin.build_builtin_registry()` 固定注册 8 个内置工具，非按分类 opt-in 装配。`ToolCategory` 实际为 `FILESYSTEM` / `SEARCH` / `EXECUTION` / `RESEARCH` / `ORCHESTRATION`（末项为 CEO 的 `delegate` 专用，不在上述 8 个内置工具内；→ 见代码 `core/types.py`）。`engine._execute_tools` 执行时对 `GRANTABLE` 工具经 `ApprovalGate` 拦截挂起（CEO 路径，见 §十四）。

### 全部 opt-in，无默认档

内置工具全部 opt-in：Agent 在 `tools` 中声明分类或工具名才加载。没有「对所有 Agent 默认发放」的 core 档——能力是刻意声明、不靠隐式继承。（⏳ MVP 暂未按此装配，见上。）

### 分类即工具包

| 分类（目标态） | 包含工具 |
|------|---------|
| `web` | web_search, read_url, rss_fetch, read_document |
| `text` | text_diff, structured_extract |
| `dev` | code_execute, http_request, sql_query |
| `productivity` | table, reminder |

**MVP 实际分类**（`ToolCategory`）：`filesystem`（file_read/write/list/str_replace/grep）、`execution`（code_execute）、`research`（web_search/read_url）；`search` 分类暂未使用。

### 工具来源统一审批

审批门与工具来源无关：内置/市场/连接器工具在执行层只认 `ToolBinding.approval` 一个字段，任意来源的高风险工具接入同一审批流。（⏳ MVP 执行层未拦截，见 §十四 `实现现状`。）

### 时间即上下文

当前日期时间不走工具，由 PromptAssembler 追加到 system prompt 末尾的 `<runtime_context>` 块。省一次工具往返，LLM 永远「知道现在」。

## 十六、任务分级与模型选择 ✅ 已确定

> **实现现状**：⏳ 无 `classify_task` 任务复杂度分级启发式。单 Agent / 默认回复固定 `chat` profile（`pipeline.py`/`engine.py`）；多 Agent 步骤的 `model_preference`（仅 `fast`/`strong` 两档）经 `agent_profile()` 映射到 `agent.fast` / `agent.strong`（→ 见代码 `llm/config.py`、`runtime/runs/executor.py`）。

### 档位与轮数预算

`classify_task`（按复杂度自动选档）为纯启发式设计，**⏳ 未实现**；当前 worker 档由编排器 `model_preference` 直接给出（仅 fast/strong 两档）。各 profile 实际轮数预算（`llm/config.py`）：

| profile | 轮数预算 | 模式 |
|------|---------|--------|
| agent.fast | 4 轮 | 非思考（简单/机械子任务） |
| chat | 16 轮 | 思考 high（单 Agent / 默认回复） |
| agent.strong | 28 轮 | 思考 high（复杂子任务） |

### 模型选择优先级

```
请求级显式模型 > 创作者 pin 的具体模型 > "auto"（按分级） > 角色默认档 > 全局默认
```

- 只有显式 `"auto"` 才走分级，默认尊重创作者 pin
- **角色默认档**：编排者走强档，叶子 Worker 走便宜档（判据：是否还持有委派目标）
- 未配置即 no-op，对存量零影响

## 十七、提示词架构 ✅ 已确定

### 两个互不相交的世界

| | World A — Agent 主提示词 | World B — 内部工具型提示词 |
|---|---|---|
| 是什么 | 面向用户的对话 Agent system prompt | 平台内部的窄任务 LLM 调用（标题/分类/摘要…） |
| 触发者 | 每个 Agent、每个 turn | 平台代码按需 |
| 形态 | 身份 + 技能 + 规则 + 上下文，条件装配 | 固定模板 + 少量变量，单次调用 |
| 管理方式 | PromptAssembler | 注册表 + 片段库 |

**分离原因**：两者关注点根本不同。强行共用只会互相拖累。

### World A：PromptAssembler 组装顺序

```
Agent system_prompt
  + Skills（workflow 全文 / catalog 目录）
  + Rules — 统一行为层（XML <rules>，按 priority 降序）
  + Workspace Context（RAG 检索 + 文件清单）
  + <runtime_context>（时间等运行时信息）
```

缓存：无 workspace_ctx 时按 agent_id 实例内缓存。
降级模式：低优先级规则过滤、文档截断、Skills 裁掉；Rules 保留（安全/合规约束越降级越要留）。

> **实现现状（提示词正文，统一中文）**：基座（`_DEFAULT_SYSTEM_PROMPT`）确立 AgentCore 身份与「结论必须基于工具实际返回、绝不编造」原则；CEO 在基座上叠加 `CHAT_TEAM_CAPABILITY_HINT`（`<role>` 团队管理者身份 + `<how_you_work>` 该做/不该做边界）与 `CHAT_CITATION_HINT`（引用规范）；worker 由 `runs/executor.py` 在共享基座上叠加「一次性、隔离上下文、不能反问、不能再委派」自我认知段，再接角色/目标——因 worker 拿不到完整对话、无澄清回路，须明确「信息不足就合理假设并交付」。→ 见代码 `runtime/prompt.py`、`runs/executor.py`。

### World B：注册表 + 片段库

解决「内部 LLM 调用散落在 N 个文件，每个内联硬编码字符串」的问题。

| 模块 | 职责 |
|------|------|
| `PromptTemplate` | key / system / user / temperature / max_tokens / version |
| `fragments` | 可复用静态片段（通用约束词 + 拼装型静态块） |
| `registry` | 进程级注册表，按 key 取/渲染，重复 key 报错 |
| `catalog` | 所有系统级模板的单一真相源 |

关键约定：
- key 命名 `component.task`（如 `conversation.title`）→ 可观测
- `{{var}}` 渲染（双花括号变量，单花括号 JSON 示例原样存活）
- fragments 是 opt-in 字符串，不强制全局前缀

## 十八、运行时核心模型 ✅ 已确定

> **实现现状**：本节为**目标模型**。Journal / Suspend / Resolve 为 Phase 2 方向、尚未承载；**收敛治理 `loop_controller.py` 已落地并接入**。CEO+delegate 路径当前无交互挂起（非 Redis BLPOP）；持久化走 `conversation/service.py` 消息表，非 Turn Journal。

> 运行时收敛在三个一等模型上。每个模型把一族重复子系统坍缩成单一形状。

### 18.1 三模型总览

| 模型 | 职责 | 解决的问题 |
|------|------|-----------|
| **Interaction** | 唯一挂起原语：server 停下等 client 回值 | 统一审批/ask_user/本地工具/计划评审四套同构 BLPOP |
| **Turn Journal** | 唯一回合事实源：append-only 事实流 | 消除「回合无事实源」导致的历史回放/快照/消息完整性补丁族 |
| **Run** | 唯一执行单元：一棵 Run 树 | 统一委派/DAG/编排/路由四套并存的编排子系统 |

依赖关系：Interaction 最小独立；Journal 是 Run 的地基（事实留痕在 journal）；Run 落在两者之上。

### 18.2 Interaction（统一挂起原语）

> **实现现状**：当前 CEO+delegate 路径**无挂起原语**；统一 Interaction 原语（Redis BLPOP 跨进程等待）为目标态。

```
InteractionRequest:
  id            # 请求-响应关联键
  kind          # approval | ask_user | client_tool | plan_review
  conversation_id / turn_id / run_id
  payload       # 各 kind 的请求体
  timeout_s
  scope         # call | turn（「本轮内都允许」语义泛化到原语层）
```

一套机制替换四套：统一等待器、统一挂起登记（`list_pending`）、统一恢复端点、统一回值端点。per-kind 差异降为策略位（durable / 键粒度 / at-rest 脱敏）。

### 18.3 Turn Journal（唯一事实源）

每个 turn 一条 append-only 条目流（主键 `turn_id + seq`），九类事实：

```
kind ∈ turn_started | round_boundary | llm_call | tool_call | interaction
      | note | run_event | message_final | turn_end
```

**一切皆投影**：

| 消费面 | 来源 |
|--------|------|
| SSE 流 | 引擎实时 emit（流式增量不入 journal） |
| 持久化消息行 | journal 投影器生成 |
| 暂停快照 | `round_boundary.fold` |
| 跨轮历史回放 | 文本 + interaction 答案投影 |
| LLM 窗口 | journal 投影（correct-by-construction） |

### 18.4 Run（唯一执行单元）

执行形状不再是离散「模式」而是数据，由 `depends_on` 边自然落定：

- 单 Agent = 单节点
- `fan_out` = 单波 + synthesis 终点
- `pipeline` = 线性链 + synthesis
- `adaptive` = 空计划 + captain 动态追加
- 单次 delegate = 追加一个节点
- ARENA best-of-n = 某节点 `candidates>1`

### 18.5 引擎纯化

三条去特判手段：

1. **工具效应模型**：`ToolResult(text, effect)`，`effect ∈ Continue | Handoff | Interact`。引擎只解释效应，`delegate`/`ask_user` 不再是特殊名字
2. **显式 ToolContext**：工具签名携 context（user/conv/turn 等），消灭 `set_runtime_context` 全局大杂烩
3. **去工具名特判**：引擎按能力位（`has_delegation_tool` 等）而非工具名判断行为

### 18.6 端口契约（宿主注入）

引擎面向宿主的 10 项端口（本地/云端同码、宿主注入）：

| 端口 | 定位 |
|------|------|
| Journal | 引擎唯一持久化出口 |
| EventSink | 渲染流出口（流式增量 + 离散事实实时投影） |
| InferenceGateway | LLM 调用 |
| ArtifactStore | 归档/寻回 |
| PauseSignal | 暂停信号（Redis flag） |
| ClientRequestBridge | 统一挂起原语的 4 类 kind |
| ConversationStore | 消息持久化（投影写入） |
| BillingSink | 计费事实投影 |
| DelegationTransport | 跨进程子树传输 |
| SnapshotStore | 已被 Journal 吸收 |

### 18.7 一轮一网关（Gateway 传播原则）

当用户自带 LLM 凭据时，整棵多 Agent 委派树必须在**同一把网关**下运行，避免 split-brain（队长跑用户 key，委派出去的子 Agent 回落平台 key）。

**规则**：在 Turn 最早阶段（工具装配之前）一次性解析 `effective_gateway`，随 Run 上下文贯穿整棵执行树。`InferenceGateway` 端口接收的凭据由此确定——直答、团队编排、恢复各路径读同一把。

此原则与凭据来源开关无关（无论平台供还是用户供），是执行语义的不变量。
