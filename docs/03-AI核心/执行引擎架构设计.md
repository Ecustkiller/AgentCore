## 核心定位

执行引擎是 CEO 主 Agent 与 worker 实例之间的调度中枢。它接收 CEO 经 `delegate` 下达的子任务（`build_run_plan` 据 `depends_on` 建 DAG），解析依赖图，管理 worker 生命周期，协调并行/串行执行，处理失败与取消，并向 UI 推送实时状态更新。

## 一、基础概念（DAG 调度）

> DAG 调度概念提要；运行时以 §二~§四 为准，§八 为目标模型。以下只保留代码看不直观的设计约定。

### 步骤状态与调度

计划是 DAG：每个 step 声明 `depends_on`，执行引擎扫描「依赖已满足且未启动」的 step 并发启动（受 `max_parallel` 限制）。步骤状态 `queued → running → completed`，异常分支 `failed` / `skipped`（枚举见 `runtime/runs/types.py` 的 `RunPhase`；失败重试由 `RunPolicy.on_failure=retry` 在 `runs/wave.py` 内部完成（硬上限 3 次退避），对外仍以 `FAILED` 收口并 emit `run_failed`）。并发模型为 asyncio 协程——多 Agent = 多 asyncio Task 共享事件循环（Agent 本质是 I/O 密集的 LLM 调用，协程足够）。

> **调度埋点量化 ✅**：为验证连续调度「让并行真正发生」（而非凭感觉），`WaveScheduler.run` 每次 run 回灌一条 `BatchMetrics`——并发峰值 / 平均并发度（`busy_ms÷wall_ms`）/ 槽位饥饿 / 按 reason 拆的边界 fire 数 / escalation 计数等（无晚绑定·escalation·checkpoint 的 plan 全为 0）。**设计取舍**：用 `metrics_sink` 而非返回值或直接打日志——调度器对宿主无感、cancel 路径不回灌（先 re-raise）；由宿主 `delegate` 的 `drive` 取回并打 `delegate.completed` 结构化日志（含 `avg_parallelism` / `scope_ratio`）。→ 见代码：`runtime/runs/wave.py`、`runtime/runs/types.py`（`BatchMetrics` 全字段）、`tools/builtin/delegate/drive.py`。

### 检查点决策语义

> **本篇权威**：检查点 / `plan_review` / 2b 续跑语义以本节与 §暂停与恢复 为准；编排器、协作模式等文档仅外链此处。

检查点分两类，**实现现状不同**：

- **CEO `ask_user` 检查点（✅ 已落地）**：CEO 主动调内置工具 `ask_user` 暂停回合征询用户——CEO **唯一的发问原语**（开场引导与途中拍板共用一卡一机制）。语义、字段与阻塞/非阻塞矩阵见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)。载 `message`（必填）+ 可选 `context` / `assumptions` / `questions` / `style_options`；桌面端以提交/停止两态作答，答复回流 CEO ReAct 循环；`stop` 走 `ToolResult.terminal` 优雅收口。**挂起即收口（②）**：到达检查点即**落帧并收口终止**（`ToolEffect.SUSPEND → FinishReason.PAUSED`，进程内 resolve Future 永不 park），经**单一冷路** `POST …/resume` 续跑——不再 `POST …/interactions` 原地解析；问答入 journal 可回放。属 `ToolCategory.INTERACTION`（非 ORCHESTRATION），仅在 `settings.checkpoint_gate_enabled` 且有交互用户时装配，worker 路径不给。
- **DAG `checkpoint_after` 结构化挂起（✅ Phase 2a 已落地）**：step 带 `checkpoint_after` 且 `COMPLETED`、下游仍待跑时，`WaveScheduler` 在波间 `await` `plan_review` 交互（`kind=plan_review`，continue/adjust/stop——adjust 把备注作为 steer 注入未跑下游的 `RunSpec.steer`、由 executor 渲染为最高优先级指示块；stop/abort 后未跑尾部统一标 `SKIPPED`）；**挂起即收口（②）**：检查点在波边界**落帧并收口终止**（`SUSPEND→PAUSED`），不再 `POST …/interactions` 原地解析，且**仅顶层 `depth==0` 设检查点**（嵌套子团队直接放行）；事件 `plan_review_required`/`plan_review_resolved` 入 journal 可回放；前端见 [`前端UX设计.md` §三/§五](/docs/04-前端/前端UX设计.md)。**✅ 2b 已落地**：turn 级落盘（`paused_turns` 帧）+ `POST …/resume` 续跑（**纠正设计：不加** `RunPhase.PAUSED` 第三终态，回合级落盘，见 §暂停与恢复）。⏳ 余项：跨进程 Redis（多 worker）+ 治理强制层（声明即必停、非 CEO 自声明，见 [`../06-规划/远期规划.md` §2.3](/docs/06-规划/远期规划.md)）。

> **勿与工具审批混淆**：`approval_required` / `approval_resolved` SSE 事件**不是**检查点，而是**工具审批闸门**（GRANTABLE 工具暂停待用户授权），已落地（按 `settings.approval_gate_enabled` 开关）。CEO 自身不持 `GRANTABLE` 工具，故实际在**本地模式 worker** 层生效（worker 继承 CEO 门，双模式 P2d），云端 worker 不 gate（隔离沙箱）。审批语义见 [`../05-平台与运维/安全权限与治理.md` §三](/docs/05-平台与运维/安全权限与治理.md)。审批 / 本地工具 / worker 升级 / 辩论轮共用 `runtime/interaction.py` 的 `InteractionRegistry`（§8.6 ClientRequestBridge）同构挂起-恢复，单一 resolve 端点 `POST …/interactions/{id}`（按 kind 判别）；**`ask_user` / `plan_review` 检查点已挂起即收口（②）**——改走 `POST …/resume` 冷路、其 resolve schema 已从该端点移除。

> **开工提案卡是 `ask_user` 的一种形态**：开场与途中共用同一挂起机制。→ 见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)。

### 受监督的波循环（晚绑定 + 边界让出）✅ 已落地

> **本篇权威**：晚绑定 / 波边界让出 / `replan` 续跑的**执行语义**以本节为准；CEO 侧 `replan` 工具形态见 [`编排器与CEO主Agent.md` §一 `replan` 原语](/docs/03-AI核心/编排器与CEO主Agent.md)。

**解决的痛**：worker 职责在 CEO `delegate` 那一刻就绑定死，但下游真正要干的活往往得等上游产物落地才清楚——团队闷头按可能过时的初始计划做完（「计划漂移」）。把执行模型从「CEO 下完计划即缺席」改为「**CEO 是波边界的监督者**」：`build_run_plan` 一次建全 DAG（开局全貌可见），节点可**晚绑定**，`WaveScheduler` 自主跑波、只在**决策边界**把控制权交回 CEO 定稿 / 纠偏后续，续跑同一张图（不重建）。这是 §一 检查点语义的推广——检查点只是边界的一种。

**形态**：

- **晚绑定节点**（`RunSpec.bind_after_deps`）：spec 关键字段先占位，依赖落地后由 CEO 在边界定稿（复用 `steer` 的 in-place mutate 范式）；`_select_ready(defer_bind=)` 绝不调度未定稿节点。
- **边界判据**（`BoundaryReason ∈ {CHECKPOINT, BIND, SCOPE}`）：① `checkpoint_after`（让用户把关）；② 依赖已就位、待定稿的晚绑定节点（让 CEO 定稿）；③ 已完成节点带未消费的 `escalate kind=scope` 偏离信号（让 CEO 纠偏）。
- **边界结果**（`BoundaryOutcome ∈ {PROCEED, YIELD, ABORT}`）：`YIELD` = 软暂停（复用 `should_stop` 语义：排空 in-flight、返回 partial、尾部不 skip），把控制权交回 CEO 主循环。
- **续跑**：`delegate` 的 `_drive` 收到 `YIELD` 返**非终态** ToolResult（CONTINUE）+「计划已让出」简报给 CEO，暂存 `(plan, completed)`；CEO 经 `replan` 定稿 / 纠偏 / 追加 / 收口后，`_drive(seed_completed=…)` 续跑同一 DAG。

**双臂：同一边界，让给用户 or 让给 CEO**（按影响力分档，对齐 `ask_user` / checkpoint 心智）：

| 臂 | 触发 | 谁裁决 | 用户感知 |
|---|---|---|---|
| 让给 CEO（BIND / SCOPE） | 低杠杆：晚绑定定稿、据 escalate 微调下游 | CEO 自主 | **无感**（仅图上「计划已调整」轻痕迹，见 [`../04-前端/前端UX设计.md`](/docs/04-前端/前端UX设计.md)） |
| 让给用户（CHECKPOINT → `plan_review`） | 高杠杆：选错会让用户明显不满 / 推倒重来 | 用户 | 决策卡，挂起待答（见上「检查点决策语义」） |

> **复用而非另起炉灶**：两臂共用 `WaveScheduler` 的边界机制 + §8.2 唯一挂起原语；让给 CEO 的臂本质是调度器在边界把控制交回 CEO 的 ReAct 循环、续跑同一 DAG——**不新增挂起子系统**、**不增委派深度**、**不碰 worker↔worker 直连**。CEO 臂走正常回合生命周期（非终态返回 = 普通 ReAct 续跑），plan / completed 由 journal 投影重建，**不需新 durable 挂起**（区别 user 臂的 `paused_turns`）。

> **偏离信号：复用 `escalate` + 轻量 `kind=scope` / `kind=dep`**：worker 发现自己 / 下游 scope 错了（`kind=scope`），或卡在一个**还不存在**的输入 / 依赖（`kind=dep`），用现有 `escalate`（**非阻塞**）加一个提示位上报（**扩展而非新原语**）；两者**同走反应臂波边界**（`_scope_pending` + `BoundaryReason.SCOPE` 一处机器）被 captain **一等消费**——`scope`→操舵已有下游、`dep`→`replan(add)` 追加产出者。**否决**「为 scope/dep 单立信号 / `InteractionKind`」：决策的是 captain、worker 只供偏离事实，单立 = 与 `escalate` 高度重叠（补丁绊线）。kind 轴语义见 [`Agent协作模式.md` §二·escalate](/docs/03-AI核心/Agent协作模式.md)。

> **成本纪律（不变量）**：无晚绑定 / 无 escalation / 无 checkpoint 的 plan，调度器一路跑到 terminal、一次 `delegate` 返回（= 今天行为、**零新增 CEO 回合**）——**CEO 回合数 = 真实决策点数，不是波数**。
>
> **协调模式例外（✅）**：≥2 worker 默认协调时 CEO 波内存活，成本纪律重定义为「协调回合 ≤ 必要决策点 + 预算上限」（中间完成可合并；预算耗尽只喂模板）。显式 `coordinate=false` / 单 worker / finalize / 嵌套 lead 仍守上文零新增纪律。见 [`编排器与CEO主Agent.md` §协调模式](/docs/03-AI核心/编排器与CEO主Agent.md)。

> **turn 末仍开着的 supervised run**：CEO 拿到让出简报却没 `replan` 就结束回合（最终答复 / `MAX_ROUNDS` / 上游报错），则 turn 末按**隐式 `stop`** 收口（折算已完成工作 + 未跑尾记 SKIPPED + 释放暂停态），避免团队工作悬空漏计费 / 来源不显；无让出时 no-op。

> **持久化与跨端一致**：晚绑定占位、scope 的 `kind`/`consumed` 经快照往返保真——重建的暂停计划仍知该节点待定稿、**绝不未绑定就 dispatch**；`YIELD` 给 CEO 走内部续跑（不产生用户可见事件分类），`replan` 改图走 `plan_revised` 事件（入 journal 可回放、三端等价）。

> **对任何 captain 一致（lead 子树同享）✅**：受监督波循环不是「根 CEO 专属」——子 lead（`can_delegate`）经 `LeadSubteam` bundle 同获绑到自身 `child_delegate` 的 `replan` + 收尾折账，故 lead 也能在自己子树上「晚定稿 / 据偏离重规划」，去掉「只有根能 replan」的特例。工具形态与铸厂分层见 [`编排器与CEO主Agent.md` §2.4](/docs/03-AI核心/编排器与CEO主Agent.md)。`plan_revised` 按 `run_id` 折到正确子节点、子层共用父 `execution_id` 不串层。**协调模式 scope 例外**：非阻塞协调仅根 CEO（`depth==0`）；lead 仍阻塞 `delegate`。

> **被否决 / 暂不做**：① **worker 实体化**（临时角色 → 稳定专家实体，Phase 2，用户按下）——守在「CEO 在波边界监督」一层，对齐「无团队选择器 / 每回合自适应组队」赌注（见 [`编排器与CEO主Agent.md` §六 Agent 实体化](/docs/03-AI核心/编排器与CEO主Agent.md)）；② **2b 波内抢占 / CEO 波内重入**——默认阻塞路径仍「波内无活着的 CEO」，用波边界让出替代；**协调模式下** CEO 波内存活，阻塞 escalate 改走 CEO 仲裁（`resolve_escalation`，非 worker 抢占）；③ **运行期软护栏**（类比 `delegation_nudge`）——边界结构性决策后基本不需，「实测漏触发率高再加」。
>
> → 协调模式 as-built 见 [`编排器与CEO主Agent.md` §协调模式](/docs/03-AI核心/编排器与CEO主Agent.md) 与本文 §协调事件注入。

> → 见代码：`runtime/runs/scheduler.py`（`BoundaryReason` / `BoundaryOutcome` / `OnBoundary`）、`runtime/runs/wave.py`（`on_boundary` / `_select_ready(defer_bind=)` / `_scope_pending`）、`runtime/runs/builder.py`（`bind_after_deps` 解析 / `build_added_nodes`）、`tools/builtin/delegate/`（`supervised.py` 让出+续跑、`boundary.py`、`tool.py` `dispose_open_supervised`）、`tools/builtin/replan.py`、`tools/builtin/escalate.py`（`kind=scope`）、`runtime/events/run.py`（`plan_revised`）。

### 失败与取消

可重试错误（超时 / 429 / 5xx）退避重试；不可重试错误跳过该 step 或升级用户；关键 step 失败时取消传播到所有下游依赖。完整收敛治理（重试 / 熔断 / 早停 / 反思）见 §四。

### 性能约束

| 指标 | 约束值 |
|---|---|
| 最大并行 Agent | 8（`max_parallel`：`DEFAULT_MAX_PARALLEL` 单波 / `MAX_PARALLEL_DELEGATIONS` 整树，二者同步） |
| 单次 delegate 最大步骤数 | 10（`MAX_DELEGATION_TASKS`，超出截断） |
| 事件传播延迟 | < 50ms（目标） |

### Agent 间产物传递

每次执行在调度器内持有各 worker 产物，供下游依赖注入读取。

> **实现现状**：`WaveScheduler.completed[run_id]` 持有各节点 `RunState`，下游按 `depends_on` 取上游 `RunState.content`（按 `result_handling` 全文 / 摘要）。计划热修改由 CEO 多次调 `delegate` 增量追加（§八 `adaptive`）。

### 事件清单

> **升级实时可见（`run_escalation`）✅**：worker 调 `escalate` 的【调用瞬间】，执行器 emit 一条 run 级 `run_escalation`，三端折到该 run 的 `escalations`（节点 ⚠️「上报」标记 + run 详情「上报待裁决」区）——让升级在【进行中】就可见，而非埋在工具行、或只随 CEO 收尾正文到达。

> - escalate 仍**非阻塞**：报完继续按假设交付。
>
> → 见代码：`runtime/events/run.py`（`escalation_raised`）、`runtime/runs/executor.py`、`tools/builtin/escalate.py`。

### 契约生成策略

> **实现现状（✅ 已接入 CI）**：`.github/workflows/ci.yml` 的 `contracts` job（"Contracts + conformance (gen + drift gate)"）已落地「生成 + 漂移门禁」——`node scripts/gen-types.mjs` 反射后端 dataclass 重生成前端 TS 契约、`uv run python -m agentcore.conformance.export` 由 Python 向量重生成 conformance fixtures，再 `git diff --exit-code` 拦未提交漂移。下列做法即此实现。

## 三、执行管线全貌 ✅ 已确定

> 从 HTTP 请求到 SSE 输出的完整后端调用链。

### 端到端流程

HTTP 请求经 `conversation/service.py` → `runtime/pipeline/` ReAct 循环 → SSE 事件流出。

### Phase 1: Prepare

CEO 只读/检索子集 + `delegate`；worker 全集固定注册；`AgentResolver` 为 Phase 2 方向。

**历史重建原则**：每回合取**最近 N 条** user/assistant 文本（`conversation/history.py::load_chat_context` → `list_recent`）。工具 I/O 与委派详情属展示遥测（持久化供前端详情面板），不回放进 LLM 上下文——避免跨轮累积烧 token。超长会话在此之上再叠一层**压缩**（见下「长对话压缩」）。

### Phase 3: Finalize

Finalize 在 pipeline 外由 `stream_chat`（落库 `conversation/turn_persistence.py`）执行；⏳ 无 Turn 表。回合收尾按需触发：**会话标题**（首回合）与**下一步推荐**（见下）两个 World B 窄任务在 `message_end` 后经 SSE 尾发回前端（`title_generated` / `followups_generated`）；**长对话压缩**（见下）与离线记忆整合均 off the user path。

**断连收尾契约**：各步骤独立 `try/except`，失败只 warning，不中断已完成的 SSE 流。刻意「能存多少存多少」而非全有或全无——用户已离开，保住已产生的消息比元数据一致性更重要。

### 回合级「下一步推荐」(CEO→用户) ✅ 已落地

> 实现：`memory/followups.py`（生成器）、`llm/profiles.py`（`followups` profile）、`conversation/common.py::generate_followups`、`conversation/turn_persistence.py`（收尾触发 + emit）、事件 `followups_generated`；前端桌面 `components/chat/FollowupChips.tsx` + 会话 store `attachFollowupsToLastMessage`。

**定位**：回合收尾后预测用户最可能想做的 2-4 件事，作为可点选的快捷追问挂在**最新一条**助手回复下（点选即回填输入框、可改后发）。是 worker→CEO「交接简报·建议下一步」的用户侧对偶：那条把队员建议上交 CEO，这条把整回合的自然后续下达用户。

**关键契约**：

- **生成**：一次 flash 非思考 World B 窄任务（同 title），`message_end` 后在收尾块跑（off 用户阅读路径，与标题**共用一个 provider** 顺序生成）；仅在**正常结束且有正文**的回合触发（错误 / 暂停 / 空回合无「下一步」可提）。`followups` profile 比 title 的 64 tokens 宽（256），容得下 4 条短中文而不中途截断。
- **DERIVED 持久化（回写列 · 与同胞 title 同辙）**：`followups_generated` 是**实时投递**，耐久副本落 **`Message.followups` 列**——收尾块 mint 出 chips 后，先经 `MessageRepository.set_followups`（会话内寻址、幂等）回写到**那一条助手行**，**再** emit 事件（persist-then-signal，与上面 title 回写 `Conversation.title` 同序）；reload 由 `MessageDetail.followups` → 前端 `toMessage` 重现。因耐久形态是**列**而非 journal 事件，三端协议 fold 对该事件仍 **no-op**、conformance ProjectedTurn 不携带它（与 `title_generated` 同类——DERIVED 走专用列，非 journal）。**为何持久化**：chips 是「下一步该干嘛」的入口，与其孪生 title **同寿命**——刷新后 title 还在、chips 也应在（原「刷新即消失」是与 title 的错配；重载才不再重生成，省一次窄任务）。
- **best-effort**：空输出 / 超时 / 任何错误都退化为「无 chips」，绝不阻断或拖累它所点缀的回合。
- **暂仅桌面**：手机端 fold 为 no-op（chips 属桌面增量能力，符合「手机 = 桌面 − 能力层」）。

### 长对话压缩（compaction）✅ 已落地

> 实现：`conversation/compaction.py`（压缩 runner + token 触发）、`conversation/history.py::load_chat_context`（注入）、`conversations` 三列（`compaction_summary` / `compacted_through` / `compaction_input_tokens`）。

**定位**：不是防溢出（DeepSeek 1M 不溢出），而是治两件事——**context rot**（超长上下文质量随长度下降，与缓存无关）与**缓存失效成本**（exact-prefix 缓存有 TTL，慢节奏 / 隔夜回来全量重算长历史真烧钱）。稳态成本已被前缀缓存软化，故此项是**质量项、非紧急**。

**做法**：把**早于 recency 窗口**的旧轮折叠成一份结构化滚动摘要（已确立事实 / 决策 / 未决问题 / 文件路径，逐字保留标识符·数字·路径），回合改喂 `[摘要] + 最近若干轮原文`。

**关键契约**：

- **触发**：回合 input tokens（DeepSeek 实报，即 prompt 实际大小）越 `compaction_trigger_input_tokens`（配置默认 64K）→ 回合收尾 fire-and-forget 后台压缩。自限：折叠后下回合 prompt 缩回阈值下，仅当尾部再次涨过阈值才重压；漏触发由下一次越阈回合自愈（无需 sweeper）。回合总 token 是 CEO prompt 的上界，触发偏保守（宁早勿晚），无可折叠内容时 runner 空转不调 LLM。
- **水位线**：`compacted_through`（最后被折叠消息的 created_at）使重触发幂等，并让长积压**由旧到新、增量**分多次折叠追平。
- **缓存铁律**：摘要**算一次、落库、跨回合复用**；绝不每回合重算——否则改写 prompt 前缀打穿 DeepSeek exact-prefix 缓存（见 `runtime/resolve/prompt.py`）。摘要作 **assistant 块**置于恒定 system 之后，故 system 前缀恒命中，仅「摘要 + 尾部」在重压时重新缓存。
- **健壮**：BYOK 取会话主人的 key（同记忆整合）；一次 flash 非思考调用（World B 窄任务，同 title / memory）；折叠量不足 `compaction_min_fold_messages` 不调 LLM；任何失败（超时 / 空输出）留存状态不变、下次重试，绝不写空摘要、绝不影响已完成回合。
- **与记忆整合区分**：离线记忆整合读**原始**最近消息 reconcile 进记忆文件（`load_recent_history`），**不读**摘要块；压缩只作用于 CEO 回合窗口（`load_chat_context`）。
- **与 A1（执行级 journal）关系**：作用在 `messages` 表已持久化的 user/assistant 文本层，**不依赖** journal，可独立演进。

### 回合内工具结果清理（clear_tool_uses）✅ 已落地

> 实现：`runtime/engine/tool_clear.py`（纯函数 `project_cleared_window` + `cleared_placeholder`）、`runtime/engine/loop.py`（`build_request` 前投影 + `engine.tool_clear` 埋点）、`config/` 两旋钮（`engine_tool_clear_keep_recent` / `engine_tool_clear_min_chars`）。

**定位**：与「长对话压缩」同治 **context rot**，但**作用域正交**——压缩跨回合折叠旧 user/assistant 文本，本机制**回合内**收掉堆积的工具结果。一个长 worker run 会反复 `file_read` / `grep`，旧结果每轮原样重发（token）且把窗口塞满陈旧读（rot）；而按「历史重建原则」工具 I/O **不跨轮回放**、压缩也从不见它，故单个长 run 内的工具堆积**只有本机制治**。

**做法**：在**发给模型的窗口**里，把滑出「最近 `keep_recent` 个同类结果」窗口、且本身 ≥ `min_chars` 的旧「只读可重取」工具结果，折成紧凑稳定指针 `[已清理: file_read(path='…') 原 N 字符，可重取]`。**纯投影**——只在 `build_request` 那一点改发给模型的视图。

**关键契约**：

- **触发**：per-run，不靠 token 阈值而靠「**条数窗口 + 体积下限**」——某条只读结果滑出最近 `keep_recent`（默认 4）个同类结果、且 ≥ `min_chars`（默认 2000 字符）才折叠。短回合（≤ keep_recent 个合格读）**零触发**；`keep_recent` 设极大 = 等效关闭（开发期默认开，**无 enable 布尔开关**，两旋钮即调参面）。默认 4 取自真实 DeepSeek A/B 实测（`scripts/measure_tool_clear.py`）的省量/留存曲线拐点：10 读回合稳态省 ~57% input token、cache_miss 始终极小（指针仍命中前缀缓存），再降（4→3 仅 +5pp）边际收益小且压缩逐字工作集、抬高重取风险。
- **唯一事实源不破**：投影**不改** canonical `messages`、**不写** Turn Journal；journal 与 UI（结果搭 `tool_use_end`）始终全保真。压缩亦同纪律（只动模型窗口）。
- **恢复一致（确定性而非快照）**：resume 重建全量 `messages` + 重跑同一 loop → 同输入同投影，**逐字节复现**发给模型的窗口。
- **缓存铁律**：指针稳定 + **保位**（不删消息、不断 tool↔assistant 配对），已清理前缀仍命中 exact-prefix 缓存，仅每轮本就重算的移动尾部 miss——与压缩「绝不改写已缓存前缀」同律。
- **清理判据**：复用 worker 已有 `investigation_tools` 白名单（只读 / NEVER-approval / 可重取：`file_read` / `grep` / `file_list` / `git`（只读子命令）/ `web_search` / `read_url`）——只清「重取即得、清了无损」的；写类 / 有副作用 / 审批类结果**绝不碰**。

> **不变量**：轮次上限 `ModelProfile.max_rounds`；收敛治理 `LoopController`（滑窗机械循环 → NUDGE/FINALIZE、工具失败熔断、无产出早停、反思注入）；交付前核验 `finish_guard`（done 点纯代码轻层守卫、未过回炉，见下）；引擎级工具超时兜底；空响应同模型重试至阈值后 DEGRADED、LLM 硬失败直接 ERROR/DEGRADED 收口；GRANTABLE 审批在 worker 层 gate（CEO 不持 GRANTABLE）；回合内工具结果清理（旧只读结果在 `build_request` 前投影成指针，纯视图不动 `messages`/journal，见 §三）。✅ 结构化 `RoundOutcome`/`LoopDirective` 协议（每轮产出归一为 `RoundOutcome`，治理只回一个 `LoopDirective`，主循环退化成单一 `match` 执行器）。→ 见代码：`engine/loop.py`（`react_loop`）、`engine/outcome.py`、`engine/directive.py`、`loop_controller.py`、`runtime/verify.py`。

### 基本循环

`message_start` 后逐轮迭代至 `profile.max_rounds`；✅ GRANTABLE 审批挂起；✅ 工具超时兜底（B1）；✅ 空响应同模型重试后 DEGRADED / LLM 硬失败直接收口 / 工具失败熔断 / 无产出早停 / 反思注入（B2，见下表）。✅ **结构化轮协议**：每轮先组装 `RoundOutcome`（content/reasoning/usage/tool_calls/tool_results/attempts/terminal_handoff/llm_failed 的单一事实对象），治理函数（`decide_no_tool_round` / `govern_after_tools` / `decide_llm_failure`）各回一个 `LoopDirective`（`Continue`/`Rework`/`Finalize`/`Return` 密封联合），主循环对其做穷尽 `match`——取代旧的字符串 `kind` / `terminal` 哨兵 / `LoopExit | None` 散落控制流。

### 交付前核验（finish_guard）✅ 已落地（轻层：造引用 + 结构完整性）

> **不变量**：模型自报 done（无工具调用 + 有正文）是 ReAct 唯一终止信号；`react_loop` 在这一点先过一道**纯代码轻层守卫**再决定放行，未过则回炉重写。守卫无状态、不经 LLM、不靠 CEO 自觉——给「交付前先核一道」一个决定论闸门。→ 见代码：`runtime/verify.py`、`engine/loop.py`（`react_loop`）、`runtime/events/chat.py::content_reset`（CEO）、`runtime/events/run.py::run_output_reset`（worker 对偶）。

收敛治理（上）管「循环要不要继续」，本机制管「交付能不能放行」——是终止点的对称闸门。CEO captain 与 worker 跑同一个 `react_loop`，故一处落点同时盖住两条路。

- **轻层两查**（都纯机械可判、近零误报）：①**造引用**——正文 `[n]` 角标指向不存在的来源卡（编号 < 1 或 > 来源数）即命中（真实事故：CEO 直答用了 `[25][27]` 而仅 24 源，违反「绝不编造引用」却不自知）；②**结构完整性**——代码围栏未闭合（后文整片被当代码渲染）或声明了语言却空体（答应给代码却没给）。刻意**不**纳入「残留 TODO / 填空占位」（法律模板会正当留空、worker 会如实写「待客户提供」，机械判会误伤——轻层立身之本是近零误报）。后续轻层（受限的 JSON 可解析）与重层（要跑 / 要重算 / 换眼睛找漏 / 回源对照）在 `verify.py` 扩展。
- **统一底线·分路适用**：**造引用**仅 CEO 路径开（`annotate_citations=True`）——worker 文本未编号、其本地 `[n]` 汇入回合卡时会重排，角标校验语义不适用，故 worker 跳过此查；**结构完整性两查**与角标无关、对 CEO 与 worker 同样成立，二者收尾都过这道关（✅ 已扩到 worker 路径，二者跑同一 `react_loop`、共用 `finish_guard`）。
- **命中即回炉**：丢弃这一版草稿（`final_content` 退回本轮之前），注入锚定具体角标的修正提示（`format_guard_steer`，允许模型改写或继续检索补来源），回炉重写而非照发；回炉计入 `max_rounds`。上限 `engine_finish_guard_max_reworks`（默认 2）耗尽后按现状放行，残留交由 pipeline 的 `citations.out_of_range` warning 记录（观测）。
- **流式一致性**（关键约束）：done 轮正文已逐 token `emit` 到气泡、无法「收回」，故回炉时发 `content_reset`——前端清当前气泡已累积正文（含 process 尾部 content 步）并丢弃 rAF 缓冲，重写版重新流式，呈现为「违规版 → 修正版」一次干净替换而非追加。同一 reset 规则**三端镜像**（共用 `lib/processTimeline.ts::dropTrailingContentSteps`）；`content_reset` transport-only 不进 journal（历史回放：纯对话回合用最终 `message.content`、有工具回合用已 pop 草稿的 process timeline）。**worker 回炉发其对偶 `run_output_reset`**（`runtime/events/run.py`）——清该 worker 卡片已累积的 `outputChunks`、保留 reasoning（思考是真实过程），同样三端镜像（桌面 `stores/execution` fold + 手机 `protocol/fold.ts` + oracle）、transport-only 不进 journal（重载由 worker 终态 `message_final` fact 重建）。
- **覆盖边界**：仅拦**模型自报 done** 的正常收口；`LoopController` 的强制收口（`_force_finalize`：机械空转两段式 `FINALIZE` / 无产出早停 / 轮预算耗尽 mid-tool-call）走独立路径、**不过此守卫**——那是已判定异常的回合，第一刀不在其上再叠回炉。

⏳ **测试验证循环**（低优先级 backlog，与 `finish_guard` 轻层正交）：编排层 Skill + `test_run` 工具（结构化跑 `ProjectProfile.test_commands`、解析 pytest/vitest 输出），**不**新建 TestFixAgent 子系统。worker：改代码 → `test_run` → 失败则 `file_read` 修复 → 重试；CEO `delegate` 可附 `acceptance: "相关测试通过"`。收敛复用 `LoopController`（同失败签名 3 次 NUDGE 停用 `test_run`）；默认 max **3** 轮修复，仍失败 → `degraded` done 并列出失败用例；**禁止** agent 修改测试文件；测试命令本身报错 → `escalate` kind=dep。云端可靠执行依赖 [真实沙箱](/docs/06-规划/远期规划.md) §2.1；sidecar 可先用 subprocess 验证逻辑。→ 工具侧见 [工具与能力系统](/docs/03-AI核心/工具与能力系统.md)。

### SSE 桥接

执行侧与输出侧经**无界 `asyncio.Queue`** 解耦。背压只对可丢弃事件（`content_delta` / `reasoning_delta`）生效，生命周期/终止事件保证送达。

**前端兜底对账**：消息落定时递归收口所有悬挂的 running/queued run 节点——后端可靠送达是主路径，前端对账是 last-resort 兜底。

### 执行与请求解耦（断连续跑 + 实时重连续看）✅ slice 1a + 1b 已落地

> **实现现状**：✅ slice 1a + 1b。回合执行从 SSE 请求生命周期**解耦**——`send` / `regenerate` / `resume` / `retry-failed` 四路由把 pipeline 作为 **detached task** 交 `runtime/turn_runs.py::TurnRunRegistry`（进程内、按 `conversation_id`，单机姿态同 approvals / locks）托管，SSE 仅 **attach**（`sse_response(..., detach_on_disconnect=True)`）；断连后客户端可经 `GET …/stream` **重新 attach、回放 + tail 续看**。源起证据：生产复盘案例 1（2026-06-23 断连丢回合）。

### 用户级重试失败项（retry-failed）✅ 已落地

**意图分离**：`regenerate` = 推翻重来（删消息后整回合重跑）；`retry-failed` = 补救失败（复用已成功 worker，只补跑失败节点）。与 `resume`（checkpoint 续跑）共用 `seed_completed` 底层，但语义不同——resume 从挂起点之后全部重跑，retry-failed 只重跑当时仍为 `failed` 的节点。

**后端路径**（`POST …/messages/{message_id}/retry-failed`）：

1. 从该 user 消息对应 assistant turn 的 journal 提取 `phase == COMPLETED` 的 worker → `completed_from_journal`
2. 写入 `runtime/retry.py::retry_seed` contextvar
3. `delete_after` 该 user 消息之后的消息，CEO loop 重跑；`DelegateTool` 读 seed 并以 `seed_completed` 交给 `WaveScheduler`，已成功节点跳过

**节点自动重试**（第一层防线）：DAG 节点默认 `RunPolicy(on_failure="retry", max_retries=1, retry_delay_ms=2000)`（`runs/constants.py` / `builder.py::_dag_policy`）；调度器内部静默退避重试，用尽仍失败才 `run_failed` 上报用户。

**确定性失败区分** ✅：非重试类上游失败（prompt 超长 / 400 / 鉴权 / 余额，`AgentCoreError.retryable=False`）经 `RunState.error_retryable` 从 worker executor 传导到 `WaveScheduler`——`on_failure="retry"` 遇确定性失败即**跳过**盲目重跑（不再烧 `max_retries` + token 复现同一个 400），并落一条 `run.deterministic_failure` 审计（category=`state`，不重复计 failure），后端从此对确定性失败「有感知」；`error_retryable` 随 `state_to_json` 落 journal，resume / retry-failed 重建时保留。**用户接受收口** ✅（run_redirect Step 4）：run 详情在 `run.deterministic_failure` 或 `run.redirect_ignored` 审计行存在时提示「接受此结果」→ `POST …/accept-outcome` 幂等落 `run.outcome_accepted`（owner-scoped，复用 append-only 审计表，无新 SSE）。整轮「放弃」仍走 `clearExecution` 清本地投影。→ 见代码：`runs/wave.py`、`runs/executor_agent.py`、`audit/projector.py::project_run_deterministic_failure`、`api/routes/conversations/run_redirect.py`、`conversation/turns.py::retry_failed_chat`

**契约**：

- **客户端断连 ≠ 取消**（1a）：断连只让 `_event_generator` 调 `sink.detach()`（停止入队、封顶未读队列），run 在后台**跑完并照常 `_persist_turn_result` 落库**——直接消灭「7 分钟长回合断连即丢交付」。
- **显式停止 = 取消**（1a）：用户「停止」改走 `POST …/conversations/{id}/stop` → `turn_runs.stop` → `task.cancel()`，经回合既有 `CancelledError` salvage 路（已完成队员产出落「未完成」消息，断线别白干）。幂等：无在飞 run 返回 `stopped=false`（前端 `services/stopTurn.ts` 在 abort 本地流之外补发此请求，因断连不再代为取消）。
- **持久化独立于连接**（1a）：journal / 落账 / 遥测 / 快照本就在 pipeline 返回后跑、与 SSE 消费无关；`EventSink.detach` 仍保留 journal / process / fact 累积，故断连后回合仍完整重放。
- **重连即回放 + tail**（1b）：`GET …/stream` 命中在飞 run → `EventSink.take_over` **原子地**丢弃未读积压、快照 `_history`、重挂队列，先回放后 tail；无在飞 run 返回 **204**，前端回落到读持久化消息。`_history` 是**有界、合并**的可重放转录（增量逐流合并、工具结果封顶、纯活性事件不入），独立于 SSE `_queue`，内存随**可见正文**而非 token 数增长；事件 shape 与原流一致，前端 live / reload / reconnect 三态同构折叠。
- **前端重连姿态**（1b）：传输级断连（`StreamError.kind==="network"`）不再 resend/regenerate（那会**双跑**仍在飞的回合），改 `services/turns.ts::rejoinLiveTurn`——清掉残缺气泡后 attach（回放重建）；`"none"` 则该回合已落库，reload 取回；连不上给「重连」banner（永不 resend）。开会话若末条是 user 消息（尚无落库回复），`attachOnOpen` 顺带重连续看（重开 App 也能看它跑完）。sidecar 本地回合失败 kind 为 `"sidecar"` 非 `"network"`，自动跳过重连、维持原 resend。
- **边界**：进程内注册表，重启丢在飞 run（同 handoff 作业现状）；单活跃消费者姿态（多端并发 attach 共享单队列会分流，非目标）；**跨进程持久队列 / 多副本**（C2 · Redis）为后续。

### 暂停与恢复（回合级落盘续跑）

> **设计不变量**：不引入 `RunPhase.PAUSED` 第三终态——结构化挂起暂停的是**整个回合**（CEO loop + delegate 子 DAG），而非单个 Run 节点；改用**回合级**落盘（`paused_turns` 一行 = 一个挂起回合），Run 模型零改动。
>
> **Resume = 同一回合续写（身份不变量）**：`POST …/resume` **不**开新 turn——`message_id`（= `turn_id`）、`execution_id`（取自 journal 末张 `run_plan`）、journal 游标权威源（DB `max_seq+1`）三者在 pause→resume 间不变。前端投影键同钉 `serverMessageId`（live）/ 消息 `id`（reload 已是 server id）；**禁止**「删暂停气泡 + 新建气泡 + remount 协作图」——续跑只把同一条助手消息翻回流式。否决「resume 伪装成新回合」与「client UUID 当执行槽键」——二者会反复制造 remount / UniqueViolation / 图丢帧类补丁。

**挂起即收口（②）**：到达 `plan_review` / `ask_user` / `team_preview` 检查点的回合在 `await` **之前**把整帧（`TurnSuspension`，以 `kind` 判别）落到 `paused_turns`，**落帧成功即收口终止**回合（`SUSPEND→PAUSED`、进程内 resolve Future 永不 park），所有续跑——含同会话——统一走单一冷路 `POST …/resume`，把冷热双态在检查点处塌缩为一条冷路。**窄兜底（§六-1 薄网）**：帧没存住（`saved=False`，无法冷恢复）时退到一条**后端限时挂起**——客户端已无解析路径（resolve schema 已删），仅 timeout **自动续跑、不丢回合**（`ask_user→CONTINUE`、`plan_review→放行下游`；`plan_review` 另仅顶层 `depth==0` 成立）。

- **持久缝**：`frame` JSONB 仅存 **resume 控制元信息**；CEO 窗口/历史、已完成 worker **不再入帧**——窗口由 `journal_entries` + `window_from_journal` 投影，历史在消息库，已完成 worker 由 `completed_from_journal` 投影，`plan` 由 `plan_from_journal` 取末张重建，`execution_id` 由 journal `run_plan` 投影。
- **pause 后 journal 硬边界**：`save_paused_turn` flush 落帧后，本 turn 的 append-on-emit writer **不再**为后续收口噪声（挂起工具的 `tool_use_end` 等）追加 DURABLE 行——snapshot 与 DB 对齐；resume 的 `TurnJournalWriter.initial_seq` **只认** DB `max_seq+1`（snapshot 长度仅作校验）。
- **恢复**：`POST …/messages/{mid}/resume`（原子 claim）→ 载 journal → `seed_journal` 回放 → `window_from_journal` 重建 CEO 窗口 → 按 `kind` 分流结算跑尾部（复用原 `execution_id`）→ 续跑 CEO loop；重开会话经 `GET …/recovery` 一次拿到 `live_running` + 待恢复帧（统一恢复态，前端据此择一可操作面，避免双拍板卡）。
- **续跑前先拆在线 run（断连未重启）**：**挂起即收口（②）下正常收口回合的在线 run 已结束**，故续跑前拆 run 通常 no-op；但保留作安全 drain：仍可能有在线 run 未拆净——未拆净的收口 / 在飞 attach / §六-1 薄网仍阻塞在交互上握着 folder 级 `workspace_lock` 直到 `checkpoint_timeout`（默认 600s）。故 `resume_message` claim 帧后、起续跑 run **前**先 `turn_runs.stop_and_drain(conversation_id)`：cancel 该在线 run（`CancelledError` 解栈即释放锁、且**留帧不删**），并**等它真正解栈**再取锁。少了这步会（1）续跑 run 抢同一把锁**死等至 600s**、（2）在线 run 超时后**二次续跑同一回合**。claim 成功才拆，保证只在「确属挂起回合」时动在线 run。→ 见代码：`runtime/turn_runs.py::stop_and_drain`、`api/routes/conversations/turns.py::resume_message`。
- **计费**：整回合**一次**计费——实时路完成则正常落账删帧；断连路只在 resume 完成时落账。
- **TTL**：`paused_turns` 7 天 idle 清理（镜像 `session_retention`）。
- **显式停止兜底**：含未持久挂起点的回合被显式停止时，把已完成 worker 产出落成 `finish_reason="cancelled"` 的「未完成」消息；纯断连不触发本路（见「执行与请求解耦」）。
- ⏳ 余项：跨进程 Redis（多 worker 实时分发）+ 治理强制层（见 [`../06-规划/远期规划.md` §2.3](/docs/06-规划/远期规划.md)）。

> **实现现状（⏳ 未落地）**：注册表 / 片段库尚未实现，`runtime/resolve/prompt.py` 目前只承载 World A（基座 + CEO/worker hint 装配）。当前每个内部 LLM 窄任务调用**各自手搓**：模块内一个 system 常量 + 一个 Python 渲染函数，直接拼成 `LLMMessage`。现有三处：会话标题（`memory/conversation_title.py`）、用户记忆抽取（`memory/user_memory.py`）、回合级下一步推荐（`memory/followups.py`，见 §回合级「下一步推荐」）。
>
> **「第三处出现」触发已到、仍判暂不收敛（2026-06，经评估）**：本节原以「第三处内部调用出现」为收敛扳机；下一步推荐即第三处。但复看三者形态：标题与下一步**真正同形**（一次性 `complete` → 文本清洗 → 输出），而记忆抽取是**多步异类**（结构化 ops 解析 + 确定性应用），真正重叠的只有标题/下一步那点「provider 构建 + 超时 + sanitize」样板，约 30 行、稳定且已被各自单测钉住。故判定：**抽统一 registry 的收益此刻仍不抵重构三条在跑路径的风险**（且与「为复用而复用」绊线相悖）。扳机改记为：**当标题/下一步的同形样板开始相互拖累、或出现第 4 处窄任务时**再收敛（届时优先抽「one-shot complete + sanitize」薄助手，而非大一统模板引擎）。

## 八、运行时核心模型 ✅ 已确定

> **已落地**：Interaction 统一挂起（`InteractionRegistry`，六 kind）；`checkpoint_after` 波间 `plan_review`；回合级 `paused_turns` 续跑；Turn Journal 唯一事实源（`turn_journal` 表 + `TurnFactLog`）；`window_from_journal` / `completed_from_journal` / `plan_from_journal` 投影；`transcript`/`history`/`completed`/`plan` 已退出 `frame` 序列化；deltas 降纯传输。
>
> **⏳**：跨进程挂起（Redis BLPOP）；`frame` 再瘦 / 大正文卸 `ArtifactStore`。（结构化 `RoundOutcome`/`LoopDirective` 已落地，见 §四。）
>
> → 见代码：`runtime/journal/`、`runtime/interaction.py`、`runtime/facts.py`。

> 运行时收敛在三个一等模型上。每个模型把一族重复子系统坍缩成单一形状。

### 8.1 三模型总览

| 模型 | 职责 | 解决的问题 |
|------|------|-----------|
| **Interaction** | 唯一挂起原语：server 停下等 client 回值 | 统一审批/ask_user/本地工具/计划评审/阻塞式升级/逐轮辩论六套同构 BLPOP |
| **Turn Journal** | 唯一回合事实源：append-only 事实流 | 消除「回合无事实源」导致的历史回放/快照/消息完整性补丁族 |
| **Run** | 唯一执行单元：一棵 Run 树 | 统一委派/DAG/编排/路由四套并存的编排子系统 |

依赖关系：Interaction 最小独立；Journal 是 Run 的地基（事实留痕在 journal）；Run 落在两者之上。

### 8.2 Interaction（统一挂起原语）

统一挂起原语收编审批 / `ask_user`（语义见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)）/ 本地工具 / `plan_review` / 阻塞式升级 / 逐轮辩论 六 kind，单一 resolve 端点 `POST …/interactions/{id}`。→ 见代码：`runtime/interaction.py`（`InteractionRequest`，`kind ∈ approval | ask_user | client_tool | plan_review | escalation | debate_round`）。

一套机制替换四套：统一等待器、统一挂起登记（`list_pending`）、统一恢复端点、统一回值端点。per-kind 差异降为策略位（durable / 键粒度 / at-rest 脱敏）。**`paused` 落盘续跑**见 §暂停与恢复；**跨进程等待**（Redis BLPOP）⏳。

### 8.3 Turn Journal（唯一事实源）

每 turn 一条 append-only 条目流（主键 `turn_id + seq`）。→ 见代码：`runtime/journal/`、`runtime/facts.py`、`runtime/journal/writer.py`。

**关键设计抉择**：执行事实与展示事件共用**单一有序日志**（`TurnFactLog`：sink 转发 + 引擎直记交织），否决「执行流与展示流分家再归并」——两流须同发生序才能正确 fold 窗口/快照。

**持久化模型（Append-on-Emit）✅**：每条 fact 在 **SSE 送达前先落盘**（`TurnJournalWriter` contextvar 绑定每个 turn），否决旧的「pause 时 batch snapshot」——前端能看到的一切 DB 里必然已有。数据流：`record_turn_fact → DB append (barrier) → SSE emit`。**并发模型**：writer 是**单消费者有序 write-behind**（`seq` 入队即定 = emit 序），同刻只占 1 条 DB 连接——否决「每条 fact 扇出任务+连接」（宽并行委派下多 worker 并发 emit 会瞬时打爆连接池：asyncpg `connection_lost` + GC 回收未归还连接）。**turn owner 在每条回合路径终了（新回合 / resume / pause）都必须在 reset writer 前 `await flush()`** drain 队列尾巴，否则在飞写任务被放置 → GC 强杀已 checkout 的连接；pause 再额外写控制帧（journal 早已逐条在 DB），消除「frame 在 journal 缺」的中间态。单条写入失败降级为内存态（`writer.degraded → journal_degraded`），不中断 pipeline。删消息时联动清理 `paused_turns`（防 orphan frame）。

**投影不变量表**：

| 消费面 | 来源 | 现状 |
|--------|------|------|
| SSE 流 | 引擎实时 emit（流式增量不入 journal；DB barrier 在 emit 前） | ✅ |
| 执行级事实记录 | `react_loop` 经 `record_turn_fact` 直写单一有序日志 + DB | ✅ |
| 持久化消息行 | journal 投影器 `runs_from_entries` | ✅ |
| 暂停快照 / resume | `turn_journal` + `window_from_journal` / `completed_from_journal` / `plan_from_journal` | ✅（`transcript`/`history`/`completed`/`plan` 已退出 `frame` 序列化） |
| 跨轮历史回放 | 文本 + interaction 答案投影 | ⏳ |
| LLM 窗口 | `window_from_journal` | ✅ |

**审计投影层 ✅**：`agent_audit_events`（多 Agent 协作追溯）是 journal + 运行时钩子的**下游只读投影**——`AuditRecorder` 先 journal 后审计偏序采集、`causal` 复用 `depends_on`/`parent_run_id` 重建 parent/depends_on/inject 因果边，**非第二事实源**。治理面（受众 / schema / 因果 / 双 API + 文件反查 / 留存 / 被否决取舍）→ [`安全权限与治理.md §八·Agent 行为审计`](/docs/05-平台与运维/安全权限与治理.md)；→ 见代码：`runtime/audit/`。

### 8.4 Run（唯一执行单元）

执行形状不再是离散「模式」而是数据，由 `depends_on` 边自然落定：

- 单 Agent = 单节点
- `fan_out` = 单波 + captain 汇聚
- `pipeline` = 线性链 + captain 汇聚
- `adaptive` = 空计划 + captain 动态追加
- 单次 delegate = 追加一个节点
- best-of-N 择优 = 某节点 `candidates>1`（`RunPolicy` 策略位，非独立 kind）
- 辩论/审查 = 主持人（Moderator）驱动的逐轮交锋（✅ 已落地，见 [`辩论编排设计.md`](/docs/03-AI核心/辩论编排设计.md)）：主持人是 CEO 的 `debate` 工具内的确定性循环（非 LLM 委派角色）、辩手为 `depth+2` 叶子，底层仍是普通 AGENT DAG（**非独立 kind / 无 arena 子系统**），轮次由主持人逐轮判收敛自停（取代旧的 CEO 手搓静态跨轮 `depends_on`）

> **决策（CEO = 根 Run 节点 ✅）**：CEO chat loop 即本回合 `CAPTAIN` 根 Run；content/reasoning 走气泡级 `content_delta`/`reasoning_delta`（非 run 级）；captain 一次定价、落真实台账行。**否决**旧的 `synthesis` 零成本伪 run。

> **决策（嵌套委派）**：`depth < MAX_DELEGATION_DEPTH` 的 worker 默认获 `delegate`+`replan`（启动即有委派能力，见 [`编排器与CEO主Agent.md` §2.4](/docs/03-AI核心/编排器与CEO主Agent.md)）。**硬上限 `depth ≤ 2`**：depth=2 sub-worker 永不获 `delegate`；单 lead 扇出上限 `MAX_WORKER_SUBDELEGATIONS = 4`。

> **决策（可恢复运行 `RunSession`）✅**：一次 worker run 执行后不丢弃，保留完整 transcript = `RunSpec` / `RunState` 的**可恢复延伸**；CEO 经 `revise` 在保留 transcript 上追加指令、重跑 `react_loop` 即「修订」（同轮 / 跨轮 / 跨进程留人，双 miss 回落重派）。统一收编自动返工 / CEO 热修 / 重派兜底三条接缝。详见 [`多轮编排与队员热修.md`](/docs/03-AI核心/多轮编排与队员热修.md)。

### 8.5 引擎纯化

三条去特判手段：

1. **工具效应模型**：`ToolResult(text, effect)`，`effect ∈ Continue | Handoff | Interact`。引擎只解释效应，`delegate`/`ask_user` 不再是特殊名字
2. **显式 ToolContext**：工具签名携 context（user/conv/turn 等），消灭 `set_runtime_context` 全局大杂烩
3. **去工具名特判**：引擎按能力位（`has_delegation_tool` 等）而非工具名判断行为

### 8.6 端口契约（宿主注入）

引擎面向宿主的 10 项端口（本地/云端同码、宿主注入）；契约在代码里镜像为 `runtime/ports.py`（**ClientRequestBridge / Journal 已落地**、EventSink 已是端口，余项仍为其具体实现、待 Sidecar 取用时再 Protocol 化）：

| 端口 | 定位 |
|------|------|
| Journal ✅ | 引擎唯一持久化出口；`turn_journal` 表 + `TurnJournalRepository`，`runs` 读取时投影自它（§8.3） |
| EventSink ✅ | 渲染流出口（流式增量 + 离散事实实时投影）；`runtime/events/`，`ports.py` 再导出 |
| InferenceGateway | LLM 调用 |
| ArtifactStore | 归档/寻回 |
| PauseSignal | 暂停信号（Redis flag） |
| ClientRequestBridge ✅ | 统一挂起原语（`runtime/interaction.py`；审批 / ask_user / 本地工具 / **plan_review（2a）** / escalation / debate_round） |
| ConversationStore | 消息持久化（投影写入） |
| BillingSink | 计费事实投影 |
| DelegationTransport | 跨进程子树传输 |
| SnapshotStore | 已被 Journal 吸收 |

### 8.7 一轮一网关（Gateway 传播原则）

当用户自带 LLM 凭据时，整棵多 Agent 委派树必须在**同一把网关**下运行，避免 split-brain（captain 跑用户 key，委派出去的子 Agent 回落平台 key）。

**规则**：在 Turn 最早阶段（工具装配之前）一次性解析 `effective_gateway`，随 Run 上下文贯穿整棵执行树。`InferenceGateway` 端口接收的凭据由此确定——直答、团队编排、恢复各路径读同一把。

此原则与凭据来源开关无关（无论平台供还是用户供），是执行语义的不变量。
