# 执行引擎内部架构设计

> **状态**：已确定方向

---

> **现状**：多 Agent 编排 = CEO 在 ReAct 循环里调 `delegate` → `runtime/runs/`（`build_run_plan` + `WaveScheduler`）。§十二~§十四 为已落地运行时；§十五~§十七 为设计方向；§十八 为目标模型（Interaction / Turn Journal / Run）。
>
> → 见代码：`apps/server/agentcore/runtime/`
>
> **章节编号说明**：§二–§十一已废弃，外链请用 §十二 / §十五 / §十八。

## 核心定位

执行引擎是 CEO 主 Agent 与 worker 实例之间的调度中枢。它接收 CEO 经 `delegate` 下达的子任务（`build_run_plan` 据 `depends_on` 建 DAG），解析依赖图，管理 worker 生命周期，协调并行/串行执行，处理失败与取消，并向 UI 推送实时状态更新。

---

## 一、基础概念（DAG 调度，早期设计）

> DAG 调度概念提要；运行时以 §十二~§十四 为准，§十八 为目标模型。以下只保留代码看不直观的设计约定。

### 步骤状态与调度

计划是 DAG：每个 step 声明 `depends_on`，执行引擎扫描「依赖已满足且未启动」的 step 并发启动（受 `max_parallel` 限制）。步骤状态 `queued → running → completed`，异常分支 `failed` / `skipped`（枚举见 `runtime/runs/types.py` 的 `RunPhase`；失败重试由 `RunPolicy.on_failure=retry` 在 `runs/wave.py` 内部完成（硬上限 3 次退避），对外仍以 `FAILED` 收口并 emit `run_failed`）。并发模型为 asyncio 协程——多 Agent = 多 asyncio Task 共享事件循环（Agent 本质是 I/O 密集的 LLM 调用，协程足够）。

### 检查点决策语义

> **本篇权威**：检查点 / `plan_review` / 2b 续跑语义以本节与 §暂停与恢复 为准；编排器、协作模式等文档仅外链此处。

检查点分两类，**实现现状不同**：

- **CEO `ask_user` 检查点（✅ 已落地）**：CEO 主动调内置工具 `ask_user` 暂停回合、征询用户——这是 CEO **唯一的发问原语**，开场引导（开工提案卡）与执行途中的高代价岔路**共用一卡一机制**（开场味已并入，原独立的非挂起 `kickoff` 工具已撤销，见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)）。载 `message`（开场白 / 现状，必填）+ 可选 `context` / `assumptions`（起步计划只读）/ `questions`（≤5，每题 `kind=choice|text`、`multiple` 决定单/多选、开场预填 `default`）/ `style_options`（视觉类）。桌面端以**提交 / 停止**两态作答：提交把各题选择 + 风格 + 自由补充拼成一段可读 `note`（答复模型 α）续跑、`selected` 留空（`CheckpointResponse` 一等字段仍在，供非桌面端按 `questions` 选项过滤回传），停止结束本回合。线路枚举 `CheckpointDecision` 仍为 `continue / adjust / stop`（超时落 `timeout`），其中 `adjust` 已合并入「提交」、仅留作老对话回放（故 `continue` 现也读 `note`）。这是一个**工具效应**而非调度器结构挂起——`ask_user` 经统一挂起原语 `InteractionRegistry`（与工具审批、本地工具同构，§18.2）等用户经 `POST …/interactions/{id}` 回值，答复回流 CEO 的 ReAct 循环；`stop` 走 `ToolResult.terminal` 优雅收口本回合。问答入回合日志可回放。该工具属 `ToolCategory.INTERACTION`（**非** ORCHESTRATION，故不触发引擎的 CEO→synthesis 边界），仅在 `settings.checkpoint_gate_enabled` 且有交互用户（审批开）时装配，worker 委派路径不给。
- **DAG `checkpoint_after` 结构化挂起（✅ Phase 2a 已落地）**：step 带 `checkpoint_after` 且 `COMPLETED`、下游仍待跑时，`WaveScheduler` 在波间 `await` `plan_review` 交互（`kind=plan_review`，continue/adjust/stop——adjust 把备注作为 steer 注入未跑下游的 `RunSpec.steer`、由 executor 渲染为最高优先级指示块；stop/abort 后未跑尾部统一标 `SKIPPED`），经 `InteractionRegistry` 与 `POST …/interactions/{id}` resolve；事件 `plan_review_required`/`plan_review_resolved` 入 journal 可回放；前端见 [`前端UX设计.md` §三/§五](/docs/04-前端/前端UX设计.md)。**✅ 2b 已落地**：turn 级落盘（`paused_turns` 帧）+ `POST …/resume` 续跑（**纠正设计：不加** `RunPhase.PAUSED` 第三终态，回合级落盘，见 §暂停与恢复）。⏳ 余项：跨进程 Redis（多 worker）+ 治理强制层（声明即必停、非 CEO 自声明，见 [`../07-规划/远期规划.md` §2.3](/docs/07-规划/远期规划.md)）。

> **勿与工具审批混淆**：`approval_required` / `approval_resolved` SSE 事件**不是**检查点，而是**工具审批闸门**（GRANTABLE 工具暂停待用户授权），已落地（按 `settings.approval_gate_enabled` 开关）。CEO 自身不持 `GRANTABLE` 工具，故实际在**本地模式 worker** 层生效（worker 继承 CEO 门，双模式 P2d），云端 worker 不 gate（隔离沙箱）。审批语义见 [`../05-平台与运维/安全权限与治理.md` §三](/docs/05-平台与运维/安全权限与治理.md)。三者（审批 / `ask_user` 检查点 / 本地工具）现共用 `runtime/interaction.py` 的 `InteractionRegistry`（§18.6 ClientRequestBridge）同构挂起-恢复，单一 resolve 端点 `POST …/interactions/{id}`（按 kind 判别）。

> **开工提案卡是 `ask_user` 的一种形态**：CEO 的开工提案卡（开场引导）是 `ask_user` 的「开场味」内容形态，**与途中拍板共用同一挂起机制**——曾有独立的非挂起 `kickoff` 工具，开发期已并入 `ask_user`、`kickoff_proposed` 事件已删。本原语里唯一的**终态** `ToolEffect.INTERACT` 是用户选「停止」时优雅收口本回合；提交则是 `CONTINUE` 续跑。决策分档与「为何不做成两个工具」见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)。

### 失败与取消

可重试错误（超时 / 429 / 5xx）退避重试；不可重试错误跳过该 step 或升级用户；关键 step 失败时取消传播到所有下游依赖。完整收敛治理（重试 / 熔断 / 早停 / 反思）见 §十四。

### 性能约束

| 指标 | 约束值 |
|---|---|
| 最大并行 Agent | 8（`max_parallel`：`DEFAULT_MAX_PARALLEL` 单波 / `MAX_PARALLEL_DELEGATIONS` 整树，二者同步） |
| 单次 delegate 最大步骤数 | 10（`MAX_DELEGATION_TASKS`，超出截断） |
| 事件传播延迟 | < 50ms（目标） |

### Agent 间产物传递

每次执行在调度器内持有各 worker 产物，供下游依赖注入读取。

> **实现现状**：`WaveScheduler.completed[run_id]` 持有各节点 `RunState`，下游按 `depends_on` 取上游 `RunState.content`（按 `result_handling` 全文 / 摘要）。计划热修改由 CEO 多次调 `delegate` 增量追加（§十八 `adaptive`）。

## 十二、SSE 事件协议 ✅ 已确定

后端 → 前端的实时通信采用 SSE（Server-Sent Events），定义标准事件类型。

### 事件清单

> 真相源：后端 `runtime/events.py` 的 `EventType` + 前端 `types/events.ts`（二者已对齐，共 28 类）；下表为语义说明，新增/调整事件须同改两处与本表。

| 事件 | 触发时机 / 语义 |
|------|---------------|
| `message_start` | 助手回合开始 |
| `turn_saved` | 用户消息落库后即发（模型运行前），回传权威 `user_message_id`——前端据此把乐观气泡换成真实行 id；中途失败重试从已存回合重生成（不重发用户消息） |
| `content_delta` | 文本增量 |
| `reasoning_delta` | 推理增量（思考模式） |
| `tool_progress` | CEO captain 正在拼装某个工具调用的**参数**（主要是 `delegate` 任务书）：载 `tool_name` + 已流式参数字符数。气泡级，是 `run_tool_progress`（run 级，worker 用）的孪生——captain 的声音走气泡，且大 `delegate` 调用在 `run_plan` 之前就拼装（此时尚无团队图，run 级事件会被前端丢弃），故单独发它驱动气泡的「正在生成 {工具}…」实时行，补上 delegate 前的空白期。**纯传输不入 journal**（调用执行后由气泡正文/团队图接管） |
| `tool_use_start` | 工具开始执行 |
| `tool_use_end` | 工具执行完成 |
| `approval_required` | ✅ 工具审批闸门：GRANTABLE 工具暂停待用户授权（CEO 路径；worker 委派路径不 gate） |
| `approval_resolved` | ✅ 审批落定（approve / approve_always / approve_always_files / deny；超时=deny），前端清除内联提示 |
| `checkpoint_required` | ✅ CEO 检查点：调 `ask_user` 暂停回合征询用户（统一开场引导 + 途中拍板，载 `question` / `context` / `assumptions` / `questions` / `style_options`）。**入回合日志**（`_JOURNAL_EVENT_TYPES`），故可随消息回放——区别于纯瞬态的 `approval_*` |
| `checkpoint_resolved` | ✅ 检查点落定（continue / adjust / stop / timeout；`note` 载补充/停止收尾语、`selected` 载勾选项），前端把内联检查点卡片翻为已决态 |
| `plan_review_required` | ✅ DAG 结构化挂起：`checkpoint_after` step 完成且下游仍待跑，波间暂停待计划评审（continue/adjust/stop） |
| `plan_review_resolved` | ✅ 计划评审落定（continue/adjust/stop/timeout；adjust 将备注注入未跑下游 `RunSpec.steer`） |
| `workspace_op_required` | ✅ 本地工作区 op 通道（双模式 P2）：服务端 `LocalWorkspace` 请求绑定桌面端对真实本地目录执行 op（read/list/grep…）并回传结果（keyed by `request_id`）。**仅传输、不入团队 journal**，仅本地模式出现 |
| `handoff_snapshot_done` | ✅ 本地→云 handoff（P2e/e1）：本地工作区经通道归档并快照到对象存储，载新 `snapshot_id`；handoff 专用流上一次性发出 |
| `handoff_job_started` | ✅ 本地→云 handoff（P2e/e2）：基线快照完成、云端团队任务已派发，载 `job_id`（前端轮询状态）；SSE 关闭后云端任务后台续跑 |
| `handoff_apply_done` | ✅ 本地→云 handoff（P2e/e3）：所选结果改动经通道写回本地，载逐文件结果（applied/skipped/conflict/error）+ 计数 |
| `run_plan` | 预声明一批 run 节点（DAG 规划完成时；每节点带 `parent_run_id`，供前端图在 `run_started` 前即按委派父子成组） |
| `run_started` | 一个 Agent run 开始（编排步骤与子 Agent 的统一节点） |
| `run_output_delta` | run 自身答案文本增量 |
| `run_reasoning_delta` | run 自身思考链增量（run 级归属，与 `run_output_delta` 对称）：仅 worker 用，承载 worker 思考全文。CEO captain 根 run 的思考走气泡（`reasoning_delta`），不归 run 级 |
| `run_tool_progress` | worker 正在拼装某个工具调用的**参数**（如 `file_write` 的文件正文）：载 `tool_name` + 已流式参数字符数。这些字节既非 content 也非 reasoning，且 `tool_use_start` 要等参数拼完才触发，否则写大文件的几分钟里节点全程空白——故单独发它驱动节点/详情的「正在生成 {工具} · N 字」实时行。**纯传输不入 journal**（节流按参数增量发；重载时该 run 由 journal 的 `tool_use_start/end` 显示成稿调用，实时进度已无意义） |
| `run_completed` | run 成功完成 |
| `run_failed` | run 失败 |
| `run_progress` | 一批 run 的聚合进度 |
| `message_end` | 回合结束（含 `finish_reason` / usage） |
| `error` | 不可恢复错误 |
| `title_generated` | 会话标题生成 |
| `citations` | 本回合 `web_search`/`read_url` 来源聚合去重，emit 于 `message_end` 前；单 Agent 路径经 `CHAT_CITATION_HINT` 规范 `[n]` 角标与卡片下标对齐，团队 worker 不注入 |

### finish_reason 枚举

| 值 | 含义 |
|---|---|
| `end_turn` | 正常完成 |
| `max_rounds` | 达到最大轮次限制 |
| `degraded` | LLM 连续返回空响应（⏳ 枚举已定义于 `FinishReason.DEGRADED`，当前未 emit） |
| `error` | LLM 不可恢复失败 |
| `cancelled` | 手动取消或断开 |

### 契约生成策略

> **实现现状**：⏳ 未接入 CI。`.github/workflows/ci.yml` 当前仅 ruff + pytest + 前端 lint/test，无 dataclass→TS 自动生成与 `git diff` 门禁。

后端是 SSE 类型的唯一真相源。目标做法：
- 后端用 dataclass 定义每个事件的 payload schema（声明 = 构造同一对象，杜绝漂移）
- 由脚本反射 dataclass 自动生成前端 TypeScript interface
- CI 门禁：重跑生成器 + `git diff --exit-code`，拦契约漂移

## 十三、执行管线全貌 ✅ 已确定

> 从 HTTP 请求到 SSE 输出的完整后端调用链。

### 端到端流程

HTTP 请求经 `conversation/service.py` → `runtime/pipeline.py` ReAct 循环 → SSE 事件流出。

### Phase 1: Prepare

CEO 只读/检索子集 + `delegate`；worker 全集固定注册；`AgentResolver` 为 Phase 2 方向。

**历史重建原则**：只回放 user/assistant 文本。工具 I/O 与委派详情属展示遥测（持久化供前端详情面板），不回放进 LLM 上下文——避免跨轮累积烧 token、撑爆窗口。

### Phase 2: Execute（ReAct 循环）

见 §十四 详述。

### Phase 3: Finalize

Finalize 在 pipeline 外由 `stream_chat` 执行；⏳ 无 Turn 表、无长对话摘要归档。

**断连收尾契约**：各步骤独立 `try/except`，失败只 warning，不中断已完成的 SSE 流。刻意「能存多少存多少」而非全有或全无——用户已离开，保住已产生的消息比元数据一致性更重要。

### Trace 关联

> **实现现状**：⏳ `trace_id` 跨链路与 NATS 未实现。

一次用户交互跨多个执行上下文（HTTP、后台 worker、委派 worker）。目标：用统一 `trace_id` 作关联键，在管线入口铸一次，随 NATS payload 流到 worker。排查时 `grep trace_id=<id>` 即得全链路。

## 十四、ReAct 循环与收敛治理 ✅ 已确定

> **实现现状**：`engine.react_loop` = 轮次上限（`ModelProfile.max_rounds`）+ LLM provider 层 3 次重试（`llm/deepseek.py`，429/5xx/timeout）+ **收敛治理 `LoopController` 已接入**（重复调用 / A-B-A-B 交替 / 重复失败的滑窗检测 → 两段式 `NUDGE` 反思注入 / `FINALIZE` 强制收口）。仍缺：引擎级 fallback 模型、工具 30s 超时、`FinishReason.DEGRADED`（枚举存在但未 emit）、结构化 `RoundOutcome`/`LoopDirective` 协议。**工具审批已在执行层生效**：`engine._execute_tools` 对 `GRANTABLE` 工具经 `ApprovalGate` 挂起待授权（按 `settings.approval_gate_enabled`）；CEO 自身已不持有 `GRANTABLE` 工具（协调者工具边界），故审批实际在 worker 层生效——本地模式 worker 继承 CEO 的门（双模式工作区 P2d），云端 worker 不 gate（隔离沙箱）。

### 基本循环

`message_start` 后逐轮迭代至 `profile.max_rounds`；✅ GRANTABLE 审批挂起；⏳ 无引擎级 fallback、无 30s 工具超时、轮顶查取消等为目标态。

### 收敛治理（LoopController）

> **实现现状**：**部分落地**。`loop_controller.py` 已实现并接入 `react_loop`：滑窗检测三类机械循环（重复调用 / A-B-A-B 交替 / 重复失败）→ 两段式干预（首次 `NUDGE` 注入锚定「观察到的重复事实」的反思，再次 `FINALIZE` 强制无工具收口）。下表为完整目标机制，其余行（fallback 模型 / 空响应 degraded / 工具 30s 超时 / 结构化 `RoundOutcome`·`LoopDirective` 协议）仍为目标态。

所有「循环要不要继续」的判断统一收敛到 LoopController，引擎每轮交结构化 `RoundOutcome`，按 `LoopDirective` 行动：

| 机制 | 阈值 | 行为 |
|------|------|------|
| 重复调用检测 | 相同签名连续 3 轮（滑窗） | ✅ 锚定事实的 `NUDGE` 反思；再次触发则 `FINALIZE` 强制无工具收口 |
| A-B-A-B 交替 | 两动作振荡连续 3 轮 | ✅ 同上两段式干预 |
| 重复失败检测 | 同工具同方式失败连续 3 轮 | ✅ 同上两段式干预 |
| LLM 重试 | 3 次指数退避 | ⏳ provider 层已落地；引擎级 fallback 未落地 |
| Fallback 模型 | 主模型耗尽 | ⏳ 切 fallback_model，裁剪 system prompt |
| 工具失败熔断 | 累计失败 2/3 次 | ⏳ 2 次提示勿重试；3 次本轮停用 |
| 无产出早停 | 连续 3 轮全失败且无正文 | ⏳ `finish_reason=unproductive` |
| 反思注入 | 第 4 轮起每 3 轮 | ⏳ 注入进度复盘 prompt |
| 空响应 | 连续 2 轮 | ⏳ `finish_reason=degraded` |
| 工具超时 | 30s | ⏳ `[ERROR]` 前缀返回 |
| 协作取消 | CancellationToken | ⏳ 沿委派树向下传播 |

### SSE 桥接

执行侧与输出侧经**无界 `asyncio.Queue`** 解耦。背压只对可丢弃事件（`content_delta` / `reasoning_delta`）生效，生命周期/终止事件保证送达。

**前端兜底对账**：消息落定时递归收口所有悬挂的 running/queued run 节点——后端可靠送达是主路径，前端对账是 last-resort 兜底。

### 暂停与恢复（回合级落盘续跑）

> **实现现状**：✅ Phase 2b 已落地。**纠正设计：不引入 `RunPhase.PAUSED` 第三终态**——结构化挂起暂停的是**整个回合**（CEO loop + delegate 子 DAG），而非单个 Run 节点（已完成的 worker 是真 COMPLETED、未跑的是真 pending）；硬塞 `paused` 终态会污染调度器 / 执行器 / 计费每个 phase 分支且语义错位。改用**回合级**落盘（`paused_turns` 一行 = 一个挂起回合），Run 模型零改动。

挂起回合走**混合「实时 + 持久 backstop」**：连着的客户端仍用进程内 `InteractionRegistry` 的 `await`（2a 体验字节不变），同时在 `await` **之前**把整帧（`TurnSuspension`，以 `kind` 判别 `plan_review` / `ask_user`）落到 `paused_turns`；实时 resolve / timeout 后删帧，断连 / 崩溃则帧留存可续。

- **持久缝**：`paused_turns` 一行 = 一个挂起回合（PK = 回合 assistant `message_id`，resume 复用同 id），`frame` JSONB 存 CEO transcript + plan（带已铸 run_id）+ seed_completed + journal。
- **捕获**：`captain_transcript` ContextVar 在 `react_loop` 执行工具前发布 live `messages`，挂起面（delegate checkpoint hook / `AskUserTool`）读它快照。
- **恢复**：`POST …/messages/{mid}/resume`（原子 claim 杜绝二次恢复）重建帧 → `seed_journal` 回放整图 → 按 `kind` 分流结算跑尾部 → 续跑 CEO loop 写回复；重开会话经 `GET …/paused` 列待恢复帧渲染卡片。
- **计费**：整回合**一次**计费——实时路完成则正常落账删帧；断连路只在 resume 完成时落账（断连时实时路从未落账）。
- **TTL**：`paused_turns` 7 天 idle 清理（镜像 `session_retention`）。
- **断连兜底**：含**未持久挂起点**（如 approval，transport-only 不 journaled）的回合被取消时，把已完成 worker 产出落成一条 `finish_reason="cancelled"` 的「未完成」消息（零重放）；与 resume 由「挂起事件是否 journaled」天然区分、不重复。
- ⏳ 余项：跨进程 Redis（多 worker 实时分发）+ 治理强制层（见 [`../07-规划/远期规划.md` §2.3](/docs/07-规划/远期规划.md)）。

## 十七、提示词架构 ✅ 已确定

### 两个互不相交的世界

| | World A — Agent 主提示词 | World B — 内部工具型提示词 |
|---|---|---|
| 是什么 | 面向用户的对话 Agent system prompt | 平台内部的窄任务 LLM 调用（标题/分类/摘要…） |
| 触发者 | 每个 Agent、每个 turn | 平台代码按需 |
| 形态 | 身份 + 技能 + 规则 + 上下文，条件装配 | 固定模板 + 少量变量，单次调用 |
| 管理方式 | PromptAssembler（✅ 已落地） | 注册表 + 片段库（⏳ 目标态，当前各自手搓） |

**分离原因**：两者关注点根本不同。强行共用只会互相拖累。

### World A：PromptAssembler 组装顺序

基座 + CEO/worker 条件叠加；无 workspace_ctx 时按 agent_id 实例内缓存。

降级模式：低优先级规则过滤、文档截断、Skills 裁掉；Rules 保留（安全/合规约束越降级越要留）。

> **实现现状（提示词正文，统一中文）**：基座确立 AgentCore 身份与「结论必须基于工具实际返回、绝不编造」原则；CEO 叠加团队管理者与引用规范 hint；worker 叠加「一次性、隔离上下文、不能反问、不能再委派」自我认知段——因 worker 拿不到完整对话、无澄清回路，须明确「信息不足就合理假设并交付」。

### World B：注册表 + 片段库 ⏳ 目标态

**目标态**：内部窄任务提示词收敛到统一的注册表 + 片段库——`PromptTemplate` / `fragments` / `registry` / `catalog`，key 命名 `component.task`，`{{var}}` 渲染，fragments opt-in。

> **实现现状（⏳ 未落地）**：注册表 / 片段库尚未实现，`runtime/prompt.py` 目前只承载 World A（基座 + CEO/worker hint 装配）。当前每个内部 LLM 窄任务调用**各自手搓**：模块内一个 system 常量 + 一个 Python 渲染函数，直接拼成 `LLMMessage`。两处现状：会话标题（`memory/conversation_title.py`：`_TITLE_SYSTEM_PROMPT` + `_render_title_prompt`）、用户记忆抽取（`memory/user_memory.py`：`_EXTRACT_SYSTEM_PROMPT` + `_render_extract_prompt`）。第三处内部调用出现、或手搓样板开始相互拖累时再行收敛——当前两处尚不构成收敛收益。

## 十八、运行时核心模型 ✅ 已确定

> **实现现状**：本节为**目标模型**，部分已落地。**Interaction 统一挂起原语已落地**（进程内 `runtime/interaction.py` 的 `InteractionRegistry` ＝ §18.6 ClientRequestBridge，收编审批 / ask_user / 本地工具 / **`plan_review`（2a 波间结构化挂起）** 四 kind，单一 resolve 端点 `POST …/interactions/{id}`）；**`checkpoint_after` 波间挂起（2a）已落地**（`WaveScheduler.on_checkpoint` + delegate 协调器）。**收敛治理 `loop_controller.py` 已落地并接入**。**持久挂起续跑（2b）已落地**（回合级 `paused_turns` 帧 + `POST …/resume`，不加 `RunPhase.PAUSED`，见 §暂停与恢复）。**Turn Journal 地基已落地**：每回合执行事实流持久化到 append-only `turn_journal` 表（唯一事实源，§18.3），`messages.runs` 列删除、回放载荷读取时投影；暂停的 journal-so-far 也落 `turn_journal`（`paused_turns.frame` 仅余 resume 控制态）；`Journal` 端口（§18.6）已 Protocol 化。仍为 Phase 2：按 `round_boundary.fold` 从 journal 重建暂停快照的 plan/completed/transcript、LLM 窗口投影、跨进程挂起（多 worker 的 Redis BLPOP）。

> 运行时收敛在三个一等模型上。每个模型把一族重复子系统坍缩成单一形状。

### 18.1 三模型总览

| 模型 | 职责 | 解决的问题 |
|------|------|-----------|
| **Interaction** | 唯一挂起原语：server 停下等 client 回值 | 统一审批/ask_user/本地工具/计划评审四套同构 BLPOP |
| **Turn Journal** | 唯一回合事实源：append-only 事实流 | 消除「回合无事实源」导致的历史回放/快照/消息完整性补丁族 |
| **Run** | 唯一执行单元：一棵 Run 树 | 统一委派/DAG/编排/路由四套并存的编排子系统 |

依赖关系：Interaction 最小独立；Journal 是 Run 的地基（事实留痕在 journal）；Run 落在两者之上。

### 18.2 Interaction（统一挂起原语）

> **实现现状（✅ 进程内已落地）**：统一挂起原语 = `runtime/interaction.py` 的 `InteractionRegistry`（§18.6 ClientRequestBridge），收编审批 / `ask_user` / 本地工具 / **`plan_review`** 四 kind 的「挂起-登记-恢复-回值」：单一注册表（`create` / `resolve` / `discard` / `get` / `list_pending`，按 `kind` 标记）+ 单一 resolve 端点 `POST …/interactions/{id}`（按 kind 判别 body）。per-kind 差异留在四个薄面（`ApprovalGate` / `AskUserTool` / `WorkspaceChannel` / delegate `on_checkpoint`）。**`paused` 落盘续跑（2b）已落地**（回合级 `paused_turns` 帧 + `POST …/resume`，不加第三终态，见 §暂停与恢复）；**跨进程等待**（Redis BLPOP，多 worker）仍为目标态。

```
InteractionRequest:
  id            # 请求-响应关联键
  kind          # approval | ask_user | client_tool | plan_review
  conversation_id / turn_id / run_id
  payload       # 各 kind 的请求体
  timeout_s
  scope         # call | turn（「本轮内都允许」语义泛化到原语层）
```

一套机制替换四套：统一等待器、统一挂起登记（`list_pending`）、统一恢复端点、统一回值端点。per-kind 差异降为策略位（durable / 键粒度 / at-rest 脱敏）。

### 18.3 Turn Journal（唯一事实源）

> **实现现状（地基已落地，投影面分批接入）**：`turn_journal` 表（append-only，主键 `turn_id + seq`，`turn_id == assistant message_id`）+ `Journal` 端口（§18.6，Postgres 实现 `db/repositories.py::TurnJournalRepository`）+ `runs`↔事实投影（`runtime/journal.py` 的 `entries_from_runs` / `runs_from_entries`，互为逆）已落地：**每回合执行事实流落库为唯一持久源，`messages.runs` 列已删除**，assistant 消息的回放载荷（`MessageDetail.runs`）在读取时由 journal 投影（消息列表端点一次批量 `load_map`，无 N+1）。当前覆盖 run/tool/interaction 事件 + 单 Agent「思考·工具」步 + `turn_end`。**暂停的 journal-so-far 也已落 `turn_journal`**：暂停时由 `save_paused_turn` 写入、resume 时 `claim_paused_turn` 从中 seed 投影（`paused_turns.frame` 仅余 resume 控制态 plan/completed/transcript，不再存 journal 副本）。**清理走应用级级联**（无 DB 外键，循仓储约定）：随宿主消息/会话硬删连带清（删会话 `hard_delete`、regenerate/edit 截断 `delete_after`、单删消息 `delete_by_id`，后两者按 `conversation_id` 作用域防 IDOR），弃用暂停回合由 TTL 扫一并清——`turn_journal` 不悬挂、不孤儿。仍为目标态：按 `round_boundary.fold` 从 journal 重建 plan/completed/transcript（暂停快照的剩余部分）、以及 LLM 窗口投影——**受阻于现 journal 为「展示级」**（`run_completed` 只发摘要、CEO transcript 不入流），须先加执行级事实（`llm_call`/`message_final`/全文 content），属独立初创，见 [远期规划 §1.1](/docs/07-规划/远期规划.md)。

每个 turn 一条 append-only 条目流（主键 `turn_id + seq`），九类事实：

```
kind ∈ turn_started | round_boundary | llm_call | tool_call | interaction
      | note | run_event | message_final | turn_end
```

**一切皆投影**：

| 消费面 | 来源 | 现状 |
|--------|------|------|
| SSE 流 | 引擎实时 emit（流式增量不入 journal） | ✅ |
| 持久化消息行 | journal 投影器生成 | ✅ `runs_from_entries` 读取投影 |
| 暂停快照 | `round_boundary.fold` | journal ✅ 落 `turn_journal`（resume seed 投影）；plan/completed/transcript 的 fold 重建 ⏳ |
| 跨轮历史回放 | 文本 + interaction 答案投影 | ⏳ 目标 |
| LLM 窗口 | journal 投影（correct-by-construction） | ⏳ 目标 |

### 18.4 Run（唯一执行单元）

执行形状不再是离散「模式」而是数据，由 `depends_on` 边自然落定：

- 单 Agent = 单节点
- `fan_out` = 单波 + captain 汇聚
- `pipeline` = 线性链 + captain 汇聚
- `adaptive` = 空计划 + captain 动态追加
- 单次 delegate = 追加一个节点
- best-of-N 择优 = 某节点 `candidates>1`（`RunPolicy` 策略位，非独立 kind）
- 辩论/审查 = 带 `stance`/`group`/`round` 标记的普通 AGENT DAG（非独立 kind）；真·多轮辩论（Arena）亦是此 DAG 模式（跨轮 `depends_on`，已落地），独立 arena 子系统已否决（见 [`Agent协作模式.md` §7.4](/docs/03-AI核心/Agent协作模式.md)）

> **决策（CEO = 根 Run 节点 ✅）**：CEO chat loop 即本回合 `CAPTAIN` 根 Run；content/reasoning 走气泡级 `content_delta`/`reasoning_delta`（非 run 级）；captain 一次定价、落真实台账行。**否决**旧的 `synthesis` 零成本伪 run。

> **决策（嵌套委派）**：worker 默认叶子；`can_delegate=true` 才获 `delegate`（**默认关、显式开**，见 [`编排器与CEO主Agent.md` §2.4](/docs/03-AI核心/编排器与CEO主Agent.md)）。**硬上限 `depth ≤ 2`**（`MAX_DELEGATION_DEPTH`）：深度 2 永不获 `delegate`，树不可再深。

> **决策（可恢复运行 `RunSession`）✅**：一次 worker run 执行后不丢弃，保留完整 transcript = `RunSpec` / `RunState` 的**可恢复延伸**；CEO 经 `revise` 在保留 transcript 上追加指令、重跑 `react_loop` 即「修订」（同轮 / 跨轮 / 跨进程留人，双 miss 回落重派）。统一收编自动返工 / CEO 热修 / 重派兜底三条接缝。详见 [`多轮编排与队员热修.md`](/docs/03-AI核心/多轮编排与队员热修.md)。

### 18.5 引擎纯化

三条去特判手段：

1. **工具效应模型**：`ToolResult(text, effect)`，`effect ∈ Continue | Handoff | Interact`。引擎只解释效应，`delegate`/`ask_user` 不再是特殊名字
2. **显式 ToolContext**：工具签名携 context（user/conv/turn 等），消灭 `set_runtime_context` 全局大杂烩
3. **去工具名特判**：引擎按能力位（`has_delegation_tool` 等）而非工具名判断行为

### 18.6 端口契约（宿主注入）

引擎面向宿主的 10 项端口（本地/云端同码、宿主注入）；契约在代码里镜像为 `runtime/ports.py`（**ClientRequestBridge / Journal 已落地**、EventSink 已是端口，余项仍为其具体实现、待 Sidecar 取用时再 Protocol 化）：

| 端口 | 定位 |
|------|------|
| Journal ✅ | 引擎唯一持久化出口；`turn_journal` 表 + `TurnJournalRepository`，`runs` 读取时投影自它（§18.3） |
| EventSink ✅ | 渲染流出口（流式增量 + 离散事实实时投影）；`runtime/events.py`，`ports.py` 再导出 |
| InferenceGateway | LLM 调用 |
| ArtifactStore | 归档/寻回 |
| PauseSignal | 暂停信号（Redis flag） |
| ClientRequestBridge ✅ | 统一挂起原语（`runtime/interaction.py`；审批 / ask_user / 本地工具 / **plan_review（2a）**） |
| ConversationStore | 消息持久化（投影写入） |
| BillingSink | 计费事实投影 |
| DelegationTransport | 跨进程子树传输 |
| SnapshotStore | 已被 Journal 吸收 |

### 18.7 一轮一网关（Gateway 传播原则）

当用户自带 LLM 凭据时，整棵多 Agent 委派树必须在**同一把网关**下运行，避免 split-brain（captain 跑用户 key，委派出去的子 Agent 回落平台 key）。

**规则**：在 Turn 最早阶段（工具装配之前）一次性解析 `effective_gateway`，随 Run 上下文贯穿整棵执行树。`InferenceGateway` 端口接收的凭据由此确定——直答、团队编排、恢复各路径读同一把。

此原则与凭据来源开关无关（无论平台供还是用户供），是执行语义的不变量。
