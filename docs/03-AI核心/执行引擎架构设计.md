## 核心定位

执行引擎是 CEO 主 Agent 与 worker 实例之间的调度中枢。它接收 CEO 经 `delegate` 下达的子任务（`build_run_plan` 据 `depends_on` 建 DAG），解析依赖图，管理 worker 生命周期，协调并行/串行执行，处理失败与取消，并向 UI 推送实时状态更新。

## 一、基础概念（DAG 调度）

> DAG 调度概念提要；运行时以 §二~§四 为准，§八 为目标模型。以下只保留代码看不直观的设计约定。

### 步骤状态与调度

计划是 DAG：每个 step 声明 `depends_on`，执行引擎扫描「依赖已满足且未启动」的 step 并发启动（受 `max_parallel` 限制）。步骤状态 `queued → running → completed`，异常分支 `failed` / `skipped` / `cancelled`（枚举见 `runtime/runs/types.py` 的 `RunPhase`；失败重试由 `RunPolicy.on_failure=retry` 在 `runs/wave.py` 内部完成（硬上限 3 次退避），对外仍以 `FAILED` 收口并 emit `run_failed`；级联跳过 / stop 后未跑尾部物化为 `SKIPPED` 并 emit `run_skipped`、中途取消（redirect/stop）emit `run_cancelled`——二者均 DURABLE，重载图上呈「未执行 / 已停止」而非假排队/假运行）。并发模型为 asyncio 协程——多 Agent = 多 asyncio Task 共享事件循环（Agent 本质是 I/O 密集的 LLM 调用，协程足够）。

> **调度埋点量化 ✅**：为验证连续调度「让并行真正发生」（而非凭感觉），`WaveScheduler.run` 每次 run 回灌一条 `BatchMetrics`——并发峰值 / 平均并发度（`busy_ms÷wall_ms`）/ 槽位饥饿 / 按 reason 拆的边界 fire 数 / escalation 计数等（无晚绑定·escalation·checkpoint 的 plan 全为 0）。**设计取舍**：用 `metrics_sink` 而非返回值或直接打日志——调度器对宿主无感、cancel 路径不回灌（先 re-raise）；由宿主 `delegate` 的 `drive` 取回并打 `delegate.completed` 结构化日志（含 `avg_parallelism` / `scope_ratio`）。→ 见代码：`runtime/runs/wave.py`、`runtime/runs/types.py`（`BatchMetrics` 全字段）、`runtime/delegate/drive.py`。

### 检查点决策语义

> **本篇权威**：检查点 / `plan_review` / 2b 续跑语义以本节与 §暂停与恢复 为准；编排器、协作模式等文档仅外链此处。

检查点分两类，**实现现状不同**：

- **CEO `ask_user` 检查点（✅ 已落地）**：CEO 主动调内置工具 `ask_user` 暂停回合征询用户——CEO **唯一的发问原语**（开场引导与途中拍板共用一卡一机制）。语义、字段与阻塞/非阻塞矩阵见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)。载 `message`（必填）+ 可选 `context` / `assumptions` / `questions` / `style_options`；桌面端以提交/停止两态作答，答复回流 CEO ReAct 循环；`stop` 走 `ToolResult.terminal` 优雅收口。**挂起即收口（②）**：到达检查点即**落帧并收口终止**（`ToolEffect.SUSPEND → FinishReason.PAUSED`，进程内 resolve Future 永不 park），经**单一冷路** `POST …/resume` 续跑——不再 `POST …/interactions` 原地解析；问答入 journal 可回放。属 `ToolCategory.INTERACTION`（非 ORCHESTRATION），仅在 `settings.checkpoint_gate_enabled` 且有交互用户时装配，worker 路径不给。
- **DAG `checkpoint_after` 结构化挂起（✅ Phase 2a 已落地）**：step 带 `checkpoint_after` 且 `COMPLETED`、下游仍待跑时，`WaveScheduler` 在波间 `await` `plan_review` 交互（`kind=plan_review`，continue/adjust/stop——adjust 把备注作为 steer 注入未跑下游的 `RunSpec.steer`、由 executor 渲染为最高优先级指示块；stop/abort 后未跑尾部统一标 `SKIPPED`）；**挂起即收口（②）**：检查点在波边界**落帧并收口终止**（`SUSPEND→PAUSED`），不再 `POST …/interactions` 原地解析，且**仅顶层 `depth==0` 设检查点**（嵌套子团队直接放行）；事件 `plan_review_required`/`plan_review_resolved` 入 journal 可回放；前端见 [`前端UX设计.md` §三/§五](/docs/04-前端/前端UX设计.md)。**✅ 2b 已落地**：turn 级落盘（`paused_turns` 帧）+ `POST …/resume` 续跑（**纠正设计：不加** `RunPhase.PAUSED` 第三终态，回合级落盘，见 §暂停与恢复）。**协调态例外**：有 `CoordinationSession` 时波边界只发 `BOUNDARY_YIELD`（不写 `TurnSuspension` / 不 seal / 不发 `plan_review_required` 收口）；用户拍板走 `ask_user`。⏳ 余项：跨进程 Redis（多 worker）+ 治理强制层（声明即必停、非 CEO 自声明，见 [`../06-规划/远期规划.md` §2.3](/docs/06-规划/远期规划.md)）。

> **勿与工具审批混淆**：`approval_required` / `approval_resolved` SSE 事件**不是**检查点，而是**工具审批闸门**（GRANTABLE 工具暂停待用户授权），已落地（按 `settings.approval_gate_enabled` 开关）。CEO 自身不持 `GRANTABLE` 工具，故实际在**本地模式 worker** 层生效（worker 继承 CEO 门，双模式 P2d；`worker_gate_applies` 仅 local 为真）；云端执行类工具按**沙箱→审批姿态**分流（`runtime/sandbox_approval.py` 三态：local → `REQUIRES_AUTH`、云端无沙箱 → `UNAVAILABLE` 不注册、`GVISOR_ENABLED` → `AUTO_PASS` 免审批）。审批语义与策略表见 [`../05-平台与运维/安全权限与治理.md` §三](/docs/05-平台与运维/安全权限与治理.md)。审批 / 本地工具 / worker 升级 / 辩论轮共用 `runtime/interaction.py` 的 `InteractionRegistry`（§8.6 ClientRequestBridge）同构挂起-恢复，单一 resolve 端点 `POST …/interactions/{id}`（按 kind 判别）；**`ask_user` / `plan_review` 检查点已挂起即收口（②）**——改走 `POST …/resume` 冷路、其 resolve schema 已从该端点移除。

> **开工提案卡是 `ask_user` 的一种形态**：开场与途中共用同一挂起机制。→ 见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)。

### 受监督的波循环（晚绑定 + 边界让出）✅ 已落地

> **本篇权威**：晚绑定 / 波边界让出 / `replan` 续跑的**执行语义**以本节为准；CEO 侧 `replan` 工具形态见 [`编排器与CEO主Agent.md` §一 `replan` 原语](/docs/03-AI核心/编排器与CEO主Agent.md)。

**解决的痛**：worker 职责在 CEO `delegate` 那一刻就绑定死，但下游真正要干的活往往得等上游产物落地才清楚——团队闷头按可能过时的初始计划做完（「计划漂移」）。把执行模型从「CEO 下完计划即缺席」改为「**CEO 是波边界的监督者**」：`build_run_plan` 一次建全 DAG（开局全貌可见），节点可**晚绑定**，`WaveScheduler` 自主跑波、只在**决策边界**把控制权交回 CEO 定稿 / 纠偏后续，续跑同一张图（不重建）。这是 §一 检查点语义的推广——检查点只是边界的一种。

**形态**：

- **晚绑定节点**（`RunSpec.bind_after_deps`）：spec 关键字段先占位，依赖落地后由 CEO 在边界定稿（复用 `steer` 的 in-place mutate 范式）；`_select_ready(defer_bind=)` 绝不调度未定稿节点。
- **边界判据**（`BoundaryReason ∈ {CHECKPOINT, BIND, SCOPE}`）：① `checkpoint_after`（让用户把关）；② 依赖已就位、待定稿的晚绑定节点（让 CEO 定稿）；③ 已完成节点带未消费的 `escalate kind=scope` 偏离信号（让 CEO 纠偏）。
- **边界结果**（`BoundaryOutcome ∈ {PROCEED, YIELD, ABORT}`）：`YIELD` = 软暂停（复用 `should_stop` 语义：排空 in-flight、返回 partial、尾部不 skip），把控制权交回 CEO 主循环。
- **续跑**：`delegate` 的 `_drive` 收到 `YIELD` 返**非终态** ToolResult（CONTINUE）+「计划已让出」简报给 CEO，暂存 `(plan, completed)`；CEO 经 `replan` 定稿 / 纠偏 / 追加 / 收口后，`_drive(seed_completed=…)` 续跑同一 DAG。

**双臂：同一边界，让给用户 or 让给 CEO**（按影响力分档，对齐 `ask_user` / checkpoint 心智）：

| 臂 | 触发 | 谁裁决 | 用户感知 |
|---|---|---|---|
| 让给 CEO（BIND / SCOPE） | 低杠杆：晚绑定定稿、据 escalate 微调下游 | CEO 自主 | **无感**（仅图上「计划已调整」轻痕迹——`plan_revised` 折到节点徽标「职责已定稿 / 方向已校准」，不打断，见 [`../04-前端/前端UX设计.md`](/docs/04-前端/前端UX设计.md)） |
| 让给用户（CHECKPOINT → `plan_review`） | 高杠杆：选错会让用户明显不满 / 推倒重来 | 用户 | 决策卡，挂起待答（见上「检查点决策语义」）；**协调态例外**：只发 `BOUNDARY_YIELD`，用户拍板改走 `ask_user` |

> **复用而非另起炉灶**：两臂共用 `WaveScheduler` 的边界机制 + §8.2 唯一挂起原语；让给 CEO 的臂本质是调度器在边界把控制交回 CEO 的 ReAct 循环、续跑同一 DAG——**不新增挂起子系统**、**不增委派深度**、**不碰 worker↔worker 直连**。CEO 臂走正常回合生命周期（非终态返回 = 普通 ReAct 续跑），plan / completed 由 journal 投影重建，**不需新 durable 挂起**（区别 user 臂的 `paused_turns`）。

> **偏离信号：复用 `escalate` + 轻量 `kind=scope` / `kind=dep`**：worker 发现自己 / 下游 scope 错了（`kind=scope`），或卡在一个**还不存在**的输入 / 依赖（`kind=dep`），用现有 `escalate`（**非阻塞**）加一个提示位上报（**扩展而非新原语**）；两者**同走反应臂波边界**（`_scope_pending` + `BoundaryReason.SCOPE` 一处机器）被 captain **一等消费**——`scope`→操舵已有下游、`dep`→`replan(add)` 追加产出者。**否决**「为 scope/dep 单立信号 / `InteractionKind`」：决策的是 captain、worker 只供偏离事实，单立 = 与 `escalate` 高度重叠（补丁绊线）。kind 轴语义见 [`Agent协作模式.md` §二·escalate](/docs/03-AI核心/Agent协作模式.md)。

> **成本纪律（不变量）**：无晚绑定 / 无 escalation / 无 checkpoint 的 plan，调度器一路跑到 terminal、一次 `delegate` 返回（= 今天行为、**零新增 CEO 回合**）——**CEO 回合数 = 真实决策点数，不是波数**。
>
> **协调模式例外（✅）**：≥2 worker 默认协调时 CEO 波内存活，`delegate` 立即返回；同回合再调 `delegate` 往同一张协作图追加（**一回合一张图**），不必等全队完成。成本纪律重定义为「协调回合 ≤ 必要决策点 + 预算上限」（中间完成可合并；预算耗尽只喂模板）。显式 `coordinate=false` / 单 worker / finalize / 嵌套 lead / **批含 `checkpoint_after` 且 checkpoint 闸开**（B1：把关卡须 durable 弹给用户，走经典阻塞）仍守上文零新增纪律。见 [`编排器与CEO主Agent.md` §协调模式](/docs/03-AI核心/编排器与CEO主Agent.md)。

> **turn 末仍开着的 supervised run**：CEO 拿到让出简报却没 `replan` 就结束回合（最终答复 / `MAX_ROUNDS` / 上游报错），则 turn 末按**隐式 `stop`** 收口（折算已完成工作 + 未跑尾记 SKIPPED + 释放暂停态），避免团队工作悬空漏计费 / 来源不显；无让出时 no-op。

> **持久化与跨端一致**：晚绑定占位、scope 的 `kind`/`consumed` 经快照往返保真——重建的暂停计划仍知该节点待定稿、**绝不未绑定就 dispatch**；`YIELD` 给 CEO 走内部续跑（不产生用户可见事件分类），`replan` 改图走 `plan_revised` 事件（入 journal 可回放、三端等价）。

> **对任何 captain 一致（lead 子树同享）✅**：受监督波循环不是「根 CEO 专属」——子 lead（`can_delegate`）经 `LeadSubteam` bundle 同获绑到自身 `child_delegate` 的 `replan` + 收尾折账，故 lead 也能在自己子树上「晚定稿 / 据偏离重规划」，去掉「只有根能 replan」的特例。工具形态与铸厂分层见 [`编排器与CEO主Agent.md` §2.4](/docs/03-AI核心/编排器与CEO主Agent.md)。`plan_revised` 按 `run_id` 折到正确子节点、子层共用父 `execution_id` 不串层。**协调模式 scope 例外**：非阻塞协调仅根 CEO（`depth==0`）；lead 仍阻塞 `delegate`。

> **被否决 / 暂不做**：① **worker 实体化**（临时角色 → 稳定专家实体，Phase 2，用户按下）——守在「CEO 在波边界监督」一层，对齐「无团队选择器 / 每回合自适应组队」赌注（见 [`编排器与CEO主Agent.md` §六 Agent 实体化](/docs/03-AI核心/编排器与CEO主Agent.md)）；② **2b 波内抢占 / CEO 波内重入**——默认阻塞路径仍「波内无活着的 CEO」，用波边界让出替代；**协调模式下** CEO 波内存活，阻塞 escalate 改走 CEO 仲裁（`resolve_escalation`，非 worker 抢占）；③ **运行期软护栏**（类比 `delegation_nudge`）——边界结构性决策后基本不需，「实测漏触发率高再加」。
>
> → 协调模式 as-built 见 [`编排器与CEO主Agent.md` §协调模式](/docs/03-AI核心/编排器与CEO主Agent.md) 与本文 §协调事件注入。

> → 见代码：`runtime/runs/scheduler.py`（`BoundaryReason` / `BoundaryOutcome` / `OnBoundary`）、`runtime/runs/wave.py`（`on_boundary` / `_select_ready(defer_bind=)` / `_scope_pending`）、`runtime/runs/builder.py`（`bind_after_deps` 解析 / `build_added_nodes`）、`runtime/delegate/`（`supervised.py` 让出+续跑、`boundary.py`）、`tools/builtin/delegate/tool.py`（`dispose_open_supervised`）、`tools/builtin/replan.py`、`tools/builtin/escalate.py`（`kind=scope`）、`runtime/events/run.py`（`plan_revised`）。

### 失败与取消

可重试错误（超时 / 429 / 5xx）退避重试；不可重试错误跳过该 step 或升级用户；关键 step 失败时取消传播到所有下游依赖。完整收敛治理（重试 / 熔断 / 早停 / 反思）见 §四。

### 性能约束

| 指标 | 约束值 |
|---|---|
| 最大并行 Agent | 8（`max_parallel`：`DEFAULT_MAX_PARALLEL` 单波 / `MAX_PARALLEL_DELEGATIONS` 整树，二者同步） |
| 单次 delegate 最大步骤数 | 10（`MAX_DELEGATION_TASKS`，超出截断） |
| 事件传播延迟 | < 50ms（目标） |

### Agent 间产物传递

每次执行在调度器内持有各 worker 产物，供下游依赖注入读取。

> **实现现状**：`WaveScheduler.completed[run_id]` 持有各节点 `RunState`，下游按 `depends_on` 取上游 `RunState.content`（按 `result_handling` 全文 / 摘要）。计划热修改由 CEO 多次调 `delegate` 增量追加（§八 `adaptive`）。

## 二、SSE 事件协议 ✅ 已确定

后端 → 前端的实时通信采用 SSE（Server-Sent Events），定义标准事件类型。

### 事件清单

→ 见代码：`runtime/events/types.py`（`EventType`）+ 前端 `types/events.ts`。

**处置权威**：`runtime/events/disposition.py`（`EVENT_DISPOSITION` 穷尽覆盖全部 `EventType`）。DURABLE 入 `turn_journal`；DERIVED 走专用列 / 投影；EPHEMERAL 有意不落库。

**EPHEMERAL（不入 journal）**：`tool_progress` / `tool_use_progress` / `run_tool_progress`（秒级心跳）、`content_reset` / `run_output_reset`、客户端工具往返、handoff 控制帧等。流式增量（`*_delta`）为 DERIVED——终态落列 / `message_final`，流中另有 `turn_stream_state` 快照（见 §8.3）。

**DURABLE 可回放（含用户可见过程态）**：交互卡、团队便签、`debate_round_started` / `debate_round`（辩论进行态）、`team_synthesis_preview`（协调进展预览，同 key 保最新由前端 fold）、`turn_warning`（预检横幅）等——重载经 `hydrateFromJournal` / 三端 fold 重建。

> **升级实时可见（`run_escalation`）✅**：worker 调 `escalate` 的【调用瞬间】，执行器 emit 一条 run 级 `run_escalation`，三端折到该 run 的 `escalations`（节点 ⚠️「上报」标记 + run 详情「上报待裁决」区）——让升级在【进行中】就可见，而非埋在工具行、或只随 CEO 收尾正文到达。
>
> - **引擎纯化**：经 `ToolContext.on_escalate` narrow 回调，工具不碰事件词表（事件形状归执行器）。
> - **DURABLE + `escalation_id`（统一时间线二期 D6）**：`run_escalation` 落 journal、payload 带 `escalation_id`——raised 轻行、图节点 ⚠️ 徽标与时间线 `escalation` 标记 reload 后幂等重现（消灭 live-only 漂移）；`RunState.escalations`（transcript harvest → `_format_for_ceo` 供 CEO 裁决）仍为裁决用持久副本。
> - escalate 仍**非阻塞**：报完继续按假设交付。
>
> → 见代码：`runtime/events/run.py`（`escalation_raised`）、`runtime/runs/executor.py`、`tools/builtin/escalate.py`。

### 回合级「下一步推荐」(CEO→用户) ✅ 已落地

> 实现：`memory/followups.py`（生成器）、`llm/profiles.py`（`followups` profile）、`conversation/common.py::generate_followups`、`conversation/store/cloud.py`（`_finalize_cloud` / `_finalize_local` 收尾触发）、事件 `followups_generated`（含 `message_id`）；桌面 `FollowupChips` + `attachFollowups`（按 `message_id` 匹配 `id || serverMessageId`）+ 画布 `CanvasCommandBar` 同挂；手机 `ChatPage` live `extractFollowups`（按 id 对齐）+ reload `MessageDetail.followups`。

**定位**：回合收尾后预测用户最可能想做的 2-4 件事，作为可点选的快捷追问挂在**对应那一条**助手回复下（点选即回填输入框、可改后发）。是 worker→CEO「交接简报·建议下一步」的用户侧对偶：那条把队员建议上交 CEO，这条把整回合的自然后续下达用户。

**关键契约**：

- **生成**：一次 flash 非思考 World B 窄任务（同 title），`message_end` 后在收尾块跑（off 用户阅读路径，与标题**共用一个 provider** 顺序生成）；**仅** `finish_reason == end_turn` 且正文非空才 mint（`None` / 缺省 / paused / error / cancelled / max_rounds / degraded / … 一律不 mint）。`followups` profile 比 title 的 64 tokens 宽（256），容得下 4 条短中文而不中途截断。字数硬上限 **40**（`FOLLOWUPS_ITEM_MAX_CHARS` 单一常量；prompt 对齐；超长**截断到 40 并加 `…`**，禁止整行丢弃）。
- **身份接缝**：`followups_generated` payload 带 `message_id`（与 `set_followups` 目标行一致）；客户端按 `message_id` 匹配助手行（`id || serverMessageId`）；**缺 `message_id` → no-op**，禁止挂 last fallback。Local 经 `RecordTurnResponse.followups` 回传（对标 title），outbox writeback → `applyReconcile` 按 `assistant_message_id` 写回。
- **DERIVED 持久化（回写列 · 与同胞 title 同辙）**：`followups_generated` 是**实时投递**，耐久副本落 **`Message.followups` 列**——收尾块 mint 出 chips 后，先经 `MessageRepository.set_followups`（会话内寻址、幂等）回写到**那一条助手行**，**再** emit 事件（persist-then-signal，与上面 title 回写 `Conversation.title` 同序）；reload 由 `MessageDetail.followups` → 前端重现（桌面 `toMessage` / 手机 `toMessageDetail`）。因耐久形态是**列**而非 journal 事件，三端协议 fold 对该事件仍 **no-op**、conformance ProjectedTurn 不携带它（与 `title_generated` 同类——DERIVED 走专用列，非 journal）。
- **best-effort**：空输出 / 超时 / 任何错误都退化为「无 chips」，绝不阻断或拖累它所点缀的回合；不重试 mint、不从 debrief 拼 chips、不轮询。
- **桌面 + 手机**：两端均有 live chips 与 reload 重现；画布命令栏与聊天共用同一 FollowupChips 数据源/门控。

### 长对话压缩（compaction）✅ 已落地

> 实现：`conversation/compaction.py`（压缩 runner + token 触发）、`conversation/history.py::load_chat_context`（注入）、`conversations` 三列（`compaction_summary` / `compacted_through` / `compaction_input_tokens`）。

**定位**：不是防溢出（DeepSeek 1M 不溢出），而是治两件事——**context rot**（超长上下文质量随长度下降，与缓存无关）与**缓存失效成本**（exact-prefix 缓存有 TTL，慢节奏 / 隔夜回来全量重算长历史真烧钱）。稳态成本已被前缀缓存软化，故此项是**质量项、非紧急**。

**做法**：把**早于 recency 窗口**的旧轮折叠成一份结构化滚动摘要（已确立事实 / 决策 / 未决问题 / 文件路径，逐字保留标识符·数字·路径），回合改喂 `[摘要] + 最近若干轮原文`。

**关键契约**：

- **触发**：回合 input tokens（DeepSeek 实报，即 prompt 实际大小）越 `compaction_trigger_input_tokens`（配置默认 64K）→ 回合收尾 fire-and-forget 后台压缩。自限：折叠后下回合 prompt 缩回阈值下，仅当尾部再次涨过阈值才重压；漏触发由下一次越阈回合自愈（无需 sweeper）。回合总 token 是 CEO prompt 的上界，触发偏保守（宁早勿晚），无可折叠内容时 runner 空转不调 LLM。
- **水位线**：`compacted_through`（最后被折叠消息的 created_at）使重触发幂等，并让长积压**由旧到新、增量**分多次折叠追平。
- **缓存铁律**：摘要**算一次、落库、跨回合复用**；绝不每回合重算——否则改写 prompt 前缀打穿 DeepSeek exact-prefix 缓存（见 `runtime/resolve/prompt.py`）。摘要作 **assistant 块**置于恒定 system 之后，故 system 前缀恒命中，仅「摘要 + 尾部」在重压时重新缓存。
- **健壮**：BYOK 取会话主人的 key（同记忆整合）；一次 flash 非思考调用（World B 窄任务，同 title / memory）；折叠量不足 `compaction_min_fold_messages` 不调 LLM；任何失败（超时 / 空输出）留存状态不变、下次重试，绝不写空摘要、绝不影响已完成回合。
- **与记忆整合区分**：离线记忆整合读**原始**最近消息 reconcile 进记忆文件（`load_recent_history`），**不读**摘要块；压缩只作用于 CEO 回合窗口（`load_chat_context`）。
- **与 A1（执行级 journal）关系**：作用在 `messages` 表已持久化的 user/assistant 文本层，**不依赖** journal，可独立演进。

### 回合内工具结果清理（clear_tool_uses）✅ 已落地

> 实现：`runtime/engine/tool_clear.py`（纯函数 `project_cleared_window` + `cleared_placeholder`）、`runtime/engine/loop.py`（`build_request` 前投影 + `engine.tool_clear` 埋点）、`config/` 两旋钮（`engine_tool_clear_keep_recent` / `engine_tool_clear_min_chars`）。

**定位**：与「长对话压缩」同治 **context rot**，但**作用域正交**——压缩跨回合折叠旧 user/assistant 文本，本机制**回合内**收掉堆积的工具结果。一个长 worker run 会反复 `file_read` / `grep`，旧结果每轮原样重发（token）且把窗口塞满陈旧读（rot）；而按「历史重建原则」工具 I/O **不跨轮回放**、压缩也从不见它，故单个长 run 内的工具堆积**只有本机制治**。

**做法**：在**发给模型的窗口**里，把滑出「最近 `keep_recent` 个同类结果」窗口、且本身 ≥ `min_chars` 的旧「只读可重取」工具结果，折成紧凑稳定指针 `[已清理: file_read(path='…') 原 N 字符，可重取]`。**纯投影**——只在 `build_request` 那一点改发给模型的视图。

**关键契约**：

- **触发**：per-run，不靠 token 阈值而靠「**条数窗口 + 体积下限**」——某条只读结果滑出最近 `keep_recent`（默认 4）个同类结果、且 ≥ `min_chars`（默认 2000 字符）才折叠。短回合（≤ keep_recent 个合格读）**零触发**；`keep_recent` 设极大 = 等效关闭（开发期默认开，**无 enable 布尔开关**，两旋钮即调参面）。默认 4 取自真实 DeepSeek A/B 实测（`scripts/measure_tool_clear.py`）的省量/留存曲线拐点：10 读回合稳态省 ~57% input token、cache_miss 始终极小（指针仍命中前缀缓存），再降（4→3 仅 +5pp）边际收益小且压缩逐字工作集、抬高重取风险。
- **唯一事实源不破**：投影**不改** canonical `messages`、**不写** Turn Journal；journal 与 UI（结果搭 `tool_use_end`）始终全保真。压缩亦同纪律（只动模型窗口）。
- **恢复一致（确定性而非快照）**：resume 重建全量 `messages` + 重跑同一 loop → 同输入同投影，**逐字节复现**发给模型的窗口。
- **缓存铁律**：指针稳定 + **保位**（不删消息、不断 tool↔assistant 配对），已清理前缀仍命中 exact-prefix 缓存，仅每轮本就重算的移动尾部 miss——与压缩「绝不改写已缓存前缀」同律。
- **清理判据**：复用 worker 已有 `investigation_tools` 白名单（只读 / NEVER-approval / 可重取：`file_read` / `grep` / `file_list` / `git`（只读子命令）/ `web_search` / `read_url`）——只清「重取即得、清了无损」的；写类 / 有副作用 / 审批类结果**绝不碰**。

### Trace 关联

## 四、ReAct 循环与收敛治理 ✅ 已确定

> **不变量**：轮次上限 `ModelProfile.max_rounds`（Worker 另叠累计 token 硬顶 backstop，见收敛治理表 + 「到顶收口」）；收敛治理 `LoopController`（滑窗机械循环 → NUDGE/FINALIZE、工具失败熔断、无产出早停、反思注入）；交付前核验 `finish_guard`（done 点纯代码轻层守卫、未过回炉，见下）；引擎级工具超时兜底；空响应同模型重试至阈值后 DEGRADED、LLM 硬失败直接 ERROR/DEGRADED 收口；GRANTABLE 审批在 worker 层 gate（CEO 不持 GRANTABLE）；回合内工具结果清理（旧只读结果在 `build_request` 前投影成指针，纯视图不动 `messages`/journal，见 §三）。✅ 结构化 `RoundOutcome`/`LoopDirective` 协议（每轮产出归一为 `RoundOutcome`，治理只回一个 `LoopDirective`，主循环退化成单一 `match` 执行器）。→ 见代码：`engine/loop.py`（`react_loop`）、`engine/outcome.py`、`engine/directive.py`、`loop_controller.py`、`runtime/verify.py`。

### 基本循环

`message_start` 后逐轮迭代至 `profile.max_rounds`；✅ GRANTABLE 审批挂起；✅ 工具超时兜底（B1）；✅ 空响应同模型重试后 DEGRADED / LLM 硬失败直接收口 / 工具失败熔断 / 无产出早停 / 反思注入（B2，见下表）。✅ **结构化轮协议**：每轮先组装 `RoundOutcome`（content/reasoning/usage/tool_calls/tool_results/attempts/terminal_handoff/llm_failed 的单一事实对象），治理函数（`decide_no_tool_round` / `govern_after_tools` / `decide_llm_failure`）各回一个 `LoopDirective`（`Continue`/`Rework`/`Finalize`/`Return` 密封联合），主循环对其做穷尽 `match`——取代旧的字符串 `kind` / `terminal` 哨兵 / `LoopExit | None` 散落控制流。

### 协调事件注入（CEO 协调模式）✅ 已落地

当根 CEO 以多 worker 默认（或显式）进入协调后，`react_loop` 在轮间调用 `await_coordination_injection`：从 `CoordinationSession` 队列取事件（完成 / 便签 / 升级 / 超时 / 全部完成 / 边界让出 / **用户插话**），合并为一条 user 侧简报注入窗口，再进入下一轮 think。超时计时器与 escalate 路由只**通知**、不自动取消 worker；SCOPE 在协调模式下 `PROCEED`（不波边界 YIELD）。产品语义见 [`编排器与CEO主Agent.md` §协调模式](/docs/03-AI核心/编排器与CEO主Agent.md)。→ 见代码：`runtime/coordination/`、`engine/loop.py`。

**用户插话（`USER_INTERJECTION` ✅）**：协调 turn 运行中用户发的新消息经消息入口注入 session 队列（必要决策点，必唤醒 CEO），SSE 发 DURABLE `user_interjection`（`status=delivered`）。CEO 自主处置：相关 → 图内（`update_synthesis` / 再调 `delegate` 追加 / `cancel_worker`）；无关 → `queue_user_message` 工具转对话级排队并更新同 `interjection_id` 的状态为 `queued`（下一回合处理）。**插话附件 ✅**：delivered 分支在 API 层即走与正常回合同一 `persist_attachments` 落盘（幂等：stash 保留 `workspace_path` + 内联 `text`，转排队 drain 再过驻留不重复写盘）；CEO 简报与 SSE payload 只带元数据（名字 + 工作区路径 + 二进制标记，不内联正文），团队按路径 `file_read` / `code_execute` 自取——沿用「落盘 + 路径引用」消费模型，不新增通道。图片仍不支持（无视觉通道，与插话无关）。

### 到顶收口与顺序分裂退役 ✅ 已落地

> **不变量**：`max_rounds` 或 Worker token 硬顶触发的强制收口一律 `force_finalize`（杜绝死循环）；「正轨 vs 打转」按 `LoopController.is_thrashing()` 分流。运行时**不自发分解**任务——真·独立并行分解只在规划层（CEO `delegate` + waves）。→ 见代码：`engine/loop.py`（`react_loop` 尾部）、`engine/finalize.py`、`loop_controller.py::is_thrashing`。

- **到顶态分流**：`is_thrashing()`（= 无产出早停 `unproductive_early_stop` 或机械空转 convergence-`FINALIZE`）为真 = 打转 → `FinishReason.DEGRADED` + emit `escalation_raised`，并 append 一条 `kind="normal"` 结构化信号进 `gate_escalation_sink`（经 `executor_agent` harvest 去重合并入 `RunState.escalations`），供 CEO 聚合**自愿** replan——**不自动重分解**（信号只上浮、不触发 wave 边界动作）。为假 = 正轨 → 正常 `force_finalize`、从保留 `messages` 合成最佳产出。
- **顺序分裂（Sequential Split）已退役**：运行时不再把撞预算的 worker 自发拆成「前半 + 收尾兄弟」——收尾兄弟结构上拿不到前半产出、预算虚构，属 compaction-continue 的错误包装。两个需求各归其位：**连贯 worker 撞预算但在正轨** → 同 worker 压缩（`tool_clear`，§三）续跑 + Worker token 硬顶（上表）；**任务天然可独立并行** → 规划层 `delegate`（plan + waves，见 §一 · [编排器与CEO主Agent](/docs/03-AI核心/编排器与CEO主Agent.md)）。

### 交付前核验（finish_guard）✅ 已落地（轻层：造引用 + 结构完整性）

> **不变量**：模型自报 done（无工具调用 + 有正文）是 ReAct 唯一终止信号；`react_loop` 在这一点先过一道**纯代码轻层守卫**再决定放行，未过则回炉重写。守卫无状态、不经 LLM、不靠 CEO 自觉——给「交付前先核一道」一个决定论闸门。→ 见代码：`runtime/verify.py`、`engine/loop.py`（`react_loop`）、`runtime/events/chat.py::content_reset`（CEO）、`runtime/events/run.py::run_output_reset`（worker 对偶）。

收敛治理（上）管「循环要不要继续」，本机制管「交付能不能放行」——是终止点的对称闸门。CEO captain 与 worker 跑同一个 `react_loop`，故一处落点同时盖住两条路。

- **轻层两查**（都纯机械可判、近零误报）：①**造引用**——正文 `[n]` 角标指向不存在的来源卡（编号 < 1 或 > 来源数）即命中；②**结构完整性**——代码围栏未闭合（后文整片被当代码渲染）或声明了语言却空体（答应给代码却没给）。刻意**不**纳入「残留 TODO / 填空占位」（法律模板会正当留空、worker 会如实写「待客户提供」，机械判会误伤——轻层立身之本是近零误报）。后续轻层（受限的 JSON 可解析）与重层（要跑 / 要重算 / 换眼睛找漏 / 回源对照）在 `verify.py` 扩展。
- **统一底线·分路适用**：**造引用**仅 CEO 路径开（`annotate_citations=True`）——worker 文本未编号、其本地 `[n]` 汇入回合卡时会重排，角标校验语义不适用，故 worker 跳过此查；**结构完整性两查**与角标无关、对 CEO 与 worker 同样成立，二者收尾都过这道关（✅ 已扩到 worker 路径，二者跑同一 `react_loop`、共用 `finish_guard`）。
- **命中即回炉**：丢弃这一版草稿（`final_content` 退回本轮之前），注入锚定具体角标的修正提示（`format_guard_steer`，允许模型改写或继续检索补来源），回炉重写而非照发；回炉计入 `max_rounds`。上限 `engine_finish_guard_max_reworks`（默认 2）耗尽后放行；pipeline 出口先记 `citations.out_of_range` warning（观测），再剥离悬空角标，保证进入 conversation store 的终稿与 citations 自洽。
- **流式一致性**（关键约束）：done 轮正文已逐 token `emit` 到气泡、无法「收回」，故回炉时发 `content_reset`——前端清当前气泡已累积正文（含 process 尾部 content 步）并丢弃 rAF 缓冲，重写版重新流式，呈现为「违规版 → 修正版」一次干净替换而非追加。同一 reset 规则**三端镜像**（共用 `lib/processTimeline.ts::dropTrailingContentSteps`）；`content_reset` transport-only 不进 journal（历史回放：纯对话回合用最终 `message.content`、有工具回合用已 pop 草稿的 process timeline）。**worker 回炉发其对偶 `run_output_reset`**（`runtime/events/run.py`）——清该 worker 卡片已累积的 `outputChunks`、保留 reasoning（思考是真实过程），同样三端镜像（桌面 `stores/execution` fold + 手机 `protocol/fold.ts` + oracle）、transport-only 不进 journal（重载由 worker 终态 `message_final` fact 重建；finish_guard 的 rework 痕迹另经 `run_process_rework` 步持久化）。
- **reset 语义分流（`reason` 必填）**：`content_reset` / `run_output_reset` 不止回炉一个来源——LLM 流式透明重试（`engine/stream.py`）、captain 软门控打回（`engine/soft_gates.py`）、worker 旁白回滚（`engine/tool_round.py`）、blocking `ask_user` 吸收（`engine/ask_user_absorb.py`）都会清已流式草稿。payload 带枚举 `reason ∈ {finish_guard, retry, soft_gate, narration, ask_user}`（`payloads/chat.py::ResetReason`，emit 端 `on_reset(reason)` 由各调用点声明）；三端 fold + oracle **仅对 `finish_guard` 折出「已按交付规范重写」rework chip / `didRework`**，其余 reason 只清正文、不留痕——否则网络重试 / 正常旁白归档会被谎报成「交付违规重写」（误报根治，conformance 向量 `single_agent_retry_reset` / `multi_agent_worker_deliverable_reset` 锁死该分流）。
- **覆盖边界**：仅拦**模型自报 done** 的正常收口；`LoopController` 的强制收口（`_force_finalize`：机械空转两段式 `FINALIZE` / 无产出早停 / 轮预算耗尽 mid-tool-call）走独立路径、**不过此守卫**——那是已判定异常的回合，第一刀不在其上再叠回炉。

**测试验证循环**（✅ 工具 + 技能 + 完工门已落地；与 `finish_guard` 轻层正交）：编排层 Skill `verify_and_fix`（`runtime/skills.py`）+ `test_run` 工具（`tools/builtin/test_run.py`，结构化跑 `WorkspaceProfile.test_commands`、解析 pytest/vitest 输出），**不**新建 TestFixAgent 子系统。worker：改代码 → `test_run` → 失败则 `file_read` 修复 → 重试；CEO `delegate` 可附完工门 `completion_criteria: "code_verified"`（回执核验 transcript 里 `test_run` 真通过才算 done，`runtime/delegate/completion.py`）；**禁止** agent 修改测试文件；测试命令本身报错 → `escalate` kind=dep。⏳ 余项：引擎级收敛（`LoopController` 同失败签名 3 次 NUDGE 停用 `test_run`）未接；云端可靠执行依赖 [真实沙箱](/docs/06-规划/远期规划.md) §2.1（sidecar 先用 subprocess）。→ 工具侧见 [工具与能力系统](/docs/03-AI核心/工具与能力系统.md)。

### SSE 桥接

执行侧与输出侧经**无界 `asyncio.Queue`** 解耦。背压只对可丢弃事件（`content_delta` / `reasoning_delta`）生效，生命周期/终止事件保证送达。

**前端兜底对账**：消息落定时递归收口所有悬挂的 running/queued run 节点——后端可靠送达是主路径，前端对账是 last-resort 兜底。

### 执行与请求解耦（断连续跑 + 实时重连续看）✅ slice 1a + 1b 已落地

> **实现现状**：✅ slice 1a + 1b + 持久租约。回合执行从 SSE 请求生命周期**解耦**——`send` / `regenerate` / `resume` / `retry-failed` 四路由把 pipeline 作为 **detached task** 交 `runtime/turn_runs.py::TurnRunRegistry`（进程内缓存）托管，SSE 仅 **attach**；同时写入 `turn_leases` 持久 RUNNING 租约，进程重启后 sweeper 经 `recover_turn` 续跑。

### 用户级重试失败项（retry-failed）✅ 已落地

**意图分离**：`regenerate` = 推翻重来（删消息后整回合重跑）；`retry-failed` = 补救失败（复用已成功 worker，只补跑失败节点）。与 `resume`（checkpoint 续跑）共用 `seed_completed` 底层，但语义不同——resume 从挂起点之后全部重跑，retry-failed 只重跑当时仍为 `failed` 的节点。

**后端路径**（`POST …/messages/{message_id}/retry-failed`）：

1. 从该 user 消息对应 assistant turn 的 journal 经 `TurnState.from_journal` 提取 `phase == COMPLETED` 的 worker
2. 写入 `runtime/retry.py::retry_seed` contextvar
3. `delete_after` 该 user 消息之后的消息，CEO loop 重跑；`DelegateTool` 读 seed 并以 `seed_completed` 交给 `WaveScheduler`，已成功节点跳过

> ⏳ **后续**：retry-failed 是否应开新 turn 的对外语义纠正（本次仅内部投影去重，行为不变）。

**节点自动重试**（第一层防线）：DAG 节点默认 `RunPolicy(on_failure="retry", max_retries=1, retry_delay_ms=2000)`（`runs/constants.py` / `builder.py::_dag_policy`）；调度器内部静默退避重试，用尽仍失败才 `run_failed` 上报用户。

**确定性失败区分** ✅：非重试类上游失败（prompt 超长 / 400 / 鉴权 / 余额，`AgentCoreError.retryable=False`）经 `RunState.error_retryable` 从 worker executor 传导到 `WaveScheduler`——`on_failure="retry"` 遇确定性失败即**跳过**盲目重跑（不再烧 `max_retries` + token 复现同一个 400），并落一条 `run.deterministic_failure` 审计（category=`state`，不重复计 failure），后端从此对确定性失败「有感知」；`error_retryable` 随 `state_to_json` 落 journal，resume / retry-failed 重建时保留。**用户接受收口** ✅（run_redirect Step 4）：run 详情在 `run.deterministic_failure` 或 `run.redirect_ignored` 审计行存在时提示「接受此结果」→ `POST …/accept-outcome` 幂等落 `run.outcome_accepted`（owner-scoped，复用 append-only 审计表，无新 SSE）。整轮「放弃」仍走 `clearExecution` 清本地投影。→ 见代码：`runs/wave.py`、`runs/executor_agent.py`、`audit/projector.py::project_run_deterministic_failure`、`api/routes/conversations/run_redirect.py`、`conversation/turns.py::retry_failed_chat`

**契约**：

- **客户端断连 ≠ 取消**（1a）：断连只让 `_event_generator` 调 `sink.detach()`（停止入队、封顶未读队列），run 在后台**跑完并照常 `_persist_turn_result` 落库**——直接消灭「7 分钟长回合断连即丢交付」。
- **显式停止 = 取消**（1a）：用户「停止」改走 `POST …/conversations/{id}/stop` → `turn_runs.stop` → `task.cancel()`，经回合既有 `CancelledError` salvage 路（已完成队员产出落「未完成」消息，断线别白干）。幂等：无在飞 run 返回 `stopped=false`（前端 `services/stopTurn.ts` 在 abort 本地流之外补发此请求，因断连不再代为取消）。
- **持久化独立于连接**（1a）：journal / 落账 / 遥测 / 快照本就在 pipeline 返回后跑、与 SSE 消费无关；`EventSink.detach` 仍保留 journal / process / fact 累积，故断连后回合仍完整重放。
- **重连即回放 + tail**（1b）✅：`GET …/stream` 命中在飞 run。**无 `Last-Event-ID`**：`EventSink.take_over` 全量 `_history` 快路径（进程内）。**有 header**（前端 rejoin/attach 一律带，无历史则 `0`）：journal-backed 回放该回合**全量事实**——DURABLE 工具/团队事件与渐进落盘的 `process_*` / `run_process_*` **按 journal 原序交织**（文本步译成合成 delta；结构性 `process_tool` / marker 跳过、由对应 DURABLE 重建）+ 仅当 journal 尚无对应 process 文本时才用 `turn_stream_state` 补未闭合尾；+ live tail。header 值仅观测。无在飞 run → **204**，前端回落读持久化消息。DURABLE / process 帧携 `id:` = journal seq（barrier 回流）；EPHEMERAL/token-delta 不带 id。→ 见代码：`runtime/events/attach_replay.py`、`api/sse.py`。
- **前端重连姿态**（1b）：传输级断连不再 resend/regenerate，改 **clear-then-fold**（truncate 气泡 process + execution 槽）后 attach 带游标回放；`"none"` 则回合已落库，reload 取回。开会话末条为 user 且 `live_running` → `attachOnOpen` 续看。sidecar 失败 kind `"sidecar"` 跳过自动重连。
- **边界**：`TurnRunRegistry` 是进程内缓存；**持久 RUNNING 真相**在 `turn_leases`。进程重启后心跳过期 → sweeper：有 DAG → `recover_turn`；**无 DAG 纯聊天** → 从 `turn_stream_state` salvage 为 `usage.status=incomplete` + `finish_reason=interrupted`（不再 skip 成幽灵回合）。⏳ **跨进程 Redis 租约 / 事件总线**、**写类工具幂等键**、**retry-failed 对外语义纠正**为后续。

### 暂停与恢复（回合级落盘续跑）

> **设计不变量**：不引入 `RunPhase.PAUSED` 第三终态——结构化挂起暂停的是**整个回合**（CEO loop + delegate 子 DAG），而非单个 Run 节点；改用**回合级**落盘（`paused_turns` 一行 = 一个挂起回合），Run 模型零改动。
>
> **Resume = 同一回合续写（身份不变量）**：`POST …/resume` **不**开新 turn——`message_id`（= `turn_id`）、`execution_id`（取自 journal 末张 `run_plan`）、journal 游标权威源（DB `max_seq+1`）三者在 pause→resume 间不变。前端投影键同钉 `serverMessageId`（live）/ 消息 `id`（reload 已是 server id）；**禁止**「删暂停气泡 + 新建气泡 + remount 协作图」——续跑只把同一条助手消息翻回流式。否决「resume 伪装成新回合」与「client UUID 当执行槽键」——二者会反复制造 remount / UniqueViolation / 图丢帧类补丁。

**挂起即收口（②）**：到达 `plan_review` / `ask_user` / `team_preview` 检查点的回合在 `await` **之前**把整帧（`TurnSuspension`，以 `kind` 判别）落到 `paused_turns`，**落帧成功即收口终止**回合（`SUSPEND→PAUSED`、进程内 resolve Future 永不 park），所有续跑——含同会话——统一走单一冷路 `POST …/resume`，把冷热双态在检查点处塌缩为一条冷路。**窄兜底已删除（D11 ✅ · 三 kind 一致）**：原「帧没存住时退到后端限时挂起、超时自动继续」是无人能答的假等待，已删。落帧失败分两类：**运行态失败**（saver 已接线但保存抛错，如 DB / 磁盘故障）⇒ 三 kind 一律**显式报错终止回合**（`SuspensionPersistError` 上抛，不许静默放行烧钱；sidecar 本机帧 saver 同姿态——失败抛错，绝不「假 saved」）；**配置态不可用**（无 saver / 嵌套 depth>0 / 无 transcript——非生产场景）⇒ `ask_user` 如实报错、`plan_review` / `team_preview` 跳过挂起放行（`persist_unavailable`）。→ 见代码：`runtime/suspension_capture.py`。

- **持久缝**：`frame` JSONB 仅存 **resume 控制元信息**；CEO 窗口/历史、已完成 worker **不再入帧**——统一经 `TurnState.from_journal` 投影（收编原 `window_from_journal` / `completed_from_journal` / `plan_from_journal` / `execution_id_from_journal` / coordination snapshot）；`upto_seq` 支持 time-travel/fork（本次无 UI）。**显示/控制态**（正文、思考、过程时间线、引用池、LoopController latch）不散落各处——挂起时组装成 `turn_paused` fact 随快照落库、resume 单点再水化（见 §8.3「回合态暂停快照」）。
- **pause 后 journal 硬边界**：`save_paused_turn` flush 落帧后，本 turn 的 append-on-emit writer **不再**为后续收口噪声（挂起工具的 `tool_use_end` 等）追加 DURABLE 行——snapshot 与 DB 对齐；resume 的 `TurnJournalWriter.initial_seq` **只认** DB `max_seq+1`（snapshot 长度仅作校验）。
- **恢复**：`POST …/messages/{mid}/resume` = peek 帧 → **live-task drain**（不 cancel；仍在跑 ⇒ 409 `turn_in_progress`，帧不消费）→ **settlement 事实先落库**（失败 5xx、frame 原样保留可重试，D8）→ 原子 claim（竞争失败 404）→ 载 journal → `TurnState.from_journal` → 单一原语 `recover_turn`（投影 → seed WaveScheduler / settle → 续 CEO loop）；**claim 成功后的帧解析 / journal 载入失败 ⇒ 帧写回 + 5xx**（绝不吞成 404 丢帧）。plan_review / team_preview / ask_user 三 kind 与崩溃租约恢复均路由到它。重开会话经 `GET …/recovery` 一次拿到 `live_running` + 待恢复帧 + 全 kind `pending_interactions`（§8.2）。
- **持久 RUNNING 租约**：回合起跑写 `turn_leases`、运行中心跳、终态/暂停清；`TurnRunRegistry` 降为本进程缓存。启动 + 周期 sweeper（与 TTL 清理并列）认领心跳过期租约 → **先 orphan 该 turn 热路 pending 交互（写 `interaction_orphaned`）→ `recover_turn` 重驱动**未完成 DAG（D6：旧卡失效、重驱到确认点发新卡，orphan 与恢复续跑不打架；不可重驱则 orphan + 失败收口）。
- **续跑与同会话并发（D9 对齐）**：冷路 paused 不占锁，会话可能已在跑**新**回合——故 resume **不得 cancel** 会话的在跑 run（原「claim 后无差别 `stop_and_drain`」会误杀 D9 允许的新回合，已废除）。续跑前只做**不取消的有限 drain**（等已收口回合的残余解栈——未拆净的收口 / 在飞 attach 可能仍握着 folder 级 `workspace_lock`，不等会死锁）；drain 超时仍有 live task ⇒ **409 `turn_in_progress`**（帧保留，等新回合结束或显式 `/stop` 后重试）。cancel 版 `stop_and_drain` 仅存于 `/stop` 与 regenerate / retry 入口。→ 见代码：`runtime/turn_runs.py::drain`、`api/routes/conversations/turns.py::resume_message`。
- **计费**：整回合**一次**计费——实时路完成则正常落账删帧；断连路 / 崩溃恢复续跑仍是同一 `message_id`，不得双算；只在 resume / recover 完成时落账。
- **TTL**：`paused_turns` 7 天 idle 清理（镜像 `session_retention`）。
- **暂停行读投影**：写侧暂停快照保持 `usage.status=running` + `usage.paused=true`（overlay / 促升的 live 门闩语义**不动**）；读侧 `MessageDetail.paused` 抬升该旗，各端水合为**已停态**（`finishReason=paused`、非流式、不进 generating）——重开会话不再把 paused 回合误当「仍在生成」（否则续跑被 isGenerating 守卫挡死、「paused 可发消息」被前端打破）。帧被 TTL 清掉的残留 running 行仍走 ghost→interrupted 降级。
- **显式停止兜底**：含未持久挂起点的回合被显式停止时，把已完成 worker 产出落成 `finish_reason="cancelled"` 的「未完成」消息；纯断连不触发本路（见「执行与请求解耦」）。
- ⏳ 余项：跨进程 Redis 租约；写类工具幂等键；retry-failed 对外语义纠正（内部投影已收敛到 `TurnState.from_journal`）；治理强制层（见 [`../06-规划/远期规划.md` §2.3](/docs/06-规划/远期规划.md)）。

## 八、运行时核心模型 ✅ 已确定

> **已落地**：Interaction 统一挂起（`InteractionRegistry`，八 kind）+ 统一生命周期（全 kind journal 化 / orphaned 失效语义 / 无限等待默认 / settlement 必达，提问确认交互统一重构）；`checkpoint_after` 波间 `plan_review`；回合级 `paused_turns` 续跑；Turn Journal 唯一事实源（`turn_journal` 表 + `TurnFactLog`）+ seq DB 权威双模式；**流式耐久投影 `turn_stream_state`**（StreamCheckpointer + 读路径 overlay + 无 DAG salvage）+ SSE `id:` / journal-backed 续流；单一投影入口 `TurnState.from_journal`（收编 window / completed / plan / execution_id / coordination）；单一恢复原语 `recover_turn`（resume 三 kind + 崩溃租约，恢复前先 orphan 热路 pending）；持久 RUNNING 租约 `turn_leases` + lifespan sweeper；`transcript`/`history`/`completed`/`plan` 已退出 `frame` 序列化；deltas 降纯传输（流中走 segment 快照）。
>
> **⏳**：跨进程挂起（Redis BLPOP）/ Redis 租约与事件总线；写类工具幂等键；retry-failed 对外语义纠正；`frame` 再瘦 / 大正文卸 `ArtifactStore`。（结构化 `RoundOutcome`/`LoopDirective` 已落地，见 §四；sidecar 本地流中耐久见 [双模式工作区 §10.3 D6](/docs/02-架构/双模式工作区.md)。）
>
> → 见代码：`runtime/journal/`、`runtime/events/stream_checkpointer.py`、`runtime/events/attach_replay.py`、`runtime/turn_state.py`、`runtime/recover.py`、`runtime/leases/`、`runtime/interaction.py`、`runtime/facts.py`。

> 运行时收敛在三个一等模型上。每个模型把一族重复子系统坍缩成单一形状。

### 8.1 三模型总览

| 模型 | 职责 | 解决的问题 |
|------|------|-----------|
| **Interaction** | 唯一挂起原语：server 停下等 client 回值 | 统一审批/ask_user/本地工具/计划评审/阻塞式升级/逐轮辩论六套同构 BLPOP |
| **Turn Journal** | 唯一回合事实源：append-only 事实流 | 消除「回合无事实源」导致的历史回放/快照/消息完整性补丁族 |
| **Run** | 唯一执行单元：一棵 Run 树 | 统一委派/DAG/编排/路由四套并存的编排子系统 |

依赖关系：Interaction 最小独立；Journal 是 Run 的地基（事实留痕在 journal）；Run 落在两者之上。

### 8.2 Interaction（统一挂起原语 + 统一生命周期）

统一挂起原语收编审批 / `ask_user`（语义见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)）/ 本地工具 / `plan_review` / `team_preview` / 委派级授权 / 阻塞式升级 / 逐轮辩论 八 kind，热路单一 resolve 端点 `POST …/interactions/{id}`（冷路检查点走 `POST …/resume`）。→ 见代码：`runtime/interaction.py`（`InteractionRequest`，`kind ∈ approval | ask_user | client_tool | plan_review | team_preview | escalation | debate_round | delegation_authorization`）。其中 `delegation_authorization` **半退役**：独立热路已并入 `team_preview` 开工卡（能力授权随卡合并征询），kind / SSE 事件 / resolve schema 保留用于旧 journal 回放与 conformance。

一套机制替换四套：统一等待器、统一挂起登记（`list_pending`）、统一恢复端点、统一回值端点。per-kind 差异降为策略位（durable / 键粒度 / at-rest 脱敏）。**`paused` 落盘续跑**见 §暂停与恢复；**跨进程等待**（Redis BLPOP）⏳。

**统一生命周期（提问确认交互统一重构 ✅）**：8 种「问用户」交互共享「登记 → 展示 → 答复 → 留痕 → 失效」一条生命周期；唯一保留的分叉是答复后回合怎么继续（冷恢复 vs 热唤醒——「阻塞整轮 vs 不阻塞」是本质二元，escalation 挂起时兄弟 worker 还在跑）。

- **全 kind journal 化（D3）**：所有 `*_required` / `*_resolved` / `interaction_orphaned` 均为 DURABLE 入 turn_journal（`events/disposition.py`）。**pending 集 = journal fold**（required 无匹配 resolved/orphaned，`runtime/journal/pending_interactions.py` 单一实现，recovery 端点与 conformance oracle 共用）；**否决**新建 `interactions` DB 表（= 第二真相源）。
- **失效（orphaned）语义**：新事实 `interaction_orphaned {id, kind}` 消灭「假卡」（journal 有 required、Future 已随进程消失）。四触发点：① turn 结束 finally 防御性 orphan 未 settle 热路交互；② lease sweeper / 启动恢复**先 orphan 热路 pending、再 `recover_turn` 重驱**（旧卡失效、重驱到确认点发新卡，见 §暂停与恢复）；③ resolve 端点兜底——journal 有 required、Future 不在 → 写 orphaned + 返回 410「已失效」，不再裸 404；④ regenerate / retry-failed / stop 入口先 orphan。**断连 ≠ 失效**（detached 运行 Future 仍在，不 orphan）；协调模式 `awaiting=ceo` 的升级由 CEO 仲裁，不 orphan。
- **不答语义（D2）**：所有 kind 默认**无限期等待**（`config/approval.py` / `config/checkpoint.py` 超时默认 None，运维可设上限）；废除审批 300s 静默 auto-DENY、escalation 超时自动回落、debate 超时自动收敛——回落/收敛改为卡片常驻按钮由用户显式触发（「按假设继续」/「让裁判决定」）。词汇表：escalation 状态 `timed_out` 单一拼写；`orphaned` 进各 decision 枚举公共尾部。
- **同对话并发语义（D9 + 运行中消息路由 ✅）**：发新消息按序判定——① 热路挂起（持 `workspace_lock`、turn 保持 running）→ **409** + 明确提示（废除静默等锁）；② 活跃**协调** turn → 注入 `CoordinationSession` 作**用户插话**（**202** `SendMessageInterjectedResponse`，`status=delivered`，见 §协调事件注入）；③ 其他 in-flight turn（经典阻塞 / 单 Agent）→ 对话级 FIFO `turn_queue`（**202** `SendMessageQueuedResponse`，`queue_id`/`position` 可见，当前 turn 收口后 done-callback 自动按序起下一回合）——废除旧「靠 `workspace_lock` 偶然排队 + `TurnRunRegistry` 槽覆盖只打 warning」的未定义行为；④ 空闲 → 正常起回合。冷路 paused 不占锁、可正常发消息；反向同理——冷 paused 会话已在跑新回合时点续跑 ⇒ resume 端 **409 `turn_in_progress`**（不 cancel、不 claim，帧保留）。热挂起主动出口 = `POST …/stop`（cancel + orphan）；冷 paused 出口 = resume 卡「停止」决策。→ 见代码：`runtime/turn_queue.py`、`api/routes/conversations/messages.py`。
- **恢复通道**：`GET …/recovery` 返回 `live_running` + 冷路 `paused` 帧 + 全 kind `pending_interactions`（journal fold 产出，含 escalation / delegation / debate_round）；sidecar 本地模式热路交互同样经 Outbox 落 journal。
- **跨端一致（D4）**：桌面 / 手机 8 种卡全部补齐（conformance `interactions[]` 向量 + parity 表钉住）；**否决**「后端感知客户端能力降级」（如手机无卡时自动 per_call）——补齐客户端，不折叠语义。

### 8.3 Turn Journal（唯一事实源）

每 turn 一条 append-only 条目流（主键 `turn_id + seq`）。→ 见代码：`runtime/journal/`、`runtime/facts.py`、`runtime/journal/writer.py`。

**关键设计抉择**：执行事实与展示事件共用**单一有序日志**（`TurnFactLog`：sink 转发 + 引擎直记交织），否决「执行流与展示流分家再归并」——两流须同发生序才能正确 fold 窗口/快照。

**持久化模型（Append-on-Emit）✅**：每条 fact 在 **SSE 送达前先落盘**（`TurnJournalWriter` contextvar 绑定每个 turn），否决「pause 时 batch snapshot」——前端能看到的一切 DB 里必然已有。数据流：`record_turn_fact → DB append (barrier) → SSE emit`（barrier Future 回流 seq → SSE `id:`）。**并发模型**：writer 是**单消费者有序 write-behind**（入队即定 emit 序），同刻只占 1 条 DB 连接——否决「每条 fact 扇出任务+连接」（宽并行委派会打爆连接池）。**turn owner 在每条回合路径终了（新回合 / resume / pause）都必须在 reset writer 前 `await flush()`** drain 队列尾巴（否则在飞写任务泄漏连接）；pause 再额外写控制帧（journal 早已逐条在 DB），消除「frame 在 journal 缺」的中间态。删消息时联动清理 `paused_turns`（防 orphan frame）。

**process / run_process 车道渐进持久化 ✅**（运行中刷新真源）：

> **不变量**：凡 live 经 CEO `process` / worker `run_processes` 时间线可见的步骤，必须在对用户可见前（或与同序 DURABLE 同一 writer 队列 barrier）写入 `turn_journal`；运行中刷新与终态重载的回放只 fold journal（+ live tail）。`messages.content` 仍只含 `deliverable_only` 交付——旁白不进 content 列、不进下一轮 history。

- **落盘粒度** = 语义边界步（`tool_use_start` 关闭开敞文本、`tool_use_end` 落完整工具步、marker 插入、`content_reset` / `run_output_reset`、轮末 / pause 前 / finalize flush）——**不** per-token、不定时强切。
- **kind**：`process_{step.kind}` / `run_process_{step.kind}`（payload 形状与 live `ProcessStep` 一致；worker 另带 `run_id`）。
- **Finalize**：由「整表 dump process」改为「只补未闭合尾步 + `turn_end`」；序数游标幂等（resume seed 跳过已落盘步），禁止全量重写已存在步。
- **写序 + barrier**：关闭文本步的 `process_*` 在触发它的 DURABLE **之前**入 writer 队列，并与该 DURABLE 同一 SSE barrier——本地 Outbox 与云端 PG 同构，语义边界后 outbox journal 即对 attach / 崩溃投影可见（不靠 finalize 收口）。
- **读路径**：journal 有 `process_*` / `run_process_*` 则用之；挂起冷启动无 process_* 时回退读旧帧 `turn_paused.process`（只读兼容）。结构化回合**不再**用扁平 segment 拼旁白。
- → 见代码：`runtime/events/process_persist.py`、`runtime/events/sink.py`、`runtime/pipeline/finalize.py`；conformance `mid_run_refresh_ceo_narration`。

**流式耐久投影（`turn_stream_state`）✅**：token 级增量仍不进 journal（「deltas 降纯传输」维持）；在飞通道的**累积文本快照**经 `StreamCheckpointer`（EventSink 侧）UPSERT 到 `turn_stream_state`（主键 `(turn_id, channel)`，channel = `captain:content|reasoning` / `run:{id}:output|reasoning`）。flush：3s / 4KB / 语义边界；同代单调只增、`content_reset` 换代可清空。走 `ConversationStore` 端口（`CloudStore` 落库；`OutboxStore` 写本机 record `stream_segments`，硬杀后桌面 restart salvage 补正文——见 [双模式工作区 §10.3 D6](/docs/02-架构/双模式工作区.md)；本地不做 overlay 读侧）。

> **纯散文回合边界（已拍板）**：无工具 / 无团队 / 无 process 车道的回合**不**扩展 `process_*`——`messages.content` 即答案，`turn_stream_state` / 本地 `stream_segments` 保留「散文-only 加速 / salvage」角色。结构化回合（有工具或 process 车道）以 journal `process_*` 为旁白真源，禁止用 `captain:content` segment 拼回过程旁白。

**读路径 overlay**：`usage.status=running` 且非 paused 时，用 segment 填思考 / worker 未终态进度；**结构化回合或 journal 已有 `process_content` 时，禁止把 `captain:content` 灌进 `messages.content`**（deliverable_only——旁白只在 process 车道）。有 process 文本步时 attach 亦跳过对应扁平 channel。**时序**：finalize / salvage / pause 快照落库成功后才 `delete_for_turn`。错误 / captain FAILED / 无 DAG 崩溃 → salvage-from-segments（`pick_longest` + reasoning 单调合并）。→ 见代码：`runtime/events/stream_checkpointer.py`、`conversation/store/overlay.py`、`db/repositories/stream_state.py`。

**seq 权威在 DB · 双模式（D7 ✅）**：`ConversationStore.append_journal(seq: int | None)` 显式区分——**live 模式**（云端 / 进程内 writer）`seq=None` ⇒ DB 事务内 `pg_advisory_xact_lock(hash(turn_id))` 串行化 + `MAX(seq)+1` 原子分配，跨 writer（resume 段 vs 残留 live writer）无竞态；**merge 模式**（sidecar Outbox 回写 `/local-turns`）保留 record 显式 seq + `(turn_id, seq)` 幂等去重，禁止云端重排本地流。**禁止**「无锁 MAX+1 + `on_conflict_do_nothing` 吞冲突」（settlement 行被静默丢弃不可接受）；**否决**主键改 ULID（伤筋动骨且排序语义换轴，DB 原子分配已根治）。

**settlement 事实必达（D8 ✅）**：交互结算从 best-effort 升级为**必须成功**，且不引入第二写入者——settlement 走同一 write-behind 队列**插队** + 端点 `await` 落库 Future：**热路 resolve** = 写成功 → settle Future → awaiter 照旧 emit `*_resolved`（单一发射者，journal 侧幂等跳过）；写失败返回 5xx、Future 不 settle、用户可重试，无双态。**冷路 resume** = **settlement 先落库、再 `claim_paused_turn`**（反序会造成 frame 已删且无从重试，禁止）；claim 后 resume writer 从 journal 种子化 dedupe，pipeline 重放 emit 不重复落库。幂等识别按 kind→自有 id 映射（`approval_id` / `authorization_id` / `escalation_id` / `decision_id` / `checkpoint_id`）+ 进程内 dedupe 集合（多 worker 化之前须迁共享存储）。其余事实仍 best-effort（写失败降级内存态 `writer.degraded → journal_degraded`，不中断 pipeline）。→ 见代码：`runtime/settlement.py`。

**回合态暂停快照（`turn_paused`）✅**：durable 挂起（ask_user / plan_review / team_preview 三面）经共用捕获骨架把**可恢复回合态**组装成一条 `turn_paused` fact，随挂起快照作为 trailing 条目落库（`*_required` 之后）。字段：`content`（deliverable 正文——ask_user 面取 absorb 前气泡、delegate/kickoff 面取 `final_content`，多周期 ⊕ 累积）、`reasoning`、`citations`（回合引用池）、`controller`（LoopController 五个跨挂起 latch）。**`process` / `run_processes` 已退役双写**——pause 前 `flush_process_to_journal` + 锚点 marker 写入 `process_*`；新帧这两个字段为空。读侧仍接受旧帧快照（`runs_from_entries` / resume rehydrate 在无 `process_*` 时回退）。resume 侧**单点再水化**：优先从 journal `process_*` / `run_process_*` seed 显示态，旧帧回退 `turn_paused.process`；引用池双落点、controller seed、pre_pause 供收口 join 与 resume 段 `content_reset` 重灌。取消 salvage（sidecar / 云）以 `pre_pause_from_journal` 拼接 pre_pause。「上周期基底」在捕获时直接从 journal 读上一条 `turn_paused`。**规则：新增任何回合内累积态，必须同时声明挂起归宿与再水化点，禁止散落各面自行启发式恢复。**→ 见代码：`runtime/turn_paused_capture.py`、`runtime/suspension_capture.py`、`runtime/pipeline/resume/rehydrate.py`、`runtime/facts.py`。

**投影不变量表**：

| 消费面 | 来源 | 现状 |
|--------|------|------|
| SSE 流 | 引擎实时 emit（流式增量不入 journal；DB barrier 在 emit 前；DURABLE 帧带 `id:`） | ✅ |
| 执行级事实记录 | `react_loop` 经 `record_turn_fact` 直写单一有序日志 + DB | ✅ |
| 持久化消息行 | journal 投影器 `runs_from_entries` + 在飞 overlay（`turn_stream_state`） | ✅ |
| 流中部分态 | `turn_stream_state` UPSERT 快照（终态后删除） | ✅ |
| 暂停快照 / resume / 崩溃恢复 | `turn_journal` + `TurnState.from_journal` → `recover_turn`；显示/控制态经 `turn_paused` 单点再水化；无 DAG → stream_state salvage | ✅ |
| 跨轮历史回放 | 文本 + interaction 答案投影 | ⏳ |
| LLM 窗口 | `window_from_journal` | ✅ |

**审计投影层 ✅**：`agent_audit_events`（多 Agent 协作追溯）是 journal + 运行时钩子的**下游只读投影**——`AuditRecorder` 先 journal 后审计偏序采集、`causal` 复用 `depends_on`/`parent_run_id` 重建 parent/depends_on/inject 因果边，**非第二事实源**。治理面（受众 / schema / 因果 / 双 API + 文件反查 / 留存 / 被否决取舍）→ [`安全权限与治理.md §八·Agent 行为审计`](/docs/05-平台与运维/安全权限与治理.md)；→ 见代码：`runtime/audit/`。

### 8.4 Run（唯一执行单元）

执行形状不再是离散「模式」而是数据，由 `depends_on` 边自然落定：

- 单 Agent = 单节点
- `fan_out` = 单波 + captain 汇聚
- `pipeline` = 线性链 + captain 汇聚
- `adaptive` = 空计划 + captain 动态追加
- 单次 delegate = 追加一个节点
- best-of-N 择优 = 某节点 `candidates>1`（`RunPolicy` 策略位，非独立 kind）
- 辩论/审查 = 主持人（Moderator）驱动的逐轮交锋（✅ 已落地，见 [`辩论编排设计.md`](/docs/03-AI核心/辩论编排设计.md)）：主持人是 CEO 的 `debate` 工具内的确定性循环（非 LLM 委派角色）、辩手为 `depth+2` 叶子，底层仍是普通 AGENT DAG（**非独立 kind / 无 arena 子系统**），轮次由主持人逐轮判收敛自停（取代旧的 CEO 手搓静态跨轮 `depends_on`）

> **决策（CEO = 根 Run 节点 ✅）**：CEO chat loop 即本回合 `CAPTAIN` 根 Run；content/reasoning 走气泡级 `content_delta`/`reasoning_delta`（非 run 级）；captain 一次定价、落真实台账行。**否决**旧的 `synthesis` 零成本伪 run。

> **决策（嵌套委派）**：`depth < MAX_DELEGATION_DEPTH` 的 worker 默认获 `delegate`+`replan`（启动即有委派能力，见 [`编排器与CEO主Agent.md` §2.4](/docs/03-AI核心/编排器与CEO主Agent.md)）。**硬上限 `depth ≤ 2`**：depth=2 sub-worker 永不获 `delegate`；单 lead 扇出上限 `MAX_WORKER_SUBDELEGATIONS = 4`。

> **决策（可恢复运行 `RunSession`）✅**：一次 worker run 执行后不丢弃，保留完整 transcript = `RunSpec` / `RunState` 的**可恢复延伸**；CEO 经 `delegate` 带 `continue_from_run_id` 在保留 transcript 上追加指令、重跑 `react_loop` 即「续干」（改稿或新任务；同轮 / 跨轮 / 跨进程留人，双 miss 明确拒绝回落冷委派）。统一收编自动返工 / CEO 续派 / redirect 热修 / 辩论续轮四条接缝。详见 [`多轮编排与同人续派.md`](/docs/03-AI核心/多轮编排与同人续派.md)。

### 8.5 引擎纯化

三条去特判手段：

1. **工具效应模型**：`ToolResult(text, effect)`，`effect ∈ Continue | Handoff | Interact`。引擎只解释效应，`delegate`/`ask_user` 不再是特殊名字
2. **显式 ToolContext**：工具签名携 context（user/conv/turn 等），消灭 `set_runtime_context` 全局大杂烩
3. **去工具名特判**：引擎按能力位（`has_delegation_tool` 等）而非工具名判断行为

### 8.6 端口契约（宿主注入）

引擎面向宿主的 10 项端口（本地/云端同码、宿主注入）；契约在代码里镜像为 `runtime/ports.py`（**ClientRequestBridge / Journal / ConversationStore 已落地**、EventSink 已是端口，余项仍为其具体实现、待 Sidecar 取用时再 Protocol 化）：

| 端口 | 定位 |
|------|------|
| Journal ✅ | 引擎唯一持久化出口；`turn_journal` 表 + `TurnJournalRepository`，`runs` 读取时投影自它（§8.3） |
| EventSink ✅ | 渲染流出口（流式增量 + 离散事实实时投影）；`runtime/events/`，`ports.py` 再导出 |
| InferenceGateway | LLM 调用 |
| ArtifactStore | 归档/寻回 |
| PauseSignal | 暂停信号（Redis flag） |
| ClientRequestBridge ✅ | 统一挂起原语（`runtime/interaction.py`；审批 / ask_user / 本地工具 / **plan_review（2a）** / escalation / debate_round） |
| ConversationStore ✅ | 回合持久化 driver（`begin_turn` / `checkpoint` / `append_journal` / `finalize` / `salvage`）；`CloudStore` 直落 PG、sidecar `OutboxStore` 落本机 outbox，本地经 `/local-turns` 走 `finalize(mode=local)` 合并落库（链路 + 合并契约见 [双模式 §10.3](/docs/02-架构/双模式工作区.md)） |
| BillingSink | 计费事实投影 |
| DelegationTransport | 跨进程子树传输 |
| SnapshotStore | 已被 Journal 吸收 |

### 8.7 一轮一网关（Gateway 传播原则）

当用户自带 LLM 凭据时，整棵多 Agent 委派树必须在**同一把网关**下运行，避免 split-brain（captain 跑用户 key，委派出去的子 Agent 回落平台 key）。

**规则**：在 Turn 最早阶段（工具装配之前）一次性解析 `effective_gateway`，随 Run 上下文贯穿整棵执行树。`InferenceGateway` 端口接收的凭据由此确定——直答、团队编排、恢复各路径读同一把。

此原则与凭据来源开关无关（无论平台供还是用户供），是执行语义的不变量。
