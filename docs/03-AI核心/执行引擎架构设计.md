## 核心定位

执行引擎是 CEO 主 Agent 与 worker 实例之间的调度中枢。它接收 CEO 经 `delegate` 下达的子任务（`build_run_plan` 据 `depends_on` 建 DAG），解析依赖图，管理 worker 生命周期，协调并行/串行执行，处理失败与取消，并向 UI 推送实时状态更新。

## 一、基础概念（DAG 调度）

> DAG 调度概念提要；运行时以 §二~§四 为准，§八 为目标模型。以下只保留代码看不直观的设计约定。

### 步骤状态与调度

计划是 DAG：每个 step 声明 `depends_on`，执行引擎扫描「依赖已满足且未启动」的 step 并发启动（受 `max_parallel` 限制）。步骤状态 `queued → running → completed`，异常分支 `failed` / `skipped`（枚举见 `runtime/runs/types.py` 的 `RunPhase`；失败重试由 `RunPolicy.on_failure=retry` 在 `runs/wave.py` 内部完成（硬上限 3 次退避），对外仍以 `FAILED` 收口并 emit `run_failed`）。并发模型为 asyncio 协程——多 Agent = 多 asyncio Task 共享事件循环（Agent 本质是 I/O 密集的 LLM 调用，协程足够）。

> **调度埋点量化 ✅**：为验证连续调度「让并行真正发生」（而非凭感觉），`WaveScheduler.run` 每次 run 回灌一条 `BatchMetrics`——并发峰值 / 平均并发度（`busy_ms÷wall_ms`）/ 槽位饥饿 / 按 reason 拆的边界 fire 数 / escalation 计数等（无晚绑定·escalation·checkpoint 的 plan 全为 0）。**设计取舍**：用 `metrics_sink` 而非返回值或直接打日志——调度器对宿主无感、cancel 路径不回灌（先 re-raise）；由宿主 `delegate` 的 `drive` 取回并打 `delegate.completed` 结构化日志（含 `avg_parallelism` / `scope_ratio`）。→ 见代码：`runtime/runs/wave.py`、`runtime/runs/types.py`（`BatchMetrics` 全字段）、`tools/builtin/delegate/drive.py`。

### 检查点决策语义

> **本篇权威**：检查点 / `plan_review` / 2b 续跑语义以本节与 §暂停与恢复 为准；编排器、协作模式等文档仅外链此处。

检查点分两类，**实现现状不同**：

- **CEO `ask_user` 检查点（✅ 已落地）**：CEO 主动调内置工具 `ask_user` 暂停回合征询用户——CEO **唯一的发问原语**（开场引导与途中拍板共用一卡一机制）。语义、字段与阻塞/非阻塞矩阵见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)。载 `message`（必填）+ 可选 `context` / `assumptions` / `questions` / `style_options`；桌面端以提交/停止两态作答，答复回流 CEO ReAct 循环；`stop` 走 `ToolResult.terminal` 优雅收口。经 `InteractionRegistry`（§8.2）挂起、`POST …/interactions/{id}` 回值；问答入 journal 可回放。属 `ToolCategory.INTERACTION`（非 ORCHESTRATION），仅在 `settings.checkpoint_gate_enabled` 且有交互用户时装配，worker 路径不给。
- **DAG `checkpoint_after` 结构化挂起（✅ Phase 2a 已落地）**：step 带 `checkpoint_after` 且 `COMPLETED`、下游仍待跑时，`WaveScheduler` 在波间 `await` `plan_review` 交互（`kind=plan_review`，continue/adjust/stop——adjust 把备注作为 steer 注入未跑下游的 `RunSpec.steer`、由 executor 渲染为最高优先级指示块；stop/abort 后未跑尾部统一标 `SKIPPED`），经 `InteractionRegistry` 与 `POST …/interactions/{id}` resolve；事件 `plan_review_required`/`plan_review_resolved` 入 journal 可回放；前端见 [`前端UX设计.md` §三/§五](/docs/04-前端/前端UX设计.md)。**✅ 2b 已落地**：turn 级落盘（`paused_turns` 帧）+ `POST …/resume` 续跑（**纠正设计：不加** `RunPhase.PAUSED` 第三终态，回合级落盘，见 §暂停与恢复）。⏳ 余项：跨进程 Redis（多 worker）+ 治理强制层（声明即必停、非 CEO 自声明，见 [`../07-规划/远期规划.md` §2.3](/docs/07-规划/远期规划.md)）。

> **勿与工具审批混淆**：`approval_required` / `approval_resolved` SSE 事件**不是**检查点，而是**工具审批闸门**（GRANTABLE 工具暂停待用户授权），已落地（按 `settings.approval_gate_enabled` 开关）。CEO 自身不持 `GRANTABLE` 工具，故实际在**本地模式 worker** 层生效（worker 继承 CEO 门，双模式 P2d），云端 worker 不 gate（隔离沙箱）。审批语义见 [`../05-平台与运维/安全权限与治理.md` §三](/docs/05-平台与运维/安全权限与治理.md)。三者（审批 / `ask_user` 检查点 / 本地工具）现共用 `runtime/interaction.py` 的 `InteractionRegistry`（§8.6 ClientRequestBridge）同构挂起-恢复，单一 resolve 端点 `POST …/interactions/{id}`（按 kind 判别）。

> **开工提案卡是 `ask_user` 的一种形态**：开场与途中共用同一挂起机制。→ 见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)。

### 受监督的波循环（晚绑定 + 边界让出）✅ 已落地

> **本篇权威**：晚绑定 / 波边界让出 / `replan` 续跑的**执行语义**以本节为准；CEO 侧 `replan` 工具形态见 [`编排器与CEO主Agent.md` §一 `replan` 原语](/docs/03-AI核心/编排器与CEO主Agent.md)。

**解决的痛**：worker 职责在 CEO `delegate` 那一刻就绑定死，但下游真正要干的活往往得等上游产物落地才清楚——团队闷头按可能过时的初始计划做完（「计划漂移」）。把执行模型从「CEO 下完计划即缺席」改为「**CEO 是波边界的监督者**」：`build_run_plan` 一次建全 DAG（开局全貌可见），节点可**晚绑定**，`WaveScheduler` 自主跑波、只在**决策边界**把控制权交回 CEO 定稿 / 纠偏后续，续跑同一张图（不重建）。这是 §一 检查点语义的推广——检查点只是边界的一种。

**形态**：

- **晚绑定节点**（`RunSpec.bind_after_deps`）：spec 关键字段先占位，依赖落地后由 CEO 在边界定稿（复用 `steer` 的 in-place mutate 范式）；`_select_ready(defer_bind=)` 绝不调度未定稿节点。
- **边界判据**（`BoundaryReason ∈ {CHECKPOINT, BIND, SCOPE}`）：① `checkpoint_after`（让用户把关）；② 依赖已就位、待定稿的晚绑定节点（让 CEO 定稿）；③ 已完成节点带未消费的 `escalate kind=scope` 偏离信号（让 CEO 纠偏）。
- **边界结果**（`BoundaryOutcome ∈ {PROCEED, YIELD, ABORT}`）：`YIELD` = 软暂停（复用 `should_stop` 语义：排空 in-flight、返回 partial、尾部不 skip），把控制权交回 CEO 主循环。
- **续跑**：`delegate` 的 `_drive` 收到 `YIELD` 返**非终态** ToolResult（CONTINUE）+「计划已让出」简报给 CEO，暂存 `(plan, completed)`；CEO 经 `replan` 定稿 / 纠偏 / 追加 / 收口后，`_drive(seed_completed=…)` 续跑同一 DAG。

**双臂：同一边界，让给用户 or 让给 CEO**（按影响力分档，对齐 `ask_user` / checkpoint 心智）：

| 臂 | 触发 | 谁裁决 | 用户感知 |
|---|---|---|---|
| 让给 CEO（BIND / SCOPE） | 低杠杆：晚绑定定稿、据 escalate 微调下游 | CEO 自主 | **无感**（仅图上「计划已调整」轻痕迹，见 [`../04-前端/前端UX设计.md`](/docs/04-前端/前端UX设计.md)） |
| 让给用户（CHECKPOINT → `plan_review`） | 高杠杆：选错会让用户明显不满 / 推倒重来 | 用户 | 决策卡，挂起待答（见上「检查点决策语义」） |

> **复用而非另起炉灶**：两臂共用 `WaveScheduler` 的边界机制 + §8.2 唯一挂起原语；让给 CEO 的臂本质是调度器在边界把控制交回 CEO 的 ReAct 循环、续跑同一 DAG——**不新增挂起子系统**、**不增委派深度**、**不碰 worker↔worker 直连**。CEO 臂走正常回合生命周期（非终态返回 = 普通 ReAct 续跑），plan / completed 由 journal 投影重建，**不需新 durable 挂起**（区别 user 臂的 `paused_turns`）。

> **偏离信号：复用 `escalate` + 轻量 `kind=scope`**：worker 发现自己 / 下游 scope 错了，用现有 `escalate`（**非阻塞**）加一个 `kind=scope` 提示位上报（**扩展而非新原语**）；信号在波边界被**一等消费**——CEO 据此重写未跑下游。**否决**「为 scope 单立信号 / `InteractionKind`」：决策的是 CEO、worker 只供偏离事实，单立 = 与 `escalate` 高度重叠（补丁绊线）。

> **成本纪律（不变量）**：无晚绑定 / 无 escalation / 无 checkpoint 的 plan，调度器一路跑到 terminal、一次 `delegate` 返回（= 今天行为、**零新增 CEO 回合**）——**CEO 回合数 = 真实决策点数，不是波数**。

> **turn 末仍开着的 supervised run**：CEO 拿到让出简报却没 `replan` 就结束回合（最终答复 / `MAX_ROUNDS` / 上游报错），则 turn 末按**隐式 `stop`** 收口（折算已完成工作 + 未跑尾记 SKIPPED + 释放暂停态），避免团队工作悬空漏计费 / 来源不显；无让出时 no-op。

> **持久化与跨端一致**：晚绑定占位、scope 的 `kind`/`consumed` 经快照往返保真——重建的暂停计划仍知该节点待定稿、**绝不未绑定就 dispatch**；`YIELD` 给 CEO 走内部续跑（不产生用户可见事件分类），`replan` 改图走 `plan_revised` 事件（入 journal 可回放、三端等价）。

> **被否决 / 暂不做**：① **worker 实体化**（临时角色 → 稳定专家实体，Phase 2，用户按下）——守在「CEO 在波边界监督」一层，对齐「无团队选择器 / 每回合自适应组队」赌注（见 [`编排器与CEO主Agent.md` §六 Agent 实体化](/docs/03-AI核心/编排器与CEO主Agent.md)）；② **2b 波内抢占 / CEO 波内重入**——撞「波内没有在跑的 CEO」那堵墙，[协作模式 §二](/docs/03-AI核心/Agent协作模式.md) 已否决 worker→CEO 中介，用波边界让出替代；③ **运行期软护栏**（类比 `delegation_nudge`）——边界结构性决策后基本不需，「实测漏触发率高再加」。

> → 见代码：`runtime/runs/scheduler.py`（`BoundaryReason` / `BoundaryOutcome` / `OnBoundary`）、`runtime/runs/wave.py`（`on_boundary` / `_select_ready(defer_bind=)` / `_scope_pending`）、`runtime/runs/builder.py`（`bind_after_deps` 解析 / `build_added_nodes`）、`tools/builtin/delegate/`（`supervised.py` 让出+续跑、`boundary.py`、`tool.py` `dispose_open_supervised`）、`tools/builtin/replan.py`、`tools/builtin/escalate.py`（`kind=scope`）、`runtime/events/run.py`（`plan_revised`）。

### 失败与取消

可重试错误（超时 / 429 / 5xx）退避重试；不可重试错误跳过该 step 或升级用户；关键 step 失败时取消传播到所有下游依赖。完整收敛治理（重试 / 熔断 / 早停 / 反思）见 §四。

### 性能约束

| 指标 | 约束值 |
|---|---|
| 最大并行 Agent | 8（`max_parallel`：`DEFAULT_MAX_PARALLEL` 单波 / `MAX_PARALLEL_DELEGATIONS` 整树，二者同步） |
| 单次 delegate 最大步骤数 | 10（`MAX_DELEGATION_TASKS`，超出截断） |
| 事件传播延迟 | < 50ms（目标） |

### Agent 间产物传递

每次执行在调度器内持有各 worker 产物，供下游依赖注入读取。

> **实现现状**：`WaveScheduler.completed[run_id]` 持有各节点 `RunState`，下游按 `depends_on` 取上游 `RunState.content`（按 `result_handling` 全文 / 摘要）。计划热修改由 CEO 多次调 `delegate` 增量追加（§八 `adaptive`）。

### 事件清单

→ 见代码：`runtime/events/types.py`（`EventType`）+ 前端 `types/events.ts`。

## 三、执行管线全貌 ✅ 已确定

> 从 HTTP 请求到 SSE 输出的完整后端调用链。

### 端到端流程

HTTP 请求经 `conversation/service.py` → `runtime/pipeline.py` ReAct 循环 → SSE 事件流出。

### Phase 1: Prepare

CEO 只读/检索子集 + `delegate`；worker 全集固定注册；`AgentResolver` 为 Phase 2 方向。

**历史重建原则**：每回合取**最近 N 条** user/assistant 文本（`conversation/history.py::load_chat_context` → `list_recent`）。工具 I/O 与委派详情属展示遥测（持久化供前端详情面板），不回放进 LLM 上下文——避免跨轮累积烧 token。超长会话在此之上再叠一层**压缩**（见下「长对话压缩」）。

### Phase 2: Execute（ReAct 循环）

见 §四 详述。

### Phase 3: Finalize

Finalize 在 pipeline 外由 `stream_chat` 执行；⏳ 无 Turn 表。回合收尾按需触发**长对话压缩**（见下）与离线记忆整合，均 off the user path。

**断连收尾契约**：各步骤独立 `try/except`，失败只 warning，不中断已完成的 SSE 流。刻意「能存多少存多少」而非全有或全无——用户已离开，保住已产生的消息比元数据一致性更重要。

### 长对话压缩（compaction）✅ 已落地

> 实现：`conversation/compaction.py`（压缩 runner + token 触发）、`conversation/history.py::load_chat_context`（注入）、`conversations` 三列（`compaction_summary` / `compacted_through` / `compaction_input_tokens`）。

**定位**：不是防溢出（DeepSeek 1M 不溢出），而是治两件事——**context rot**（超长上下文质量随长度下降，与缓存无关）与**缓存失效成本**（exact-prefix 缓存有 TTL，慢节奏 / 隔夜回来全量重算长历史真烧钱）。稳态成本已被前缀缓存软化，故此项是**质量项、非紧急**。

**做法**：把**早于 recency 窗口**的旧轮折叠成一份结构化滚动摘要（已确立事实 / 决策 / 未决问题 / 文件路径，逐字保留标识符·数字·路径），回合改喂 `[摘要] + 最近若干轮原文`。

**关键契约**：

- **触发**：回合 input tokens（DeepSeek 实报，即 prompt 实际大小）越 `compaction_trigger_input_tokens`（默认 64K，对齐 `llm.mdc`）→ 回合收尾 fire-and-forget 后台压缩。自限：折叠后下回合 prompt 缩回阈值下，仅当尾部再次涨过阈值才重压；漏触发由下一次越阈回合自愈（无需 sweeper）。回合总 token 是 CEO prompt 的上界，触发偏保守（宁早勿晚），无可折叠内容时 runner 空转不调 LLM。
- **水位线**：`compacted_through`（最后被折叠消息的 created_at）使重触发幂等，并让长积压**由旧到新、增量**分多次折叠追平。
- **缓存铁律**：摘要**算一次、落库、跨回合复用**；绝不每回合重算——否则改写 prompt 前缀打穿 DeepSeek exact-prefix 缓存（见 `runtime/prompt.py`）。摘要作 **assistant 块**置于恒定 system 之后，故 system 前缀恒命中，仅「摘要 + 尾部」在重压时重新缓存。
- **健壮**：BYOK 取会话主人的 key（同记忆整合）；一次 flash 非思考调用（World B 窄任务，同 title / memory）；折叠量不足 `compaction_min_fold_messages` 不调 LLM；任何失败（超时 / 空输出）留存状态不变、下次重试，绝不写空摘要、绝不影响已完成回合。
- **与记忆整合区分**：离线记忆整合读**原始**最近消息 reconcile 进记忆文件（`load_recent_history`），**不读**摘要块；压缩只作用于 CEO 回合窗口（`load_chat_context`）。
- **与 A1（执行级 journal）关系**：作用在 `messages` 表已持久化的 user/assistant 文本层，**不依赖** journal，可独立演进。

### 回合内工具结果清理（clear_tool_uses）✅ 已落地

> 实现：`runtime/engine/tool_clear.py`（纯函数 `project_cleared_window` + `cleared_placeholder`）、`runtime/engine/loop.py`（`build_request` 前投影 + `engine.tool_clear` 埋点）、`config.py` 两旋钮（`engine_tool_clear_keep_recent` / `engine_tool_clear_min_chars`）。

**定位**：与「长对话压缩」同治 **context rot**，但**作用域正交**——压缩跨回合折叠旧 user/assistant 文本，本机制**回合内**收掉堆积的工具结果。一个长 worker run 会反复 `file_read` / `grep`，旧结果每轮原样重发（token）且把窗口塞满陈旧读（rot）；而按「历史重建原则」工具 I/O **不跨轮回放**、压缩也从不见它，故单个长 run 内的工具堆积**只有本机制治**。

**做法**：在**发给模型的窗口**里，把滑出「最近 `keep_recent` 个同类结果」窗口、且本身 ≥ `min_chars` 的旧「只读可重取」工具结果，折成紧凑稳定指针 `[已清理: file_read(path='…') 原 N 字符，可重取]`。**纯投影**——只在 `build_request` 那一点改发给模型的视图。

**关键契约**：

- **触发**：per-run，不靠 token 阈值而靠「**条数窗口 + 体积下限**」——某条只读结果滑出最近 `keep_recent`（默认 4）个同类结果、且 ≥ `min_chars`（默认 2000 字符）才折叠。短回合（≤ keep_recent 个合格读）**零触发**；`keep_recent` 设极大 = 等效关闭（开发期默认开，**无 enable 布尔开关**，两旋钮即调参面）。默认 4 取自真实 DeepSeek A/B 实测（`scripts/measure_tool_clear.py`）的省量/留存曲线拐点：10 读回合稳态省 ~57% input token、cache_miss 始终极小（指针仍命中前缀缓存），再降（4→3 仅 +5pp）边际收益小且压缩逐字工作集、抬高重取风险。
- **唯一事实源不破**：投影**不改** canonical `messages`、**不写** Turn Journal；journal 与 UI（结果搭 `tool_use_end`）始终全保真。压缩亦同纪律（只动模型窗口）。
- **恢复一致（确定性而非快照）**：resume 重建全量 `messages` + 重跑同一 loop → 同输入同投影，**逐字节复现**发给模型的窗口。
- **缓存铁律**：指针稳定 + **保位**（不删消息、不断 tool↔assistant 配对），已清理前缀仍命中 exact-prefix 缓存，仅每轮本就重算的移动尾部 miss——与压缩「绝不改写已缓存前缀」同律。
- **清理判据**：复用 worker 已有 `investigation_tools` 白名单（只读 / NEVER-approval / 可重取：`file_read` / `grep` / `file_list` / `web_search` / `read_url`）——只清「重取即得、清了无损」的；写类 / 有副作用 / 审批类结果**绝不碰**。

### Trace 关联

> **实现现状**：⏳ `trace_id` 跨链路与 NATS 未实现。

一次用户交互跨多个执行上下文（HTTP、后台 worker、委派 worker）。目标：用统一 `trace_id` 作关联键，在管线入口铸一次，随 NATS payload 流到 worker。排查时 `grep trace_id=<id>` 即得全链路。

### 交付前核验（finish_guard）✅ 已落地（第一刀）

> **不变量**：模型自报 done（无工具调用 + 有正文）是 ReAct 唯一终止信号；`react_loop` 在这一点先过一道**纯代码轻层守卫**再决定放行，未过则回炉重写。守卫无状态、不经 LLM、不靠 CEO 自觉——给「交付前先核一道」一个决定论闸门。→ 见代码：`runtime/verify.py`、`engine/react_loop`、`runtime/events/chat.py::content_reset`。

收敛治理（上）管「循环要不要继续」，本机制管「交付能不能放行」——是终止点的对称闸门。CEO captain 与 worker 跑同一个 `react_loop`，故一处落点同时盖住两条路。

- **第一刀只查造引用**：正文 `[n]` 角标指向不存在的来源卡（编号 < 1 或 > 来源数）即命中——真实事故是 CEO 直答用了 `[25][27]` 而仅 24 源，违反「绝不编造引用」却不自知。纯机械可判、近零成本。后续轻层（残留 TODO / JSON 可解析）与重层（要跑 / 要重算 / 换眼睛找漏 / 回源对照）在 `verify.py` 扩展。
- **仅 CEO 路径**（`annotate_citations=True`）：worker 文本未编号、其本地 `[n]` 汇入回合卡时会重排，角标校验语义不适用，故 worker 收尾跳过。
- **命中即回炉**：丢弃这一版草稿（`final_content` 退回本轮之前），注入锚定具体角标的修正提示（`format_guard_steer`，允许模型改写或继续检索补来源），回炉重写而非照发；回炉计入 `max_rounds`。上限 `engine_finish_guard_max_reworks`（默认 2）耗尽后按现状放行，残留交由 pipeline 的 `citations.out_of_range` warning 记录（观测）。
- **流式一致性**（关键约束）：done 轮正文已逐 token `emit` 到气泡、无法「收回」，故回炉时发 `content_reset`——前端清当前气泡已累积正文（含 process 尾部 content 步）并丢弃 rAF 缓冲，重写版重新流式，呈现为「违规版 → 修正版」一次干净替换而非追加。同一 reset 规则**三端镜像**（共用 `lib/processTimeline.ts::dropTrailingContentSteps`）；`content_reset` transport-only 不进 journal（历史回放：纯对话回合用最终 `message.content`、有工具回合用已 pop 草稿的 process timeline）。
- **覆盖边界**：仅拦**模型自报 done** 的正常收口；`LoopController` 的强制收口（`_force_finalize`：机械空转两段式 `FINALIZE` / 无产出早停 / 轮预算耗尽 mid-tool-call）走独立路径、**不过此守卫**——那是已判定异常的回合，第一刀不在其上再叠回炉。

### SSE 桥接

执行侧与输出侧经**无界 `asyncio.Queue`** 解耦。背压只对可丢弃事件（`content_delta` / `reasoning_delta`）生效，生命周期/终止事件保证送达。

**前端兜底对账**：消息落定时递归收口所有悬挂的 running/queued run 节点——后端可靠送达是主路径，前端对账是 last-resort 兜底。

### 执行与请求解耦（断连续跑 + 实时重连续看）✅ slice 1a + 1b 已落地

> **实现现状**：✅ slice 1a + 1b。回合执行从 SSE 请求生命周期**解耦**——`send` / `regenerate` / `resume` 三路由把 pipeline 作为 **detached task** 交 `runtime/turn_runs.py::TurnRunRegistry`（进程内、按 `conversation_id`，单机姿态同 approvals / locks）托管，SSE 仅 **attach**（`sse_response(..., detach_on_disconnect=True)`）；断连后客户端可经 `GET …/stream` **重新 attach、回放 + tail 续看**。源起证据见 [实测案例复盘 案例 1](/docs/07-规划/实测案例复盘.md)。

**契约**：

- **客户端断连 ≠ 取消**（1a）：断连只让 `_event_generator` 调 `sink.detach()`（停止入队、封顶未读队列），run 在后台**跑完并照常 `_persist_turn_result` 落库**——直接消灭「7 分钟长回合断连即丢交付」。
- **显式停止 = 取消**（1a）：用户「停止」改走 `POST …/conversations/{id}/stop` → `turn_runs.stop` → `task.cancel()`，经回合既有 `CancelledError` salvage 路（已完成队员产出落「未完成」消息，断线别白干）。幂等：无在飞 run 返回 `stopped=false`（前端 `services/stopTurn.ts` 在 abort 本地流之外补发此请求，因断连不再代为取消）。
- **持久化独立于连接**（1a）：journal / 落账 / 遥测 / 快照本就在 pipeline 返回后跑、与 SSE 消费无关；`EventSink.detach` 仍保留 journal / process / fact 累积，故断连后回合仍完整重放。
- **重连即回放 + tail**（1b）：`GET …/stream` 命中在飞 run → `EventSink.take_over` **原子地**丢弃未读积压、快照 `_history`、重挂队列，先回放后 tail；无在飞 run 返回 **204**，前端回落到读持久化消息。`_history` 是**有界、合并**的可重放转录（增量逐流合并、工具结果封顶、纯活性事件不入），独立于 SSE `_queue`，内存随**可见正文**而非 token 数增长；事件 shape 与原流一致，前端 live / reload / reconnect 三态同构折叠。
- **前端重连姿态**（1b）：传输级断连（`StreamError.kind==="network"`）不再 resend/regenerate（那会**双跑**仍在飞的回合），改 `services/turns.ts::rejoinLiveTurn`——清掉残缺气泡后 attach（回放重建）；`"none"` 则该回合已落库，reload 取回；连不上给「重连」banner（永不 resend）。开会话若末条是 user 消息（尚无落库回复），`attachOnOpen` 顺带重连续看（重开 App 也能看它跑完）。sidecar 本地回合失败 kind 为 `"sidecar"` 非 `"network"`，自动跳过重连、维持原 resend。
- **边界**：进程内注册表，重启丢在飞 run（同 handoff 作业现状）；单活跃消费者姿态（多端并发 attach 共享单队列会分流，非目标）；**跨进程持久队列 / 多副本**（C2 · Redis）为后续。

### 暂停与恢复（回合级落盘续跑）

> **设计不变量**：不引入 `RunPhase.PAUSED` 第三终态——结构化挂起暂停的是**整个回合**（CEO loop + delegate 子 DAG），而非单个 Run 节点；改用**回合级**落盘（`paused_turns` 一行 = 一个挂起回合），Run 模型零改动。

挂起回合走**混合「实时 + 持久 backstop」**：连着的客户端仍用进程内 `InteractionRegistry` 的 `await`，同时在 `await` **之前**把整帧（`TurnSuspension`，以 `kind` 判别 `plan_review` / `ask_user`）落到 `paused_turns`；实时 resolve / timeout 后删帧，断连 / 崩溃则帧留存可续。

- **持久缝**：`frame` JSONB 仅存 **resume 控制元信息**；CEO 窗口/历史、已完成 worker **不再入帧**——窗口由 `journal_entries` + `window_from_journal` 投影，历史在消息库，已完成 worker 由 `completed_from_journal` 投影，`plan` 由 `plan_from_journal` 取末张重建。
- **恢复**：`POST …/messages/{mid}/resume`（原子 claim）→ 载 journal → `seed_journal` 回放 → `window_from_journal` 重建 CEO 窗口 → 按 `kind` 分流结算跑尾部 → 续跑 CEO loop；重开会话经 `GET …/paused` 列待恢复帧。
- **计费**：整回合**一次**计费——实时路完成则正常落账删帧；断连路只在 resume 完成时落账。
- **TTL**：`paused_turns` 7 天 idle 清理（镜像 `session_retention`）。
- **显式停止兜底**：含未持久挂起点的回合被显式停止时，把已完成 worker 产出落成 `finish_reason="cancelled"` 的「未完成」消息；纯断连不触发本路（见「执行与请求解耦」）。
- ⏳ 余项：跨进程 Redis（多 worker 实时分发）+ 治理强制层（见 [`../07-规划/远期规划.md` §2.3](/docs/07-规划/远期规划.md)）。

| | World A — Agent 主提示词 | World B — 内部工具型提示词 |
|---|---|---|
| 是什么 | 面向用户的对话 Agent system prompt | 平台内部的窄任务 LLM 调用（标题/分类/摘要…） |
| 触发者 | 每个 Agent、每个 turn | 平台代码按需 |
| 形态 | 身份 + 技能 + 规则 + 上下文，条件装配 | 固定模板 + 少量变量，单次调用 |
| 管理方式 | PromptAssembler（✅ 已落地） | 注册表 + 片段库（⏳ 目标态，当前各自手搓） |

**分离原因**：两者关注点根本不同。强行共用只会互相拖累。

### World A：PromptAssembler 组装顺序

基座 + CEO/worker 条件叠加；无 workspace_ctx 时按 agent_id 实例内缓存。装配落到 `runtime/context/assembler.py`（`ContextAssembler`）：每个常驻源是一个 `PromptContributor` 插件，渲染序由 `SectionOrder` 声明（非调用点书写次序）、稳定排序后拼接，稳定前缀在前护 DeepSeek 前缀缓存（档位坐标系与逐字节一致约束详见 [记忆系统 §5.5](/docs/03-AI核心/Agent记忆与知识系统.md)）。

⏳ **降级模式（未落地）**：低优先级规则过滤、文档截断、Skills 裁掉；Rules 保留（安全/合规约束越降级越要留）。目标态——今天 `PromptContributor.budget` 字段已预留**唯一读取点**，但预算 / 裁剪 / 降级逻辑尚未实现，按需才长（触发条件见 [上下文注入统一性讨论](/docs/07-规划/上下文注入统一性讨论.md) 扳机 B）。

> **实现现状（提示词正文，统一中文）**：基座确立 AgentCore 身份与「结论必须基于工具实际返回、绝不编造」原则；CEO 叠加协调者角色与「用户为老板、CEO 对其负责」身份层级及引用规范 hint；worker 叠加「一次性、隔离上下文、不能反问、不能再委派」自我认知段——因 worker 拿不到完整对话、无澄清回路，须明确「信息不足就合理假设并交付」。

### World B：注册表 + 片段库 ⏳ 目标态

**目标态**：内部窄任务提示词收敛到统一的注册表 + 片段库——`PromptTemplate` / `fragments` / `registry` / `catalog`，key 命名 `component.task`，`{{var}}` 渲染，fragments opt-in。

> **实现现状（⏳ 未落地）**：注册表 / 片段库尚未实现，`runtime/prompt.py` 目前只承载 World A（基座 + CEO/worker hint 装配）。当前每个内部 LLM 窄任务调用**各自手搓**：模块内一个 system 常量 + 一个 Python 渲染函数，直接拼成 `LLMMessage`。两处现状：会话标题（`memory/conversation_title.py`：`_TITLE_SYSTEM_PROMPT` + `_render_title_prompt`）、用户记忆抽取（`memory/user_memory.py`：`_EXTRACT_SYSTEM_PROMPT` + `_render_extract_prompt`）。第三处内部调用出现、或手搓样板开始相互拖累时再行收敛——当前两处尚不构成收敛收益。

## 八、运行时核心模型 ✅ 已确定

> **已落地**：Interaction 统一挂起（`InteractionRegistry`，四 kind）；`checkpoint_after` 波间 `plan_review`；回合级 `paused_turns` 续跑；Turn Journal 唯一事实源（`turn_journal` 表 + `TurnFactLog`）；`window_from_journal` / `completed_from_journal` / `plan_from_journal` 投影；`transcript`/`history`/`completed`/`plan` 已退出 `frame` 序列化；deltas 降纯传输。
>
> **⏳**：跨进程挂起（Redis BLPOP）；`frame` 再瘦 / 大正文卸 `ArtifactStore`；结构化 `RoundOutcome`/`LoopDirective`。
>
> → 见代码：`runtime/journal/`、`runtime/interaction.py`、`runtime/facts.py`。

> 运行时收敛在三个一等模型上。每个模型把一族重复子系统坍缩成单一形状。

### 8.1 三模型总览

| 模型 | 职责 | 解决的问题 |
|------|------|-----------|
| **Interaction** | 唯一挂起原语：server 停下等 client 回值 | 统一审批/ask_user/本地工具/计划评审四套同构 BLPOP |
| **Turn Journal** | 唯一回合事实源：append-only 事实流 | 消除「回合无事实源」导致的历史回放/快照/消息完整性补丁族 |
| **Run** | 唯一执行单元：一棵 Run 树 | 统一委派/DAG/编排/路由四套并存的编排子系统 |

依赖关系：Interaction 最小独立；Journal 是 Run 的地基（事实留痕在 journal）；Run 落在两者之上。

### 8.2 Interaction（统一挂起原语）

统一挂起原语收编审批 / `ask_user`（语义见 [`编排器与CEO主Agent.md` §四](/docs/03-AI核心/编排器与CEO主Agent.md)）/ 本地工具 / `plan_review` 四 kind，单一 resolve 端点 `POST …/interactions/{id}`。→ 见代码：`runtime/interaction.py`（`InteractionRequest`，`kind ∈ approval | ask_user | client_tool | plan_review`）。

一套机制替换四套：统一等待器、统一挂起登记（`list_pending`）、统一恢复端点、统一回值端点。per-kind 差异降为策略位（durable / 键粒度 / at-rest 脱敏）。**`paused` 落盘续跑**见 §暂停与恢复；**跨进程等待**（Redis BLPOP）⏳。

### 8.3 Turn Journal（唯一事实源）

每 turn 一条 append-only 条目流（主键 `turn_id + seq`）。→ 见代码：`runtime/journal/`、`runtime/facts.py`。

**关键设计抉择**：执行事实与展示事件共用**单一有序日志**（`TurnFactLog`：sink 转发 + 引擎直记交织），否决「执行流与展示流分家再归并」——两流须同发生序才能正确 fold 窗口/快照。

**投影不变量表**：

| 消费面 | 来源 | 现状 |
|--------|------|------|
| SSE 流 | 引擎实时 emit（流式增量不入 journal） | ✅ |
| 执行级事实记录 | `react_loop` 经 `record_turn_fact` 直写单一有序日志 | ✅ |
| 持久化消息行 | journal 投影器 `runs_from_entries` | ✅ |
| 暂停快照 / resume | `turn_journal` + `window_from_journal` / `completed_from_journal` / `plan_from_journal` | ✅（`transcript`/`history`/`completed`/`plan` 已退出 `frame` 序列化） |
| 跨轮历史回放 | 文本 + interaction 答案投影 | ⏳ |
| LLM 窗口 | `window_from_journal` | ✅ |

### 8.4 Run（唯一执行单元）

执行形状不再是离散「模式」而是数据，由 `depends_on` 边自然落定：

- 单 Agent = 单节点
- `fan_out` = 单波 + captain 汇聚
- `pipeline` = 线性链 + captain 汇聚
- `adaptive` = 空计划 + captain 动态追加
- 单次 delegate = 追加一个节点
- best-of-N 择优 = 某节点 `candidates>1`（`RunPolicy` 策略位，非独立 kind）
- 辩论/审查 = 主持人（Moderator）驱动的逐轮交锋（✅ 已落地，见 [`辩论编排设计.md`](/docs/03-AI核心/辩论编排设计.md)）：主持人是 CEO 的 `debate` 工具内的确定性循环（非 LLM 委派角色）、辩手为 `depth+2` 叶子，底层仍是普通 AGENT DAG（**非独立 kind / 无 arena 子系统**），轮次由主持人逐轮判收敛自停（取代旧的 CEO 手搓静态跨轮 `depends_on`）

> **决策（CEO = 根 Run 节点 ✅）**：CEO chat loop 即本回合 `CAPTAIN` 根 Run；content/reasoning 走气泡级 `content_delta`/`reasoning_delta`（非 run 级）；captain 一次定价、落真实台账行。**否决**旧的 `synthesis` 零成本伪 run。

> **决策（嵌套委派）**：worker 默认叶子；`can_delegate=true` 才获 `delegate`（**默认关、显式开**，见 [`编排器与CEO主Agent.md` §2.4](/docs/03-AI核心/编排器与CEO主Agent.md)）。**硬上限 `depth ≤ 2`**（`MAX_DELEGATION_DEPTH`）：深度 2 永不获 `delegate`，树不可再深。

> **决策（可恢复运行 `RunSession`）✅**：一次 worker run 执行后不丢弃，保留完整 transcript = `RunSpec` / `RunState` 的**可恢复延伸**；CEO 经 `revise` 在保留 transcript 上追加指令、重跑 `react_loop` 即「修订」（同轮 / 跨轮 / 跨进程留人，双 miss 回落重派）。统一收编自动返工 / CEO 热修 / 重派兜底三条接缝。详见 [`多轮编排与队员热修.md`](/docs/03-AI核心/多轮编排与队员热修.md)。

### 8.5 引擎纯化

三条去特判手段：

1. **工具效应模型**：`ToolResult(text, effect)`，`effect ∈ Continue | Handoff | Interact`。引擎只解释效应，`delegate`/`ask_user` 不再是特殊名字
2. **显式 ToolContext**：工具签名携 context（user/conv/turn 等），消灭 `set_runtime_context` 全局大杂烩
3. **去工具名特判**：引擎按能力位（`has_delegation_tool` 等）而非工具名判断行为

### 8.6 端口契约（宿主注入）

引擎面向宿主的 10 项端口（本地/云端同码、宿主注入）；契约在代码里镜像为 `runtime/ports.py`（**ClientRequestBridge / Journal 已落地**、EventSink 已是端口，余项仍为其具体实现、待 Sidecar 取用时再 Protocol 化）：

| 端口 | 定位 |
|------|------|
| Journal ✅ | 引擎唯一持久化出口；`turn_journal` 表 + `TurnJournalRepository`，`runs` 读取时投影自它（§8.3） |
| EventSink ✅ | 渲染流出口（流式增量 + 离散事实实时投影）；`runtime/events/`，`ports.py` 再导出 |
| InferenceGateway | LLM 调用 |
| ArtifactStore | 归档/寻回 |
| PauseSignal | 暂停信号（Redis flag） |
| ClientRequestBridge ✅ | 统一挂起原语（`runtime/interaction.py`；审批 / ask_user / 本地工具 / **plan_review（2a）**） |
| ConversationStore | 消息持久化（投影写入） |
| BillingSink | 计费事实投影 |
| DelegationTransport | 跨进程子树传输 |
| SnapshotStore | 已被 Journal 吸收 |

### 8.7 一轮一网关（Gateway 传播原则）

当用户自带 LLM 凭据时，整棵多 Agent 委派树必须在**同一把网关**下运行，避免 split-brain（captain 跑用户 key，委派出去的子 Agent 回落平台 key）。

**规则**：在 Turn 最早阶段（工具装配之前）一次性解析 `effective_gateway`，随 Run 上下文贯穿整棵执行树。`InferenceGateway` 端口接收的凭据由此确定——直答、团队编排、恢复各路径读同一把。

此原则与凭据来源开关无关（无论平台供还是用户供），是执行语义的不变量。
