# 多轮编排与队员热修

> **定位**：看到队员产物后，让「**同一个队员带着现场记忆接着改**」（热修），而非每次从零重派冷上下文新人。是 [`编排器与CEO主Agent.md` §五](/docs/03-AI核心/编排器与CEO主Agent.md) 「多轮编排」开放项的落地。
>
> **现状**：✅ 核心链路已落地——同轮热修 → conversation 维度留人 → 跨进程落盘续写 → 前端版本链展示。唯产品决策 P-3「回落换人**轻标记**」⏳ 未落地（见 §六）。
>
> → 见代码：`apps/server/agentcore/runtime/runs/session.py`、`tools/builtin/revise.py`

---

## 一、心智：老板不微操队员

用户是老板，**只对 CEO** 表达「改哪、怎么改」；CEO 自行判断热修原作者 / 另找人 / 重做。不在 worker 产物卡上做定向「要求修改」入口（产品决策 P-1）。这条心智决定了：热修能力对用户**不可见**，全部经 CEO 的工具调用发生。

---

## 二、核心设计：统一为「可恢复运行 `RunSession` + 续写」一个原语

把一次 worker run 视为**可恢复运行**：执行后不丢弃，保留完整 transcript（消息序列）。**「修订」= 在保留的 transcript 上追加一条指令、重跑 `react_loop`**。

这一个原语收编了三件本会割裂的事：

| 场景 | 续写指令来自 |
|---|---|
| 自动返工（contract 不达标） | 系统把「差距」喂回——且队员**这次看得到自己旧稿**（不再盲改） |
| CEO 热修 | CEO 把「修改意见」喂回 |
| 甲兜底（见 §三） | session 不在时用旧产物**重建**新 session 再续写 |

**为何能近免费捕获 transcript**：`react_loop` 原地往传入的 `messages` 追加，worker 跑完后该局部变量**已是完整 transcript**——以前只是被丢弃。

> **被否决：三套独立「重做」机制并存**。理由：触发项目纪律「补丁绊线」（同一接缝第 3 次打补丁）；且 `react_loop` 现成支持续接消息再循环，无需另起炉灶。

---

## 三、甲 / 乙：同一接缝的两种命中态

| 代号 | 形态 | 数据流 |
|---|---|---|
| **甲** | 拿旧产物当输入，重新派新人改 | 产物 → 输入 → 新执行 |
| **乙** | 唤回原作者，带现场记忆续写 | 续接已有 transcript |

**关键**：乙做跨轮必然要把记忆落盘、下一轮取出喂给一次新执行——这条兜底分支的数据流**就是甲**。所以甲不是独立开发项，而是**乙在缓存（内存 + 盘）双 miss 时的透明回落路径**。唤回未命中 / 超限时，`revise` 拒绝并提示 CEO 回落甲（重新 `delegate`）。

---

## 四、关键组件与契约（现状）

| 契约项 | 约束 |
|---|---|
| 改次上限 | 默认 **3** 次定向热修 / run，超限回落甲（重 `delegate`） |
| roster 内存 | conversation 维度；LRU + TTL（默认 ~30 min）+ 字节/条数上限 |
| 跨进程落盘 | `run_sessions` 表，默认 **7 天**空闲 TTL；`session_roster_persist_enabled`（默认开） |
| 双 miss 回落 | `revise` 内存 miss → 从盘回温；仍 miss → 拒绝并提示 CEO 回落甲 |

→ 见代码：`runtime/runs/session.py`、`tools/builtin/revise.py`。

---

## 五、约束边界与配置

- **改次上限**：默认 **3** 次定向热修 / run（常量 `DEFAULT_RECALL_LIMIT`，参照 contract「一次自动返工」给人工热修略宽至 3）；超限回落甲。
- **roster 内存**：挂 conversation 维度；LRU + TTL（默认 ~30 min）+ 字节 / 条数上限，对齐 approvals / channel / locks 的单机 posture。
- **落盘保留**：默认 **7 天**空闲 TTL，到期清理；开关 `session_roster_persist_enabled`（默认开）。
- **委派深度**：续写不增加委派深度；嵌套委派硬上限 `depth ≤ 2`（见 [`执行引擎架构设计.md` §8.4](/docs/03-AI核心/执行引擎架构设计.md)）。

## 六、已确认决策

### 产品（用户拍板）

| # | 议题 | 决定 | 理由 |
|---|---|---|---|
| P-1 | 修订入口 | **纯 CEO 对话驱动**，不在 worker 产物卡做定向修改入口 | 贴合「掌管一支由 CEO 带队的团队」心智，CEO 是唯一交互面 |
| P-2 | 修订历史可见性 | **保留版本链、可对比**：每次续写在图上挂「修订 v2/v3」子节点，保留每版、可展开对比 | 过程透明、可回看；与「新子节点」图模型一致 |
| P-3 | 回落换人呈现 | **默认无感 ✅ + 轻标记 ⏳**：回落甲（重启 / 跨轮失忆 / 超限）时 CEO 重新 `delegate` 一个新 worker，体验天然连续（无感已成立）。但「已由新队员接手」这处轻标识**尚未实现**——回落产生的新 worker 当前与普通委派节点无异，前后端均无「换人」信号 / 文案；`revise` miss / 超限仅以文本引导 CEO 改用 `delegate`，不携带可供前端识别的 handoff 标记 | 既诚实（不假装原作者）又不弹窗骚扰。被否：完全透明 / 每次硬告知 |

### 技术（AI 定稿，可后续微调）

| # | 议题 | 决定 |
|---|---|---|
| T-1 | `revise` 入口形态 | 独立工具 `revise(target_run_id, feedback)`，不污染 `delegate` schema |
| T-2 | 跨轮 transcript 存储 | 独立 `run_sessions` 表，独立于 `message.runs` 图回放 journal（生命周期不同） |
| T-3 | 运行时约束默认值 | 改次上限 / roster TTL / 落盘保留期见 §五 |
| T-4 | 续写花费 | 每次续写独立计一行 member ledger，`parent_run_id` 溯源 |

## 七、被否决 / 暂不做

- **三套独立「重做」机制并存**——否决（补丁绊线；见 §二）。
- **删掉甲、只支持同轮乙**——否决：**换角色改**（研究员稿→工程师改）、**救失败稿**、**合并多产物**这三类结构上就是「新派一人 + 旧产物当输入」=甲，乙再满血也覆盖不了，故甲能力须保留（即 §三 的 miss 回落分支）。
- **语义裁判（判「写得好不好」的额外 LLM 校验）**——暂不做，沿用机械 contract；续写指令由 CEO（人类意图代理）或机械差距给出。
