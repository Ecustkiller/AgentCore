# 多轮编排与队员热修

> **定位**：看到队员产物后，让「**同一个队员带着现场记忆接着改**」（热修），而非每次从零重派冷上下文新人。是 [`编排器与CEO主Agent.md` §五](/docs/03-AI核心/编排器与CEO主Agent.md) 「多轮编排」开放项的落地。
>
> **现状**：✅ 核心链路已落地——同轮热修 → conversation 维度留人 → 跨进程落盘续写 → 前端版本链展示。唯产品决策 P-3「回落换人**轻标记**」⏳ 未落地（见 §六）。
>
> → 见代码：`apps/server/agentcore/runtime/runs/session.py`、`tools/builtin/revise.py`

---

## 一、心智：老板不微操队员

用户是老板，**只对 CEO** 表达「改哪、怎么改」；CEO 自行判断热修原作者 / 另找人 / 重做。不在 worker 产物卡上做定向「要求修改」入口（产品决策 P-1）。这条心智决定了：热修能力对用户**不可见**，全部经 CEO 的工具调用发生。

---

## 二、核心设计：统一为「可恢复运行 `RunSession` + 续写」一个原语

把一次 worker run 视为**可恢复运行**：执行后不丢弃，保留完整 transcript（消息序列）。**「修订」= 在保留的 transcript 上追加一条指令、重跑 `react_loop`**。

这一个原语收编了三件本会割裂的事：

| 场景 | 续写指令来自 |
|---|---|
| 自动返工（contract 不达标） | 系统把「差距」喂回——且队员**这次看得到自己旧稿**（不再盲改） |
| CEO 热修 | CEO 把「修改意见」喂回 |
| 甲兜底（见 §三） | session 不在时用旧产物**重建**新 session 再续写 |

**为何能近免费捕获 transcript**：`react_loop` 原地往传入的 `messages` 追加，worker 跑完后该局部变量**已是完整 transcript**——以前只是被丢弃。

> **被否决：三套独立「重做」机制并存**。理由：触发项目纪律「补丁绊线」（同一接缝第 3 次打补丁）；且 `react_loop` 现成支持续接消息再循环，无需另起炉灶。

---

## 三、甲 / 乙：同一接缝的两种命中态

| 代号 | 形态 | 数据流 |
|---|---|---|
| **甲** | 拿旧产物当输入，重新派新人改 | 产物 → 输入 → 新执行 |
| **乙** | 唤回原作者，带现场记忆续写 | 续接已有 transcript |

**关键**：乙做跨轮必然要把记忆落盘、下一轮取出喂给一次新执行——这条兜底分支的数据流**就是甲**。所以甲不是独立开发项，而是**乙在缓存（内存 + 盘）双 miss 时的透明回落路径**。唤回未命中 / 超限时，`revise` 拒绝并提示 CEO 回落甲（重新 `delegate`）。

---

## 四、关键组件与契约（现状）

| 契约项 | 约束 |
|---|---|
| 改次上限 | 默认 **3** 次定向热修 / run，超限回落甲（重 `delegate`） |
| roster 内存 | conversation 维度；LRU + TTL（默认 ~30 min）+ 字节/条数上限 |
| 跨进程落盘 | `run_sessions` 表，默认 **7 天**空闲 TTL；`session_roster_persist_enabled`（默认开） |
| 双 miss 回落 | `revise` 内存 miss → 从盘回温；仍 miss → 拒绝并提示 CEO 回落甲 |

→ 见代码：`runtime/runs/session.py`、`tools/builtin/revise.py`。

## 五、约束边界与配置

- **改次上限**：默认 **3** 次定向热修 / run（常量 `DEFAULT_RECALL_LIMIT`，参照 contract「一次自动返工」给人工热修略宽至 3）；超限回落甲。
- **roster 内存**：挂 conversation 维度；LRU + TTL（默认 ~30 min）+ 字节 / 条数上限，对齐 approvals / channel / locks 的单机 posture。
- **落盘保留**：默认 **7 天**空闲 TTL，到期清理；开关 `session_roster_persist_enabled`（默认开）。
- **委派深度**：续写不增加委派深度；嵌套委派硬上限 `depth ≤ 2`（见 [`执行引擎架构设计.md` §8.4](/docs/03-AI核心/执行引擎架构设计.md)）。

## 七、修订投影：星型建模 → 链式可视化（✅ 现状）

「保留版本链、可对比」（§六 P-2）在图上的**投影架构**：后端按星型存、前端铺成链渲染，二者刻意分离。

- **后端＝星型建模**：每个修订 run 的 `parent_run_id` / `revisionOf` 都指回**原始 run**（非指前一修订）。修订＝同一 run 的多次重跑，锚在原始最稳、无需维护链式指针。
- **前端＝链式可视化投影**：`buildGraphStructure` 把星型**铺成链**（原始→v2→v3→…）交 ELK 顺序布局，各版本互不重叠。**为何投影层铺链、不反噬后端拓扑**：「一条演进链」是呈现职责。曾有 bug＝前端照星型为每版从原始各拉平行边 → ELK 把每版塞进原始的同一后继槽、坐标近乎重合 → N 版只剩最后一版可见；根治＝投影层铺链，后端星型不动。
- **修订身份随 `run_started` 上 wire**：修订序号（`recall_count`）会与业务轮次脱钩，故 `run_started` 显式携 `round`（辩论另携 `stance`/`group`）声明身份 → 三端 fold 据此把修订投到正确轮次 / 立场；老日志缺字段时**从原始 run 继承**兜底。辩论叠加见 [`辩论编排设计.md §7.3`](/docs/03-AI核心/辩论编排设计.md)。
- **三端一致（conformance）**：后端 golden oracle（`conformance/projection.py`）与桌面 / 手机 fold 对同一向量断言 `== golden`；改任一端投影须重生 golden 再跑 `pnpm conformance`（见 [`protocol-conformance.mdc`](/.cursor/rules/protocol-conformance.mdc)）。

→ 见代码：`runtime/events/run.py`（`run_started` 携身份）、`runtime/runs/executor_continue.py`；前端 `stores/execution/{frames,project}.ts`、`components/graph/helpers.ts`（`buildGraphStructure` 铺链）、`lib/elk-layout.ts`（compound 内修订边顺序布局，链直不重叠）。

## 八、交付正文只留最终交付、旁白入 journal（全队对称 ✅）

> **定位**：一次 run 跨多轮 ReAct 时，「调**非终止**工具前写的那段话」（开场白 / 对注入的 `[系统提示]` 操舵的口头应答）是**过程旁白**，不是**交付**。持久化的成品只留最终答案轮的文本，旁白入 journal。CEO / worker / 辩手 / **续写** / eval **全队对称**——续写（§二 的原语、`executor_continue`）同样只把「完整最终产出」落成品。

**根因**：曾观察到 CEO 把「谢谢指正，我重新整理。」写进持久化正文——那是对引擎注入的 finish_guard 操舵 `[系统提示]` 的口头应答，却被当成交付攒进了 `messages.content` / 下一轮 history / 搜索预览。过程旁白泄漏进成品。

**机制（复用 finish_guard 回炉，不新增机制）**：`react_loop` 收 `deliverable_only`。某轮写了正文又调**非终止**工具 → 把这段正文从累加器 `final_content` 回退掉（镜像 finish_guard `Rework` 的回退），只有**最终答案轮**的文本进成品。旁白仍逐字直播过、且每轮记进 journal 的 `llm_call` fact（→ 过程时间线）。**终止轮**（`ask_user` / handoff / 挂起 checkpoint）的工具前文本**保留**——那在该边界上**就是**交付。

**两种显示纪律，按「通道」分（关键、代码看不出的架构点）**：

| 角色 | 通道形态 | 旁白回退后 |
|---|---|---|
| **CEO**（`on_reset=None`；正文与过程时间线是**两条**通道） | 不发 reset | 旁白仍在过程时间线里透明可见；仅 `messages.content`（旁路 conformance）被裁 |
| **worker / 辩手 / 续写**（`on_reset→run_output_reset`；卡片＝数据是**同一**通道） | 发 `run_output_reset` | 卡片上已直播的旁白也清掉，使 **直播 ＝ 重载（合成自 `message_final`）＝ 交付** |
| **eval 单跑** | 同 CEO（`on_reset=None`） | 打分只看最终交付，忠实反映用户所见 |

**为何 worker 必须发 reset、CEO 不发**：worker 卡片是「显示＝数据」单通道，重载时其产物由 `message_final` fact **合成** `run_output_delta`（`journal/fold.py` 的 `_splice_synthetic_deltas`）——若直播留旁白而 `message_final` 已裁，就出现「直播 ≠ 重载」，破 §七 的 conformance 不变式；故直播也须 `run_output_reset` 对齐。CEO 的正文（`messages.content`）与过程时间线（`content_delta` 流）本就是两条通道，旁白留时间线不污染成品，无需 reset。

> **被否决：给 worker 也开「旁白单独一路显示」的双通道**——否决：徒增协议面 + 存储，且 worker 过程旁白的观看价值低于 CEO；复用 finish_guard 已有的 `run_output_reset` 对偶即达成「不留补丁」。

### 8.1 多段交付拼接成连贯终稿 ✅

长回合的持久化终稿可能由多段交付拼接（终止轮边界文本如 `ask_user` / handoff 前段、挂起→续跑的续段、`force_finalize` 收尾段）。契约仍是 **deliverable_only**（不做全程叙事、不另开全量 LLM 重写收尾）。连贯性靠两层：

| 层 | 手段 | 作用 |
|---|---|---|
| **组合接缝** | `join_segments`：归一空白、段落间 `\n\n`、去掉新段对上段末的复述前缀 | 机械去断裂 / 去重复开场 |
| **作答操舵** | 已有交付前文时注入 `[系统提示]` continuity（resume 续跑、force_finalize） | 模型自然衔接，不另起一篇独立答卷 |

搜索预览与下轮 history 仍只用拼接后的交付正文。气泡「复制 / 分享」另提供「含过程」档读 journal 过程时间线——见 [前端 UX §一B](/docs/04-前端/前端UX设计.md)。

→ 见代码：`runtime/engine/segments.py`（`join_segments` / `deliverable_continuity_instruction`）、`runtime/engine/finalize.py`、`runtime/pipeline/resume/pipeline.py`。

→ 见代码：`runtime/engine/loop.py`（`deliverable_only` + 回退 / `emit_reset`）、`runs/executor_captain.py`（CEO）、`runs/executor_shared.py`（`_react_and_capture`：worker / 辩手 / 续写）、`evals/harness.py`（单跑）；conformance 向量 `multi_agent_worker_deliverable_reset`。

## 九、被否决 / 暂不做

- **三套独立「重做」机制并存**——否决（补丁绊线；见 §二）。
- **删掉甲、只支持同轮乙**——否决：**换角色改**（研究员稿→工程师改）、**救失败稿**、**合并多产物**这三类结构上就是「新派一人 + 旧产物当输入」=甲，乙再满血也覆盖不了，故甲能力须保留（即 §三 的 miss 回落分支）。
- **语义裁判（判「写得好不好」的额外 LLM 校验）**——暂不做，沿用机械 contract；续写指令由 CEO（人类意图代理）或机械差距给出。

## 十、跑一半改方向（`run_redirect`）

> **定位**：并行 worker **仍在 running** 时，用户侧栏点「立即改此人」→ 只停一个跑偏 worker → 带新方向重跑；并行队友与整轮不受影响。与便签 `heads_up`（软广播）分工：redirect 是硬约束，便签是软信号——简介审查「方向错了」两条线都要。

### 10.1 现状

| 步 | 能力 | 状态 |
|---|---|---|
| Step 1 | 交互契约：`run_redirect`（`run_id` + `feedback` + `execution_id`）→ turn 级 redirect 队列；`RunDetailBody`「立即改此人」→ `POST …/run-redirect` | ✅ |
| Step 2 | `WaveScheduler` 单人 cancel（单 task cancel 不拖死整批；被取消节点 `CANCELLED`、不级联 skip、兄弟照跑）；`run_cancelled(reason=redirect\|stop)` 双语义（redirect=单人改方向；stop=整轮停止）。整轮 abort 时 wave 外层 `cancel("stop")` + `shield` drain，保证每个 in-flight worker 都落到 journal/SSE；conformance `multi_agent_run_stop_cancels_workers` | ✅ |
| Step 3A | 热续写（优先）：cancel 时 salvage 可续写 transcript → `continue_run` 修订子节点；编号对齐 `revise`（`{run_id}_rev{recall_count+1}`，wire `revision=recall_count+2`，同作者链递增）；conformance `multi_agent_run_redirect_hot` | ✅ |
| Step 3B | 冷诚实回落：空/不可续写 → drive 追加同角色接手节点（`{run_id}_redir` + `replaces_run_id` + `steer`），`WaveScheduler` 重扫即调度；对该接手节点再热续写走 `{redir_id}_revN`；conformance `multi_agent_run_redirect_cold_fallback` | ✅ |
| Step 4 | 忽略路径收口：`run.redirect_ignored` / `run.deterministic_failure` 审计触发 → run 详情「接受此结果」→ `POST …/accept-outcome` 落 `run.outcome_accepted`（幂等、owner-scoped）；conformance `multi_agent_run_redirect_ignored`（wire 无幻影节点、无 `run_cancelled`） | ✅ |

**关键接缝**：热优先·冷诚实回落——有可 salvage 的 partial 走 3A 修订链；空产出或热失败才走 3B `_redir` 接手（图上标「接手」，非并行幻影）。`run_cancelled.reason` 区分 redirect（单人，可跟热/冷 follow-up）与 stop（整轮 abort，无 per-worker 接手）。同人多次「立即改此人」共用作者链 `recall_count`（与 `revise` 改次闸一致），勿固定 `_rev1`。delegate 期间 CEO 阻塞，redirect 必须走 **interaction 桥**（用户直控），不能等 CEO 自己 `revise`。「记下改法」预填输入框是 **跑完后发送** 的折中；真正单人中途 steer 由 Step 2–3B 承接。Step 4 收口的是**来不及应用**的 steer（`run.redirect_ignored`）与**确定性失败**（`run.deterministic_failure`）——二者均走审计带外 + accept-outcome REST，**不新增 SSE 事件**；整轮「放弃」仍用 `clearExecution` 清本地投影。

→ 见代码：`redirect_queue.py`、`runs/wave.py`（`cancel_run_ids`）、`runs/salvage.py`、`tools/builtin/delegate/drive.py`（热优先 continue_run / 冷 `_redir` / `on_run_redirect_ignored`）、`api/routes/conversations/run_redirect.py`、`services/runRedirect.ts`、`RunDetailBody.tsx`。

### 10.2 验收标准

1. 并行 ≥2 worker，redirect 其一 → 另一仍在 running/completed，整轮不 `cancelled`
2. 被 redirect worker 出现新产出（热：revision 子节点；冷：`_redir` 接手节点）
3. redirect 事件 journal 可回放；`#/preview` 可见节点态变化
4. 「停止整轮」仍 abort 全回合（回归）
