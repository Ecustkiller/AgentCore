# 同人连续委派提案

> 状态：🗂️ 讨论提案（2026-07-12，已过一轮双线审计并修订）。已拍板：需求立项、「接续链而非实体化」定位、**统一原语**（不做 revise / 续派双轨）。待定：§五现场保留语义确认。定稿后按 §八 切片实施、结论迁 `01`–`05`。

## 一、需求与三问

- **谁用**：CEO 主 Agent（受益方还包括看协作图的用户）。
- **真实问题**：CEO 想让「刚干完任务 A 的那个 worker」接着干——可能是改 A 的产出，也可能是干强相关的新任务 B。今天前者走 `revise`、后者只能冷启动新人（阶段 1 `agent_id == run_id`）+ task 手动转述，而 **ReAct 轨迹（读过什么、试错过什么、决策理由）无法转述**，恰恰是最值钱的现场。
- **产品呈现**：CEO 委派时可声明「这个任务让某个 worker 带现场接着干」；协作图上同一人连续干的活串成一条「续」链（新节点 + 角标 + 弱样式接续边）。

## 二、定位（已拍板）：接续关系，不是 Agent 实体化

「同人」建模为 **run 之间的接续链**（`continues_run_id`，类比既有 `replaces_run_id` 接手链），**不引入跨 run 稳定的 agent 实体**：

1. **不撞已否决赌注**：执行引擎否决的「worker 实体化」是「临时角色 → 稳定专家实体 / 固定团队」（守「无团队选择器、每回合自适应组队」）；接续链只是「那个人的现场还在，让他接着干」，不新造持久实体，不预锁 Phase 2 `AgentResolver` 形态。
2. **前端流式隔离零改动**：桌面 fold 把流式产出存在 agent 维度、靠 `agent_id == run_id` 隔离；续派 run 沿用「新 run 新 agent_id」，同人性由 `continues_run_id` 表达，避开流式串台雷。（fold 字段与图投影本身必改，见 §八；零改动仅指流式隔离模型。）
3. 身份色按 role 派生，同 role 自然同色，「角色延续」观感免费获得。

## 三、统一原语（已拍板）：一个动作「带现场续派」，revise 退役

**产品判断（用户拍板，2026-07-12）**：「改稿」与「接新任务」在机制与产品上是同一件事——唤回同一现场、追加新指令、继续干；区别只在指令内容。不做双轨（本提案初稿的 revise / 续派并行方案被否，见 §七）。

### 3.1 CEO 侧：`delegate` 的 `tasks[]` 增加可选 `continue_from_run_id`

- 声明该任务由目标 run 的作者**带现场**接着干；task 内容自然表达是改稿还是新任务，CEO 无需二选一。
- 续派任务获得 `delegate` 全套能力：`depends_on`、`deliverable` 契约、`objective` 等（旧 `revise` 不具备）。
- **`revise` 工具退役**：能力被完全覆盖（改稿 = 续派 + task 写修改要求）。开发期无真实数据、无兼容包袱，直接删除不留别名。
- 冷委派（换角色 / 救失败 / 合并任务线，原「甲」路径）能力不变，仍是独立新任务的正路。
- schema 指导文案：强相关接续（改稿 / 延续调查 / 接着实现）→ 带现场续派；独立新任务 → 冷委派（防上下文污染）。

### 3.2 执行路径：`continue_run` 收敛为单一「续干」态

`continue_run`（RunSession transcript 续写）现有消费方——`revise`、redirect 热修、辩论续轮/质询/结辩——收敛后统一为「续干」语义：

- **run 身份**：普通 `del_*` 新 run id；wire 挂 **`continues_run_id`**。
- **星型建模（沿用既有拍板，不推翻）**：`continues_run_id` **恒指现场根**（原始 run，即 RunSession 的键）——与底层「所有续写都在同一个 session 上迭代」天然一致；前端照旧铺链呈现（[多轮编排与队员热修.md](/docs/03-AI核心/多轮编排与队员热修.md) §七既有决策：后端星型、前端铺链，链序由事件序保证；历史教训「照星型画平行边」不得重演）。
- **`parent_run_id` 保留、仅退役其修订用法**：该字段同时承载嵌套委派 / 辩论主持人的**父子结构**（不能动）与修订星型锚（由 `continues_run_id` 接管）。续写 run 的 `parent_run_id` 恢复为真正的委派父（captain / moderator），不再指向被续写的 run。**wire 的 `revision` 数值字段退役**；辩论轮次语义本就由 `round` + `run_context.channel` 承载。同 run 内契约自动返工不受影响（不发新 run）。
- **追加消息**：统一「续干」模板——新指令 + 该任务的依赖产物注入（与冷开局同构的块渲染进续写消息），不再区分「修改要求 / 新任务」两套模板。
- **现场登记时机提前**：由「整波结束后统一登记」改为「**单个 run 完成即登记**」，使同批「`depends_on` X + `continue_from_run_id` X」组合成立（先等他干完、再让他带现场接着干）。
- **输入校验（明确报错，不静默）**：目标 run 进行中 / 未登记 / 自指 → 拒绝该项并说明；session 双 miss（内存 + DB）→ 拒绝并提示冷委派（已拍板：不静默降级——CEO 以为有现场实际没有，比明确失败更糟）。
- **唤回上限：闸只管 CEO 侧**——CEO 主动续派与 redirect 热修共用每条链合计 3 次（`recall_count`，堆的是同一份 transcript）；**辩论等编排性续写豁免**（审计确认现状辩论走 `continue_run` 涨计数但不受闸，多轮 + 质询 + 结辩单方续写常 ≥4 次，统一闸会卡死辩论；轮次上限由辩论编排自身的 `RoundPolicy` 管）。

### 3.3 wire 契约与 conformance

- `RunStartedPayload`：加 `continues_run_id`、退役 `revision`（`round` / `stance` / `group` / `parent_run_id` 不动）；`ContextChannel` 的 `revision` 通道更名 `continuation`（语义泛化）。
- **勿误伤同名字段**：`plan_revised` 事件的 `revisions`（bind / steer 计划修订）与 run 级 `revision` 同名不同义，本提案不碰。
- `payloads/run.py` → 重生 `packages/contract-types`；受影响向量批量重做（`multi_agent_revision`、redirect 系列、辩论 / 圆桌 multibeat 等）+ 新增 `multi_agent_redelegate_continuation`；oracle `projection.py` 合成逻辑同步；export → 两端 fold → `pnpm conformance`。

## 四、图呈现（按 [`前端UX设计.md` §五裁决准则](/docs/04-前端/前端UX设计.md)）

- 续派 run = **①类新委派节点**；同一人连续的活串成一条链：角标统一为「续 ×N」（multi_agent 场景；辩论仍按 `round` / `channel` 出「第 N 轮」「结辩」，`planCapabilities` 查表不变），源 → 续派画弱样式**接续边**（替代原 `revision` 边 kind）。
- **辩论投影判据点名迁移**（防回归重点）：质询折叠宿主解析（`debateStatementHostId`）、子队盒修订根归属（`projectFlowGraph` parentId 解析 + `elk-layout` `containsTeam` / `revisionRootOf`——此处有历史 phantom gap bug，迁移判据时四处一致性必须复验）、辩论直播轮次链（`stores/execution/debate.ts`）。
- **对比透镜泛化**：原「修订版本对比」改为「接续链上任意两次产出对比」；状态条「改了 N 版」计数判据由 `revisionOf` 迁 `continuesRunId`（辩论照旧不计），文案实施时按链内容打磨；`turn_metrics.revises` 等指标语义同步改「续派次数」（不计辩论），admin 协作质量卡跟随。
- 侧栏 `RunRevisionChain` 更名接续链区段；hover peek「接续 {role} 的现场」。

## 五、现场保留（待拍板）：「对话在，现场就在」

RunSession 双层存储：内存 roster（30 min TTL，纯性能缓存，miss 自动 DB 回温，用户无感）+ DB `run_sessions` write-through。现状 DB 侧 `session_roster_retention_days = 7` 天清扫——**省存储的默认参数，不是架构约束**。

**提议的产品语义**：现场生命周期跟随对话——对话存在则现场可唤回；删对话时级联清理。**审计确认级联是新做**：现状 `ConversationRepository` 的 soft / hard delete 均**故意不删** `run_sessions`，需新增按 `conversation_id` 的级联清理（纳入 §八 切片 1）。定期清扫仅作远期存储保护兜底，开发期不启用激进清理（无真实数据，存储膨胀是假设问题）。

## 七、被考虑并放弃的路线

| 路线 | 放弃理由 |
|---|---|
| **revise / 续派双轨并行**（本提案初稿） | 用户否决（2026-07-12）：机制与产品上是同一内容，双轨 = 在旧设计上打补丁——两套入口 / 标记 / 图呈现，CEO 还要二选一 |
| 前情摘要注入（新 run 冷开局 + 上一 run 产出摘要块） | 丢 ReAct 现场，本质是自动化转述，增量小 |
| 新工具 `redelegate` | 与 `delegate` 重合 90%，CEO 工具面膨胀 |
| 跨 run 稳定 `agent_id`（真实体化） | 前端流式按 agent 维度存会串台；提前锁死 Phase 2 形态、撞「自适应组队」赌注 |
| 统一 `recall_count` 闸覆盖辩论 | 审计 P0：多轮辩论单方续写常 ≥4 次，会被 3 次闸卡死；辩论轮次上限归 `RoundPolicy` |
