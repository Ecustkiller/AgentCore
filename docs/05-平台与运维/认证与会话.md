## 一、设计基线

| 维度 | 选择 | 理由 |
|---|---|---|
| 登录标识 | **用户名 + 密码** | `username` 唯一非空；`email` 可空，留作后期找回/OAuth |
| 令牌传输 | **httpOnly Cookie** | 前端 `credentials:include`、CORS `allow_credentials=True`；SSE/fetch 天然带 Cookie，前端 JS 拿不到令牌明文（抗 XSS） |
| 令牌载体 | **双 Cookie**：access（短）+ refresh（长，path 限 `/v1/auth`） | refresh 限定 path，减小暴露面 |
| 密码哈希 | **argon2id**（`pwdlib[argon2]`） | 规避 passlib+bcrypt≥4.1 兼容坑；salt + 参数内嵌于哈希串 |
| 注册开放性 | **邀请码**（`invites` 表） | 公网防滥用 |
| 暴力破解 | 失败计数 + 5 次锁定 15min | |

> **Schema 真相源**：本仓 ORM + alembic 是数据库 schema 的**单一真相源**（初始迁移 `bfb6ea2824ae_initial_schema` 全新接管，不与任何历史库结构兼容）。

## 二、数据模型

四张表（→ 见代码 `db/models.py`）：

| 表 | 关键字段 | 说明 |
|---|---|---|
| `users` | `user_id`(PK) / `username`(唯一) / `display_name` / `email`(可空) / `role` / `status` | 账号主体；`role∈{user,admin}`、`status∈{active,disabled}` |
| `credentials` | `user_id`(PK,1:1) / `password_hash` / `failed_attempts` / `locked_until` | 密码与锁定状态独立成表，与账号资料解耦 |
| `invites` | `code`(唯一) / `created_by` / `used_by` / `used_at` / `expires_at` | 邀请码；一次性，用后置 `used_at` |
| `refresh_tokens` | `token_hash` / `token_family` / `expires_at` / `revoked_at` / `rotated_at` | 轮换 + 重用检测的载体；**库里只存哈希** |

设计约束：

- **密码只存哈希**：argon2id，不可逆，无明文列。
- **refresh 只存哈希**：明文（`secrets.token_urlsafe(48)` 高熵随机串）发给客户端，库存 SHA-256 摘要——高熵随机串无需慢 KDF，热路径用快摘要即可。
- 遵循数据建模约定（无 ForeignKey、UUID 主键、`server_default`），见 [`../02-架构/核心接口定义.md` §6.2](/docs/02-架构/核心接口定义.md)。

## 三、令牌模型

| 令牌 | 形态 | 生命周期 | 用途 |
|---|---|---|---|
| access | **无状态 JWT**（HS256，claims `sub`/`type`/`iat`/`exp`） | 默认 30min | 所有 API 请求，随 access Cookie 自动携带 |
| refresh | **不透明随机串**（库存哈希） | 默认 7d | 仅换新 access；随 refresh Cookie 带到 `/v1/auth` |

access 校验是纯本地 JWT 解码（无需查库）；任何无效/篡改/过期/类型不符一律抛 `AuthenticationError` → 401，调用方统一翻译。

## 四、端点契约

`POST /v1/auth/{register,login,refresh,logout}` + `GET /v1/auth/me`（已在 `main.py` 注册，`prefix=/v1`）。响应模型以 `api/schemas.py` 为准。

| 端点 | 请求 | 成功 | 失败 |
|---|---|---|---|
| `register` | `{username, password(≥8), invite_code, display_name?, email?}` | 201 + `UserResponse` | 422 邀请码无效/已用、用户名占用、弱密码 |
| `login` | `{username, password}` | 200 + `UserResponse`，Set-Cookie 双令牌 | 401 用户名或密码错误（**不区分账号是否存在**）、账号锁定 |
| `refresh` | 无体，依赖 refresh Cookie | 200 + `StatusResponse`，轮换双令牌 | 401 缺失/无效/过期/重用（并清 Cookie） |
| `logout` | 无体 | 200，撤销当前 family + 清 Cookie | — |
| `me` | access Cookie | 200 + `UserResponse` | 401 未认证 |

`UserResponse` 字段：`id` / `username` / `display_name` / `email` / `role` / `created_at`。

**邀请签发（admin 专属）**：`POST /v1/auth/invites`（生成单次邀请码，body `{expires_in_days?}`，201 + `InviteResponse`）、`GET /v1/auth/invites`（列出近期邀请，带 `active/used/expired` 状态）。经 `AdminUser` 依赖闸门，非 admin → 403。`InviteResponse` 字段：`id/code/status/created_by/used_by/created_at/expires_at/used_at`。前端入口在「设置 → 成员」（仅 admin 可见）。

> **首个 admin 引导**：注册受邀请码闸门，新部署无邀请码 → admin 无法自注册（鸡生蛋）。用 `scripts/create_admin.py <username>`（密码取 `ADMIN_PASSWORD` 或交互输入，幂等：创建 / 提升 / 补密码）创建首个 admin，登录后从「设置 → 成员」签发邀请码。`UserRepository.set_role` 支撑提升。

> **注入约定**（落实 `.cursor/rules/api.mdc`）：`AuthUser`（必须登录，401）/ `OptionalUser`（未登录返 None）/ `AdminUser`（须 admin，否则 403），读 `access_token` Cookie 解析。权限在 **service 层**校验。

## 五、刷新令牌轮换 + 重用检测

refresh 单次使用，every refresh 把旧令牌标 `rotated_at`，并在**同一 `token_family`** 内签发后继（仅 login 起新 family）：

| 场景 | 行为 |
|---|---|
| 令牌首次交换 | 标记 `rotated_at`、同 family 签发后继 |
| 已 `rotated`/`revoked` 的令牌再次出现 | 判为泄露/重放 → **吊销整个 family**（`revoke_family`），强制重登 |
| 令牌已过期 | 拒绝 |

> **与原设计的偏差**：原设计含「10s 并发宽限窗口」应对多标签页善意并发；**当前实现未做宽限窗口**——任何已轮换令牌再现即连根撤销 family。多标签并发刷新可能互踢，待 Phase 3 评估是否补窗口。

## 六、静默刷新与流式通道约束

> ✅ 前端（Phase 2）已落地：`auth` store（loading/authenticated/unauthenticated 三态）、登录/注册页、`AuthGate` 启动探测 `/auth/me` + 路由守卫、`api.ts` 401→刷新→重放、SSE 流（`streamConversation.ts`）同款 401 处理、`UserMenu` 登出。以下为静默刷新现状与**必须遵守的约束**。

access 过期由 401 触发刷新 → 换新 → 重试原请求，对用户无感；refresh 过期才真正跳登录。重发安全：401 在认证依赖层抛出、handler 未执行、请求无副作用，可安全重发。

**关键约束——流式通道必须各自接入刷新**：聊天 SSE（发消息、恢复、异步委派流）通常绕过统一 HTTP 封装直接 `fetch`。这些通道**必须各自包一层 401→刷新→重发**，否则「读了半小时再发消息」会因 access 过期直接掉登录，而非无感续期。**新增任何绕过统一请求层的 fetch/XHR 通道时，都须接入此机制。**

## 七、Cookie、CSRF 与易踩坑

实现现状（→ 见 `routes/auth.py` `_set_auth_cookies`）：

| 属性 | access_token | refresh_token |
|---|---|---|
| httpOnly | ✅ | ✅ |
| secure | `cookie_secure`（生产置 True） | 同左 |
| sameSite | `cookie_samesite`（默认 `lax`，可配 `strict`） | 同左 |
| path | `/` | `/v1/auth` |
| maxAge | 30min | 7d |

- **CSRF**：当前仅靠 SameSite 兜底（默认 `lax`）。原设计的 **SameSite=Strict + 写操作校验自定义头（X-CSRF 双提交）未做**，归入 Phase 3。`lax` 为兼容本地跨端口 / Electron 自定义协议客户端；待客户端 Origin 固定后可收紧到 `strict`。
- **refresh Cookie path 坑**：当前桌面端直连 `/v1/auth/refresh`，故 path 限定 `/v1/auth` 可正常回传。**但若改为 web 与 api 同源、反向代理把 `/api/` 重写到后端**，则按 RFC 6265 浏览器实际请求路径需以 Cookie path 为前缀，否则 Cookie 永不回传 → 静默刷新 100% 失败（dev 直连测不出，仅生产触发）。改部署拓扑时务必复核此项。
- **CORS 源可配置**：`CORS_ALLOW_ORIGINS`（逗号分隔）取代硬编码 localhost；凭证式 CORS 禁用 `*`，须逐一列源。CORS 中间件置于限流外层，故 429 也带 CORS 头。**Electron 生产包走 `file://`（Origin `null`），跨站无法带 Cookie 到远端 API**——仅放行 CORS 不够，需 Web 与 API 同站（反代）或改 `app://` 自定义协议 / Authorization 头模式；属部署架构决策，尚未实施。
- **排障口径**：「总是掉登录」先查刷新链路（Cookie path / SSE 是否接入刷新 / 轮换是否互踢），调长 access 过期时间只是掩盖、非根治。
