## 〇、为什么成本是产品而非基建

AgentCore 是 multi-agent，一条用户消息 = CEO + N 个委派 worker，**花销天然能按 Agent/角色拆开**——这是单 Agent 竞品（Cursor/Codex/Claude）做不到的「团队工资单」。别人只能说「这次花了 ¥X」；AgentCore 能说「CEO ¥0.03 / 调研员 ¥0.05 / 写作 ¥0.04」。所以用量可观测是**产品差异点**，台账的 per-run 粒度（§三）正是为这个差异点服务。

## 〇·五、计费模式：内测期 BYOK（自带端点，✅ 已落地）

内测期默认 **BYOK（bring-your-own-key）**：每个用户在「设置·模型配置」自备任意 **OpenAI 兼容端点**（`api_key` + `base_url` + `default_model`），每条对话跑在用户自己的上游额度上，平台不提供 key、不承担调用成本。由 `config.billing_mode` 单一开关定调（`byok`（默认）/ `platform`）。

**为什么禁用而非删除平台付费**：平台付费整套（全局 key fallback + 配额防线 + 成本账本）是带 DB 列、带防线逻辑的资产；内测期模型未定，「日后是否重启平台付费」未终结。删了再加要跑破坏性迁移 + 反向重建 + 重测一整套计费（正是开发准则「同一接缝反复动」要避免的）。故**全部保留、仅靠 `billing_mode` 开关休眠**——日后翻回 `platform` + 填全局 platform 凭据即恢复，零迁移、零 churn。

**一道闸门收口（不撒补丁）**：回合开始前的 preflight（`_preflight_turn_llm`，紧邻 §一 限流/所有权之后）按模式二选一：

- `byok`：解析用户凭据（`resolve_user_llm_credentials`，fail-safe 永不抛），无可用 key → `BYOKKeyMissingError` → **402 `LLM_KEY_REQUIRED`**（流开始前返回干净错误，前端引导到「设置·模型配置」）；解析出的凭据贯穿整条 turn——**preflight 通过 == 真能跑在这把 key 上**。
- `platform`：照走 §一 的 `enforce_quota` 配额防线。

因此 **byok 下配额防线天然休眠**——只多「`billing_mode != "byok"` 才查配额」这一个条件，不在各处撒补丁。

**BYOK 计费语义**：finalize 时 `cost_nano_usd = 0`（平台不对 OpenAI 兼容端点算价），**token 照常记入** `cost_events` 与 `Message.usage`——用户自担上游账单，平台只提供可观测性。用量 API 下发 `billing_mode` 供前端切换呈现（见 [`../04-前端/前端成本呈现.md` §7.4](/docs/04-前端/前端成本呈现.md)）。

**Key 管理面**：`/users/me/llm-key` GET/PUT/DELETE + `POST .../test`；三字段配置 + probe 连通性与 `supports_tools`；AES-256-GCM 加密落库，明文永不落盘。算法与 fail-closed/fail-safe 决策见 [`安全权限与治理.md` §七](/docs/05-平台与运维/安全权限与治理.md)。

→ 见代码 `llm/resolve.py`、`llm/key_service.py`、`llm/pricing.py`、`api/routes/llm_key.py`、`api/routes/conversations/_helpers.py::_preflight_turn_llm`

## 一、三层防线

三层正交：限流挡「刷得太快」，配额挡「用得太多」，计费只忠实记录、不拦截。

| 层 | 位置 | 管什么 | 失败行为 | 现状 |
|---|---|---|---|---|
| **限流** | 路由层（按用户）+ 中间件（按 IP） | **速率**——单位时间内的请求次数 | 超额拒绝（429 + `Retry-After`） | ✅ 已落地（默认内存单进程；`RATE_LIMIT_BACKEND=redis` 切多 worker 安全的 Redis ZSET 滑窗，含请求级 fail-open） |
| **配额** | 业务层（回合开始前） | **总量**——日 token / 月成本 / 日请求数 | 超额拒绝下一回合（429） | ✅ 强制已落地（含每用户覆盖 + admin `is_unlimited`） |
| **计费** | Finalize（append-only） | **记账**——每个 Run 的真实成本 | 失败只 warning，不中断 | ✅ 已落地（详见 §三、§四） |

### 限流（速率防线，✅ 已落地）

两个互补的限流器（默认内存、单进程；配 `RATE_LIMIT_BACKEND=redis` 即切 Redis ZSET 滑窗，多 worker 安全）：

- **按用户限流**（✅ 路由层滑窗）：在消息发送 / 重新生成端点按已认证用户限频，挡单账号刷回合。因按用户需已认证主体，落在**路由层**（紧邻 `enforce_quota`）而非中间件；用**滑窗**（非固定窗口）避免边界 2x 突发；被拦的请求不记账。超额抛 `RateLimitedError` → 429 `RATE_LIMITED` + `Retry-After`。→ 见代码 `conversation/rate_limit.py`、`middleware/rate_limit.py`
- **按 IP 限认证端点**（✅ 中间件固定窗口）：限登录/注册/刷新端点（默认 10 次/60s），挡撞库；非 auth 路径与未登录请求放行。→ 见代码 `middleware/rate_limit.py::AuthRateLimitMiddleware`

回合开始前三道闸顺序：**限流（按用户）→ 所有权 → 配额**——限流最外，未过则不做资源级 DB 查询。

前端如何呈现「被拒回合」见 [`../04-前端/前端成本呈现.md` §7.6](/docs/04-前端/前端成本呈现.md)。

✅ 多 worker：`RATE_LIMIT_BACKEND=redis` 经 `RateLimiter` protocol 缝切到 Redis ZSET 滑窗（`RedisSlidingWindowRateLimiter`）/ auth 固定窗（`RedisFixedWindowRateLimiter`），调用点零改动。✅ **请求级 fail-open**：Redis 请求期报错→放行（fail-open）并记 `rate_limit.redis_fail_open`（warning，可告警）；只放松「速率」防线，DB 支撑的「总量」配额防线不经 Redis、不受影响；工厂构造期不可达仍回落内存。→ 见代码 `middleware/redis_rate_limit.py`

### 配额（总量防线，✅ 强制已落地）

> 此防线属 `platform` 计费模式；**内测期默认 BYOK 下休眠**（见 §〇·五）。

| 决策 | 内容 |
|---|---|
| 检查时机 | 回合开始前（`enforce_quota`），超额 → 429，不腰斩进行中回合 |
| 三维度 | 日 token / 月成本（USD）/ 日请求数；默认 2M / $5 / 200（`config/quota.py`），**0 = 该维度不限** |
| 每用户覆盖 | `users` 表 `is_unlimited` + 三维度覆盖（NULL=继承全局）；`scripts/set_quota.py` 或 admin API（`PATCH /v1/admin/users/{id}`，见 [`管理员后台.md`](/docs/05-平台与运维/管理员后台.md)）设置 |

→ 见代码 `conversation/quota.py`、`api/routes/conversations/`

### 计费记账（✅ 已落地）

每个 **Run** 在 turn finalize 落一行 `cost_events`（决策② **per-run** 粒度：产品面只需 per-run，热路径更轻；per-call 审计交给结构化日志）。详见 §三/§四。

## 二、用量/成本不变量

token 与成本在系统中有多种形态（SSE wire、持久化、API 响应、计费台账），两条不变量保证不会算出两套数：

1. **唯一原始来源**：单次 LLM 调用的原始 `TokenUsage` **5 字段**（`input / output / reasoning / cache_hit / cache_miss`；`total` 为派生属性），所有用量从它累加。→ 见代码 `llm/protocol.py::TokenUsage`
2. **唯一定价转换**：全系统唯一的 `calculate_cost(model, usage)` 把 token 折成钱（`input / cached / output` 三价分离，缓存命中按 ~50× 更低价计），任何地方要成本一律调它，绝不另算单价。钱一律**整数 nano-USD**（1 USD = 10⁹），杜绝浮点。**BYOK 下跳过定价**（`cost_nano_usd = 0`，token 仍记）——用户自带端点，平台无通用 OpenAI 兼容价目表。→ 见代码 `llm/pricing.py`
   - **缓存拆分对账**：输入费按 `cache_hit/cache_miss` 拆价，但只要上游不返回 DeepSeek 专属拆分字段（BYOK `base_url` 指向代理/网关、换模型、字段缺失），裸用拆分会把「有 prompt 却无拆分」的输入静默记成 0。故按 `cache_miss = max(input_tokens − cache_hit, cache_miss)` 对账——原生路径（`hit+miss==prompt`）恒等无副作用，缺拆分时整段 prompt 按 miss 计，保证「被计价的输入 == prompt」永不落空。
   - **回落可观测**：未知/未配置 `model` 回落最便宜的 Flash 价（缺价绝不腰斩回合），但可能把 Pro 回合低估约 3×，故回落时打 `cost.pricing_fallback`（warning）而非静默，便于从日志发现漏价。

**真正的钱以 `cost_events` 台账为准**（不变量 #1）；`Message.usage` / `runs` 里的成本只是展示快照。新增任何成本展示点 → 复用统一定价函数，勿手算单价。

## 三、台账：per-run 成本事件（✅ 已落地）

| 决策 | 内容 |
|---|---|
| 粒度（②） | **per-run**：captain 根 + 各委派 member 各一行 |
| 货币（①） | 整数 nano-USD；冗余 `cost_total_nano` 标量列供窗口 SUM |
| 幂等 | `run_id` unique，upsert-by-run_id |
| 写入时机 | turn finalize，与 assistant message 共享 `message_id` |
| 写入失败语义 | **只 warning 不中断**——台账写失败记日志、回合回复已先提交 |
| 失败 run 计费 | 硬失败（worker `raise_on_error` 抛错、CEO/续跑循环崩溃）仍按**已完成轮**入账——`usage_sink` 把已计量 usage 从抛点带出，经 `calculate_cost` 折钱落 `FAILED` 行（token 已真花在用户 key 上，漏记 = 平台/用户白付）；用户主动取消（`CancelledError`）**刻意不记账**（`except Exception` 不捕 `BaseException`） |
| 真相源 | `cost_events`；`Message.usage` 仅展示快照 |

→ 见代码 `runtime/costing.py`、`db/repositories/billing.py::CostEventRepository`、失败计费 `runtime/runs/executor.py::_priced_failure`

## 六、成本预估 ≠ 实际记账

团队组建时提供启发式预估，与真实记账是两套东西，刻意如此：

- 预估用途是**比较不同团队组合的贵贱**（「三个 premium 模型会很贵」），不是预测真实账单
- 算法基于固定假设（Captain 跑 3 轮、队员各 2 轮，每轮约 3000 输入 + 700 输出 token）
- 假设串始终展示给用户，确保该数字永远不被误当成事实
