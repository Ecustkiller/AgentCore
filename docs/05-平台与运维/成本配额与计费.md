# 成本、配额与计费

> **状态**：**内测期默认 BYOK（自带 Key）已落地**——对话跑在用户自己的 DeepSeek key 上，平台付费路径（全局 key + 配额防线 + 账本）由 `config.billing_mode` 开关休眠、代码全保留（详见 §〇·五）。以下计费/配额机制在 `platform` 模式下生效、byok 下休眠但随时可翻回：**计费记账 + 读侧用量/成本聚合 + 配额强制（含每用户覆盖）已落地**——`calculate_cost` 唯一定价 + `cost_events` per-run 台账 + 三个聚合读端点（团队工资单 / 对话累计 / 账户仪表盘）+ 回合前配额检查（每用户覆盖 → 退回全局阈值，超额回合返回 429，admin `is_unlimited` 直接放行，→ 见代码 `conversation/quota.py`）。**限流（速率防线）已落地（内存单进程）**——按用户消息限流（路由层滑窗）+ 按 IP 认证端点限流（中间件固定窗口）；多 worker 的 Redis ZSET 滑窗 + fail-open 仍为目标设计（⏳，详见 §一）。
>
> 鉴权与会话见 [`认证与会话.md`](/docs/05-平台与运维/认证与会话.md)；工具审批等安全治理见 [`安全权限与治理.md`](/docs/05-平台与运维/安全权限与治理.md)；**前端成本呈现规格**（本规格 §七：工资单组件 / 仪表盘 / 各面粒度）见 [`../04-前端/前端成本呈现.md`](/docs/04-前端/前端成本呈现.md)。

## 〇、为什么成本是产品而非基建

AgentCore 是 multi-agent，一条用户消息 = CEO + N 个委派 worker，**花销天然能按 Agent/角色拆开**——这是单 Agent 竞品（Cursor/Codex/Claude）做不到的「团队工资单」。别人只能说「这次花了 ¥X」；AgentCore 能说「CEO ¥0.03 / 调研员 ¥0.05 / 写作 ¥0.04」。所以用量可观测是**产品差异点**，台账的 per-run 粒度（§三）正是为这个差异点服务。

## 〇·五、计费模式：内测期 BYOK（自带 Key，✅ 已落地）

内测期默认 **BYOK（bring-your-own-key）**：每个用户自带 DeepSeek API Key，每条对话跑在用户自己的额度上，平台不提供 key、不承担调用成本。由 `config.billing_mode` 单一开关定调（`byok`（默认）/ `platform`）。

**为什么禁用而非删除平台付费**：平台付费整套（全局 key fallback + 配额防线 + 成本账本）是带 DB 列、带防线逻辑的资产；内测期模型未定，「日后是否重启平台付费」未终结。删了再加要跑破坏性迁移 + 反向重建 + 重测一整套计费（正是开发准则「同一接缝反复动」要避免的）。故**全部保留、仅靠 `billing_mode` 开关休眠**——日后翻回 `platform` + 填全局 `deepseek_api_key` 即恢复，零迁移、零 churn。

**一道闸门收口（不撒补丁）**：回合开始前的 preflight（`_preflight_turn_llm`，紧邻 §一 限流/所有权之后）按模式二选一：

- `byok`：解析用户 key（`resolve_user_llm_credentials`，fail-safe 永不抛），无可用 key → `BYOKKeyMissingError` → **402 `LLM_KEY_REQUIRED`**（流开始前返回干净错误，前端引导到「设置·模型配置」）；解析出的凭据贯穿整条 turn——**preflight 通过 == 真能跑在这把 key 上**。
- `platform`：照走 §一 的 `enforce_quota` 配额防线。

因此 **byok 下配额防线天然休眠**——只多「`billing_mode != "byok"` 才查配额」这一个条件，不在各处撒补丁。成本账本照记，语义从「平台成本」转为「你的 DeepSeek 花费」（账本/聚合/仪表盘复用；用量页在 byok 下把额度表改为「自带 Key 不限额」，`UsageSummary.billing_mode` 下发供前端切换）。

**Key 管理面**：`/users/me/llm-key` GET/PUT/DELETE + `POST .../test`（一人一行）。Key 经 **AES-256-GCM** 加密落库（`security.KeyEncryptor`，主密钥 `config.encryption_key` = 64 hex），明文永不落盘、只回显后 4 位；缺主密钥 → 拒绝存（**503 `KEY_STORAGE_UNAVAILABLE`**，fail-safe）。连通测试打 `/chat/completions max_tokens=1`，与运行时同凭据路径（测试 == 运行）。后台任务（标题/记忆）按 owner 解析同一 key；byok 无 key 时记忆固化优雅跳过、不推进 watermark（配 key 后自愈）。

→ 见代码：`llm/byok.py`（解析）、`llm/key_service.py`（管理）、`api/routes/llm_key.py`（路由）、preflight `api/routes/conversations.py::_preflight_turn_llm`

## 一、三层防线

三层正交：限流挡「刷得太快」，配额挡「用得太多」，计费只忠实记录、不拦截。

| 层 | 位置 | 管什么 | 失败行为 | 现状 |
|---|---|---|---|---|
| **限流** | 路由层（按用户）+ 中间件（按 IP） | **速率**——单位时间内的请求次数 | 超额拒绝（429 + `Retry-After`） | ✅ 已落地（内存单进程；多 worker 的 Redis ZSET + fail-open ⏳） |
| **配额** | 业务层（回合开始前） | **总量**——日 token / 月成本 / 日请求数 | 超额拒绝下一回合（429） | ✅ 强制已落地（含每用户覆盖 + admin `is_unlimited`） |
| **计费** | Finalize（append-only） | **记账**——每个 Run 的真实成本 | 失败只 warning，不中断 | ✅ 已落地（详见 §三、§四） |

### 限流（速率防线，✅ 已落地：内存单进程）

两个互补的限流器（当前内存实现、单服务进程；多 worker 时换 Redis ZSET 滑窗）：

- **按用户限流**（✅ 路由层滑窗）：在消息发送 / 重新生成端点按已认证用户限频（默认 20 次/60s，`user_message_rate_limit_max` ≤0 关闭），挡单账号刷回合。因按用户需已认证主体，落在**路由层**（紧邻 `enforce_quota`）而非中间件——是对原「中间件」设计的有意修正。用**滑窗**（非固定窗口）避免边界 2x 突发；被拦的请求不记账，避免一直刷把自己的重置越推越远。超额抛 `RateLimitedError` → 429 `RATE_LIMITED` + `Retry-After`。→ 见代码 `conversation/rate_limit.py`、限流器 `middleware/rate_limit.py::SlidingWindowRateLimiter`
- **按 IP 限认证端点**（✅ 中间件固定窗口）：限登录/注册/刷新端点（默认 10 次/60s），挡撞库；非 auth 路径与未登录请求放行。→ 见代码 `middleware/rate_limit.py::AuthRateLimitMiddleware`

回合开始前三道闸顺序：**限流（按用户）→ 所有权 → 配额**——限流最外，未过则不做资源级 DB 查询。

⏳ 目标（多 worker）：换 Redis ZSET 滑窗 + **fail-open**（Redis 不可达时放行，绝不因基础设施抖动把用户挡在门外）。`RateLimiter` protocol 已抽象，届时为局部替换、不动调用点。

### 配额（总量防线，✅ 强制已落地）

> 此防线属 `platform` 计费模式；**内测期默认 BYOK 下休眠**（preflight 走「有没有 key」而非「用了多少」，见 §〇·五）。下文描述 `platform` 模式行为。

阈值在 `config.py`（§五），「回合开始前检查并拒绝」已接线：消息发送 / 重新生成端点在所有权校验后、SSE 流开始前调 `enforce_quota`，超额抛 `QuotaExceededError` → HTTP 429（在流开始前返回干净的 429，不腰斩进行中回合）。限额按用户解析（`QuotaLimits.for_user`：每维度有覆盖用覆盖、否则退回全局 config；`is_unlimited` 直接放行），因已认证 `User` 已随请求加载，解析零额外查询。三维度独立判定。→ 见代码 `conversation/quota.py`、落账点 `api/routes/conversations.py`。

| 维度 | 窗口 |
|---|---|
| 日 token | 当日 0 点起 |
| 月成本（USD 内部口径） | 当月 1 号起 |
| 日请求数 | 当日 0 点起 |

关键决策：

- **0 = 该维度不限制**（fail-safe 宽松默认），全 0 则直接放行
- **回合粒度**：在回合开始前检查，超额拒绝下一个回合（不腰斩进行中回合）
- **每用户覆盖**（✅ 已落地）：`users` 表存四列覆盖（`is_unlimited` + 三维度，NULL=继承全局、显式 0=该维度对该用户不限）；`is_unlimited` 跳过所有检查。设置入口为运维脚本 `scripts/set_quota.py`（`create_admin.py` 会把首个管理员标 `is_unlimited`）；未来 admin 成员页可包同一 `UserRepository.set_quota`。→ 见代码 `db/models.py::User`
- **轻量到可放热路径**：覆盖随已认证 `User` 同行读取、**零额外查询**；一次检查 = 1–2 次成本事件聚合（先查日窗口；仅当日维度通过且配了月成本上限时再查月窗口），命中既有索引（`ix_cost_events_user_created`，§四）；全 0 / `is_unlimited` 时直接放行、零聚合

### 前端如何呈现「被拒回合」（✅ 已落地）

限流 / 配额都在 SSE 开始前返回纯 JSON 429（非事件流），前端在对话输入上方弹错误条并**按 `code` 分流**：

- `QUOTA_EXCEEDED`：展示后端原文（已含重置时间），**不给重试**——立即重试只会再撞墙，须等窗口重置
- `RATE_LIMITED`：展示冷却提示（`Retry-After`），**可重试**——等几秒再发即可

拒绝文案以后端 `message` 为**单一来源**，前端原样展示、不另造（改文案改后端）。→ 见代码 `apps/desktop/.../services/streamConversation.ts`（`describeStreamError` / `isRetriableStreamError`）

### 计费记账（✅ 已落地）

每个 **Run** 在 turn finalize 落一行 `cost_events`（决策② **per-run** 粒度：产品面只需 per-run，热路径更轻；per-call 审计交给结构化日志）。详见 §三/§四。

## 二、用量/成本不变量

token 与成本在系统中有多种形态（SSE wire、持久化、API 响应、计费台账），两条不变量保证不会算出两套数：

1. **唯一原始来源**：单次 LLM 调用的原始 `TokenUsage` **5 字段**（`input / output / reasoning / cache_hit / cache_miss`；`total` 为派生属性），所有用量从它累加。→ 见代码 `llm/protocol.py::TokenUsage`
2. **唯一定价转换**：全系统唯一的 `calculate_cost(model, usage)` 把 token 折成钱（`input / cached / output` 三价分离，缓存命中按 ~50× 更低价计），任何地方要成本一律调它，绝不另算单价。钱一律**整数 nano-USD**（1 USD = 10⁹），杜绝浮点。→ 见代码 `llm/pricing.py`

**真正的钱以 `cost_events` 台账为准**（不变量 #1）；`Message.usage` / `runs` 里的成本只是展示快照。新增任何成本展示点 → 复用统一定价函数，勿手算单价。

## 三、台账：per-run 成本事件（✅ 已落地）

| 项 | 决策 |
|---|---|
| 粒度（决策②） | **per-run**：一个 Agent 参与一行（captain 根 + 各委派 member 各一行），`rounds` 记该 run 内 LLM 调用次数 |
| 货币（决策①） | 存**整数 nano-USD**；`cost = {input, cached, output, total}` + 冗余 `cost_total_nano` 标量列（窗口 SUM 走整数、命中索引、不挖 JSONB）；CNY 仅展示层用单一汇率折算 |
| 幂等 | `run_id` unique，台账写是 upsert-by-run_id（`on_conflict_do_nothing`），重试不双记 |
| 写入时机 | turn finalize（captain 根 + 各 member 各落一行），与 assistant message 共享 `message_id`，故工资单按 `message_id` 查即对齐持久化消息 |
| 失败语义 | **只 warning 不中断**（文档铁律）：台账写失败回滚该笔、记日志、继续；回合的回复已先提交、不受影响。即便无 assistant 文本也落账（token 已花） |
| 真相源 | `cost_events`（不变量 #1）；`Message.usage` 仅展示快照 |

→ 见代码：`runtime/costing.py`（RunState → 台账行，唯一桥）+ `db/repositories.py::CostEventRepository` + 落账点 `conversation/service.py`

## 四、读侧聚合与接口（✅ 已落地）

**SSE（实时点亮）**：成本是**完成时事实**（usage 只在最后一个 chunk 到达），无流式成本增量 → 一律挂完成事件：`run_completed.{role, model, usage, cost}` 点亮工资单一行，`message_end.cost` 给回合总账。

**REST（回放 / 聚合）**：

| 端点 | 用途 | 数据源 |
|---|---|---|
| `GET /v1/messages/{id}/cost` | 团队工资单（per-Agent 明细 + 回合合计） | 按 `message_id` |
| `GET /v1/conversations/{id}/cost` | 对话累计 | 按 `conversation_id` |
| `GET /v1/usage/summary` | 账户仪表盘（今日/本月用量+成本、quota、汇率） | 按 `(user_id, created_at)` 窗口 |

- **聚合**：JSONB 的 token/cost 分量 cast 求和，回合总额走冗余 `cost_total_nano` 标量列；`turns` 数 distinct `message_id`（请求/回合代理）。命中两个复合索引 `ix_cost_events_user_created`（账户窗口）/ `ix_cost_events_message`（工资单）。
- **权限**：三个读都按 `user_id` 收敛（IDOR-safe）；message 端点对非所有者返回零值空名单、不泄露存在性。
- **类型**：Pydantic ↔ TS 一一对应（OpenAPI 生成）；钱以整数 nano-USD 流转，`cny_total` / `cny_per_usd` 由服务端用单一汇率折算下发，前端不写死汇率（合计仍以各 run 已定价之和为准，不重新定价）。

→ 见代码：`api/routes/usage.py` + `api/schemas.py`（`CostBreakdown` / `UsageBreakdown` / `AgentCostLine` / `TurnCost` / `ConversationCost` / `UsageSummary` 系列）

## 六、成本预估 ≠ 实际记账

团队组建时提供启发式预估，与真实记账是两套东西，刻意如此：

- 预估用途是**比较不同团队组合的贵贱**（「三个 premium 模型会很贵」），不是预测真实账单
- 算法基于固定假设（Captain 跑 3 轮、成员各 2 轮，每轮约 3000 输入 + 700 输出 token）
- 假设串始终展示给用户，确保该数字永远不被误当成事实
