## 〇、为什么成本是产品而非基建

AgentCore 是 multi-agent，一条用户消息 = CEO + N 个委派 worker，**花销天然能按 Agent/角色拆开**——这是单 Agent 竞品（Cursor/Codex/Claude）做不到的「团队工资单」。别人只能说「这次花了 ¥X」；AgentCore 能说「CEO ¥0.03 / 调研员 ¥0.05 / 写作 ¥0.04」。所以用量可观测是**产品差异点**，台账的 per-run 粒度（§三）正是为这个差异点服务。

## 一、三层防线

三层正交：限流挡「刷得太快」，配额挡「用得太多」，计费只忠实记录、不拦截。

| 层 | 位置 | 管什么 | 失败行为 | 现状 |
|---|---|---|---|---|
| **限流** | 中间件（Redis 滑窗） | **速率**——单位时间内的请求次数 | fail-open（Redis 故障放行） | ⏳ 目标设计 |
| **配额** | 业务层（回合开始前） | **总量**——日 token / 月成本 / 日请求数 | 超额拒绝下一回合 | ⏳ 阈值已配置，强制未接入 |
| **计费** | Finalize（append-only） | **记账**——每个 Run 的真实成本 | 失败只 warning，不中断 | ✅ 已落地（详见 §三、§四） |

### 限流（速率防线，⏳ 目标设计）

两个互补的滑窗限流器（Redis ZSET 滑窗）：

- **按用户限流**：限制对话消息发送端点的频率（N 次/60s），挡单账号刷回合。值 ≤0 关闭；未登录请求放行（让路由自身返回 401）
- **按 IP 限认证端点**：限登录/注册/刷新端点，挡撞库

二者均 **fail-open**：Redis 不可达时放行，绝不因基础设施抖动把用户挡在门外。

### 配额（总量防线，⏳ 强制未接入）

阈值已在 `config.py`（§五），但「回合开始前检查并拒绝」尚未接线。目标设计：每回合 prepare 时检查，三维度独立判定。

| 维度 | 窗口 |
|---|---|
| 日 token | 当日 0 点起 |
| 月成本（USD 内部口径） | 当月 1 号起 |
| 日请求数 | 当日 0 点起 |

关键决策：

- **0 = 该维度不限制**（fail-safe 宽松默认），全 0 则直接放行
- **回合粒度**：在回合开始前检查，超额拒绝下一个回合（不腰斩进行中回合）
- **每用户覆盖**：支持按用户存覆盖值，管理员可标记 `is_unlimited` 跳过所有检查
- **轻量到可放热路径**：一次检查 = 1 次 quota 表读 + 1 次成本事件聚合，命中既有索引（`ix_cost_events_user_created`，§四）

### 计费记账（✅ 已落地）

每个 **Run** 在 turn finalize 落一行 `cost_events`（决策② **per-run** 粒度：产品面只需 per-run，热路径更轻；per-call 审计交给结构化日志）。详见 §三/§四。

## 二、用量/成本不变量

token 与成本在系统中有多种形态（SSE wire、持久化、API 响应、计费台账），两条不变量保证不会算出两套数：

1. **唯一原始来源**：单次 LLM 调用的原始 `TokenUsage` **5 字段**（`input / output / reasoning / cache_hit / cache_miss`；`total` 为派生属性），所有用量从它累加。→ 见代码 `llm/protocol.py::TokenUsage`
2. **唯一定价转换**：全系统唯一的 `calculate_cost(model, usage)` 把 token 折成钱（`input / cached / output` 三价分离，缓存命中按 ~50× 更低价计），任何地方要成本一律调它，绝不另算单价。钱一律**整数 nano-USD**（1 USD = 10⁹），杜绝浮点。→ 见代码 `llm/pricing.py`

**真正的钱以 `cost_events` 台账为准**（不变量 #1）；`Message.usage` / `runs` 里的成本只是展示快照。新增任何成本展示点 → 复用统一定价函数，勿手算单价。

## 三、台账：per-run 成本事件（✅ 已落地）

| 项 | 决策 |
|---|---|
| 粒度（决策②） | **per-run**：一个 Agent 参与一行（captain 根 + 各委派 member 各一行），`rounds` 记该 run 内 LLM 调用次数 |
| 货币（决策①） | 存**整数 nano-USD**；`cost = {input, cached, output, total}` + 冗余 `cost_total_nano` 标量列（窗口 SUM 走整数、命中索引、不挖 JSONB）；CNY 仅展示层用单一汇率折算 |
| 幂等 | `run_id` unique，台账写是 upsert-by-run_id（`on_conflict_do_nothing`），重试不双记 |
| 写入时机 | turn finalize（captain 根 + 各 member 各落一行），与 assistant message 共享 `message_id`，故工资单按 `message_id` 查即对齐持久化消息 |
| 失败语义 | **只 warning 不中断**（文档铁律）：台账写失败回滚该笔、记日志、继续；回合的回复已先提交、不受影响。即便无 assistant 文本也落账（token 已花） |
| 真相源 | `cost_events`（不变量 #1）；`Message.usage` 仅展示快照 |

→ 见代码：`runtime/costing.py`（RunState → 台账行，唯一桥）+ `db/repositories.py::CostEventRepository` + 落账点 `conversation/service.py`

## 四、读侧聚合与接口（✅ 已落地）

**SSE（实时点亮）**：成本是**完成时事实**（usage 只在最后一个 chunk 到达），无流式成本增量 → 一律挂完成事件：`run_completed.{role, model, usage, cost}` 点亮工资单一行，`message_end.cost` 给回合总账。

**REST（回放 / 聚合）**：

| 端点 | 用途 | 数据源 |
|---|---|---|
| `GET /v1/messages/{id}/cost` | 团队工资单（per-Agent 明细 + 回合合计） | 按 `message_id` |
| `GET /v1/conversations/{id}/cost` | 对话累计 | 按 `conversation_id` |
| `GET /v1/usage/summary` | 账户仪表盘（今日/本月用量+成本、quota、汇率） | 按 `(user_id, created_at)` 窗口 |

- **聚合**：JSONB 的 token/cost 分量 cast 求和，回合总额走冗余 `cost_total_nano` 标量列；`turns` 数 distinct `message_id`（请求/回合代理）。命中两个复合索引 `ix_cost_events_user_created`（账户窗口）/ `ix_cost_events_message`（工资单）。
- **权限**：三个读都按 `user_id` 收敛（IDOR-safe）；message 端点对非所有者返回零值空名单、不泄露存在性。
- **类型**：Pydantic ↔ TS 一一对应（OpenAPI 生成）；钱以整数 nano-USD 流转，`cny_total` / `cny_per_usd` 由服务端用单一汇率折算下发，前端不写死汇率（合计仍以各 run 已定价之和为准，不重新定价）。

→ 见代码：`api/routes/usage.py` + `api/schemas.py`（`CostBreakdown` / `UsageBreakdown` / `AgentCostLine` / `TurnCost` / `ConversationCost` / `UsageSummary` 系列）

## 六、成本预估 ≠ 实际记账

团队组建时提供启发式预估，与真实记账是两套东西，刻意如此：

- 预估用途是**比较不同团队组合的贵贱**（「三个 premium 模型会很贵」），不是预测真实账单
- 算法基于固定假设（Captain 跑 3 轮、成员各 2 轮，每轮约 3000 输入 + 700 输出 token）
- 假设串始终展示给用户，确保该数字永远不被误当成事实
