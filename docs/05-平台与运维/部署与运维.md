>
> 自动部署集成点与约束：
> - **触发**：`master` 分支 push 且命中 `apps/website/**`（或手动 `workflow_dispatch`）。
> - **鉴权**：依赖 GitHub repo secret `CLOUDFLARE_API_TOKEN`（权限 `Cloudflare Pages → Edit`，应长期有效——过期会导致后续自动部署失败）；account ID 非敏感，直接写在 workflow。
> - **生产分支约束**（两个独立概念，勿混）：git 主干为 `master`，故 deploy-website 的 git 触发分支即 `master`；Cloudflare Pages 项目生产分支名为 `main`（Cloudflare 侧设置，与 git 分支无关），故 direct-upload 部署须显式传 `--branch=main` 钉为 Pages **生产**部署，自定义域才会跟随更新（落到其他分支名会成 preview 部署、域名不更新）。
> - **被否决：原生 Git OAuth 集成**——现有 Pages 项目是 direct-upload 类型，Cloudflare 不允许为其接 Git；改走 GitHub Actions + wrangler，避免重建项目并迁移已绑定的 apex 域名（有停机窗口）。

### CI/CD 流程

> **实现现状**：✅ 已接入（构建/部署双触发，对齐 §7.2「master=WIP、部署认 prod-* 发布点」）。
> `build-backend.yml`（push `master`）与 `deploy-backend.yml`（push `prod-*` tag）见 `.github/workflows/`。

```
push master ─→ build-backend.yml ─→ 构建 api 镜像(钉 GIT_SHA/BUILT_AT) ─→ 推 ACR(公网端点)
                                                         打 <short-sha> + latest 双标签
push prod-* tag ─→ deploy-backend.yml ─→ SSH ─→ deploy-server.sh <tag>
                                                  ↓
            fetch→解析 tag 为 SHA → 迁移前 pg_dump 快照 → alembic upgrade → compose up(拉 VPC 端点)
                                                  ↓
                            /readyz 健康检查 → 记录 .last-deployed-sha
```

**端点分流**：CI 推 ACR **公网**端点（GitHub 在 Aliyun VPC 外）、服务器拉 **VPC** 端点（同仓两路由）。`ACR_REGISTRY`(CI) 与 `IMAGE_REGISTRY`(服务器 production.env) 命名空间一致、仅 host 差 `-vpc`。

**所需 GitHub secrets**（源码仓 Settings → Secrets and variables → Actions）：

| secret | 用途 |
|---|---|
| `ACR_REGISTRY` | ACR **公网**端点 + 命名空间（如 `crpi-xxx.cn-shenzhen.personal.cr.aliyuncs.com/agentcore1`） |
| `ACR_USERNAME` / `ACR_PASSWORD` | ACR 推送凭据（build-backend 登录用） |
| `DEPLOY_SSH_HOST` / `DEPLOY_SSH_USER` / `DEPLOY_SSH_KEY` | 服务器 SSH 地址 / 用户 / 私钥（deploy-backend 用） |
| `DEPLOY_SSH_PORT` | SSH 端口（可选，默认 22） |

**服务器一次性前置**：`$AGENTCORE_HOME/repo` 已 clone、`$AGENTCORE_HOME/.env` 含 ACR 拉取凭据 + `IMAGE_REGISTRY`(VPC)、`deploy/config/production.env` 已填值（见 §8.2）。

**发布动作**：日常 `push master` 自动出镜像；要上线就在目标 SHA 打 `prod-*` tag 并 `git push --tags` → 自动部署。回退：对旧 `prod-*` tag 手动 `workflow_dispatch` 重跑（deploy-server.sh 自动识别回退、跳正向迁移）。

部署脚本：`/opt/agentcore/repo/deploy/scripts/deploy-server.sh`
- 支持正向部署和回退（传旧 SHA 即回退，镜像在 ACR 秒级切换）
- 迁移前自动做 DB 逻辑快照

## 七、发布策略 ✅ 已确定

> **实现现状**：以下为**目标发布/运维契约**；MVP 后端暴露 `GET /livez`（存活，恒 200）、`GET /readyz`（就绪，含 DB 探测，未就绪回 503）与 `GET /version`（version + git_sha + built_at）（→ 见代码 `apps/server/agentcore/api/routes/system.py`）。`/version` 端点已实装；启动入口（`python -m agentcore`，即 systemd ExecStart）在环境未注入时按 git 工作树补 `GIT_SHA`、按启动时刻补 `BUILT_AT`（→ 见代码 `apps/server/agentcore/buildinfo.py`），发布流水线经环境变量注入则优先。`deploy-server.sh` 已入仓且发布自动化已接入（`build-backend.yml`：push `master` → 构建推 ACR；`deploy-backend.yml`：push `prod-*` tag → SSH 跑 `deploy-server.sh`，见 §三）；`prod-*` 发布 tag 即部署触发器。漂移哨兵仍未接入。CI（`ci.yml`）测试触发分支为 `master`。

### 7.1 版本钉定

部署一律按 **git SHA**，不按浮动 `latest`。应用镜像构建期注入 `GIT_SHA` / `BUILT_AT`，运行时经 `GET /version` 暴露（端点已实装；启动入口在环境未注入时自 git 工作树补 SHA、按启动时刻补构建时间，发布流水线经环境变量注入则优先）。部署脚本传 `latest` 时，会先解析为当前 `master` 的具体 SHA 再 pin——容器跑的永远是确定 SHA（可追溯、可秒回）。

### 7.2 发布点（Release Point）

`master` 是 WIP 快照主干，**HEAD ≠ 可上线点**。用 `prod-*` tag 标记发布点（语义：「这个 SHA 是要上线的版本」）。部署以发布点为准，而非 `origin/master`——✅ `deploy-backend.yml` 即由 `prod-*` tag 触发 SSH 部署（漂移哨兵仍 ⏳）。

### 7.3 漂移检测

CI 每日自动比对线上 `/version` 与最新 `prod-*` tag（⏳ 目标；MVP 未接入）：

- prod 落后 tag → 「发了版没部署」（真漂移，告警）
- `master` 超前 tag → 「攒了未发布的 WIP」（正常，不告警）

桌面端同理：比对 `package.json` version 与公开发布仓的 `releases/latest` tag（⏳ 未接入）。

### 7.4 Deploy ≠ Release

构建/部署之上还有一层「部署 ≠ 发布」解耦——后端功能可先暗发到生产，由配置/特性开关翻开才对用户可见。支持灰度 + 最低客户端版本门控（让后端先于桌面发版，仅追上的客户端点亮）。

### 7.5 Monorepo 选择性构建

`push master` 构建改动的服务推 ACR，但**不自动部署**（✅ `build-backend.yml` 已落地：push `master` → 构建 api → 推 ACR；部署另由 `prod-*` tag 触发，§7.2）。未改动的服务用 retag（将 `latest` 秒级 retag 为本次 SHA）保证「每个 SHA 全套镜像」契约（⏳ 多服务 retag 优化；当前仅 api 单服务，每次 master 真实构建即满足契约）。api 例外，始终真实构建——其 `/version` 是版本可观测唯一出口，retag 会让内嵌 SHA 失真。

### 7.6 桌面端构建与双仓发布

> **实现现状**：`.github/workflows/release-desktop.yml` 已落地（`desktop-v*` tag → `windows-latest` 构建 → `electron-builder --win --publish always` 推发布仓**草稿** release，含 tag↔`package.json` version 一致性校验）；`electron-builder.yml` 的 `publish` 指向 `Lawofall/AgentCore-releases`。🔧 人工前置：建公开发布仓 + 源码仓配 `RELEASE_GH_TOKEN`（跨仓 PAT，默认 `GITHUB_TOKEN` 无跨仓写权）。macOS(DMG)/Linux(AppImage) 待补（现 Win 优先）。

安装包发到**公开**发布仓，源码仓保持**私有**——electron-updater 零 token 自动更新，不泄漏源码访问权。

**构建产物**：electron-builder 出 Windows(NSIS) / macOS(DMG) / Linux(AppImage)；MVP 不签名（自签证书，正式发布前申请代码签名证书）。自动更新机制（静默下载 / 检查频率 / 远程熔断 / 双通道）见 [`../04-前端/前端技术与架构.md` §7.6](../04-前端/前端技术与架构.md)。

| 环节 | 机制 |

| 构建触发 | 源码仓打 `desktop-v<ver>` tag |

### 7.7 备份与恢复策略

**只备不可重建的主数据**——PostgreSQL + MinIO。派生索引（Neo4j / ES）丢了可重建，Redis 是缓存丢了自愈。

| 原则 | 说明 |
|---|---|
| 迁移前快照 | 每次 `alembic upgrade` 前自动 `pg_dump`，失败即终止迁移 |
| 破坏性干净恢复 | 回灌前 `DROP SCHEMA public CASCADE`（非空库直接灌会主键冲突） |
| 停应用再恢复 | 避免并发写入；恢复后不自动起应用（需重新 deploy 对齐版本） |
| 异地副本 | 默认只有本地——防不了整机损坏，放量前必须开异地 |
| **灾备演练** | 备份未验证过恢复 = 没有备份。放量前必做一次完整恢复演练 |

### 7.9 特性开关架构

特性开关是 §7.4「Deploy ≠ Release」的落地机制——后端代码先暗发到生产，由配置翻开才对用户可见。

**服务端求值**：灰度/版本逻辑只在后端运行，客户端与后端代码路径都只读「已解析的布尔」。理由：求值逻辑不泄漏到端、各调用方判定一致、单一真相源。

**三道门顺序求值**：每个 flag 按以下顺序判定，任一道关闭即最终为 `false`：

| 门 | 含义 |
|---|---|
| `enabled` | 总开关（关 = 永远关） |
| `min_client_version` | 仅 ≥ 该版本的客户端可见（跨列车安全阀） |
| `rollout` | 灰度百分比（0–100），按稳定 key 分桶 |

**跨列车安全阀**：`min_client_version` 让需要新客户端支持的后端功能先进生产，仅追上版本的客户端点亮——将「后端先上、桌面后放量」的跨列车顺序约束变成开关里的硬门，而非靠人工记顺序。

**分桶策略**：优先用户 `user_id`（同一用户跨设备判定一致），未登录回落到设备 `client_id`（UUID 持久化）。同一 key 永远落同一桶（不抖动），按 flag 加盐避免不同 flag 命中同一批人。登录成功后需重拉开关以纠正分桶 key 切换。

**fail-safe vs fail-open 对偶**——刻意相反的失败行为：

| 机制 | 失败兜底 | 为什么 |
|---|---|---|
| 特性开关 | **fail-safe（默认关）** | 未发布的功能要保守，不能因后端抖动误开半成品 |
| 桌面自动更新 | **fail-open（默认开）** | 已发布的安全网络要保活，可远程熔断 |

**演进预留**：v1 配置驱动（翻转需重启），运行时即时翻转（Redis/DB override）为 v2 注入缝。

## 八、配置分层与种子数据 ✅ 已确定

### 8.1 启动依赖层级

| 层级 | 服务/配置 | 失败行为 |
|---|---|---|
| L0 硬依赖 | PostgreSQL, Redis | 启动失败 |
| L0 生产硬约束 | `JWT_SECRET_KEY`(非默认/非空)；`COOKIE_SAMESITE=none` ⇒ `COOKIE_SECURE=true`（桌面端 `app://` 跨站 cookie 前提） | `RuntimeError`（fail-closed，启动即拒） |
| L1 软依赖 | NATS, MinIO, 搜索引擎 | 警告后继续，相关功能降级 |
| L2 运行时 | LLM_API_KEY, Embedding | API 可运行，调用时失败或跳过 |

**设计原则**：关键安全配置走 fail-closed（缺失即拒绝启动），功能性配置走 fail-safe（降级但不崩溃）。

### 8.2 环境变量分层

两个 `.env` 文件明确分工：

| 文件 | 内容 | 消费方 |
|---|---|---|
| 根 `.env` | 镜像仓库凭据、镜像标签、依赖密码、内存调优 | compose `--env-file` + 部署脚本 |
| `config/.env` | 应用运行配置（JWT/LLM Key/CORS 等） | api 容器 `env_file` |

DB/Redis/NATS 等连接串在 `config/.env` 仅占位，由 compose 的 `environment` 覆盖为服务名。

### 8.3 种子数据与确定性 UUID

使用 **UUID v5** 确定性生成种子实体 ID：`uuid5(NAMESPACE, slug)` → 同一 slug 永远同一 ID → seed 脚本幂等安全。

| 实体 | slug 规则 | 示例 |
|---|---|---|
| Agent | `{filename_stem}` | `uuid5(NS, "workspace-assistant")` |
| Agent Version | `{slug}/v1` | `uuid5(NS, "workspace-assistant/v1")` |
| Team | `team/{slug}` | `uuid5(NS, "team/default-team")` |
| Tool | `tool/{name}` | `uuid5(NS, "tool/web-search")` |
| Skill | `skill/{name}` | `uuid5(NS, "skill/contract-review")` |
| Rule | `rule/{name}` | `uuid5(NS, "rule/chinese-first")` |

### 8.4 种子安全开关

| 开关 | 默认 | 理由 |
|---|---|---|
| `SEED_CLEANUP` | **关** | 破坏性。自动部署若带它，回退到旧 SHA 会跑旧种子集、连带删掉新 SHA 才加的实体——回退应只回退代码、不静默删数据 |
| `SEED_DEMO` | 跟随 dev/prod | 演示数据不应进生产；本地保留以便联调 |

## 九、工程门禁与结构治理 ✅ 已确定

> 用 CI 不变量替代人工纪律，防止多 Agent 并行开发下行为回归/类型债/结构腐化悄悄累积。

### 核心哲学：棘轮（Ratchet）

基线 = 当前现状，落地当天全绿，只拦新增腐化。修好真问题就收紧基线（只降不升），放宽必须在 PR diff 里显形并给理由。

### 三道门禁

| 层 | 拦什么 | 策略 |
|---|---|---|
| **行为回归** | 后端 lint + 测试，前端类型检查 | 合并前 CI 硬阻塞 |
| **类型债** | tsc strict / mypy strict | 棘轮：逐文件计数基线，不允许新增错误。棘轮终局 = 修到零 → 升为硬门禁 |
| **结构治理** | god-file 膨胀、模块漏文档 | 行数棘轮（超标存量登记天花板）+ 模块文档守卫 + 清单守卫 |

### 跨端契约门禁

> **实现现状**：⏳ 未接入 CI。当前 `.github/workflows/ci.yml` 仅后端 ruff + pytest、前端 lint + test，无 OpenAPI/SSE 类型生成与 `git diff --exit-code` 门禁。

后端改 schema / SSE 事件必须重新生成前端类型并提交，`git diff --exit-code` 拦截 generated 静默漂移（目标）。覆盖两条契约：

| 契约 | 真相源 | 生成产物 |
|---|---|---|
| REST | OpenAPI schema | `openapi.ts` |
| SSE | 后端 EventType + payload dataclass | `sse-events.ts` |

`task gen:types` 一次重生成两者。根除「后端发了新事件/字段、前端 union 或 interface 漏抄、功能静默装死」。

### 拆分实操经验

- **facade + 子包**：按子域拆，`__init__` 全量 re-export 保持公共 API 不变 → 调用方零改动
- **mixin vs 协作者类**：跨切面、读写宿主多字段的状态逻辑用 mixin——经 MRO 保留 `self._x()` 调用、零调用点改动
- **棘轮行数口径**：脚本内自产自校，CI 与基线自洽；勿用不同工具对账（口径不同）
- **陷阱**：移动挂着门禁的文件要同步硬编码路径，否则门禁静默失效
