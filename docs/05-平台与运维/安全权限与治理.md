## 三、工具审批（Human-in-the-Loop） ✅ 已确定

### 核心问题

旧模型（布尔开关 `approval_required`）只有「每次都问 / 从不问」两档。批量场景崩坏：一次团队委派产出 76 个本地文件 = 76 次审批弹窗。审批疲劳的终点是用户无脑点允许——门还在，防护已经没了。

### 三态策略

审批级别是**工具的固有属性**（声明在工具定义处），判据 = 可逆性 × 副作用范围：

| 级别 | 语义 | 判据 | 代表工具 |
|------|------|------|---------|
| `never` | 静默执行 | 只读 / 纯计算 / 可信沙箱 | 检索、计算器、数据库查询 |
| `grantable` | 首次审批，可「本轮内都允许」 | 有副作用但局部可控，典型为批量发生 | 写本地文件、执行代码、HTTP 请求 |
| `always` | 每次都审批，不提供放行 | 不可逆外部副作用 | 发送邮件、支付、删除外部数据 |

`always` 不提供放行是刻意的安全边界：「我允许写文件」不能被语境拉伸成「我允许发邮件」。

> **实现现状**：✅ CEO 聊天路径已落地——`engine._execute_tools` 对 `GRANTABLE` 工具（`file_write` / `str_replace` / `code_execute`，其余只读工具为 `NEVER`；声明见 `core/types.py`、`tools/builtin/`）经 `ApprovalGate.authorize()` 挂起，SSE `approval_required` 上报、resolve 端点回填决策（→ 见 `runtime/approvals.py`、`api/routes/conversations.py`）；「本轮内都允许」(`approve_always`) 与审批超时（默认 300s → 视为 `deny`）均已实现。委派子 Agent 暂不经门（gate 未线程化进 `runs/executor.py`）。

### 「本轮内都允许」的四条边界

| # | 边界 | 理由 |
|---|------|------|
| 1 | **turn 级**，非会话级/永久 | 每条用户消息是一个新的意图边界，上轮「整理文件」的授权不延伸到下轮「清理磁盘」 |
| 2 | **同名工具**，非全部工具 | 授权语义是「这类操作我信任」，不是「随便干」 |
| 3 | **整棵 DAG/委派树共享** | 子 Agent 也执行相同操作，只对主 Agent 生效则形同虚设 |
| 4 | **新轮清场 + TTL 兜底** | 下一条消息永远从干净状态开始 |

### 交互设计

- 审批卡按钮：**允许一次 · 本轮内都允许 · 拒绝**；`always` 级只渲染两按钮（无放行选项）
- 并行同名审批自动批量放行：5 张同名卡，点一张「本轮内都允许」其余立即批准
- 工具审批超时与拒绝回填 ✅ 已实现：超时（默认 300s）视为 `deny`，被拒调用向模型回注 `not authorized` 令其改道

### 被否决的方案

- **永久 allowlist**：消费级跨天对话里永久放行 = 失去感知
- **按 Agent 放行**：用户难以理解「放行的是谁」，DAG 对用户半透明
- **审批队列批量勾选**：UI 复杂，不解决后续调用还会弹的根本问题

### 演进路线

根答案是**可回滚性决定是否需要审批**。路线：本地写入前自动备份 → 一键还原 → 写文件从 `grantable` 降为 `never`（零审批、可撤销），审批只剩不可逆动作。三态模型为此预留平滑通道——只改工具声明级别，交互不动。

## 五、代码执行沙箱 ✅ 已确定

> AI 的「跑代码」工具（`code_execute`）的隔离边界设计。

> **MVP 采用受限 subprocess + SandboxProvider 抽象**（落地细节见本节 §5.2~5.7）。以下 gVisor / Docker Worker / NATS 方案为**目标架构（Post-MVP）**。

### 5.1 为何需要独立沙箱

API 容器内子进程不构成安全边界——三层根本问题：

1. **资源爆炸拖垮全站**：无内存/进程上限，与 API 共享容器内存。一段吃满内存的代码撑爆容器 → 全站对话中断
2. **直连内部数据库**：子进程与 API 共享网络，可达 PG/Redis/MinIO
3. **黑名单是错的安全模型**：2026 年前沿大模型能自动绕过普通容器+黑名单，共享内核不构成安全边界

### 5.2 方案选型（目标架构，Post-MVP）

| 方案 | 隔离强度 | 需特殊硬件 | 能读文件/上网 | 结论 |
|------|---------|-----------|-------------|------|
| 现状强化（子进程 + 限制） | 弱 | 否 | 能 | **MVP 采用** |
| **gVisor（用户态内核拦截）** | 中高 | 否 | 能 | Post-MVP 升级目标 |
| 独立小虚拟机（Firecracker） | 最高 | 是（/dev/kvm） | 能 | 换机器后升级 |
| WASM | 中高 | 否 | 不能 | 用途不匹配 |
| 托管沙箱（E2B 等） | 最高 | 否 | 能 | 数据出境 + 成本 |

**Post-MVP 选 gVisor 理由**：不挑硬件、强度足够，是「强度/运维/硬件」在当前服务器的最佳平衡。升级路径清晰——换带 KVM 的机器后可平滑切到小虚拟机方案。

### 5.3 可替换 Seam 架构

```python
class SandboxProvider(Protocol):
    async def run(self, code: str, limits: SandboxLimits) -> SandboxResult: ...
```

`code_execute` 只依赖 `SandboxProvider` 协议，背后实现由配置切换（`off`/`subprocess`/`gvisor`/`microvm`）。升级只需加一个后端实现 + 改配置，上层零改动。

### 5.4 默认关闭治理

> **实现现状**：`code_sandbox_backend` 开关为设计项、MVP **无此配置**；`tools.builtin.build_builtin_registry()` **始终注册** `CodeExecuteTool`（→ 见 `tools/builtin/__init__.py`）。

两个语义清晰的开关，关闭时对应工具不进入工具列表（零开销、零调用面）——**目标设计**：

| 开关 | 默认值 | 控制 |
|------|-------|------|
| `code_sandbox_backend` | `off`（设计项；MVP 无开关，`code_execute` 默认注册） | `code_execute` 及其执行后端 |
| `http_request_enabled` | `false` | `http_request`（同属高风险面） |

### 5.5 gVisor 执行模型（Post-MVP）

每次执行起一个**用完即弃**的容器，跑在 gVisor 运行时下——代码面对用户态内核，碰不到宿主机内核。

锁死项：默认禁止联网、只读根文件系统、内存=swap、CPU/pids 上限、非 root、丢弃所有 capability、禁止提权。

**独立 Worker 架构（Post-MVP）**：唯一能访问 Docker 的是独立 worker 容器；用户面 API 永不接触 Docker。代码执行经 NATS request 从 API 进程转发到 worker。

### 5.6 失败语义

所有后端遵守同一契约：**普通执行失败绝不抛异常**（docker 缺失/超时/非零退出），一律映射为 `SandboxResult`——绝不让一段坏代码打断 ReAct 循环。

### 5.7 资源限额（默认值）

| 限制 | 值 |
|------|---|
| 内存 | 256MB |
| CPU | 1.0 |
| pids | 128 |
| 网络 | 默认禁止 |
| 并发 | 2 |
| 超时 | 用户可配 |

## 七、凭据加密与密钥管理 ✅ 已确定

> **实现现状**：设计已定，代码未实现——`config.py` 无 `ENCRYPTION_KEY`，无加密模块。

用户敏感凭据（如自带 LLM API Key）加密入库，明文永不落库、永不返回前端。

### 加密方案

| 项 | 规格 |
|---|---|
| 算法 | AES-256-GCM |
| 密钥来源 | 环境变量 `ENCRYPTION_KEY`（64 hex = 32 字节），非法长度启动即报错 |
| Wire format | `nonce(12B) \|\| ciphertext+tag`，每次加密随机 nonce（同明文不同密文） |
| 回显 | 视图层解密后只取后 4 位，掩码为 `****xxxx` 返回 |

### 失败行为（fail-closed / fail-safe 二分）

加密主密钥缺失时的行为取决于凭据是否为必选：

| 场景 | 行为 | 理由 |
|---|---|---|
| 凭据为必选（如 REQUIRE_BYOK 开） | 生产启动 `SystemExit`（fail-closed） | 功能默认开、依赖却没配 = 全员不可用，拒绝带病启动 |
| 凭据为可选 | 静默不可用（fail-safe） | 平台兜底仍可工作，仅该功能消失 |

## 八、治理模块边界 ✅ 已确定

### 应用边界原则

「一受众一应用」：面向不同受众的系统（终端用户产品、管理后台、营销站）独立为单独应用，各自独立部署、隔离网络与主题，不混在同一路由组。

### 管理后台模块定位

管理后台是**平台通用能力**（非垂直行业插件），负责用户治理、内容审核、平台概览。

**聚合只读 + 委托域写**：管理模块只做跨域聚合读取 + 审计写入，所有领域写操作委托回域 service（如下架委托 `AgentService`），不在管理模块复制业务逻辑——避免退化为耦合全模块的 god-module。

例外规则：域 service 无对应写方法的治理专用字段（如 `role`/`status`），由管理模块端到端拥有；一旦域将该写操作正式暴露为 service 方法，立即改为委托。

### 审计日志

管理操作写入 **append-only 审计表**，确保所有治理行为（下架、角色变更、停用）可追溯。

### 内容审核策略

| 策略 | 描述 | 取舍 |
|---|---|---|
| **B（事后治理，首选）** | 保留创作者自助发布，管理侧抽查下架 | 零侵入发布链路、最快见效；代价是违规内容有窗口期 |
| A（前置过审，保留） | `draft→pending_review→published`，强制审批 | 零窗口期但侵入发布链路，违规压力上升时启用 |
