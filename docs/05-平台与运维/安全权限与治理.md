### 对话导出与公开分享（导出对话 / 分享对话）✅ 已落地

> 把对话「带出产品」的两条路径，安全要点全在「代码看不出来的取舍」上。→ 见代码 `api/routes/conversations/crud.py`（export）、`api/routes/sharing.py`、`conversation/export.py`、`conversation/sharing.py`、`db/models/conversations.py:ConversationShare`。

**导出（私有下载）**：所有者把整段对话存成 Markdown（仅问答正文，给人读/粘贴）或 JSON（全保真，可再导入）下载。读**整段**转录（非滚动窗口，避免漏）、owner-scoped（非属主 404，IDOR）；花费等台账字段不进导出（在成本台账，不在消息体）。下载文件名由服务端净化并带 RFC 5987 `filename*`（承载中文标题），经 CORS `expose_headers` 放行供前端读取。

**分享（公开只读链接）**——决策与约束：

| 决策 | 取舍 |
|---|---|
| **冻结快照**而非实时只读 | 链接 = 创建那刻的内容拷贝（`conversation_shares.snapshot`）；之后编辑 / 新回合都不影响已有链接（所见即所享），杜绝「未来内容意外泄露」，也免去公开面实时鉴权 |
| **仅问答正文**（user/assistant 文本） | 快照只取对话正文，**剔除** reasoning / 成本 / 工具内部数据 / 引用等敏感或冗余面——公开面最小化暴露 |
| **服务端渲染 HTML**（非前端构建） | 公开页 `GET /shared/{token}` 直出自包含 HTML，无需装应用即可看；Markdown 经 `markdown-it-py`（`html=False` + 拒危险链接 scheme）渲染——未受信正文当数据、绝不当可执行 HTML / 活链接，杜绝 XSS。页面带 `noindex` |
| **不泄露存在性** | 未知 / 已撤销 / 格式非法 token 一律返回极简 404 页（不 500，也不区分「不存在」与「已撤销」） |
| **可随时撤销** | 软撤销（`revoked_at`）：撤销后公开页立即 404；创建 / 列出 / 撤销管理端点均 owner-scoped |
| **级联撤销** | 删除对话、或注销账户（匿名化）时连带撤销其全部分享链接——数据卫生与隐私一致性（→ `ConversationShareRepository.revoke_all_for_*`，调用点见 `conversations/crud.py` 删除、`auth.py` 注销） |
| 过期策略 | ✅ 新建默认 **30 天** TTL（`expires_in_days` 可选 7/30/`null` 永不过期）；到期公开页 404。仍可显式撤销 + 级联 |

> 这是统一 `share` 插件（[`后端架构.md` §二·平台业务](/docs/02-架构/后端架构.md)：文件 + 对话 + `share_token` + 过期）的**首个落地切片**，现以对话专用实现内建于 conversation 模块；统一插件仍 ⏳。

## 三、工具审批（Human-in-the-Loop） ✅ 已确定

### 核心问题

旧模型（布尔开关 `approval_required`）只有「每次都问 / 从不问」两档。批量场景崩坏：一次团队委派产出 76 个本地文件 = 76 次审批弹窗。审批疲劳的终点是用户无脑点允许——门还在，防护已经没了。

### 三态策略

审批级别是**工具的固有属性**（声明在工具定义处），判据 = 可逆性 × 副作用范围：

| 级别 | 语义 | 判据 | 代表工具 |
|------|------|------|---------|
| `never` | 静默执行 | 只读 / 纯计算 / 可信沙箱 | 检索、计算器、数据库查询 |
| `grantable` | 首次审批，可「本轮内都允许」 | 有副作用但局部可控，典型为批量发生 | 写本地文件、执行代码、HTTP 请求 |
| `always` | 每次都审批，不提供放行 | 不可逆外部副作用 | 发送邮件、支付、删除外部数据 |

`always` 不提供放行是刻意的安全边界：「我允许写文件」不能被语境拉伸成「我允许发邮件」。

> **实现现状**：✅ CEO 聊天路径已落地——`ApprovalGate.authorize()` 对 `GRANTABLE` 工具挂起，SSE `approval_required` + resolve 端点回填；「本轮内都允许」与超时（默认 300s → `deny`）均已实现。委派 worker 本地模式经同款门。

→ 见代码 `runtime/approvals.py`、`api/routes/conversations/`、`tools/builtin.file_mutation_tool_names`（文件改动类口径）

### 「本轮内都允许」的四条边界

| # | 边界 | 理由 |
|---|------|------|
| 1 | **turn 级**，非会话级/永久 | 每条用户消息是一个新的意图边界，上轮「整理文件」的授权不延伸到下轮「清理磁盘」 |
| 2 | **按「类操作」放行**，非全部工具 | 授权语义是「这类操作我信任」、不是「随便干」：默认粒度是【同名工具】；文件改动另给一档【文件改动类】（`file_write`/`str_replace`/`file_delete`/`file_move` 一并放行，口径 = GRANTABLE ∩ FILESYSTEM），而更高危的 `code_execute`（执行类、真机副作用）始终单独把关、不被任何文件档覆盖 |
| 3 | **整棵 DAG/委派树共享** | 子 Agent 也执行相同操作，只对主 Agent 生效则形同虚设 |
| 4 | **新轮清场 + TTL 兜底** | 下一条消息永远从干净状态开始 |

### 交互设计

- 审批卡按钮：**允许一次 · 本轮内都允许 · 拒绝**；文件改动类工具（写/改/删/移）多一档 **本轮内允许所有文件改动**（一次覆盖整类，`code_execute` 不含在内、仍单独审批）；`always` 级只渲染两按钮（无放行选项）
- 并行审批自动批量放行：多张待批卡，点一张放行、其余【同 scope】立即放行——「本轮内都允许」扫同名工具，「本轮内允许所有文件改动」扫整个文件改动类。**权威实现在后端门**：`ApprovalGate` 在放行落定时按 `list_pending` 回溯放行该 scope 所有【已挂起】审批（`_sweep_pending_tools`），关掉「兄弟卡 `approval_required` 还在 SSE 途中、点击时尚未进前端 store」的竞态；前端 `decideApproval` 的乐观兄弟放行只作即时反馈，与后端幂等共存（重复 resolve 对已结项是 no-op）。
- 工具审批超时与拒绝回填 ✅ 已实现：超时（默认 300s）视为 `deny`，被拒调用向模型回注 `not authorized` 令其改道

### 被否决的方案

- **永久 allowlist**：消费级跨天对话里永久放行 = 失去感知
- **按 Agent 放行**：用户难以理解「放行的是谁」，DAG 对用户半透明
- **审批队列批量勾选**：UI 复杂，不解决后续调用还会弹的根本问题

### 演进路线

根答案是**可回滚性决定是否需要审批**。路线：本地写入前自动备份 → 一键还原 → 写文件从 `grantable` 降为 `never`（零审批、可撤销），审批只剩不可逆动作。三态模型为此预留平滑通道——只改工具声明级别，交互不动。

## 五、代码执行沙箱 ✅ 已确定

> AI 的「跑代码」工具（`code_execute`）的隔离边界设计。

> **MVP**：受限 subprocess + `SandboxProvider` 抽象。Post-MVP gVisor / Docker Worker / NATS 细节 → 见 [`07-规划/远期规划.md` §2.1](/docs/07-规划/远期规划.md)。

### 5.1 为何需要独立沙箱

API 容器内子进程不构成安全边界——资源爆炸拖垮全站、子进程可达内部 DB、黑名单模型不可靠。

### 5.4 默认关闭治理

> **实现现状 ✅**：云端 `location=server` 工作区默认**不注册** `code_execute`（`CODE_EXECUTE_CLOUD_ENABLED=false`）；本地 / sidecar（`location=local`）保留 + 审批门。独立沙箱 worker ⏳ 远期。

**目标设计 ⏳（未落地）**：`code_sandbox_backend`（默认 `off`）与 `http_request_enabled`（默认 `false`）——关闭时工具不进入工具列表。

### 5.x SandboxProvider Seam

→ 见 [`核心接口定义.md` §三](/docs/02-架构/核心接口定义.md)（`SandboxProvider` 协议、`code_execute` 只依赖协议、失败语义映射为 `ExecutionResult` 不抛异常打断 ReAct 循环）。

## 七、凭据加密与密钥管理 ✅ 已确定

> **实现现状**：✅ 已落地。加密模块 `security.KeyEncryptor`（AES-256-GCM）；写入面 `llm/key_service.py`，读取面 `llm/byok.py`（fail-safe，永不抛）。

用户敏感凭据加密入库，明文永不落库、永不返回前端。算法细节（wire format、回显掩码）与 BYOK 管理面交叉引用 [`成本配额与计费.md` §〇·五](/docs/05-平台与运维/成本配额与计费.md)。

### 失败行为（fail-closed / fail-safe 二分）

| 场景 | 行为 | 理由 |
|---|---|---|
| 凭据为必选（`billing_mode=byok`） | 生产启动即抛 `RuntimeError`（fail-closed）✅ | 拒绝带病启动 |
| 凭据为可选（`billing_mode=platform`） | 静默不可用（fail-safe）✅ | 平台兜底仍可工作 |

## 八、治理模块边界 ✅ 已确定

### 应用边界原则

「一受众一应用」：面向不同受众的系统（终端用户产品、管理后台、营销站）独立为单独应用，各自独立部署、隔离网络与主题，不混在同一路由组。

### 管理后台模块定位

→ 详见 [`管理员后台.md`](/docs/05-平台与运维/管理员后台.md)（独立 `apps/admin`、P0 契约、鉴权姿态）。

例外规则：域 service 无对应写方法的治理专用字段（如 `role`/`status`），由管理模块端到端拥有；一旦域将该写操作正式暴露为 service 方法，立即改为委托。

### 审计日志

管理操作写入 **append-only 审计表**，确保所有治理行为（下架、角色变更、停用）可追溯。

### 内容审核策略

| 策略 | 描述 | 取舍 |
|---|---|---|
| **B（事后治理，首选）** | 保留创作者自助发布，管理侧抽查下架 | 零侵入发布链路、最快见效；代价是违规内容有窗口期 |
| A（前置过审，保留） | `draft→pending_review→published`，强制审批 | 零窗口期但侵入发布链路，违规压力上升时启用 |
