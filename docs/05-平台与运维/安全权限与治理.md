## 三、工具审批（Human-in-the-Loop） ✅ 已确定

### 核心问题

旧模型（布尔开关 `approval_required`）只有「每次都问 / 从不问」两档。批量场景崩坏：一次团队委派产出 76 个本地文件 = 76 次审批弹窗。审批疲劳的终点是用户无脑点允许——门还在，防护已经没了。

### 三态策略

审批级别是**工具的固有属性**（声明在工具定义处），判据 = 可逆性 × 副作用范围：

| 级别 | 语义 | 判据 | 代表工具 |
|------|------|------|---------|
| `never` | 静默执行 | 只读 / 纯计算 / 可信沙箱 | 检索、计算器、数据库查询 |
| `grantable` | 首次审批，可「本轮内都允许」 | 有副作用但局部可控，典型为批量发生 | 写本地文件、执行代码、HTTP 请求 |
| `always` | 每次都审批，不提供放行 | 不可逆外部副作用 | 发送邮件、支付、删除外部数据 |

`always` 不提供放行是刻意的安全边界：「我允许写文件」不能被语境拉伸成「我允许发邮件」。

> **实现现状**：✅ CEO 聊天路径已落地——`ApprovalGate.authorize()` 对 `GRANTABLE` 工具挂起，SSE `approval_required` + resolve 端点回填；「本轮内都允许」与超时（默认 300s → `deny`）均已实现。委派 worker 本地模式经同款门。

→ 见代码 `runtime/approvals.py`、`api/routes/conversations.py`、`tools/builtin.file_mutation_tool_names`（文件改动类口径）

### 「本轮内都允许」的四条边界

| # | 边界 | 理由 |
|---|------|------|
| 1 | **turn 级**，非会话级/永久 | 每条用户消息是一个新的意图边界，上轮「整理文件」的授权不延伸到下轮「清理磁盘」 |
| 2 | **按「类操作」放行**，非全部工具 | 授权语义是「这类操作我信任」、不是「随便干」：默认粒度是【同名工具】；文件改动另给一档【文件改动类】（`file_write`/`str_replace`/`file_delete`/`file_move` 一并放行，口径 = GRANTABLE ∩ FILESYSTEM），而更高危的 `code_execute`（执行类、真机副作用）始终单独把关、不被任何文件档覆盖 |
| 3 | **整棵 DAG/委派树共享** | 子 Agent 也执行相同操作，只对主 Agent 生效则形同虚设 |
| 4 | **新轮清场 + TTL 兜底** | 下一条消息永远从干净状态开始 |

### 交互设计

- 审批卡按钮：**允许一次 · 本轮内都允许 · 拒绝**；文件改动类工具（写/改/删/移）多一档 **本轮内允许所有文件改动**（一次覆盖整类，`code_execute` 不含在内、仍单独审批）；`always` 级只渲染两按钮（无放行选项）
- 并行审批自动批量放行：多张待批卡，点一张放行、其余【同 scope】立即放行——「本轮内都允许」扫同名工具，「本轮内允许所有文件改动」扫整个文件改动类。**权威实现在后端门**：`ApprovalGate` 在放行落定时按 `list_pending` 回溯放行该 scope 所有【已挂起】审批（`_sweep_pending_tools`），关掉「兄弟卡 `approval_required` 还在 SSE 途中、点击时尚未进前端 store」的竞态；前端 `decideApproval` 的乐观兄弟放行只作即时反馈，与后端幂等共存（重复 resolve 对已结项是 no-op）。
- 工具审批超时与拒绝回填 ✅ 已实现：超时（默认 300s）视为 `deny`，被拒调用向模型回注 `not authorized` 令其改道

### 被否决的方案

- **永久 allowlist**：消费级跨天对话里永久放行 = 失去感知
- **按 Agent 放行**：用户难以理解「放行的是谁」，DAG 对用户半透明
- **审批队列批量勾选**：UI 复杂，不解决后续调用还会弹的根本问题

### 演进路线

根答案是**可回滚性决定是否需要审批**。路线：本地写入前自动备份 → 一键还原 → 写文件从 `grantable` 降为 `never`（零审批、可撤销），审批只剩不可逆动作。三态模型为此预留平滑通道——只改工具声明级别，交互不动。

## 五、代码执行沙箱 ✅ 已确定

> AI 的「跑代码」工具（`code_execute`）的隔离边界设计。

> **MVP**：受限 subprocess + `SandboxProvider` 抽象。Post-MVP gVisor / Docker Worker / NATS 细节 → 见 [`07-规划/远期规划.md` §2.1](/docs/07-规划/远期规划.md)。

### 5.1 为何需要独立沙箱

API 容器内子进程不构成安全边界——资源爆炸拖垮全站、子进程可达内部 DB、黑名单模型不可靠。

### 5.4 默认关闭治理

> **实现现状**：MVP **无** `code_sandbox_backend` 开关；`code_execute` 默认注册（→ 见 `tools/builtin/__init__.py`）。

**目标设计**：`code_sandbox_backend`（默认 `off`）与 `http_request_enabled`（默认 `false`）——关闭时工具不进入工具列表。

### 5.x SandboxProvider Seam

```python
class SandboxProvider(Protocol):
    async def run(self, code: str, limits: SandboxLimits) -> SandboxResult: ...
```

`code_execute` 只依赖协议，背后实现由配置切换（`off`/`subprocess`/`gvisor`/`microvm`）。**失败语义**：普通执行失败映射为 `SandboxResult`，不抛异常打断 ReAct 循环。

## 八、治理模块边界 ✅ 已确定

### 应用边界原则

「一受众一应用」：面向不同受众的系统（终端用户产品、管理后台、营销站）独立为单独应用，各自独立部署、隔离网络与主题，不混在同一路由组。

### 管理后台模块定位

管理后台是**平台通用能力**（非垂直行业插件），负责用户治理、内容审核、平台概览。

**聚合只读 + 委托域写**：管理模块只做跨域聚合读取 + 审计写入，所有领域写操作委托回域 service（如下架委托 `AgentService`），不在管理模块复制业务逻辑——避免退化为耦合全模块的 god-module。

例外规则：域 service 无对应写方法的治理专用字段（如 `role`/`status`），由管理模块端到端拥有；一旦域将该写操作正式暴露为 service 方法，立即改为委托。

### 审计日志

管理操作写入 **append-only 审计表**，确保所有治理行为（下架、角色变更、停用）可追溯。

### 内容审核策略

| 策略 | 描述 | 取舍 |
|---|---|---|
| **B（事后治理，首选）** | 保留创作者自助发布，管理侧抽查下架 | 零侵入发布链路、最快见效；代价是违规内容有窗口期 |
| A（前置过审，保留） | `draft→pending_review→published`，强制审批 | 零窗口期但侵入发布链路，违规压力上升时启用 |
