## 二、状态管理策略

### 统一 Zustand

所有客户端状态统一使用 Zustand 管理。通过正确的 selector 模式实现精确订阅。

| Store | 管理什么 |
|-------|----------|
| `useSessionStore` | 当前会话、会话列表 |
| `useAgentsStore` | 所有 Agent 的运行状态、进度、输出 |
| `useSettingsStore` | 用户设置、UI 偏好 |

服务端数据（会话历史、模板列表等）通过 TanStack Query 管理。

### 强制规则

> 所有从 store 读取状态的组件必须使用精确 selector，禁止 `useXxxStore()` 不带参数直接获取整个 store。

### Agent 状态 Store 示例

```typescript
// stores/agents.ts
import { create } from 'zustand'

interface AgentState {
  status: 'idle' | 'working' | 'completed' | 'error'
  progress: number
  output: string[]
  role: string
  task: string
  model: string
}

interface AgentsStore {
  agents: Record<string, AgentState>
  activeIds: string[]
  setAgentStatus: (id: string, status: AgentState['status']) => void
  setAgentProgress: (id: string, progress: number) => void
  appendOutput: (id: string, chunk: string) => void
  initAgents: (plan: TaskPlan) => void
  reset: () => void
}

export const useAgentsStore = create<AgentsStore>((set) => ({
  agents: {},
  activeIds: [],
  setAgentStatus: (id, status) =>
    set((s) => ({ agents: { ...s.agents, [id]: { ...s.agents[id], status } } })),
  setAgentProgress: (id, progress) =>
    set((s) => ({ agents: { ...s.agents, [id]: { ...s.agents[id], progress } } })),
  appendOutput: (id, chunk) =>
    set((s) => ({
      agents: { ...s.agents, [id]: { ...s.agents[id], output: [...s.agents[id].output, chunk] } }
    })),
  initAgents: (plan) => { /* 根据编排器返回的计划初始化 */ },
  reset: () => set({ agents: {}, activeIds: [] }),
}))
```

```typescript
// 组件中精确订阅
function AgentCard({ agentId }: { agentId: string }) {
  const agent = useAgentsStore((s) => s.agents[agentId])
  return <div>...</div>
}

function OverallProgress() {
  const progress = useAgentsStore((s) => {
    const ids = s.activeIds
    if (ids.length === 0) return 0
    return ids.reduce((sum, id) => sum + s.agents[id].progress, 0) / ids.length
  })
  return <ProgressBar value={progress} />
}
```

## 三、流式输出性能优化

### 问题

每个 Agent 的 LLM 流式输出约 30 token/s，4 Agent 并行 = 120 次状态更新/s。
性能瓶颈不在状态管理库，而在 DOM 渲染。

### 优化策略

| 优化 | 解决什么 | 实现 |
|------|----------|------|
| Token 批量更新 | 减少 state 更新频率 | requestAnimationFrame 批量刷新 |
| 虚拟滚动 | 长输出不卡 | 只渲染可见区域 DOM 节点 |
| 进度条用 CSS | 60fps 动画 | `transition` 而非逐帧重渲染 |
| 主面板单焦点 | 只渲染当前 Agent 输出 | 其他 Agent 存 store 不渲染 |

```typescript
// 关键优化：token 批量更新
class OutputBuffer {
  private buffer: string[] = []
  private timer: number | null = null

  push(token: string) {
    this.buffer.push(token)
    if (!this.timer) {
      this.timer = requestAnimationFrame(() => {
        const batch = this.buffer.join('')
        this.buffer = []
        this.timer = null
        useAgentsStore.getState().appendOutput(this.agentId, batch)
      })
    }
  }
}
```

### 性能边界

| Agent 数 | 状态更新频率 | 是否有问题 |
|---------|------------|-----------|
| 1-4 | ~120/s | 无问题 |
| 5-10 | ~300/s | 无问题（正确用 selector） |
| 10-20 | ~600/s | 需要节流 |
| 20+ | 不现实的场景 | - |

## 四、IPC 通信方案

### 核心原则

- 所有 IPC 通道和消息类型定义在 `shared/ipc-contract.ts`
- preload 和 renderer 引用同一套类型
- 编译期发现类型错误

### 消息类型

```typescript
// shared/ipc-contract.ts

// Renderer → Main（请求/响应模式）
export interface IpcInvokeContract {
  'session:create': { payload: { prompt: string }; response: { sessionId: string } }
  'session:cancel': { payload: { sessionId: string }; response: void }
  'session:list': { payload: void; response: SessionSummary[] }
}

// Main → Renderer（事件推送模式）
export interface IpcEventContract {
  'agent:status': { data: { agentId: string; status: AgentStatus; progress: number } }
  'agent:output': { data: { agentId: string; chunk: string; isStreaming: boolean } }
  'task:plan': { data: { sessionId: string; plan: TaskPlan } }
  'task:checkpoint': { data: { sessionId: string; checkpoint: CheckpointInfo } }
  'task:completed': { data: { sessionId: string; result: TaskResult } }
  'task:error': { data: { sessionId: string; error: ErrorInfo } }
}
```

### Preload 封装

```typescript
// electron/preload.ts
const api = {
  invoke: <K extends keyof IpcInvokeContract>(
    channel: K,
    payload: IpcInvokeContract[K]['payload']
  ): Promise<IpcInvokeContract[K]['response']> =>
    ipcRenderer.invoke(channel, payload),

  on: <K extends keyof IpcEventContract>(
    channel: K,
    callback: (data: IpcEventContract[K]['data']) => void
  ) => {
    const handler = (_: unknown, data: IpcEventContract[K]['data']) => callback(data)
    ipcRenderer.on(channel, handler)
    return () => ipcRenderer.removeListener(channel, handler)
  }
}

contextBridge.exposeInMainWorld('electronAPI', api)
```

## 五、窗口布局设计 ✅ 已确定

> 参考 `C:\Project\1` 的 IDE 式布局架构。核心原则：**全局侧栏 + 页面级自定义布局**，不再使用全局三栏固定结构。

### 全局骨架（AppShell）

```
┌─────────────────────────────────────────────────────────────┐
│  flex h-screen w-screen overflow-hidden                     │
├──────────────┬──────────────────────────────────────────────┤
│  <aside>     │  <div flex-1 flex-col>                       │
│  全局侧栏     │  ┌────────────────────────────────────────┐ │
│  w-60/w-14   │  │ 顶栏 h-10 (拖拽区 + WindowControls)    │ │
│              │  ├────────────────────────────────────────┤ │
│  品牌/折叠    │  │  <main flex-1 min-h-0>                 │ │
│  搜索        │  │    <Outlet /> → 页面级布局              │ │
│  主导航      │  │                                        │ │

└──────────────┴──────────────────────────────────────────────┘
```

AppShell 只负责：全局侧栏 + 顶部标题栏 + `<Outlet />`。所有页面内容由路由对应的页面组件自行决定内部布局（单栏、双栏、三栏等）。

| 维度 | 方案 |

| 状态管理 | Zustand `useSidebarStore`（collapsed、expandedSections） |
| 折叠方式 | 手动切换按钮，非响应式自动折叠 |

| 会话列表 | 对话历史列表（flex-1 可滚动） |
| 底栏 | 用户头像 + 设置入口 |

**主导航项：**

| 导航项 | 路由 | 图标 | 说明 |
|--------|------|------|------|

#### 面板物理参数

| 配置 | 值 |
|------|-----|
| 最小宽度 | 280px |
| 最大宽度 | 560px |
| 默认宽度 | 400px |
| 持久化 | localStorage (`agentcore:detail-panel-width`、`agentcore:detail-panel-open`) |
| 开关 | 可完全关闭（简单任务时隐藏，体验同 ChatGPT） |
| 拖拽实现 | 手写 pointer 事件（`onPointerDown` + `pointermove`，不引入第三方库） |
| 状态管理 | Zustand `useDetailPanelStore`（open、width、tabs、activeTabId） |

#### 动态 Tab 模式

**不使用固定 Tab 栏**，而是用户点击不同元素时动态打开新 Tab：

| 配置 | 值 |
|------|-----|
| 最大 Tab 数 | 6（超出时挤掉最旧 Tab） |
| Tab 可关闭 | 是（多 Tab 时每个 Tab 显示 × 按钮） |
| Tab 全关闭 | 面板自动隐藏 |
| Tab ID 生成 | 由 TabView 类型 + 关键 ID 组合（去重） |

#### Tab 类型定义

```typescript
export type TabView =
  | { type: 'task-progress'; messageId: string }
  | { type: 'reasoning'; messageId: string; title: string }
  | { type: 'run-detail'; runId: string; messageId: string; title: string }
  | { type: 'task-graph'; messageId: string }
  | { type: 'conversation-artifacts'; conversationId: string };
```

#### 各 Tab 内容

| Tab 类型 | 触发方式 | 内容 |
|----------|---------|------|
| `task-progress` | 点击任务卡片进度区域 / 消息上的进度入口 | 总进度条 + 所有 Agent 状态列表（点击 Agent 下钻） |
| `run-detail` | 点击 task-progress 中的 Agent 行 / 任务卡片 [展开] | 单个 Agent/run 完整详情：任务、思考、输出、工具调用、子任务、资源消耗 |
| `task-graph` | 任务卡片 [图] 按钮 / 多 Agent 任务自动打开 | React Flow 缩略 DAG 图 + [最大化] 进入全屏图视图 |
| `reasoning` | 点击消息气泡的「思考」入口 | LLM reasoning 内容（流式 Markdown） |
| `conversation-artifacts` | 点击对话级产物入口 | 本对话所有产物聚合视图 |

#### run-detail 内部区段结构

| 区段 | 默认状态 | 内容 |
|------|---------|------|
| 头部 | 始终显示 | Agent 头像 + 角色名 + 状态 + 实时计时 |
| 任务 | 展开 | 编排器分配的任务描述 |
| 错误 | 展开（仅失败时） | 错误信息红色高亮 |
| 思考过程 | 折叠 | LLM reasoning（可展开查看） |
| 输出 | 展开 | 实时流式内容 / 最终输出（Markdown） |
| 工具调用 | 展开 | 工具调用列表 + 各调用详情 |
| 子任务 | 展开 | 子 run 列表（点击打开新 run-detail Tab） |
| 资源消耗 | 折叠 | 模型 / token 数 / 费用 / 耗时 |

#### 数据源策略

```
实时执行态（runs store byMessage[messageId]）
        ↓ 优先
消息快照（message.runs，flattenRuns 拍平后按 runId 查找）
```

- 统一 run 概念：编排步骤和委派子 Agent 都是 run，详情走同一套组件
- 实时态流式更新 → 面板自动跟随
- `message_end` 时快照存入 message.runs 持久化供回放，释放实时槽

#### 面板自动打开规则

| 场景 | 行为 |
|------|------|
| 多 Agent 任务启动 | 自动打开面板，激活 task-progress Tab |
| 单 Agent 任务 | 不自动打开（保持 ChatGPT 体验） |
| 用户手动关闭 | 记住偏好，下次不自动打开（直到用户再次手动打开） |
| 面板已开 + 新任务 | 在已有 Tab 旁新增 Tab |

### 页面宽度规范

主内容区使用 `PageContainer` 组件统一约束宽度：

| 梯度 | 类名 | 最大宽度 | 适用场景 |
|------|------|----------|----------|
| content | `max-w-4xl mx-auto` | 896px | 对话、设置、表单 |
| canvas | `max-w-[1200px] mx-auto` | 1200px | 探索、列表、网格 |

统一内边距：`px-6 py-8`。

### 设计原则

| 原则 | 说明 |
|------|------|
| 全局只管壳 | AppShell 不预设右面板，页面自行决定布局 |
| 对话页突出差异 | 仅对话页有 DetailPanel，展示 Agent 协作信息 |
| 简单任务零噪音 | 单 Agent 时关闭右面板，体验同 ChatGPT |
| 桌面优先 | 不做移动端适配，少量 breakpoint 用于窗口极窄场景 |
| 页面自治 | 各页面/插件自定义内部布局，互不干扰 |

## 七、桌面端架构 ✅ 已确定

> 桌面端是唯一产品客户端（无独立 Web 端）。定位：**常驻本地、会协作的 AI 团队**——后台干活、碰本地文件、需要时敲你一下。

### 7.1 桌面价值主张（vs Web/PWA）

| 能力 | 网页天花板 | 桌面解锁 |
|------|-----------|---------|
| 异步任务 + 审批门禁 | 关标签即断 | 后台常驻 + 原生通知 + 审批闭环 |
| 全局热键召唤 | 埋在标签页里 | Spotlight 式悬浮窗 |
| 文件工作区 | 只能上传 | 本地文件直连 / Agent 读写磁盘 |
| MCP 工具层 | 浏览器跑不了 stdio | 本地 MCP 运行时（常驻进程池） |

被否决：PWA（无常驻/通知/文件）、全原生 UI（贵且漂移）、Tauri（团队无 Rust，WKWebView 有差异，备选）。

### 7.2 主进程架构

```
主进程 (Node.js)
├─ connection-manager  ← 独立 attention 轮询 + 通知（不依赖窗口存活）
├─ mcp-pool            ← MCP server 常驻进程池（crash 退避重启）
├─ fs-service          ← 本地文件 IPC 服务
└─ local-store         ← sql.js，对话/消息读缓存
renderer (Vite + React Router，本地)
└─ 桌面业务组件 + IPC ↔ 主进程；SSE 直连后端
         │ API (HTTPS)
         ▼
云端 api-server（LLM 推理 · Agent 运行时 · 数据持久化）
```

| 决策 | 结论 | 理由 |
|------|------|------|
| renderer 加载 | 本地（prod 走 custom protocol `app://`） | 给本地 renderer 正式 origin，CORS/CSP/cookie 可控 |
| SSE 连接 | renderer 直连后端（非 IPC 转发） | 长连接高吞吐，IPC 序列化开销不可接受 |
| 本地数据层 | sql.js（读缓存优先，非离线写） | 零 native 依赖、免 electron-rebuild；先验证读缓存价值 |
| 组件策略 | 桌面端独立演进（非共享 packages 业务组件） | 桌面优先 = 自由演进 > 两端一致 |

### 7.3 安全基线

- `contextIsolation: true` + `sandbox: true` + renderer 关 `nodeIntegration`
- 原生能力只经 preload 白名单 IPC 暴露
- httpOnly cookie 持久 session（Chromium OS DPAPI/Keychain 加密），不额外上 safeStorage

### 7.4 OS 深度集成

- **资源管理器右键菜单**：安装期注册 shell verb，`--analyze <path>` 唤起，授权目录后 Agent 可读
- **文件关联双击**：electron-builder `fileAssociations`，`.md/.txt/.json/.csv/.yaml` 等
- **全局热键**：Spotlight 式召唤悬浮窗
- **Taskbar/Dock badge**：未读通知计数
- **深链**：`openDeepLink(target)` 统一入口，本地 renderer 已加载走 React Router，否则 `loadURL`

### 7.5 通知双通路

| 通路 | 覆盖场景 | 机制 |
|------|---------|------|
| 方向 A：SSE 桥接 | 桌面正持有 SSE 流 | `approval_required` / `ask_user` / `message_end` 等事件桥接到原生通知 |
| 方向 B：Attention 轮询 | 未持有 SSE 流的盲区 | `GET /v1/attention`（45s 间隔），补 durable paused turns + pending approvals |

A+B 共用去重集（稳定 id），避免同一待办双弹。

### 7.6 自动更新

- 静默下载 + 用户决定安装时机
- 检查频率：启动 + 每 4h + `powerMonitor 'resume'`
- 远程熔断：后端 `updates_enabled = false` 才暂停（fail-open）
- 双通道：beta / stable；灰度分桶 `stagingPercentage`
- 平台：Windows + macOS（Win 优先），Linux 附带

### 7.7 关窗 = 隐藏到托盘

attention 轮询 + SSE 挂在渲染进程，`close` 默认 `preventDefault + hide`（仅 `before-quit` 放行销毁）。可配置：托盘开关「关闭时最小化到托盘」。

## 八、本地文件系统设计 ✅ 已确定

> 把本机磁盘文件提升为 **Agent 可直接读写的一等对象**。核心原则：**本地 = 唯一真身，云端不持久化文件字节**。

### 8.1 隐私边界

| 边界 | 含义 | 策略 |
|------|------|------|
| **at-rest** | 不把文件字节/正文存进服务端 | 默认守住；用户显式「备份/分享」为知情例外 |
| **in-transit** | Agent 读文件时正文临时发给 LLM | 接受（同 Cursor 把代码发给模型） |

铁律：Agent 要理解文件 → 正文必须进 prompt；at-rest 默认不外发。

### 8.2 Client-Tool 桥架构

云端运行时 + 本地文件桥（与 Cursor / Claude Desktop 同构）：

```
云端 executor 命中 client-bound 工具（文件读写）
  → emit SSE client_tool_requested{op, params}
  → Redis BLPOP 阻塞（keyed by conv_id + tool_call_id）
[SSE] → Electron 渲染层 → IPC → 主进程 fs-service 在授权根内执行
  → POST /v1/conversations/{id}/client-tool-result 回传
  → resolve → 续跑 ReAct
```

设计选择：
- **原地阻塞而非 durable 快照**：文件读写秒级；桌面须在线才能执行——断连即 cancel、本轮干净失败
- **不落 Postgres**：client_tool 请求是临时态，持久化会把路径写库违 at-rest，只用 Redis
- **安全护栏**：桌面 fs 桥的授权根 allowlist + realpath 边界校验，云端视为不可信请求方

### 8.3 对话产物落点

由「本轮有无可写本地根」一个开关决定：

| 运行语境 | 落点 |
|---------|------|
| 桌面 + 有可写根 | 只挂本地写工具，产出写本地原件 |
| 桌面 + 无根（随手新对话） | 懒创建：首次写文件时在默认根创建目录，之后同上 |
| 无桌面（headless / 自动化） | 禁产：不挂写工具；要产物须声明显式出口（webhook 等） |

### 8.4 文件树设计原则

- **一棵本地主树**：以本地授权目录为根，非"本地/云端两个平级源"
- 无全局树 store——各目录节点各自懒读子项并 watch，互不串扰
- 选中/改名/新建态由组件局部持有、单向下传
- fs 操作在 IPC 边界返回判别结果（`{ ok, reason }`）而非抛异常
- `fs.watch` 跟随展开状态，磁盘变更即刷新

### 8.5 本地目录授权模型

- 授权 = 持久契约（非会话参数）——per-target 显式授权
- 作用域变更对用户与 Agent 同等显式
- 兜底只追加、不替换、留痕迹
- 绝对路径不出本机（错误语言按受众分层）

### 8.6 项目身份模型（dotfile）

**本地文件夹 = 项目**：文件夹根下 `.agentcore/` dotfile 记录云端项目编号（类比 `.git/`），桌面打开即认、换机即认、零绑定仪式。

```
<项目文件夹>/
  .agentcore/
    project.json     # { schemaVersion, id, name, createdAt }
    rules/*.md       # 文件夹级规则
    memory/*.md      # 文件夹级记忆
```

**决策：云端权威 + dotfile 记号**（否决本地发号）。云端继续发编号、管对话，dotfile 只负责"记号"——保留手机/网页/平板等无本地文件夹设备的接入能力（纯本地身份会从结构上焊死手机端）。

| 旧（per-device 绑定） | 新（dotfile 自带） |
|---|---|
| 映射存设备 `preferences`，换机丢失须重绑 | dotfile 跟文件夹走，同步即带、打开即认 |
| 解析方向：云端号 → 查设备表 → 路径 | 解析方向：打开路径 → 读 dotfile → 云端号 |

**复制文件夹（同号）**：学 Git 对 `cp .git/` 的态度——允许两副本指同一云端项目，并发写云端时复用三方冲突检测（冲突保留两份、绝不自动覆盖）；要独立副本须显式"另存为新项目"。

## 九、前端运行时架构模式 ✅ 已确定

> 渲染层的组件组织、状态归属和数据流决策。

### 9.1 组件组织原则

按职责分层，非按功能域：

| 层 | 职责 | 判据 |
|---|---|---|
| `components/` | 纯渲染 | 只消费不持有状态 |
| `pages/` | 路由页 | 页面级组合 |
| `stores/` | Zustand 状态 | 所有状态 |
| `hooks/` | SSE 流与副作用 | 所有副作用 |
| `lib/` | 纯函数 / API client / mapper | 无副作用的可纯计算 |

`components/` 默认扁平、仅当功能多文件协作内聚成体系才开子目录。刻意不预先按功能域切深目录——浅层 + 少数子目录比深路径更易定位。

### 9.2 Store 关键拆分

| Store | 职责 | 关键决策 |
|---|---|---|
| `chat` | 消息列表 + 消息状态机 | 不含执行态 |
| `runs` | 统一 run 树 | 独立于 chat，按 messageId 隔离执行槽 |
| `detail-panel` | 面板 tab | 仅存引用（指针），不存数据 |

**run 树独立成 store** 是核心决策：执行态（编排步骤 + 委派子 Agent 统一为一种 run）与消息态正交，分开既防 chat reducer 膨胀、又让 run 按 messageId 隔离。

### 9.3 按 messageId 隔离执行态

`useRunsStore` 用 `byMessage: Record<messageId, RunExec>`，每条消息只读自己的执行槽——若用全局单例，同一会话连发多回合时第二条消息会读到上一回合残留步骤（节点串台）。

`message_end` 时把该槽 snapshot 为 run 树存进 `message.runs` 持久化供回放，随即 clear 释放实时槽，长会话不累积。

### 9.4 单一数据源、两层投影

聊天区分成两层：**inline 信号层（状态轨）** 和 **详情面板层**：

- 两层同口径取数——实时优先执行槽，回落快照
- 面板 tab 只存引用不存数据（渲染时现从 run 树取），流式中 run 树更新 → 面板自动跟随
- 编排步骤与委派子 Agent 是同一种 run，面板用同一套下钻（不区分来源）

### 9.5 事件归属显式化

所有后端事件在出口统一带 `message_id`，前端各 handler 一律按 `event.message_id` 归属。无差别注入 = 新增事件类型零改动自动路由，无「可路由事件白名单」需维护。

## 十、设计系统 ✅ 已确定

### 10.1 令牌唯一源

视觉令牌只有一份（共享包的 `theme.css`），所有端的 CSS 入口 `@import` 它，禁止本地重定义令牌。改令牌只改一处，四端生效。

### 10.2 色彩令牌设计

| 组 | 令牌 | 说明 |
|---|---|---|
| 主色 | primary / secondary | 、无品牌色相——克制，让内容与状态色说话 |
| 表面 | background / foreground / card / popover / muted | 标准语义表面层 |
| 交互 | accent / accent-foreground | 蓝色交互色（链接/选中/活跃/进行中） |
| 边框 | border / input / ring | |
| 状态 | destructive + status-success | 仅 2 个状态色：危险（红）+ 成功（绿） |
| 侧栏 | sidebar 系列 | 带极淡蓝色相，仅桌面端用 |

**关键取舍**：
- 组件中优先用语义工具类（`bg-primary`），需裸变量时用 `var(--color-*)`
- 消灭散落的 Tailwind 原生色类（`blue-*` → `accent`，`red-*` → `destructive`，`green-*` → `status-success`）
- 圆角不进令牌，统一用 Tailwind v4 默认档

### 10.3 桌面端冷灰变体

四端共享中性基色为 neutral（零色相纯灰）。桌面端通过 `.theme-desktop` scope 叠加 slate 蓝调冷灰，仅桌面端 `<html>` 挂该 class 时生效。选 scope 覆盖而非改基础令牌——变蓝只限桌面端，改基础会波及所有端。

### 10.4 暗色模式

Light-first。`theme.css` 保留 `.dark {}` 覆盖块作未来脚手架，当前不启用。真正启用需：Tailwind v4 配 `@custom-variant dark` + 主题切换 + `<html class="dark">`。

### 10.5 组件复用边界

| 层 | 策略 |
|---|---|
| **令牌** | 全端共享（已统一） |
| **原语**（button/input/dialog） | 共享包已有，桌面端不强迁，新组件上机会性收敛 |
| **域卡片** | 不设共享包。等有真实跨端消费者再从桌面端提取 |

## 十一、桌面端插件架构 ✅ 已确定

### 11.1 插件分类

| 类型 | 特征 | 示例 |
|------|------|------|
| 垂直工具 | 有独立页面、可能有本地存储 | 法规库、表格、Arena |
| 基础设施 | 有独立生命周期、push 事件 | 文件系统、MCP |
| 轻量工具 | 仅主进程 I/O + 简单页面 | 脱敏、日程 |

### 11.2 六贡献点（类比后端 Vertical）

| 贡献点 | 消费方 |
|--------|--------|
| 路由注册 | router（经 `getPluginRoutes()` 注入） |
| 侧栏导航 | app-shell（经 `getPluginNavItems()` 注入） |
| IPC Handlers | 主进程注册表（自动加 `app:{id}:` 前缀） |
| 生命周期 | 应用启动/退出时调用 |
| 推送事件 | 主进程 → renderer 单向推送 |
| 跨插件服务 | 其他插件经 `getPluginService()` 调用 |

### 11.3 IPC 类型安全

三层结构建立编译时契约：

```
plugins/{name}/ipc-schema.ts   ← 单一真相源
        ↓
plugins/{name}/main.ts         ← TypedHandlers<Schema> 约束实现
        ↓
preload/index.ts               ← IpcBridge<Schema> + AssertIpcBridge 断言
```

新插件必须先写 schema 再写 handler；旧插件按需迁移。

### 11.4 错误隔离

每个插件路由自动包裹 ErrorBoundary（注册表注入，插件开发者无感知）。单插件崩溃仅影响其自身路由区域，不触发全局错误。

### 11.5 设计决策

| 决策 | 理由 |
|------|------|
| 显式注册（非约定扫描） | 当前体量下显式 import 更可控、可 tree-shake |
| IPC Schema 渐进迁移 | 避免大爆炸重写 preload |
| ErrorBoundary 注入在 registry | 零额外代码 |
| 路由嵌套在统一工具布局下 | 侧栏/顶栏/面包屑一致 |

## 十二、SSE 事件消费规范

后端 SSE 事件（定义于执行引擎 §十二）到前端 Zustand Store 的映射关系。每条事件有唯一的消费路径，避免多 Store 竞争更新。

### 事件→Store 映射表

| SSE 事件 | 目标 Store | 更新字段/行为 | UI 组件影响 |
|----------|-----------|-------------|-----------|
| `message_start` | conversation | 创建新助手消息条目 | MessageList 追加气泡 |
| `content_delta` | conversation | 追加消息文本增量 | StreamingText 渲染 |
| `reasoning_delta` | conversation | 追加推理过程增量 | 可折叠思考区域 |
| `tool_use_start` | execution | 添加工具调用记录，状态=running | TaskCard 显示工具名 |
| `tool_use_end` | execution | 更新工具调用结果，状态=completed/failed | TaskCard 显示结果摘要 |
| `approval_required` | execution + ui | execution: 添加待审批项；ui: 弹出审批通知 | CheckpointCard 或审批弹窗 |
| `approval_resolved` | execution | 移除待审批项 | 审批弹窗关闭 |
| `ask_user_requested` | execution + ui | execution: 添加待回复项；ui: 聚焦输入框 | 特殊输入框状态 |
| `run_plan` | execution + graph | execution: 设置计划结构；graph: 创建节点和边 | TaskCard 出现；GraphView 渲染 DAG |
| `run_started` | execution + graph | execution: Agent 状态→running；graph: 节点状态更新 | 节点发光动画启动 |
| `run_output_delta` | execution | 追加 Agent 输出增量 | TaskCard 展开区实时输出 |
| `run_completed` | execution + graph | execution: Agent 状态→completed；graph: 节点状态更新 | 节点动画停止，标记完成 |
| `run_failed` | execution + graph | execution: Agent 状态→failed；graph: 节点标红 | 错误状态展示 |
| `run_retrying` | execution + graph | execution: Agent 状态→retrying | 节点闪烁动画 |
| `run_progress` | execution | 更新聚合进度（completed/total） | 进度条 |
| `task_state_updated` | execution | 更新工作记忆快照 | — |
| `pipeline_summary` | execution | 存储执行汇总 | 完成后统计展示 |
| `message_end` | conversation + execution | conversation: 消息标记完成；execution: 收口所有悬挂节点 | 流式结束，按钮状态恢复 |
| `error` | ui | 设置全局错误状态 | 错误通知弹窗 |
| `title_generated` | conversation | 更新对话标题 | ConversationList 标题更新 |

### SSE 连接管理

| 场景 | 行为 |
|------|------|
| 发送消息 | `POST /v1/conversations/{id}/messages` 返回 SSE 流 |
| 断线 | 自动重连（指数退避 1s/2s/4s），最多 5 次 |
| 401 过期 | 触发静默令牌刷新（§九 鉴权），刷新后重建 SSE 连接 |
| 恢复暂停 | `POST /v1/conversations/{id}/resume` 返回新 SSE 流 |
| 停止生成 | `POST /v1/conversations/{id}/stop`，前端立即 close SSE |

### 消费层实现模式

```typescript
// services/sse.ts — 事件分发器
function handleSSEEvent(event: SSEEvent) {
  switch (event.type) {
    case 'content_delta':
      useConversationStore.getState().appendDelta(event.payload)
      break
    case 'run_started':
      useExecutionStore.getState().setRunStatus(event.payload.run_id, 'running')
      useGraphStore.getState().updateNodeState(event.payload.run_id, 'running')
      break
    case 'message_end':
      useConversationStore.getState().finalizeMessage()
      useExecutionStore.getState().reconcileAllRuns()
      break
    // ...
  }
}
```

### 设计约束

- **单一入口**：所有 SSE 事件经 `services/sse.ts` 统一分发，不在组件中直接监听
- **Store 最小更新**：每条事件只更新必需的 Store 字段，不做全量替换
- **对账兜底**：`message_end` 时执行 `reconcileAllRuns()`，修正任何未收到终态事件的 run 节点
- **乐观更新**：发送消息时立即在 conversation store 创建 user message 条目，无需等后端确认
