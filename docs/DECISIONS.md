## 5. Agent 角色策略

不做预制 Agent 角色，采用"动态角色分配 + 用户可选行为模板"模式。

### 核心原则

| 原则 | 说明 |
|------|------|
| 无预制身份 | 系统中没有"代码Agent""写作Agent"这种固定角色 |
| 动态专精 | 编排器根据任务自动为协作 Agent 分配临时角色/工具集 |
| 行为模板（可选） | 用户可保存"我的代码审查工作流"作为可复用配置，但不是固定角色 |
| 用户自定义 | 高级用户可创建 Agent 配置（system prompt + 工具集 + 记忆偏好），作为 power feature |

### 决策理由

1. 预制角色把路由决策推给用户，与"管理团队"心智模型矛盾
2. 真实任务跨域，预设边界僵硬
3. LLM 能力增长会让专精角色过时
4. 竞品数据表明无产品因预制角色而赢得市场

**状态：已确定**

## 6. 编排器架构

采用"专职编排器 LLM + 检查点"模式。

### 核心设计

| 设计点 | 决策 |
|--------|------|
| 编排器定位 | 专职 LLM，只做意图理解和协作规划，不做任何内容执行 |
| 调度模式 | 检查点模式：规划后在关键节点设置检查点，由编排器轻量审视中间结果并决定是否调整 |
| 输入 | 用户请求 + 可用工具清单 + 用户行为模板（如有）+ 项目/会话上下文摘要 |
| 输出 | 结构化协作计划（Agent 列表、角色 prompt、工具集、工作流类型、依赖关系） |

### 编排器职责边界

```
✅ 理解用户意图
✅ 分解任务
✅ 决定 Agent 数量与角色
✅ 分配工具集
✅ 定义协作流程（串行/并行/辩论等）
✅ 在检查点审视中间结果并调整计划
❌ 不做任何内容生产
❌ 不调用任何工具
❌ 不直接与用户对话（通过 UI 层转发）
```

### 检查点触发条件

| 触发条件 | 编排器行为 |
|----------|-----------|
| Agent 完成一个阶段 | 审视输出摘要，确认是否继续下一步 |
| Agent 报告失败/异常 | 重新规划或分配备用 Agent |
| Agent 请求协助 | 决定是否增加新 Agent |
| 用户主动干预 | 重新规划 |
| 并行任务全部完成 | 触发汇总阶段 |

### 决策理由

1. 专职不执行：关注点分离，编排器 prompt 精简、输出结构化，延迟和成本可控
2. 检查点优于纯 fire-and-forget：能应对执行中的意外，但又不像持续监控那样每步都多一次 LLM 调用
3. 检查点优于持续监控：只在关键节点介入，平衡了灵活性和成本

**状态：已确定**

## 9. 后端技术栈

Python + FastAPI，通过 OpenAPI 自动生成 TypeScript 类型实现前后端类型同步。

| 决策点 | 选择 |
|--------|------|
| 语言 | Python 3.12+ |
| Web 框架 | FastAPI |
| 异步运行时 | asyncio (uvicorn) |
| 数据模型 | Pydantic v2 |
| 前后端类型同步 | FastAPI 自动生成 OpenAPI schema → openapi-typescript 生成 TS 类型 |

### 决策理由

1. Python AI 生态最强：LiteLLM、LangGraph、LlamaIndex、MCP SDK 等核心库均为 Python-first
2. FastAPI 原生异步、自动 OpenAPI 文档、Pydantic 类型验证，是 AI 后端的事实标准
3. 性能瓶颈在 LLM API 调用延迟而非后端计算，Python 的 I/O 性能完全满足需求
4. 跨语言类型同步通过 OpenAPI 工具链自动化解决，不需要手动维护两套类型

**状态：已确定**

## 10. 编排器实现方案

自研编排器，不依赖 LangGraph 等第三方编排框架。

### 核心模块

| 模块 | 职责 |
|------|------|
| 任务解析器 | 用户输入 → 结构化任务图（子任务、依赖关系、并行/串行） |
| Agent 分配器 | 根据任务角色需求分配 Agent 实例、工具集、system prompt |
| 执行引擎 | 管理 Agent 的并行/串行执行，处理依赖关系 |
| 状态管理器 | 维护任务状态、Agent 中间结果、检查点快照 |
| 检查点控制器 | 在关键节点审视中间结果，决定继续/调整/重规划 |
| 错误处理器 | Agent 失败时的重试、回退、重新分配策略 |

### 决策理由

1. 编排器是 AgentCore 的核心竞争力和产品壁垒，必须完全掌控
2. 第三方框架的抽象可能与「Agent 团队管理」的心智模型不完全匹配
3. 自研可以针对产品的具体需求做深度定制，不受框架约束
4. 避免框架锁定风险

**状态：已确定**

## 11. Agent 运行时模型

分层设计：Agent 逻辑和工具执行采用不同的运行时模型。

| 层 | 运行时 | 说明 |
|---|---|---|
| Agent 逻辑 | asyncio 协程 | Agent 的核心工作是调用 LLM API + 决策，纯 I/O 密集型，用协程最轻量 |
| 普通工具 | 同进程异步 | 文件读写、搜索等安全操作，无需额外隔离 |
| 代码执行 | 受限 subprocess（MVP）| MVP 用 subprocess + 资源限制，SandboxProvider 抽象接口预留升级 |

### 沙箱架构原则

- 设计抽象沙箱接口，后端实现可插拔
- 倾向自托管/自定制方案
- 安全最佳实践：默认禁止出站流量、凭证不进沙箱、文件系统边界严格、全量审计日志

### 决策理由

1. Agent 逻辑是 I/O 密集型（调 LLM API、等工具返回），协程最合适且与 FastAPI 天然融合
2. 代码执行的安全需求与 Agent 逻辑不同，必须分层处理
3. 沙箱具体实现是工程细节，架构上只需定义好接口

**状态：已确定**

## 12. 数据存储

最小组件策略：用尽量少的组件覆盖所有存储需求。

| 组件 | 覆盖的数据 | 说明 |
|------|----------|------|
| PostgreSQL + pgvector | 结构化数据 + 向量检索 | 用户/账户、Agent 配置、会话历史、Agent 记忆（语义检索） |
| Redis | 实时状态、缓存 | Agent 运行状态、任务进度、热数据缓存 |
| S3 兼容存储 | 大文件 | 代码执行结果、上传文件、工具输出等非结构化数据 |

### 决策理由

1. PostgreSQL + pgvector 一个库解决结构化数据和向量检索两个需求，运维最简
2. 3 个组件覆盖所有场景，早期不引入不必要的复杂度
3. 后续规模扩大可拆分：专用向量库（Qdrant）、消息队列（Kafka）等

**状态：已确定**

## 13. MVP 方向决策

已确定 MVP 的几项关键方向。功能集详见 §24。

| 决策点 | 选择 |
|--------|------|
| 客户端 | Electron |
| 场景覆盖 | 通用场景（编码 + 研究 + 写作 + 分析），不聚焦单一垂直 |
| 编排器实现 | 第一版直接使用 LLM 编排，不做硬编码规则 |
| 开发方式 | 全部由 AI 开发，一人决策，支持多 Agent 并行开发 |

### 决策理由

1. **Electron Day 1**：产品核心体验是"可视化 Agent 团队协作"，这需要 GUI 来承载（进度面板、协作流程图、实时输出流）。CLI 能验证逻辑，但无法验证用户体验。
2. **通用场景**：产品定位是"面向大众的 AI 工作台"，如果 MVP 只做编码就与 Cursor 直接竞争且无差异化。通用场景才能验证 Multi-Agent 的核心价值——不同类型任务的协作分工。
3. **LLM 编排直出**：硬编码规则需要预判所有场景，与"通用"矛盾。LLM 编排虽有风险（不稳定、成本高），但这正是产品核心竞争力所在，必须直面解决。
4. **全 AI 开发**：开发者全部是 AI Agent，需要模块接口清晰、文档充分、测试覆盖，以支持并行推进。

**状态：已确定**

## 14. 简单任务处理策略

所有任务统一经过编排器，由编排器通过输出计划的规模来区分简单/复杂场景。

### 核心设计

| 设计点 | 决策 |
|--------|------|
| 路由方式 | 无前置分类器，编排器是唯一入口 |
| 简单任务处理 | 编排器输出最小化计划（Agent列表=1，无检查点，无依赖） |
| 编排器模型 | DeepSeek V4 Flash（非思考模式），控制判断延迟在 300-800ms |
| 流式编排 | 编排器输出流式化，一旦确定计划类型即刻启动执行，不等完整计划生成 |
| 界面适配 | 自适应 UI：单Agent时为聊天形态，多Agent时展开协作面板 |

### 编排器输出的三种规模

| 场景 | 编排器输出 | 用户感知 |
|------|----------|---------|
| 简单对话 | Agent列表=1，无检查点 | 即时聊天回复，与 ChatGPT 体验一致 |
| 中等任务 | Agent列表=1-2，少量检查点 | 轻量协作提示 |
| 复杂任务 | Agent列表=3+，多检查点，有依赖关系 | 协作面板展开，展示完整分工 |

### 升级机制

对话可从简单逐步演变为复杂。编排器每轮重新评估当前任务复杂度，自然触发从"单Agent聊天"到"多Agent协作"的升级。升级时给用户明确的视觉信号。

### 决策理由

1. 编排器的结构化计划已天然覆盖所有规模，无需额外分类器组件
2. 统一入口避免维护两套决策逻辑的不一致风险
3. 快速模型 + 流式编排将感知延迟控制在可接受范围内
4. 后续如延迟确实困扰用户，可加规则预过滤层作为优化手段（而非架构改动）

**状态：已确定**

## 16. 前端 UX 架构

双视图架构：聊天视图（主）+ 图视图（辅）。全局布局采用 **侧栏 + 页面级自定义布局**（参考 C:\Project\1）。详细设计见 [`前端UX架构设计.md`](前端UX架构设计.md)。

### 核心设计

| 设计点 | 决策 |
|--------|------|
| 全局布局 | 侧栏 + 页面级自定义布局（非全局三栏） |
| 对话页布局 | 聊天主区 + 右侧可拖拽 DetailPanel（280~560px，可开关） |
| 主界面 | 标准聊天对话流，简单任务体验同 ChatGPT |
| 差异化元素 | 多 Agent 任务时对话流中自动出现「任务卡片」 |
| 详情面板 | 对话页专属，Tab 结构：Agent 状态 / 任务图 / 工具调用 / 输出 |
| 图视图 | 全屏覆盖视图，从详情面板或任务卡片进入 |
| 信息层次 | 逐步披露（5 层：输出→进度→Agent活动→内部通信→原始日志） |
| 用户干预 | 只在检查点和异常时请求用户操作 |
| 图视图引擎 | React Flow + elkjs + Framer Motion + SVG animate |

### 任务卡片状态机

```
规划中 → 执行中 → 检查点 → 已完成
                     ↓
                  失败/异常
```

- 简单任务（单 Agent）：卡片不出现，详情面板可关，体验同 ChatGPT
- 复杂任务（多 Agent）：卡片自动嵌入对话流，详情面板自动打开
- 检查点：用户可批准/调整/停止

### 图视图特性

- 分层树形布局（默认），可切换径向/力导向/左右流
- 节点实时状态（发光/脉冲/粒子流动动画）
- 右键菜单操作（暂停/重试/修改指令/替换模型）
- 50 节点规模，60fps，切换延迟 <200ms
- 进入方式：详情面板「图」Tab 放大 / 任务卡片 [图] 按钮

### 决策理由

1. 聊天为主保证零门槛，图视图为辅提供差异化和口碑传播点
2. 页面级布局比全局三栏更灵活——非对话页不被 Agent Panel 束缚
3. 详情面板可关闭——简单任务时体验等同 ChatGPT
4. 任务卡片将 §14 简单任务策略的"自适应 UI"落地为具体交互
5. 图视图截图极适合社交媒体传播（「看，我的 AI 团队在并行工作」）
6. 与 §15 前端技术选型一致，React Flow 已列入技术栈
7. 全局布局参考 C:\Project\1 已验证方案，降低设计风险

**状态：已确定**

## 17. 执行引擎架构

执行引擎是编排器与 Agent 实例之间的中枢，负责解析计划、调度执行、管理生命周期。详见 [`执行引擎架构设计.md`](执行引擎架构设计.md)。

### 核心设计

| 设计点 | 决策 |
|--------|------|
| 核心数据结构 | TaskGraph（DAG），由编排器 JSON 解析而来 |
| 调度算法 | 事件驱动循环：扫描 ready 步骤 → 启动 → 等待事件 → 处理 |
| 并发模型 | asyncio 协程，多 Agent = 多 asyncio Task 共享事件循环 |
| Agent 管理 | 实例可复用（同 Agent 多 step 串行），不同 Agent 间并行 |
| 检查点处理 | 暂停调度 → 编排器审视 → continue/adjust/escalate |
| 失败策略 | 可重试错误退避重试 + 不可重试错误跳过或升级用户 + 取消传播 |
| 计划热修改 | 支持运行时添加/修改/取消未启动的步骤（Hot DAG Modification） |
| UI 通信 | SSE 事件流，~20 种标准事件类型（详见执行引擎架构设计.md §十二） |

### 性能约束

| 指标 | 目标值 |
|------|--------|
| 最大并行 Agent | 10 |
| 最大步骤数 | 20 |
| 事件传播延迟 | < 50ms |

### 决策理由

1. DAG + 事件驱动循环是最自然的调度模型，与编排器的 depends_on 依赖图直接对应
2. asyncio 协程与已确定的 FastAPI 运行时天然融合，无需额外进程/线程管理
3. Agent 实例复用保留上下文窗口内历史，减少重复注入
4. SSE 事件流协议让前端可以实时渲染任务进度

> **架构演进**：执行引擎经历了从简单 DAG 模型到 Run/Journal/ReAct 统一模型的演进。当前已确定的实现架构为 §十二~§十八 的统一模型（ChatPipeline + ReAct 循环 + Run 树 + Turn Journal），§一~§十一 作为基础概念保留参考。详见执行引擎架构设计.md。

**状态：已确定（架构方向）；持久化、超时策略等细节待定**

## 18. LLM 接入策略

MVP 阶段只接入 DeepSeek V4，利用 Flash + Pro 双模型覆盖所有场景。

### 模型分配

| 角色 | 模型 | 模式 | 理由 |
|------|------|------|------|
| 编排器 | deepseek-v4-flash | 非思考模式 | 延迟最低、成本最低，适合快速意图判断 |
| 简单任务 Agent | deepseek-v4-flash | 思考模式 (high) | 性价比最优，简单任务够用 |
| 复杂任务 Agent | deepseek-v4-pro | 思考模式 (high) | 更强推理能力 |
| 极复杂任务 Agent | deepseek-v4-pro | 思考模式 (max) | 最大推理能力，需 384K+ 上下文 |

### 价格优势（截至 2026-06-14 官网价格）

| 模型 | 输入/1M（缓存命中） | 输入/1M（缓存未命中） | 输出/1M |
|------|-------------------|---------------------|--------|
| V4-Flash | $0.0028 | $0.14 | $0.28 |
| V4-Pro | $0.003625 | $0.435 | $0.87 |

对比 Claude Opus 4.7（$5 / $25）和 GPT-5.4（$2.5 / $15），成本优势在一个数量级以上。

### 关键技术要点

- 1M token 上下文窗口，384K max output
- 思考模式下 tool call 必须回传 `reasoning_content`
- 支持 OpenAI 和 Anthropic 两种 API 格式，使用 OpenAI 格式
- 缓存命中时输入价格降至 $0.0028/1M（Flash），极大降低多轮对话成本

### 架构预留

代码中定义 `LLMProvider` 抽象接口，MVP 只实现 DeepSeek 后端。未来增加其他模型供应商只需新增实现，不改核心代码。

### 决策理由

1. Flash + Pro 天然匹配编排器 + Worker 的双层架构
2. 成本极低，MVP 阶段可大胆实验不用担心 token 消耗
3. 1M 上下文对 Agent 场景是质变——项目上下文、多轮历史、工具输出都能放入窗口
4. 单供应商简化集成，通过抽象接口预留扩展能力
5. V4-Pro-Max 在 Agent 基准（SWE Verified 80.6、MCPAtlas 73.6）上已接近闭源前沿

## 19. 编排器输出结构

编排器输出结构化 JSON 计划，驱动执行引擎。详细设计见 [`编排器Prompt与输出结构.md`](编排器Prompt与输出结构.md)。

### 核心设计

| 设计点 | 决策 |
|--------|------|
| 输出格式 | 结构化 JSON（plan_type / agents / steps / checkpoints / output_strategy） |
| 并行控制 | steps[].depends_on 声明依赖，执行引擎自动推导并行度 |
| 模型抽象 | agents[].model_preference 用 fast/standard/strong 表达，运行时映射 |
| 流式解析 | 字段按优先顺序输出，增量解析器可在计划未完成时提前启动 Agent |
| 检查点审视 | 独立调用，输入=原计划+中间结果，输出=continue/adjust/escalate |
| 失败兜底 | 编排失败回退 single_agent 模式，最差也是普通聊天体验 |

### 决策理由

1. 结构化输出使执行引擎可机械执行，不依赖自然语言理解
2. depends_on 依赖图比显式声明"并行/串行"更灵活
3. model_preference 抽象解耦编排逻辑和模型选择
4. 流式编排将感知延迟从"规划完成"推前到"首个 Agent 可启动"

## 21. Agent 协作范式

MVP 支持四种协作范式，全部统一为 DAG 执行模型。

### 支持的范式

| 范式 | DAG 表示 | 场景举例 | 汇总方式 |
|------|---------|---------|---------|
| 串行流水线 | A → B → C | 调研→分析→报告 | 前序输出作为后序输入 |
| 并行分工 | A ∥ B → 汇总 | 同时研究多个方面 | 合并各 Agent 输出 |
| 辩论/审查 | A(pro) ∥ B(con) → 比较 | 方案对比、代码审查、观点辩论 | 编排器比较选择 |
| 混合 | 串行 + 并行的任意组合 | 先并行调研，再串行综合 | DAG 拓扑决定 |

### 辩论/审查与并行分工的区别

| 维度 | 并行分工 | 辩论/审查 |
|------|---------|----------|
| 输入 | 不同子任务 | 同一任务，不同视角 |
| Agent 角色 | 互补 | 对立/独立 |
| 汇总策略 | 合并（merge） | 比较选择（compare） |
| DAG 标记 | 各自独立子任务，依赖同一汇总节点 | 同一任务不同视角，compare 汇总策略 |

### 通信机制：共享工作区 + 编排器中转

MVP 阶段 Agent 间不直接通信，通过编排器和共享工作区间接协作。

```
Agent A 输出 → 写入 TaskWorkspace → 编排器检查点审视 → Agent B 读取
```

| 设计点 | 决策 |
|--------|------|
| Agent 间通信 | 不直接通信，通过 TaskWorkspace |
| TaskWorkspace | 每个任务会话一个，内存 KV 存储 |
| 数据格式 | Agent 输出以 `step:{step_id}:output` 为 key 写入（详见执行引擎 §十一） |
| 依赖传递 | 编排器在任务分配时指定依赖关系，执行引擎保证顺序 |
| 编排器可见性 | 编排器可读取所有 workspace 内容 |

### 冲突解决

| 冲突类型 | 解决方式 |
|----------|---------|
| 意见冲突 | 编排器在检查点审视并裁决 |
| 资源冲突 | DAG 依赖关系避免并发写入 |
| 优先级冲突 | 编排器负责任务排序 |
| 置信度低 | 编排器升级给用户决策 |

### 执行引擎统一模型

四种范式在执行引擎层全部统一为 DAG 拓扑排序 + 并发调度（asyncio.gather）。无需为不同范式编写不同的执行逻辑。

### 决策理由

1. DAG 是所有协作范式的超集，一套执行引擎覆盖全部场景
2. 辩论/审查增量实现成本低（只是 DAG 的特殊拓扑 + 比较检查点），但差异化价值高
3. 共享工作区避免 Agent 间直接 LLM 通信带来的成本翻倍和控制权丢失
4. 编排器中转保证所有协作过程对用户透明可观测

**状态：已确定**

## 23. 代码执行沙箱方案

MVP 阶段采用受限 subprocess，不引入 Docker 容器层。

### 核心设计

| 设计点 | 决策 |
|--------|------|
| 执行方式 | `subprocess.Popen` + 超时控制 |
| 资源限制 | `resource.setrlimit`（内存、CPU 时间） |
| 网络隔离 | 禁止出站网络（iptables 规则 或 seccomp） |
| 文件系统 | 只写临时目录，执行完自动清理 |
| 支持语言 | Python（Day 1），Node.js（Day 2） |
| 抽象接口 | `SandboxProvider` 协议，后续可替换为 Docker/gVisor/Firecracker |

### 决策理由

1. MVP 是单用户产品，安全风险可控
2. subprocess 启动零延迟，用户体验最佳
3. 实现复杂度最低，AI 开发速度最快
4. `SandboxProvider` 抽象保证后续无缝升级

## 26. 差异化定位

### 品牌理念

> **协作，是更高级的智能。**

人类文明的突破从来不是因为某个人变得更聪明，而是因为我们学会了分工与协作。AI 也一样——单个模型的智能有天花板，协作智能没有。

### 产品定位

> **AgentCore — 协作智能平台（Collaborative Intelligence Platform）**

不是「AI 助手」，不是「AI 代码编辑器」，而是一个让多个 AI Agent 协作完成复杂任务的平台。

### 定位体系

| 层级 | 内容 | 使用场景 |
|------|------|----------|
| 品牌理念 | 协作，是更高级的智能 | 品牌叙事、关于页面 |
| 品类定义 | 协作智能平台 | 产品介绍首句、官网标题 |
| 产品标语 | AI 的下一步不是更聪明的个体，而是更好的协作 | 官网副标题、宣传素材 |
| 功能标语 | 多 Agent 协作 · 全程可见 · 你是领导者 | 功能页、README |
| 竞品对比 | 单个模型的智能有天花板。协作智能没有。 | 对比页、PR 回应 |

### 用户角色定义

| 竞品 | 用户是… | AgentCore |
|------|---------|-----------|
| ChatGPT / Claude | 提示者（Prompter） | 领导者（Leader） |
| Cursor / Codex | 指令者（Commander） | 团队管理者（Team Manager） |
| Devin / Manus | 委托者（Delegator） | 协作指挥者（Conductor） |

用户心智模型：「管理一个 AI 团队」，而非「和一个助手聊天」（与 §2 核心理念一致）。

### 决策理由

1. 「协作智能」创造新品类，避免在「更强模型」维度与巨头直接竞争
2. 与产品技术架构完全对齐——多 Agent 协作是真实能力，不是营销包装
3. 中英文双语自然（协作智能 / Collaborative Intelligence），利于国际化
4. 为未来品牌扩展留空间（协作智能生态、协作智能开发者平台等）
