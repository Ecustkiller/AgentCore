## 核心定位

执行引擎是连接编排器和 Agent 实例的中枢。它接收编排器输出的结构化计划，解析依赖图，管理 Agent 生命周期，协调并行/串行执行，处理检查点和失败，并向 UI 推送实时状态更新。

## 二、核心数据结构

### 2.1 任务图（TaskGraph）

从编排器输出解析而来的 DAG（有向无环图）：

```python
@dataclass
class TaskNode:
    step_id: str
    agent_id: str
    task: str
    depends_on: list[str]
    dependents: list[str]       # 反向索引，由解析器构建
    status: StepStatus
    result: StepResult | None
    checkpoint_after: Checkpoint | None
    started_at: datetime | None
    completed_at: datetime | None

@dataclass
class TaskGraph:
    nodes: dict[str, TaskNode]
    root_nodes: list[str]       # 无依赖的起始节点
    terminal_nodes: list[str]   # 无后续的终止节点
    
    def get_ready_steps(self) -> list[TaskNode]:
        """找出所有依赖已满足且未启动的步骤"""
        ...
    
    def is_terminal(self) -> bool:
        """所有终止节点是否已完成或取消"""
        ...
```

### 2.2 步骤状态机（StepStatus）

```
              ┌────────────────┐
              │                │
              ▼                │
pending → ready → running → completed
              │       │         │
              │       │         ▼
              │       ├──→ failed ──→ retrying ─┐
              │       │                         │
              │       ▼                         │
              │    cancelled                    │
              │                                 │
              └─────────────────────────────────┘
```

| 状态 | 含义 | 进入条件 |
|------|------|----------|
| `pending` | 等待依赖完成 | 初始状态（有依赖） |
| `ready` | 依赖已满足，可以启动 | 所有 depends_on 均 completed |
| `running` | Agent 正在执行 | 调度器启动 |
| `completed` | 成功完成 | Agent 返回结果 |
| `failed` | 执行失败 | Agent 报错 / 超时 |
| `retrying` | 正在重试 | 重试策略触发 |
| `cancelled` | 已取消 | 用户/编排器取消 / 依赖失败传播 |

## 三、调度器算法（Scheduler）

调度器是执行引擎的核心循环，负责决定「下一步做什么」。

### 调度循环

```python
async def scheduler_loop(execution: TaskExecution):
    while not execution.is_terminal():
        # 1. 找出所有 ready 的步骤
        ready_steps = execution.graph.get_ready_steps()
        
        # 2. 启动它们（受并行度限制）
        running_count = count_running_steps(execution)
        available_slots = execution.plan.constraints.max_parallel - running_count
        
        for step in ready_steps[:available_slots]:
            await start_step(execution, step)
        
        # 3. 等待任一事件发生
        event = await wait_for_event()
        
        # 4. 处理事件
        match event:
            case StepCompleted(step_id, result):
                handle_step_completed(execution, step_id, result)
            case StepFailed(step_id, error):
                handle_step_failed(execution, step_id, error)
            case CheckpointTriggered(checkpoint):
                await handle_checkpoint(execution, checkpoint)
            case UserIntervention(action):
                await handle_user_action(execution, action)
            case PlanAdjustment(adjustments):
                apply_plan_adjustment(execution, adjustments)
```

### 依赖解析

```python
def get_ready_steps(graph: TaskGraph) -> list[TaskNode]:
    ready = []
    for node in graph.nodes.values():
        if node.status != StepStatus.PENDING:
            continue
        if all(graph.nodes[dep].status == StepStatus.COMPLETED 
               for dep in node.depends_on):
            node.status = StepStatus.READY
            ready.append(node)
    return ready
```

### 步骤完成处理

```python
async def handle_step_completed(execution, step_id, result):
    node = execution.graph.nodes[step_id]
    node.status = StepStatus.COMPLETED
    node.result = result
    node.completed_at = datetime.now()
    
    # 发射事件给 UI
    execution.event_emitter.emit("step.completed", {
        "step_id": step_id,
        "result_summary": result.summary
    })
    
    # 检查是否触发检查点
    if node.checkpoint_after:
        execution.event_emitter.emit("checkpoint.triggered", {
            "checkpoint": node.checkpoint_after,
            "step_result": result.summary
        })
        # 暂停调度器，等待检查点处理完成
        await handle_checkpoint(execution, node.checkpoint_after)
    
    # 更新整体进度
    execution.metrics.completed_steps += 1
```

## 四、Agent 实例管理

### 4.1 Agent 实例生命周期

```
create → initialize → execute(step) → [execute(step)] → destroy
                            │
                            ▼
                      pause / resume
```

| 阶段 | 行为 |
|------|------|
| `create` | 分配 Agent ID，准备配置 |
| `initialize` | 加载 system prompt + 工具集 + 模型配置 |
| `execute` | 执行一个 step（可被多次调用，同一 Agent 可执行多个 step） |
| `pause` | 保存当前状态，暂停执行 |
| `resume` | 恢复执行 |
| `destroy` | 释放资源 |

### 4.3 Agent 上下文注入

当 Agent 开始执行一个有依赖的 step 时，前置步骤的输出会被注入为上下文：

```python
def build_agent_prompt(step: TaskNode, graph: TaskGraph) -> str:
    prompt_parts = []
    
    for dep_id in step.depends_on:
        dep_node = graph.nodes[dep_id]
        prompt_parts.append(
            f"## 前置任务结果\n"
            f"来自 [{dep_node.role}] 的输出：\n"
            f"{dep_node.result.summary}"
        )
    
    prompt_parts.append(f"## 你的任务\n{step.task}")
    
    return "\n\n".join(prompt_parts)
```

### 4.4 Agent 复用策略

同一个 Agent 实例可以执行多个 step（如果编排器为同一 agent_id 分配了多个步骤）：

- **优势**：保留上下文窗口内的历史，不需要重新注入背景
- **策略**：同一 Agent 的多个 step 串行执行，不同 Agent 之间并行

## 五、检查点处理流程

```
步骤完成 → 检测到 checkpoint_after
    │
    ▼
暂停调度器（不启动新步骤）
    │
    ▼
调用编排器审视（checkpoint review）
    │
    ├── continue → 恢复调度器
    ├── adjust   → 应用计划调整 → 恢复调度器
    └── escalate → 通知 UI → 等待用户操作
                       ├── 用户「继续」 → 恢复调度器
                       ├── 用户「调整」 → 补充指令 → 重新编排 → 应用新计划
                       └── 用户「停止」 → 取消所有剩余步骤
```

### 检查点审视调用

```python
async def handle_checkpoint(execution, checkpoint):
    # 暂停调度器
    execution.status = ExecutionStatus.PAUSED
    
    # 准备审视输入
    review_input = {
        "review_type": "checkpoint",
        "original_plan": execution.plan,
        "completed_step": {
            "step_id": checkpoint.after_step,
            "output_summary": execution.graph.nodes[checkpoint.after_step].result.summary
        },
        "review_focus": checkpoint.review_focus,
        "remaining_steps": get_remaining_step_ids(execution)
    }
    
    # 调用编排器
    review_result = await orchestrator.review(review_input)
    
    # 处理结果
    match review_result.decision:
        case "continue":
            execution.status = ExecutionStatus.RUNNING
        case "adjust":
            apply_plan_adjustment(execution, review_result.plan_adjustments)
            execution.status = ExecutionStatus.RUNNING
        case "escalate":
            execution.event_emitter.emit("checkpoint.escalated", {
                "checkpoint": checkpoint,
                "summary": review_result.user_message
            })
            # 等待用户操作（通过事件）
```

## 六、失败处理策略

### 6.1 重试策略

```python
@dataclass
class RetryPolicy:
    max_retries: int = 2
    backoff_base_ms: int = 1000
    backoff_multiplier: float = 2.0
    retry_on: list[str] = field(default_factory=lambda: [
        "timeout", "rate_limit", "model_error", "network_error"
    ])
    no_retry_on: list[str] = field(default_factory=lambda: [
        "invalid_tool_use", "permission_denied", "context_overflow"
    ])
```

### 6.2 失败处理流程

```
Agent 报错
    │
    ├── 可重试错误（timeout/rate_limit）
    │       │
    │       ├── 未达上限 → 等待退避时间 → 重试
    │       └── 已达上限 → 升级为不可恢复
    │
    ├── 不可重试错误（逻辑错误/权限）
    │       │
    │       ├── 该步骤可跳过 → 标记 failed，继续其他步骤
    │       └── 该步骤关键 → escalate 给用户
    │
    └── 整体任务失败
            └── 保留已完成结果，通知用户
```

### 6.3 取消传播

当一个关键步骤失败时，所有直接/间接依赖它的后续步骤都应被取消：

```python
def propagate_cancellation(graph: TaskGraph, failed_step_id: str):
    queue = [failed_step_id]
    while queue:
        current = queue.pop(0)
        for dependent_id in graph.nodes[current].dependents:
            dep_node = graph.nodes[dependent_id]
            if dep_node.status in (StepStatus.PENDING, StepStatus.READY):
                dep_node.status = StepStatus.CANCELLED
                queue.append(dependent_id)
```

## 七、计划动态调整（Hot DAG Modification）

编排器审视后可能调整计划，执行引擎需要支持热修改 DAG：

| 操作 | 行为 | 约束 |
|------|------|------|
| `modify_steps` | 修改未启动步骤的 task 描述 | 不能修改 running/completed 步骤 |
| `add_steps` | 添加新节点和边到 DAG | 新节点自动进入 pending 状态 |
| `remove_steps` | 取消未启动的步骤 | 不能取消 running 步骤 |
| `add_agents` | 创建新 Agent 实例 | 在 Agent 管理器中注册 |

```python
def apply_plan_adjustment(execution, adjustments):
    if adjustments.modify_steps:
        for mod in adjustments.modify_steps:
            node = execution.graph.nodes[mod.step_id]
            assert node.status in (StepStatus.PENDING, StepStatus.READY)
            node.task = mod.new_task
    
    if adjustments.add_steps:
        for new_step in adjustments.add_steps:
            node = TaskNode(
                step_id=new_step.id,
                agent_id=new_step.agent_id,
                task=new_step.task,
                depends_on=new_step.depends_on,
                dependents=[],
                status=StepStatus.PENDING,
                ...
            )
            execution.graph.nodes[new_step.id] = node
            # 更新反向索引
            for dep_id in new_step.depends_on:
                execution.graph.nodes[dep_id].dependents.append(new_step.id)
    
    if adjustments.remove_steps:
        for step_id in adjustments.remove_steps:
            node = execution.graph.nodes[step_id]
            assert node.status in (StepStatus.PENDING, StepStatus.READY)
            node.status = StepStatus.CANCELLED
    
    # 通知 UI 图发生变化
    execution.event_emitter.emit("plan.adjusted", adjustments)
```

## 九、并发模型

基于已确定的 asyncio 协程模型（DECISIONS §11）：

```python
async def start_step(execution, step):
    agent = execution.agents[step.agent_id]
    step.status = StepStatus.RUNNING
    step.started_at = datetime.now()
    
    # 启动协程执行，不阻塞调度器
    asyncio.create_task(
        run_agent_step(agent, step, execution.event_emitter)
    )

async def run_agent_step(agent, step, event_emitter):
    try:
        prompt = build_agent_prompt(step, execution.graph)
        result = await agent.execute(prompt, on_event=event_emitter)
        event_emitter.emit("step.completed", ...)
    except AgentError as e:
        event_emitter.emit("step.failed", ...)
```

多 Agent 并行 = 多个 asyncio Task 同时运行，共享事件循环。由于 Agent 工作本质是调 LLM API（I/O 密集），协程完全足够。

## 十一、TaskWorkspace 数据结构

TaskWorkspace 是 Agent 间共享数据的中心存储，每个任务执行实例拥有一个独立的 workspace。

### 11.1 定位与职责

```
Agent A 输出 → 写入 workspace → 编排器审视可读 → Agent B 依赖注入时读取
                                                → UI 展示时读取
```

| 职责 | 说明 |
|------|------|
| 步骤输出存储 | Agent 完成步骤后将结构化输出写入 |
| 依赖数据传递 | 后续步骤启动前从 workspace 读取前置输出 |
| 检查点审视输入 | 编排器读取 workspace 内容进行审视 |
| UI 展示数据源 | 前端读取 workspace 渲染 Agent 输出和产物 |
| 最终结果汇总 | 输出策略模块从 workspace 读取并合并 |

### 11.2 核心数据结构

```python
@dataclass
class TaskWorkspace:
    execution_id: str
    entries: dict[str, WorkspaceEntry]

    def write(self, key: str, entry: WorkspaceEntry) -> None:
        self.entries[key] = entry

    def read(self, key: str) -> WorkspaceEntry | None:
        return self.entries.get(key)

    def read_by_step(self, step_id: str) -> list[WorkspaceEntry]:
        return [e for e in self.entries.values() if e.step_id == step_id]

    def read_by_agent(self, agent_id: str) -> list[WorkspaceEntry]:
        return [e for e in self.entries.values() if e.agent_id == agent_id]

    def get_step_output(self, step_id: str) -> StepOutput | None:
        entry = self.read(f"step:{step_id}:output")
        return entry.content if entry else None
```

### 11.3 Key 命名规范

```
step:{step_id}:output                   → 步骤主要输出（StepOutput）
step:{step_id}:artifact:{artifact_name} → 步骤产生的文件/代码/数据
step:{step_id}:error                    → 步骤错误信息
checkpoint:{checkpoint_id}:review       → 编排器检查点审视结果
execution:final_output                  → 最终汇总输出
```

| 前缀 | 写入者 | 读取者 |
|------|--------|--------|
| `step:*:output` | Agent（步骤完成时） | 调度器（依赖注入）、编排器（审视）、UI |
| `step:*:artifact:*` | Agent（产生文件时） | UI（展示产物）、后续 Agent |
| `step:*:error` | 执行引擎（步骤失败时） | UI（展示错误）、编排器（失败处理） |
| `checkpoint:*:review` | 编排器（审视完成时） | 执行引擎（决定下一步）、UI |
| `execution:*` | 输出汇总器 | UI（最终结果展示） |

```python
    prompt_parts = []

    for dep_id in step.depends_on:
        output = workspace.get_step_output(dep_id)
        if output:
            prompt_parts.append(
                f"## 前置任务结果\n"
                f"来自 [{output.agent_id}] 的输出：\n"
                f"{output.summary}\n"
            )
            # 如果前置步骤产生了代码文件，也注入
            artifacts = workspace.read_by_step(dep_id)
            code_artifacts = [
                a for a in artifacts
                if isinstance(a.data, Artifact) and a.data.content_type.startswith("text/")
            ]
            if code_artifacts:
                for a in code_artifacts:
                    prompt_parts.append(
                        f"### 产物：{a.data.name}\n```\n{a.data.content}\n```"
                    )

    prompt_parts.append(f"## 你的任务\n{step.task}")
    return "\n\n".join(prompt_parts)
```

### 11.7 Workspace 生命周期

| 阶段 | 行为 |
|------|------|
| 执行开始 | 创建空 workspace |
| 步骤完成 | Agent 写入 `step:{id}:output` + 产物 |
| 检查点触发 | 编排器读取相关输出 → 写入 `checkpoint:{id}:review` |
| 计划调整 | 新步骤可读取已有 workspace 内容 |
| 执行完成 | 汇总器从 workspace 生成 `execution:final_output` |
| 归档 | workspace 序列化到 PostgreSQL（会话历史） |

### 11.8 设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 内存 vs 持久化 | 运行时内存 dict，完成后归档 | 执行期间性能最优，归档后可回溯 |
| summary 必填 | 是 | 编排器审视和依赖注入都只读 summary，避免传递大量原始内容 |
| 产物与输出分离 | 是 | 产物可能很大（代码文件），单独存储便于按需加载 |
| Key 用冒号分隔 | 是 | 类 Redis 命名惯例，便于前缀查询 |
| workspace 不可变 | 否 | 但只允许追加（append-only），已写入的 entry 不可修改 |

## 十二、SSE 事件协议 ✅ 已确定

后端 → 前端的实时通信采用 SSE（Server-Sent Events），定义标准事件类型。

### 事件清单

| 事件 | 触发时机 / 语义 |
|------|---------------|
| `message_start` | 助手回合开始 |
| `content_delta` | 文本增量 |
| `reasoning_delta` | 推理增量（思考模式） |
| `tool_use_start` | 工具开始执行 |
| `tool_use_end` | 工具执行完成 |
| `approval_required` | 需人工审批（带 `grantable` 标志） |
| `approval_resolved` | 审批完成 |
| `ask_user_requested` | Agent 向用户提问 |
| `run_plan` | 预声明一批 run 节点（DAG 规划完成时） |
| `run_started` | 一个 Agent run 开始（编排步骤与子 Agent 的统一节点） |
| `run_output_delta` | run 自身答案文本增量 |
| `run_completed` | run 成功完成 |
| `run_failed` | run 失败 |
| `run_retrying` | run 重试 |
| `run_progress` | 一批 run 的聚合进度 |
| `task_state_updated` | 任务工作记忆快照更新 |
| `pipeline_summary` | 执行管线结束汇总 |
| `message_end` | 回合结束（含 `finish_reason` / usage / cost） |
| `error` | 不可恢复错误 |
| `title_generated` | 会话标题生成 |

### finish_reason 枚举

| 值 | 含义 |
|---|---|
| `end_turn` | 正常完成 |
| `max_rounds` | 达到最大轮次限制 |
| `degraded` | LLM 连续返回空响应 |
| `error` | LLM 不可恢复失败 |
| `cancelled` | 手动取消或断开 |

### 契约生成策略

后端是 SSE 类型的唯一真相源。推荐做法：
- 后端用 dataclass 定义每个事件的 payload schema（声明 = 构造同一对象，杜绝漂移）
- 由脚本反射 dataclass 自动生成前端 TypeScript interface
- CI 门禁：重跑生成器 + `git diff --exit-code`，拦契约漂移

## 十三、执行管线全貌 ✅ 已确定

> 从 HTTP 请求到 SSE 输出的完整后端调用链。

### 端到端流程

```
POST /v1/conversations/{conv_id}/messages
│
├─ router.send_message
│   └─ ConversationService.stream_chat
│       └─ ChatPipeline.run
│           │
│           ├─ [Prepare]  → ChatContext
│           ├─ [Execute]  → SSE 事件流 (asyncio.Queue)
│           └─ [Finalize] → DB 持久化 + 计费
│
└─ StreamingResponse → Client SSE
```

### Phase 1: Prepare

将 HTTP 请求转化为执行上下文：

1. 认证 + 校验对话归属
2. 载工作区上下文（RAG / 文件 / 规则）
3. AgentResolver.resolve → 组装 system prompt、选模型、解析工具集
4. 注入文件/RAG/委派/交互工具
5. 落用户消息 → 载历史（40% token 预算）
6. 解析团队与编排模式

**产出**：`ChatContext`（conv, system_prompt, model, tools, history, content_parts, team 配置）

**历史重建原则**：只回放 user/assistant 文本。工具 I/O 与委派详情属展示遥测（持久化供前端详情面板），不回放进 LLM 上下文——避免跨轮累积烧 token、撑爆窗口。

### Phase 2: Execute（ReAct 循环）

见 §十四 详述。

### Phase 3: Finalize

- 落库助手消息（content / tool_calls / usage）
- 记账 CostEvent（顶层 + 按委派子 Agent 分摊）
- 长对话摘要归档
- 收尾 Turn（status=completed）

**断连收尾契约**：各步骤独立 `try/except`，失败只 warning + rollback，不中断已完成的 SSE 流。刻意「能存多少存多少」而非全有或全无——用户已离开，保住已产生的消息与计费比元数据一致性更重要。

### Trace 关联

一次用户交互跨多个执行上下文（HTTP、后台 worker、委派 worker）。用统一 `trace_id` 作关联键，在管线入口铸一次，随 NATS payload 流到 worker。排查时 `grep trace_id=<id>` 即得全链路。

## 十四、ReAct 循环与收敛治理 ✅ 已确定

### 基本循环

`message_start` 后逐轮迭代至 `max_rounds`：

1. **轮顶查取消**（命中即 `message_end("cancelled")`）
2. **构建消息**（`trim_history_smart` + 滑动摘要）
3. **调用 LLM**（3 次重试 + fallback）
4. **执行工具调用**（并行 ≤5 / 30s 超时 / 审批）
5. **交 LoopController 判定** → 停用工具 / 注入引导 / 反思 / 终止

终止条件：`directive.stop` / 有正文且无工具调用 → `end_turn` / 超轮 → `max_rounds`

### 收敛治理（LoopController）

所有「循环要不要继续」的判断统一收敛到 LoopController，引擎每轮交结构化 `RoundOutcome`，按 `LoopDirective` 行动：

| 机制 | 阈值 | 行为 |
|------|------|------|
| LLM 重试 | 3 次指数退避 | 仅 429/5xx/timeout |
| Fallback 模型 | 主模型耗尽 | 切 fallback_model，裁剪 system prompt |
| 工具失败熔断 | 累计失败 2/3 次 | 2 次提示勿重试；3 次本轮停用 |
| 无产出早停 | 连续 3 轮全失败且无正文 | `finish_reason=unproductive` |
| 重复调用检测 | 相同签名连续 3 轮 | 注入「换策略」提示 |
| 反思注入 | 第 4 轮起每 3 轮 | 注入进度复盘 prompt |
| 空响应 | 连续 2 轮 | `finish_reason=degraded` |
| 工具超时 | 30s | `[ERROR]` 前缀返回 |
| 协作取消 | CancellationToken | 沿委派树向下传播 |

### SSE 桥接

执行侧与输出侧经**无界 `asyncio.Queue`** 解耦。背压只对可丢弃事件（`content_delta` / `reasoning_delta`）生效，生命周期/终止事件保证送达。

**前端兜底对账**：消息落定时递归收口所有悬挂的 running/queued run 节点——后端可靠送达是主路径，前端对账是 last-resort 兜底。

### 暂停与恢复（第三终态）

在 `completed` / `cancelled` 之外引入 `paused`——不 finalize、状态落盘、可重建续跑。

- **进入条件**：显式暂停 / 停止且已跨≥1个完成轮次边界
- **快照缝**：ReAct 轮顶是唯一干净快照点（history 满足消息配对不变量）
- **恢复**：经 `POST /resume` 开新 SSE、从断点续跑
- **计费**：暂停即计费（无清道夫），resume 段只计自己

## 十五、工具装配策略 ✅ 已确定

### 全部 opt-in，无默认档

内置工具全部 opt-in：Agent 在 `tools` 中声明分类或工具名才加载。没有「对所有 Agent 默认发放」的 core 档——能力是刻意声明、不靠隐式继承。

### 分类即工具包

| 分类 | 包含工具 |
|------|---------|
| `web` | web_search, read_url, rss_fetch, read_document |
| `text` | text_diff, structured_extract |
| `dev` | code_execute, http_request, sql_query |
| `productivity` | table, reminder |

### 工具来源统一审批

审批门与工具来源无关：内置/市场/连接器工具在执行层只认 `ToolBinding.approval` 一个字段，任意来源的高风险工具接入同一审批流。

### 时间即上下文

当前日期时间不走工具，由 PromptAssembler 追加到 system prompt 末尾的 `<runtime_context>` 块。省一次工具往返，LLM 永远「知道现在」。

## 十七、提示词架构 ✅ 已确定

### 两个互不相交的世界

| | World A — Agent 主提示词 | World B — 内部工具型提示词 |
|---|---|---|
| 是什么 | 面向用户的对话 Agent system prompt | 平台内部的窄任务 LLM 调用（标题/分类/摘要…） |
| 触发者 | 每个 Agent、每个 turn | 平台代码按需 |
| 形态 | 身份 + 技能 + 规则 + 上下文，条件装配 | 固定模板 + 少量变量，单次调用 |
| 管理方式 | PromptAssembler | 注册表 + 片段库 |

**分离原因**：两者关注点根本不同。强行共用只会互相拖累。

### World A：PromptAssembler 组装顺序

```
Agent system_prompt
  + Skills（workflow 全文 / catalog 目录）
  + Rules — 统一行为层（XML <rules>，按 priority 降序）
  + Workspace Context（RAG 检索 + 文件清单）
  + <runtime_context>（时间等运行时信息）
```

缓存：无 workspace_ctx 时按 agent_id 实例内缓存。
降级模式：低优先级规则过滤、文档截断、Skills 裁掉；Rules 保留（安全/合规约束越降级越要留）。

### World B：注册表 + 片段库

解决「内部 LLM 调用散落在 N 个文件，每个内联硬编码字符串」的问题。

| 模块 | 职责 |
|------|------|
| `PromptTemplate` | key / system / user / temperature / max_tokens / version |
| `fragments` | 可复用静态片段（通用约束词 + 拼装型静态块） |
| `registry` | 进程级注册表，按 key 取/渲染，重复 key 报错 |
| `catalog` | 所有系统级模板的单一真相源 |

关键约定：
- key 命名 `component.task`（如 `conversation.title`）→ 可观测
- `{{var}}` 渲染（双花括号变量，单花括号 JSON 示例原样存活）
- fragments 是 opt-in 字符串，不强制全局前缀

## 十八、运行时核心模型 ✅ 已确定

> 运行时收敛在三个一等模型上。每个模型把一族重复子系统坍缩成单一形状。

### 18.1 三模型总览

| 模型 | 职责 | 解决的问题 |
|------|------|-----------|
| **Interaction** | 唯一挂起原语：server 停下等 client 回值 | 统一审批/ask_user/本地工具/计划评审四套同构 BLPOP |
| **Turn Journal** | 唯一回合事实源：append-only 事实流 | 消除「回合无事实源」导致的历史回放/快照/消息完整性补丁族 |
| **Run** | 唯一执行单元：一棵 Run 树 | 统一委派/DAG/编排/路由四套并存的编排子系统 |

依赖关系：Interaction 最小独立；Journal 是 Run 的地基（事实留痕在 journal）；Run 落在两者之上。

### 18.2 Interaction（统一挂起原语）

```
InteractionRequest:
  id            # 请求-响应关联键
  kind          # approval | ask_user | client_tool | plan_review
  conversation_id / turn_id / run_id
  payload       # 各 kind 的请求体
  timeout_s
  scope         # call | turn（「本轮内都允许」语义泛化到原语层）
```

一套机制替换四套：统一等待器、统一挂起登记（`list_pending`）、统一恢复端点、统一回值端点。per-kind 差异降为策略位（durable / 键粒度 / at-rest 脱敏）。

### 18.3 Turn Journal（唯一事实源）

每个 turn 一条 append-only 条目流（主键 `turn_id + seq`），九类事实：

```
kind ∈ turn_started | round_boundary | llm_call | tool_call | interaction
      | note | run_event | message_final | turn_end
```

**一切皆投影**：

| 消费面 | 来源 |
|--------|------|
| SSE 流 | 引擎实时 emit（流式增量不入 journal） |
| 持久化消息行 | journal 投影器生成 |
| 暂停快照 | `round_boundary.fold` |
| 跨轮历史回放 | 文本 + interaction 答案投影 |
| LLM 窗口 | journal 投影（correct-by-construction） |

### 18.4 Run（唯一执行单元）

执行形状不再是离散「模式」而是数据，由 `depends_on` 边自然落定：

- 单 Agent = 单节点
- `fan_out` = 单波 + synthesis 终点
- `pipeline` = 线性链 + synthesis
- `adaptive` = 空计划 + captain 动态追加
- 单次 delegate = 追加一个节点
- ARENA best-of-n = 某节点 `candidates>1`

### 18.5 引擎纯化

三条去特判手段：

1. **工具效应模型**：`ToolResult(text, effect)`，`effect ∈ Continue | Handoff | Interact`。引擎只解释效应，`delegate`/`ask_user` 不再是特殊名字
2. **显式 ToolContext**：工具签名携 context（user/conv/turn 等），消灭 `set_runtime_context` 全局大杂烩
3. **去工具名特判**：引擎按能力位（`has_delegation_tool` 等）而非工具名判断行为

### 18.6 端口契约（宿主注入）

引擎面向宿主的 10 项端口（本地/云端同码、宿主注入）：

| 端口 | 定位 |
|------|------|
| Journal | 引擎唯一持久化出口 |
| EventSink | 渲染流出口（流式增量 + 离散事实实时投影） |
| InferenceGateway | LLM 调用 |
| ArtifactStore | 归档/寻回 |
| PauseSignal | 暂停信号（Redis flag） |
| ClientRequestBridge | 统一挂起原语的 4 类 kind |
| ConversationStore | 消息持久化（投影写入） |
| BillingSink | 计费事实投影 |
| DelegationTransport | 跨进程子树传输 |
| SnapshotStore | 已被 Journal 吸收 |

### 18.7 一轮一网关（Gateway 传播原则）

当用户自带 LLM 凭据时，整棵多 Agent 委派树必须在**同一把网关**下运行，避免 split-brain（队长跑用户 key，委派出去的子 Agent 回落平台 key）。

**规则**：在 Turn 最早阶段（工具装配之前）一次性解析 `effective_gateway`，随 Run 上下文贯穿整棵执行树。`InferenceGateway` 端口接收的凭据由此确定——直答、团队编排、恢复各路径读同一把。

此原则与凭据来源开关无关（无论平台供还是用户供），是执行语义的不变量。
