## 核心术语

| 术语 | 定义 |
|------|------|
| **AgentCore** | 产品名，AI Agent 生态平台。不设中文名 |
| **Agent** | 角色定义实体——包含人设、沟通风格、模型选择，是 Skill 的载体。创作者构建的可复用产品单元 |
| **Skill** | Agent 的领域能力——包含工作流指引、约束、输出格式；市场实体，经绑定注入 Prompt。单一来源（无内联） |
| **Tool** | 确定性动作执行器——无推理；内置函数或市场工具经声明式连接器执行。分两个家族：**动作工具**（执行确定性动作、不留可编辑产物，如 file/grep/web/exec）与**创作工具**（产出可持久编辑的产物类型，见下） |
| **创作工具（Creation Tool）** | 面向用户的工具，每个对应一种**产物类型**（思维导图/画布/多维表格/文档）；有"用户编辑器（人）+ Agent 工具（AI）"两副面孔，共编同一份产物。同属"工具"，故 Agent 也能用 |
| **产物（Artifact）** | 创作工具产出的可持久化、可反复编辑结果；进统一文件/产物体系，可被对话 `@` 引用、分享、重开 |
| **Rule** | 可复用规则——约束 Agent 行为的指令片段，可安装/共享 |
| **Team** | Agent 团队——多个 Agent 的编排组合，有 captain 和 members |
| **AgentVersion** | Agent 版本——包含 system_prompt、model、tools、delegations 的快照 |
| **Fork** | 复制他人 Agent 并独立改进的机制，类似 GitHub Fork |
| **Delegation** | Agent 委派——一个 Agent 将子任务交给另一个 Agent 处理 |
| **Arena** | 竞技场——多个 Agent 围绕同一主题进行多轮对抗/讨论（多轮辩论）。**实现 = 普通 AGENT DAG 的跨轮 `depends_on` 模式 + `stance`/`round` 标记**，非独立执行子系统（独立子系统已否决，见 `Agent协作模式.md` §7.4）；≠ best-of-N 择优，见下 |
| **best-of-N 择优** | 高不确定环节并行跑同一任务 N 个候选、择优输出的策略（`RunPolicy.candidates>1`）；执行策略位而非独立节点种类，与 Arena（多轮辩论）两回事 |
| **MCP** | Model Context Protocol（行业 Agent↔Tool 标准） |
| **A2A** | Agent-to-Agent Protocol（行业 Agent↔Agent 通信标准） |
| **ReAct** | Reasoning + Acting 循环，Agent 的推理-执行模式 |
| **SSE** | Server-Sent Events，对话流式输出的传输协议 |
| **Turn** | 交互聚合层——一次用户消息触发的完整 ReAct + 委派过程 |
| **Run** | 执行单元——一次被调度的 Agent 工作（委派的 worker / DAG 节点）；一个 Turn 含一棵 Run 树。生命周期见 `RunPhase`。代码层统一称 Run（旧称 Step 已废弃），用户展示用「任务 / 子任务」 |
| **CostEvent** | 成本事件——记录单次 LLM 调用的 token 用量和 CNY 成本 |
| **Approval** | 工具执行审批——安全门禁，按 tool_call_id 独立等待 |
| **Checkpoint** | 运行时状态快照——ReAct 循环各阶段自动保存，供调试和断点续跑 |
| **AgentCard** | Agent 能力声明——capabilities, input/output_modes, endpoint |
| **TaskRequest** | 标准化委派信封——instruction, context, constraints |
| **可发现性（Visibility）** | Agent 的固有属性，三态：`public`（上架）/ `unlisted`（凭 id 可达但不在发现面）/ `private`（仅创作者）。与 `is_featured`（编辑精选）正交 |

## 模型与质量档术语

> 用户面看到「质量档」，引擎内部跑「场景画像」——两者正交、易混，故并列于此。

| 术语 | 定义 |
|------|------|
| **质量档（Quality Tier · Model Mode）** | 用户可选的「团队角色 → 模型」映射，叠加在场景画像基座上，**只换 model、不动思考 / 温度 / 回合预算**。系统预设 `经济档`（全 Flash·默认）/ `高质量档`（CEO 本体 + 主力 worker 升 Pro）；可在运营 ceiling 内建自定义档。→ 见代码 `llm/modes.py` |
| **场景画像（ModelProfile · profile）** | 每个 LLM 使用场景的内部参数包（基座模型 + 思考 + reasoning_effort + 温度 + ReAct 回合预算）。五个：`chat`（单聊 / CEO 默认回复）、`agent.strong` / `agent.fast`（两 worker 能力档）、`memory` / `title`（后台非思考）。**内部实现，不外露给用户与 worker LLM**；与质量档正交——画像定参数，质量档换模型。→ 见代码 `llm/config.py` |
| **Flash / Pro** | DeepSeek V4 的两个实体模型（`deepseek-v4-flash` / `-pro`）。Flash = 经济基座（开发期所有画像默认基座）；Pro = 高质量，经质量档按角色叠加 |
| **思考强度档（reasoning effort）** | `high`（默认有效档）/ `max`（per-agent 按需解锁，**只升不降**）/ 非思考（标题·记忆等后台机械任务）。worker `fast` / `strong` 同为 `high`，靠回合预算（4 vs 28）区分，非靠思考强度 |

## 命名约定（代码符号 ↔ 展示文案）

统一术语、消除「同义多词」。代码符号（标识符 / 字段 / 事件 key）用规范名，面向用户的中文展示用展示文案；二者不混淆。开发期无兼容层，旧词直接废弃。

### 执行单元：Run（弃用 Step）

- 代码层一律 `run`：`run_id` / `RunPhase`（后端权威生命周期：queued·running·completed·failed·skipped·retrying）/ `RunStatus`·`RunNode`（前端投影态）/ `runs`；图节点高亮由 SidePanel 当前激活 run tab 派生（早期 `selectedRunId`/`selectRun` 跨 store 选中态已弃用）。
- 旧的 `step` 词汇（`step_id` / `StepStatus` / `steps` / `stepId` …）全部废弃。
- 用户展示文案仍用「任务 / 子任务」（展示语，非代码符号）。
- 例外：与 Run 无关的通用「step」保留——如 React Flow 的阶梯边 `StepEdge`、CSS 缓动 `step-end`、时间轴步进 `STEP_INTERVAL`。

### 终止：状态 cancelled，动作 stop

- 数据层（状态值 / `FinishReason` / 投影态）= `cancelled`。
- 动作层（按钮 / handler / 动词）= `stop`（如 `stopGeneration`）。
- 中文展示统一「已停止」（用户主动喊停，「停止」比「取消」自然）。

### 重跑：regenerate（整轮）vs retry（重试）

- `regenerate` = 从某条用户消息整轮重跑的原语（后端 `/regenerate`、`regenerate_chat`；前端 `runRegenerate`）。两种入口：直接重跑、改输入后重跑。
- `retry` = ① 前端传输错误后重发上一请求（`RetryBanner`）；② 后端自动重试（`RunPhase.RETRYING` / `max_retries`）。
- 中文展示固定三词：**重新生成**（要个新答案）/ **调整后重发**（改了输入）/ **重试**（失败后再试）。弃用游离的「重跑」。

## Agent-Skill-Tool 三层概念模型

### 不可违反的边界

| 维度 | Agent（专家） | Skill（技能） | Tool（工具） |
|------|--------------|--------------|-------------|
| 本质 | 有独立推理的参与者 | Agent 的内在能力（Prompt 注入） | 确定性原子能力 |
| LLM | 有独立画像与系统提示 | 无独立 LLM；知识注入宿主 Agent | 无；由当前 Agent 发起调用 |
| 执行 | 占轮次，参与共享上下文 | Prompt 组装时注入 system prompt | 步骤层内调用，不占轮次 |
| 调度 | 由委派或路由触发 | 绑定后始终注入（不按需） | Agent 推理决定调用 |
| 前端表现 | 独立气泡/身份标识 | 不直接呈现（隐含在回复质量中） | 折叠在宿主消息下 |

**核心原则：Agent 与 Tool 概念不相交**——需要 LLM 综合与表达的归入 Agent 轮次；输入输出确定的归入 Tool。不承认「会思考的工具」中间形态。

### 判定标准

- 需要 LLM 推理（有 ReAct 循环）→ **Agent**
- 描述一类任务的 SOP 工作流（Prompt 指引 + 工具绑定）→ **Skill**
- 不需要推理、给参数固定执行返回结果 → **Tool**

### Skill 与 Rule 的区分

| 维度 | Skill | Rule |
|------|-------|------|
| 职责 | 「怎么做」— 多步操作模板、领域指引 | 「不能做什么」— 行为约束、质控合规 |
| 粒度 | 域级（如"合同审查"、"数据分析"） | 原子级（如"中文优先"、"禁止虚构") |
| 加载方式 | 绑定加载；超阈值转目录 + consult_skill 按需取 | 按 apply_mode 分流：always 常驻、conditional 按条件注入、on_demand 按需取 |

### Agent→Skill 降级判定

当某个 Agent 满足以下全部条件时，应降级为 Skill：

1. 其**每次判断都依赖领域上下文**（不具备独立完成推理的能力）
2. 领域 Agent 挂载对应 Skill 后**可独立完成同等质量输出**
3. 该 Agent 的存在**增加调度歧义**（委派路由难以区分）
