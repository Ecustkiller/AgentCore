## 核心问题

Multi-Agent 系统中，Agent 之间如何协作？通信机制、冲突解决、任务编排的具体设计。

---

## 设计哲学：Multi-Agent First ✅ 已确定

AgentCore 以多 Agent 协作为默认范式，而非将其视为单 Agent 之上的扩展功能。

| 原则 | 含义 |
|------|------|
| **组合优于堆叠** | 新业务能力优先拆分为可组合的专职 Agent，而非在单个 Agent 的 system_prompt 中堆叠功能 |
| **单 Agent 是退化特例** | 一个独立 Agent 等价于「只有 Captain、没有成员的 Team」，运行时代码路径统一 |
| **委派是一等公民** | 每个 Agent 天然拥有委派能力（受白名单约束），LLM 自主决定何时调用 |
| **编排可组合** | Pipeline / Fan-out / Adaptive 三种编排模式可嵌套（Team 成员可以是另一个 Team 的 Captain） |

### 统一执行路径

所有对话（单 Agent / Team）走同一条代码路径，差异仅在委派工具的注入和编排策略的选择：

```
用户消息 → 解析 Agent/Team → 组装工具（含 delegate 工具）→ RuntimeEngine.execute()
                                    ↑
                      单 Agent: 仅 delegate tool
                      Team pipeline/fan_out: 编排前置 → Captain 综合
                      Team adaptive: Captain 自主调度（delegate tool 指向成员）
```

### 开发指导

- **新增业务功能时**：先问「这是独立 Agent 还是现有 Agent 的工具？」，优先选择独立 Agent + 委派
- **设计 system_prompt 时**：保持单一职责，复杂任务通过委派拆解

## 一、协作范式 ✅ 已确定

MVP 支持四种范式，全部统一为 DAG 执行模型。编排器自动选择范式，用户无需手动指定。

> 详见 [DECISIONS.md §21](DECISIONS.md#21-agent-协作范式)

| 范式 | DAG 表示 | 场景举例 | MVP 状态 |
|------|---------|---------|---------|
| **串行流水线** | A → B → C | 调研→分析→报告 | ✅ 支持 |
| **并行分工** | A ∥ B → 汇总 | 同时研究多个方面 | ✅ 支持 |
| **辩论/审查** | A(pro) ∥ B(con) → 比较 | 方案对比、代码审查 | ✅ 支持 |
| **混合** | 串行 + 并行组合 | 先并行调研，再串行综合 | ✅ 支持 |
| ~~主从委派~~ | — | — | 已被编排器架构吸收 |
| ~~自由对话~~ | — | — | 延后（复杂度高、成本高） |

## 二、通信机制 ✅ 已确定

共享工作区 + 编排器中转。Agent 间不直接通信。

> 详见 [DECISIONS.md §21](DECISIONS.md#21-agent-协作范式)

```
Agent A 输出 → 写入 TaskWorkspace → 编排器检查点审视 → Agent B 读取
```

| 设计点 | 决策 |
|--------|------|
| Agent 间通信 | 不直接通信，通过 TaskWorkspace 间接协作 |
| TaskWorkspace | 每个任务会话一个，内存 KV 存储 |
| 数据格式 | Agent 输出以 `step:{step_id}:output` 为 key 写入 |
| 可观测性 | 所有 workspace 内容对用户透明可查 |

### 为什么不要 Agent 直接通信

- Agent 间每次通信 = 额外 LLM 调用，成本和延迟翻倍
- 通信内容编排器看不到，失去控制和可观测性
- 共享工作区更简单，且天然支持任意范式

## 三、冲突解决 ✅ 已确定

编排器是唯一裁决者，用户裁决仅在置信度低时触发。

| 冲突类型 | 解决方式 |
|----------|---------|
| 意见冲突 | 编排器在检查点审视并裁决 |
| 资源冲突 | DAG 依赖关系避免并发写入 |
| 优先级冲突 | 编排器负责任务排序 |
| 置信度低 | 编排器升级给用户决策 |

## 五、Multi-Agent 设计约束 ✅ 已确定

> 基于 2026 年行业实践（Anthropic Building Effective Agents、LangGraph、CrewAI、Google A2A）提炼的 7 条行为约束。

| # | 约束 | 一句话 | 行业依据 |
|---|------|-------|---------|
| 1 | **单一职责** | 每 Agent 一个明确职责，prompt 不出现"先…再…" | Anthropic: orchestrator + specialized workers |
| 2 | **强制上层委派** | Agent 间任务传递只走编排器调度，禁止隐式状态共享 | Supervisor + Specialists 模式的故障隔离 |
| 3 | **读写分离** | 分析型 Agent 不持有写入工具（Analyzer / Mutator 二分） | LangGraph 强制不可变状态更新 |
| 4 | **上下文最小传递** | 子 Agent 只收到它声明需要的上下文，非父 Agent 全量历史 | 避免 5000 token planner 输出无差别传递 |
| 5 | **分层熔断** | 单 Agent 失败不拖垮整个 DAG（5 层×3 重试 = 243× 放大） | Google SRE Book |
| 6 | **幂等性执行** | 有副作用的操作携带幂等 key，重试不产生双重执行 | Cycles.io: 写操作必须 idempotency key |
| 7 | **模型分级** | 编排器用 V4-Flash 非思考模式（低延迟）；Worker 简单任务用 Flash 思考模式(high)，复杂任务用 Pro 思考模式(high/max) | 编排器轻量规划 + Worker 按复杂度分级，成本与质量平衡 |

### 约束 1 判断标准

| 问题 | 答 Yes → 拆 |
|------|------------|
| 这个 Agent 需要两种不同的 system prompt 才能做好？ | 拆成两个 Agent |
| 这个操作需要不同的模型或上下文窗口？ | 拆成独立 Agent |
| 失败时需要独立重试、不影响其他部分？ | 拆成独立 Agent |

**工具 vs 委派边界**：Agent 调用工具完成自身职责内的原子操作（检索、格式化、计算）是合理的。只有当操作本质上是另一个领域的完整子任务时，才应委派。

### 约束 3 读写分离落地

| 角色 | 能力 | 工具注入 |
|------|------|---------|
| **Analyzer（分析型）** | 读取、检索、推理、评估 | 仅注入只读工具 |
| **Mutator（执行型）** | 写入、修改、创建、删除 | 注入读写工具 |

实现要点：工具需标记 `mutation` 属性；运行时按 Agent 角色自动过滤写入工具。

### 约束 5 熔断参数参考

| 参数 | 推荐值 | 理由 |
|------|--------|------|
| 熔断阈值 | 连续 3 次失败 | 平衡故障识别速度和噪声容忍 |
| 冷却期 | 60 秒 | 足够让短暂故障恢复 |
| 隔离键 | (parent_agent_id, agent_id) | 某子 Agent 在一个父下故障，不连累别的父 |
| Redis 不可用时 | fail-open（放行） | 熔断器记账不能成为委派跑不起来的原因 |

### 约束 7 模型分级策略

| 角色 | 默认模型档 | 思考强度 |
|------|----------|---------|
| 编排器 / 检查点审视 | V4-Flash | 非思考（低延迟） |
| Worker Agent（简单任务） | V4-Flash | 思考模式 high |
| Worker Agent（复杂任务） | V4-Pro | 思考模式 high/max |
| Standalone 直答 | 系统默认 | 默认 |

**关键原则**：分级跟「行为」不跟「位置」——判据是该 Agent 是否还有下游调度任务，而非它被谁调用。

### 相关行业协议对照

| 协议 | 层级 | 用途 | AgentCore 对应 |
|------|------|------|---------------|
| MCP | Agent ↔ 工具 | 标准化工具/数据源接入 | MCP 连接器 |
| A2A (Google) | Agent ↔ Agent | 跨组织 Agent 互操作 | 内部委派协议参考 |
| AG-UI | Agent → 前端 | 实时事件流 | SSE 事件流 |

## 六、产物传递与共享工作区 ✅ 已确定

多 Agent 协作中「上游产物如何可靠传到下游」是核心问题。

### 核心决策

| 决策 | 结论 | 理由 |
|------|------|------|
| 协作边界 | **对话是产物的天然归属**（而非可选文件夹） | 一次对话的产物天然属于这次协作 |
| 产物空间 | 对话级工作区，所有参与 Agent 共享可见 | 消除"无 folder 时产物不可见"的断链 |
| DAG 注入方式 | **递指针不递全文**：注入 file_id + 摘要，需全文则自行读取 | 破除截断限制，跨轮依然有效 |
| 安全网 | Agent 未主动落库时，系统自动保存产物到工作区 | 宁污勿漏——误兜底可清理，下游断料才是致命的 |
| 安全网策略 | **只追加，从不覆盖** | 覆盖即静默丢数据，一个会弄丢东西的安全网就不是安全网 |

### 可见性公式

下游 Agent 看到的工作区 = **本对话产物 ∪ 所在 folder 内容（若有）**

所有「落工作区」的工具都从统一上下文获取 `conversation_id` 写归属，委派子 Agent 的 `conversation_id` 从顶层对话透传到底。

### 生命周期

| 操作 | 正式产物（用户/Agent 主动创建） | 系统备份（安全网） |
|------|------|------|
| 软删对话 | 不动，留在文件库 | 一起软删 |
| 永久删对话 | 解绑对话引用，保留在文件库 | 硬删 |

> 取向：删对话时**绝不丢用户主动产出的交付物**。

## 七、多 Agent 运行时机制 ✅ 已确定

> 三种多 Agent 交互模式（委派 / 编排 / Arena）的运行时机制，均复用同一 RuntimeEngine 内核。

### 7.1 委派（Delegation）

父 Agent 通过统一的 `delegate` 工具将子任务交给目标 Agent。执行链经过**规划（纯函数）→ 调度**两阶段：

1. `build_run_plan` 把 tasks 参数变成一个 `RunPlan`——执行形状不再是离散「模式」而是数据，由 `depends_on` 边自然落定（1 task 无 deps = 单跑；N 无 deps = 并行；有 depends_on = DAG；某节点 candidates>1 = ARENA best-of-n）
2. 唯一的 `WaveScheduler` 逐波次驱动执行

委派 / 团队 / 异步三条多 Agent 路径已全部收敛为「一个 RunPlan + 一个 WaveScheduler」。

| 机制 | 说明 |
|------|------|
| 白名单控制 | Agent 版本定义可委派目标，各层级独立白名单 |
| 上下文传递 | 子 Agent 收到父对话近期摘要；有依赖的下游节点注入上游产物；并行兄弟节点注入彼此任务摘录（分工感知） |
| 深度限制 | 最大委派深度 3 层；树级并发上限 10 |
| 路由引擎 | 统一 embedding 语义匹配，供委派动态扩展 + Agent 发现端点消费 |

### 7.2 委派预审（Preflight Audit）

当 Team 配置了预审 Agent 时，Captain 的所有委派走两阶段流程：

1. **delegate**（提案 + 审计）：Captain 提交方案 → 系统自动调用审计 Agent → 返回审计意见 + plan_id
2. **confirm_plan**（确认执行）：Captain 审阅意见后调用 → 系统执行方案

#### 统一裁决协议

所有评审型 Agent 共用一段裁决片段，裁决收敛为三档：

| 裁决 | 含义 | 行为 |
|------|------|------|
| 通过 | 无阻断项 | 直接执行 |
| 带建议通过 | 有建议但非阻断 | 执行，建议下传 |
| 打回 | 存在阻断项 | 返工重排 |

判据收敛：唯有「打回」才返工；「通过 / 带建议通过 / 无法解析」一律放行。把握不准归建议项（宁可少打回）。

#### 有界预检环

每轮对话最多 N 次 plan→audit（默认 2）。达上限后不再审计，直接「带风险放行」执行最新方案，由后续质量闸门兜底。这是补在 Captain 自由裁量之外的硬收敛保证。

### 7.3 Team 编排（Orchestration）

Team 的 `orchestration` 字段决定执行模式：

| 模式 | 行为 |
|------|------|
| `pipeline` / `sequential` | 成员按序执行，每步接收前一步输出。铺成线性链 + SYNTHESIS 终点 |
| `fan_out` | 所有成员并行执行，各自接收原始任务。铺成单波 + SYNTHESIS 终点 |
| `adaptive` | Captain 作为直接 RuntimeEngine 运行，团队成员作为委派目标注入，LLM 自主调度 |

#### TeamMember 字段语义

| 字段 | 用途 |
|------|------|
| `trigger_condition` | pipeline 下作为 instruction 注入；adaptive 下作为成员描述供 Captain 参考 |
| `context_strategy` | `previous`（仅前一步）/ `all`（所有已完成步骤）/ `none`（仅原始任务）|
| `result_handling` | 下游保真度：`pass_through`/`direct`=全文（默认）、`summarize`=摘要 |
| `timeout_ms` | 单步超时，默认 60s |
| `on_failure` | `skip` / `abort` / `retry`，默认 skip |

**依赖传递保真默认全文**：分析/检索→写作链路必须保留金额、法条编号等细节，「一律摘要」会丢失关键信息。`summarize` 仅用于大扇入合成省 token 的场景。

### 7.4 Arena（对抗）

独立于协作模式的结构化多 Agent 对话（辩论/法庭/谈判）：

- 固定阶段轮转，按 `respond_to_phase` 过滤历史
- 各角色从 Agent 版本加载 system_prompt 和 model
- 独立 SSE 事件族

#### 状态机

```
setup → running ⇄ paused → completed | cancelled | error
```

控制端点（pause/resume/skip/cancel）各自既落库状态、又向在跑引擎发信号（按 phase 边界生效，非轮中即停）。

#### 终态重开 = 回放，不重跑

重新打开终态 Arena 时回灌已落库内容、不启动 SSE——按「加载时后端状态是否终态」分流，终态走回放，非终态才续跑。

### 7.5 Agent 通信协议 (v1)

委派从进程内函数调用升级为标准化协议交互，内外部 Agent 走同一接口：

| 抽象 | 用途 |
|------|------|
| `AgentCard` | Agent 能力声明（capabilities, input/output_modes, endpoint） |
| `TaskRequest` | 标准化委派信封（instruction, context, constraints） |
| `TaskResponse` | 标准化响应（status, content, structured_output, usage） |

协议参考 A2A 但更轻量，面向内部 Agent 间通信。远程委派作为协议扩展位保留。

### 7.6 运行时基础设施

| 机制 | 说明 |
|------|------|
| CancellationToken | 协作式取消令牌，SSE 断开时沿委派树向下传播 |
| UsageAggregator | 全委派树的 token 用量聚合器 |
| 并发预算 | 树级并发上限经 contextvar 传播、按扇出细分预算，嵌套 fan-out 从 10→100→1000 收敛到整树 ≤10 |
| Session 隔离 | 并行委派每个子任务用独立 DB session |
| Prompt 缓存 | PromptAssembler 同实例内按 agent_id 缓存 |

**并发预算被否决方案**：树级共享 Semaphore——父持槽 await 子、子又抢同一信号量 → 必然死锁。

## 八、团队设计模式 ✅ 已确定

> 从旧系统法律团队和软件工程团队的实践中提炼的多 Agent 团队设计原则。

### 8.1 认知模式分离

团队角色从「不可合并的认知模式」推导，而非从岗位职称出发：

| 认知模式 | 职责 | 可合并？ |
|---|---|---|
| 编排 | 理解需求、选路由、编排 DAG、驱动返工 | 与其他模式不可合并 |
| 设计 | 模糊需求 → 结构化规格 + 技术设计 | 需求分析与架构设计可合并（同一模式） |
| 实现 | 按契约产出代码/文档 | 按领域分化（前端/后端），不与设计合并 |
| 评判 | 验证、审查、红队攻击 | 必须与实现分离（读写分离铁律） |
| 事实确立 | 读懂既有系统、定位故障 | 仅 brownfield 场景激活 |

**原则**：同一认知模式的细分可合并（减少上下文交接），不同认知模式不可合并。每多一个 Agent 多一次上下文交接——LLM 的弱点。

### 8.2 拓扑设计原则

| 原则 | 说明 |
|---|---|
| **拍平优先** | 纯路由层（不做分析的中间层）应删除，用 prompt 查找表替代 |
| **行业参数化** | 通用 Agent 的 prompt 不含行业词汇，行业上下文由调用方 brief 传入 |
| **双通道路由** | 队长/协调官按复杂度自动选路：简单 → 快速通道（直接委派），复杂 → 深度通道（完整 DAG） |
| **读写分离** | 评判者（质检员/审计员）`analyze` 只读，绝不改码；实现者 `full` 可写 |

### 8.3 质量保证机制

| 机制 | 说明 |
|---|---|
| **有界自动返工** | 质检员打回 → 队长自动派修 → 复跑质检，≤ 2-3 轮，超限升级用户 |
| **best-of-N 择优** | 高不确定环节并行调同一 Agent N 次，择优输出 |
| **契约固化 SSOT** | 设计阶段产出代码级契约文件，并行实现者共读同一份 |
| **Preflight Audit** | 提升为平台级 Agent，可被任何团队引用 |

### 8.4 构建助手设计模式

「对话式创建 Agent/Skill/Tool/Team」的安全边界：

| 原则 | 说明 |
|---|---|
| 配置型创建 | 永不生成/执行宿主代码（RCE 红线），仅声明式连接器 |
| 工具门控 | 构建工具按 agent 声明门控，须声明 `builder` 才获得写入权限 |
| 结构化 spec + 校验闸门 | 落库前 `validate_spec` 一次返回全部问题；`persist_spec` 原子落库 + 回执对比 |
| 归属强制 | `creator_id` 强制 = 当前用户，工具层强制，不信任 LLM 传参 |
| 草稿 + 发布 | 创建即 `draft`，发布需用户显式确认 |
