## 八、成本与配额模型 ✅ 已确定

> 计费与配额是平台的商业核心，也是内测期唯一的成本防线。

### 8.1 三层防线

三层正交：限流挡「刷得太快」，配额挡「用得太多」，计费只忠实记录、不拦截。

| 层 | 位置 | 管什么 | 失败行为 |
|---|---|---|---|
| **限流** | 中间件（Redis 滑窗） | **速率**——单位时间内的请求次数 | fail-open（Redis 故障放行） |
| **配额** | 业务层（回合开始前） | **总量**——日 token / 月成本 / 日请求数 | 超额拒绝下一回合 |
| **计费** | Finalize（append-only） | **记账**——每次 LLM 调用的真实成本 | 失败只 warning，不中断 |

#### 限流（速率防线）

两个互补的滑窗限流器（Redis ZSET 滑窗）：

- **按用户限流**：限制对话消息发送端点的频率（N 次/60s），挡单账号刷回合。值 ≤0 关闭；未登录请求放行（让路由自身返回 401）
- **按 IP 限认证端点**：限登录/注册/刷新端点，挡撞库

二者均 **fail-open**：Redis 不可达时放行，绝不因基础设施抖动把用户挡在门外。

#### 配额（总量防线）

每回合 prepare 时检查，三维度独立判定：

| 维度 | 窗口 |
|---|---|
| 日 token | 当日 0 点起 |
| 月成本（CNY） | 当月 1 号起 |
| 日请求数 | 当日 0 点起 |

关键决策：

- **0 = 该维度不限制**（fail-safe 宽松默认），全 0 则直接放行
- **回合粒度**：在回合开始前检查，超额拒绝下一个回合（不腰斩进行中回合）
- **每用户覆盖**：支持按用户存覆盖值，管理员可标记 `is_unlimited` 跳过所有检查
- **轻量到可放热路径**：一次检查 = 1 次 quota 表读 + 1 次成本事件聚合，命中既有索引

#### 计费记账（append-only）

每次 LLM 调用在 Finalize 落一行成本事件：tokens（prompt / completion / cache_hit / cache_miss）、四类成本（input / cached / output / total CNY）、rounds、duration。

- **成本口径**：`成本 = tokens × 模型单价`，input / cached / output **三类单价分开**——缓存命中按更低的 cached 价计，如实反映前缀缓存省下的钱
- **角色归属**：通过 trace 标记区分顶层回合（captain）与委派子 Agent（member），支撑按角色看花销
- **多 Agent 分摊**：一次用户交互的成本 = 顶层 + 各委派子 Agent 之和，逐事件记录、可按 conversation / agent / 角色聚合

### 8.2 用量/成本类型不变量

token 与成本在系统中有多种形态（SSE wire、持久化、API 响应、计费台账），但两条不变量保证不会算出两套数：

1. **唯一原始来源**：单次 LLM 调用的原始 Usage（prompt / completion / total + cache_hit / cache_miss + reasoning 六字段），所有用量都从它累加
2. **唯一定价转换**：全系统唯一的 `calculate_cost(model, usage)` 函数把 token 折成钱（input/cached/output 三价分离），任何地方要成本一律调它，绝不另算单价

**真正的钱以 `cost_events` 台账为准**，message/runs 里的成本只是展示快照。新增任何成本展示点 → 复用统一定价函数，勿手算单价。

### 8.3 成本预估 ≠ 实际记账

团队组建时提供启发式预估，与真实记账是两套东西，刻意如此：

- 预估用途是**比较不同团队组合的贵贱**（「三个 premium 模型会很贵」），不是预测真实账单
- 算法基于固定假设（Captain 跑 3 轮、成员各 2 轮，每轮约 3000 输入 + 700 输出 token）
- 假设串始终展示给用户，确保该数字永远不被误当成事实

## 九、鉴权与会话 ✅ 已确定

> 跨「前端 + 反向代理 + 后端」的登录会话设计。

### 9.1 双令牌 httpOnly Cookie 模型

| 令牌 | 生命周期 | 用途 |
|---|---|---|
| access_token | 短期（默认 30min） | 所有 API 请求 |
| refresh_token | 长期（默认 7d；remember_me 30d） | 仅用于换新 access_token |

两者均为 httpOnly Cookie，前端拿不到令牌明文，靠 `credentials: 'include'` 自动携带。

### 9.2 静默刷新（Reactive）

访问令牌过期后由 401 触发刷新 → 换新 → 重试原请求，对用户无感；刷新令牌过期才真正跳登录。

**关键约束——流式通道必须独立接入刷新**：

聊天 SSE（发消息、恢复、异步委派流）通常绕过统一的 HTTP 请求封装直接 fetch。这些通道**必须各自包一层 401→刷新→重发**，否则「读了半小时再发消息」会因访问令牌过期而直接掉登录，而非无感续期。新增任何绕过统一请求层的 fetch/XHR 通道时，都需接入此机制。

重发安全保证：401 在认证依赖层抛出、路由 handler 尚未执行，请求无副作用，可安全重发。

### 9.3 刷新令牌轮换 + 并发宽限窗口

刷新令牌单次使用：每次 refresh 把旧令牌标记已轮换，并在同一 token family 内签发后继（仅 login/register 起新 family）。

**要解决的问题——多标签页互踢**：浏览器跨标签共享 Cookie，多个标签或一批并发 401 会同时拿到同一个 refresh 令牌。若每次都吊销整族，并发竞态中「后到的那次」会被踢下线。

**解法——宽限窗口**（默认 10s）：

| 场景 | 行为 |
|---|---|
| 令牌首次交换 | 标记已轮换、同 family 签发后继 |
| 已轮换令牌在窗口内再次出现 | 判为善意并发（多标签/并发重试），重新签发、不杀会话 |
| 已轮换令牌在窗口外再次出现 | 判为泄露/重放 → 吊销整族，强制重登 |

### 9.4 Cookie Path 约束（生产专属坑）

当 web 与 api 同源部署（反向代理把 `/api/` 反代到后端）时，refresh Cookie 的 `path` 必须是 `/`，**不能**写后端真实路由。否则按 RFC 6265，浏览器实际请求路径不以 Cookie path 为前缀 → Cookie 永不回传 → 静默刷新 100% 失败 → 30min 后用户被踢回登录页。

此坑 dev 环境测不出（直连后端，路径恰好命中），只在生产触发。会话隔离（如产品/管理后台并存）靠 Cookie **名字**区分，不靠 path。

### 9.5 易踩坑速查

- 动 refresh Cookie 的 `path` → 只能用 `/`，否则生产必掉登录
- 新增绕过统一请求层的 fetch/XHR（尤其 SSE）→ 必须自行接 401→刷新→重发
- "总是掉登录"先查刷新链路（Cookie path / SSE 是否接入刷新 / 轮换是否互踢），调长访问令牌过期时间只是掩盖、非根治

## 十、后端架构模式 ✅ 已确定

> **与项目结构的关系**：本节描述的是完整目标架构的模块体系。MVP 阶段的实际目录结构见 [`项目结构.md`](项目结构.md)，仅包含标记为 ✅ MVP 的模块。Post-MVP 模块在需要时逐步添加。

### 10.1 五层分层

每个业务模块遵循 `models → schemas → repository → service → router`，调用方向严格单向、不可反转：

| 层 | 职责 | 约束 |
|----|------|------|
| **models** | ORM 定义 | 无 ForeignKey（应用层维护引用；MVP 阶段可使用 FK 简化开发，上线前评估是否需要去除）；主键用 UUID |
| **schemas** | Pydantic request/response | 命名规范 `CreateXxxRequest`、`XxxDetail`、`XxxListItem` |
| **repository** | 纯数据访问 | 接收 AsyncSession；不含业务逻辑 |
| **service** | 业务逻辑 | 构造注入 AsyncSession，内部实例化 repository，组合多 repo |
| **router** | HTTP 端点 | 薄层委托 service，用 DI 别名，不直接操作 DB |

| memory | 工作记忆：工件存储 + TWM 注入 |
| suspend | 持久暂停/恢复 + checkpoint |
| sandbox | 代码执行沙箱后端 |

### 10.4 垂直插件机制

平台核心行业无关，垂直领域作为可插拔插件接入。核心可在不加载任何垂直时独立启动、测试、发布。

#### 契约（6 个贡献点）

| 贡献点 | 用途 |
|--------|------|
| `builtin_modules()` | 无状态内置工具 |
| `tool_providers()` | 有上下文的工具提供器 |
| `routers()` | FastAPI 路由 |
| `task_handlers()` | 异步任务类型处理器 |
| `on_startup()` | 垂直专属设施启动 |
| `on_shutdown()` | 垂直专属设施关闭 |

#### 发现机制

约定式扫描垂直子包目录，环境变量白名单控制启用哪些垂直（空 = 纯净核心）。

#### 反向依赖消除

「核心 → 垂直」反向依赖一律通过注册/钩子反转消除——垂直经贡献点接入，核心不反向 import。边界规则：垂直可依赖核心，核心不得依赖任何垂直。验证指标：白名单为空时平台核心独立运行。

## 十一、评估体系 ✅ 已确定

> 多 Agent 运行时的质量评测架构：回答「拿什么守护 AI 输出质量与协作正确性」。

### 11.1 为何需要独立评估

AI 模块是**非确定性**的：同一输入两次执行结果不同。普通 mock 单测只能验证「机制是否运转」，覆盖不了两个决定产品质量的问题：

1. **输出好不好**——最终回答是否答到点、结构是否完整（语义判断）
2. **协作对不对**——该委派的有没有委派、是否陷入循环/降级/撞上限（过程判断）

### 11.2 两层模型

| 层 | 性质 | 依赖 | 门禁 | 触发 |
|---|---|---|---|---|
| **Layer 1** 离线确定性 | 静态/机制检查 | 零 LLM、零 DB、毫秒级 | **PR CI 硬门禁** | 每次 PR |
| **Layer 2** 在线 LLM-in-the-loop | 真实 Agent 执行 + 评判 | 真 LLM + 已 seed 的 DB | **软门禁**（仅告警不阻断） | 定时/手动 |

**为何这样分**：质量评测天然要调真 LLM（语义判断无法 mock），但真 LLM 慢、要钱、非确定——进 PR 硬门禁会 flaky 且昂贵。把「给定事件流即可裁定」的确定性部分下沉 Layer 1 硬门禁，把「必须真 LLM」的留 Layer 2 软门禁。**软门禁是刻意决策**——LLM 非确定，通过率低于阈值只告警，不硬卡。

### 11.3 Layer 1 维度

| 维度 | 说明 |
|---|---|
| **种子完整性 lint** | 种子 JSON 的静默失败检测（委派目标不存在、团队成员缺失、非法分类等） |
| **执行轨迹断言** | 从运行时事件流还原结构化轨迹，按声明式期望裁定过程正确性（委派目标、工具调用、读写分离、轮次上限、循环检测等） |

轨迹断言是确定性的（只消费事件流，不重跑 LLM），可跨层复用：Layer 1 用 MockGateway 驱动真实引擎产出事件流做回归；Layer 2 把同一套断言叠加到真实 SSE 流上。

### 11.4 Layer 2 维度

| 维度 | 评什么 | 方法 |
|---|---|---|
| **路由准确率** | Pilot 的路由决策质量 | 真实 LLM 单轮，截获 `delegate` 目标与 golden 比对。固定 temperature=0 测能力基线 |
| **输出质量** | 最终回答是否答到点 | 端到端真实 Agent 执行 + LLM 裁判按 rubric 打分（1-5），叠加确定性规则断言 |

**判定口径**：规则断言全过 **且** 裁判分 ≥ 3 才算通过。

### 11.5 关键决策

| 决策 | 理由 |
|---|---|
| Layer 2 走 HTTP 真实链路 | 质量评测要完整最终输出，打生产 API 保证「测的就是生产链路」 |
| LLM-as-judge 固定 temperature=0 | 评分是判断不是创作，须可复现 |
| 路由 eval 固定 temperature=0 | 生产 Pilot 用高温兼顾通用对话，但评测须测「能力稳定基线」 |
