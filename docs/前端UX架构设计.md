## 核心设计理念

用户心智模型是「管理一个 Agent 团队」，UI 是用户感知这一心智模型的唯一窗口。设计需在「零门槛入门」和「差异化体验」之间取得平衡。

## 一、全局布局与视图架构

### 全局布局

全局采用 **侧栏 + 页面级自定义布局** 模式（参考 `C:\Project\1`），详见 [`前端技术选型.md`](前端技术选型.md) §五。核心对话页的内部布局为：

```
┌──────────────────────────────────────┬──────────────────┐
│                                      │ ← 拖拽手柄       │
│  聊天视图（主交互）                    │  DetailPanel     │
│  消息流 + 任务卡片 + 流式输出          │  (可开关/拖拽)    │
│                                      │                  │
│                                      │  Tab: Agent 状态  │
│                                      │  Tab: 任务图     │
│                                      │  Tab: 工具调用    │
│  ┌────────────────────────────┐      │                  │
│  │ 输入框                      │      │                  │
│  └────────────────────────────┘      │                  │
└──────────────────────────────────────┴──────────────────┘
```

### 双视图：聊天 + 图

```
默认用户体验：熟悉的聊天界面（零学习成本）
差异化体验：可随时切换到全屏图视图看团队协作全貌
```

| 维度 | 聊天视图（主） | 图视图（辅） |
|------|---------------|-------------|
| 定位 | 主要交互界面 | 全屏可视化（从详情面板或任务卡片进入） |
| 信息层 | Layer 0-1（输出 + 进度） | Layer 0-3（全量信息） |
| 输入能力 | 有（底部输入框） | 有限（只能干预，不发新任务） |
| 适用场景 | 日常使用、简单任务 | 复杂任务监控、调试、Power User |
| 用户群 | 所有用户 | 好奇/高级用户 |
| 进入方式 | 默认 | 详情面板「图」Tab 点击放大 / 任务卡片 [图] 按钮 |

### 信息层次模型

```
Layer 0 — 最终输出     ← 用户最关心的东西
Layer 1 — 任务进度     ← 哪些子任务、谁在做、做完了吗
Layer 2 — Agent 活动   ← 每个 Agent 具体在做什么（工具调用、中间输出）
Layer 3 — 内部通信     ← Agent 之间传递了什么
Layer 4 — 原始日志     ← LLM 调用、token 消耗、延迟
```

默认可见：Layer 0 + Layer 1
详情面板展开：Layer 2
图视图 / Debug 模式：Layer 3 + 4

### 信息呈现位置映射

| 信息层 | 聊天视图中的位置 | 详情面板中的位置 | 图视图中的位置 |
|--------|----------------|-----------------|---------------|
| Layer 0 | 消息流中直接展示 | — | 汇总节点 |
| Layer 1 | 任务卡片（Agent 列表 + 进度） | Agent Tab | 所有节点概览 |
| Layer 2 | 任务卡片 [展开] | Agent Tab 详情 | 节点内部 + 双击 |
| Layer 3 | — | — | 边上的数据流 |
| Layer 4 | — | — | 右键节点 → Token 用量 |

## 二、聊天视图

### 基本结构

标准对话流界面（类似 ChatGPT / Cursor），但嵌入 Multi-Agent 特有 UI 元素。

### 聊天视图中的 Multi-Agent 特有元素

| 元素 | 作用 | 何时出现 |
|------|------|----------|
| **任务卡片** | 展示任务分解、Agent 分工、整体进度 | 多 Agent 任务时自动出现 |
| **Agent 标签** | 当前输出来自哪个 Agent | 流式输出时 |
| **检查点提示** | 编排器请求用户确认或调整 | 检查点触发时 |
| **[查看图]按钮** | 切换到图视图 | 任务卡片右上角常驻 |

简单任务（单 Agent）时：任务卡片不出现，整体体验和 ChatGPT 完全一样。

### 输入框 (InputBar) ✅ 已确定

卡片式输入框，底部固定于聊天区下方：

```
┌──────────────────────────────────────────────────┐
│ [文件夹 pill]  [附件 chips...]  [产物 pill]       │
├──────────────────────────────────────────────────┤
│                                                  │
│  输入消息...                                      │
│                                                  │
├──────────────────────────────────────────────────┤
│ [🤖 Agent 选择]  [📎 附件]         [123字] [发送] │
└──────────────────────────────────────────────────┘
```

| 特性 | 说明 |
|------|------|
| Textarea 自动增高 | 随内容调整高度，最大 200px |
| Agent/Team 选择器 | 工具栏左侧，选择对话目标 Agent |
| @ 引用文件 | 输入 @ 触发文件选择弹窗，选中文件成为附件 |
| / Slash 命令 | 行首输入 / 触发命令选择（新对话、切换Agent、清空等） |
| 拖拽文件 | 拖入文件成为附件 chip |
| 文件夹 Pill | 显示当前工作目录（对话绑定的本地文件夹） |
| 产物 Pill | 显示对话产物聚合入口 |
| 流式状态 | 发送按钮变为停止按钮（方形图标） |
| 字数统计 | 工具栏右侧实时显示字数 |

**键盘快捷键：**

| 快捷键 | 行为 |
|--------|------|
| Enter | 发送消息（非 IME 输入法组合中） |
| Ctrl/Cmd + Enter | 插入换行 |
| Escape | 关闭 @/slash 弹窗 |
| 上下箭头 | 弹窗内导航选项 |
| Tab / Enter | 确认弹窗选择 |

### 消息气泡 (MessageBubble) ✅ 已确定

| 元素 | 说明 |
|------|------|
| Agent 头像 + 名称 | 消息来源标识（AI 侧显示） |

| 时间戳 | 显示消息时间 |

| 元素 | 触发条件 | 行为 |

## 三、任务卡片设计

任务卡片是 AgentCore 聊天界面与普通对话 AI 的核心视觉差异点。

### 状态机

```
规划中 → 执行中 → 检查点 → 已完成
                     ↓
                  失败/异常
```

### 状态 1：规划中

```
┌──────────────────────────────────────┐
│ ⚡ 规划中...                          │
│                                      │
│ 正在分析任务并分配 Agent 团队          │
│ ███░░░░░░░░░░░░░░░░░░░░░░░░░░░      │
└──────────────────────────────────────┘
```

- 可见内容：加载动画 + 一句话描述
- 可交互：取消按钮
- 设计意图：让用户知道系统在思考，而不是卡住了

### 状态 2：执行中

```
┌──────────────────────────────────────┐
│ 实现用户登录模块            [图] [···] │
│ 3 Agents · 2/5 子任务完成             │
├──────────────────────────────────────┤
│                                      │
│ 🔵 架构师                             │
│   ✅ 分析需求 · ✅ 设计接口            │
│                                      │
│ 🟢 开发者                    [展开 ▼] │
│   ⏳ 实现登录端点 (auth/login)        │
│                                      │
│ ⚪ 测试员                             │
│   ··· 等待 API 接口完成              │
│                                      │
├──────────────────────────────────────┤
│ ████████████░░░░░░░░░░░░░░ 40%      │
└──────────────────────────────────────┘
```

**内容结构：**

| 区域 | 内容 |
|------|------|
| 头部 | 任务标题（编排器生成的一句话摘要）+ 快捷操作 |
| 副标题 | Agent 数量 + 子任务完成比 |
| Agent 列表 | 每个 Agent 一行：色点 + 角色名 + 当前步骤 + 状态图标 |
| 进度条 | 整体进度百分比 |

**可交互元素：**

| 元素 | 位置 | 点击后行为 |
|------|------|-----------|
| [图] 按钮 | 头部右侧 | 切换到图视图 |
| [···] 菜单 | 头部右侧 | 操作菜单：停止任务 / 重新规划 / 复制任务 ID |
| 角色名 | Agent 行 | 点击展开该 Agent 的详细输出 |
| [展开] 按钮 | Agent 行右侧 | 展开显示 Agent 的实时输出流 |

### 状态 3：检查点

```
┌──────────────────────────────────────┐
│ ⚠️ 阶段审视                    [图]  │
├──────────────────────────────────────┤
│                                      │
│ 架构师完成了 API 设计：               │
│ • POST /auth/login                   │
│ • POST /auth/register                │
│ • POST /auth/refresh                 │
│                                      │
│ 编排器建议进入下一阶段：开发者开始     │
│ 实现、测试员开始编写测试用例。         │
│                                      │
├──────────────────────────────────────┤
│ [✅ 继续]  [✏️ 调整方向]  [⏹ 停止]   │
└──────────────────────────────────────┘
```

**可交互元素：**

| 按钮 | 行为 |
|------|------|
| 继续 | 批准编排器建议，继续执行 |
| 调整方向 | 弹出输入框，用户可以给编排器补充指令 |
| 停止 | 终止整个任务 |

设计意图：用户「管理团队」的核心时刻——像经理在关键节点审批团队工作。

### 状态 4：已完成

```
┌──────────────────────────────────────┐
│ ✅ 实现用户登录模块            [图]  │
│ 3 Agents · 5/5 子任务 · 用时 2m 34s  │
├──────────────────────────────────────┤
│ ✅ 架构师 · ✅ 开发者 · ✅ 测试员     │
└──────────────────────────────────────┘
```

- 卡片收缩为最简形式
- 点击可展开查看完整结果

### 状态 5：失败/异常

```
┌──────────────────────────────────────┐
│ ❌ 任务异常                    [图]  │
├──────────────────────────────────────┤
│                                      │
│ 开发者 在"实现登录端点"步骤失败：     │
│「无法读取文件 auth_config.yaml」      │
│                                      │
├──────────────────────────────────────┤
│ [🔄 重试]  [✏️ 调整后继续]  [⏹ 放弃] │
└──────────────────────────────────────┘
```

| 按钮 | 行为 |
|------|------|
| 重试 | 从失败点重新执行 |
| 调整后继续 | 弹出输入框，用户提供额外信息或修正方向 |
| 放弃 | 终止任务，保留已完成部分 |

### Agent 详情展开

点击 Agent 行的 [展开] 后，在卡片内部展开详细信息：

```
┌─ 开发者 ──────────────────────────────┐
│ ⏳ 实现登录端点                        │
│                                       │
│ 工具调用：                             │
│   • file_write: auth_service.py       │
│   • file_write: auth_router.py        │
│   • terminal: pip install pyjwt        │
│                                       │
│ 当前输出：                             │
│   「正在实现 JWT token 生成和验证...」  │
│                                       │
│ [-- 25 tokens/s --] [-- 1.2s --]      │
└───────────────────────────────────────┘
```

### 出现时机规则

| 场景 | 任务卡片行为 |
|------|-------------|
| 简单任务（单 Agent） | **不出现**，直接流式输出，体验同 ChatGPT |
| 多 Agent 任务 | **自动出现**，嵌入在对话流中 |
| 任务完成 | **收缩**为一行摘要，不占大量空间 |
| 用户发新消息 | 上一个任务卡片自动折叠 |

## 四、辩论/审查范式 UX 设计

MVP Day 1 支持辩论/审查范式（DECISIONS §21），需要专门的 UX 设计来区别于普通并行分工。

### 辩论与并行的视觉区分

| 维度 | 并行分工 | 辩论/审查 |
|------|---------|----------|
| 任务卡片标题 | "并行执行中 · 3 个 Agent" | "辩论进行中 · 正方/反方" |
| Agent 标签 | 中性（Agent A/B/C） | 对立标签（正方✅ / 反方❌ 或 方案A / 方案B） |
| 输出展示 | 各自独立折叠区 | **并排对比布局**（左右分栏） |
| 汇总阶段 | "合并结果" | "编排器比较评审" |
| 检查点动作 | 继续/调整/停止 | 采纳方案A / 采纳方案B / 要求补充论证 / 用户自行判断 |

### 聊天视图中的辩论卡片

辩论范式在聊天流中显示为特殊的任务卡片：

```
┌─────────────────────────────────────────┐
│ ⚖️ 辩论进行中 · [主题描述]                │
│                                          │
│ ┌──────────────┐  ┌──────────────────┐   │
│ │ ✅ 正方       │  │ ❌ 反方           │   │
│ │ Agent-1      │  │ Agent-2          │   │
│ │ ████████ 75% │  │ ██████████ 100%  │   │
│ │              │  │                  │   │
│ │ [展开查看]   │  │ [展开查看]       │   │
│ └──────────────┘  └──────────────────┘   │
│                                          │
│ ⏳ 等待编排器比较评审...                   │
└─────────────────────────────────────────┘
```

展开后显示各方论点摘要（来自 Agent 输出的 summary 字段）。

### 辩论完成后的结果展示

```
┌─────────────────────────────────────────┐
│ ⚖️ 辩论已完成 · [主题描述]                │
│                                          │
│ 📋 编排器评审结论：                        │
│ ┌─────────────────────────────────────┐  │
│ │ 采纳 ✅ 正方 方案，理由：...           │  │
│ │                                     │  │
│ │ 正方优势：...                        │  │
│ │ 反方参考点：...                      │  │
│ └─────────────────────────────────────┘  │
│                                          │
│ [查看正方完整论述] [查看反方完整论述]        │
└─────────────────────────────────────────┘
```

### 图视图中的辩论拓扑

辩论在图视图中表现为特殊的 DAG 结构：

```
         [编排器规划]
          /       \
    [正方 Agent]  [反方 Agent]    ← 并行节点，不同颜色标记
          \       /
       [比较评审节点]            ← 特殊节点样式（天平图标）
            |
        [最终输出]
```

- 正方节点：绿色边框
- 反方节点：红色/橙色边框
- 比较评审节点：金色/黄色，天平图标
- 连接线样式与普通依赖边一致

### 检查点交互

辩论完成后的检查点卡片提供辩论特有的操作：

| 操作 | 说明 |
|------|------|
| 采纳方案 A | 以正方结论为最终输出 |
| 采纳方案 B | 以反方结论为最终输出 |
| 要求补充论证 | 向编排器发补充指令，可能触发新一轮辩论 |
| 用户自行总结 | 用户输入自己的综合判断 |

### 辩论 SSE 事件处理

辩论的 SSE 事件与普通多 Agent 完全一致（run_plan/run_started/run_completed 等），区别在于：
- `run_plan` 的 plan 结构中 `output_strategy.merge_type = "compare"`
- 前端根据 merge_type 选择不同的 TaskCard 渲染模式（并排 vs 独立折叠）
- 比较评审节点的 `run_completed` 包含结构化的对比结论

### 待定事项

- 多于 2 方的辩论（如三角辩论）的 UX 表达
- 辩论过程中的实时"观点对比"动画

## 五、图视图设计

通过「查看图」按钮或快捷键切换，展示完整的任务图结构。

### 图的结构层次

```
                    ┌─────────┐
                    │  用户输入  │  ← 顶部入口节点
                    └────┬────┘
                         │
                    ┌────┴────┐
                    │  编排器   │  ← 中枢节点
                    └┬───┬───┬┘
                     │   │   │
              ┌──────┴┐ ┌┴────┐ ┌┴──────┐
              │Agent A│ │Agent B│ │Agent C│  ← 执行节点
              └───┬──┘ └──┬──┘ └──┬───┘
                  │       │       │
                  └───────┼───────┘
                          │
                    ┌─────┴────┐
                    │  汇总输出  │  ← 终点节点
                    └──────────┘
```

### 节点类型

| 节点类型 | 形状 | 默认尺寸 | 色彩基调 | 图标 |
|----------|------|----------|----------|------|
| 用户输入 | 圆角矩形 | 180×60 | 蓝 (#3B82F6) | 用户头像 |
| 编排器 | 六边形 | 80×80 | 金 (#F59E0B) | ⚙️ 齿轮 |
| Agent | 圆角卡片 | 160×80 | 动态色（角色相关） | 角色图标 |
| 检查点 | 菱形 | 60×60 | 橙 (#F97316) | ⚠️ |
| 汇总 | 圆角矩形 | 180×60 | 绿 (#10B981) | ✅ |
| 工具调用 | 小圆点 | 24×24 | 灰 (#6B7280) | 工具图标 |

### Agent 节点内容

```
┌─────────────────────┐
│ 🟢  开发者           │  ← 状态指示灯 + 角色名
│ 实现登录端点        │  ← 当前任务
│ ██████░░░░ 60%     │  ← 进度条
└─────────────────────┘
```

### 节点状态与视觉变化

| 状态 | 指示灯色 | 边框 | 背景 | 动画效果 |
|------|----------|------|------|----------|
| 等待中 | ⚪ 灰 | 虚线边框 | 半透明 | 无 |
| 执行中 | 🟢 绿 | 实线 + 发光 | 不透明 | 边框脉冲发光 |
| 已完成 | ✅ 绿勾 | 实线 | 不透明 | 完成打勾动画 |
| 失败 | 🔴 红 | 红色边框 | 淡红背景 | 轻微抖动 |
| 暂停 | 🟡 黄 | 黄色边框 | 不透明 | 边框闪烁 |

状态过渡动画：
- 等待 → 执行：节点从半透明淡入为实体，边框亮起，300ms ease-out
- 执行 → 完成：进度条填满 → 打勾图标动画 → 边框变绿，500ms
- 执行 → 失败：节点轻微抖动 + 变红，200ms

### 边（连接线）类型

| 边类型 | 线型 | 箭头 | 动画 | 含义 |
|--------|------|------|------|------|
| 任务分发 | 实线曲线 (bezier) | 有 | 粒子流动 | 编排器分配任务给 Agent |
| 数据传递 | 虚线曲线 | 有 | 慢速粒子流 | Agent 间传递中间产物 |
| 检查点回报 | 点线 | 反向箭头 | 无 | Agent 报告结果给编排器 |
| 汇总 | 多对一实线 | 有 | 粒子汇聚 | 多 Agent 结果汇聚 |
| 依赖等待 | 灰色虚线 | 无 | 无 | B 等待 A 完成 |

边的状态：
- 活跃（数据正在流动）：粒子动画 + 线条发光
- 完成（已传递完毕）：实线，淡绿色，无动画
- 挂起（依赖未满足）：灰色虚线
- 异常（传递失败）：红色虚线 + ❌ 标记

粒子流动动画参数：
- 粒子大小：4-6px 圆点
- 粒子速度：约 2s 完成一次流动
- 粒子间距：同时 3-5 个粒子在一条边上
- 粒子颜色：与源节点颜色一致，带拖尾效果

### 布局算法

**默认布局：分层树形（Top-Down Hierarchical）**

```
层 0：        [用户输入]
层 1：         [编排器]
层 2：    [Agent A] [Agent B] [Agent C]
层 3：         [检查点]
层 4：    [Agent A'] [Agent D]
层 5：         [汇总]
```

算法参数：
- 层间距：120px
- 同层间距：80px
- 边类型：Bezier 曲线，控制点在垂直方向 50% 位置

选择树形布局的理由：
1. 与「组织架构图」心智模型一致
2. 任务流向（上→下）符合自然阅读顺序
3. 不同"层"代表不同执行阶段，时序清晰
4. 实现简单，性能好

**备选布局（用户可切换）：**

| 布局 | 适用场景 | 视觉效果 |
|------|----------|----------|
| 分层树形（默认） | 线性工作流、组织架构感 | 整齐、正式 |
| 左右流 | 长流程、管道式任务 | 像流程图 |
| 径向布局 | 编排器为中心的思维导图风格 | 发散性思维 |
| 力导向 | 自由探索、复杂依赖关系 | 有机感 |

用户可通过工具栏的「布局」下拉菜单切换，切换时用 spring 动画平滑过渡。

## 七、设计原则总结

| 原则 | 说明 |
|------|------|
| 零门槛入门 | 新用户看到的就是普通聊天，不会被面板或图吓走 |
| 渐进式揭示差异 | 任务卡片 → 详情面板 → 图视图，三级渐进 |
| 简单任务零噪音 | 单 Agent 时无任务卡片、详情面板可关，体验同 ChatGPT |
| 只在关键点求交互 | 检查点和异常时才需要用户操作 |
| 视图切换无损 | 切到图视图再回来，对话流状态不变 |
| 口碑传播点 | 图视图的截图非常适合社交媒体传播 |
| 页面自治 | 各页面自定义布局，全局壳不强制面板结构 |

## 八、技术选型

### 推荐方案：React Flow 为基座 + 自定义动画层

#### 技术栈组合

```
图视图技术栈：
├─ React Flow (xyflow)     → 核心图引擎（节点/边/交互）
├─ elkjs / dagre           → 自动布局算法
├─ Framer Motion           → 节点状态切换动画
├─ SVG animate / CSS       → 边上粒子流动
└─ Radix UI / custom       → 右键菜单、tooltip
```

#### 分层职责

| 层 | 技术 | 职责 |
|---|---|---|
| 图引擎层 | React Flow | 节点布局、边连接、缩放平移、选中 |
| 动画层 | Framer Motion + SVG | 节点入场/退场、状态切换、边粒子流 |
| 布局层 | elkjs | 计算节点坐标，支持多种布局算法 |
| 业务层 | 自写 hooks | 状态管理、WebSocket 实时更新、操作分发 |

#### 选型理由

1. **与技术栈完美契合**：已确定 React，React Flow 是原生 React 库，自定义节点就是普通 React 组件
2. **开发效率最优先**：图视图是补充视图（不是主界面），不值得花几个月自研
3. **节点数小**：场景不超过 50 节点，React Flow 完全能处理
4. **粒子动画可增量实现**：通过自定义边组件，用 SVG animate 实现
5. **渐进式复杂度**：初期用基础功能快速出效果，后续逐步加动画

#### 不选 D3 的理由

- 与 React 的 DOM 管理模型冲突
- 节点内容复杂（进度条、多行文字、状态指示器），SVG 手工绘制极其痛苦
- React 组件的可复用性、状态管理在 D3 中全部丢失
- 我们的动画需求用 SVG animate + CSS 完全能实现

#### 不选自研画布的理由

- 图视图是补充视图，不是产品的核心壁垒（编排器才是）
- 自研画布引擎需要 1-2 个月，资源错配
- 50 节点规模不需要 Canvas/WebGL 的极限性能

#### 风险与缓解

| 风险 | 缓解 |
|------|------|
| React Flow 更新破坏性变更 | 锁定版本，抽象 adapter 层 |
| 粒子动画性能 | 用 CSS animation 而非 JS，减少 re-render |
| elkjs 布局算法慢 | Web Worker 中计算，不阻塞主线程 |
| Pro 功能付费 | 评估是否需要，大多数功能 MIT 已足够 |

### 性能约束

| 指标 | 目标值 | 说明 |
|------|--------|------|
| 节点数 | ≤ 50 | 单个任务不应超过 50 个节点 |
| 帧率 | ≥ 60fps | 动画流畅 |
| 首屏渲染 | < 200ms | 切换到图视图的感知延迟 |
| 布局计算 | < 100ms | 动态添加节点时重新布局 |

## 九、文件交互设计 ✅ 已确定

> 详细的本地文件系统设计见 [`前端技术选型.md`](前端技术选型.md) §八；本节只覆盖 UX 层面。

### 9.1 文件树交互

**设计原则**：一棵以本地授权目录为根的树。不是「云端/本地两平级源」上下分段——后者已否决（心智割裂 + 主次写死）。

| 交互 | 行为 |
|------|------|
| 添加文件夹 | 选本地目录 = 立即成为一个项目（建云端身份一步到位） |
| 展开目录 | 懒读子项 + 启动 watch；折叠即停止 watch |
| 内联改名 | 就地 input，回车/blur 提交，Esc 取消 |
| 拖拽移动 | 源节点 dragstart 带元数据，落点校验（非原父/非自身子树） |
| 右键菜单 | 根节点与普通节点分开（根有「设为项目」「连接/断开」等） |

### 9.2 用户旅程：本地文件协作

1. **连接**：点「添加文件夹」→ 选目录 → 文件夹就绪，AI 可读写
2. **协作**：对话中 AI 默认在当前文件夹工作——本地找→读→产出
3. **延续**：关应用再开，文件夹仍记得本地目录
4. **不可用**：盘没插/目录被删 → 提示「未连接」+ 重新连接/重选/只读历史

### 9.3 审批 UX（写操作）

| 状态 | 体验 |
|------|------|
| 只读 | AI 能读不能写；尝试写时引导开启 |
| 可写 | 写前弹审批（可「本轮内都允许」批量放行） |

批量场景依赖 §三工具审批三态策略（`grantable` 级别），避免 N 次文件写 = N 次弹窗。

### 9.4 对话落点的 UX 表达

| 语境 | 用户看到什么 |
|------|------------|
| 已选文件夹 | 输入框「文件夹」pill 显示项目名 |
| 未选但 Agent 已自动落点 | pill 显示"自动工作目录"（标「自动」），提供「固定为文件夹」一键升级 |
| 无桌面 | 不挂写工具；真要产物须声明显式出口 |

### 9.5 隐私承诺（面向用户的表述）

- **默认不留存**：未备份的文件内容不进云
- **在途可用**：AI 读文件时正文临时发给模型（同用户贴代码给 AI）
- **备份/分享 = 显式上传**：不自动同步；操作前文案须明示「这一步会把文件上传到云」

## 十、详情面板与委派展示 ✅ 已确定

> 物理参数（宽度/拖拽/持久化）和完整 Tab 类型定义见 [`前端技术选型.md`](前端技术选型.md) §五「对话页详情面板」。本节聚焦 UX 定位和交互原则。

### 10.1 详情面板定位

聊天右侧的详情面板 = Agent 执行的「点开看详情」查看器。聊天气泡只放紧凑信号（思考摘要 / 任务状态 / 工具卡 / 协作图），点击元素后右侧推入完整详情。

**核心价值**：Multi-Agent 一次交互信息量大，正文保持简报、细节按需点开。

### 10.2 Tab 类型与入口

| Tab 类型 | 内容 | 入口（点击触发） |
|---|---|---|
| `task-progress` | 总进度条 + 所有 Agent 状态列表 | 任务卡片进度区域 / 消息上的进度入口 |
| `run-detail` | 单 run 完整详情（任务/思考/输出/工具/子任务/资源） | task-progress 中点击 Agent 行 / 任务卡片 [展开] |
| `task-graph` | React Flow 缩略 DAG + [最大化] 进入全屏图视图 | 任务卡片 [图] 按钮 / 多 Agent 任务自动打开 |
| `reasoning` | LLM reasoning 全文（流式 Markdown） | 气泡顶部「思考」折叠条 |
| `conversation-artifacts` | 本对话所有产物聚合视图 | 对话级产物入口 |

### 10.3 关键行为

| 决策 | 取值 | 理由 |
|---|---|---|
| Tab 管理模式 | 动态打开/关闭（非固定 Tab 栏） | 用户只看关心的，不强制所有 Tab 始终存在 |
| 标签上限 | 6，超出淘汰最旧 | 防无限堆积 |
| 持久化 | 仅 `open` + `width`；Tab 集会话级 | Tab 是临时工作态 |
| 多开 | 多个 `run-detail` 可并存对比 | 否决每次覆盖 |
| 数据获取 | Tab 只存引用（指针），详情从 run 树现取 | 单一数据源 |
| 下钻导航 | 子任务点击开新 Tab | 无限层级下钻，各 Tab 独立 |
| 自动打开 | 多 Agent 任务启动时自动打开 task-progress | 单 Agent 不打开（零噪音） |

### 10.4 委派展示统一

单一可视化 + 单一数据模型覆盖所有委托场景：

| 统一项 | 说明 |
|---|---|
| `CollaborationGraph`（task-graph Tab） | 一张图同时表达委派树和 `depends_on` 依赖 |
| `AgentRun` 模型 | 编排步骤与委派子 Agent 共用同一节点类型 |
| `run_*` 事件族 | 前端不再需要拼接两路事件流 |
| 时间线渲染 | 过程元素归属于产生它的消息，跟随时间线位置渲染 |

**被否决**：前端按 N 隐藏其一（状态仍分叉）；保留双协议只在前端合并（双写漂移）。

### 10.5 聊天紧凑化原则

1. **inline 只做信号展示**——思考折叠条、任务状态、工具卡（多次调用默认折叠）、协作图
2. **面板承担完整详情**——思考全文、run 全文 + 工具 IO + 用量
3. **失败 / 运行中强制展开**（错误绝不藏）
4. **图 Tab 做缩略预览**——详细交互进全屏图视图

## 十一、Agent 可发现性 ✅ 已确定

### 可发现性是固有属性

可发现性是 Agent 的固有属性，单独成轴，不从「被哪个团队/竞技场引用」反推。三态模型：

| 可发现性 | 含义 |
|---|---|
| `public` | 上架：进入探索 / 选择器 / 搜索 / 智能路由候选池 |
| `unlisted` | 后台构件：不进发现面，但按 id 可直达 |
| `private` | 仅创作者可见 |

### 设计原则

- **单一谓词**：一处过滤 `visibility=public`，自动覆盖全部发现入口
- **`is_featured` 解耦**：回归「编辑精选」本职，与可见性正交
- **缺省 public**：历史数据、用户自建 Agent 默认可见，避免误隐藏
- **组件型默认 unlisted**：团队成员、队长、竞技场角色自动设为 unlisted

**被否决**：把 Arena 角色拆成独立实体——违背 Multi-Agent First，破坏 Arena 槽位可插拔。
