# 工作流固化与复跑

> **主循环归属**：[组](/docs/01-产品/产品定位与品牌.md)——把一次成功的组队固化下来复用。复跑时不再由 CEO 判轻重组队，改按图组。
>
> 站立任务 / Webhook 怎么触发它 → [后端架构 · 站立任务](/docs/02-架构/后端架构.md#站立任务--webhook)。

本文只写代码看不出来的那部分：入口为什么在对话里、复跑到什么程度算「同一件事」、哪些形态有意不接、`definition` 归谁所有。

## 一、主入口在对话里，不在画布

工具箱里从零画一张 DAG 要求用户先想清楚分几步、谁做什么、怎么依赖——这是**编排税**，与「说一句话就开工」的主循环相悖。真实的动机产生在另一刻：**一轮协作刚跑完、用户觉得这次拆得不错**。

所以入口挂在完成态状态条上，画布退居**事后微调**工具。

判据是结构化的（完成态 + 顶层队员 ≥ 2），不猜用户意图：单队员和纯对话回合没有可复用的分工，硬停的回合也不是「满意的一轮」。

## 二、快照带走什么

固化的是**最后一条顶层 `plan_snapshot`**——中途 CEO adjust 过的拓扑天然被它吃掉，用户在关卡处的 steer 文本并进任务描述。带走「谁做什么、先后依赖、交付要求」，不带走模型选择、思考档、工具与检索预算。

丢什么逐条写进工作流说明里，不拦下保存。这是[执行引擎 · 可用性诚实性](/docs/03-AI核心/执行引擎架构设计.md)的同一口径：能做多少说多少，不假装完整。

**嵌套子团队不进画布**：再派单的 worker 会把自己的子计划记进同一条 turn journal，靠节点 `depth` 区分顶层与嵌套。

## 三、复跑 ≠ 原轮，这是结构性的

工作流走 mechanism-direct，**CEO 不在场**（不是被 `topology_lock` 挡住——没有 react 循环，`replan` 永远不会被调用；锁只是给仍可能摸到 plan 的旁路兜底）。所以复跑拿到的是原轮**最终形态的静态化石**：同样输入若跑出不同的中间产物，没有任何机制能再改拓扑，用户只能在 `human_gate` 处做文本 steer——**能改内容，改不了拆法**。

### 为什么不让 CEO 回到复跑现场

**否决：复跑时带 CEO，让工作流当「起手建议」而非死图。** 否决理由是它误解了需求。用户说「上次那样很好，再来一次」，真正要的是**换个输入还这么拆**，不是复现当时那些临场判断的随机性——如果每次跑出来结构都不一样，那反而不叫「再来一次」。

这里有两种动机，产品上要分清：

| 动机 | 用户要什么 | 谁服务它 |
|---|---|---|
| 「这个流程固定下来」（每周一出简报） | 确定性：结构一致、成本可预期 | 锁拓扑 + 无 CEO，正对 |
| 「再来一次那样的协作」 | 换个输入还这么拆 | **参数化**（§四），不是 CEO |

把第二种动机误读成「要自适应」，就会得出「该带 CEO」的错误结论。

## 四、参数化：槽位与它的时机

从一轮固化出来的工作流，任务描述里写死的是那一轮的具体主题（「调研 Notion 的协作功能定价」）。没有参数化，它的复用性天生比官方模板差——用户下次想换个对象，得进画布逐个节点手改。

**槽位的默认值就是原轮的原值**。所以「原样再跑」与「换个主题跑」是同一套机制：跑一次时预填默认值，不动就是逐字复现原轮，改了才带覆盖值；站立任务用默认值跑，正对「每周同一主题出简报」。

### 抽槽挂在「跑一次」，不在保存路径

**否决：保存时同步抽槽。** 三条理由，第一条最轻：

1. 用户点保存最长要等一次模型调用（慢）；
2. 抽槽失败就**永久**没有槽位，用户既不知情也没法补；
3. 抽出什么用户在保存那一刻**看不见**，质量不可见。

根子上是时机错了。用户点保存时的心智是「这轮不错先存下来」，他还没想到换主题；**真正需要槽位的时刻是第二次要用它**、看到任务里写死着上一轮主题的时候。所以抽槽移到「跑一次」路径按需做一次：抽出来的参数表当场摆在用户面前预填原值让他过目，抽错能改，失败就退化成按原文直接跑、下次还能再试。

这与「主入口搬进对话」是同一条原则：**把工作放在需求产生的那一刻，而不是提前猜**。

只对固化来源抽——官方模板复制来的本来就带槽位，手画的由用户在画布上自己管。

### 模型只有指认权，没有改写权

抽槽是唯一让模型碰用户任务文本的地方，所以它被约束成：模型只能报**原文里逐字出现的片段**，代码自己去找那段做替换，找不到就丢掉这个槽位；替换完还要用默认值正向展开一遍与原文逐字比对，对不上整份作废。

这保证了「不填任何覆盖值地跑一次」必然复现原轮——参数化不会悄悄改写用户的任务。

## 五、辩论有意不进画布

**否决：支持把一场辩论固化成工作流。**

**需求层**：辩论天然绑定一个具体命题，「选 Postgres 还是 MySQL」辩完就结束，没有人每周辩同一个命题——而工作流的全部价值建立在可重复之上。辩论里真正可复用的是**形态**（红队 / 正反 / 圆桌、轮次、取证要求），它的正确载体是带命题槽位的官方模板，不是「从一轮固化」。工作流对辩论能提供的三样东西——复用拆法、定时跑、精确控形态——逐条都很弱。

**技术层**三条各自独立，补任何一条都不够：

1. 辩论回合**不写 `plan_snapshot`**（那只有 delegate 路径写），供给侧没有数据；
2. 辩手节点 `depth = 2`，过不了画布的顶层过滤；
3. 辩论的身份（命题、形态、轮次策略、裁判、庭前取证）从来不在 plan 层，而在 `DebateConfig` 与主持人循环里。

所以现状是**诚实拒绝**：纯辩论回合不出「存为工作流」按钮。判据是从队员人头里减去辩论席位，不是 `isDebate` 一刀切——混合回合（既派了单又打了辩论）服务端存得下 delegate 那半，要继续出按钮，只是会在工作流说明里**明写辩论环节不在快照内**。不写这句就是静默变质：用户以为存下了那场精彩辩论，实际存的是它前面的调研。

## 六、`definition` 归谁所有

同一个形状栽过四次——**有人拿一份多方共享的 JSON 文档，按自己知道的字段把它重建了一遍**，别人加的字段就被静默抹掉，且没有任何信号。所以所有权必须写下来：

| 内容 | 归属 | 规则 |
|---|---|---|
| 固化来源 | 服务端权威 | 独立列，只在创建时写一次；更新路径不收这个参数 |
| `nodes` / `edges` / `slots` | 用户画布内容 | 服务端**只校验不重建**，未知字段原样透传 |

来源不放在 `definition` 里，除了防丢，更因为客户端整份覆盖那份 JSON——放里面它既能被删，也能被**伪造**，让手画的工作流冒充固化来源去骗抽槽。

推论：给画布加字段不需要改服务端白名单；给工作流加服务端权威元数据则必须走独立列，不许塞进 `definition`。

任务描述里的占位符字符集是**前后端逐字一致**的契约。认得比服务端多，画布上就会把字面量画成变量胶囊而跑出来不替换。

## 七、跨端

工作流整组面**有意只做桌面**（画布、CRUD、直跑、槽位）。手机端裁决登记在 `apps/mobile/src/protocol/parity.ts`，`pnpm conformance` 会盯着——新增桌面交互面必须给出手机对等裁决。
