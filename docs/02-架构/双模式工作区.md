# 双模式工作区（云 + 本地）

> **状态**：✅ 项目即工作区（Folder 必绑 local/cloud）+ 项目内会话共享 `folder:<id>` + 裸聊默认云 `conv:<id>` scratch（桌面显式本机草稿仍可落本地 `conversations/<id>/`）+ 清单稀疏化 + 系统文件隐藏 + `WorkspaceBackend`（云/本地）+ 绑定路由 + 文件进出/快照/交接/云产物一键导出已落地。多 worker 化：锁/审批门/通道/handoff 现为进程内态，多机需 Redis + durable queue。
>
> **定位**：让「AI 对话能选文件夹、并在该文件夹工作」，一套分层同时支撑**云**与**本地**两种**平等**模式——**不给用户云/本地开关，模式跟着「文件在哪」自动走**（§六）。
>
> → 见代码：`apps/server/agentcore/workspace/`

---

## 一、需求推导结论：两种模式平等

- **内核需求**：给每次协作一个**持久、可累积的项目空间**——多 Agent 在同一张「桌子」上靠文件协作。「在不在本地磁盘」是第二层偏好，非内核。
- **云模式（服务端托管）= 零前提的起点**：打开即用、不暴露整块磁盘；并行团队同台协作，天然可观测、可隔离。
- **本地模式（桌面执行，对标 Cursor）= 平等的另一种，后做**：开发者内环（改真实本地仓）。
- **不给用户云/本地开关**——模式跟着「文件在哪」自动走（§六）；「云优先 / 本地优先」只是构建顺序。

## 二、`WorkspaceBackend` 抽象

沿用项目「Protocol + 实现 + 工厂」同构范式（同 `LLMProvider` / `SandboxProvider` / `SearchBackend`），引擎与工具只对接口编程：

- **接口**：`read / write / list / replace / grep / execute / read_lines / list_tree` + `location`(server·local) + `root_label`（相对路径渲染、不暴露绝对路径）。`read_lines` 供 `file_read` 行号范围；`list_tree` 供 `file_list` 递归树。
- **签名一次到位**：P0 即钉死结构化结果类型（`DirEntry` / `ReplaceOutcome` / `GrepResult` / `ReadLinesResult` / `TreeResult` 等），失败走类型化异常 `WorkspaceError` 子类（`OutsideWorkspace` / `PathNotFound` / `NotAFile` / `NotUTF8` / `AmbiguousMatch` …），工具层捕获后映射回原报错文案（用户侧报错零变化）。
- **护栏 1·瘦接口**：持久化（snapshot/restore）**不进 backend**——是回合级存储策略（轴3），归独立 `StorageProvider`，由 service 在 run 前后调（§三、§四）。backend 只管「文件 + 执行」这对**必须同源**的能力（一个 backend = 一个执行平台）。
- **为何 P0 就引入抽象**：本地模式（B）是**已承诺、必然建完**的路线；接口先行（项目 house style）使新增 `LocalWorkspace` 时工具与引擎零改动。
- **唯一接缝**：`ToolContext.workspace_dir: Path` → `ToolContext.backend: WorkspaceBackend`，工作区文件工具（`file_ops` 等）+ `grep` + `code_execute` 与引擎退化薄壳。`code_execute` 收编进 `backend.execute`（`ServerWorkspace` 内委托 `SandboxProvider` + 带 cwd），顺修「代码与文件不在同一目录」的潜伏 bug。

## 三、三正交轴与「本地默认云储存」判定

| 轴 | 取值 |
|---|---|
| 轴1 执行位置 | server / local |
| 轴2 文件源头 | server dir / local dir |
| 轴3 持久化 | S3 快照 / 仅本地盘 / 实时同步 |

「云 / 本地模式」是在**轴1+轴2** 选一整套。用户提的「本地默认云储存」= `轴1=local、轴2=local、轴3=cloud`——**不是第三种模式，而是 LOCAL backend 的存储策略**：

- ✅ **接受**快照 / 交接语义（git-push 式）：本地是唯一真相源，按需经 `StorageProvider` 快照到 S3，用于备份 / 跨设备 / 把活交给云端团队。
- ❌ **拒绝**实时双向同步（Dropbox 式）：双真相源 + 冲突地狱，在「并行 Agent 团队并发写」下尤其致命。

## 四、两个 Backend 实现

| Backend | 文件在哪 | 执行在哪 | 模式 | 传输 |
|---|---|---|---|---|
| `ServerWorkspace` | 服务端：项目会话共享 `<data_dir>/workspaces/<user_id>/<folder_id>/`；裸聊每对话 scratch `…/<user_id>/conv/<conversation_id>/` | 服务端（复用 `SubprocessSandbox`） | 云 | 同进程 |
| `LocalWorkspace` | 用户真实本地目录（绑定在**对话** scratch 列：`local_root_id` + `local_subpath`；裸聊空 subpath → `conversations/<conversation_id>/`） | 桌面端（op 路由到 Electron） | 本地 | 泛化审批门接缝 |

`LocalWorkspace` 的传输**不另造**：把 `runtime/approvals.py` 的「服务端挂起 `asyncio.Future` + 客户端 HTTP 回填」泛化成一条工具执行通道（`WorkspaceChannel`）——服务端挂起 + `workspace_op_required` SSE + `POST …/interactions/{id}`（kind=client_tool，§8.2 统一挂起原语）resolve 回填；桌面 `main/fs/workspace/dispatch.ts`（`executeWorkspaceOp`）处理全 op（含 `READ_LINES` / `LIST_TREE` / `COPY`）、渲染端 `workspaceOps.ts` 收 SSE→IPC→回填。每个 op 串行路由、回传结构化结果或同款 `WorkspaceError`，故工具 / 引擎不动。Sidecar 模式文件 op 直接复用 `ServerWorkspace`（不经 channel）。

**文件删除默认可逆 ✅**：`WorkspaceBackend.delete(permanent=False)`——`LocalWorkspace` 通道桌面 `shell.trashItem`（系统回收站；失败则回落工作区软删区）；`ServerWorkspace`（云端 + sidecar）移入 `.agentcore/trash/<id>/` 并写 `meta.json`（`original_path` / `deleted_at` / `is_dir`）。`permanent=true` 硬删。区外（W3）只读边界不变——不引入任何区外写能力。另：`copy` op 支持二进制与目录树；工具面另见 `file_copy` / `mkdir` / `file_batch`（[工具与能力系统](/docs/03-AI核心/工具与能力系统.md)）。

**后台进程 op（终端 M1）✅**：`WorkspaceOp` 扩 `process_start/read/stop/list` 四值，供 worker-only `terminal` 工具把长时进程（dev server 等）交**桌面主进程**代持（`main/process-service.ts`：spawn / 环形 buffer ~1MB / 杀进程树 / 按对话记账 / 应用退出全停）。两种本地形态同一条通道：LocalWorkspace 复用自己的 channel；**sidecar 例外走通道**（`workspace_channel_for_tools`——sidecar 文件 op 本机直跑，但进程必须交主进程代持，sidecar 生命周期短于 dev server）。sidecar 通道无桌面根注册表（`root_id` 恒空），renderer `workspaceOps.ts` 对 process op 按会话绑定补齐容器根（与 sidecar respond 寻址同构）并把 scratch 子路径前缀进 `start` 的 cwd；`conversation_id` 亦在该处注入（不进公开工具 schema）。进程输出直播是本机 IPC（`process-contract.ts`，push 仿 sidecar event），**不进跨端协议、零新 SSE / journal 事件类型**。

**用户交互 shell（终端 M3）✅**：桌面主进程另立 `pty-service.ts`（node-pty + 环形 buffer，与 process-service 并列）；右坞「你的终端」经独立 `pty-contract` IPC。**零新工具 / 协议**：`process_list` / `process_read` 融合用户 pty（name=`用户终端 #N`、read strip ANSI）；`process_stop` 对用户终端 typed 拒绝（仅用户可关）。→ 见代码 `main/pty-service.ts`、`main/fs/workspace/process.ts`。

## 五、落地能力现状

| 能力 | 现状 |
|---|---|
| **接缝 + 云模式** ✅ | `WorkspaceBackend`（读写 / 列举 / 检索 / 执行等约二十个协议方法，含 `read_lines`/`list_tree`/`index_files`/`code_search`）+ `ServerWorkspace`；`ToolContext.backend`；文件工具 + `grep` + `code_execute` 改薄壳；`StorageProvider` 快照/恢复/下载；文件进出 + `git clone` + 附件驻留（含**引用即驻留** + **分流预解析**：区外/二进制由桌面主进程复制进 `attachments/`，云占位短超时失败；docx/pdf/pptx/txt 等入库时 markitdown 抽文本写 `*.md` 副本，xlsx/csv 不预解析；扫描 PDF 首版不做 OCR、给降级提示；**会话级目录只读授权** W3：`external/<别名>/` 多根只读路由，写拒绝；不做无授权区外直读）+ 保留期清理 |
| **本地模式** ✅ | `LocalWorkspace` 经 `WorkspaceChannel` 全 op 路由桌面；`local_root_id` 绑定 API + 模式条 UI；worker 审批门透传（P2d） |
| **后台进程（终端 M1）** ✅ | `terminal` 工具四 subcommand 经通道 `process_*` op 交桌面主进程代持；跨回合存活、对话删除 / 应用退出终止；右坞「终端」tab 观测 + 停止 |
| **用户交互 shell（终端 M3）** ✅ | node-pty + xterm；单对话上限 3；纳入 `process_list`/`read`、拒 `process_stop`；删对话 / 退出全杀 |
| **本地→云交接** ✅ | 三段式：打包上传 → 云端 autonomous 跑团队 → diff/三方判定/回写（`HandoffJob` 专表） |
| **多 worker** ⏳ | 锁 / 审批门 / 通道 / handoff 作业为进程内态；多机需 Redis + durable queue |

> **本地真实编辑 = 正交模型的一个配置**：= 轴1 `server` + 轴2 `local_dir`，仅在「服务端 = 用户机器的可信自托管」下成立——`resolve_safe_path` 仍管越界，但允许把 `local_dir` 喂给工作区根。与「云端杜绝用户传任意服务端路径」不矛盾（前者可信运维配置，后者不可信多租户默认）。

## 六、绑定模型与「模式跟着文件走」

- **项目 = 工作区（Folder）**：创建时必须声明 `mode: local | cloud`。local 复用 `local_root_id` + `local_subpath`；cloud 两列为 NULL，服务端共享 scope `folder:<folder_id>`。绑定创建后不可改（本期不做 relocate）。
- **会话归入项目则继承**：带 `folder_id` 创建的会话不写会话级 `local_*` / `local_container_root_id`；生效工作区解析（`resolve_local_binding` 及同链路）继承项目绑定；云项目内会话共用 `folder:<id>`，不再各自 `conv:<id>` scratch。
- **出生定终身**：无 `PATCH /conversations/{id}/folder`；删项目软删并归档其会话（不解组）。
- **裸聊（无 folder_id）**：云端默认 `conv:<id>` scratch；桌面新建裸聊默认云执行（不拉 sidecar）。显式绑本地时：本地容器根（桌面默认 `~/Documents/AgentCore`）下每对话 scratch 子目录 `conversations/<conversation_id>/`（空 `local_subpath` 即解析为此形态，懒建；跨端契约）；桌面可写 `local_container_root_id` / 对话级 bind。容器根机制仅服务显式绑回本地的裸聊。
- **无云/本地开关**：路由判定读生效绑定（项目列或会话列）→ `LocalWorkspace`，否则 `ServerWorkspace`。
- **清单稀疏化**：CEO overview 与 worker manifest 同一策略——默认只注入「本回合附件（`attachments/`）+ 本对话 scratch 内文件 + 同回合队友产出（role 标注）」；**项目共享**模式下其余文件不逐条列，改为一句「另有 N 个文件，需要时用 file_list / grep」（另保留最多 5 条「最近触达」补充）。裸聊因整树即 scratch，非附件文件照常列入（仍受条数/字符预算）。→ 见 `workspace/sparse_listing.py`、`runtime/context/workspace_overview.py`、`runtime/runs/executor_context.py`。
- **系统文件隐藏（两档）**：系统噪音（`.agentcore` / `.git` / `node_modules` / 缓存目录 / `*.db` / `*.pyc` 等）对 AI 与用户文件 UI **都**隐藏；AI 噪音（媒体 / 压缩包 / 字体 / 二进制对象）仅从 AI 视角（`index_files` / `list_tree` / `grep` / `file_list`）排除，用户文件面板保持可见。规则在 `workspace/_paths.py`（`IGNORED_DIRS` + `SYSTEM_IGNORED_FILE_SUFFIXES` + `AI_NOISE_FILE_SUFFIXES`），桌面 `workspaceIgnore.ts` 对齐同一清单。
- **删对话软删**：对话 `deleted_at` 软删；云端 scratch 对齐 30 天保留期再物理清（`workspace/retention.py`）。本地 scratch 目录软删由桌面执行；服务端不在删对话时立刻 rmtree。
- **不做存量迁移**：开发期无真实用户；旧散落在容器根的文件直接无视。
- **Memory project scope**：仍用 `folder_id` 作项目记忆作用域（与文件工作区同键、不同树）。

→ 见代码：`conversation/scratch.py`、`conversation/common.py`（`resolve_local_binding`）、`workspace/locate.py`、`conversation/turn_backend.py`。

## 七、风险与边界

| 项 | 处理 |
|---|---|
| 路径越界 | `resolve_safe_path` 下沉 `ServerWorkspace`；服务端目录由 user/conv 生成，杜绝用户传任意服务端路径 |
| 裸聊（未分组会话） | 云 `conv:<id>`；本地 `conversations/<conversation_id>/` 在容器根下（空 subpath 解析为此形态）；零文件时目录可不存在，首写 lazy `mkdir`，不创建 Folder |
| 对话与项目的归属变更 | **不支持**（出生定终身）；跨项目延续走「在项目中继续」（目标项目开新草稿 + 上下文摘要交接），文件搬运是显式动作、MVP 不做 |
| folder / 会话删除后文件 | 与软删对齐：软删原样保留可恢复；超保留期（默认 30 天，可配）物理清 conv scratch + 记录 + OSS 备份；「彻底删除」立即清。本地目录软删由桌面执行 |
| 同 conv scratch 并发写 | 对话级锁（`workspace/locks.py`，进程内，多机再 Redis） |
| `LocalWorkspace` 下并行团队 | 单桌面通道是瓶颈；正解 = 本地内环 + snapshot 到云由云端跑并行团队（交接 e2，呼应 §三 快照语义） |
| 本地 worker 直接执行 | 本地模式被委派 worker 共用 CEO 同一回合审批门（仅 `backend.location=="local"` 透传 `ApprovalGate`）；云模式不下发门（沙箱隔离） |
| execute 通道传输期限 | 代码执行 = 代码自身超时 + 余量（默认 30s）；文件 op 走扁平期限（默认 60s）——避免长但合法的执行被传输层提前丢弃 |

## 八、关键决策（已定）

下文为 §二–§六 的决策摘要；细节见对应章节。

1. **抽象与路由**（§二–§四、§六）：P0 `WorkspaceBackend`；不给云/本地开关，模式跟着文件走；三正交轴，本地+云储存 = 快照语义、拒绝实时双向同步；`LocalWorkspace` 经泛化审批门接缝。
2. **存储与交接**（§五）：文件进出先上传 + `git clone`；阿里云 OSS；快照非每写必存；本地→云三段式 `HandoffJob`。
3. **一等资源**（§九）：`/v1/workspaces/{ws_id}` 支持 `folder:<id>`（项目）与 `conv:<id>`（裸聊）。
4. **添加本地目录**：裸聊经 `PUT /conversations/{id}/workspace/binding`；项目经创建时 `mode=local` + `local_root_id`（创建后不可改）。**否决** auto-promote 裸聊为 Folder。
5. **@ 提及覆盖云端工作区**（F4）：云/本地同进一套索引；按生效 `folder:` / `conv:` 索引。→ 见 [`前端技术与架构.md` §八](/docs/04-前端/前端技术与架构.md)。
6. **项目即工作区**：Folder 必绑 local/cloud；项目内会话共享空间、出生定终身。**否决** auto-promote + `workspace_promoted`。**否决**会话中途改 folder。
7. **路由默认值**（2026-07-15 改版）：web / 手机 → 云 scratch；桌面绑本地目录 → 本地 scratch；**桌面裸聊默认云 scratch** ✅（关桌面续跑、多端可见、环境统一；显式「本机草稿」仍可落容器根）。重型并行多 Agent 团队仍交接到云跑（§七）。按当前任务路由，非按用户身份分人群。用户心智一句话：「**你的文件在哪，AI 就在哪干活；没给文件，就在云上干**」。
   - **为什么切云**：① 关桌面任务停是 Multi-Agent 长任务核心体验硬伤（云回合断连续跑，见 [执行引擎 §执行与请求解耦](/docs/03-AI核心/执行引擎架构设计.md)）；② 大众用户裸聊产物的交付形态是「云端预览 + 一键导出」而非本地文件夹，且云沙箱环境统一可控（大众本机无开发环境，AI 生成的软件本地跑起来成功率低）；③ 工作区文件多端可见、手机接力天然成立；④ 隐私论点不支持 local-first——混合态下对话本就全量回写云（§十）。开发者「指着本地文件干活」场景由绑本地文件夹路径完整保留（本地权威 + sidecar 默认开，不动）。
   - **被替代决策**：桌面裸聊默认 local-first（2026-07-15 前现状）——关桌面即停 + 手机看不到流中态对大众裸聊是硬伤，其隐私优势在混合态下又不成立。容器根机制与显式本地绑定（§六）保留不删，用户仍可手动把裸聊绑到本地（草稿 chip「本机草稿」/ 命令面板）。
   - **配套 ✅ 云 scratch 产物导出**：「预览（复用既有云工作区浏览）+ 一键导出到本地」（git-pull 式单向 checkout，与 §三 快照语义对称；仍拒绝实时双向同步）。→ 见 `services/workspace.ts` `exportWorkspaceToLocal` + 主进程 `fs:checkoutArchive`。
   - **免费档成本口径**（2026-07-15 定，无真实数据、按假设起步）：**不为云执行新增配额维度**，`free_tier_*` 三维仍是唯一闸门——任务量被推理配额天然封顶、执行沙箱假设为成本小头；云 scratch 存储沿用 30 天保留期清理。真实负载数据出来再议执行维闸门（与 [远期规划 §3.3](/docs/06-规划/远期规划.md) COST-004「待真实负载再开」同姿态）。
   - **§10.7 不变量重估**（默认路由变更触发）：裸聊切云后 sidecar 仅剩绑本地文件夹会话，本地恢复面语义不变、覆盖面缩小；「手机看桌面流中态」维持另案、优先级下调不升级。
8. **sidecar 本地引擎**（✅ 已落地，详见 §十）：引擎本体搬到桌面子进程跑同一 `run_chat_pipeline`、工作区直连本地盘；推理 / 计费 / 持久化仍借道云（岔路 B：平台 key 不下放、计费权威在云）。用户可开「本地引擎」让本机本地文件夹对话走 sidecar。⏳ 完全离线 + 跨进程分发，见 [`远期规划.md §一`](/docs/06-规划/远期规划.md)。
9. **引用即驻留 + 分流预解析**（✅）：用户经回形针 / @ / 拖拽附加**工作区外或二进制**文件时，桌面主进程把原始字节复制进对话工作区 `attachments/`（云端工作区则 PUT 同路径）；prompt 只暴露工作区相对路径，**否决**区外直读（两层路径守卫不减配）。云占位（OneDrive 按需下载等）在复制步检测 + 短超时快速失败。CEO 见用户消息中的区外绝对路径时引导附加，不委派硬读。
   - **分流**：对话场景行业主流是 ingest 时预解析——docx/pdf/pptx/txt 等文本型文档在驻留后用 markitdown 抽文本，生成与原件并存的可读副本（如 `报告.docx.md`），首轮 prompt 内联正文（超阈值截断并指路全文副本）；xlsx/csv **不**预解析全表，仍走路径提示 + 运行时 `code_execute`（适配大表计算 / 写回）。扫描版 PDF 首版不做 OCR，识别后写明确降级提示（建议告知用户），不静默失败。解析失败不阻塞上传，回落「路径提示 + 委派解析」。
   - **旧决策「不加文档解析器」**：已部分撤销——仅撤销「文本型办公文档完全不解析」；仍不做通用 OCR/视觉依赖，也不把表格全量 ingest。
   - → 见代码 `main/fs/stageAttachment.ts`、`workspace/attachments.py`、`workspace/attachment_parse.py`、`runtime/resolve/prepare.py`。
10. **会话级目录授权**（✅ W3 只读 + ✅ P1 organize）：用户要分析或整理**整个区外文件夹**时，CEO 用 `ask_user` + `action=grant_readonly_folder`（只读）或 `grant_organize_folder`（整理读写）开授权卡；用户经文件夹选择器确认后，桌面登记会话级根（`sessionOnly` + 显式 `mode: readonly | organize`，不进永久 `fs-roots.json`），服务端 grant store 映射 `external/<别名>/…`。只读：`file_list` / `file_read` / `grep` 多根路由，写硬拒；`code_execute` 经 `AGENTCORE_EXTERNAL_<ALIAS>` 注入绝对路径（软约束，与 W3 定位一致）。organize：白名单 = list/read/grep/stat + move/copy/mkdir + 回收站删除；**显式拒绝** write/append/replace、execute、process_start、archive；区外 `permanent=true` 路由层硬闸（与 mode 无关）；**不注入** `AGENTCORE_EXTERNAL_*`。同 root 由 readonly 升 organize 须重新弹卡。对话删除或用户撤销即失效。LocalWorkspace 通道与 sidecar 双路径通；云端 / 非桌面 → 明确降级。**不改** workspace binding 契约、不减配 `resolve_safe_path` / pathGuard。→ 见 `workspace/external_mounts.py`、`grant_store.py`、`main/fs/workspace/dispatch.ts`、`lib/grantOrganizeFolder.ts`；整理工作流 → [桌面文件整理工作流提案](/docs/06-规划/桌面文件整理工作流提案.md)。

## 十、本地引擎（Sidecar 进程内核）✅

> **定位**：§四 `LocalWorkspace` 是「引擎在云、文件 op 经 `WorkspaceChannel` 遥控桌面」；本节更深一层——**引擎本体也搬到本地**：桌面 spawn `python -m agentcore.sidecar` 子进程跑**同一 `run_chat_pipeline`**，整轮在用户机器上执行、工作区直连本地真实磁盘（无单 op 往返）。**驱动力**：同一用户兼做「改本地真实仓」与「泛知识工作」，本地交互不能长期二等（单通道遥控在速度 / 并行 / 离线均受限）。
>
> **现状**：✅ **混合态**本地引擎已落地（引擎在本地，推理 / 持久化 / 计费仍借道云）；完全离线（本地推理 + 本地消息库）+ 跨进程分发为远期触发项，见 [`../06-规划/远期规划.md §一`](/docs/06-规划/远期规划.md)。
>
> **对外表述边界（隐私）**：混合态下对话正文全量回写云端权威存储（§10.2 / §10.3），产品 / 营销**不得承诺「数据不出本机」**；解锁该承诺的前置是完全离线触发项落地（本地推理 + 本地消息库或不回写选项）。
>
> → 见代码：`apps/server/agentcore/sidecar/`（`server.py` / `protocol.py` / `paused_store.py`）；桌面 `apps/desktop/src/main/sidecar-service.ts` + `sidecar-event-buffer.ts` + `src/renderer/services/sidecar*.ts` / `turns/sidecarAttach.ts`。

### 10.1 形态与路由

- **通道**：桌面主进程 spawn sidecar 子进程，**stdio 行分隔 JSON-RPC 2.0**（一行一消息；**非 MCP**——MCP 仍用于 Agent↔外部工具）。回合事件经 `turn/event` notification 桥回 renderer，**复用同一 `dispatchSSEEvent`**（云 / 本地共用一套事件处理与协议 fold）。Python JSON-RPC 方法集：`initialize` / `startTurn`（响应延迟到回合结束、携最终结果）/ `respond`（live 结算挂起）/ `resume` / `listPaused` / `cancel` / `shutdown`（`PROTOCOL_VERSION` 校验防陈旧配对）。桌面宿主另有 **IPC 恢复面**（§10.7）：`sidecar:recovery` / `sidecar:attach`——不进 Python 协议、不升 `PROTOCOL_VERSION`；桌面侧原 `listPaused` IPC 已并入 recovery（主进程直读帧文件，零 spawn）。
- **会话路由**：**绑本机本地文件夹**的对话默认走 sidecar，裸聊（默认云）/ 云端项目 / 带附件仍走云链路。开关「**本地引擎**」（设置 → 模型配置）已毕业到**默认开**、可关闭；偏好**三态**持久化（`unset` 跟随默认 / 显式 `on` / `off`），故翻默认不误开显式关过的用户。
- **启动失败自动降级**：sidecar 在产出任何输出前就失败（拉不起 / 握手 / venv 缺失）时，本轮自动改走云链路重跑、用户无感（一行提示）；引擎已开跑后的**中途**失败不自动降级（避免重复副作用），照常出针对性横幅 + 重试。**这是「默认开」的安全前提。**
- **首次探活 + 会话级健康缓存**：每个 app 会话**首次**真正走 sidecar 前先探活一次（`sidecar:probe` 拉起进程 + `initialize` 握手即返回、不跑回合；握手成功的进程被随后首个回合复用，零额外拉起）。探活失败或启动期降级时，按 `root + subpath` 标记该根**本会话不健康**（仅 app 进程内、不持久化），二者**共用**同一「记坏→命中缓存」出口。
  - **关键不变量**：健康只决定「要不要拉起 sidecar 跑回合」，**不掺进路由的绑定判定**（`resolveSidecarRoot` 纯看开关 + 绑定）——否则会污染续跑 / 列暂停帧（它们读**本机**帧、绝不能误降级走云）。故健康收敛分散到各调用方按自身语义处理：
    - 新回合 `sendTurn`：见缓存坏则**静默走云**（坏环境只首轮提示一次，不再每轮「试→降级」）；
    - 续跑 `runResume`：探活失败**或本地根不可得**（本地引擎关闭 / 根不在本机 / 会话缓存未就绪）均**保留续跑卡 + 出横幅**、绝不降级（暂停帧只在本机，云端续跑必 404）；帧 `origin` 按**帧粒度**打标（同会话可混云 / 本机帧，合并按 `message_id`、sidecar 胜出），不再整会话单一 origin；
    - 列暂停帧 / 刷新恢复：经 `sidecar:recovery` 直读本机 turns 内存 + outbox + paused 帧，**不关心**进程健康、**不读** `resolveSidecarRoot`（那是新回合路由意向，见 §10.7）。
  - 用户在设置里重新开启「本地引擎」会清空缓存、允许对修好的根重探。
- sidecar 工作区是 `ServerWorkspace(location="local")`（root = 用户真实磁盘），故被委派 worker 的机器接触类工具（`file_write` / `code_execute`）走审批门（同云端本地模式 P2d，§七）。

### 10.2 岔路 B：平台 key 不下放，计费权威在云

LLM 调用经云推理代理 `/v1/inference`（cookie 兑换的短期作用域令牌作 Bearer）——**平台 key 永不下放用户机器**。代理服务端解析真实凭据 + 过门（平台配额 / BYOK 校验）+ 按真实 usage **权威落** `cost_events`，**故计费不从客户端上报**（防篡改）。token 2h TTL，桌面每次 `startTurn` / `resume` 重发 `inference` 块刷新（长会话不 401）。

> **否决·岔路 A**：把平台 key 下放本机直连 DeepSeek——key 泄漏面 + 客户端上报计费不可信。

### 10.3 持久化：本机 outbox → 主进程回写云端

**根因与收敛**：早先本地回合正文只由 renderer 在回合末一次性 best-effort HTTP 回写（内存重试 3 次即弃、失败弹 toast），刷新即焚；重度并行回合打爆 asyncpg 连接池时正文更是从未落库。本方案把耐久性从「事后旁路」收敛为统一 **`ConversationStore` driver**（`begin_turn` / `checkpoint` / `append_journal` / `finalize` / `salvage`；云 / 本地同一算法内核绑同一端口，见 [执行引擎 §8.6](/docs/03-AI核心/执行引擎架构设计.md)）：云端 `CloudStore` 直落 Postgres，sidecar `OutboxStore` 每个方法不写库、序列化成有序 record 追加本机 outbox 文件。

**回写链路**：sidecar 渐进写本机 outbox（有序 `begin → N×(checkpoint | journal) → finalize`，对齐 §10.4 本机帧先例）；Electron **主进程** Bearer 回写器读 outbox → `POST .../local-turns`（纯 Bearer、不带会话 cookie，鉴权见 [认证与会话 §七](/docs/05-平台与运维/认证与会话.md)）→ 云端 `CloudStore.finalize(mode=local)` 合并落库 → 云确认后删文件。**失败分级**（2026-07 schema 落后 500 风暴后收敛）：4xx（除 401/408/429）= 永久失败 → 记录挪入 `<userData>/sidecar/dead-letter/` 留档停投（如会话已删的 404，不再无限重试）；401/408/429/5xx/网络错误 = 瞬态 → per-record 指数退避重投（2s 基数、翻倍、封顶 5min + 抖动，`retry_count`/`next_attempt_at` 写回记录文件）；用户显式 `flushTurn` 绕过退避立即尝试。每回合携乐观 `userMessageId` 作幂等锚，主进程据此独立组请求、**跨 renderer 刷新 / app 重启扫盘续传**。Renderer 退出回写职责，只显示 + 反映同步态（本地 `synced_pending` → 主进程 `outbox:synced` IPC 翻转后清除），**不**再做 HTTP 重试 / toast。

**服务端合并契约**（对 outbox 乱序 / 重试显式保证，纠正「把已展示当已保存」）：content **checkpoint 单调 + 终稿权威**（迟到 checkpoint 不覆盖更长 / 已终态正文；`complete` finalize 是权威交付、可覆盖更长的流中半成品——deliverable_only 裁掉旁白后终稿常更短；salvage / incomplete 仍单调保护，见 `conversation/store/merge.py::pick_merged_content`）· status **门闩**（只前进，checkpoint 不把 `complete` 打回 `running`）· journal 按 `(turn_id, seq)` **幂等**去重 · finalize 携**全量** journal 补中途丢失 · **废弃早退**（「user+assistant 已存在即 return」改幂等合并 upsert，否则 `begin` 占位后 finalize 永不落库）。journal seq 权威双模式见 [执行引擎 §8.3](/docs/03-AI核心/执行引擎架构设计.md)；`complete` 语义 = 云端落库确认（非「已渲染」）。

> **trace 链路（打通气泡↔日志）**：一次 sidecar 回合的「推理」是无状态的代理调用（§10.2）、「落库」是另一条 REST 回写，二者本无共享键。故桌面为每个本地回合铸一枚 `trace_id`，**同时**随每次云代理 LLM 调用（`X-AgentCore-Trace` 头 → 代理 `bind_log_context` 绑入日志）与 outbox 回写（落到 assistant 消息行）上报；服务端回写**复用**该 id（非另铸），使一次本地回合的推理日志、计费行与气泡归并为同一条可 grep 的 trace。旧桌面缺省 `trace_id` 时服务端补铸（链路退化但不报错）。

> **流中耐久（D6）✅**：云端走 `turn_stream_state`；本地则把同一 `StreamCheckpointer` flush（3s / 4KB / 语义边界，**非**每 delta）渐进写入该回合 outbox record 的 `stream_segments`（`channel → {text, generation}`，与 journal map 同形）。硬杀（崩溃 / 断电 / 强退，不经 salvage）后 `content` 常仍为空——主进程 `recoverLocalPersistence` 促升时若 open 且正文空，回退用 `captain:content` / `captain:reasoning` 补 `content` / `reasoning_content`，再按 cancelled + incomplete 促升回写。**不做**本地流中 overlay 进云端 `GET …/messages`（`list_stream_segments` 仍空；云端 overlay 不变）——刷新后活回合可见性走宿主恢复面（§10.7），不靠消息窗口 overlay；常规轮询**不**促升 open record。**过程时间线**（CEO 旁白 / worker `run_processes`）以 journal 渐进 `process_*` / `run_process_*` 为运行中刷新唯一真源（见 [执行引擎 §8.3](/docs/03-AI核心/执行引擎架构设计.md)）：语义边界写入后经同一 SSE barrier 落本机 outbox journal（与云端 PG 同构，**非** finalize 收口才可见）；活回合 attach 仍走事件缓冲（§10.7，同构云端 `take_over`），journal 供崩溃 / 投影 / 保序真源。纯散文回合继续用 `stream_segments` 加速 / salvage，不扩展 `process_*`。

### 10.4 结构化挂起：本机帧（path A，投影同形）

plan_review / ask_user / team_preview 挂起的帧 `TurnSuspension` 写 `<userData>/sidecar/paused/<msg>.json`（一回合一 JSON、原子写、claim 经 `.claimed` 改名 + conversation 校验防双取 / IDOR），由 `LocalPausedTurnStore` 管增删；**save 失败抛错**（对齐云端 D11——绝不「假 saved」出卡后帧不在盘上）。桌面经 `sidecar:recovery` 一次 IPC 直读本机帧（零 spawn；原独立 `listPaused` IPC 已并入），重现续跑卡；`resume` RPC claim 帧跑 `resume_chat_pipeline`。**摘要与云 `paused_turns` 投影同形**（snake_case `PausedTurnSummary`），**故前端不分叉**。approval / client_tool 挂起仍仅内存（live `respond`），与云一致——刷新后热路卡靠 §10.7 事件回放重建。

**决策即事实：settlement 预写即消费帧 ✅**（2026-07 收口——「授权开赛后杀进程、重启回退成待授权卡」根因重设计）：用户提交决策后、启动任何 pipeline **之前**，sidecar 先把 settlement（`*_resolved`）预写进本机 outbox journal（durable），**预写成功立即删除帧**——帧的生命周期＝决策等待期，「用户决策了吗」只剩 journal 一个答案（与云端 `prewrite_cold_resume_settlement` 先落库再消费帧同构）。此后 pipeline 同步失败或中途崩溃**一律不还帧**（`rollback_claim`「还帧再授权」语义退役——用户决策一旦发生即是事实，不可由系统回退）；孤儿 `.claimed` 恢复按 journal 裁决：无 settlement（预写前崩溃）→ 还待授权帧，有 settlement → 幂等补删完成消费。**否决**：保留帧 + 冷启动用 journal 对账改写 paused[]（给双真相源加对账层，正是补丁绊线禁止的形态）；新增显式状态列/状态文件（本身成为下一个漂移源——journal 存事实、状态永远派生）。→ 见代码 `sidecar/settlement_prewrite.py`、`sidecar/paused_store.py`；测试 `test_sidecar_paused.py`（含 prewrite 后崩溃不复活决策卡）。

> **与 outbox 的关系（D8）**：挂起帧与本机 outbox（§10.3）同置 `<userData>/sidecar/{paused,outbox}` 根、分类型处理器、各自生命周期——**不并同一状态机**（pause 是「等用户决策」控制面 + claim 互斥；outbox 是「等云确认」回写面，强并会互相打架）。因进程边界（pause claim 归 sidecar、outbox 回写归 Electron 主进程），二者各自在启动时扫盘恢复，不强并单一入口。

### 10.5 内置 Python 打包（方案 B）

安装包内置独立 CPython（`--target` 预装 agentcore），`app.isPackaged` 时拉起——**用户机零依赖**（无需系统 Python / venv / uv）。原生 wheel / 解释器不可交叉编译，故每 OS runner 各自打包本平台运行时。CI 接线（`bundle:sidecar` 步骤、产物入包）见 [`../05-平台与运维/部署与运维.md` §7.6](/docs/05-平台与运维/部署与运维.md)。

### 10.6 与「可迁移核」的关系（剩余端口留缝）

sidecar 现**复用同一引擎**，只把 [执行引擎 §8.6](/docs/03-AI核心/执行引擎架构设计.md) 宿主端口里的 **Workspace（→本地盘）/ 挂起（→本机帧）** 换了本地实现；其余端口（持久化 / 计费 / 推理）仍借道云（§10.2/10.3）。**`Journal` 端口 + 执行级事实已落地**（执行级溯源地基就位，见 [执行引擎 §8.3](/docs/03-AI核心/执行引擎架构设计.md)）。完全离线（剩 7 端口出本地实现 + 本地推理 + 本地消息库）按「无第二实现不抽象」纪律留缝、待触发——见 [`../06-规划/远期规划.md §一`](/docs/06-规划/远期规划.md)。

### 10.7 刷新恢复面（宿主端口对等实现）✅

> **定位**：恢复面是宿主端口的一部分。云端 = `TurnRunRegistry` + `GET /recovery` + `GET /stream`（回放+续流）+ 读侧 overlay；本地宿主在桌面主进程补**对等实现**，前端两路汇入同一水合链与同一 `dispatchSSEEvent`，协议 fold 零变化。禁止轮询 / 特例兜底。
>
> **不变量**：本地引擎默认开 ⇒ 其恢复面必须与云端对齐；**任何一侧默认路由变更须重估另一侧豁免**（早先「不做本地重挂」在默认开后失效，曾导致刷新空白）。

**主进程权威**：每个活回合（`startTurn` 与 `resume` 登记一视同仁）维护有序事件缓冲（`sidecar-event-buffer.ts`）——`turn/event` **先入缓冲再转发**，目标 WebContents 已销毁也不丢。合并/跳过规则镜像引擎 `EventSink._history`；**有意偏离**：缓冲保留 `message_end` / `error`（云端 attach 不需要收尾——已结束走 204；本地存在「收尾 notification 已到、`turns.delete` 未执行」微窗口，无收尾则气泡悬挂「生成中」）。

**两条语义不得混用**：
| | 路由意向 | 恢复事实 |
|---|---|---|
| 问什么 | 下一回合走哪 | 本机现在有没有活回合 / 未同步 outbox / 挂起帧 |
| 权威 | renderer：`resolveSidecarRoot`（开关 + 对话列表缓存） | 主进程：turns 内存 + outbox / paused 文件 |
| 谁用 | 新回合发送、用户点击续跑 | 打开对话水合 / recovery / attach |

刷新后对话列表缓存必空——用路由意向做恢复分支判定会**必然误判云端**（首版验收失败根因）。故 `loadRecovery`（桌面 `hasLocalEngine()`）**无条件**并行查本地 recovery + 云端 `GET /recovery`；分支只认 `sidecarLive || unsynced.length > 0`。

**三件套**：
1. **recovery IPC** → `{ liveRunning, turnId?, unsynced[], paused[] }`（paused 兼并原 listPaused；unsynced 为投影自足摘要，不透传原始 journal）。
2. **attach IPC** → 重绑 wc→快照缓冲段**零 await**（快照点即重绑点，事件互斥不重不漏）；响应携登记元数据 + `events[]`；renderer 先订 `onEvent` 暂存 live → attach → `setActiveSidecarTurn`（防 respond 误走云）→ 合成用户行 / sidecar 专用 clear-then-fold → 回放 → 排空队列续看。resume 类活回合：挂起前事实不重发 SSE → **保留行内容、仅增量 fold**。`attached:false` 立即重查 recovery 降级投影/ghost，禁止悬挂；RPC settle 时若无终止事件，主进程在 `turns.delete` 前补发合成终止。
3. **unsynced 投影** → 摘要适配成 `BackendMessage` 经 `toMessage` 追加（ready→完整+`synced_pending`；无活回合的 open→ghost）；**先投影、后 attach**（同会话可「上一轮 ready 未同步 + 本轮 live」并存）。

**「已决策 · 执行中断」派生态 + 无帧续跑 ✅**（与 §10.4 settlement 预写同期收口）：投影判定统一用 **journal fold 的 pending 语义**（与云端交互统一重构同源），不以「帧存在」或「unsynced 非空」为触发前提——fold 有 pending（有 `*_required` 无对应 `*_resolved`）→ 显示决策卡（二次挂起 / 多决策卡按 interaction 独立派生，禁止会话级单一状态）；无 pending + turn 未终态 + 无活执行 → `interrupted_after_decision`，UI 呈现「已授权 · 执行中断」+ **手动一键续跑**（**否决**默认自动续跑——重启后未经知情自动消费 LLM 成本；自动化留作设置项）。续跑走**无帧续跑 API**（按 turn 从 outbox journal 重建挂起上下文进 resume pipeline，幂等 + 与 claim 同级互斥防多窗口双跑）——**否决**复用 `continueTurn` / regenerate（审计实证其语义是「新开一条用户回合」、不携 settlement）。**retain-open 不变量**：已结算未终态的 outbox 记录不上云、直到续跑进入终态才回写（判定与续跑材料恒在本地，回归测试钉住）。续跑语义＝**从决策点重跑**（辩论即 `skip_kickoff` 式重跑整场，丢弃已跑部分进度）；执行内精确续局无现成机制（moderator 非 DAG、无逐轮 checkpoint），登记远期（[远期规划 §一](/docs/06-规划/远期规划.md)）。→ 见代码 `shared/recoveryFold.ts`、`services/turns/continueAfterDecision.ts`、`interruptedAfterDecision` store；测试 `ResumePrompt.interrupted`。

**边界（有意与云端同构 / 另案）**：不做流中回写云端（手机/web 看桌面本地进行中 = 另案）；`workspace_op` / `client_tool` 跨刷新不恢复（与云端 attach skip 同语义）；app 整体重启硬杀仍走既有 `recoverLocalPersistence`。前端水合序 → [前端技术 §12.1](/docs/04-前端/前端技术与架构.md)。
