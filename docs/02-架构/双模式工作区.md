# 双模式工作区（云 + 本地）

> **状态**：✅ 已落地——`WorkspaceBackend` 抽象 + `ServerWorkspace`（云）+ `LocalWorkspace`（本地）+ 绑定路由（模式跟着文件走）+ 文件进出 / 快照 / `git clone` / 附件驻留 / 保留期清理 + 本地→云 snapshot 交接（三段式，前后端齐全）。⏳ 仅余多 worker 化：锁 / 审批门 / 工具执行通道 / handoff 作业现为**进程内态**，多机需前置 Redis + durable queue。
>
> **定位**：让「AI 对话能选文件夹、并在该文件夹工作」，一套分层同时支撑**云**与**本地**两种**平等**模式——**不给用户云/本地开关，模式跟着「文件在哪」自动走**（§七）。
>
> 代码真相源：`workspace/{protocol,server,local,locate,channel,snapshots,files,git,attachments,retention,locks,handoff,handoff_diff,handoff_apply,_paths}.py`、`storage/*`、`runtime/pipeline.py`、`tools/builtin/{file_ops,grep,code_execute}.py`。

## 一、起点：三个割裂的「文件夹」概念（已接通）

抽象引入前有三个互不相干的「文件夹」：侧栏 `Folder.local_dir`（DB 纯标签）、桌面 FS Roots（仅读文本喂 @ 附件）、AI 工作区（曾写死 `Path.cwd()` 全会话共用）。缺口不是壳，是把三者接起来。

**为何 P0 就引入 `WorkspaceBackend` 抽象**（而非推迟）：本地模式（B）是**已承诺、必然建完**的路线，非投机性未来，故「接口先行」（项目 house style）压过「避免过早抽象」。早接缝的回报是**跨切面只动一次**——把工具 / 引擎改成对接口编程后，新增第二实现 `LocalWorkspace` 时工具与引擎零改动，省掉「同步 `Path` 操作回炉成异步 + 二次触碰全部工具」的大改。

## 二、需求推导结论：两种模式平等

- **内核需求**：给每次协作一个**持久、可累积的项目空间**——多 Agent 在同一张「桌子」上靠文件协作。「在不在本地磁盘」是第二层偏好，非内核。
- **云模式（服务端托管）= 零前提的起点**：打开即用、不暴露整块磁盘；并行团队同台协作，天然可观测、可隔离。
- **本地模式（桌面执行，对标 Cursor）= 平等的另一种，后做**：开发者内环（改真实本地仓）。
- **不给用户云/本地开关**——模式跟着「文件在哪」自动走（§七）；「云优先 / 本地优先」只是构建顺序。

## 三、`WorkspaceBackend` 抽象

沿用项目「Protocol + 实现 + 工厂」同构范式（同 `LLMProvider` / `SandboxProvider` / `SearchBackend`），引擎与工具只对接口编程：

- **接口**：`read / write / list / replace / grep / execute` + `location`(server·local) + `root_label`（相对路径渲染、不暴露绝对路径）。
- **签名一次到位**：P0 即钉死结构化结果类型（`DirEntry` / `ReplaceOutcome` / `GrepResult` 等），失败走类型化异常 `WorkspaceError` 子类（`OutsideWorkspace` / `PathNotFound` / `NotAFile` / `NotUTF8` / `AmbiguousMatch` …），工具层捕获后映射回原报错文案（用户侧报错零变化）。
- **护栏 1·瘦接口**：持久化（snapshot/restore）**不进 backend**——是回合级存储策略（轴3），归独立 `StorageProvider`，由 service 在 run 前后调（§四、§六 P1）。backend 只管「文件 + 执行」这对**必须同源**的能力（一个 backend = 一个执行平台）。
- **唯一接缝**：`ToolContext.workspace_dir: Path` → `ToolContext.backend: WorkspaceBackend`，6 个工具（`file_ops` 4 个 + `grep` + `code_execute`）与引擎退化薄壳。`code_execute` 收编进 `backend.execute`（`ServerWorkspace` 内委托 `SandboxProvider` + 带 cwd），顺修「代码与文件不在同一目录」的潜伏 bug。

## 四、三正交轴与「本地默认云储存」判定

| 轴 | 取值 |
|---|---|
| 轴1 执行位置 | server / local |
| 轴2 文件源头 | server dir / local dir |
| 轴3 持久化 | S3 快照 / 仅本地盘 / 实时同步 |

「云 / 本地模式」是在**轴1+轴2** 选一整套。用户提的「本地默认云储存」= `轴1=local、轴2=local、轴3=cloud`——**不是第三种模式，而是 LOCAL backend 的存储策略**：

- ✅ **接受**快照 / 交接语义（git-push 式）：本地是唯一真相源，按需经 `StorageProvider` 快照到 S3，用于备份 / 跨设备 / 把活交给云端团队。
- ❌ **拒绝**实时双向同步（Dropbox 式）：双真相源 + 冲突地狱，在「并行 Agent 团队并发写」下尤其致命。

## 五、两个 Backend 实现

| Backend | 文件在哪 | 执行在哪 | 模式 | 传输 |
|---|---|---|---|---|
| `ServerWorkspace` | 服务端 `<data_dir>/workspaces/<user_id>/<folder_id>/`（文件夹）或 `…/conv/<conversation_id>/`（未分组） | 服务端（复用 `SubprocessSandbox`） | 云 | 同进程 |
| `LocalWorkspace` | 用户真实本地目录 | 桌面端（op 路由到 Electron） | 本地 | 泛化审批门接缝 |

`LocalWorkspace` 的传输**不另造**：把 `runtime/approvals.py` 的「服务端挂起 `asyncio.Future` + 客户端 HTTP 回填」泛化成一条工具执行通道（`WorkspaceChannel`）——服务端挂起 + `workspace_op_required` SSE + `POST …/workspace/ops/{request_id}` resolve 回填；桌面 `fs-service.ts` 处理全 op、渲染端 `workspaceOps.ts` 收 SSE→IPC→回填。每个 op 串行路由、回传结构化结果或同款 `WorkspaceError`，故工具 / 引擎不动。

## 七、绑定模型与「模式跟着文件走」

- **粒度**：默认每个对话有独立工作区；放进文件夹的对话**共用该文件夹工作区**（文件夹 = 项目）。顺现有 `folder_id` 模型。
- **无云/本地开关**：路由判定（`workspace/locate.py`）——有 `local binding`（`Folder.local_root_id` / `Conversation.local_root_id`）→ `LocalWorkspace`，否则 `ServerWorkspace`。直接聊 / 上传 / 手机端 → 云；桌面绑定本地文件夹 → 本地。
- **跨设备**：云项目跨设备同步；本地项目仅在那台机器；手机无本地文件夹概念，自动走云。
- **注入路径**：`conversation/service.py` 解析 `conversation →（文件夹空间 / 本对话空间）→（有绑定 local_dir 则本地、否则云）` → 构造 `WorkspaceBackend` → 经 `run_chat_pipeline` 注入 `base_tool_context.backend`；worker 经 `replace(...)` 自动继承。

## 八、风险与边界

| 项 | 处理 |
|---|---|
| 路径越界 | `resolve_safe_path` 下沉 `ServerWorkspace`；服务端目录由 user/folder 生成，杜绝用户传任意服务端路径 |
| 未分组会话 | 每对话独立空间 `…/conv/<id>/`（§九 ③） |
| 已开始对话跨文件夹移动 | 禁止——有消息后锁定归属（前端隐入口 + 后端 409，§九 ⑩） |
| folder / 会话删除后文件 | 与软删对齐：软删原样保留可恢复；超保留期后台清（§九 ⑦） |
| 同 folder 跨会话并发写 | 文件夹级锁（`workspace/locks.py`，进程内，多机再 Redis）；任务内并行小队不受限（§九 ④） |
| `LocalWorkspace` 下并行团队 | 单桌面通道是瓶颈；正解 = 本地内环 + snapshot 到云由云端跑并行团队（P2e e2，呼应 §四 交接语义） |
| 本地 worker 直接执行 | 本地模式被委派 worker 共用 CEO 同一回合审批门（§九 ⑧）；云模式不下发门（沙箱隔离） |
| 多 worker 进程态 | 审批门 / 通道 / 锁 / handoff 作业现为单进程内存态，多 worker 需前置 Redis + durable queue |

## 九、关键决策（已定）

1. **P0 引入 `WorkspaceBackend` 抽象**：B 为已承诺路线，接口先行（§三、§六）。
2. **不给用户云/本地开关**：模式跟着「文件在哪」自动走；直接聊 / 手机端走云（§七）。
3. **未分组会话 = 每对话独立空间**（`…/conv/<id>/`）；放进文件夹才共用文件夹空间（= 项目）。
4. **同 folder 跨会话 = 文件夹级锁**（进程内，多机再 Redis）；任务内并行小队不受限。
5. **文件进出：先上传**（人人可用、结果可下载）；**`git clone` 紧随**（公开仓先、私有令牌后）。
6. **云存储 = 阿里云 OSS**（通用 S3 接口，dev MinIO，客户端库 `boto3`）；**快照 = 改过文件的任务结束后后台备份 + 手动留版本 + 随时下载**（非每写必存）。
7. **删除生命周期 = 与软删对齐**：软删原样保留可恢复；超保留期（默认 30 天，可配）物理清目录 + 记录 + OSS 备份；「彻底删除」立即清。文件归项目（文件夹）所有。
8. **本地模式 worker 也过执行门**（P2d）：仅 `backend.location=="local"` 把 CEO 审批门透传 worker（触碰本机 GRANTABLE 工具需同意）；云模式不下发门。复用既有审批机制，不另造门。
9. **execute 通道传输期限 = 代码自身超时 + 余量**（P2d，默认 30s）：桌面执行超时才是强杀线；文件 op 走扁平期限（默认 60s）。避免长但合法的执行被传输层提前丢弃留孤儿进程。
10. **对话开始后工作区锁定**（禁跨文件夹移动）：有消息的对话移动会改写工作区目录、翻转模式、孤立文件；零消息空对话可自由归档，有消息后前端隐入口 + 后端 `PATCH …/folder` 实际改 folder 返回 409。
11. **P2e 本地→云交接 = 三段式 + 派发式云作业**：`HandoffJob` 专表 + 隐藏 `mode="handoff"` 作业对话；云作业 autonomous 免审批（区别于 P2d 交互门）；冲突判定服务端权威；完成通知 MVP=轮询，作业为进程内态（重启丢在飞作业，MVP 可接受，后续前置 durable queue）。
