> **状态**：✅ 已确定（五层分层、模块体系、runtime 子包划分、垂直插件、评估体系）

> **与项目结构的关系**：本文描述完整**目标架构**的模块体系与分层约定；实际目录结构见 [`项目结构.md`](/docs/02-架构/项目结构.md)。运行参数 / 接口契约见 [`核心接口定义.md`](/docs/02-架构/核心接口定义.md)。

## 一、五层分层

每个业务模块遵循 `models → schemas → repository → service → router`，调用方向严格单向、不可反转：

| 层 | 职责 | 约束 |
|----|------|------|
| **models** | ORM 定义 | → 见 [核心接口定义.md §6.2](/docs/02-架构/核心接口定义.md)（无 ORM FK、软删除、文件单表等建模约定） |
| **schemas** | Pydantic request/response | 严格区分 request / detail / list item 等分层 |
| **repository** | 纯数据访问 | 接收 AsyncSession；不含业务逻辑 |
| **service** | 业务逻辑 | 构造注入 AsyncSession，内部实例化 repository，组合多 repo |
| **router** | HTTP 端点 | 薄层委托 service，用 DI 别名，不直接操作 DB |

## 二、模块组织

后端按职责分三区。下表只记录**非显然边界**；完整目录 → 见代码 `apps/server/agentcore/`。

**平台核心**（基础设施 + 平台级通用能力）：

| 模块 | 定位 | 边界说明 |
|------|------|----------|
| common | DB / Redis / 消息队列 / 对象存储 / 错误 / 日志 基础设施 | MVP 精简为 db + core |
| middleware | JWT 认证 + 请求日志 + 限流 + 服务间内部认证 | 认证走路由依赖 `api/dependencies.py`；`auth.py` JWT 中间件仍空壳；请求日志/服务间认证 ⏳ |
| user | 注册/登录/JWT 刷新/用户偏好 | 见 [`认证与会话.md`](/docs/05-平台与运维/认证与会话.md) |
| agent | Agent & Team CRUD + 版本管理 + Fork + 语义发现路由 | ⏳ Post-MVP（MVP 用 CEO 按需 `delegate` 动态分配） |
| conversation | 对话管理 + SSE 流式聊天 + Turn 聚合层 | 导出（MD/JSON）+ 公开只读分享 ✅，见 [安全治理 §一](/docs/05-平台与运维/安全权限与治理.md) |
| runtime | ReAct 引擎 + Prompt 组装 + 工具注册 + Agent 委派 + CEO 编排 + 工具审批 | DAG 检查点 ⏳ Phase 2 |
| llm | LLM Gateway — 多 Provider 统一调用 | |
| capability | Tool / Skill / Rule 三类能力实体的定义/绑定/版本 | ⏳ Post-MVP（MVP 内置工具直接注册） |
| file | 文件上传/下载 + 在线文档 + 工作区上下文 + RAG 检索 | ⏳ Day 2 |
| billing | LLM 调用的 token 用量 + 成本记录 | 见 [`成本配额与计费.md`](/docs/05-平台与运维/成本配额与计费.md) |
| task | 异步任务引擎 — 消息队列 + Worker 后台执行 | ⏳ Post-MVP |

## 三、runtime 子包结构

> 目标子包划分如下；实现现状 → 见代码 `apps/server/agentcore/runtime/`。

`runtime/` 是执行核心，按运行时关注点分子包：

| 子包 | 关注点 | 现状 |
|------|--------|------|
| engine | ReAct 主循环（LLM 调用 / 工具执行 / 轮次控制 / 上下文装配） | ✅ `engine/`（loop / round / governance …） |
| runs | **Run 模型**：统一执行单元——RunPlan + WaveScheduler + 执行器 | ✅ |
| journal | **Turn Journal**：每 turn append-only 事实流 | ✅ `journal/`（entries / fold / persist） |
| interactions | **统一交互原语**：server→client 等待的单一类型 | ✅ `interaction.py` |
| delegation | Agent 委派执行：派发 + 契约 + 熔断 + 并发预算 + 预审 | ✅ 经 `delegate` + `runs/` |
| prompt | system prompt 组装（skills / rules / workspace 注入） | ✅ shim → `resolve/prompt` |
| events | SSE 事件类型 + 事件总线 | ✅ |
| host | 运行时宿主端口（各接缝 Protocol） | ✅ `ports.py` |
| resolve | 回合准备：agent→prompt→tools 解析 + 任务复杂度分级 | ✅ `resolve/`（prompt / profile / prepare） |
| memory | 工作记忆：工件存储 + TWM 注入 | ⏳ |
| suspend | 持久暂停/恢复 + checkpoint | ✅ `suspension*.py`（非独立子包） |
| sandbox | 代码执行沙箱后端 | ✅ 在 `tools/sandbox/` |

**CEO 内置编排原语**（`tools/builtin/`，与 `runtime/` 子包同构——按变更原因拆目录）：

| 原语 | 路径 | 子模块 | 现状 |
|------|------|--------|------|
| `delegate` | `tools/builtin/delegate/` | tool / drive / supervised / suspension … | ✅ |
| `ask_user` | `tools/builtin/ask_user/` | tool / suspend / result / schema | ✅ |
| `debate` | `tools/builtin/debate/` | tool / rounds / prompt / events / schema | ✅ |

## 四、垂直插件机制

平台核心行业无关，垂直领域作为可插拔插件接入。核心可在不加载任何垂直时独立启动、测试、发布。

### 契约（6 个贡献点）

| 贡献点 | 用途 |
|--------|------|
| `builtin_modules()` | 无状态内置工具 |
| `tool_providers()` | 有上下文的工具提供器 |
| `routers()` | FastAPI 路由 |
| `task_handlers()` | 异步任务类型处理器 |
| `on_startup()` | 垂直专属设施启动 |
| `on_shutdown()` | 垂直专属设施关闭 |

### 发现机制

约定式扫描垂直子包目录，环境变量白名单控制启用哪些垂直（空 = 纯净核心）。

### 反向依赖消除

垂直可依赖核心，核心不得依赖任何垂直。验证指标：白名单为空时平台核心独立运行。

## 五、评估体系（功能 Layer 1 ✅ / Layer 2 ⏳；多 Agent 对比 P0 ✅）

> **现状**：评估骨架落地于 `agentcore/evals/`（离线 CLI：`python -m agentcore.evals`），三维落地度见下表（功能 Layer 1 + 多 Agent 对比 P0 已落地）。⏳ 未落地：Layer 2 绝对裁判 `LLMJudge`、baseline 回归门禁、等算力 C 臂 / 预算对齐 / 路由闭环。per-PR CI 仅跑零-LLM 自测（假 provider），真模型评测尚无专用 workflow。

| 维度 | 说明 |
|---|---|
| **功能 Layer 1** | 种子完整性 lint + 执行轨迹断言（零 LLM）→ 见代码 `agentcore/evals/{seed_lint,checks,harness}.py` |
| **功能 Layer 2** | 路由准确率 + 输出质量（真 LLM + 裁判 rubric）→ 见代码 `agentcore/evals/judge.py`（`LLMJudge` ⏳） |
| **多 Agent 对比** | 三臂对照 + 成对盲评 + pass^k → 见代码 `agentcore/evals/comparison.py`、`judge.py` |

→ 未落地 P1+ 演进及 CI 深化：见 [`远期规划.md §2.4`](/docs/07-规划/远期规划.md)。
