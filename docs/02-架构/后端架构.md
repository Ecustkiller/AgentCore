## 一、五层分层

每个业务模块遵循 `models → schemas → repository → service → router`，调用方向严格单向、不可反转：

| 层 | 职责 | 约束 |
|----|------|------|
| **models** | ORM 定义 | **目标与现状均无 ORM ForeignKey**（`models.py` 实际无 FK 声明）；引用在应用层维护；主键用 UUID |
| **schemas** | Pydantic request/response | 命名规范 `CreateXxxRequest`、`XxxDetail`、`XxxListItem` |
| **repository** | 纯数据访问 | 接收 AsyncSession；不含业务逻辑 |
| **service** | 业务逻辑 | 构造注入 AsyncSession，内部实例化 repository，组合多 repo |
| **router** | HTTP 端点 | 薄层委托 service，用 DI 别名，不直接操作 DB |

## 三、runtime 子包结构

> **实现现状**：`runtime/` 当前为扁平模块 + `runs/` 子包（`pipeline` / `engine` / `events` / `prompt` / `runs/*` 等已落地）。✅ 结构化挂起 2a/2b 已落地（`suspension*.py`、`paused_turns` 表、`POST …/resume`）。⏳ `journal/`、`resolve/` 子包尚未抽取；Turn Journal 事实流未建表。委派经 `delegate` + `runs/`。下表为目标子包划分。

`runtime/` 是执行核心，按运行时关注点分子包：

| 子包 | 关注点 | 现状 |
|------|--------|------|
| engine | ReAct 主循环（LLM 调用 / 工具执行 / 轮次控制 / 上下文装配） | ✅ 扁平模块 |
| runs | **Run 模型**：统一执行单元——RunPlan + WaveScheduler + 执行器 | ✅ |
| journal | **Turn Journal**：每 turn append-only 事实流 | ⏳ 未抽取 |
| interactions | **统一交互原语**：server→client 等待的单一类型 | ✅ `interaction.py` |
| delegation | Agent 委派执行：派发 + 契约 + 熔断 + 并发预算 + 预审 | ✅ 经 `delegate` + `runs/` |
| prompt | system prompt 组装（skills / rules / workspace 注入） | ✅ |
| events | SSE 事件类型 + 事件总线 | ✅ |
| host | 运行时宿主端口（各接缝 Protocol） | ✅ `ports.py` |
| resolve | 回合准备：agent→prompt→tools 解析 + 任务复杂度分级 | ⏳ 未抽取 |
| memory | 工作记忆：工件存储 + TWM 注入 | ⏳ |
| suspend | 持久暂停/恢复 + checkpoint | ✅ `suspension*.py`（非独立子包） |
| sandbox | 代码执行沙箱后端 | ✅ 在 `tools/sandbox/` |

> 三个一等运行时模型（Interaction / Turn Journal / Run）的目标设计见 [`执行引擎架构设计.md` §十八](/docs/03-AI核心/执行引擎架构设计.md)。

## 四、垂直插件机制

平台核心行业无关，垂直领域作为可插拔插件接入。核心可在不加载任何垂直时独立启动、测试、发布。

### 契约（6 个贡献点）

| 贡献点 | 用途 |
|--------|------|
| `builtin_modules()` | 无状态内置工具 |
| `tool_providers()` | 有上下文的工具提供器 |
| `routers()` | FastAPI 路由 |
| `task_handlers()` | 异步任务类型处理器 |
| `on_startup()` | 垂直专属设施启动 |
| `on_shutdown()` | 垂直专属设施关闭 |

### 发现机制

约定式扫描垂直子包目录，环境变量白名单控制启用哪些垂直（空 = 纯净核心）。

### 反向依赖消除

垂直可依赖核心，核心不得依赖任何垂直。验证指标：白名单为空时平台核心独立运行。

## 五、评估体系（功能 Layer 1 ✅ / Layer 2 ⏳；多 Agent 对比 P0 ✅）

> **实现现状**：评估骨架落地于 `agentcore/evals/`（**离线工具、未接 CI**；CI 仍仅 ruff + pytest + 前端 lint/test）。**功能评估**：评估类型 + 确定性 Check + seed_lint + harness + runner + report + CLI + 8 核心用例 ✅；Layer 2 绝对裁判 `LLMJudge`、baseline 回归门禁 ⏳。**多 Agent 对比评估**：`comparison` runner + 成对裁判 `LLMPairwiseJudge`（盲评+位置对调）+ 13 例 + `--compare` CLI ✅；等算力 C 臂 / 预算对齐 / 路由闭环 ⏳。

| 维度 | 说明 |
|---|---|
| **分类** | **功能评估**（判单条回合对不对）= Layer 1 离线确定性（PR 硬门禁）+ Layer 2 在线 LLM 绝对裁判（软门禁）；**多 Agent 对比评估**（判团队是否真比单体好）= 三臂成对盲评（软门禁）。共用 `agentcore/evals/` 包 |
| **功能 Layer 1** | 种子完整性 lint + 执行轨迹断言（零 LLM、毫秒级）→ 见代码 `agentcore/evals/{seed_lint,checks,harness}.py` |
| **功能 Layer 2** | 路由准确率 + 输出质量（真 LLM 执行 + 裁判 rubric ≥3 分）→ 见代码 `agentcore/evals/judge.py`（`LLMJudge` ⏳ P1） |
| **多 Agent 对比** | 三臂对照（单体/团队/等算力单体）+ 成对盲评 + pass^k + 按原型分段，制胜边界喂回路由 → 见代码 `agentcore/evals/comparison.py`、`judge.py`（`LLMPairwiseJudge` ✅） |
