## 一、五层分层

每个业务模块遵循 `models → schemas → repository → service → router`，调用方向严格单向、不可反转：

| 层 | 职责 | 约束 |
|----|------|------|
| **models** | ORM 定义 | 无 ForeignKey（应用层维护引用；MVP 阶段可使用 FK 简化开发，上线前评估是否需要去除）；主键用 UUID |
| **schemas** | Pydantic request/response | 命名规范 `CreateXxxRequest`、`XxxDetail`、`XxxListItem` |
| **repository** | 纯数据访问 | 接收 AsyncSession；不含业务逻辑 |
| **service** | 业务逻辑 | 构造注入 AsyncSession，内部实例化 repository，组合多 repo |
| **router** | HTTP 端点 | 薄层委托 service，用 DI 别名，不直接操作 DB |

## 二、模块组织

后端按职责分三区：

**平台核心**（基础设施 + 平台级通用能力）：

| 模块 | 定位 | MVP 阶段 |
|------|------|----------|
| common | DB / Redis / 消息队列 / 对象存储 / 错误 / 日志 基础设施 | ✅ MVP（精简为 db + core） |
| middleware | JWT 认证 + 请求日志 + 限流 + 服务间内部认证 | 部分落地（`rate_limit.py` ✅ 已实现并挂载[auth 端点按 IP 固定窗口限流]；`auth.py` JWT 中间件仍空壳——认证走路由依赖 `api/dependencies.py`；请求日志/服务间认证 ⏳） |
| user | 注册/登录/JWT 刷新/用户偏好 | ✅ 核心已落地（注册/登录/刷新/登出/me；见 [`认证与会话.md`](../05-平台与运维/认证与会话.md)） |
| agent | Agent & Team CRUD + 版本管理 + Fork + 语义发现路由 | ⏳ Post-MVP（MVP 用 CEO 按需 `delegate` 动态分配） |
| conversation | 对话管理 + SSE 流式聊天 + Turn 聚合层 | ✅ MVP |
| runtime | ReAct 引擎 + Prompt 组装 + 工具注册 + Agent 委派 + CEO 编排 + 工具审批 | ✅ MVP（DAG 检查点 ⏳ Phase 2） |
| llm | LLM Gateway — 多 Provider 统一调用 | ✅ MVP |
| capability | Tool / Skill / Rule 三类能力实体的定义/绑定/版本（能力地基层） | ⏳ Post-MVP（MVP 内置工具直接注册） |
| file | 文件上传/下载 + 在线文档 + 工作区上下文 + RAG 检索 | ⏳ Day 2 |
| billing | LLM 调用的 token 用量 + 成本记录 | ⏳ Post-MVP（设计见 [`成本配额与计费.md`](../05-平台与运维/成本配额与计费.md)） |
| task | 异步任务引擎 — 消息队列 + Worker 后台执行 | ⏳ Post-MVP |

**平台业务**（面向用户的业务模块）：

| 模块 | 定位 | MVP 阶段 |
|------|------|----------|
| webhook | Agent 触发器 + headless Run 执行（事件驱动） | ⏳ Post-MVP |
| scheduler | 提醒与日程 | ⏳ Post-MVP |
| attention | 跨会话「待办流」：聚合可恢复的暂停 Run + 待审批工具调用 | ⏳ Post-MVP |

| table | 多维表格 — 结构化数据记录 CRUD | ⏳ Post-MVP |
| admin | 管理后台：管理员鉴权 + 操作审计 + 用户运营 | ⏳ Post-MVP |
| desktop | 桌面自动更新策略（版本政策 + 远程熔断 + 下载入口） | ⏳ Post-MVP |
| flags | 特性开关 / 远程配置（灰度百分比 + 最低客户端版本门控） | ⏳ Post-MVP |

## 三、runtime 子包结构

> **实现现状**：`runtime/` 当前为扁平模块 + `runs/` 子包（`pipeline` / `engine` / `events` / `prompt` / `runs/*` 等已落地；`suspend` / `journal` / `resolve` 为空壳）。委派经 `delegate` + `runs/`。下表为目标子包划分。

`runtime/` 是执行核心，按运行时关注点分子包：

| 子包 | 关注点 |
|------|--------|
| engine | ReAct 主循环（LLM 调用 / 工具执行 / 轮次控制 / 上下文装配） |
| runs | **Run 模型**：统一执行单元——RunPlan + WaveScheduler + 执行器 |
| journal | **Turn Journal**：每 turn append-only 事实流 |
| interactions | **统一交互原语**：server→client 等待的单一类型 |
| delegation | Agent 委派执行：派发 + 契约 + 熔断 + 并发预算 + 预审 |
| prompt | system prompt 组装（skills / rules / workspace 注入） |
| events | SSE 事件类型 + 事件总线 |
| host | 运行时宿主端口（各接缝 Protocol） |
| resolve | 回合准备：agent→prompt→tools 解析 + 任务复杂度分级 |
| memory | 工作记忆：工件存储 + TWM 注入 |
| suspend | 持久暂停/恢复 + checkpoint |
| sandbox | 代码执行沙箱后端 |

> 三个一等运行时模型（Interaction / Turn Journal / Run）的目标设计见 [`执行引擎架构设计.md` §十八](../03-AI核心/执行引擎架构设计.md)。

## 四、垂直插件机制

平台核心行业无关，垂直领域作为可插拔插件接入。核心可在不加载任何垂直时独立启动、测试、发布。

### 契约（6 个贡献点）

| 贡献点 | 用途 |
|--------|------|
| `builtin_modules()` | 无状态内置工具 |
| `tool_providers()` | 有上下文的工具提供器 |
| `routers()` | FastAPI 路由 |
| `task_handlers()` | 异步任务类型处理器 |
| `on_startup()` | 垂直专属设施启动 |
| `on_shutdown()` | 垂直专属设施关闭 |

### 发现机制

约定式扫描垂直子包目录，环境变量白名单控制启用哪些垂直（空 = 纯净核心）。

### 反向依赖消除

垂直可依赖核心，核心不得依赖任何垂直。验证指标：白名单为空时平台核心独立运行。

## 五、评估体系

> **实现现状**：本节为评估体系**目标设计**，MVP **未落地**——CI（`.github/workflows/ci.yml`）仅跑后端 ruff + pytest（已有 `runs/` 等单测）+ 前端 lint/test；无种子 lint、无执行轨迹断言、无 Layer 2 LLM 评判。

### 5.1 两层模型

| 层 | 性质 | 依赖 | 门禁 | 触发 |
|---|---|---|---|---|
| **Layer 1** 离线确定性 | 静态/机制检查 | 零 LLM、零 DB、毫秒级 | **PR CI 硬门禁** | 每次 PR |
| **Layer 2** 在线 LLM-in-the-loop | 真实 Agent 执行 + 评判 | 真 LLM + 已 seed 的 DB | **软门禁**（仅告警不阻断） | 定时/手动 |

**为何这样分**：质量评测天然要调真 LLM（语义判断无法 mock），但真 LLM 慢、要钱、非确定——进 PR 硬门禁会 flaky 且昂贵。把「给定事件流即可裁定」的确定性部分下沉 Layer 1 硬门禁，把「必须真 LLM」的留 Layer 2 软门禁。

### 5.2 Layer 1 维度

| 维度 | 说明 |
|---|---|
| **种子完整性 lint** | 种子 JSON 的静默失败检测（委派目标不存在、团队成员缺失、非法分类等） |
| **执行轨迹断言** | 从运行时事件流还原结构化轨迹，按声明式期望裁定过程正确性 |

### 5.3 Layer 2 维度

| 维度 | 评什么 | 方法 |
|---|---|---|
| **路由准确率** | Pilot 的路由决策质量 | 真实 LLM 单轮，截获 `delegate` 目标与 golden 比对。固定 temperature=0 |
| **输出质量** | 最终回答是否答到点 | 端到端真实 Agent 执行 + LLM 裁判按 rubric 打分（1-5） |

**判定口径**：规则断言全过 **且** 裁判分 ≥ 3 才算通过。

> 工程门禁（棘轮 / 类型债 / 结构治理 / 跨端契约门禁）见 [`部署与运维.md` §九](../05-平台与运维/部署与运维.md)。
