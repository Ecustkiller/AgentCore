## 二、后端分层（apps/server/agentcore）

> 目录与文件清单 → 见代码：`apps/server/agentcore/`。编排 = CEO + `delegate`；多 Agent 调度在 `runtime/runs/`。下表为代码看不出的依赖约束。

| 模块 | 职责 | 依赖 | 不依赖 |
|------|------|------|--------|
| `api/` | HTTP 入口，参数验证，SSE 响应 | schemas, conversation, middleware | runtime, llm, tools |
| `middleware/` | JWT 认证、限流 | db, core | 业务模块 |
| `conversation/` | 对话生命周期管理，stream_chat 入口 | runtime, db, memory | api |
| `runtime/` | CEO ReAct 循环、`delegate` 按需委派、多 Agent DAG 波次调度（`runs/`） | llm, tools, core | conversation, api |
| `llm/` | LLM API 调用封装 | core | 所有其他模块 |
| `tools/` | 工具注册、执行、审批 | sandbox, core | 所有其他模块 |
| `memory/` | 长期记忆维护（ops 提取/套用 + 文件存储）+ 会话标题接口 | llm, core, config | db, runtime |
| `db/` | 数据持久化 | core | 所有其他模块 |
| `core/` | 共享类型和工具 | 无 | 所有其他模块 |

### 调用链路

```
POST /v1/conversations/{id}/messages
  → api.routes.conversations.send_message()
  → conversation.service.stream_chat()                # 入口：持久化用户消息、载入历史
      → conversation.history.load_history()           # 会话内历史（最近 N 条）
      → runtime.pipeline.run_chat_pipeline()          # ChatPipeline（Prepare + Execute）
          │
          ├─ [Prepare]
          │   → memory.store 载入用户长期记忆
          │   → runtime.prompt.assemble_system_prompt()   # 记忆包成 <rules> 软注入
          │   → 注册 8 个内置工具（web_search / read_url / file_read·write·list / str_replace / grep / code_execute）
          │
          ├─ [Execute]  CEO + delegate
          │   → runtime.engine.react_loop()            # CEO 自己应答；工具集 = 内置工具 + delegate
          │       → llm.deepseek.stream()              # 调用 LLM（流式）
          │       → tools.registry.execute()           # 执行工具（并行，上限 5）
          │       → delegate（按需委派，非终态）：
          │           → runtime.runs.builder.build_run_plan()   # tasks → RunPlan（depends_on 定形）
          │           → runtime.runs.wave.WaveScheduler.run()   # 逐波调度（树级并发预算）
          │           → runtime.runs.executor 每个 worker 跑一次 react_loop
          │           → 产出回交 CEO 的 ReAct 循环，CEO 用自己声音收尾
          │       → runtime.events.emit()              # SSE 推送（content_delta / run_*）
          │
          └─ [Finalize]                                # 在 conversation.service 内，pipeline 结束后
              → db.repositories.save()                 # 持久化助手消息
              → memory.conversation_title 生成标题       # 仅首轮；title_generated SSE 即时刷新侧栏
              → memory.maintenance.maintain_user_memory()  # 每轮 extract→apply→save，无变化则跳过写
  → SSE StreamingResponse → Client
```

## 三、前端组织原则（apps/desktop/src）

> 目录与文件清单 → 见代码：`apps/desktop/src/`（`main/` 主进程、`preload/` 安全桥、`shared/` 三端共享契约、`renderer/` React 渲染层）。下表为代码看不出的组织判据。

1. **页面级布局（pages/ + router）**：全局只有 AppShell（侧栏 + Outlet），各页面自定义布局（对齐 [前端UX设计.md](../04-前端/前端UX设计.md)）
2. **components/ 按业务域分目录**：chat / graph / files / sidebar / layout，组件就近组织
3. **stores/ 集中管理**：多页面共享状态（如 execution 被 chat 与 graph 同时消费）；单测就近放 `stores/__tests__/`
4. **shared/ipc-contract.ts**：主/preload/renderer 三端共享的 IPC 契约单一真相源（本地文件系统）
5. **types/ 自动生成（待接入）**：`api.generated.ts` 规划由后端 OpenAPI schema 生成，不手动编辑
6. **shadcn/ui（待建）**：基础组件计划从 shadcn/ui 添加（`components/ui/`），当前直接用 Tailwind

## 四、部署结构（deploy/）

```
deploy/
├── docker-compose.dev.yml         # 本地开发（PG + Redis + SearXNG）
├── docker-compose.server.yml      # 生产基础设施（infra-only；应用在宿主机以 uv/systemd 运行）
├── config/production.env.example  # 生产环境变量模板（真实 production.env 被 .gitignore 忽略）
├── searxng/settings.yml           # SearXNG 引擎配置（dev/prod 共用）
└── scripts/init-db.sh             # DB 初始化
```

> 后端 Dockerfile、生产应用容器化 compose、Nginx / Cloudflare 配置源、`deploy-server.sh` 自动部署**尚未纳入仓库**（详见 [`../05-平台与运维/部署与运维.md` §三](../05-平台与运维/部署与运维.md)）。
