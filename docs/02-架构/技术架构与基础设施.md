## 一、Agent 运行时模型 ✅ 已确定

分层设计：Agent 逻辑和工具执行采用不同的运行时模型。

| 层 | 运行时 | 说明 |
|---|---|---|
| Agent 逻辑 | asyncio 协程 | 纯 I/O 密集型，用协程最轻量 |
| 普通工具 | 同进程异步 | 文件读写、搜索等安全操作 |
| 代码执行 | 受限 subprocess（MVP，`SandboxProvider` 抽象预留） | 当前仅 timeout + tempdir 隔离；Docker/gVisor 升级后置 |

### 沙箱架构原则

- 设计抽象沙箱接口，后端实现可插拔
- 默认禁止出站流量、凭据不进沙箱、文件系统边界严格、全量审计日志

> 沙箱安全的完整设计见 [`../05-平台与运维/安全权限与治理.md`](/docs/05-平台与运维/安全权限与治理.md)。

## 二、LLM 接入策略 ✅ 已确定

MVP 只接入 **DeepSeek V4 单 Provider**，经命名 `ModelProfile` 分场景——编排器 / 单聊 / worker 按角色选 profile，不在各调用点手抄模型参数。

→ 见 [核心接口定义.md §1.2](/docs/02-架构/核心接口定义.md) 与 `.cursor/rules/llm.mdc`；轮数预算见 [`../03-AI核心/执行引擎架构设计.md` §十六](/docs/03-AI核心/执行引擎架构设计.md)；API 细节见 [`../06-参考/DeepSeek-V4-API参考.md`](/docs/06-参考/DeepSeek-V4-API参考.md)。

## 三、数据存储 ✅ 已确定

最小组件策略：用尽量少的组件覆盖所有存储需求。

| 组件 | 覆盖的数据 | 说明 |
|------|----------|------|
| PostgreSQL + pgvector | 结构化数据 + 向量检索 | 用户/账户、Agent 配置、会话历史 |
| Redis | 实时状态、缓存 | Agent 运行状态、任务进度、热数据缓存 |
| S3 兼容存储 | 大文件 | 代码执行结果、上传文件、工具输出 |

> **实现现状**：开发 compose（`deploy/docker-compose.dev.yml`）起 PostgreSQL 16 + Redis。**pgvector 扩展、向量检索 ⏳ 未接入**；server **不读写 Redis**（`config.redis_url` 已配置未用）。✅ **工作区快照** `StorageProvider` 已接线（dev 文件系统 / prod 可切 S3，见 `storage/`）；⏳ **通用上传对象存储**（头像、大附件等独立 bucket 流程）未接入。**Agent 长期记忆走工作区文件树**（AI 维护的规则文件），不落 PG 表（见 [`../03-AI核心/Agent记忆与知识系统.md`](/docs/03-AI核心/Agent记忆与知识系统.md)）。数据模型与建模约定见 [`核心接口定义.md` §六](/docs/02-架构/核心接口定义.md)。
