## 一、Agent 运行时模型 ✅ 已确定

分层设计：Agent 逻辑和工具执行采用不同的运行时模型。

| 层 | 运行时 | 说明 |
|---|---|---|
| Agent 逻辑 | asyncio 协程 | 纯 I/O 密集型，用协程最轻量 |
| 普通工具 | 同进程异步 | 文件读写、搜索等安全操作 |
| 代码执行 | 受限 subprocess（MVP，`SandboxProvider` 抽象预留） | 当前仅 timeout + tempdir 隔离；Docker/gVisor 升级后置 |

### 沙箱架构原则

- 设计抽象沙箱接口，后端实现可插拔
- 默认禁止出站流量、凭证不进沙箱、文件系统边界严格、全量审计日志

> 沙箱安全的完整设计见 [`../05-平台与运维/安全权限与治理.md`](/docs/05-平台与运维/安全权限与治理.md)。

## 二、LLM 接入策略 ✅ 已确定

MVP 只接入 DeepSeek V4，用 Flash + Pro 双模型覆盖所有场景：编排器 / 单聊 / worker 按角色分思考档位，标题与记忆维护走非思考。开发期统一 `high` / `max` 两档有效思考强度——worker 的 `fast` / `strong` 同为 `high`，靠回合预算区分（两者基座均 Flash，`strong` 经质量档可升 Pro）；`max` 由 per-agent 覆盖按需解锁（只升不降）。

> **档位与思考强度以 `llm.mdc` §思考强度按角色分档 为权威**；轮数预算与模型映射见 [`../03-AI核心/执行引擎架构设计.md` §十六](/docs/03-AI核心/执行引擎架构设计.md)，运行参数单一真相源是 `apps/server/agentcore/llm/config.py` 的 `PROFILES`。DeepSeek V4 API 细节见 [`../06-参考/DeepSeek-V4-API参考.md`](/docs/06-参考/DeepSeek-V4-API参考.md)。

## 三、数据存储 ✅ 已确定

最小组件策略：用尽量少的组件覆盖所有存储需求。

| 组件 | 覆盖的数据 | 说明 |
|------|----------|------|
| PostgreSQL + pgvector | 结构化数据 + 向量检索 | 用户/账户、Agent 配置、会话历史、Agent 记忆 |
| Redis | 实时状态、缓存 | Agent 运行状态、任务进度、热数据缓存 |
| S3 兼容存储 | 大文件 | 代码执行结果、上传文件、工具输出 |

> **实现现状**：开发 compose（`deploy/docker-compose.dev.yml`）起 PostgreSQL 16 + Redis；**pgvector 扩展、S3/MinIO 对象存储、向量检索均未接入**，server 代码当前不读写 Redis / S3（`config.redis_url` 已配置未用）。数据模型与建模约定见 [`核心接口定义.md` §六](/docs/02-架构/核心接口定义.md)。
