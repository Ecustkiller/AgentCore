## 〇、一句话结论

那个参考实现 ≈ **我们自己 docs 里大量标着「⏳ 未实现 / 目标态」的运行时设计的一个可运行样板**，并且它的核心编排架构**恰好就是我们 2026-06-14 刚确认的「CEO 主 Agent + 单一 `delegate` 原语」方向**（见 `规划/编排器重定位-讨论与规划.md` 的 D1′/D2/D3）。

所以「借鉴它」的本质不是「换架构」，而是：

1. **照一个已跑通的样板，把我们已决定但没落地的东西按优先级落地**（Run 统一模型、WaveScheduler、Turn Journal、ContextComposer、TWM/recall、统一 Interaction、delegate 工具、Arena、Preflight 审计……全在我们 docs 里，全已在那边落地）；
2. 它另有 **4 项超出我们现有设计**的方向，需要单独决策：**Sidecar 可迁移核 / JSON-RPC 运行时协议 / 客户端工具执行·本地优先 / Turn Journal 作为唯一事实源**。

## 三、它如何回答我们刚留下的开放问题（编排重定位 O1–O4）

`规划/编排器重定位-讨论与规划.md` §四留了 4 个「落地阶段再定」的开放问题。参考实现对每个都给了已验证的工程答案：

| 我们的开放问题 | 参考实现的答案 | 关键文件 |
|---|---|---|
| **O1 计划 vs 动态的边界**（CEO 何时全景、何时临场喊人） | 同一 `delegate` 工具：一次塞 N 个 task = 全景计划；运行时 `RunPlan.add` 增量追加（`RunOrigin.CAPTAIN`）= 动态委派；`candidates>1` 自动升 best-of-N。**正是我们 D1′ 的设想，已跑通**。复杂域用 `adaptive`（CEO 自主构图），简单域用固定 `pipeline/fan_out`。 | `runs/builder.py`、`runs/plan.py`、`delegation/manager.py` |
| **O2 收尾开销**（CEO 重读 worker 产出的延迟/token） | 合稿是 DAG 的**终端 `SYNTHESIS` 节点**：先用确定性代码 `default_pipeline_output` 按依赖拼接子结论（诚实暴露缺口），再交 captain **无工具引擎**合稿；`result_handling: pass_through(全文)/summarize(省 token)` 逐边控制保真度。 | `runs/synth_exec.py`、`delegation/synthesis.py` |
| **O3 并行表达**（动态委派如何保留并行） | 不靠并行 tool call：`delegate` 的 `tasks[]` 中无 `depends_on` 的节点天然落在同一 wave 并行；有依赖即串行/DAG。并行兄弟节点互注入 `sibling_summary`（分工感知，防重复劳动）。 | `runs/wave.py`、`runs/builder.py` |
| **O4 检查点 LLM 审视**（是否补上 CEO 审视） | 用 **Preflight Audit** 实现：`delegate`(提案)→ 系统自动调审计 Agent →`confirm_plan`(确认) 两阶段；有界预检环（默认 ≤2 次，超限带风险放行）；质检 Agent 打回触发有界自动返工；外加 `plan_review` interaction 让用户介入。 | `delegation/preflight.py`、`delegation/manager.py` |

> 含义：我们可以把 O1–O4 从「待定」直接收敛为「参照样板落地」，省去重新探索。

## 四、五大子系统可借鉴清单（按子系统）

> 每条标注**借鉴难度**（低/中/高）。难度=结合我们现状的迁移成本，非那边的实现复杂度。

### 4.1 执行引擎与多 Agent 运行时
- **统一 Run 模型 + WaveScheduler + RunKind 分发**（中）：消灭 single/parallel/DAG/team 多套代码路径，前端只需一种 `run_*` 协作图。**最高优先级地基**。
- **调度/执行分离**（中）：`RunScheduler` 协议 + 注入 `RunExecutor`，调度纯函数可单测；云/本地只换 executor 叶子。
- **树级并发预算 `gather_bounded`**（中）：嵌套委派时防 6×6×6 爆炸，比单纯 wave 宽 cap 更安全。
- **声明式 `RunPolicy`**（低）：`on_failure(retry/skip/abort/degrade)`、契约门、`candidates` 从代码分支变数据。
- **Ports 依赖注入**（低）：`runs` 包零 infra 依赖，全分支可 fake 单测。

### 4.2 委派与团队协作
- **队长 ReAct + `delegate` 工具，而非外部 Planner LLM**（中）：编排决策与领域推理同属队长人格，计划可随对话动态修订。**直接落地我们的 CEO/D1′**。
- **Agent 种子即产品：prompt 内嵌协作拓扑 + `delegations` 白名单**（低）：把 DAG 模式/快慢通道/返工环写进队长 instructions，平台只提供 `delegate` 原语。可直接借鉴 `seeds/agents/*.json` + `seeds/teams/*.json` 的契约结构。
- **`adaptive` vs `pipeline`/`fan_out` 双模式团队**（中）：复杂域队长自主构图，简单域固定编排，用户零学习成本。
- **逐子任务契约门 + `result_handling`**（中）：检索→写作链路 `pass_through` 保真，合稿前 `summarize` 省 token。
- **RoutingEngine 作白名单外扩展（非主路由）**（低）：embedding 语义匹配只用于「Agent 发现」与「动态委派扩展」，主路由仍是队长 LLM 枚举 `delegate` 目标——保住 Multi-Agent First「人定义角色」。

### 4.3 协议 / Sidecar / 工具系统
- **声明式工具加载 + analyze 读写分离**（低）：`AgentVersion.tools` 按 category/tool_id 过滤，`analyze` Agent 自动 strip mutation 工具。**落地我们约束3**。
- **双注册表：`@builtin_tool` 装饰器 + `ToolProvider` 上下文注册**（中）：无状态工具简单注册，需 DB/session/桌面的工具可插拔；`ToolContext` 显式传参替代 contextvar 全局态。
- **`CodeSandbox` 协议层替代裸 subprocess**（低-中）：`python_exec` → `get_sandbox()`，默认 off，可换 gvisor，统一安全门。
- **Capability 市场与运行时 connector 分离**（中）：DB 目录 + `http`/`mcp` connector 执行桥，用户可配工具无需改代码。（中长期）
- **JSON-RPC 2.0 统一运行时协议**（中-高，见 §五）。
- **Sidecar 可迁移核**（高，见 §五）。
- **客户端工具执行 + 不透明 root_id 本地优先**（中-高，见 §五）。

### 4.4 上下文 / 记忆 / 会话编排
- **跨 turn 只回放 user/assistant 文本 + ask_user 答案特例**（低）：根治 orphaned tool_calls 400，又保留澄清问答记忆；可测试锁定。**低成本高收益，建议尽早做**。
- **ContextComposer（Segment + Placement + 中央预算）**（中）：把「顺序/缓存/裁剪」类型化，防止以后改窗口把 volatile 块挪到 prefix 前面废掉缓存。
- **TWM + Artifact Recall 双层运行时记忆**（中）：TWM 锚定长任务；trim 不丢信息可 recall；比「整段摘要」更可控。
- **统一 Interaction 原语（4 种等待一个 bridge）**（中）：消灭 4 套重复挂起；approval 可持久化、其余 Redis-only。
- **Turn Journal 事实流 + 投影层**（高，见 §五）。
- **PromptAssembler 分层 + Rules 统一 + catalog/consult 按需**（中）：角色差异靠 binding 而非硬编码，大 skill 集不爆窗。

### 4.5 桌面端多 Agent 可视化 UX
- **ToolCallGroup 三层折叠**（低）：总结条 / 相邻同名合并 / ask_user 内联——工具刷屏不挤占最终答案。
- **DecisionCard 统一决策带**（低）：approval/plan/ask/rework 视觉一致，固定在输入框上方；ask 时隐藏输入框防双输入。
- **TaskStatePanel（TWM 内嵌气泡）**（低）：Agent 自报目标/计划/发现/待解问题，流式展开、历史收起。
- **runs/chat 双 store CQRS + message_end 快照**（高）：实时执行槽与持久快照分离，历史回放零特殊路径。
- **React Flow 协作图 + 结构指纹防抖**（中）：`structureKeyOf` 避免流式 token 整图重排；节点按 runId 独立订阅 liveness。
- **SSE 事件类型代码生成 + 穷尽 dispatch**（中）：前后端契约 CI 漂移门禁，新增事件编译失败而非运行时漏处理。

## 五、超出我们现有设计、需单独决策的 4 个架构方向

> 这 4 项**不在**我们现有 docs 里，是参考实现独有的架构投入。每项都是「架构选型」级别，**请人拍板**。

### A. Sidecar 可迁移核（桌面本地跑同一引擎）
- **是什么**：桌面 spawn 一个 Python 子进程 `python -m agentcore.sidecar`，通过 stdio JSON-RPC 与 Electron 通信；进程内跑**同一套 `RuntimeEngine`**，只把宿主端口换成本地实现（SQLite journal/artifacts/definitions、内存 pause、in-process bridge）。Agent 定义从云端 `resolution-bundle` 拉取并缓存到本地 `definitions.db`，**离线可降级**。
- **价值**：桌面优先产品的本地执行/离线/弱网/隐私基础；云与本地同一引擎代码。
- **代价/风险**：宿主端口面很大（journal/bridge/billing/artifact/delegation…）；双实现维护成本；**高**难度。
- **建议**：列为中长期目标（Phase 3），先不动；但**新代码尽量按"引擎面向宿主端口"组织**，为将来留缝。

### B. JSON-RPC 2.0 统一运行时协议
- **是什么**：用 JSON-RPC 2.0 承载**整轮对话运行时**（9 个 client 方法 initialize/startTurn/resume/pause/cancel/respond/getResumable/listPending/subscribe），事件流映射为 notification，传输可换 stdio（sidecar）/WebSocket（云）。交互走 `*_requested` 事件 + `respond`，不用反向 RPC。**注意：这不是 MCP**（MCP 仍可用于"Agent↔外部工具"）。
- **价值**：云/桌面/UI 一套代码；pause/resume/交互回值天然统一。
- **代价/风险**：要把现有 SSE+HTTP 端点重构为协议层；**中-高**难度。可渐进（先 stdio sidecar，再 WS）。
- **建议**：与 A 绑定决策——若做 Sidecar 则顺带做协议层；否则暂缓。

### C. 客户端工具执行 + 本地优先 folder 模型
- **是什么**：部分工具带 `client_exec`（`ClientFsOp`），运行时发 `client_tool_requested` 事件 → 桌面 `client-tool-exec.ts` 在本机执行 fs/exec（read/write/edit/search/exec_command/fetch）→ 回传结果解阻塞。云端**只持不透明 `root_id`+相对路径，绝对路径不出桌面**。folder 身份↔本地路径靠 `.agentcore/project.json` dotfile 绑定；`PENDING_LANDING_ROOT_ID` 懒创建落点（纯聊天不建空目录）。
- **价值**：**对"桌面优先 + 真碰用户本地文件"的产品定位价值极高**——这是 Cursor 式体验的关键；我们现在只有 `fs-service.ts` 雏形。
- **代价/风险**：需 Electron IPC + 授权根模型 + 懒落点 + 前后端 `CLIENT_FS_OPS` 单一真相源；**中-高**难度。
- **建议**：**这一项可能是对我们产品差异化收益最高的借鉴**，建议优先级上调，列入近-中期重点讨论。

### D. Turn Journal 作为唯一事实源（投影架构）
- **是什么**：一次 turn 所有事实写入 append-only journal（9 类），持久化 messages/turns 行、跨 turn 历史、暂停 fold 全部从 journal **投影**出来，而非内存 `ChatResult` 手拼。暂停恢复只存「派生态 fold（loop/TWM/summary）」，**不存 history**，resume 时从 journal 重建。
- **价值**：单一真相源，消除 SSE/DB/resume/历史四处手拼导致的补丁族（我们 docs §18.3 已认这个方向）。
- **代价/风险**：是运行时持久化的**地基级重写**；**高**难度，牵一发动全身。
- **建议**：作为「Run 统一模型」落地后的第二阶段地基；不宜与业务功能并行赶工。

## 六、分期借鉴建议（提案）

> 排序依据：①对齐我们已定方向、②风险/难度、③对产品差异化的价值。

**Phase 1 — 对齐已定方向、低风险先落地**
1. 统一 `delegate` 工具单一原语（落地编排重定位 D1′/D2/D3，解 O1–O4）。
2. 统一 Run 模型 + WaveScheduler + RunKind 分发（执行引擎地基）。
3. 声明式工具加载 + `analyze` 读写分离（落地约束3）。
4. 跨 turn 只回放文本 + ask_user 特例（低成本高收益）。
5. 前端：ToolCallGroup 三层折叠 + DecisionCard 统一决策带 + TaskStatePanel。

**Phase 2 — 补齐目标态运行时**
6. ContextComposer + TWM/recall。
7. 统一 Interaction 原语（4 kind 一个 bridge）。
8. Arena/best-of-N + Preflight 审计 + 有界返工。
9. 前端：React Flow 协作图 + runs/chat 双 store + SSE 类型代码生成。
10. Turn Journal 投影架构（地基级，单独立项）。

**Phase 3 — 架构级，需专门立项 + 人确认**
11. 客户端工具执行 + 本地优先 folder（**建议从 Phase 3 上调讨论**，见 §五C）。
12. Sidecar 可迁移核 + JSON-RPC 运行时协议（A+B 绑定）。
13. 能力市场 + connector（http/mcp）。

**暂不借鉴**：异步委派 NATS worker（复杂度高、MVP 用不上）、video-* / billing / social / 法律垂直插件（与 AI 核心无关）。

## 七、待你拍板的问题（驱动后续详细讨论）

1. **借鉴的目标定位**：是「照样板把我们已定的目标态逐步落地」，还是「更激进地直接对齐参考实现的架构」？这决定 Phase 划分的激进程度。
