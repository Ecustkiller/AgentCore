## 一、背景与目标

- 现状：应用以 `_MVP_USER_ID` 硬编码单用户跑通，**无任何真实鉴权**。
- 目标：注册 / 登录 / 登出 / 会话保持（令牌轮换）+ **资源按用户隔离** + 一条可上公网的安全基线。
- 边界：本期只做「账号密码 + 会话隔离」。第三方/OAuth、组织/团队、细粒度 RBAC **不在本期**。

## 二、现状摸底（精确事实）

| 已有地基 | 缺失 / 风险 |
|---|---|
| `config.py`：JWT secret / access 30min / refresh 7d | 无 Cookie 相关配置（secure/samesite/domain） |
| `db/models.py`：`RefreshToken` 完整（`token_hash`/`token_family`/`expires_at`/`revoked_at`/`rotated_at`，是轮换+重用检测设计） | 🟥 **`users` 表无密码列**（仅 `username/display_name/email/role/status`）→ 需 schema 迁移 |
| `core/errors.py`：已备 `AuthenticationError(401)`/`AuthorizationError(403)` | `middleware/auth.py`、`routes/auth.py` 均空壳 |
| `pyproject.toml`：已装 `python-jose[cryptography]`、`passlib[bcrypt]` | `UserRepository` 仅 `get_by_id`；`RefreshToken` 无 repository |
| 前端 `api.ts` 已 `credentials:"include"`；`main.py` CORS 已 `allow_credentials=True` | 前端无登录/注册 UI、无 401 刷新重试、无 auth store |
| `.cursor/rules/api.mdc` 已规定注入约定 `AuthUser`/`OptionalUser`、「权限在 service 层校验」 | 该约定**尚无实现**（全仓无 `get_current_user`） |

### 🟥 两个必须正视的风险

1. **`users` 无密码列**：密码登录需 alembic 迁移加 `password_hash` + `email` 唯一约束；且现存 `_MVP_USER_ID` 行需处理（见 D7）。
2. **会话路由零归属校验（IDOR）**：`get/update/delete/{id}`、`/{id}/messages`、`/{id}/checkpoints/.../resolve` 现在**只按 ID 取，不校验属主**——任何人拿到 ID 即可读写他人会话。多用户上线**必须同步堵上**，否则鉴权形同虚设。

## 三、关键决策点（待你拍板）

> 每项给出推荐与理由；标 ⭐ 的是我建议的默认。

| # | 决策 | 选项与推荐 | 理由 |
|---|---|---|---|
| D1 | 凭证形态 | ⭐邮箱+密码 / 用户名+密码 / +OAuth(后期) | `email` 列已存在；邮箱可承载找回密码 |
| D2 | 令牌传输 | ⭐httpOnly Cookie / Authorization Bearer | 前端已 `credentials:include`、CORS 已放行；SSE/fetch 天然带 Cookie，Bearer 在 SSE 上传 token 麻烦 |
| D3 | 令牌载体 | ⭐双 httpOnly Cookie：access(短) + refresh(长, `path=/v1/auth/refresh`) | refresh 限定 path，减小暴露面 |
| D4 | 密码哈希库 | passlib+bcrypt 有坑(passlib1.7.4 读 `bcrypt.__about__` 在 bcrypt≥4.1 报错)。⭐换 `pwdlib[argon2]`(argon2id) / 或 pin `bcrypt<4.1` / 或直用 `bcrypt` | **新依赖决策**；pwdlib 现代、默认 argon2id，规避兼容坑 |
| D5 | CSRF 防护 | ⭐SameSite=Strict + 写操作校验自定义头(如 `X-CSRF`)；纯 Web 端再加双提交 token | 桌面端(Electron)风险低，起步从简但不裸奔 |
| D6 | 注册开放性 | ⭐邀请码/白名单 起步 / 完全公开+限流 | 公网防滥用；上线初期可控 |
| D7 | 历史数据 `_MVP_USER_ID` | ⭐迁移给首个注册的管理员 / 保留为 demo / 清空 | 避免孤儿会话 |
| D8 | schema 迁移 | 加 `users.password_hash`、`username` 唯一且非空；走 alembic（`upgrade`/`downgrade` 成对） | 遵循 `database.mdc`，`alembic check` 须零漂移 |
| D9 | 测试 DB 策略 | ⭐单元用 fake repo(内存) + 集成用真 PG 测试库 / 全 fake / SQLite | 模型用 PG 专有类型(PG_UUID/JSONB)，SQLite 不兼容；CI 是否有 PG 待确认 |

## 四、技术方案（分层设计）

### 1. 数据层
- 迁移：`users` 加 `password_hash String(255) NOT NULL`、`username` 唯一索引且非空（登录标识，D1）；`email` 保持可空（留作后期找回密码/OAuth）；处理 `_MVP_USER_ID` 历史行（D7）。
- `UserRepository` 增：`get_by_username(username)`、`create(username, password_hash, display_name?, email?)`。
- 新增 `RefreshTokenRepository`：`create`、`get_by_hash`、`rotate(old→new, 同 family)`、`revoke_family(family)`（重用检测时连根撤销）、`revoke_all_for_user(user_id)`（登出全端）。
- 遵循 `database.mdc`：`select()` 构建、`server_default`、`commit/refresh` 内聚。

### 2. 安全工具 `agentcore/security.py`（纯函数，易测）
- `hash_password` / `verify_password`（按 D4 选型）。
- `encode_access_token(user_id, exp)` / `decode_access_token(token) -> claims`（python-jose，校验签名+过期，失败抛 `AuthenticationError`）。
- `generate_refresh_token() -> (raw, hash)`：返回明文(发给客户端)与哈希(落库)，**库里只存哈希**。

### 3. 服务层 `agentcore/auth/service.py`（业务逻辑，权限校验在此层）
- `register`：查重→哈希→建 User；按 D6 校验邀请码。
- `login`：取用户→verify→签发 access + refresh(新 family)。
- `refresh`：查 refresh 哈希→若已 `revoked/rotated`（重用）→**撤销整个 family** 并拒绝；否则轮换(旧标记 rotated，发新)。
- `logout`：撤销当前 refresh（可选全端）。
- `me`：返回当前用户公开字段。

### 4. 依赖注入 `agentcore/api/dependencies.py`（落实 `api.mdc` 约定）
- `get_current_user` → 类型别名 `AuthUser`（无有效 access Cookie 抛 401）。
- `get_optional_user` → `OptionalUser`（未登录返回 None）。

### 5. 路由 `agentcore/api/routes/auth.py`
- `POST /v1/auth/register | login | refresh | logout`、`GET /v1/auth/me`。
- 薄层：解析→调 service→set/clear Cookie→返回。

### 6. 接入与堵漏
- `main.py`：`include_router(auth.router, prefix="/v1")`；（可选）`tools` 只读路由。
- **堵 IDOR**：`conversations.py` 全部端点注入 `AuthUser`，service 层校验 `conv.user_id == user.user_id`，不符按 `NotFoundError` 处理（不泄露存在性）；删除 `_MVP_USER_ID`，`stream_chat`/`resolve_checkpoint` 同步带上属主校验。

### 7. 配置
- `Settings` 增 `cookie_secure`/`cookie_samesite`/`cookie_domain`/`auth_invite_required` 等；`.env.example` 同步并提示生产必改 `JWT_SECRET_KEY`。

### 8. 前端（桌面端）
- `auth` store（Zustand）+ 登录/注册页 + 路由守卫（未登录→登录页）。
- `api.ts` 拦截 401 → 调 `/auth/refresh` → 重试一次 → 仍失败则登出跳登录。
- 登出按钮接 `UserMenu`。Electron：确认渲染进程 fetch 的 Origin 被 CORS 放行（自定义协议/`file://` 需处理）。

## 六、评审计划与验收标准

**安全检查清单（评审必过）**
- [ ] 密码仅存哈希（argon2id/bcrypt），无明文/可逆。
- [ ] refresh 仅存哈希；轮换 + 重用检测（family 撤销）生效。
- [ ] Cookie：`HttpOnly` + 生产 `Secure` + `SameSite`；refresh 限定 path。
- [ ] CSRF 按 D5 落实。
- [ ] 错误信息不区分「用户不存在/密码错」。
- [ ] 全部受保护端点接入 `AuthUser`；IDOR 已堵。
- [ ] `JWT_SECRET_KEY` 生产强制非默认（启动校验或文档红字）。

**验收标准**：上述清单全绿 + 第五节测试全绿 + 全流程手测通过。

## 七、建议推进顺序与分期

1. **Phase 1 · 后端核心（先行）**：D1–D9 定稿 → 迁移 + security + service + deps + routes + 接入 main + **堵 IDOR** + 单元/集成测试。这是上线必需最小集。
2. **Phase 2 · 前端**：登录/注册 + 路由守卫 + 401 刷新重试 + 登出。
3. **Phase 3 · 加固**：限流、邀请码后台、（Web 端）CSRF 双提交、找回密码。

> 工作量直觉：Phase 1 是大头（安全敏感，测试占比高），Phase 2 中等，Phase 3 可上线后迭代。

## 八、风险与遗留

- 🟥 **IDOR 必须与 auth 同期修**，否则鉴权无意义。
- 🟡 D4 是新依赖决策（passlib+bcrypt 兼容坑），需你确认换库还是 pin。
- 🟡 D9 测试 DB：CI/本地是否有 PostgreSQL 决定集成测试形态。
- 🟡 `_MVP_USER_ID` 历史会话归属（D7）。
- 🟡 Electron 渲染进程 Origin 与 Cookie/CORS 的实际联调（桌面端非标准 http Origin）。
