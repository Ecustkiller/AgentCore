# 编排器重定位为「CEO 主 Agent」— 讨论与规划

> 本文是讨论记录与提案。方向已于 2026-06-14 确认（D1/D2/D3 见第三节），但**尚未落地代码**；落地前 `docs/编排器Prompt与输出结构.md` 对应章节保留「现状」标注。

---

## 一、动机：当前「双大脑 + 合成器」的三处不顺

现状链路（聊天优先 + 按需编排）：

- 入口 = 高频**聊天 Agent**（`pipeline.py`，`chat` 档），拥有对话、直接回复，带内置工具 + `assemble_team`。
- 判断需要团队 → 调 `assemble_team` → **编排器**（`planner.make_plan`，独立 LLM，`orchestrator` 档）出结构化 JSON 计划。
- 计划驱动 `runs.run_multi_agent`（DAG 调度）→ **合成器**把最终答案直接流式给用户；聊天 Agent 此后 `terminal=True` 退场。

→ 见代码：`runtime/pipeline.py`、`tools/builtin/assemble_team.py`、`runtime/planner.py`、`runtime/runs.py`

不顺之处：

1. **双大脑职责重叠**：聊天 Agent 判一次意图（要不要升级），编排器再判一次意图（怎么规划）。
2. **三次人格切换**：聊天 Agent → 隐形编排器 → 合成器。用户先跟聊天 Agent 说话，团队跑完却由「合成器」用另一种声音作答——「我在跟谁说话」不连贯。
3. **编排器不能与用户对话**（明令 ❌）：面对模糊的大任务只能拿到啥规划啥，无法先澄清。

---

## 二、新模型：一个「CEO 主 Agent」

把聊天 Agent + 编排器 +（收尾的）合成器**统一成一个会话型 CEO**：

- 用户 ↔ **CEO**（唯一对话入口与声音）→ workers（员工）。
- CEO 直接对话、可来回澄清；判断需要团队时**下达指令**（声明式全景计划）；团队跑完由 **CEO 用自己的声音收尾汇报**。

### 必须守住的底线（不可破）

合并的是**「对用户的身份/声音」**，不是「每轮都跑重规划」。CEO 默认是**快的会话模型**；「组团/下计划」是它**按需触发**的能力，简单对话（你好/问答/单点）绝不付重规划税——这正是当初放弃「编排器唯一入口」的原因（实测 ~15s 首字）。

## 三、已确认决策（2026-06-14）

| # | 决策 | 结论 | 说明 |
|---|---|---|---|
| D1′ | 声明式 DAG vs 动态委派（合并修订） | ✅ **单一委派原语，粒度由 CEO 自选** | A（全景计划）与 B（动态委派）不是两套系统，是同一原语在两种「承诺粒度」上的样子。统一为一个 `delegate` 工具：往一张活 DAG 登记 1..N 个委派节点（各带 `role/tools/model/depends_on/task`）。一次塞一批 = 全景计划，逐个增量塞 = 动态委派；同一工具 / schema / 调度 / 校验。任务卡 = 活 DAG 的可视化。 |
| D2 | CEO 能否与用户来回澄清 | ✅ **能** | 下达指令前可与用户澄清。这是 CEO 模型相对旧编排器最大的能力增益。 |
| D3 | 团队收尾由谁汇报 | ✅ **CEO 用自己声音收尾** | 合成器角色并入 CEO，保证全程一个声音。为压低「再读一遍 worker 产出」的额外开销：收尾用 CEO 同款模型 + 同款口吻，而非另起人格。 |

> D1′（2026-06-14 合并修订，取代原「A 主 B 辅」）：原方案是同一接缝两套决策逻辑（违反开发纪律「避免两套决策逻辑不一致」）。合并后 A/B 溶解为「批量大小」，由 CEO 按场景自选粒度。底层 `runs.py` / `plan.py` 的 DAG 引擎保留，只把「图怎么来」从「LLM 一次吐全 JSON」改为「`delegate` 增量 append + 每次 append 跑无环/预算校验」。额外收益：`docs` §四「流式解析大 JSON、边解析边触发」的复杂度直接消失——每个 `delegate` 调用本身就是触发点。

## 四、对架构的影响（落地前预判，待细化）

| 模块 | 现状 | 重定位后 |
|---|---|---|
| 入口 | 聊天 Agent（`pipeline.py`） | CEO（同一会话主体，承袭聊天优先的低延迟） |
| 编排器 | 独立隐形 LLM，产 JSON，不与用户对话 | CEO 的「按需规划能力」；可先澄清再出计划 |
| 升级路径 | `assemble_team` 工具（`terminal=True` 退场） | CEO 不退场：`delegate` 增量 append 节点 → 团队执行 → 控制权回到 CEO 收尾 |
| 合成器 | 独立声音收尾 | 并入 CEO，用 CEO 口吻收尾 |
| 计划结构 | `OrchestratorPlan` / `depends_on` DAG | **引擎保留**；不再由「编排器 LLM 一次吐全 JSON」产生，改由 `delegate` 工具增量 append 节点到活 DAG（D1′）。一次一批 = 全景，逐个 = 动态。 |
| 检查点 | 挂起问用户（无 LLM 审视） | CEO 天然在环：读中间结果决定下一步，必要时问用户（与 D2 一致） |

### 待细化的开放问题（落地阶段再定）

- ~~**O1 计划 vs 动态的边界**~~ → 已并入 **D1′**（合并为单一委派原语）。剩余子问题转为 G1–G3：
  - **G1 粒度引导**：prompt 怎么引导 CEO「能预见结构就一次塞一批（拿并行 + 完整卡片），预见不了才增量」。
  - **G2 弱模型并行**：快档可能不擅长用并行 tool call 自己发现并行，故保留「一次塞一批 + 显式 `depends_on`」口子，让 CEO 显式声明依赖更稳。
  - **G3 可视化取向**：任务卡「现场生长」vs「一次显示完整」，影响 prompt 引导 CEO 倾向大批量还是增量。
- **O2 收尾开销**：CEO 收尾要重读 worker 产出，如何压低这一次往返的延迟/token——D3 的「同款模型 + 口吻」是否够，还是需要把 worker 产出做结构化摘要再喂给 CEO。
- ~~**O3 并行表达**~~ → 已由 **D1′** 解决：`depends_on` 驱动并行，与节点是「一批来」还是「分轮来」无关，跨轮的无依赖节点也并行；弱模型并行的稳健性细节归 **G2**。
- **O4 检查点 LLM 审视**：是否借这次把「CEO 审视检查点」补上（原 §五设计方向，至今未落地）。
