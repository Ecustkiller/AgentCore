## 详细发现

### F1 · `reasoning_effort` 声明但执行从不读取（声明≠生效）

- **严重度**：P2
- **类别**：SEAM / DRIFT
- **证据**：
  - schema 向 CEO 暴露并承诺功能：`tools/builtin/delegate/schema.py:84-88`（每 task `reasoning_effort` enum `high/max`，描述「极复杂子任务可设 max 解锁更深推理」）；skill 复述同承诺：`runtime/skills.py:91`（「可再设 `reasoning_effort="max"` 解锁更深推理」）。
  - 解析进模型：`runtime/runs/builder.py:356,377`（`RunSpec.reasoning_effort`）、`runtime/runs/types.py:177`。
  - 执行侧**不读**：`runtime/runs/executor_agent.py:313-319` 仅用 `model_preference→profiles.agent()` 与 `spec.model`；`runtime/runs/executor_shared.py:140-171`（`_react_and_capture → react_loop`）只透传 `profile` + `turn_model`，无 `reasoning_effort`/`thinking`。全仓 `reasoning_effort`/`thinking` 的其余引用**仅供展示**（`tools/builtin/delegate/plan_events.py:49-50`、`conformance/projection.py:62-63`）。
- **影响**：CEO 被 schema/skill 明确告知可用该字段「解锁更深推理」，但引擎丢弃它——设置任何值都无效果，误导模型并浪费其决策注意力/token。这正是「schema 声明了但执行不读」型接缝。
- **设计上下文**：`docs/03-AI核心/编排器与CEO主Agent.md §2.1` 已声明「MVP 约束：thinking / reasoning_effort 默认不发…⏳ per-provider 推理字段适配见远期」。故代码行为与 MVP 一致，**缺口在模型可见的 schema/skill 措辞超前于已知的 MVP 限制**。
- **修复方向**：二选一——① 在 provider 层落地 per-node reasoning 透传（兑现远期承诺）；② 把 schema/skill 措辞降级为「预留 / MVP 暂不生效」，与「默认不发」对齐，别让模型误以为有效。

### F2 · `finalize_stopped` 漏 `absorb_children` → 嵌套子队账目/来源泄漏

- **严重度**：P2
- **类别**：BUG / DESIGN（违反「不漏算」不变量）
- **证据**：
  - `absorb_children(tool)` **仅**在正常终态路径调用：`tools/builtin/delegate/drive.py:365`（全仓唯一有效调用点，见 `nesting.py:77-81`：这是子队 `child._acc` 并入父 `_acc` 的唯一通道）。
  - 收尾路径 `tools/builtin/delegate/supervised.py:148-176`（`finalize_stopped`）只做 `accumulate_usage`/`collect_ledger`/`collect_citations`/`register_sessions`，**未调 `absorb_children`**。
  - 三条 stop/dispose 入口都汇入 `finalize_stopped`：`tool.py:454-455`（`replan(stop)`）、`tool.py:361-362`（`resume_plan` STOP）、`tool.py:487`（`dispose_open_supervised`，由回合末 `runtime/pipeline/run.py:503` 调用）。
  - 边界让出/部分失败暂存路径本就不折账（`drive.py:272-347` 注释「fold on the resume or dispose path」），依赖 resume 的终态 drive 或 dispose 折账——但 dispose 走 `finalize_stopped`，遂漏折子队。
- **影响**：当 depth-1 lead 已扇出子队（`child._acc` 攒有子 worker 的 token/成本/web 来源），随后**父计划在波边界让出**且 CEO **收口而非正常 replan 续跑**（`replan(stop)` / 回合末 dispose / 部分失败后停），子队花销与来源**永不并入回合总账**——欠计费 + 丢来源卡。直接违反 `docs/03-AI核心/编排器与CEO主Agent.md §2.4`「账目按树回滚…不漏算」与 §受监督循环「收尾折账（堵漏）」。
- **前置条件**：嵌套 lead 扇出子队 + 父计划让出边界（bind/scope/部分失败）+ CEO 停止（非正常 replan drive）。属边界组合，但可达且金额真实。`test_nesting.py:126-147` 只测了「子级 dispose + 显式 absorb」，未覆盖父级 stop 路径缺 absorb。
- **修复方向**：`finalize_stopped` 在折账时补 `absorb_children(tool)`（与 `drive.py:357-365` 终态路径一致）；补一条「嵌套 lead + 父 stop」的账目回归。

### F3 · `checkpoint_gate_enabled=False` 不能阻止 `checkpoint_after` 结构挂起

- **严重度**：P2
- **类别**：SEAM（配置闸门在一条路径被绕过）
- **证据**：
  - CHECKPOINT 边界判据**只查** registry/conversation_id/depth，**不查** `_checkpoint_enabled`：`tools/builtin/delegate/boundary.py:59-66`。而同文件 `boundary.py:24-26` 的 `checkpoint_active()` 恰含 `_checkpoint_enabled`，此分支却没复用它。
  - `on_boundary` 对**任意含 `depends_on` 的 DAG** 都会 wire（不需 checkpoint_active）：`drive.py:206-215`。
  - checkpoint 节点入队仅 gate 于 `on_boundary is not None`：`wave.py:306-312`；随后 CHECKPOINT 边界照 fire：`wave.py:317-325`。
  - `registry`（交互桥）**无条件**传入 DelegateTool：`runtime/resolve/prepare.py:113`。而闸门源 `runtime/pipeline/run.py:337`（`checkpoint_enabled = settings.checkpoint_gate_enabled and approvals_enabled`）只用于 `escalation_armed` 与 ask_user 装配（`prepare.py:162,180`）。
- **影响**：运维关闭 `checkpoint_gate_enabled` 后，含 `checkpoint_after` 节点的多步 DAG 仍会在顶层波边界挂起，与「关闭闸门」预期不符。因 plan_review 的 resolve schema 已下线（`boundary.py:94-97` 注释），实测退化为**卡到超时 `checkpoint_timeout_seconds` 后 auto-continue** 的意外停顿（非数据丢失，但主路径出现非预期停滞）。
- **NEEDS-VERIFY**：是否有意（把 `checkpoint_after` 当「始终生效的结构声明」，闸门只管 ask_user/escalate）。若有意，应在文档明确二者边界；若非，则为闸门泄漏。
- **修复方向**：CHECKPOINT 分支复用 `checkpoint_active(tool)`（或加 `tool._checkpoint_enabled` 判据），使 kill-switch 对结构挂起一致生效；或在文档写清 `checkpoint_after` 不受该闸约束的理由。

### F4 · `complexity_hint=light` 的「默认 finalize=true 行为」未实现

- **严重度**：P3
- **类别**：DRIFT（模型可见 schema 承诺 > 实现）
- **证据**：schema 承诺 `tools/builtin/delegate/schema.py:293-295`（「引擎据此裁剪：light 时…默认 finalize=true 行为」）。实际 `tool.py:325` 传 `finalize=bool(arguments.get("finalize"))`，无 light→finalize 逻辑；`drive.py:74,204-215` 中 light 只关 `note_wall` 与 `on_boundary`；`drive.py:368` 的直出短路只看传入 `finalize`。全仓无据 `complexity_hint` 置 finalize 的代码。
- **影响**：CEO 依 schema 以为 light（含单 worker 自动推断，`tool.py:203-205`）会默认直出，但引擎仍走 CEO 合成轮。最坏多一次合成轮，非正确性破坏；但模型可见文本不准。
- **修复方向**：要么 light 且单 worker 成功时缺省直出（在 `drive.py:368` 放宽 finalize 条件），要么删 schema 该句。

### F5 · 陈旧注释：称 `checkpoint_after`/`bind_after_deps`「CEO 无从设置、恒 inert」

- **严重度**：P3
- **类别**：DRIFT（注释与现状矛盾）
- **证据**：`runtime/runs/builder.py:390-396` 与 `runtime/runs/types.py:198-208` 注释均称「schema 入口待激活层接入前，CEO 无从设置此字段，故此处恒为 False、完全 inert」；但 `tools/builtin/delegate/schema.py:145-166` **现已把 `checkpoint_after` / `bind_after_deps` 暴露为可设 task 字段**，并被 `wave.py`（CHECKPOINT/BIND 边界）真实消费、`test_runs_builder.py:418-443` 覆盖解析。
- **影响**：注释误导读代码者以为字段是死路；代码本身正确、字段已激活。属文档-代码漂移（注释层）。
- **修复方向**：更新两处注释为现状（字段已由 schema 暴露、由 `on_boundary` 消费；仍保留「无 hook 时 inert」的正确部分）。

### F6 · 显式 `complexity_hint=light` 会关掉 DAG 的波边界（bind 节点未定稿即派发）

- **严重度**：P3
- **类别**：BUG（健壮性；需自相矛盾输入触发）
- **证据**：`drive.py:204-205` 对 light **无条件**置 `on_boundary=None`；`tool.py:202` 直取 `complexity_hint`，未校验与 plan 形状是否冲突。`wave.py:178`（`defer_bind = on_boundary is not None`）与 `wave.py:219-229`：无 hook 时 `bind_after_deps` 节点按普通节点派发。
- **影响**：CEO 若对含 `bind_after_deps`/`depends_on` 的多节点 DAG **显式**传 `light`，晚绑定节点会带占位 `role/task`（`format_bind_boundary` 里的「占位角色：未填」）直接运行、scope 升级也不在波边界消费——静默错误。自动推断已规避（`_should_auto_light_delegate` 遇 depends_on/bind/checkpoint 即不判 light，`tool.py:44-53`），故仅显式误用触发、概率低。
- **修复方向**：light 与 `depends_on`/`bind_after_deps`/`checkpoint_after` 并存时忽略 light（或校验拒绝），别据 light 关闭波边界。

### F7 · `Deliverable.output_schema` 声明但三方不接（无入口、不校验）

- **严重度**：P3
- **类别**：SEAM / DESIGN（阶段2 预留位悬空）
- **证据**：字段声明 `runtime/runs/types.py:85`；builder 从 `deliverable` dict 解析 `runtime/runs/builder.py:548-550`。但 `contract` schema **不暴露** `output_schema`（`tools/builtin/delegate/schema.py:176-225` 仅 required_sections/must_contain/min/max/output_format/requires_files/strict）；`runtime/runs/contract.py:32-85`（`check_contract`）**从不校验** `output_schema`（仅 `output_format=="json"` 做可解析性检查）。
- **影响**：CEO 无法经 contract schema 设置 output_schema，且即使设置也不被校验——声明/入口/实现三方不接的死字段。低危（阶段2 slot）。
- **修复方向**：要么落地 JSON Schema 校验 + 在 contract schema 暴露入口，要么移除该字段避免误导。
