# 05 · 工具与能力系统审计

> 只读审计分册。范围：`tools/`（registry / protocol / builtin 除 delegate·debate·read_notes）+ 审批门 + 沙箱/权限 + Skill/Rule 的 tools 侧。
> 方法：对照 `工具与能力系统.md`、`执行引擎架构设计.md §五`、`安全权限与治理.md §三/§五/§十` 逐条查证；断言前两端代码均已读到。

## 严重度计数

| 严重度 | 数量 | 摘要 |
|---|---|---|
| P0 | 1 | `test_run` 以 `approval=NEVER` 执行任意代码，绕过审批门；并绕过云端 `code_execute` 默认关治理（云端默认 subprocess = RCE） |
| P1 | 0 | — |
| P2 | 3 | 工具异常不隔离（崩整轮）；grep 用户正则同步阻塞事件循环（ReDoS）；git/test_run 两个最敏感工具零单测 |
| P3 | 4 | git branch/checkout 缺 `--` 分隔符；ApprovalGate 字段注释漂移；沙箱输出 head-only 截断；gVisor network 死分支 + /workspace 只读不一致 |
| NEEDS-VERIFY | 2 | 云端 server 模式是否真面向不可信多租；gVisor 下 code_execute 无法写工作区是否预期 |

**总体接缝结论**：注册↔装配↔执行三段**接通、无断裂**——14 个内置工具全部经 `registry.get_optional` 可被引擎调用（`tool_exec.py:73`），能力图鉴与运行时共用 `build_worker_registry`/`build_ceo_tool_registry`（`catalog.py:94-104`，单一事实源，无「注册没装配 / 装配没实现」）。路径逃逸单守卫 `resolve_safe_path` 与 read_url/web_search 的 SSRF 姿态均**扎实**（见文末「已核实为安全」）。**唯一系统性缺口集中在「代码执行类工具的审批一致性」**：`code_execute` 被严格把关，而等价执行力的 `test_run` 完全没有。

## P0

### P0-1 [SEC] `test_run` 绕过审批门执行任意代码；并绕过云端 `code_execute` 默认关治理

**证据（两端均已读到）**：
- `test_run` 声明为 `category=EXECUTION` 且 `approval=ToolApproval.NEVER`（`tools/builtin/test_run.py:326-329`），执行体直接调 `context.backend.execute(ExecutionRequest(...))`（`test_run.py:384-394`）——与 `code_execute` **同一条沙箱执行链**（`workspace/server.py:595-606` → `sandbox.execute`）。
- 执行门只对 `GRANTABLE` 及 `git` 写子命令挂起（`runtime/engine/tool_exec.py:85-90` + `runtime/approvals.py:36-52`）；`NEVER` 工具**永不过门**。故 `test_run` 无论本地/云端、CEO/worker，都**不弹审批**。
- `TestRunTool` 在 `build_builtin_registry` 中**无条件注册**（`tools/builtin/__init__.py:65`），不像 `code_execute` 受 `code_execute_enabled_for(backend)` 门控（`__init__.py:30-41,66-67`）。因 `approval=NEVER`，它还被 `build_ceo_tool_registry()` 收入 CEO 只读子集（`__init__.py:105-128`），能力图鉴亦标注 CEO+worker 可用（`catalog.py:94-101`）。
- 命令白名单 `_ALLOWED_PREFIXES` 只限**启动器**（`pytest`/`npx vitest`/`npm test`/`pnpm test` 等，`test_run.py:56-66`），不限其运行的内容：`pytest` 会 import 执行工作区内 `conftest.py`/测试模块（任意 Python），`npm test`/`pnpm test` 执行 `package.json` 的 `test` 脚本（任意命令）。worker 持 `file_write`，可先写恶意 `tests/test_x.py` / `package.json` 再 `test_run` → 任意代码执行。
- 云端启动守卫 `_validate_production_security` **只检查 `code_execute_cloud_enabled`**（`main.py:116-128`），完全不覆盖 `test_run`。而 `create_sandbox(location="server", gvisor_enabled=False)` 返回 `SubprocessSandbox`（`tools/sandbox/__init__.py:24-30`），`GVISOR_ENABLED` 默认关。

**影响**：
1. **本地/sidecar 模式**（`location="local"`，root=用户真实磁盘）：`test_run` 在用户真机上执行任意代码，**零审批**——直接破掉「委派 worker 不得未经同意在用户真机跑代码」这一本地执行门（`approvals.py:9-13` 的设计目标）。
2. **云端 server 模式（默认 gVisor 关）**：`test_run` 经 subprocess 在 **API 容器内**执行任意代码，未过门、且**无视 `code_execute` 为此专门设的默认关治理**（`安全权限与治理 §5.4`）。等于 `subprocess.py:8-19` 与 `main.py:108-115` 警告的「authenticated RCE，可读 `JWT_SECRET_KEY`/`ENCRYPTION_KEY`/全体用户加密密钥」——只是换了 `test_run` 这个入口绕过守卫。
3. 「协调者 CEO 只看不改」的边界被破：CEO 实际持有一个 EXECUTION 工具（`run.py:288-299` 注释仅列 `code_execute` 为被排除项，遗漏了 test_run 同为执行工具）。

**修复方向**：把 `test_run` 视同 `code_execute`——① 升为 `GRANTABLE` 并纳入 `per_call_tools`（每次审批，PI-004 同款）；② 让它复用 `code_execute_enabled_for` 的云端门控与 gVisor 要求，并把 `_validate_production_security` 扩展到 test_run；③ 从 CEO 只读子集移除（改为仅 worker）。若产品坚持 test_run 低摩擦，则至少必须让云端治理 + 隔离沙箱对它同等生效。

**NEEDS-VERIFY**：云端 `location="server"` 是否已（或计划）面向不可信多租运行——若仅自用/单租，facet 2 的现实危害下降，但 facet 1（本地无审批执行）不受影响、仍成立。

## P2

### P2-1 [BUG] 执行器只捕获 `TimeoutError`，工具其他异常冒泡崩掉整轮工具执行

**证据**：`execute_tools._run_one` 仅 `except TimeoutError`（`tool_exec.py:119-142`），其余异常直接冒泡；`asyncio.gather`（`tool_exec.py:194`）在首个异常时取消并行兄弟。而 `code_execute`（`code_execute.py:103-105`）与 `test_run`（`test_run.py:394`）调用 `backend.execute` **无 try**；`SubprocessSandbox.execute` 在 `OSError`（解释器/`bash` 不存在等）时 `raise SandboxError`（`sandbox/subprocess.py:253-254`）。`loop.py:302` 调用处也无 try。

**影响**：本地 Windows sidecar 上 `test_run`（`language="bash"`）或 `code_execute(language="bash")` 遇无 bash、或任一工具意外抛异常时，会以未处理异常冒泡出 ReAct 循环、**丢失同轮其他并行工具结果**，并可能中止整个回合——本应是模型可自愈的一条工具错误消息。

**修复方向**：在 `code_execute`/`test_run` 包裹 `backend.execute` 的 `SandboxError`→`ToolResult(success=False)`；并在 `execute_tools` 加**每工具异常防火墙**（`try/except Exception` 转成工具错误消息），保证任一工具崩溃只影响自身、不牵连兄弟与回合。

### P2-2 [SEC/BUG] `grep` 用户可控正则在事件循环上同步执行，ReDoS/大扫描阻塞整进程

**证据**：`grep` 编译用户正则（合法性已校验，`grep.py:106-109`），但 `ServerWorkspace.grep` 用 `re.compile` + `os.walk` + `regex.search` **同步**遍历至多 5000 文件（`workspace/server.py:487-533`，`_MAX_FILES_SCANNED=5000`），虽是 `async def` 却无 `await`/线程卸载。引擎超时兜底走 `asyncio.wait_for`（`tool_exec.py:120-123`），**无法中断 C 层同步正则**——超时只在控制权回到事件循环时才生效。

**影响**：单进程 in-process 姿态下（`approvals.py:1-7` 明示 single-worker），一条灾难性回溯正则（或超大工作区）会**阻塞整个事件循环**，拖垮所有并发请求；超时形同虚设。模型自发或经提示注入均可触发。

**修复方向**：把 grep（及其它重文件遍历/读取）经 `asyncio.to_thread` 卸载到线程，使超时可生效、事件循环不被独占；可加正则复杂度/单行长度上限的保护。

### P2-3 [TEST] 两个最敏感工具 `git`（写）与 `test_run`（执行）无任何专门单测

**证据**：全 tests 目录**无任何文件 import `GitTool` 或 `TestRunTool`**（grep `from ...git_ops` / `from ...test_run` / `GitTool()` / `TestRunTool()` = 0 命中）。`test_workspace_git.py` 测的是 `workspace/git.py`（另一个 workspace 助手模块），**非** `tools/builtin/git_ops.py` 的 GitTool。

**影响**：git 的安全护栏——`_FORBIDDEN_PATTERNS`（push/reset/…）、`_PROTECTED_BRANCHES`（禁 main/master 直提）、`_validate_add_paths`（禁 `.`/`-A`/通配）、CEO 上下文禁写、branch/checkout 参数处理——以及 test_run 的命令白名单/框架检测/审批姿态，全部**无回归网**。任一护栏被后续改动悄悄破坏不会被测试发现（与 P0-1 叠加尤其危险）。

**修复方向**：为 GitTool 补禁令/保护分支/add 路径/CEO 写拒绝的单测；为 TestRunTool 补白名单与审批级别（回归锁定 P0-1 修复后应为 GRANTABLE）的单测。

## P3

### P3-1 [SEC] `git` branch/checkout 未用 `--` 终止选项，`-` 开头分支名会被当作 git 选项

**证据**：`_cmd_branch` 用 `["branch", branch]`（`git_ops.py:350`）、`_cmd_checkout` 用 `["checkout", branch]` / `["checkout","-b",branch]`（`git_ops.py:359-368`），均**无 `--` 分隔符**；`_FORBIDDEN_PATTERNS` 只对 subcommand 生效、不查 branch 值（`git_ops.py:219-220`）。argv 模式已杜绝多参注入（分支名是单 token），但 `branch="-f"` 之类会被 git 解析为选项（如 `checkout -f` 强制丢弃未提交改动）。

**影响**：需先过写审批、影响限于工作区（丢未提交改动），危害有限；属加固项。

**修复方向**：拒绝以 `-` 开头的分支名，或在分支参数前插入 `--`。

### P3-2 [DRIFT] `ApprovalGate.file_op_tools` 字段注释与生产注入不符

**证据**：字段注释称来源 `file_mutation_tool_names`（`GRANTABLE∩FILESYSTEM`，**不含 git**，`approvals.py:112-117`），但生产实际注入 `approval_class_tool_names()`（含 git，`run.py:319`、`resume/pipeline.py:189`）。**行为正确**（「本轮内允许所有文件改动」确实覆盖 git 写，符合 `安全权限与治理 §三` 与 `_granted` 逻辑 `approvals.py:187-192`），仅内部注释漂移。

**修复方向**：注释改为引用 `approval_class_tool_names`。

### P3-3 [BUG] 沙箱输出 head-only 截断，先丢尾再交给 head+tail

**证据**：`ExecutionResult.__post_init__` 对 stdout/stderr 各做 **head-only** 截断到 8000（`sandbox/protocol.py:49-57`，`self.stdout[:8000]+"…"`）；随后 `code_execute` 拼成 `output` 再经 `ToolResult` 的 **head+tail** 截到 4000（`tools/protocol.py:242-248`）。与「工具输出 head+tail、保尾」口径（`执行引擎`/`core.text.truncate_head_tail`）不一致——长 stdout 的尾部（常含 traceback 末行/退出摘要）在 8000 处即被切掉，head+tail 已无从挽回。

**修复方向**：`ExecutionResult` 改用 `truncate_head_tail`，或把截断下沉到 ToolResult 一处完成。

### P3-4 [DESIGN] gVisor `network_mode` 死分支 + `/workspace` 只读不一致

**证据**：`runsc run` 恒传 `--network=none`（`gvisor.py:146`），使 `_build_oci_config` 里 `if request.network_mode != "none": namespaces.append({"type":"network"})`（`gvisor.py:269-270`）**永不生效**——网络恒关（方向安全，符合「云端默认禁网」，仅冗余误导）。另 `/workspace` 恒以 `ro` 绑定挂载（`gvisor.py:283`），而 `SubprocessSandbox` 以可写 `cwd=root` 运行（`server.py:595-606`）：云端 gVisor 下 `code_execute` 生成的文件写不进工作区、静默失败，而 `file_write`（走 backend 非沙箱）可写——两模式行为不一致。

**NEEDS-VERIFY**：`/workspace` 只读是否为「只读根 + tmpfs 工作区」的预期取舍（gVisor 默认关，影响面小）。

**修复方向**：删除 network 死分支（或让 CLI 尊重 network_mode）；明确 gVisor 下 code_execute 的可写工作区语义（如改绑 rw 或文档化只读约束）。
