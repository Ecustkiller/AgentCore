## 一、发现清单

### C&M-01 · P2 · DRIFT — 文档反复引用的 `MAX_INSTRUCTION_CHARS / MAX_INSTRUCTION_DOCS` 预算口径在代码中不存在

- **证据**：
  - 文档四处把它当既定口径：`Agent记忆与知识系统.md` §1.4「与全局规则共享同一 `MAX_INSTRUCTION_*` 口径」「整体计入 `MAX_INSTRUCTION_CHARS`、全局优先存活」、§二「记忆分层注入…整体计入 `MAX_INSTRUCTION_CHARS`、全局优先存活」、§5.3「共享同一注入预算口径（`MAX_INSTRUCTION_*`）…累积合并时全局优先」、§5.4 表「always | 计入 `MAX_INSTRUCTION_CHARS`」、§5.6 表「`MAX_INSTRUCTION_DOCS` / `MAX_INSTRUCTION_CHARS`」。
  - 代码全仓 `apps/server/**` grep `MAX_INSTRUCTION_CHARS` / `MAX_INSTRUCTION_DOCS`：**0 命中**。
  - 记忆注入实际口径是**逐文件**上限 `memory_injected_file_char_cap`（`config/persistence.py:34`=4000），在 `memory/injection.py:40-60`（`_cap_memory_body`）逐文件套用；`load_injected_memory`（`memory/injection.py:63-104`）只是「全局文件在前、项目文件在后」拼接，**没有总预算、没有「全局优先存活」的淘汰逻辑、没有文档数上限**。`runtime/pipeline/run.py:202` 传入的也是这个逐文件 cap。
- **影响**：§二（标注为「✅ 已确定」）把「整体计入 `MAX_INSTRUCTION_CHARS` + 全局优先存活」描述成**当前行为**，但内存注入实为「逐文件 4000 字符封顶、无淘汰」。审计「预算计算是否正确」时会被文档误导：所谓共享预算与全局优先淘汰**并未实现**。
- **根因判断**：`MAX_INSTRUCTION_*` 属于「云端文件树 rule 注入」目标管线（文档自述 §1.4/§5.4 该管线 ⏳ 未落地），是蓝图常量；漂移点在于**已落地的记忆注入**被描述成用了这套不存在的口径。非功能 bug。
- **修复方向**：把 §二 / §5.3 中描述记忆注入的段落改写为现状——逐文件 `memory_injected_file_char_cap` 封顶、无总预算 / 无全局优先淘汰；`MAX_INSTRUCTION_*` 及「全局优先存活」保留在 ⏳ 目标形态段并明确标注未落地。

### C&M-02 · P3 · DRIFT — 工作区概览注入的 XML 标签，代码是 `<workspace_file_index>`，文档写 `<workspace_context>`

- **证据**：代码渲染标签 `runtime/context/workspace_overview.py:102`（`<workspace_file_index>…</workspace_file_index>`），测试也钉死此标签 `tests/test_workspace_overview.py:50-51`；`project_profile.py:145` 注释亦称 "workspace_file_index"。但文档一律用 `<workspace_context>`：`上下文工程.md` §5.5「注入 `<workspace_context>`（`WORKSPACE_OVERVIEW` 档）」/§5.6 表、`Agent记忆与知识系统.md` §5.2「列入 `<workspace_context>` 概览」。`run.py:407` 装配用的 `key="workspace_context"` 也与实际标签名不一致（key 仅调试用，不进提示词，非模型可见）。
- **影响**：文档描述的模型可见标签名与真实注入不符；排查提示词 / 复现缓存前缀时按 `<workspace_context>` 搜会落空。纯命名漂移，无行为影响。
- **修复方向**：统一以代码为准，把三处文档的 `<workspace_context>` 改为 `<workspace_file_index>`（并可顺手把 `run.py:407` 的 assembler key 对齐为 `workspace_file_index` 消歧义）。

### C&M-03 · P3 · DRIFT — `SectionOrder` 装配序「单一权威」（§5.5）漏了 `CEO_VISUALIZATION`

- **证据**：`Agent记忆与知识系统.md` §5.5 自称装配顺序「单一权威」，列：`BASE 100 → RUNTIME_CONTEXT 200 → MEMORY 300 → CEO_CORE 400 → SKILL_DIRECTORY 500 → MEMORY_TOPICS 550 → CITATION 600 → WORKSPACE_OVERVIEW 800 → ATTACHMENT 900`。代码 `runtime/context/contributor.py:35-51` 实际有 **10 档**，多出 `CEO_VISUALIZATION = 700`（CEO 专属 `<visualization>`，`prompt.py:443-447` 真在装配）。`INSTRUCTIONS = 250`（对话级自定义指令）已于 2026-07 移除。
- **影响**：作为「单一权威」的顺序表不完整——CEO 可视化块的位次没进权威表；新增常驻源时可能与这个未记档位撞序理解偏差。行为本身正确（间隔 100 留槽、渲染序稳定）。
- **修复方向**：把 `CEO_VISUALIZATION 700` 补进 §5.5 顺序表。

### C&M-04 · P3 · BUG（NEEDS-VERIFY）— 长对话压缩摘要块 + 近期尾部可能产生「连续两条 assistant 消息」

- **证据**：压缩摘要以 `role="assistant"` 作为历史首项注入（`conversation/history.py:43-56` `_summary_block`，注释明说「用 assistant 而非 user，以免出现两条连续 user 消息」）；`load_chat_context`（`history.py:59-94`）返回 `[摘要块(assistant)] + 水位线之后的尾部`。尾部起点由 `compact_conversation` 的水位线 `fold_msgs[-1].created_at` 决定（`conversation/compaction.py:183`），而 `_select_fold`（`compaction.py:76-87`）按**消息条数**切（`len(batch) - recency`），**不保证切在「user 回合边界」**。若折叠边界落在某个 assistant 消息之前，则尾部首条为 assistant → 序列变成 `[assistant 摘要, assistant 回复, …]`。
- **影响**：设计只规避了「连续 user」，未规避「连续 assistant」。DeepSeek（目标厂商）对同角色相邻较宽容，故实际多半无碍；但 `openai_compatible` 走到严格校验的厂商时，连续同角色可能被拒（400）。低概率、厂商相关的边界正确性隐患。
- **NEEDS-VERIFY**：需确认 (a) 折叠边界在真实回合流下是否可能落在 assistant 前（消息按 user→assistant 交替持久化，`recency` 奇偶 + 折叠数奇偶决定尾部首条角色）；(b) LLM 网关层（01 范围）是否对相邻同角色做归一或存在严格厂商。
- **修复方向**：`_select_fold` 折叠数向下取整到「完整回合边界」（成对折叠，保证尾部恒以 user 开头）；或在 `load_chat_context` 组装后做一次相邻同角色合并 / 归一。

### C&M-05 · P3 · DRIFT（代码注释，跨 03 范围）— CEO 上下文块注释仍写已退役的「用量明细 / powerMode」门控

- **证据**：`runtime/runs/executor_context.py:196-198` `_build_captain_context_blocks` 注释：「`system` prompt（决策②: 默认隐藏，开「用量明细」才展开）」。但 `上下文传递可视化.md` §五 决策② 现状已改为「桌面按需弹窗对所有人可见 / 手机恒隐藏」并「退役 `powerMode`/`usageDetail` 门控」。
- **影响**：代码注释与现行决策相反，读代码者会误以为仍有分级门控。仅注释，无行为影响；且该文件属 03-编排原语范围，此处仅登记备并册。
- **修复方向**：把该注释更新为现状（按需弹窗、对所有人可见）。
