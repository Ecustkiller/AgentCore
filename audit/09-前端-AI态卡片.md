## 详细发现

### F1 · 辩手「模型徽章」展示 CEO 声称的 per-side 模型，后端却全跑同一模型（前端把 06 F1 的谎话渲染给用户）

- **严重度**：P2
- **类别**：DRIFT / SEAM
- **证据**：
  - **前端消费端**：`debate/model/projection.ts:156-158` 收场从 `debate.sides` 建 `modelBySideKey`（`s.key → s.model`），`:183` 每方 `model: modelBySideKey.get(side.key) ?? ""`；徽章渲染在 `arena/Scoreboard.tsx:254,266,301`（`VersusSide` 用 `proSide?.model`/`conSide?.model`）、`SideChip.tsx:46-60`（`SideIdentity`）、`arena/brief/index.tsx:445-448`（`SidePointsGrid`）、`:112-116`（红队方案方回应）、`:155-159`（RiskBoard）。`ModelBadge.tsx:12-24` + `model/labels.ts:161-179`（`modelVendorLabel` 映射「豆包/DeepSeek/Kimi/智谱」，自述「谁更聪明对战的核心可读性」）。
  - **后端产端**（交叉核对 06 F1，已两端读到）：`runtime/debate/types.py:507-531` `to_event_payload` 逐方仍发 `"model": s.model`（:529，注释自述「让前端标注正方=豆包/反方=DeepSeek」）；但 `tools/builtin/debate/prompt.py:171-174` 把 `payload["model"] = side.model` **整段注释禁用**（「MVP 全链路统一用户 model，per-side override 在 debater_task 中忽略」）。→ CEO 一旦用 `sides[].model` 参数，各方实际全跑同一默认模型，而前端据 roster `model` 渲染出「豆包 vs DeepSeek」徽章。
  - **口径自相矛盾**：`FinaleStage.tsx:69` 主持人徽章用**真实** `moderatorRun.model`（run 节点真跑的模型），辩手徽章却用**声称**的 roster `side.model`——同一页两种真值来源。而 `DebateSideModel.run`（`model/types.ts:31`）本就带真实辩手 run（`run.model` 可取真跑模型），前端**有真实源却选用了声称源**。
- **影响**：辩论「谁更聪明」headline 卖点在被点名使用时前端**主动向用户展示与实际不符的模型徽章**（正方=豆包/反方=DeepSeek，实则同模型自导自演）。缺省（CEO 不设 model）时 `s.model` 为空、不渲染徽章，故爆炸半径限于「CEO 用了 schema 鼓励的 model 参数」；但一旦触发即用户可见的错误信息。根因是后端「发了不用」（06 F1 判 P1，含权威文档 §7.5「透传链已核验」错述），前端为忠实渲染方 + 建了整套围绕禁用能力的徽章 UI，故前端本册记 P2 并交叉引用 06 F1。
- **修复方向**：随 06 F1 一并处置——要么恢复后端注入并端到端验证、兑现徽章；要么前端改渲染**真实** `side.run.model`（run 未带则不显），或 `to_event_payload` 暂不发 `model`、前端徽章下线，直到 per-side 真跑。切勿让声称态独自漂在前端。

### F2 · 检查点 / 计划复核卡片「内联可操作」已被「挂起即收口」挪走，权威 UX 文档仍按旧描述

- **严重度**：P2
- **类别**：DRIFT
- **证据**：
  - **代码现状（内联卡=纯被动记录）**：`CheckpointCard.tsx:45-54`——非 `resolved` 一律返回 `null`（pending 内联**不渲染任何可点面**）；`PlanReviewCard.tsx:17-22`——pending 走 `DormantPlanReview`（无「继续/调整/停止」按钮，只「曾在此暂停过目」记录）。可操作面**唯一**落在 `ResumePrompt`（`ResumePrompt.tsx:38-44,88-92`，`AskUserCard`/`PlanReviewResumeCard` 三按钮 → `runResume`）。代码注释已明写此为「挂起即收口 (②, Phase 3)：CEO 检查点 finalize 回合、in-process resolve Future 不再 park，可操作面永远是耐久 resume 卡」。
  - **文档描述（旧「内联 live 可操作」）**：`docs/04-前端/前端UX设计.md` §三——检查点卡片段（~line 127）称「**会话流内独立卡片**……两动作：**提交**续跑 / **停止**……**卡片仅在 live 挂起时可操作**」；结构化挂起卡片段（~line 137）称 `PlanReviewCard`「**继续 / 调整 / 停止** 三按钮」、三态含可操作的 **pending**；`ResumePrompt` 段（~line 143）把它框成仅「**断连/重启后**」的场景卡——而代码里 resume 卡是**所有** live 挂起的常规且唯一可操作面（非仅断连）。
- **影响**：功能不缺（ResumePrompt 承载全部交互、动作回路完好），属纯文档滞后；但权威 UX 文档误导「内联检查点卡可点」，读它推进/复刻的人或 AI 会去内联卡找不存在的按钮、或误判 resume 卡只在断连时出现。违 `doc-governance.mdc`「文档滞后即修正」。
- **修复方向**：更新 §三——把 CheckpointCard/PlanReviewCard 描述为「内联仅渲染挂起/已决记录，pending 即 finalize 回合」，把 `ResumePrompt` 提升为「结构化挂起的常规且唯一可操作面（不限断连）」，补一句「挂起即收口 Phase 3」的现状。

### F3 · 质询解析：JSON 数组元素非 dict 时静默丢答、不回退启发式（06 F2 的前端同源缺陷）

- **严重度**：P3
- **类别**：BUG
- **证据**：
  - `debate/model/crossExamParse.ts:110-111`：`extractJsonArray` 只要 `[...]` 能 `JSON.parse` 成非空数组即返回，**不校验元素是否为 dict**。
  - `:40-43`：`parseCrossExamResponse` 一旦 `extractJsonArray` 返回非 null 就走 JSON 路径、**不回退**启发式 `buildCrossExamExchanges`。
  - `:127-135`：`exchangesFromJsonItems` 对每个非 dict 元素 `return`（跳过），默认输出 `[{answer:"", ok:false}…]` 原样返回。
  - **触发形态**：辩手把作答写成 JSON 字符串数组（`["答一","答二"]`，「要求输出 JSON 数组」下颇常见的少一层 wrapper 畸形）或 prose 里夹可解析标量数组 → 全部交换变 `answer="" / ok=false`。
  - **无测试**：`model/__tests__/crossExamParse.test.ts:7-56` 仅覆盖 dict 数组 / fence / 启发式降级 / 分号切，**无非 dict 数组用例**。
  - **前端触发面小于后端**：权威 `exchanges[]` 路径不经本模块（`projection.ts:404`），仅 **live 流式**（`liveCrossExamPayload`，`projection.ts:57-77`）与 **旧产物 `questions`-only**（`projection.ts:405-407`）走 `parseCrossExamResponse`，故仅进行中/旧回合的质询区短暂显空作答，不污染收场记分。
- **影响**：畸形作答下 live 质询区把已作答的方显示成「未正面回答」（`CrossExamSection` 圆点/摘要失真），收场以权威 `exchanges[]` 纠正。属边界正确性缺口 + 与后端 06 F2 同根（宜同批修）。
- **修复方向**：与后端 `cross_exam_parse.py` 对齐——JSON 路径产出 0 条有效映射时回退启发式；或对标量数组按位置映射为 `answer`；补非 dict 数组用例。

### F4 · 「你 vs AI」软对照按累计净分判 AI 倾向，与设计「leaning 文本含该方名」口径不一

- **严重度**：P3
- **类别**：DRIFT
- **证据**：`arena/FinaleStage.tsx:52-60`——`stanceAgree` 取 `tally`（`tallyScores` 累计净分）排序、比对**净分最高方** `sideKey` 是否等于用户站队方；而 `docs/04-前端/前端UX设计.md` §4.4（~line 252）述为「终局……软对照（`leaning` **文本含该方名**→看似一致）」。两者机制不同：净分驱动 vs leaning 文本匹配，价值之争/罚分场景可分歧（净分赢家未必是 leaning 文本点名方）。
- **影响**：轻量提示的判定依据与文档不符；对用户仅「看似一致/或有不同」软提示、不下硬判，影响小。代码用净分其实比脆弱的文本匹配更稳，属「实现优于文档、但未回写文档」。
- **修复方向**：把 §4.4 改写为「按累计净分最高方对照」，或若坚持 leaning 语义则代码改回文本匹配——二选一对齐口径。

### F5 · 关键动作回路服务缺桌面测试（掌舵 resolve / 后台任务派发·应用·轮询）

- **严重度**：P3
- **类别**：TEST
- **证据**：
  - `services/debate.ts` 的 `decideDebateRound`（辩论掌舵**唯一** resolve 通道）无任何桌面测试驱动（`__tests__` 无引用；仅 `stores/__tests__/execution.test.ts` 测 `debate_round` 决策事件的 fold）。
  - `services/handoff.ts` 的 `dispatchHandoffJob` / `applyHandoffJob` / `getHandoffDiff` 与 `stores/backgroundTasks.ts` 的轮询 `useBackgroundTasksSync` 无测试；仅 `lib/__tests__/handoff-review.test.ts` 测纯函数 `buildReviewRows/buildSelections/countChanges`。
  - `services/interaction.ts` 的 `resolveInteraction`（approval/debate_round/escalate 统一 choke point，含云/sidecar 路由）无直接单测。
  - **对比（已有覆盖，非缺口）**：`runResume` 冷路径 surfacing 有 `resume.test.ts`；审批 store 有 `approvals.test.ts`；`toDebateModel` 质询投影有 `projection.test.ts`；toolResult 有 `ToolResultView.test.tsx`/`diff.test.ts`。
- **影响**：掌舵与后台任务是用户驱动的挂起态推进接缝，其服务层（含 sidecar/云路由分叉、乐观态/权威覆盖、SSE op 履行）属未测路径，回归（如 resolve 载荷字段、轮询节奏、apply 冲突门变更）会静默漏过。
- **修复方向**：补 `decideDebateRound`（断言 body 携 `decision/focus/ask/ask_target`、404 吞掉）与后台任务 dispatch→poll→apply 流的服务测（假 SSE / 假 fsApi），至少锚定动作载荷与冲突门重哈希。

### F6 · 2 方辩论 `ask_target` 依赖后端 side.key 恒为 `pro`/`con`（NEEDS-VERIFY）

- **严重度**：P3（NEEDS-VERIFY）
- **类别**：SEAM
- **证据**：`arena/SteeringPanel.tsx:52-56` 追问定向 chip 的 key 取本轮 `sides[].sideKey`；进行中 2 方由 `projection.ts:286-299`（`twoSide`）把 `sideKey` 定为 `stance`（`"pro"`/`"con"`）。提交时 `ask_target=sideKey`（`services/debate.ts:44-46`）→ 后端按 `side.key` 匹配注入下一轮该方 prompt。**仅读到前端端**：未确认后端 2 方辩论的 `DebateSide.key` 恒为 `pro`/`con`（若 builder/`parse_sides` 用别的 key，则定向追问会静默落到「全场」或错方）。
- **影响**：若 key 空间不一致，用户「追问正方」可能被当成全场或错方（静默、无报错）。正反 clash 高亮依赖同一 pro/con 假设且过 conformance，故大概率一致——但定向追问这条路径未被 conformance/测试覆盖，故标 NEEDS-VERIFY。
- **修复方向**：核对后端 2 方 `DebateSide.key`；若非 pro/con，前端 `twoSide` 的 `sideKey` 应取后端真实 key（而非 stance），并加一条追问定向的端到端/契约用例。
