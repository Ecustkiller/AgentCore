## P2 发现

### P2-1 · SEAM · 因果图子系统建成/单测/API 暴露，但无任何产品消费方

- **证据（producer 端）**：`apps/server/agentcore/runtime/audit/causal.py:15`（`build_causal_graph` 重建 parent/depends_on/inject 三类边）；`apps/server/agentcore/api/routes/conversations/audit.py:39,48`（`include_causal` 查询开关 + `_to_causal_graph`）；`apps/server/agentcore/api/schemas/agent_audit.py`（`AuditCausalGraph/Node/Edge` 响应模型）。
- **证据（consumer 端，已两端确认）**：全仓 `apps/desktop` + `apps/mobile` 源码中 `include_causal` / `causal_graph` / `AuditCausalGraph` **仅**出现在 `node_modules/@agentcore/contract-rest-types/src/api.generated.ts`（生成类型）；`apps/desktop/src/renderer/services/audit.ts:23-30` 的 `fetchTurnAudit` **不传** `include_causal`（默认 false），无任何 `.tsx` 读取/渲染 `causal_graph`；后端唯一调用方是单测 `apps/server/tests/test_audit_causal.py`。
- **一句话影响**：整个因果图能力（用于「同波 worker 输入依赖谁」的并行因果可视化）产品侧不可见，属"写了没人读"的休眠接缝；`docs/06-规划/README.md` 与 `安全权限与治理.md §八` 称"因果图 Phase 1–2 全落地"，与前端零消费存在口径差。
- **修复方向**：二选一——(a) 前端 GraphView/RunAudit 以 `include_causal=true` 拉取并渲染因果边，兑现文档"与 GraphView 同源"；(b) 文档把因果图标注为"后端就绪 · 前端 ⏳"，消除"全落地"漂移。判定前建议确认意图（见 NEEDS-VERIFY-2）。

### P2-2 · DRIFT/TEST · oracle 的 `process` 与运行时 `_accumulate_process` 双实现、无交叉钉死测试，且已在 8KB 结果截断上漂移

- **证据**：运行时 `apps/server/agentcore/runtime/events/sink.py:282-283`（`_accumulate_process` 把 `tool_use_end` 的 `result` 截断至 `_PROCESS_RESULT_CAP=8000`，常量见 `runtime/events/journal_config.py:23`）、`sink.py:197-198`（`_record_history` 同截断）；oracle `apps/server/agentcore/conformance/projection.py:218-227`（`project_turn` 的 `tool_use_end` 分支 `result` **verbatim 不截断**）；事件工厂 `apps/server/agentcore/runtime/events/chat.py:129`（`result=output` 原样，未截断）。无任一测试断言 `EventSink.process_timeline() == project_turn(events)["process"]`（`project_turn` 仅现于 `export.py`/`projection.py`/`tests/test_conformance_projection.py`；oracle 从不喂真实运行时输出）。
- **一句话影响**：`process_timeline()` docstring 自称"live/reload/golden 对齐"，但对 >8000 字工具结果，持久化/重放的 `process` 被截断而 oracle golden（及 live 事件流）不截断 → 三者不一致；且因**无向量覆盖 >8KB**，`pnpm conformance` 无法发现这处已存在的漂移。
- **修复方向**：让 `sink._accumulate_process` 与 `projection.project_turn` 共用同一段 process 折叠逻辑（或 oracle 同步施加同一 cap），并补一条 >8KB `result` 向量 + 一个 `process_timeline()==project_turn()['process']` 的交叉钉死测试，把"三处投影对齐"从人工维护变成机器可抓。

## P3 发现

### P3-1 · BUG/DRIFT · `audit_retention` 用 naive `datetime.now()` 对齐 tz-aware 列，与已修的同族 sweeper 不一致

- **证据**：`apps/server/agentcore/runtime/audit_retention.py:19`（`before = datetime.now() - timedelta(days=settings.audit_retention_days)`，naive 本地时）；列定义 `apps/server/agentcore/db/models/runs.py`（`AgentAuditEvent.created_at` 为 `DateTime(timezone=True)` + server `now()`，即 tz-aware UTC）；对照 `apps/server/agentcore/runtime/suspension_retention.py:35`（`datetime.now(UTC)`，且注释显式"cutoff is tz-aware UTC, matching how ... updated_at is stamped"）。`runtime/session_retention.py:30` 同样是 naive（同类隐患）。
- **一句话影响**：非 UTC 部署下 90 天 TTL 截断点按本地偏移偏移数小时（本机 UTC+8 即约 8h），非数据丢失但与 tz-aware 列/同族 sweeper 姿态不一致。
- **修复方向**：改为 `datetime.now(UTC)`（顺带对齐 `session_retention.py`）。

### P3-2 · BUG · 顺利路径 `audit_drops` 少计 finally 阶段 journal 收尾产生的降级

- **证据**：`apps/server/agentcore/runtime/pipeline/run.py:590`（先 `await audit_recorder.flush()`）→ `:612`（return dict 内读 `"audit_drops": audit_recorder.drops`，此值在 finally 前定格）→ `finally :652`（`journal_writer.flush()` 收尾会再触发 `on_journal_fact_appended` → `recorder.schedule`）→ `:657`（`audit_recorder.flush()` 再排空、可能再 drop）；持久化端 `apps/server/agentcore/conversation/turn_persistence.py:259` 落的是 return 的旧值；resume 路径 `runtime/pipeline/resume/pipeline.py:280-281,352-353,385` 同构。
- **一句话影响**：`turn_metrics.audit_drops` 及 admin `aggregate_audit_drops_for_window` 可能少计回合收尾阶段的审计写降级，遥测轻微偏低（不影响回合正确性）。
- **修复方向**：把 `.drops` 的读取/写入移到 finally 的最终 `flush()` 之后再定格。

## NEEDS-VERIFY

- **NV-1（关联 P2-2）**：8KB 截断漂移是否**用户可见**，取决于前端 reload 走"重放 journal 重折"（journal 存 uncapped → 与 oracle 一致，无感）还是"直接读持久化 `process_timeline`"（capped → 与 live 不一致）。需读桌面/手机 reload 折叠路径确认；若前端一律 re-fold journal，则 P2-2 用户影响降为"仅 conformance 盲区 + 内部投影不一致"。
- **NV-2（关联 P2-1）**：因果图无产品消费方是"设计上后端先行、前端渲染延后"（文档措辞为"可选/按需返回"，未明确承诺前端渲染），还是"接口建了忘接前端"。属产品意图，需人确认后再定按 (a) 补消费 / (b) 改文档口径处置。
