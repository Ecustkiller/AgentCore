## P1

### F1 · Fallback 模型阶梯：文档标 ✅ 已落地，代码已整条移除（含配置/指令死码）
- **类别**：DRIFT（+ 连带 DESIGN 死码，另见 F2）
- **证据**：
  - 权威设计文档仍将「Flash→Pro fallback 阶梯」列为 ✅ 已落地，三处：
    - `docs/03-AI核心/执行引擎架构设计.md:250`「Fallback 模型 | 空响应（首次）/ LLM 硬失败 | ✅ 切 `profile.fallback_model`（Flash→Pro）重跑该轮；gated `settings.engine_fallback_enabled`」
    - `docs/03-AI核心/执行引擎架构设计.md:251`「LLM 硬失败 | ✅ 先走 Fallback 模型重跑一轮；fallback 不可用 / 已用尽则收口」
    - `docs/03-AI核心/执行引擎架构设计.md:255`「空响应 | 连续 2 轮 | ✅ …首次切 fallback 模型重跑，连续第 2 次 → DEGRADED」；§四引言 `:234` 同样声称「空响应 degraded + fallback 升档 / LLM 硬失败 fallback 阶梯」。
  - 代码里该机制**不存在**：
    - `apps/server/agentcore/runtime/engine/round.py:213` `decide_no_tool_round` 恒以 `controller.empty_response_action(fallback_available=False)` 调用 → `Intervention.FALLBACK` 在生产路径永不产生。
    - `apps/server/agentcore/runtime/engine/governance.py:137` `decide_llm_failure` 显式丢弃 `profile/active_model/upstream_error`（`_ = (…)`），直接返回 `DEGRADED/ERROR`，无任何换模型重跑。
    - `apps/server/agentcore/runtime/engine/directive.py:24` `SwitchModel` 指令**无任何产出方**；`loop.py:440` 的 `case SwitchModel` 分支因此不可达。
    - `apps/server/agentcore/llm/profiles.py:21-28` `ProfileParams` 无 `fallback_model` 字段（全仓 `fallback_model` 无定义）。
    - `apps/server/agentcore/config/engine.py:10` `engine_fallback_enabled` 定义后全仓无读取点。
  - 测试已按「无 fallback」新行为改写并反向锁定：`apps/server/tests/test_engine_governance.py:833-844`（`test_llm_failure_errors_without_model_escalation` 断言 `provider.models == ["primary"]`）、`:765-773`（`test_empty_response_degrades_without_model_switch`）、`:847-889`。→ 说明**代码是有意为之的现状，文档是滞后**。
- **影响**：权威文档把一项核心韧性机制误标为已实现；任何据「空响应/硬失败会自动升档 Pro」做能力假设或排障的人都会被误导（实际只是「同模型重试一轮 → DEGRADED/ERROR」）。
- **修复方向**：把 §四收敛表 3 行与引言由「✅ fallback 阶梯」改写为现状（空响应=同模型重试至阈值后 DEGRADED；硬失败=直接 DEGRADED/ERROR），并同步删除随之而来的死码（见 F2）；若确要恢复 fallback 则另立设计。

## P2

### F2 · 移除 fallback 后遗留的一批死码/失效配置
- **类别**：DESIGN（补丁/裁剪未清尾）
- **证据**：
  - `apps/server/agentcore/runtime/engine/directive.py:24,60` `SwitchModel` 密封联合成员 + `loop.py:30,440` 的 import 与 `case SwitchModel` 分支，全链无产出方 → 不可达。
  - `apps/server/agentcore/runtime/loop_controller.py:310-324` `empty_response_action` 的 `fallback_available` 形参与 `Intervention.FALLBACK` 分支，生产仅以 `False` 调用 → FALLBACK 分支死代码。
  - `apps/server/agentcore/config/engine.py:10` `engine_fallback_enabled` 配置项无读取点。
  - `apps/server/agentcore/runtime/engine/governance.py:130-142` `decide_llm_failure` 保留 `profile/active_model/upstream_error` 形参却整体 `_ =` 丢弃。
- **影响**：暴露出「像是有 fallback」的假接口面，后续有人误按其重新接线易引入 bug；`_` 丢弃的形参也让签名误导读者以为参与决策。
- **修复方向**：随 F1 一并删除或（若恢复功能）重新接线；至少给死分支/死配置加显式退役注记。

### F3 · fallback 的单测仍绿，但锁的是生产已不走的死分支
- **类别**：TEST
- **证据**：
  - `apps/server/tests/test_loop_controller.py:171,190,193` 断言 `empty_response_action(fallback_available=True) is Intervention.FALLBACK` / `CONTINUE` —— 但生产恒传 `False`（F1），该路径整体死。
  - `apps/server/tests/test_engine_governance.py:696` 段标题仍写「B2: empty-response degraded + fallback model」、辅助类/夹具沿用 `fallback`/`_FailingProvider` 命名，实际断言却是「不换模型」。
- **影响**：覆盖率与命名给人「fallback 有测试保护」的错觉，实际保护的是隔离态的死分支；真出问题（误以为 fallback 生效）测试不会红。
- **修复方向**：删除或标注「仅隔离态、生产不经此」；把 governance 段命名改为「同模型重试→DEGRADED/ERROR」以名实相符。

## P3

### F4 · WaveScheduler BIND 边界：宿主若 `PROCEED` 而未定稿会死循环（NEEDS-VERIFY，当前被宿主约定遮蔽）
- **类别**：BUG（潜伏）
- **证据**：
  - `apps/server/agentcore/runtime/runs/wave.py:219-229`：BIND 边界在 `not running` 时 `_bind_pending` 命中即 `await on_boundary(BIND,…)`；`PROCEED` 不改任何状态。若宿主返回 `PROCEED` 却未把该节点的 `bind_after_deps` 清掉，则 `_bind_pending`（`wave.py:503-526`）下一轮再次命中同一节点 → 无限重触发（忙等/回合卡死）。docstring `wave.py:216-218` 声称「PROCEED…no spin」只在「宿主必定稿或必 YIELD」前提下成立，调度器自身无护栏。
  - 之所以现网不触发：唯一宿主 `apps/server/agentcore/tools/builtin/delegate/boundary.py:56-58` 对 BIND/SCOPE **恒返回 `YIELD`**（软暂停交回 CEO），从不 `PROCEED`。
- **影响**：契约耦合——调度器的「不自旋」保证由宿主约定兜着；将来新增/替换宿主一旦在 BIND 处 `PROCEED` 而未定稿，即活锁。
- **修复方向**：调度器在 BIND `PROCEED` 后若该节点仍 `bind_after_deps` 未清，应视为无进展（记一次告警并当作不可推进/收口），而非无条件复触发。

### F5 · WaveScheduler.run 不自校验拓扑，坏计划会静默丢节点（NEEDS-VERIFY，当前被构建期校验遮蔽）
- **类别**：DESIGN（防御缺口）
- **证据**：
  - 环/悬空依赖仅在**构建期**由 `apps/server/agentcore/runtime/runs/plan.py:49-76` `RunPlan.waves()` 拦截（`_dag_plan` 调 `plan.waves()`、`build_added_nodes` 组合图预检）；`WaveScheduler.run`（`wave.py`）本身从不调 `waves()`。
  - 若一张带环/悬空 `depends_on` 的计划绕过构建校验直达 `run()`（如未来的直接构造、或异常的 resume 重建种子），`_select_ready` 永远选不出就绪节点，`wave.py:251-252` `if not running: break` 直接返回，环内节点**既不 COMPLETED 也不 SKIPPED**，静默从 `completed` 消失。
- **影响**：当前所有构造路径都校验，故为潜伏；但一处漏校验就会变成「worker 静默不产出、无报错」的难查故障。
- **修复方向**：`run()` 入口加一次廉价 `plan.waves()`/可达性自检（失败即显式失败或全标 SKIPPED），或在契约层显式声明该前置条件。

### F6 · 单轮多个终止工具时只认第一个，SUSPEND 与 HANDOFF 同轮存在语义竞态（边界）
- **类别**：BUG（边界/低触达）
- **证据**：
  - `apps/server/agentcore/runtime/engine/tool_exec.py:206` `terminal = next((t … if t is not None), None)` 取**首个**终止结果；`loop.py:345` `paused = terminal.effect is ToolEffect.SUSPEND` 仅据这首个终止结果判定是否 PAUSED。若同一轮既有 HANDOFF/INTERACT 终止工具、又有 SUSPEND（如 ask_user 已在 `execute` 内落挂起帧），则调用顺序决定回合是收口还是暂停，另一终止语义（如已落 `paused_turns` 帧）可能悬空。
  - 触达低：CEO 持 ask_user（SUSPEND）但不持 handoff（worker 专属）；worker 持 handoff 但不持 ask_user；delegate 的 checkpoint 也走 SUSPEND，与 ask_user 同为 SUSPEND→两者皆 paused，无冲突。故需要某 agent 同时持「SUSPEND 类」与「非 SUSPEND 终止类」两工具才可触发。
- **影响**：模型异常同轮双终止调用时，可能出现「回合已 HANDOFF 收口却残留一条挂起帧」之类不一致；正常工具装配下基本不可达。
- **修复方向**：定义终止优先级（SUSPEND 优先）或对「一轮多终止」显式拒绝/告警。
